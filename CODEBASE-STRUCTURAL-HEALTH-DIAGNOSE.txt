[M66이 언급한 "1,248개"의 정체 재확인]
  M66 원문은 "tests/ 디렉토리 자체가 1,248개 파일(+__pycache__ 1,043개)"라고
  기록했으나, 이번 실측으로 이 수치가 **소스 파일 수가 아님**이 확인됨:
    git 추적 .py 1,046개 + 잔존 테스트 산출물 .db 파일 192개
    + .db-journal 임시파일 10개 ≈ 1,248개 (거의 정확히 일치)
  즉 소스가 1,248개로 불어난 게 아니라, 소스 1,046개에 테스트 실행 중
  정리 안 된 SQLite 산출물(.db/.db-journal, 모두 git 미추적) 200여개가
  디스크 스냅샷 집계에 섞여 들어간 결과다. "1,248"을 소스 규모로 오인해
  향후 리팩터링 스코프를 잡으면 안 됨 — 실제 소스 규모는 1,046개.

[M66 현상과 비대화의 관련성]
  M66이 실측한 병목(디렉토리 1개로 넘기면 12,378개 테스트를 35초/2.8ms당
  테스트, 같은 대상을 개별 CLI 인자 140개로 나열하면 1,946개 테스트에
  72~74초/37ms당 테스트 — 13배 느림)은 pytest가 "인자 개수 × 디렉토리
  크기(파일 개수)"만큼 반복 판정(is_file() stat 호출)을 수행하는 구조적
  특성 때문이며, **총 라인수(229,501줄)와는 무관**하다. 즉 "파일 개수"는
  관련 있지만("디렉토리가 커질수록 개별 인자 나열의 페널티가 커짐"),
  "라인수 비대화"와는 별개 축이다 — tests/ 파일이 얇든 두껍든 pytest
  인자 나열 방식을 쓰는 한 개수에 비례해 느려진다.
