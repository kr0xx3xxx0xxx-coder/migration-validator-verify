============================================================
0. 종합 요약 / 권장 착수 순서
============================================================

당초 사용자가 최고 심각도로 의심한 시나리오("2단계 COUNT 실행 중 1단계 SQL 재실행")는
실측 결과 **안전**했다(자동 abort + 세션버전 무효화, 항목4-1). 그러나 조사 과정에서
**그 역방향(4단계 실행 중 2·3단계 조작)에서 동급 이상의 실측 오염**이 확인됐고,
항목2에서는 **다중 GROUP BY 세트 실행 자체가 서로 다른 WHERE 조건으로 뒤섞여 실행되는
오염**을 실측으로 확정했다. "치명"으로 분류할 저장 데이터 오염(서버 DB에 영구 반영)은
발견되지 않았으나(단일 실행 결과는 persist=False), 화면/세션 상태 오염과 불필요한 실
DB 재스캔은 다수 확정됐다.

권장 착수 순서(위험 대비 효과, 회귀 범위 기준):

1. **[최우선] 다중 GROUP BY 세트 루프(`_runExecutePlanSets`, ui/tabler_renderer.py:26666)
   의 신선도 방어 추가** — signal 누락으로 취소 불가 + 세트마다 라이브 DOM/전역객체
   재조회로 세트 간 실행 조건이 뒤섞이는 실측 오염(항목2-1-나, 항목4-7) 동시 해결.
   저위험·좁은 회귀면, 반나절.
2. **[최우선] 4단계 실행(`/execute`, `/execute/set`) 멈춤 버튼 신설** — 서버 취소
   로직(CancelToken)은 이미 완성돼 있고 UI만 없음(항목1). 클라이언트 전용 변경으로
   서버 DB 쿼리까지 실측으로 죽는 것을 확인. 반나절~1일.
3. **[우선] 실행 중 선택 컨트롤(체크박스·관리컬럼·조합) 잠금 신설** — 오버레이 방식
   (disabled 속성 대신 pointer-events 차단)으로 항목2 E·F 결함(실행 중 클릭 시 방금
   완료된 결과에 도달 불가, 재검증 중 클릭 무통보 유실)을 게이트 로직 변경 없이 해소.
   0.5~1일.
4. **[중간] 4단계 실행 중 2·3단계 재실행 시 무효화 롤백 차단** — 늦게 끝난 실행이
   무효화 상태를 되돌리는 문제(항목4-5,6). `_singleClearStage5ResultStale()` 무조건
   호출 조건 좁히기. 0.5일. 단, "무효화 롤백으로 되살아난 완료 플래그가 /single/save
   까지 도달 가능한가"는 이번 조사에서 다루지 못한 후속 확인 필요 사항.
5. **[선택] 2단계 COUNT 카드에 기준 SQL 표시/불일치 경고** — 항목4-3(SQL만 수정,
   재실행 안 함) 결함 보강. 중위험(계약 테스트 리터럴 영향 검토 필요).
6. **[보류] 5단계 즉시중단 死코드(cancel_token) 정리, 1·3단계 멈춤 버튼 신설,
   `_mvComputeWfStates` 직접 수정, 2·3단계 진행중 배지 표시 확대** — 비용 대비 효과가
   낮거나 공유 핵심 함수 변경이 필요해 위험이 크다. 각 절 본문 권고 참조.

핵심 발견 3가지:
1. 2·4단계(단일)는 서버 취소 로직이 이미 완성돼 있고 당길 버튼만 없다. 실측: 브라우저
   fetch abort() 호출 0.55초 후 서버측 PG 쿼리(pg_stat_activity 기준)가 실제로 소멸.
   즉 클라이언트 전용 변경만으로 서버 DB 쿼리까지 실제로 죽는다.
2. 다중 GROUP BY 축(2축 이상) 실행은 /execute/set을 타는데 여기만 취소 배선이
   통째로 빠져 있다. 가장 오래 걸리는 경로(세트마다 최대 60초 상한 x N)인데 이탈해도
   서버가 계속 돈다.
3. 5단계 "실행 중단" 버튼은 청크 경계(기본 50,000행)에서만 멈추고, 즉시 DB 쿼리를
   끊는 코드(cancel_token 경유)는 존재하지만 실측상 job dict에 cancel_token 키가 한
   번도 채워지지 않아 절대 실행되지 않는 死코드다.

항목 3. 탭 라벨 유지 — 실행 중 탭 이동/복귀 시 라벨 상태
============================================================

결론: 라벨은 DOM 직접 갱신이 아니라 상태 재계산 방식이다. _renderSingleStepNav
(:6430)는 매 호출마다 _mvSyncWf(:6164) -> _mvComputeWfStates(:6115)로 워크플로
상태를 처음부터 다시 계산하고 :6486-6494에서 배지 문구를 결정한다:
  RUNNING -> badge='진행중'(또는 일시중지)
  SUCCESS -> badge='완료'/'현재'
  그외    -> badge='대기'/'현재'
_mvUpdateStepNavInPlace(:5526)가 노드를 재사용하며 속성만 갱신하므로 재렌더로 라벨이
유실되는 구조적 결함은 없다. 문제는 "무엇을 RUNNING으로 볼 것인가"의 커버리지다.

RUNNING을 세우는 곳은 4단계 통계검증 하나뿐 — _mvComputeWfStates에서 실행 중 신호를
읽는 것은 _executeInProgress 단 하나(:6147-6149). _countInProgress·
_revalidateInProgress·runGenerate(플래그 자체가 없음)는 워크플로 상태에 전혀
반영되지 않는다.

| 실행 | 해당 탭 보는 중 | 다른 탭 이동 시 | 복귀 시 |
|---|---|---|---|
| 2단계 COUNT(/count in-flight) | 현재(진행중 아님) | 대기 | 현재 |
| 3단계 재검증 | 현재 | 대기/완료(직전 상태) | 현재 |
| 4단계 SQL 생성(1차) | 현재(진행중 아님) | 대기 | 현재 |
| 4단계 통계검증(2차) | 진행중 | 진행중 유지 | 진행중 |

S1 실측(/count 12초 지연, countInProgress:true):
  실행 중(2단계 탭)  query:완료, count:현재
  1단계 이동 후      query:현재, count:대기   <- 진행 중인데 '대기'
  2단계 복귀 후      query:완료, count:현재
즉 2단계는 애초에 '진행중' 라벨이 존재하지 않고 다른 탭에서 보면 '대기'로 보인다.
보조 신호: 하단 커맨드바는 복귀 후에도 "COUNT 실행 중…(disabled)"를 유지(_mvCmdBarLocks
덕분) — 탭 배지와 커맨드바가 서로 다른 사실을 말한다.

4단계는 유지되지만 "체크박스 한 번"에 무너진다 — 항목2(다)의 재계산 구조 때문에,
실행 중이라도 상위 단계(candidate)가 PENDING으로 내려가면 execute의 RUNNING 판정
자체에 도달하지 못한다(실측상 "진행중" -> "잠김"으로 뒤집힘). 탭 라벨 유지의 실제
취약점은 "이동/복귀"가 아니라 "실행 중 상위 단계 무효화"다.

종합 심각도: [높음]. 사용자가 제시한 핵심 시나리오("2단계 COUNT 실행 중 1단계

래핑해 요청/응답 시각·요청시점 SQL·세션버전·workflow_token 전부 기록. 실 DB: Neon PG
migration_source.src_orders_a(100만행) -> migration_target.tgt_orders(100만행).

숫자 즉시 판별 가능하게 설계.

4-2. "탭 이동만" vs "데이터 수정" — 트리거 분리 결론
| 케이스 | 조작 | 결과 |
|---|---|---|
| a1 | COUNT 실행 중 1단계 탭 이동만 | 정상, COUNT 1,000,000 정상 렌더, sqlStale=false |
| a3 | COUNT 실행 중 1단계 이동+SQL수정만(재실행 안 함) | 문제 발생(4-3) |
| a2 | COUNT 실행 중 1단계 이동+SQL수정+재실행 | 안전(4-1) |
결론: 탭 이동은 트리거가 아니다. 진짜 트리거는 "원본 데이터(SQL)의 수정"이다. 그리고
수정 후 재실행까지 하면 오히려 안전해지고, 수정만 하고 방치할 때가 가장 위험하다
(가드가 runAnalyze 진입에만 걸려 있기 때문).
부수 확인(케이스d): 전진 방향 교차는 구조적으로 불가능 — /count 실행 중 3단계 탭
클릭 시 showSingleStep(:6292)의 _mvWfStageAccessible 가드가 "선행 단계를 먼저
완료하세요(잠긴 단계로 이동 불가)"로 차단. 따라서 위험면은 "진행 중 단계N + 이미
완료된 이전 단계M(<N) 재실행"으로 한정된다.

4-3. 케이스a3 — COUNT 실행 중 SQL만 수정(재실행 안 함) [중간~높음]
실측: /count 응답 200, src=1,000,000/tgt=1,000,000(SQL_A 기준). 응답 도착 시점
#sqlInput은 이미 SQL_B(정답이라면 125,000). 화면: "목적건수 1,000,000·원본건수
1,000,000·차이0·상태●정상"+"COUNT 일치…목적지 적재율100.0%". countState='OK'.
2단계 COUNT 카드 자체에는 어느 SQL 기준인지 표시가 전혀 없다. 유일한 경고는 1단계
pane의 #singleStaleBanner("SQL이 변경되었습니다")이며 사용자가 2단계 탭에 있으면
안 보인다. 그 상태로 3단계 진입 허용됨(탭: 1=재검증필요,2=현재,3=대기,4·5=잠김).
서버 단계 가드가 최종 방파제: runGenerate가 migration_sql에 DOM의 현재 SQL을
실어(:26409) 토큰 바인딩 SQL 해시와 달라져 409 SQL_CHANGED로 차단(케이스e에서 동일
코드로 실증). 중요: 이 현상은 동시성 없이도(COUNT 완료 후 SQL 수정) 동일 재현되는
기존 결함이며, 동시성은 "응답이 수정 이후에 도착"해 오인 확률을 높이는 역할.

4-8. 서버측 가드 재확인 — 메모리 기록 대비 정정
인프로세스 실측:
  재분석(SQL 변경) 후 옛 토큰으로 /generate 검증 -> 통과(=옛 토큰 유효)
  직전 토큰을 동봉한 재분석 후 -> INVALID_WORKFLOW_TOKEN
  동일 SQL 재분석 후 -> INVALID_WORKFLOW_TOKEN
메모리의 "재분석은 직전 토큰을 즉시 폐기한다"는 조건부로만 참이다.
issue_token(:199)이 직전 토큰을 pop하려면 요청에 workflow_token이 실려 있어야 하는데
UI는 fetch 직전 reset에서 토큰을 null로 지우므로 항상 빈 문자열을 보낸다(실측: a2·e
두 케이스의 2차 /analyze 요청 reqTok:""). 따라서 SQL이 바뀐 재분석에서는 ctx_key가
달라져 옛 토큰이 서버 메모리에 계속 유효하게 남는다(LRU 512개 축출 전까지). 동일 SQL
재분석은 같은 ctx_key generation 증가로 정상 무효화된다.
/count는 validate("count",req,token_required=False)(count_route.py:47) — 토큰이
있으면 엄격 검증하나 요청 시작 시점 1회뿐이며, 완료 시 record_outcome(:371)은
generation이 어긋나면 조용히 no-op할 뿐 응답을 stale로 표시하지 않는다. 클라이언트는
그 사실을 알 방법이 없다.
서버 in-flight 방어(begin_execution)는 execute_route.py:85, execute_set_route.py:77,
single_run_route.py:84의 stage 문자열별 키뿐 — 다른 stage 간 상호 차단은 없음
(케이스b에서 /execute 진행 중 /count가 정상 통과함으로 실증, 메모리 기록과 일치).

4-11. 심각도 정리
| 시나리오 | 판정 | 등급 |
|---|---|---|
| 2단계 COUNT 실행 중->1단계 SQL수정+재실행 | abort+세션버전 무효화로 안전 | 낮음 |
| 2단계 COUNT 실행 중->1단계 탭 이동만 | 이상 없음 | 낮음 |
| 2단계 COUNT 실행 중->SQL수정만(재실행X) | 옛SQL기준 COUNT가 정상/일치로 무표시 렌더+3단계 진행 허용, 최종방어는 서버409 | 중간~높음 |
| 2<->3(COUNT중 3단계) | 전진 탭 잠금으로 구조적 차단 | 없음 |
| 4단계 실행 중->2단계 COUNT 재실행 | 가드무, 동시DB실행, 무효화후에도 세트계속실행, 무효화 롤백 | 높음 |
| 4단계 실행 중->3단계 선택 변경 | 해제한 축으로 실행 지속, 무효화 롤백, stale배너 미표시 | 높음 |
| 4단계 실행 중->1단계 재분석 | 루프가 새세션에서도 서버호출 지속(409로 저지), 진행문구·플래그 잔존 | 중간 |
| 서버 토큰 폐기 갭(옛 토큰 잔존) | UI는 토큰을 버리므로 직접 악용 경로 없음, 심층방어 결손 | 중간 |
저장 데이터 오염은 미확인 — /execute는 persist=False 고정, 공식 저장은 /single/save
뿐이라 위 오염은 화면/세션 상태 오염+불필요한 실 DB 스캔에 머문다(그래서 "치명"이
아닌 "높음"). 다만 무효화 롤백으로 되살아난 singleValidationExecuted=true가 이후
"동일조건 완료본 재사용" 경로를 통해 저장까지 이어질 가능성은 남아 후속 조사 항목으로
분리 권장(이번 조사 범위 밖).
