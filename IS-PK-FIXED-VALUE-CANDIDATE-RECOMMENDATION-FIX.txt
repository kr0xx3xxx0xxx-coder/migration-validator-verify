1. 지침 요구사항 대비 이행 결과
================================================================================
요구1 is_pk 실값 배선(JOIN/파생 경로 포함, 새 PK 조회 로직 발명 금지)
   → 이행. `get_adapter(db_type).fetch_key_metadata(conn_info, bare_table)` 를 그대로 재사용
     했다(`_build_target_pk_evidence` / `agg_diff_route` 와 동일 호출·동일 bare 테이블명 규약).
     새 카탈로그 SQL·새 엔드포인트 없음. JOIN/파생 경로는 `_cmn_fetch_tgt_col_meta` → tgt_map
     → CandidateInputBuilder → from_tgt_map 으로 값이 흘러 실제로 채워짐을 실측 확인(§3 a2/d2/e2).

요구2 복합 PK 는 is_pk=True 로 만들지 말 것 + is_composite_key_member 별도 필드
   → 이행. `'is_pk': _km_is_pk and not _km_comp`. 복합 PK 구성원은 is_pk=False 를 유지하고
     `is_composite_key_member: true` (+`key_column_count`)를 **값이 있을 때만** 덧붙인다
     (VARCHAR2 char_used/data_length 확장과 동일 규약 — 복합키 없는 테이블 dict 는 키 개수까지
     불변). 이 구분은 이미 코드베이스에 있는 규약과 동일하다
     (db_statistics_service._apply_key_metadata_adjustments: `(is_pk or is_unique) and not
      is_composite` → IDENTIFIER_LIKE / `is_composite` → COMPOSITE_KEY_MEMBER).
   ※ 지침대로 이 신규 필드를 판정에 쓰는 소비처는 만들지 않았다. 단 하나의 예외가
     candidate_engine 의 새 게이트인데, 이는 "복합 PK 를 배제하지 않기 위한 안전장치"로만
     쓰인다(값이 True 면 게이트를 통과시킴 — 배제를 늘리지 않고 줄이는 방향).

요구3 단일 컬럼 PK 를 GROUP BY 후보에서 배제(risk_flags 또는 제외 사유 명시) / SUM 정책 불변
   → 이행. 다만 **진단서가 열거하지 않은 누락 경로가 하나 있어 그곳을 함께 막았다**(§2-B).
     배제 사유는 신규 문구를 만들지 않고 기존 `_gb_non_candidate_reason` 의 PK_IDENTIFIER
     ("PK/유니크 식별자 — 행마다 고유값이라 그룹 기준 부적합")가 그대로 표기된다.
     SUM 쪽은 코드를 한 줄도 건드리지 않았고, 실측에서도 SUM 후보·자동선정 SUM·프런트
     `_sumPolicyExcl` 판정 모두 변화 0건이었다(§4).

요구4 진단서의 '체감변화 12곳' 각각 실측 확인 → §4 에 12곳 전수 기록.

[2-A] services/db_query_service.py  `_cmn_fetch_tgt_col_meta`
  ① 어댑터 키메타 1회 조회를 추가(캐시 조회 이후 · 컬럼 메타 SQL 실행 이전).
     조회 실패·미지원 방언은 `{}` 로 보수 폴백 — 'PK 없음'으로 단정하지 않고 기존 동작 유지.
  ② `_entry` 조립부의 `'is_pk': False` 고정값을 실값으로 교체.
       is_pk                    = (어댑터 is_pk) AND NOT (복합키 구성원)
       is_composite_key_member  = 복합 PK 구성원일 때만 True 로 추가
       key_column_count         = 위와 동일 조건에서만 추가
  ③ docstring 에 새 계약 명시.
  · [D8-6] batch 메모이즈와 자연 정합 — 캐시에 PK 포함본이 담긴다(캐시 갱신 로직 무변경).
  · 성능: 목적지 테이블당 카탈로그 쿼리 1회 추가. 진단서 §6-3 이 지적한
    `_build_target_pk_evidence` 와의 중복 조회(요청당 2회)는 이번 범위에서 통합하지 않았다(§7).

[2-B] services/candidate_engine.py  Step 3 (시맨틱 사전 전용 후보) DIMENSION 분기
  ★ 진단서 §2 에 없던 누락 경로다. 진단서는 is_pk 게이트로 A-1(NUMBER→SUM)/A-2(DATE_TIME→GB)/
    A-3(저카디→GB) 세 관문만 열거했으나, 실제로는 **Step 3 의 DIMENSION_* → GROUP BY 분기에
    키 게이트가 없다**. 그래서 코드성 단일 PK(DEPT_CD → DIMENSION_ORG, CODE → DIMENSION_CODE)는
    is_pk 를 실값으로 채워도 여전히 GROUP BY 후보로 생성됐다.
    실측으로 확인(d2/e2: is_pk=True 인데 후보 목록에 잔존) 후 게이트를 추가했다:
        if cm.get("is_pk") and not cm.get("is_composite_key_member"): continue
  · `not is_composite_key_member` 를 함께 보는 이유는 §2-C 에 기재(회귀 실측 근거).
  · SUM(MEASURE_*) 분기는 건드리지 않았다 — GROUP BY 배제만 이번 범위.

[2-C] services/metadata_provider.py  from_tgt_map / from_pg_stats (2개소)
  복합키 구성원 사실을 normalized_metadata 로 전파한다. **is_pk 값 자체는 손대지 않아**
  기존 관문(`not is_pk`)의 동작은 완전히 불변이다.
  · 필요했던 이유(실측 근거): 단일테이블 SQL 은 `from_pg_stats(_pg_stats, _key_meta, ...)` 로
    **원본** key_metadata 를 싣는데, 오라클 어댑터는 복합 PK 구성원에게도 is_pk=True 를 준다.
    §2-B 게이트를 is_pk 만으로 두면 b1(복합 PK 단일테이블)에서 CO_CD 가 GB 후보에서 소멸했다
    (중간 측정에서 실제 재현: GB후보 2 → 1). 복합키 신호를 전파해 게이트를 좁혀 해소했다.
  · 키는 **참일 때만** 추가한다(§6 참조 — 무조건 추가하면 provider parity 가 깨진다).
