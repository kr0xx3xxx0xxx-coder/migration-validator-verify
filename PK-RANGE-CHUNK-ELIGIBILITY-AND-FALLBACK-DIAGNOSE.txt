1-7. 사용자 가정("PK=인덱스=이미 정렬됨")이 코드에 반영돼 있는가 — **가정만 있고 검증은 없다**

  · `pk_indexed` 를 채우는 유일한 출처는 화면이다(`ui/grid_helpers.py:_mvDerivePkProfile`).
    그 함수의 **모든 반환 분기가 `pk_indexed` 를 PK 존재 여부와 동일하게 취급**한다:

      L904  return { has_pk:true, pk_kind:'COMPOSITE',       pk_indexed:true, ... }
      L908  return { has_pk:true, pk_kind:k1,                pk_indexed:true, ... }
      L912  return { has_pk:true, pk_kind:'SINGLE_NUMERIC',  pk_indexed:true, ... }   /* 물리 PK 는 인덱스를 수반한다 */
      L919  return { has_pk:true, pk_kind:'COMPOSITE',       pk_indexed:true, ... }
      L925  return { has_pk:true, pk_kind:kind,              pk_indexed:true, ... }

    즉 PK 가 있으면 `pk_indexed=true`, 없으면 `has_pk=false` 라서 조건 자체가 무의미해진다.
    **`pk_indexed=true & has_pk=false` 조합은 발생할 수 없고, 반대도 없다.**

  · 인덱스 카탈로그를 실제로 조회하는 코드는 운영 경로에 **0건**이다
    (`pg_index`/`pg_indexes`/`USER_INDEXES`/`ALL_INDEXES`/`sys.indexes` 전수 검색 결과 없음.
     `ALL_TAB_COL_STATISTICS`·`pg_stats` 는 컬럼 통계용이지 인덱스 확인이 아니다).

  · 가정 자체의 타당성: PG·오라클 모두 PK 제약은 고유 인덱스를 자동 생성하므로
    "물리 PK 가 있으면 인덱스가 있다" 는 **대체로 참**이다. 위험한 것은 그 다음 두 전제다.
      (a) 인덱스가 **쓰이는가** — 원본이 CTE/JOIN/윈도우로 감싸지면 청크 술어가 하강하지 않아
          매 청크마다 원본 전체 정렬이 재실행된다(백로그 P1, 실측 배율 1.03→1.46배·빈 청크도 0.343s).
      (b) 인덱스 순서가 **비교 의미와 같은가** — 문자 PK 는 인덱스가 있어도 문자 정렬이라
          merge-join 의 'PK 오름차순' 전제가 깨진다(백로그 S2 축 B, 5만행 청크 1개에서 역전 4,500회).
          이 축은 2026-07-29 `PK-RANGE-CHUNK-SORT-ORDER-ALIGNMENT-FIX`(934c293)로 해결됐다.

  ▶ 결론: 사용자 가정은 코드에 **반영돼 있으나 검증되지 않는다.** 정합성 위험은 S2 로 이미 해소됐고,
    남은 위험은 성능 축(P1)이다.

4. HASH_BUCKET 은 이 상황의 대안이 되는가 — **되지 않는다**(두 계층 모두)
════════════════════════════════════════════════════════════════════════════

4-1. 전수 계층 HASH_BUCKET_COMPARE — **엔진 자체가 없다**

  `services/strategy/strategy_models.py:36-39`
    # 실제 구현되어 자동 실행 가능한 전수 전략. Phase 4-B 에서 PK_RANGE_CHUNK_COMPARE 엔진 구현 → AVAILABLE(§7).
    # PARTITION_BUCKET/HASH_BUCKET 은 여전히 미구현(PHASE4_B_REQUIRED 유지).
    AVAILABLE_COMPARE_STRATEGIES = frozenset({DIRECT_STREAM_COMPARE, SAMPLE_ONLY_EARLY_STOP,
                                              PK_RANGE_CHUNK_COMPARE})

  → HASH_BUCKET_COMPARE 는 `IMPL_PHASE4_B_REQUIRED` → `is_auto_runnable()` False.
    설령 `hash_bucket_available=True` 를 보내도 계획에만 뜨고 실행되지 않는다.

4-2. 진단 드릴다운 HASH_BUCKET — SQL 빌더는 구현됐으나 **PG↔PG 조합에서만 가능**

  구현 확인: `services/diagnosis/strategies/hash_bucket.py:102 build_hash_bucket_agg_sql`
             실호출 `services/diagnosis/multi_scope.py:552-554`

  제약 1 — same-DBMS 한정(영구 차단):
    `services/diagnosis/hash_contract.py:159-160`
      if s != t:
          return None, HR_HASH_CROSS_DBMS           # 혼합 방언 — 영구 차단(정합성)
    사유(L145-149): 방언 간 canonical 발산 — PG `trim_scale(x::numeric)::text` vs 오라클 `TO_CHAR(x,'TM9')`,
    빈문자열 PG `'S:0:'` vs 오라클 `''=NULL → 'S#N'` → 같은 논리값이 다른 bucket → **거짓 불일치 대량 발생**.
    → 지침에서 확인 요청한 "same-DBMS 제약이 추가로 걸리는가" = **예, 걸린다.**

  제약 2 — 등록 방언이 postgresql 하나뿐:
    `services/diagnosis/hash_contract.py:118-120`
      # oracle 은 후속 단계에서 ("services.diagnosis.dialects_hash.oracle", "OracleHashContract") 로 등록한다.
      _HASH_CONTRACTS = {
          "postgresql": ("services.diagnosis.dialects_hash.postgresql", "PgHashContract"),
      }
    → **오라클↔오라클도 `HR_HASH_CONTRACT_NA` 로 차단된다.** 현재 실질 가용 조합은 PG↔PG 뿐.

  제약 3 — 계층이 다르다: 이건 '전수 비교' 가 아니라 '불일치 그룹을 좁히는 진단' 이다.
    라우터(`services/diagnosis/strategies/router.py:49-51`)에서 문자/UUID 키만 남으면
    `ROUTE_HASH_BUCKET` 로 가는데, 주석에도 "문자/UUID 키만 → 해시 구간 필요(**미구현**)" 로 남아 있다.

  ▶ 종합: 사용자가 "HASH_BUCKET 이 PK 정렬에 의존 안 하는 대안" 으로 이해한 것은 **설계 의도로는 맞지만
    현재 코드에서는 복합/비숫자 PK 상황의 실행 가능한 대안이 아니다.** 오라클 환경(현 실 DB 픽스처)에서는
    전수·진단 양쪽 모두 영구 불가다.

5-1. 실제로 걸리는 장치

  ① 표본 preflight 게이트  [agg_diff_route.py:344 `_run_sampling_gate`]
     전체 merge 시작 전 표본으로 EARLY_STOPPED 판정 시 전체 merge 미시작(대표 표본만 저장).

     5만행 고정 상한 → (~5만 동기 / 5만~상한 비동기 job / 상한 초과 deferred 명시 고지).

  ⑤ Source/Target 동시 조회  [agg_diff_route.py:104 `_parallel_read_decision`]

5-2. **없는 것 — 규모 기반 사전 HOLD 게이트가 없다**

  · `_resolve_execution_strategy` 는 `_unique_native_key` 가 서면 **L46-48 에서 즉시 반환**하므로
    `choose_compare_strategy`(예상 전체시간·resume 필요성 판정)를 **호출조차 하지 않는다.**
    → 복합/문자 PK + 수억행이면 규모 판정 없이 곧장 DIRECT merge 로 들어간다.
  · 조기중단 임계에 도달할 때까지는 전량 스트리밍 merge 를 그대로 수행한다.
    불일치가 임계 미만이면(= 대부분 정상인 대형 테이블) 끝까지 다 읽는다.
  · 레코드 수집 HARD CAP 500 은 여전히 미해결(백로그 P10) — 5,000만행에서 확보율 0.02%.

  ▶ 즉 "대량 + 복합/비숫자 PK" 조합의 실질적 방어선은 **조기중단(②③) 하나뿐**이고,
    구조적 사전 차단은 없다.

6-3. 청크 개수 폭증의 실제 심각도 — "대량이면 위험" 은 절반만 맞다

  · **오늘 5,000만행 테스트에서는 관측되지 않았다.** 청크 경로에 진입하지 못했기 때문이다
    (오라클 픽스처가 문자 PK → numeric_pk=false → DIRECT_COMPOSITE_PK, §3 실측 근거).
    즉 5,000만행 실측은 청크 불균형 문제에 대해 아무 증거도 제공하지 않는다.

  · 산술 위험 산정(chunk_size 50,000 고정 기준):
      PK 1~50,000,000 조밀        → 1,000 chunk
      + 이상치 PK 1건 10^10        → 200,000 chunk (199,000개가 빈 chunk)
    빈 chunk 1회 고정비 실측(PK-RANGE-CHUNK-BOUNDARY-ORDERING-ASSUMPTION-DIAGNOSE):
      PLAIN(단순 SELECT)   0.002~0.003s  → 199,000개여도 약 10분
      WRAPPED(CTE/JOIN/윈도우) 0.257~0.343s → 199,000개면 **약 19시간**(0행을 돌려주려고 매번 전체 스캔+정렬 완주)

  · ▶ 심각도의 결정 변수는 **행 수가 아니라 (a) PK 범위의 희소성/이상치, (b) 원본 SQL 이 wrapping 형태인가** 다.
    조밀한 PK + 단순 SELECT 면 5,000만행 1,000 chunk 의 빈 chunk 고정비는 3초로 무시 가능하다.
    반대로 25만행이어도 이상치 1건 + CTE 형태면 11.4분을 순수 낭비한다(P5 원문 실측).

  · ⚠ P5 보고서의 명시적 경고(§6 "하지 말 것") — 오늘 세션의 "청크 크기를 테이블별로 다르게" 논의와 직결:
    "**청크 크기를 규모에 비례해 키운다**" 를 정렬 비용 대책으로 삼지 말 것.
    pushdown 가능 형태엔 애초에 정렬 비용이 없고, 불가 형태에선 총 정렬 비용이 청크 **개수**에 비례하므로
    종착점이 "청크 1개 = 청크 미사용" 이 된다. 규모 비례 확장은 **부분 결과 노출 주기를 정하는 문제**이지
    정렬 비용 문제가 아니다.

8. 사용자 질문에 대한 직접 답변
════════════════════════════════════════════════════════════════════════════

  Q1. "PK_RANGE_CHUNK 가 실질적 이점을 가지려면 단일 컬럼 + 숫자여야 하는 것 아닌가?"
  A1. 맞다. 실행 계층의 실제 요구는 **단일 컬럼 물리 PK + 숫자 + NOT NULL + 직접 passthrough +
      JOIN 없음 + PostgreSQL/오라클** 이다. 계획 계층만 날짜를 추가로 허용하는데 그건 엔진과
      불일치하는 잘못된 자격이다(G1).

  Q2. "PK 는 인덱스가 있고 그건 이미 정렬돼 있다는 뜻이니까 — 이 가정이 코드에 있나?"
  A2. 가정은 있고 검증은 없다. `pk_indexed` 는 PK 제약 존재로부터 무조건 true 로 세팅되며
      인덱스 카탈로그를 조회하는 코드가 없다. 다만 '인덱스가 존재하는가' 보다 '인덱스가 쓰이는가(P1)'
      와 '인덱스 순서가 비교 의미와 같은가(S2, 해결됨)' 가 실제 위험이었다.

  Q3. "목적지가 숫자/PK 가 아니거나, 원본 PK 가 복합키/비숫자면 무슨 대안을 쓰는가?"
  A3. **DIRECT_STREAM_COMPARE + 실행경로 DIRECT_COMPOSITE_PK** 다.
      `_resolve_native_pk_key` 가 정식 PK → UK → 데이터상 안정 업무키 순으로 매칭키를 확정하고
      `unique_key=True` 네이티브 PK 정렬(Index Scan) merge 고속경로 + 조기중단(101)을 붙인다.
      키 확정도 실패하면 HOLD_UNSUPPORTED_SHAPE.

  Q4. "HASH_BUCKET 이 이 경우의 대안인가?"
  A4. **아니다.** 전수 계층(HASH_BUCKET_COMPARE)은 엔진 자체가 미구현이고,
      진단 계층(diagnosis/strategies/hash_bucket.py)은 same-DBMS 한정 + 계약이 postgresql 만 등록돼
      **PG↔PG 조합에서만** 동작한다. 현 오라클 실 DB 환경에서는 양쪽 모두 불가.
      지침이 물은 "same-DBMS 제약이 추가로 걸리는가" = 예, 걸리고 그 위에 방언 등록 제약이 하나 더 있다.

  Q5. "대량에서 어떤 성능/안전 장치가 있나?"
  A5. 표본 preflight 게이트 · 불일치 누적 조기중단 · 그룹당 101 조기중단 · prewarm 2단 정책 ·
      Source/Target 동시조회. **규모 기반 사전 HOLD 는 없다** — `_unique_native_key` 경로는
      전환 판정(choose_compare_strategy)을 호출조차 하지 않는다.

  Q6. "청크 크기를 테이블별로 다르게 가져가야 하나?"
  A6. 현재는 고정 50,000 이고 규모 비례 로직이 없다. 다만 P5 보고서가 명시적으로 경고하듯
      **정렬 비용을 이유로 청크를 키우는 것은 방향이 반대다.** 우선순위는 청크 크기 조정이 아니라
      (1) 이상치 방어(청크 수 임계 초과 시 실행 전 HOLD) (2) 불균형 관측성(빈 chunk 비율·최대 배수 노출)
      (3) pushdown 사전 판정(wrapping 형태면 청크 전략 미선택) 순이다.
