■ 작업명
  REIMPORT-NATIVE-PK-FASTPATH-FANOUT-DUP-GUARD-FIX

■ 배경(결함)
  목적지에 정식 PK 가 있으면 재이관 네이티브 PK 고속경로(_resolve_native_pk_key ①,
  routes/agg_diff_route.py)가 '결과셋에서도 유일한지' 검사 없이 곧바로 unique_key=True 를
  확정했다. 원본이 1:N JOIN 으로 fan-out 되면 그 PK 가 원본 결과셋에서 중복되는데도,
  고속경로(_pk_agg_sql 의 '1 AS __N' 상수 + GROUP BY 없음)가 다중성을 COUNT diff 로
  감지하지 못해 실제 불일치가 있어도 재이관 드릴다운이 '재이관 0건/전부 정상'을 조용히 반환했다.
  (실측: 참값 SUM 1500인데 fan-out 1900, total_reimport_pks=0 오판정.)

■ 수정 내용 (routes/agg_diff_route.py 단일 파일, +48/-1)
  1) _native_pk_fanout_present() 신규 — ②③ 경로가 쓰는 기존 _dup_present(GROUP BY key
     HAVING COUNT(*)>1, 1건 probe)를 PK 컬럼에 그대로 재사용(중복 로직 신규 구현 없음).
     dup 검사 대상은 파생 src_sql 직접 사용(재래핑 없음) — 파생 src_sql 이 이미
     'SELECT * FROM (... AS tgt_col ...) mv_reimport_src' 로 목적명을 노출하므로 목적 PK 명으로
     곧바로 GROUP BY 가능. (재래핑 시 밑줄선두 별칭 '__m' 이 오라클 ORA-00911 을 유발해
     _dup_present 가 None 을 반환, 게이트가 조용히 무력화되던 문제를 회피.)
  2) _resolve_native_pk_key ① 정식 PK 경로 — 원본이 JOIN/CTE/UNION 으로 wrapping 되는 형태
     (_reimport_source_needs_wrapping)일 때에 한해 위 검사를 1회 수행. 중복 확정(True)이면
     req._fanout_pk_nonunique 를 세우고 PK 문자열은 그대로 반환.
  3) _pk_resolve — _fanout_pk_nonunique 가 서면 unique_key=True 부여를 보류. 키는 그대로
     확정하되 기존 GROUP BY count 경로로 폴백해 다중성이 COUNT diff 로 표면화되게 함.
  4) _with_evidence(응답 chokepoint) — fan-out 감지 시 응답에 fanout_pk_warning 노출
     (판정/데이터 불변, 부가 키만 — 설명가능성).

■ 설계 원칙 준수
  - routes/agg_diff_route.py 만 수정(다른 파일 무접촉). _dup_present 로직은 기존 것 호출/재사용.
  - wrapping(CTE/JOIN/UNION) 형태에서만 검사(가장 위험한 형태 한정, 저비용).
  - 단순 1:1 이관은 _reimport_source_needs_wrapping=False 라 검사를 아예 타지 않음.
  - '확실히 중복(True)일 때만' 고속경로 차단 — 확인불가(None)·무중복(False)은 고속경로 유지
    → 정상 케이스 판정 불변 보장.
