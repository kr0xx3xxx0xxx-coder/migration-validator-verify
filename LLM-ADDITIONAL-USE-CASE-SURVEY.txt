1. M50 방법론 요약 — 이번 조사가 그대로 따른 판단 절차
═══════════════════════════════════════════════════════════════════════

M50(LLM-ADMIN-COLUMN-JUDGMENT-SCOPE-AND-DESIGN-DIAGNOSE → M50-EDGE-CASE-
VERDICT-DISTRIBUTION-MEASURE)이 쓴 절차는 4단계였고, 이번 조사도 동일하게 적용했다.

  [1] 삽입 지점을 코드에서 특정한다 (짐작 금지)
      - 지시서가 지목한 자리(A)뿐 아니라 조사 중 발견한 자리(B)까지 코드 라인으로 특정.
      - "코드 주석이 스스로 미해소 한계라고 자백한 지점"을 더 가치 있는 자리로 판정.

  [2] 설계를 먼저 확정한다 (전부 additive, 기존 규칙기반 판정 무변경)
      - LLM은 규칙 축이 전부 결론을 못 낸 자리에서만 호출되는 3차 근거.
      - 응답 반영은 비대칭 — 위험한 방향(하드 배제)으로만 승격 가능, 반대 방향
        자동 해제 금지(오탐 비용 > 미탐 비용, F18 결론과 일관).
      - 연동은 표준 라이브러리 urllib.request 로 Ollama OpenAI 호환 API 직접 호출
        (CLAUDE.md 외부 패키지 금지 회피). 기본 OFF + fail-open Noop 폴백 +
        circuit-breaker. 캐시는 db/migration_validator.db 신규 테이블, model_id+
        prompt_version 으로 자동 무효화, 원문 응답 저장(설명가능성).

  [3] "실제로 몇 %에서 호출되는가"를 재기 전에는 착수 판정을 안 한다
      - F18 선례("3차 신호는 오탐률 미검증 시 착수 보류")를 그대로 적용.
      - 이 숫자 없이 인프라(Ollama+모델+Docker)부터 들이면, 거의 안 쓰이는 기능에
        배포 복잡도(GPU 유무·폐쇄망 반입·컨테이너 수명주기)만 얹는다는 판단.

  [4] 실측 후 재판정 — 그리고 실측 표본의 오염을 정직하게 깎는다
      - 실 DB 재스윕 506컬럼: NOT_AUDIT_CONFIRMED 90.5% / NOT_AUDIT_AMBIGUOUS 4.7%
        / CONFIRMED 4.3% / NAMING_VALUE_MISMATCH 0.4%.
      - LLM 호출후보(N1+N3+CONFIRMED-B-only) = 27/506 = 5.3%.
      - 그중 22건이 "오늘 시점 0행 픽스처 테이블" 부작용으로 확인 → 실질 호출후보
        4~5/506 = 0.8~1.0%. → 결론: 문서화 우선·구현 보류 유지.
      - 한계 명시: PG 단일 방언·픽스처 1건 표본이라 5.3%/1.0% 어느 쪽도 일반화
        상한/하한으로 인용 금지.

  [5] ★ M50이 남긴 가장 중요한 교훈(이번 조사의 판정 기준으로 채택)
      M50의 실제 산출물은 "LLM 도입"이 아니라, LLM을 검토하다 발견한
      **순수 규칙기반으로 즉시 고칠 수 있는 결함**(biz_reg_no 가 배지 없이 조용히
      GROUP BY 자동선정에서 하드 배제)이었고, 그것이 실제로 해결됐다
      (ADMIN-AUDIT-SILENT-CONFIRMED-FULL-AUDIT-AND-FIX, 커밋 6f5d5073).
      → 따라서 이번 조사도 각 후보마다 "LLM 없이 되는가"를 먼저 묻고,
        되는 것은 LLM 후보에서 탈락시켰다. 아래 표의 '판정' 열이 그 결과다.

    근거(코드/데이터 실측)

        즉 "켜면 뭐가 달라지는지"를 재는 수단까지 갖춰져 있는데 측정 결과가 verify
        저장소 어디에도 완료보고로 남아 있지 않다(grep 0건).

    왜 이게 LLM보다 먼저인가
      · 아래 2절 판정후보 대부분(C1·C2·C8)의 근본 원인은 "컬럼명/코멘트 의미를

        현재 매칭에 실제로 쓰이는 사전은 로컬 164건뿐이다(80배 차이).
      · 사전은 결정적·설명가능·무비용·폐쇄망 안전이다. LLM은 그 어느 것도 아니다.
      · 이미 가진 사전조차 안 켠 상태에서 Ollama+모델+Docker 를 들이는 것은,
        M50이 착수 보류 근거로 든 "거의 안 쓰이는 기능에 배포 복잡도만 얹는다"를
        더 나쁜 형태로 반복하는 것이다.

    권고: shadow 계측 1건 실행 → additive-only 불변식 위반 0 확인 → flag ON.
          이건 별도 지침 대상이며 이번 조사 범위 밖(코드 무변경 원칙).
    위험: global confidence 는 0.70 캡(STRONG 0.75 미달)이라 단독 확정은 못 하지만,

          RAW_TEXT(0.7)에 대표를 뺏김)이 그대로 확대될 수 있다 → 이 결함 선해소 필요.

6-1. 세 모드의 실제 구조 관계 (코드 실측)
  · 전수검증(exhaustive)은 별도 엔진이 아니다 —

     일 뿐이다. 이 모듈은 순수(orchestration) — DB/SQL/새 connection/파서/planner/

  · 일괄검증(batch)도 같다 — F36 해결 과정에서 실제 UI 일괄검증이 타는 경로가
    batch_single_core_wrapper.py → run_single_validation_standard 임이 확인됐다.

    곱해진다** — 즉 적용 범위 확대는 "기회"가 아니라 먼저 "비용 위험"으로 봐야 한다.

6-3. 배치에서의 호출 총량 — 캐시 설계가 사실상 이 문제를 이미 푼다  ★핵심 발견
  가정(M50 §4 참고치): CPU 추론 5~20 토큰/초, 출력 50~150 토큰 → 호출당 3~15초.
  나이브 계산: 1,000 테이블 × 컬럼 20개 = 20,000 컬럼, 미스율 10% 가정 → 2,000 호출
               × 3~15초 = **1.7~8.3시간**. 동기 호출이면 배치가 사실상 멈춘다.
  그러나 M50 설계의 캐시 키는 **"정규화 컬럼명 + 코멘트 유무"**이지 테이블·행이 아니다.
  실측으로 이 키의 중복도를 확인했다:
      profile_snapshot_column 10,647행에 대해
        distinct column_name = 270  (2.5%)
        distinct table_name  = 113
      → 같은 컬럼명이 평균 39회 재등장. **캐시 히트율 97.5%.**
  즉 컬럼명 어휘는 조직 표준을 따르므로 테이블 수가 늘어도 **distinct 컬럼명 수는
  훨씬 느리게 는다**. 1,000 테이블이라도 distinct 컬럼명이 3,000종이고 그중 미스가
  10%면 실제 호출은 300회(첫 등장분만) → 15~75분, 그것도 **최초 1회뿐**이고 이후
  배치는 전량 캐시 히트다.
  ★ 따라서 "테이블 1개당 확률은 낮아도 배치 총량이 커진다"는 우려는 **캐시가 있으면
    성립하지 않는다**. 반대로 캐시를 빼면(또는 캐시 키에 테이블명·원문을 넣으면)
    즉시 성립한다 — M50이 캐시 키에서 원문을 뺀 이유("원문 포함 시 히트율 붕괴")가
    바로 이 지점이며, 그 절충안이 배치 확대의 전제 조건이다.

6-4. M50이 설계한 circuit-breaker 재사용 가능성 — 가능하나 그대로는 부족
  · 재사용 가능한 부분: M50 §3의 "첫 호출 실패 시 이후 호출 즉시 스킵(프로세스 단위
    circuit-breaker)" + fail-open Noop 폴백은 배치 경로에 그대로 유효하다.
    기존 NXTDA_INTEGRATION_ENABLED 패턴(config/model_config.py:95,
    integration/nxtda/hook_facade.py:29-33 — flag false 면 외부 통신 시도 자체가 없음)이
    이 프로젝트의 확립된 선례라 새 패턴을 만들 필요도 없다.
  · 그대로는 부족한 부분(배치 고유):
    (a) circuit-breaker 는 "장애"만 막는다. 정상 응답이 느린 경우(CPU 3~15초/호출)는
        안 막힌다 → 배치 경로에는 **호출 총량 상한(run당 N회)** 이 별도로 필요하다.
        이 프로젝트에는 유사 선례가 이미 있다(P10 재이관 수집 HARD CAP 500,
        M65 조합 자동계획 상한 4,000, F2 대표표본 상한 100).
    (b) 일괄검증은 이미 비동기+병렬(P11 세트 병렬, batch 비동기)이라 LLM 호출이
        스레드마다 동시 발생할 수 있다 → 캐시 테이블에 동시쓰기 경합 방어 필요
        (M37에서 프리셋 JSON 통째 덮어쓰기로 동시저장 유실을 겪은 전례가 있다).
    (c) 정책 축은 이미 준비돼 있다 — services/validation_policy_service.py 의
        `policy_name` 축(default/batch/exhaustive)을 쓰면 모드별로 LLM ON/OFF·상한을
        다르게 줄 수 있다(BACKLOG 3957행이 이 축의 재사용을 이미 권고).

7-1. 구분 정의와 이 프로젝트에 맞는 기준선
  · **직접 활용** — LLM 출력이 검증 판정 값에 (조건부라도) 반영되는 경우.
    실패 모드 = 조용한 오판정. 검증 도구의 존재 이유를 훼손한다.
    필수 조건(M50이 확립): ① 규칙 축이 전부 결론을 못 낸 자리에서만 호출
    ② 비대칭 반영(위험한 방향으로만 승격, 반대 자동 해제 금지)
    ③ 실측 호출빈도 선행 ④ fail-open + 기본 OFF ⑤ 근거 원문 저장(설명가능성).
  · **간접 활용** — LLM 출력이 판정에 전혀 들어가지 않고, 이미 확정된 결과를
    사람에게 설명·정리·안내하는 데만 쓰이는 경우.
    실패 모드 = 어색하거나 부정확한 문장. 판정은 불변.
    필수 조건(이번 조사가 추가로 못 박음):
    (a) 판정값·수치는 서버 계산값만 사용, 모델이 만든 숫자는 화면 금지
    (b) 모델에는 집계 통계량만 전달, 실 레코드 값은 전달 금지
    (c) 단정문 금지 — "원인은 X입니다"가 아니라 "먼저 확인해볼 것: X"
    (d) 미기동 시 기존 하드코딩 문구로 폴백.
  ★ 이 프로젝트에서 (c)는 형식 요건이 아니라 실질 요건이다. 간접 활용이라도
    "그럴듯한 원인 단정"은 사용자를 잘못된 조치로 유도해 결과적으로 판정 오류와
    같은 해악을 낸다. 간접 활용의 안전성은 "설명이라서 안전"이 아니라
    **"단정하지 않게 만들었기 때문에 안전"**이다.

7-3. "신뢰를 주는 AI 활용"이라는 관점에서의 정리
  · 이 프로젝트에서 신뢰를 주는 방식은 "LLM을 많이 쓰는 것"이 아니라
    **LLM이 손대지 않은 영역이 어디인지 사용자가 알 수 있게 하는 것**이다.
  · 그래서 도입 시 화면 표기 규칙을 함께 정할 것을 권고한다:
    (1) LLM이 생성한 문장에는 출처 표기(모델명·생성시각)를 붙인다 —
        M50 설계가 캐시에 model_id/prompt_version/원문응답을 저장하기로 한 것과
        같은 목적(설명가능성)이며, 그 저장값을 화면에 그대로 쓰면 된다.
    (2) 판정 배지·수치에는 LLM 표기가 절대 붙지 않는다(= 직접 활용을 안 켠 상태에서는
        "판정에는 AI가 관여하지 않았습니다"를 사실로 말할 수 있다). 이게 이 도구의
        신뢰 자산이며, 직접 활용을 켜는 순간 잃는 것이다.
    (3) 직접 활용을 켠 경우에도 F19가 후보 점수에서 한 것과 동일하게
        기여분을 툴팁으로 노출한다(score_contributions → 배지 title 선례).
  · 종합 권고: **직접 활용은 당분간 켜지 않는다.** 간접 활용 1건(E1)만 열고,
    그마저도 (a)~(d) 안전조건과 출처 표기를 함께 넣는다.

     그중 둘(C1·C2)은 0순위 사전 배선 후에야 필요성이 판별된다. 나머지 7건은

   · 직접/간접 층위로 보면: **직접 활용 착수 권고 0건, 간접 활용 착수 권고 1건.**
     직접 활용을 안 켠 상태에서는 "판정에는 AI가 관여하지 않았습니다"를 사실로
