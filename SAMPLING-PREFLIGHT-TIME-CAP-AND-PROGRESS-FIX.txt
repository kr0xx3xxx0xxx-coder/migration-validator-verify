작업명 : SAMPLING-PREFLIGHT-TIME-CAP-AND-PROGRESS-FIX
✅ 작업 완료 - SAMPLING-PREFLIGHT-TIME-CAP-AND-PROGRESS-FIX - 표본 preflight 확장 단계에 사전 프로브(재앙적 케이스 진입 차단) + 누적 시간 상한(기본 60초) + anchor 진행 신호(progress_cb)를 넣어, 무신호 67분 노출 구간을 실측 1.9초 보류로 교체했다

실검증 상태: 완료 (오라클 라이브 실 DB — asis 1523 / tobe 1524, NXDNP 픽스처 25만행 · 100만행)

1. 요청 요약 / 수정 범위
────────────────────────────────────────────────────────────────────────
BACKLOG P3 — `services/exact_diff/sampling_preflight.py` 의 표본 확장 단계(2,000→5,000→10,000)에
누적 시간 상한·타임아웃·진행 신호가 전혀 없어 최악 17,000 anchor 를 무신호로 소진한다.
요구 4개: (1) 사전 프로브로 진입 차단 (2) 누적 상한 + 부분 결과 안전 마무리

- 수정 파일: `services/exact_diff/sampling_preflight.py` **1개** (지시 범위 그대로, 269줄 추가 / 5줄 삭제)

2. 구조 검토(비판적 검토 의무)
────────────────────────────────────────────────────────────────────────
- 긍정적 효과: 판정 로직(§5·§6)을 전혀 건드리지 않고 '시간'만 방어한다. 상한에 걸리면 결과는 항상
  INCONCLUSIVE 이고, INCONCLUSIVE 는 기존에도 '기존 전체 merge 진행'을 뜻하므로 **최종 불일치 판정·건수는 불변**이다.
- 핵심 위험(요청서에도 명시): 사전 프로브가 정상 케이스를 INCONCLUSIVE 로 오판하면 표본 조기중단 이득이 사라진다.
  → 3절에 실측 기반 2중 완화(비용 분해 + 여유 배수)와 그 검증을 적었다.
- heuristic 증가 여부: 임계·배수를 코드에 흩지 않고 모듈 상수 3개 + env 3개 + settings override 로 단일화했다
  (`MV_COUNT_STATEMENT_TIMEOUT_MS` / `MV_EXECUTE_STATEMENT_TIMEOUT_MS` 와 같은 기존 네이밍·ms 단위 관례).
- explainability: 왜 멈췄는지가 응답에 남는다 — `reason`(최상위) + `sampling.time_cap_reason` +
  `sampling.probe`(단계별 실측 ms·고정비·단가·환산치·차단임계). 무증적 보류를 만들지 않았다.
- 구조 부채: 새 진행 메커니즘을 만들지 않았다. 페이로드 키를 `pk_range_chunk._emit_prog` 규약
  (processed_src/available/progress_at)에 맞춰 route 의 기존 콜백(_pcb → rj.update_progress)이 그대로 소비한다.

3. 구현 요약
────────────────────────────────────────────────────────────────────────
(1) 사전 프로브 `probe_expansion_cost()`
    - anchor 8개 → 32개 2단계로 시범 실행 후 비용을 **고정비 + anchor 단가**로 분해
      (1단계만 재면 쿼리 고정비가 단가로 잡혀 정상 소스를 과대추정 → 오판의 주원인).
    - 환산: `projected = 고정비 × 단계수 + 단가 × Σ(단계 anchor 수=17,000)` (최악 기준)
    - 차단 조건: `projected > cap × margin(기본 3.0)` — 프로브는 '재앙적 케이스' 만 막고,
      애매한 구간은 단계를 1회 실제로 돌린 뒤 그 실측으로 막는다(아래 (2)).
    - 2단계 간격을 x4 로 넓힌 것은 실측 근거다. 오라클 비인덱스 키에서 4→8 구간은 429ms→355ms 로
      **한계비용이 0 으로 잡혀** 그대로 통과했고, 통과한 2,000 anchor 단계가 73.9초였다.
      같은 소스의 8→32 구간은 623ms→1,303ms 로 단가(28.3ms/anchor)가 드러난다.
(2) 누적 시간 상한 `SAMPLING_TIME_CAP_MS`(기본 60,000ms)
    - 단계 **시작 전**: `경과 + 이번 단계 예상비용 > 상한` 이면 시작하지 않는다.
      예상비용의 출처가 프로브면 여유 배수로 나눠 쓰고(과대추정 보정), 직전 단계 실측이면 그대로 쓴다
      (`estimate_basis`: PROBE / MEASURED_STEP).
    - 단계 **완료 후**: 경과가 상한을 넘었으면 다음 단계로 넘어가지 않는다.
    - 마무리: 그 시점까지의 표본 통계를 그대로 담아 `status=SAMPLING_INCONCLUSIVE`,
      `reason=SAMPLING_TIME_CAP_EXCEEDED` 로 반환. **부분 표본으로 조기중단/승인 판정을 만들지 않는다**
      (판정은 완결된 단계에서만 나오므로 기존 판정 규칙이 그대로 유지된다).
(3) 진행 신호 `progress_cb`
    - 프로브 단계마다 1회, 확장 단계 완료마다 1회 발행. 페이로드에 anchor_i/anchor_total 과
      기존 키(processed_src/available/progress_at)를 함께 싣는다.
    - 콜백이 dict 위치인자든 **kw 든 모두 수용하고, 콜백 예외는 전부 삼킨다(발행이 판정을 깨지 않는다).
    - 미전달(None)이면 기존과 완전히 동일(무신호).
(4) 조정 수단: `MV_SAMPLING_TIME_CAP_MS` / `MV_SAMPLING_PROBE_ANCHORS` / `MV_SAMPLING_PROBE_MARGIN`
    (0 이면 상한·프로브 해제 = 기존 동작). settings dict 로도 override 가능(time_cap_ms/probe_anchors/probe_margin).

신호 촘촘함의 한계(정직 고지): 한 단계 내부는 batch 쿼리 1회다(§4 '표본 PK별 N+1 금지', 회귀 테스트
`test_source_target_query_counts_bounded` 가 단계당 1회를 계약으로 고정). 그래서 anchor 단위로 더 잘게
쪼개려면 그 계약을 깨야 하므로 하지 않았다 — 대신 단계 사이 무신호 구간의 **길이**를 (1)(2)로 제한했다.

4-5. progress_cb → /jobs/active 응답 확인(요구 3)
  route 와 동일한 콜백(_pcb → rj.update_progress)을 붙이고, /jobs/active 라우터 함수를 직접 호출해 받은 DTO:
    {"source": "single", "id": "PSLIVEVERIFY01", "key": "single:PSLIVEVERIFY01",
     "status": "PREPARING", "completed": 2000, "last_progress_at": 1785322085.98458,
     "started_at": 1785322085.7038436, "active": true,
     "progress_signal": "PROGRESS", "stall_seconds": 0.3, "stall_basis": "last_progress_at"}
  → `last_progress_at` 이 실제로 갱신되고, 백로그가 지적한 **START_ONLY 가 PROGRESS 로 바뀐다**
     (stall_basis 도 started_at → last_progress_at). HTTP 대신 라우터 함수를 직접 호출한 이유는
     개별검증 job 저장소가 in-memory 라 다른 프로세스(HTTP 클라이언트)에서는 이 job 이 보이지 않기 때문이다.
