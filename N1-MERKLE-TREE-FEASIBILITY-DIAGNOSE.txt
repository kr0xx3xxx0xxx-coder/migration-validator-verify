작업명 : N1-MERKLE-TREE-FEASIBILITY-DIAGNOSE
✅ 작업 완료 - 계층적 체크섬은 이미 HASH_BUCKET wave / KEY_RANGE 이분에 구현돼 있고 신규 도입 이득 구간이 사실상 비어 있음을 확인(보류 판정)

■ 요청 요약
  재이관 검증에 계층적 체크섬(Merkle tree) 전략을 새로 도입할 가치가 있는지, 전제조건·손익분기·기존
  전략과의 관계·구현범위·실측근거를 조사하고 도입 여부를 판정한다(코드 수정 없음).


■ 총평 (먼저 읽을 결론 3줄)
  1) Merkle tree 는 "미도입 신규 전략"이 아니다. services/diagnosis/multi_scope.py 의 wave 루프 +
     strategies/hash_bucket.py 의 HB1..HBn 레벨 구조가 이미 계층적 해시 트리이고, strategies/key_range.py
     의 bucket→이분→LEVEL-BATCH 가 이미 계층적 범위 트리다. 지시서가 전제한 "HASH_BUCKET 은 버킷당
     해시 하나뿐, 계층이 없다"는 사실과 다르다.
  2) 그럼에도 깊은 하강이 잘 동작하지 않는 진짜 원인은 계층의 부재가 아니라 **하강 1레벨의 비용이
     전체 스캔 1회와 같거나 그 이상**이라는 것이다(실측: 활성 경로 수에 선형, 0.85초/경로). 이 조건에서
     계층을 더 쌓으면 손해가 커질 뿐이다.
  3) 따라서 신규 Merkle 전략 구현은 보류하고, 같은 이득을 훨씬 싼 값에 주는 3가지 결함 해소
     (_hash_path_predicate OR 재평가 / pk_indexed 미검증 / 표시상한 180이 전략 깊이를 지배)를 선행해야 한다.


■ 0. 전제조건 판정 — 정렬 기준 확보 가능성
  결론: **"Merkle tree 는 정렬 기준이 필요하다"는 지시서 전제는 절반만 맞다.** 트리를 무엇으로 쪼개느냐에
  따라 전제조건이 완전히 갈리며, 이 프로젝트에는 두 종류가 이미 공존한다.

  0-1) 해시 파티션 트리 — 성립(조건부 O)
    · 정렬 기준을 요구하지 않는다는 점이 이 전략의 최대 강점이다. 지시서가 걱정한 "왼쪽 절반이 양쪽에서
      다른 행 집합을 가리킬 위험"이 원천적으로 없다.
    · 다만 다른 전제가 붙는다: hash_contract.get_hash_contract_pair() 의 L3 가드가 Source/Target
      **동일 방언**만 허용한다(HR_HASH_CROSS_DBMS, 영구 차단). 사유는 성능이 아니라 정합성이다
      (PG trim_scale vs 오라클 TO_CHAR TM9, 오라클 ''=NULL → 'S#N' vs PG 'S:0:', 날짜 서식/NLS 의존).
    · 계약 등록 방언은 현재 postgresql, oracle 2종뿐(hash_contract._HASH_CONTRACTS). mysql/mssql 은
      미등록 → HASH_CONTRACT_NOT_AVAILABLE 로 SQL 생성 자체가 차단된다.
    · 오라클 계약은 STANDARD_HASH(x,'MD5') 기반이고 RAWTOHEX hex 가 PG md5() 와 문자 동일하다는
      실측이 있으나, cross_db_comparable=False 로 못박아 두었다(계약 계층에서 비교 금지).

  0-2) 범위(PK) 트리 — 조건부 성립, 그러나 **전제가 검증되지 않았다**
    · M61 의 PK 신뢰 판정은 **그대로 재사용 가능**하다. build_chunk_key_evidence_snapshot() →
      verdict='TRUSTED_PHYSICAL_PK' → resolve_trusted_chunk_key() 경로와, 그 결과를
      routes/agg_diff_route._pk_resolve 가 req._chunk_key_trusted / _chunk_key_type /
      _chunk_key_indexed 로 보존하는 배선이 이미 있다. Merkle 이 새로 만들 필요가 전혀 없다.
    · 적용 가능 범위(실제 코드 게이트 기준):
        - 단일 컬럼 + 숫자 PK 만: key_evidence.py:377 이 norm_type != "NUMBER" 를 continue 로 탈락시키고,
          pk_range_chunk.build_chunk_bounds 가 int() 로 강제한다.
        - 날짜 PK: 2026-08-03 a758782 로 계획·전환 두 층에서도 CHUNK 자격 제외 확정(→ DIRECT_STREAM).
        - 복합 PK: key_evidence.py:377-378 이 단일컬럼만 필터해 명시적으로 배제. 복합 처리는
          diagnosis 의 match_key_evidence.resolve_confirmed_match_key(composite = len(se) > 1) 에만 있고,
          이건 해시 트리 쪽 입력이다. 즉 **복합 PK 는 범위 트리 불가 / 해시 트리 가능**.
        - 문자 PK: 불가 판정. 근거는 이론이 아니라 실측이다 — 축A(경계 절단: 문자 MIN/MAX 를 int() 캐스팅),
          축B(정렬 전제 위반: 5만행 chunk 1개에서 역전 4,500회, 참값 10,000건이 재이관 64,997 +
          목적단독 54,998 로 붕괴), 그리고 오라클 캐릭터셋 collation 실측(한글 키 1,986건이 100% 동일한데
          matched 455 / source_only 1,531 / target_only 1,531 로 거짓 불일치 3,062건 날조, 경고 없이 확정 보고).
    · **치명적 갭 — pk_indexed 는 인덱스 실재를 확인하지 않는다.**
        key_evidence.py:191 이 "indexed": bool(ev.is_pk or ev.is_unique) 로 PK 존재를 곧 인덱스 존재로
        환산하고, ui/grid_helpers._mvDerivePkProfile 의 모든 반환 분기가 pk_indexed:true 를 하드코딩한다.
        pg_index / USER_INDEXES 등 인덱스 카탈로그를 실제로 조회하는 운영 경로는 0건이다.
        이게 왜 Merkle 에서 특히 치명적인가 — 아래 1번에서 계산하듯 **범위 트리가 해시 트리보다 유리한
        유일한 근거가 "레벨을 내려갈수록 스캔량이 줄어든다(지역성)"** 인데, 그 지역성은 오직 PK 인덱스
        범위 스캔이 실제로 걸릴 때만 생긴다. 인덱스가 없으면 매 레벨이 풀스캔으로 되돌아가 범위 트리의
        경제성이 해시 트리 수준으로 붕괴한다. 지금 이 플래그는 항상 참인 무의미한 값이므로, Merkle 이
        여기 의존하면 PK_RANGE_CHUNK 와 똑같이 '확인되지 않은 전제' 위에 서게 된다.

  0-3) 0번 종합 판정
    · 해시 트리: 성립. 조건 = same-DBMS + 계약 등록 방언(PG/오라클) + MATCH_KEY 확정. 정렬 기준 불요.
    · 범위 트리: 조건부 성립. 조건 = 단일 숫자 PK + TRUSTED_PHYSICAL_PK + **실제 인덱스(현재 미검증)**.
      문자/날짜/복합 PK 는 적용 불가.
    · 계층 구조가 정렬 위험을 키우는가 → **키운다.** 단일 레벨 비교라면 "이 범위가 다르다"는 결과 1건이
      정렬 아티팩트인지 진짜 불일치인지 사람이 판단할 여지가 있지만, 계층 하강에서는 상위 레벨의 오탐이
      하위 전 서브트리로 전파되고, 하강 중 반복 재조회로 오탐 지점이 여러 개로 복제되어 "국소화된 정확한
      위치"라는 형태로 확정 보고된다. 즉 **오탐의 신뢰도만 올라간다.** 이 위험은 정렬을 쓰는 범위 트리에만
      해당하고, 해시 트리에는 없다.


■ 1. 손익분기점 추정
  1-1) 비용 기호와 실측 대입
    s = 집계 해시 스캔 1행당 비용. 오라클 실 25만행 1.02초 → **s ≈ 4.08 µs/행**
    E = 전수 행비교 1행당 비용.
        DIRECT_STREAM cold cross-host 1M / 158초 → 158 µs/행
        PK_RANGE_CHUNK(50k) 1M / 68초 →  68 µs/행
        → **E/s ≈ 17 ~ 39 (대표값 35, 신뢰밴드 15~40)**
    B = 레벨당 팬아웃(bucket 수). 현행 기본 128, 선택지 (256,128,64), KEY_RANGE 첫 분할은 8, 이후 2(이분).
    N = 전체 행 수, m = 불일치 행 수, d = m/N (불일치 비율), k_i = 레벨 i 의 활성 노드 수.

  1-2) 하강 1레벨의 손익 부등식
    레벨 i 에서 "한 레벨 더 내려간다" vs "여기서 멈추고 활성 영역을 전수비교한다" 비교:

        (레벨 비용) < E × (줄어드는 활성 행 수)

    (a) 지역성 없음(해시 트리 — 레벨마다 전체 스캔이 강제됨):
          N·s  <  E · A_i · (1 − 1/B),  A_i = k_i·N/B^i
        → **B^i < (E/s)·(1 − 1/B) ≈ E/s ≈ 35**   (k_i 가 양변에서 소거되지 않는 완화형은 B^i < 35·k_i)

    (b) 지역성 있음(범위 트리 + 실제 PK 인덱스 — 레벨 비용이 활성 행에 비례):
          A_i·s < E·A_i·(1 − 1/B) → **s < E·(1−1/B)** → E/s ≈ 35 이므로 **모든 레벨에서 항상 성립**

  1-3) 여기서 나오는 핵심 수치 — "국소화 상한 ≈ E/s ≈ 35배"
    (a) 식을 깊이에 대해 풀면 유효 레벨 수 L* = floor(log_B(E/s)) 이고, 그때 달성되는 총 국소화 배율은
    B^L* ≈ E/s 로 **팬아웃 B 와 무관하게 약 35배에서 멈춘다.**
      → 지역성이 없는 상태에서는 어떤 팬아웃·어떤 깊이 조합을 써도 전체 대비 35배 이상 좁히는 것이
        "그냥 전수비교하는 것"보다 비싸다. 즉 **계층을 깊게 쌓는 행위 자체가 이 조건에서는 무의미하다.**

    팬아웃별 유효 깊이(E/s = 35 대입, 밴드 15~40 전 구간에서 결론 불변):
      ┌──────────┬────────────────┬────────────────┬──────────────────────────────────┐
      │ 팬아웃 B │ 레벨1 (B^0=1)  │ 레벨2 (B^1=B)  │ 판정                             │
      │──────────┼────────────────┼────────────────┼──────────────────────────────────│
      │  256     │ 1 < 35  이득   │ 256 < 35 손해  │ 1레벨만 유효                     │
      │  128(현행)│ 1 < 35  이득   │ 128 < 35 손해  │ **1레벨만 유효 — wave2 부터 손해**│
      │   32     │ 1 < 35  이득   │  32 < 35 이득  │ 2레벨까지 유효                   │
      │    8     │ 1 < 35  이득   │   8 < 35 이득  │ 3레벨(64<35 실패)→2레벨까지      │
      │    2     │ 1 < 35  이득   │   2 < 35 이득  │ 5레벨까지 유효(32<35, 64>35)     │
      └──────────┴────────────────┴────────────────┴──────────────────────────────────┘
      → 시사점: **계층을 늘리는 것보다 팬아웃을 줄이는 게 먼저다.** 현행 HASH_BUCKET 의 B=128 은 하강용으로
        과도하게 넓고, KEY_RANGE 가 쓰는 8→2(이분)가 이 모델상 이미 최적에 가깝다. 즉 "Merkle 처럼
        이분탐색으로 좁힌다"는 아이디어는 KEY_RANGE 에서 이미 정답 형태로 구현돼 있다.

  1-4) 실측이 이론보다 더 나쁘다 — OR 술어 재평가 페널티
    위 (a)는 "레벨 비용 = 전체 스캔 1회"라는 낙관적 가정이다. 실제 wave2 실측은 그보다 나쁘다.
      _hash_path_predicate 가 활성 경로를 scope_set(OR 목록)으로 넘기면 옵티마이저가 OR 분기마다
      canonical 해시식을 재평가한다:
          1경로 1.02초 → 10경로 10.11초 → 40경로 33.72초 (기울기 ≈ 0.85초/경로, 순수 SELECT 원본)
      즉 레벨 비용 ≈ k_i × (전체 스캔 1회). 이걸 (a)에 넣으면

          k_i·N·s < E·k_i·(N/B^i)(1−1/B)  →  B^i < E/s

      결과 식은 같지만 **절대 비용이 k_i 배로 부푼다** — 활성 경로 2개만 돼도 하강 1레벨이 "테이블 전체를
      처음부터 다시 스캔하는 것"보다 비싸진다(0.17 + 0.85k > 1.02 ⇔ k > 1.0).
      단, CTE+JOIN+윈도우 원본은 VIEW/WINDOW SORT 장벽 덕에 평탄(1.06~1.71초)이라 이 페널티가 원본 SQL
      형태에 좌우된다 — 즉 성능이 사용자 SQL 모양에 의존하는, 설명하기 어려운 구조다.

  1-5) 불일치 희소성 구간 — "몇 % 이하일 때 이득인가"
    (ㄱ) 구조적 상한(현행 설정이 실제로 허용하는 구간)
      multi_scope.MultiScopeConfig.max_mismatch_cells_per_wave = 180 이 wave 당 불일치 cell 을 180 으로
      묶는다(주석: "통계 표시 상한 200 미만"). 하강이 유의미하려면 불일치가 서로 다른 cell 로 흩어져야
      하므로 실효 이득 구간은 **불일치 행 m ≲ 180건**이다.
          N =    1,000,000 → d ≤ 0.018 %
          N =   10,000,000 → d ≤ 0.0018 %
          N =   50,000,000 → d ≤ 0.00036 %
      (참고: dense_mismatch_ratio = 0.5 — cell 의 50% 이상이 불일치면 PLAN_HOLD_DENSE 로 하강 중단)
    (ㄴ) 이론적 상한(리프 크기 기준)
      국소화가 이득을 주려면 m × (리프 행 수) < N, 즉 **d < 1 / 리프행수**.
      ROW_DIFF_READY 임계(row_diff_threshold = 1,000)를 리프로 보면 d < 0.1 %.
    (ㄷ) 첫 분할은 언제나 이득
      레벨 0→1 조건은 B^0 = 1 < 35 로 무조건 성립한다. 즉 **"한 번 쪼개서 좁힌다"는 항상 이득이고,
      "여러 겹 쪼갠다"는 대체로 손해**다. 이게 이번 조사의 핵심 가설에 대한 답이다.

  1-6) 1번 결론
    · 지시서 가설("희소하면 이득, 광범위하면 손해")은 **맞지만 범위가 예상보다 훨씬 좁다.** 이득 구간은
      대략 d ≲ 0.0004 %(5천만행 기준 180건) 이고, 그마저도 첫 1레벨에서 거의 다 회수된다.
    · 지역성 없는 해시 계층에서 총 국소화 상한은 **≈ E/s ≈ 35배**로, 팬아웃·깊이를 어떻게 조합해도
      이 벽을 못 넘는다. 결론은 E/s 신뢰밴드 15~40 전 구간에서 불변이다(B=128 이 2레벨을 통과하려면
      E/s > 129 여야 하는데 밴드 최대값의 3배 이상이다) — 추가 실측으로 뒤집힐 결론이 아니다.
    · 단, **문자/UUID 키 경로에서는 이 손익 비교 자체가 성립하지 않는다.** 그 경로는 전수비교 대안이
      아예 없기 때문이다(exact_diff/engine.py 는 key 없으면 HOLD_NO_STABLE_KEY, 방언 불일치면
      HOLD_UNSUPPORTED_DB). router.py:50 이 match_key_only_unsupported → ROUTE_HASH_BUCKET 으로 보내는
      것도 "더 싸서"가 아니라 "유일한 수단이라서"다. 이 경로의 깊은 하강은 비용 대비 이득이 아니라
      가용성으로 정당화되며, 그건 이미 구현돼 있다.


■ 2. 기존 전략과의 관계
  2-1) 결론: 대체도 보완도 아닌 **이미 동형(同型)**이다.
    지시서·BACKLOG N1 의 전제("HASH_BUCKET 은 버킷 단위로 해시 하나만 매긴다")는 코드와 다르다.
    services/diagnosis/multi_scope.py::_run_hash_bucket_waves 는 이미 다음을 한다:
      · wave 마다 bucket level 을 하나씩 추가(HB1, HB2, HB3 …) — hash_bucket.bucket_aliases()
      · 레벨마다 다른 salt("hbw1","hbw2",…) — hash_bucket.level_salt(i), 같은 modulo 반복 방지
      · 상위 레벨을 GROUP BY 에 유지해 **부모 경로 보존**(hash_bucket.build_hash_bucket_agg_sql 의 ns 목록)
      · 활성 경로만 scope_set 으로 제한 → **부모의 자식만 분할, 일치 부모 재실행 0**(_hash_path_predicate)
      · 일치 bucket 은 재조회 0회로 가지치기(meter.add_avoided(present − mismatch))
      · max_waves = 3 → 트리 깊이 3, 종료조건 = 전부 일치 / 밀도 초과 / 활성 상한 / ROW_DIFF_READY
    그리고 결정적으로, 집계가 SUM(KH)·SUM(RH) 이다. 합은 결합·교환 법칙을 만족하므로
    **부모 노드의 해시 = 자식 노드 해시들의 합**이 자동 성립한다 — 이건 Merkle tree 의 정의적 성질
    그 자체다. 즉 계약 수준에서 이미 Merkle 이다.

    범위 축도 마찬가지다. router._expand_key_range 는
      · 첫 분할: width_bucket 8구간을 **한 번의 집계**로 비교(kr.build_bucket_agg_sql), 불일치 구간만 자식
      · 깊은 분할: midpoint 이분(kr.split_range) = 정확히 이분탐색
      · LEVEL-BATCH: 같은 깊이의 불일치 형제 전부를 CASE 축 하나로 묶어 측당 1쿼리로 일괄 재검증
        (kr.build_multi_range_agg_sql) + 자식 결과 preset 으로 재조회 제거
      · 최소 폭 도달 시 정지(width_reached / STOP_MIN_RANGE)
    이건 "PK 정렬 위에 계층만 추가한 Merkle tree" 의 교과서적 형태이며, 지시서가 물은
    "PK_RANGE_CHUNK 위에 얹는 형태로 설계 가능한가"는 **이미 그렇게 되어 있다**가 답이다.

  2-2) 하이브리드("HASH_BUCKET 1차 → 불일치 버킷만 Merkle 로 좁힌다")
    → 현행 _run_hash_bucket_waves 의 wave1 → wave2 → wave3 가 정확히 그것이다. 신규 설계가 아니다.

  2-3) 오늘 완성한 오라클 HASH_BUCKET 인프라의 재사용 가능성 — 재사용할 게 아니라 **이미 그 자체**다.
    OracleHashContract(dialects_hash/oracle.py)의 _H32 / bucket_expr(BITAND) / canon_component 는
    레벨 수와 무관하게 salt 만 바꿔 재호출되도록 이미 설계돼 있다(bucket_expr(key_canon, n, salt)).
    계층을 늘리는 데 필요한 오라클 쪽 추가 구현은 **0건**이다.

  2-4) 다만 실제 갭이 하나 있다 — canonical 계약이 2벌이다
    · 전수비교 계층: services/exact_diff/canonical.py + dialects/{postgresql,oracle}.py
      → row_hash_expr 규격 `|{순번}{타입ID}:V{길이}:{정규화값}` 를 MD5
    · 진단 계층:   services/diagnosis/hash_contract.py + dialects_hash/{postgresql,oracle}.py
      → canon_component 규격 `태그:길이:값` (NULL 은 `태그#N`)
    둘 다 MD5 기반이지만 **인코딩이 서로 달라 해시값이 호환되지 않는다.** 따라서 "전수비교가 이미
    계산한 ROW_HASH 를 계층 집계에 재활용" 하는 최적화(이론상 가장 매력적인 통합안)는 현재 불가능하고,
    가능하게 하려면 두 계약 중 하나를 다른 하나로 수렴시켜야 한다 — 저장된 run 의 계약 version 과
    resume 상태를 전부 무효화하는 변경이라 위험도가 높다(HASH_BUCKET 별칭 개명 때 이미 EVIDENCE_CHANGED
    로 옛 run 을 차단해야 했던 선례가 있다). 권장하지 않는다.


■ 3. 구현 난이도·범위
  3-1) 만약 진단 계층(diagnosis)에 "더 깊은 계층"을 넣는다면 — 난이도 낮음(설정 조정 수준)
    신규 모듈이 필요 없다. 사실상 MultiScopeConfig 파라미터 조정이다.
      max_waves(3) / default_buckets(128) / bucket_choices(256,128,64) / max_mismatch_cells_per_wave(180)
      / max_active_buckets(4000) / dense_mismatch_ratio(0.5)
    1번의 모델대로면 "깊이를 늘리기"가 아니라 **"팬아웃을 128 → 32 이하로 줄이기"** 가 정답이다.
    코드 변경 없이 config 주입만으로 A/B 가능(MultiScopeConfig 는 테스트 주입 가능하게 설계돼 있다).
    다만 아래 3-3 의 결합 문제를 먼저 풀지 않으면 파라미터만 바꿔도 wave2 선형 폭증이 그대로 남는다.

  3-2) 만약 전수비교 계층(exact_diff)에 신규 Merkle 전략을 추가한다면 — 난이도 높음(비권장)
    건드려야 하는 지점(전부 확인함):
      · services/strategy/strategy_models.py — 신규 strategy_id 상수 + AVAILABLE_COMPARE_STRATEGIES 등록
        + DEFAULT_RESOURCE_WEIGHTS 항목
      · services/strategy/strategy_transition.py::choose_compare_strategy — 3분기(DIRECT/CHUNK/MERKLE)로
        확장. 현재는 chunk_capable 게이트 1개 + 벤치/추정 2단 판정의 단순 구조라, 3번째 전략이 들어오면
        벤치 스키마(direct_total_seconds / chunk_total_seconds 쌍)부터 재설계해야 한다.
      · services/strategy/full_compare_strategy_planner.py — 계획 층 자격 판정
      · routes/agg_diff_route._resolve_execution_strategy — M61 로 갓 정리된 실행경로 배선
      · services/exact_diff/ 신규 실행기 1개 — 비교 대상 pk_range_chunk.py 가 947줄이다. 체크포인트
        (chunk_checkpoint), 재개(run_recovery), pushdown 정적판정(chunk_pushdown), 계획 게이트
        (evaluate_chunk_plan_guard) 까지 같은 수준의 부속을 다 갖춰야 운영 가능하다.
      · UI/설명 계층 — strategy_explain, 실행계획 카드(행번호·등급), 근거 스냅샷 스키마
    → 실질 규모는 PK_RANGE_CHUNK 도입과 동급(수천 줄 + 운영 부속). **1번의 손익 결론(이득 구간
      d ≲ 0.0004%)에 비해 명백히 과투자다.**

  3-3) 4방언 적용 규모
      ┌────────────┬──────────────────────┬──────────────────────┬─────────────────────────┐
      │ 방언       │ 진단 해시계약        │ 전수 canonical 어댑터│ Merkle 추가 소요        │
      │────────────┼──────────────────────┼──────────────────────┼─────────────────────────│
      │ postgresql │ 등록됨(PgHashContract)│ 등록됨               │ 추가 구현 0             │
      │ oracle     │ 등록됨(오늘 G7 완결) │ 등록됨               │ 추가 구현 0             │

      별개 선행 과제다.

  3-4) 어댑터 패턴·완료모듈 원칙과의 충돌
    · 어댑터 패턴: 충돌 없음. 방언 추가는 hash_contract._HASH_CONTRACTS 위임표 등록만으로 끝나고
      호출측 인라인 if/elif 를 강제로 막는 가드(_require_contract → HashContractUnavailableError)가 있다.
      다만 지적할 점 — CLAUDE.md 의 "구현체 교체는 config/model_config.py 한 파일" 원칙이 관리하는 축은
      SQL_PARSER / COLUMN_ANALYZER / UI_RENDERER / VALIDATOR 4개뿐이고, **비교 전략은 그 축 밖에 있다.**
      전략 구현체가 model_config 와 별개의 등록 체계(_HASH_CONTRACTS, AVAILABLE_COMPARE_STRATEGIES,
      _CANONICAL_ADAPTERS)로 3중 분산돼 있는 것 자체가 기존 부채이며, 신규 전략은 이 분산을 더 키운다.
    · 완료 모듈 존중: **전수비교 계층에 넣으면 충돌한다.** exact_diff/engine.py, pk_range_chunk.py,
      strategy_transition.py 는 완료·운영 모듈이고 M61 로 방금 배선을 정리한 참이다. 반면 진단 계층
      파라미터 조정은 충돌 없음. 이 점도 3-2 보다 3-1 을 택해야 하는 이유다.


■ 4. 실측 근거 — 기존 데이터로 충족되는가
  4-1) 판정: **충족된다. 신규 대규모 캠페인 불필요.**
    지시서 4번의 요구는 "Merkle 구현이 아니라 현재 방식의 한계를 수치로 확인"이다. 필요한 3개 수치가
    이미 전부 실측으로 존재한다.
      ┌──────────────────────────────────┬──────────────────────────────┬────────────────────────┐
      │ 필요한 수치                      │ 기존 실측                    │ 이번 조사에서의 역할   │
      │──────────────────────────────────┼──────────────────────────────┼────────────────────────│
      │ 하강 1레벨의 비용                │ wave2 선형 폭증(오라클 25만) │ 1-4 의 0.85초/경로,    │
      │                                  │ 1경로 1.02s /10경로 10.11s   │ "하강 > 전체 재스캔"   │
      │                                  │ /40경로 33.72s               │ 손익 역전 지점 산출    │
      │ 집계 스캔 단가 s                 │ 위 1경로 1.02s / 25만행      │ s ≈ 4.08 µs/행         │
      │ 전수비교 단가 E                  │ 1M cold: DIRECT 158s /       │ E ≈ 68~158 µs/행,      │
      │                                  │ CHUNK(50k) 68s               │ E/s ≈ 17~39            │
      │ 병목이 스캔인지 앱인지           │ 5천만행: DB 스캔 97%,        │ 왕복 수 증가 비용은    │
      │                                  │ 앱 0.8~2.5%                  │ 부차적이라는 전제 확인 │
      │ 그룹 수 증가의 비용              │ M65 회귀 scan:groups 4.3:1,  │ 팬아웃을 넓히는 건 싸고│
      │                                  │ cost 모델 scan 2.0/group 0.17│ 깊이를 더하는 건 비싸다│
      └──────────────────────────────────┴──────────────────────────────┴────────────────────────┘

  4-2) 기존 수치의 재해석 — 이번 조사가 새로 끌어낸 것
    · M65 의 "스캔이 그룹보다 압도적"은 지금까지 "그룹 수를 늘려도 싸다"로만 읽혔다. Merkle 문맥에서
      뒤집어 읽으면 **"레벨(=왕복)을 늘려도 그 자체는 싸지만, 레벨마다 스캔이 다시 붙으면 비싸다"**가
      되고, 이게 계층 하강이 실패하는 정확한 이유다. 왕복이 비싼 게 아니라 왕복마다 딸려오는
      **재스캔**이 비싼 것이다.
    · wave2 선형 폭증은 지금까지 "HASH_BUCKET 의 확장성 한계"로 기록돼 있었지만, 실제로는
      **_hash_path_predicate 의 OR 목록이 canonical 해시식을 분기마다 재평가시키는 구현 결함**이다.
      "활성 버킷 수에 선형"은 Merkle 이론의 본질적 성질이 아니다 — 이론상 계층 하강은 활성 노드가
      늘어도 스캔량은 오히려 줄어야 한다. 즉 이 수치는 "Merkle 이 필요하다"의 근거가 아니라
      **"현행 하강 구현을 고쳐야 한다"의 근거**다. BACKLOG N1 의 문제의식 방향을 정정해야 한다.
    · CTE/JOIN/윈도우 원본에서 폭증이 사라지는 현상(1.06~1.71초 평탄)이 이 해석을 뒷받침한다 —
      VIEW/WINDOW SORT 장벽이 재평가를 막아주는 것이므로, 병목의 정체가 옵티마이저의 식 재평가임을
      확인해준다.

  4-3) 추가 실측을 하지 않기로 한 판단과 그 근거
    · 결론의 민감도가 낮다. 유일한 불확실 변수 E/s 의 신뢰밴드는 15~40 인데, 현행 B=128 에서 2레벨이
      이득이 되려면 E/s > 129 여야 한다. 밴드 최댓값의 3배 이상이라 **어떤 추가 실측으로도 뒤집히지 않는다.**
    · 비용/위험이 크다. 5천만행급 합성 픽스처 2종(희소/광범위)은 오라클 asis/tobe 물리 호스트 공유
      환경에서 서로를 느리게 만들고, Oracle Free 23ai 는 병렬실행 자체가 에디션 제약으로 불가라
      "레벨 병렬 계산" 같은 최적화 가설은 애초에 이 환경에서 검증 불가다.
    · CLAUDE.md "구조 안정화 우선" 원칙에 따라 불필요한 실DB 부하를 만들지 않았다.
  4-4) 남은 실측 갭(정직한 명시)
    · E 와 s 를 **같은 DB·같은 테이블·같은 캐시 상태**에서 나란히 잰 값이 없다(E 는 1M cross-host cold,
      s 는 오라클 25만행). E/s 절대값의 정밀도는 낮다. 다만 4-3 대로 결론은 불변이다.
    · 밀도가 실제로 높을 때(d > 1%) 현행 하강이 얼마나 손해인지는 PLAN_HOLD_DENSE(0.5) 가 먼저 끊어서
      실측 자체가 없다. 손해 구간의 실측 데이터는 구조적으로 수집 불가하다.
    · 지역성 있는 범위 트리(1-2-(b))의 우위는 **PK 인덱스 범위 스캔이 실제로 걸린다는 미검증 전제**
      위의 이론값이다(0-2 참조). 이 전제를 검증하는 것이 어떤 Merkle 실측보다 우선순위가 높다.


■ 구조적 문제점 / 운영상 위험
  1) heuristic 하드코딩 증가 — 신규 전략은 임계값을 최소 6개 더 낳는다(레벨 수, 레벨별 팬아웃, 리프 폭,
     밀도 중단, 활성 상한, 왕복 예산). 현행 MultiScopeConfig 만 해도 근거가 서로 다른 상한 13개가 한
     dataclass 에 섞여 있다. 더 얹으면 "왜 이 값인가"를 아무도 설명 못 하는 상태가 심화된다.
  2) scoring 미성숙 — choose_compare_strategy 는 아직 가중치 없는 단락 평가(벤치 있으면 벤치, 없으면
     예상시간 1개 임계)다. 3번째 전략이 들어오면 벤치 스키마(direct/chunk 2열)부터 무너진다. Merkle
     도입은 이 미성숙한 scoring 을 확장 없이 밀어붙이게 만든다.
  3) 표시 상한이 전략 깊이를 지배하는 결합 — max_mismatch_cells_per_wave = 180 의 근거가 주석상
     "통계 표시 상한 200 미만"이다. **UI 표시 제약이 진단 알고리즘의 국소화 해상도를 결정하고 있다.**
     1-5 에서 계산한 실효 이득 구간(불일치 180건)이 사실상 이 숫자에서 나온다 — 알고리즘 파라미터가
     아니라 화면 파라미터가 전략 성능의 상한을 정하고 있는 셈이라, 계층 논의 이전에 끊어야 할 결합이다.
  4) explainability — 이 부분은 상대적으로 양호하다. WaveSummary(present_cells / mismatch_cells /
     mismatch_density / stopped) 와 stopped_reason, hash_contract version 이 근거로 남는다. 다만 계층이
     깊어질수록 "이 결과가 몇 레벨을 거쳐 어떤 경로로 좁혀졌는가"를 사용자에게 설명하는 UI 는 없다.
  5) 오탐 전파 위험(범위 트리 한정) — 0-3 참조. 정렬 역전 아티팩트가 계층 하강으로 복제·확정된다.
     자동 경로(문자 PK → 네이티브 키 → DIRECT merge 강제)는 면역이지만 명시 key_src/key_tgt 경로는 취약.
  6) 보안 — 신규 위험 없음. 해시 경로는 사용자 값 보간 없이 표현식만 다루고 범위값은 typed bind 다.
     경계값 숫자 리터럴 삽입은 서버 산출값 한정이라는 기존 원칙이 유지되면 문제없다.
  7) 테스트 가능성 — 진단 계층은 compare_fn/bounds_fn 주입 구조라 단위 테스트가 쉽다(양호). 반면
     전수비교 계층 신규 실행기는 라이브 DB 없이는 검증이 어렵다(pk_range_chunk 선례).


■ 권장 대응책 (우선순위 순 — 전부 Merkle 신규 구현보다 싸고 효과가 크다)
  P1. _hash_path_predicate 의 OR 목록 재평가 제거
      wave2 선형 폭증(0.85초/경로)의 원인이다. 대안 후보: (a) 활성 경로 제한을 걷고 레벨 전체를 한 번에
      GROUP BY(HB1..HBn) 재집계 — 비용이 활성 수와 무관한 상수 1스캔이 된다, (b) 상위 레벨 bucket 번호
      집합을 IN 리스트 1개로 접어 분기 수를 줄인다. 이것만 해결돼도 1-2-(a) 의 손익식에서 k_i 배수가
      사라져 2~3레벨 하강이 처음으로 경제적이 된다. **Merkle 도입 이전에 반드시 선행.**
  P2. pk_indexed 실측 배선(인덱스 카탈로그 조회)
      현재 PK 존재 = 인덱스 존재로 하드코딩(key_evidence.py:191, grid_helpers._mvDerivePkProfile).
      범위 트리가 해시 트리보다 유리한 유일한 근거(지역성)가 이 플래그에 달려 있는데 지금은 항상 참인
      무의미한 값이다. 이걸 실측으로 바꾸는 것이 어떤 Merkle 작업보다 이득이 크다.
  P3. 표시 상한과 전략 깊이의 결합 분리
      max_mismatch_cells_per_wave(180) 를 "화면 표시 상한"이 아니라 "국소화 해상도 예산"으로 재정의하고
      별도 값으로 분리한다.
  P4. 팬아웃 재조정 실험 (코드 변경 0 — MultiScopeConfig 주입만)
      1-3 의 표대로 B=128 은 하강용으로 과도하게 넓다. B=32 또는 16 으로 낮춘 A/B 를 기존 PG↔PG
      또는 오라클 픽스처에서 돌려보면, 신규 코드 없이 "계층을 유용하게 만드는" 효과를 확인할 수 있다.
  P5. BACKLOG N1 항목 문구 정정
      "HASH_BUCKET 은 버킷 개수가 고정이라 계층이 없다"는 전제를 "계층은 이미 wave 로 구현돼 있고,
      문제는 하강 1레벨의 비용이 전체 스캔 이상이라는 점"으로 교체한다. 그대로 두면 다음 담당자가
      이미 있는 것을 다시 설계한다.
  (하지 말 것) 두 canonical 계약(exact_diff / diagnosis) 통합 — 저장 run·resume 상태를 전부 무효화하는
      고위험 변경인데, 얻는 것은 이론적 해시 재활용뿐이다. 2-4 참조.


■ 지금 구현 여부 : **보류**
  근거:
   (1) 이득 구간이 구조적으로 좁다 — 5천만행 기준 불일치 180건(d ≈ 0.0004%) 이하에서만 유효하고,
       그마저 첫 1레벨에서 대부분 회수된다. 지역성 없는 계층의 총 국소화 상한은 ≈ E/s ≈ 35배로,
       팬아웃·깊이를 어떻게 조합해도 이 벽을 넘지 못한다(E/s 밴드 15~40 전 구간에서 결론 불변).
   (2) 이미 있다 — HASH_BUCKET wave(HB1..HBn + level_salt + 부모경로 보존 + 일치 가지치기 + SUM 해시의
       부모=자식합 성질)와 KEY_RANGE(8분할 → midpoint 이분 → LEVEL-BATCH)가 각각 해시형·범위형
       Merkle tree 다. 신규 전략 ID 를 하나 더 만드는 것은 같은 것을 두 번 짓는 일이다.
   (3) 병목이 다른 데 있다 — 실제 관측된 한계(wave2 선형 폭증)의 원인은 계층 부재가 아니라
       _hash_path_predicate 의 OR 재평가라는 구현 결함이며, 이건 P1 로 훨씬 싸게 해소된다.
   (4) 전제가 미검증이다 — 범위형 계층의 유일한 우위(지역성)가 pk_indexed 에 달려 있는데 그 값은
       인덱스 실재를 확인하지 않는다. 이 상태에서 Merkle 을 얹으면 PK_RANGE_CHUNK 와 똑같이 확인되지
       않은 전제를 물려받는다.
   (5) 비용이 과하다 — 전수비교 계층 신설 시 pk_range_chunk.py(947줄) 동급 규모 + 완료 모듈
       (engine/transition/M61 배선) 수정이 불가피해 "완료 모듈 임의 리팩토링 금지"·"구조 안정화 우선"
       원칙과 정면으로 충돌한다.
  재개 조건: P1(OR 재평가 제거)과 P2(pk_indexed 실측)가 끝난 뒤 P4 팬아웃 A/B 에서 2~3레벨 하강이
  실제로 이득을 내는 것이 관측되면, 그때 "신규 전략"이 아니라 "기존 wave 파라미터 확장"으로 재검토한다.
