■ 요약(결론 먼저)
  1. 오라클 ORA-00911 은 __BKT / __RNG 에서 실측 재현됨(SQL 레벨). 별칭만 문자 시작으로
     바꾸면 동일 SQL 이 정상 실행된다(별칭이 유일 차단 요인 — SQL 레벨).
  2. 그러나 이 별칭들은 현재 오라클 라이브 경로에 '도달하지 않는다'.
     실 route(POST /diagnosis/analyze, 8000·인증 ON, 실 오라클)는 CHUNK_KEY/MATCH_KEY 확정
     실패로 HOLD_NO_SAFE_STRATEGY 에서 멈춘다 → KEY_RANGE / HASH_BUCKET 미실행.
     선행 차단 결함 2건이 별칭보다 앞선다(아래 §4).
  3. 소비자는 전부 '이름 기반'이 맞다. 개명 시 소비자 동반 수정 필수임을 실 소비 경로로 실증
     (별칭만 개명 → "원본 SQL 결과에 필요한 컬럼이 없습니다: __BKT" 오류).
  4. 규모: __BKT/__RNG 개명은 소규모(운영 2파일 9줄 + 테스트 3파일). __HB/__KH/__RH 는
     오라클 hash 계약 자체가 PostgreSQL 전용이라 개명 실익 0 → 별도 대형 작업에 포함해야 함.
  5. 권고: 이번에 '별칭 개명 단독'은 실익이 없다. 우선순위는 ① 정적 회귀 테스트(비인용 밑줄
     별칭 금지) ② key_evidence._columns 방언 위임(진짜 차단요인) 이며, __BKT/__RNG 개명은
     ①과 함께 묶어 처리하는 것이 합리적이다.

      (router.py:194 · multi_scope.py:434 와 동일 호출 형태)

                     이 테스트를 넣으면 key_range/hash_bucket 이 즉시 실패하므로,
                     __BKT/__RNG 개명(+상수화)은 이 작업과 '한 묶음'으로 처리하는 것이 자연스럽다.
      2순위(중간)  : key_evidence._columns 방언 위임(어댑터 fetch_column_metadata).
                     오라클 KEY_RANGE 를 실제로 열어주는 유일한 선행 조치이며,
                     열리는 순간 __BKT/__RNG 가 라이브 경로가 되므로 1순위와 함께 가야 안전하다.
      3순위(큼)    : HASH_BUCKET canonical hash 계약의 오라클 이식(STANDARD_HASH/RAWTOHEX 등).
                     별칭 개명은 이 작업의 일부로 흡수. 단독 진행 금지(무의미).

  ▸ 즉답: "이번에 바로 수정 가능한 규모인가?" → __BKT/__RNG 한정이면 예(소규모).
          다만 단독으로는 실익이 없으므로 1순위(정적 회귀 테스트)와 묶어서 진행하고,
          __HB/__KH/__RH 는 3순위 작업으로 분리하는 것을 권고한다.
