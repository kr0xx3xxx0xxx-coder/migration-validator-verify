1. 무엇이 문제였나
────────────────────────────────────────────────────────────────────────
개별검증 4단계에서 '▶ 통계검증 실행'을 누르면, 실행이 끝날 때까지 화면에 보이는 것은
하단 커맨드바의 스피너('실행 중...') 하나뿐이었다. 실행 후 화면이 4단계에 머무는 정책
(자동 5단계 이동 금지) 때문에, 실행 상태를 알려줄 수 있는 요소들이 전부 5단계 pane 에
있어 .mv-pane-hidden 으로 가려졌기 때문이다.

특히 아까운 것은 GROUP BY 를 2개 이상 선택한 다중 세트 실행이었다. 클라이언트 루프
(_runExecutePlanSets)가 '세트 1/2 실행 중 — GROUP BY …' 라는 정확한 진행 문구를 이미
만들고 있었는데, 그 문구를 #executeOut(5단계 결과 카드)에 넣고 있어서 사용자는 한 번도
볼 수 없었다. 선행 진단(SINGLE-STEP4-INLINE-PROGRESS-FEASIBILITY-DIAGNOSE)은 이것이
같은 계열로 이미 두 번 고쳐진 결함(실행 오류 → #mvExecStepError, 실행 성공 요약 →
#mvExecStepResult)의 세 번째 사례라고 지적했고, 이번 작업은 그 권장안 A-3+A-1 을
그대로 구현한 것이다.

이번 작업은 처음부터 끝까지 '표시 계층'만 건드린다. 백엔드(services/, routes/)는 한 줄도
바꾸지 않았고, 판정 로직·자동 이동 정책도 그대로다.

────────────────────────────────────────────────────────────────────────
2. 무엇을 만들었나
────────────────────────────────────────────────────────────────────────
4단계 pane 안에 #mvExecStepProgress 라는 전용 영역을 하나 새로 만들었다. 기존
#mvExecStepError(실패), #mvExecStepResult(성공 요약)와 같은 자리·같은 방식이며, 세 영역은
언제나 상호배타로만 노출된다. 즉 '진행 중' 박스는 성공 요약이나 오류가 뜨는 순간 사라진다.

박스에 담은 것은 두 가지뿐이다.
  ① 경과시간 — 클라이언트 시계 기준 1초 카운트업. 60초를 넘으면 '1분 05초' 형태.
  ② 지금 무엇을 하는 중인지 — 단일 실행이면 '원본·목적지 통계 SQL 실행 중…',
     다중 세트면 '세트 1/2 실행 중 — GROUP BY CHANNEL_CD' 처럼 실제 세트/축 이름.
     세트 문구가 나오기 전 구간에는 '실행 계획(GROUP BY 세트) 생성 중…' 을 넣어
     무음 구간을 없앴다.

일부러 만들지 않은 것도 분명히 적어 둔다. 진행률(%)과 추정 진행바는 넣지 않았다.
통계검증은 GROUP BY 집계 SQL '한 번'의 실행이라, 집계가 끝나기 전에는 서버조차 자기
위치를 모른다. 그 상태에서 퍼센트를 그리면 근거 없는 숫자가 된다. 그래서 박스 안에
"진행률(%)은 표시하지 않습니다 — 집계 SQL 한 번의 실행이라 완료 전에는 중간 진행 신호가
없습니다" 라는 사유를 함께 적었다. 추정 진행바(A-2)는 근거 표기 설계가 확정될 때까지 보류다.

종료 처리는 6군데에 걸어 두었다: runExecute 의 finally(단일 세트), plan-sets 경로의
finally, 조기 중단(_execAbort), 재실행 시작(resetExecuteResultOnly), 오류 표시 시점,
성공 요약 표시 시점. 카운트업 타이머(setInterval)도 같은 지점에서 반드시 해제한다.

3. 검증하다가 추가로 고친 두 가지
────────────────────────────────────────────────────────────────────────
처음 구현을 라이브에 올려 찍어 보니, 박스는 분명히 렌더되는데 스크린샷에 안 나왔다.
원인은 단순했다. 4단계는 통계검증 SQL 카드가 길고, 실행 버튼은 화면 하단에 고정된
커맨드바라서 사용자가 스크롤을 내릴 이유가 없다. 그래서 새 박스가 뷰포트 '아래'에
그려지고 있었다. 표시를 추가해도 보이지 않으면 고친 게 아니므로, 오류/성공요약 영역과
같은 패턴으로 최초 1회 scrollIntoView 를 넣었다. 문구가 바뀔 때마다 스크롤하면 사용자
스크롤을 뺏으므로 '최초 1회'로 제한했다.

그다음 프레임을 다시 보니 이번엔 박스 마지막 줄(경과시간)이 하단 고정 커맨드바에 덮였다.
block:'nearest' 가 요소 하단을 뷰포트 하단에 맞추는데, 그 자리에 fixed 커맨드바가 떠 있기
때문이다. 실측값으로 확인했다 — top=986 / bottom=1072 인데 커맨드바 상단이 1053.
block:'center' 로 바꾼 뒤 top=887 / bottom=976 으로 내려앉아 겹침이 사라졌다.

두 건 모두 "표시는 했는데 사용자는 못 본다"는 같은 종류의 함정이고, 스크린샷이 아니라
좌표 실측(getBoundingClientRect + 커맨드바 rect 비교)으로 판정했다.

5. 남은 위험과 솔직한 한계
────────────────────────────────────────────────────────────────────────
· 진행 표시가 생기면 사용자는 '중단' 버튼을 기대하게 된다. 그런데 4단계 실행은 지금
  cancel_token 을 넘기지 않아 중단할 수 없다(진단서에 기록된 기존 한계). 이번 범위 밖이며,
  기대와 기능의 간극으로 남는다.
· 경과시간은 클라이언트 시계다. 서버 처리시간(processing_ms)과 같지 않으며 네트워크·렌더가
  포함된다. 그래서 문구도 '경과'라고만 적었다.
· '세트 i/N' 은 세트 단위 진행일 뿐이다. 한 세트 내부의 진행은 여전히 알 수 없다.
· 관측 하니스 주의(제품 결함 아님): 일부 증적 JSON 의 run.elapsed_sec 이 180초대인 것은
  playwright 의 element screenshot 이 '방금 사라진 요소'를 기다린 하니스 대기 때문이다.
  실제 실행 소요는 같은 파일의 run.exec_wall_from_frames_sec(1.3~2.9초)가 정확하다.
· 라이브 회차 중 COUNT 단계가 간헐적으로 ERROR 로 떨어진 경우가 있었다(재실행 시 정상).
  동시 세션이 같은 오라클·포트를 쓰는 환경 경합으로 판단했고, 성공 회차만 증적으로 채택했다.
