────────────────────────────────────────────────────────────────────────────
1. 무엇이 왜 깨졌나 — 재현으로 확정한 근본 원인
────────────────────────────────────────────────────────────────────────────

증상은 (f) 복합 변형에서만, 3·4단계 진입 시 각 1회 서버 로그에 찍히는 다음 한 줄이었다.

    profile DB 실행 실패 (join=False): ORA-00904: "REGION_NM": invalid identifier

발원지는 services/column_profile_service.py 의 collect_column_profiles() 예외 처리다.
문제는 "CTE 밖에서 조인 컬럼을 참조해서" 가 아니라, 그 한 단계 앞의 **파서 평탄화** 였다.

(f) 원문(scripts/dev_e2e/scatter_mismatch_perf_measure.py 의 변형 그대로):

    INSERT INTO NXDNP.MV_SCATTER_TGT (..., REGION_NM)
    WITH JOINED AS (
      SELECT s.PK_STR, ..., s.STATUS_CD, d.REGION_NM
        FROM NXDNP.MV_SCATTER_SRC s
        LEFT OUTER JOIN NXDNP.MV_SCATTER_DIM d ON s.REGION_CD = d.REGION_CD)
    SELECT ..., REGION_NM FROM JOINED WHERE STATUS_CD IN ('G01'~'G05')
    UNION ALL
    SELECT ..., REGION_NM FROM JOINED WHERE STATUS_CD IN ('G06'~'G10')

이 SQL 을 실제로 파싱해 보면(로컬 재현, 실 DB 불필요):

    from_clause : {'table': 'JOINED', 'alias': ''}      ← 최종 FROM 이 CTE 이름
    joins       : []                                     ← CTE 안의 JOIN 은 포착되지 않는다
    where       : "STATUS_CD IN ('G01'...'G05')"         ← 첫 UNION 브랜치 조건만
    columns     : REGION_NM → 'REGION_NM'                ← 별칭(d.) 없는 CTE 출력명

그리고 single_validation_analyze_service.py 는 물리 테이블 검증을 위해 CTE 이름을
**CTE 내부의 첫 물리 테이블로 치환**한다(기존 로직, 626~638행).

    from_table : JOINED → NXDNP.MV_SCATTER_SRC,  from_alias : '' ,  joins : [] 유지

여기까지가 정상 설계다. 문제는 이 치환된 from_table 을 그대로 쓰는 **보조수집 SQL** 이다.
REGION_NM 은 CTE 안에서 LEFT OUTER JOIN 으로 가져온 MV_SCATTER_DIM 의 컬럼이라
MV_SCATTER_SRC 에는 없다. 그런데 프로파일 SQL 은 이렇게 만들어졌다.

    WITH SRC AS (
      SELECT REGION_NM AS REGION_NM, AMT AS AMT, QTY AS QTY
      FROM   NXDNP.MV_SCATTER_SRC
      WHERE  STATUS_CD IN ('G01', ...))
    ...
    → ORA-00904: "REGION_NM": invalid identifier

즉 컬럼 하나가 원인인데 쿼리 한 건이 통째로 죽어, **정상적으로 수집됐어야 할 나머지
컬럼(AMT·QTY)의 근거까지 함께 유실**됐다. 이것이 "폴백으로 정상 완료되지만 후보
프로파일 품질이 떨어진다" 는 관측의 실체다.

(c) LEFT OUTER 단독에서 발생하지 않은 이유도 같은 그림에서 설명된다. (c) 는 CTE 가
없어 파서가 JOIN 을 그대로 포착하므로(joins=1), 프로파일 SQL 이 JOIN 을 복원해
d.REGION_NM 을 정상 참조한다. 로그의 join=False / join=True 가 그 차이를 그대로 드러낸다.

같은 from_table 을 쓰는 보조수집 경로는 셋이고, 전부 같은 결함을 공유했다.
  ① 후보 프로파일 COUNT/DISTINCT   (collect_column_profiles)          — WARNING 로 노출
  ② 값 샘플 LIMIT 100 SELECT       (resolve_candidate_sample_values)  — DEBUG 라 조용히 실패
  ③ 날짜 버킷 MIN/MAX·정확집계     (_collect_date_bucket_profiles)    — (f) 에 날짜 컬럼이 없어 미발현

1단계(/analyze)에서 이 오류가 안 보이던 것은 이미 "CTE 면 프로파일 샘플링 전체 생략"
게이트가 있었기 때문이고(1465~1475행), 그 게이트가 없는 3·4단계 재확정 경로
(/validation-sets/preview → finalize_recommendation_postcount)에서만 노출됐다.

2. 어떻게 고쳤나 — "조회 가능한 컬럼만" 화이트리스트
────────────────────────────────────────────────────────────────────────────

선택지는 둘이었다. (가) CTE 면 보조수집을 통째로 생략(1단계 게이트를 3·4단계에 복제),
(나) 조회 불가능한 컬럼만 골라 제외. (가)는 오류는 없애지만 품질은 그대로 0 이다.
(나)를 택했다 — 지침 요구사항 3의 "그런 컬럼을 안전하게 제외" 방향이며, (f) 기준으로
0개 → 2개 컬럼이 실제로 수집되기 때문이다.

핵심은 "CTE 출력 컬럼이 어느 테이블 소속인지" 를 **AST 로 정확히 판정**하는 것이다.
추측(이름 규칙·substring)은 쓰지 않는다.

  services/sql_cte_utils.py — resolve_flattened_cte_column_scope() 신규
    CTE 본문의 FROM/JOIN 에서 {별칭 → 물리 테이블} 을 만들고, CTE 출력 컬럼마다
    소속 테이블을 판정한다.
      · base 테이블 소속 단순 컬럼            → resolvable {출력명: base 컬럼명}
      · JOIN 상대 테이블 / 파생(함수·윈도우) / '*' → unresolvable
    파싱 실패·추적 불가(파생 FROM, CTE 본문이 UNION 등)면 analyzed=False 로 돌려주고,
    소비측 계약상 resolvable 이 비어 보조수집이 전부 생략된다 —— 잘못된 SQL 을 발행하지
    않는 안전측 폴백이다. 기존 sqlglot 타임아웃 가드(parse_one_guarded)를 그대로 쓴다.

  services/single_validation_analyze_service.py
    CTE 평탄화가 일어난 경우에만 위 판정을 수행해 parse_result["profile_source_scope"] 에
    싣는다. 화면(클라이언트)은 이미 parse_result 를 통째로 되돌려 보내므로
    (ui/validation_plan_renderer.py 의 /validation-sets/preview payload), 3·4단계까지
    추가 배선·요청 필드·화면 수정 없이 전달된다.
    같은 값을 1단계 값 샘플 조회(resolve_candidate_sample_values)에도 넘긴다.

  services/candidate_postcount_finalize.py
    from_clause_from_parse() 가 scope 를 from_clause 에 함께 실어, 이 from_clause 를
    쓰는 소비자 셋이 자동으로 같은 규약을 따르게 한다(개별검증 3·4단계와 원클릭 공통).

  services/column_profile_service.py
    collect_column_profiles() / resolve_candidate_sample_values() 가 scope 를 화이트리스트로
    적용한다. 제외된 컬럼은 warnings 와 INFO 로그에 사유를 남긴다(조용한 유실 금지).
    남는 컬럼이 하나도 없으면 SKIPPED —— DB 로 SQL 을 보내지 않는다.

scope 가 붙지 않는 일반 SQL 에서는 이 블록들이 전부 no-op 이다(무회귀).

6. 남은 제한과 부수 발견
────────────────────────────────────────────────────────────────────────────

6-1. (f) 의 프로파일 표본은 첫 UNION 브랜치 조건만 반영한다 (기존 동작, 미변경)

  파서가 UNION 의 첫 브랜치 WHERE 만 where_clause 로 남기므로, 프로파일 SQL 도
  WHERE STATUS_CD IN ('G01'~'G05') 가 붙은 5만행 표본이 된다. 그래서 (f) 의
  AMT distinct 7,429 는 (c) 의 9,973 보다 작다. (d) UNION ALL 변형도 수정 전부터
  동일하게 동작해 왔고, 프로파일은 애초에 5만행 표본 기반 보조 신호라 판정 경로에
  미치는 영향은 없다. 이번 수정 범위 밖이라 건드리지 않았다.

6-2. REGION_NM 은 여전히 프로파일되지 않는다 (설계상 정당)

  평탄화된 base 테이블에 없는 컬럼이므로 이 경로로는 수집이 불가능하다. 원본 SQL 을
  통째로 감싸는 wrapping 프로파일(COUNT/통계검증이 쓰는 방식)을 도입하면 수집 가능하지만,
  3·4단계 요청(/validation-sets/preview)은 원본 SQL 을 서버로 보내지 않아 요청 스키마와
  화면 payload 변경이 필요하다. 병행 작업이 ui/tabler_renderer.py 를 수정 중이라
  이번 범위에서는 하지 않았다. 필요하면 별도 항목으로 다룰 사안이다.

6-3. [부수 발견·미수정] extract_cte_lineage() 가 현행 sqlglot 에서 항상 빈 맵을 돌려준다

  services/sql_cte_utils.py::extract_cte_lineage 는 최종 SELECT 의 FROM 을
  `main.args.get("from")` 으로 읽는데, 현행 sqlglot 30.8.0 의 Select 는 이 키를
  **"from_"** 로 갖는다(실측: args keys = [..., 'from_', 'joins']). 그래서 final_alias_src
  가 항상 비고, alias_to_physical / cte_derived_cols / cte_explicit / cte_star /
  ambiguous_aliases 가 전부 빈 채로 반환된다.

    확인 : WITH RANKED AS (SELECT s.A, ROW_NUMBER() OVER(...) AS B FROM SRC s)
           SELECT r.A, r.B FROM RANKED r
           → cte_names={'RANKED'} 인데 나머지 5개 맵이 전부 비어 있음

  영향: single_validation_analyze_service.py 의 "CTE alias 컬럼은 최종 SELECT 컬럼검증에서
  제외" 로직(1032~1043행)이 사실상 동작하지 않는다. 고치면 지금까지 잠들어 있던 필터가
  깨어나 스키마 검증 판정이 바뀔 수 있어(차단/해제 방향 모두 가능) 별도 검증이 필요하다.
  이번 작업 범위가 아니라 수정하지 않았고, 신규 함수
  resolve_flattened_cte_column_scope 는 이 함정을 피하도록 "from" / "from_" / find(exp.From)
  세 경로를 모두 시도한다.
