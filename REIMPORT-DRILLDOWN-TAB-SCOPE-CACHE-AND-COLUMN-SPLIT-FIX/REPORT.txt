0단계 — 테스트 데이터 준비 : 요청 INSERT 실행하지 않음(안전 확인 결과)
────────────────────────────────────────────────────────────────────────
지시받은 INSERT :
    INSERT INTO NXDNP.MV_CSPK_TGT (PK_STR, AMT, QTY, ITEM_NM, STATUS_CD)
    SELECT REGION_CD || '-' || LPAD(SEQ_NO, 6, '0'), AMT, QTY, ITEM_NM, STATUS_CD
    FROM NXDNP.MV_CSPK_SRC

읽기 전용 실측(SELECT만, 쓰기 0회)으로 확인한 사실 :
  [1] 현재 행수    SRC=1,000,000  TGT=990,000  (차이 10,000)
  [2] TGT 제약     PK_MV_CSPK_TGT PRIMARY KEY (PK_STR) — 존재
  [3] 충돌 예측    INSERT 가 만들 PK_STR 1,000,000건 중 990,000건이 이미 TGT 에 존재
                   → ORA-00001 로 문장 전체 롤백(영향행수 0). 실행해도 아무 효과 없음.
  [4] 누락행 분포  MOD(g,100)=0 인 10,000행의 STATUS_CD 는 전부 'P' 한 값
  [5] 그룹별 판정  A 250,000/250,000 일치 · C 250,000/250,000 일치 · X 250,000/250,000 일치
                   P 250,000/240,000 차이 10,000 → 불일치

판단 :
  ① 이 INSERT 는 PK 제약 때문에 반드시 실패한다(영향행수 0).
  ② 제약을 우회해 성공시키면 P 그룹 누락이 0 이 되어 '불일치 그룹 1건' 재현 조건 자체가 사라진다.
     즉 재현을 만드는 INSERT 가 아니라 재현을 없애는 INSERT 다.
  ③ 참값 10,000건 규칙은 아래 2개 회귀 스크립트가 의존한다 —
       scripts/dev_e2e/pk_range_chunk_sort_order_alignment_verify.py (TRUTH_MISSING = 10000)
       scripts/dev_e2e/character_pk_silent_false_match_1m_reproduce.py
     성공 시 두 스크립트의 기준이 동시에 깨진다.
  ④ 현재 픽스처가 이미 스크린샷 조건 그대로다 — 일치 그룹 3건(A/C/X) = 버튼 라벨 '(3건)',
     불일치 그룹 P 1건 · 재이관 대상 10,000건(100건 초과).
  결론 : INSERT 미실행. 백업 테이블도 생성하지 않음(불필요). asis 는 애초에 미접촉.
         이 상태 그대로 Before/After 실측을 수행했다.

1단계 — 조사 결과

(a) '일치 행 숨기기' 토글 상태의 저장 위치
    이 화면에는 숨김 상태가 '두 개' 있고 서로 동기화되지 않았다.
      - 클라이언트 모드 : window._execHideMatched (execute_result_renderer.py)
      - 서버 페이지 모드 : window._execSrv.includeMatched → /stats-result/page 의 mismatch_only
    5단계 결과는 저장 결과(result_page)가 있으면 '서버 페이지 모드'로 동작한다(실측 srvMode=true).
    버튼 라벨은 renderExecute 의 클라이언트 템플릿 hideLabel('일치 행 숨기기 (N건)')로 한 번 찍히고
    끝이라, 서버 모드 기본값(일치 행 숨김)과 처음부터 반대였다.
    → 리셋되는 지점은 없었다. 라벨이 처음부터 실제 상태를 반대로 표기하고 있었다.

    실제로 표시가 바뀌는 지점은 따로 있었다 :
    항목 탭(전체/COUNT/AMT/QTY)은 _execSetColFilter → _execRenderResultPage 로 이어지는데,
    _execRenderResultPage 는 서버 모드를 전혀 보지 않고 클라이언트 행(_execResultRows)으로
    tbody 를 통째로 덮어쓴다. 그래서 탭을 한 번 다녀오면 서버가 숨기고 있던 일치 행(A/C/X)이
    되살아났다. 사용자가 '토글이 조용히 리셋된다'고 인지한 실제 현상이 이것이다.

(b)(c) 탭별 드릴다운 캐시/scope
    탭은 그룹 목록을 필터링만 하며, 드릴다운은 탭별 상태를 갖지 않는다.
    캐시는 이미 존재한다(window._mvPkPageCache, 키 = run_id|scope_col|scope_val|view|page).
    그런데 실측에서 매 클릭마다 재조회가 일어났고, 원인은 탭이 아니라 준비 캐시 게이트였다 :
      _mvPkEnsurePrepared 는 status === 'READY' 일 때만 캐시를 재사용한다.
      원본 100만행은 stream 준비라 prepare 가 즉시 READY 가 아니라 PREPARING(run_id 는 이미 바인딩)
      으로 응답한다 → 캐시 미적중 → 그룹을 열 때마다 /agg-diff/prepare 재 POST
      → 서버는 fingerprint 재사용 대상(READY/PREPARING)이 아닌 상태에서 새 job 을 만든다(reused:false)
      → run_id 가 매번 바뀐다 → run_id 를 키에 포함하는 _mvPkPageCache 도 통째로 무효
      → 결과적으로 항상 전량 재조회 + 서버에 중복 run 누적.
    결정적 증거 : C3(같은 '전체' 탭에서 3회차 클릭)도 C1 과 동일하게 새 run_id 로 전량 재조회됐다.
    → 탭마다 다른 scope 를 조회하는 구조가 아니다. 탭과 무관한 캐시 결함이므로 버그로 분류하고
      캐시를 적용했다(요구사항 C 의 첫 번째 갈래).

A. 상세 레코드표 원본/목적 열 분리 (ui/tabler_renderer.py · _mvPkLoadPage)
   - 값 셀 _mvPkCellHtml('원본값 → 목적값') → _mvPkCellSplit(원본 셀 / 목적 셀 2개)

   - 범례 → _mvSrcTgtLegend('arrow') → ('color'). 목적 단독 뷰는 기존 'tgt_only' 유지.
   - 전부 표본 조기중단 대표 레코드표(_mvRiApplySampleStop)가 이미 쓰던 기존 헬퍼를 재사용했다.
     새 렌더러·새 색상·새 헤더 용어를 만들지 않았다(헤더는 컬럼명 + 기존 PK 배지 + DB 코멘트 관례).
   - 강조 규칙 유지 확인(렌더러 직접 실행) :
       목적 미존재  <td …background:#eaf2ff>1,100</td><td …background:#e6f7f3;color:#C2410C;font-weight:700>-</td>
       값 불일치    목적 셀 999 에 color:#C2410C;font-weight:700
       일치 컬럼    목적 셀 강조 없음
   - 위쪽 '집계값 불일치' 요약표는 손대지 않았다(스크린샷으로 확인).

B. 토글 라벨과 실제 표시 상태 정합 (ui/execute_result_renderer.py)
   - _execHideMatchedEffective() : 모드 무관 단일 판독(서버 모드면 !includeMatched, 아니면 _execHideMatched)
   - _execSyncToggleLabel() : 실효 상태에서 라벨 재계산. _execRenderResultPage 와 _execSrvGo 양쪽에서 호출
     → 초기 렌더·토글·탭 전환·페이지 이동 어디를 거쳐도 라벨이 실제 상태를 따라간다.
   - 서버 모드 전용 어휘('불일치만 보기'/'일치 포함 보기') 제거 → 기존 라벨 쌍
     ('일치 행 보기 (N건)'/'일치 행 숨기기 (N건)')으로 통일. 새 용어 추가 아님.
   - _execRenderResultPage 의 필터 기준을 _execHideMatchedEffective() 로 교체.
   - 서버 모드에서 '전체'(항목 필터 해제)는 _execSrvGo 로 서버 저장 결과 페이지에 복귀 →
     클라이언트 행으로 조용히 갈아끼우며 일치 행이 되살아나던 경로 제거.
   - _execSrvGo 가 tbody 를 교체한 뒤 _mvWireRowsFromCache 로 행 클릭 배선 재적용
     (서버 렌더 후 그룹 행이 클릭 불가로 남던 잠재 갭도 함께 해소).
   선택 이유 : '탭마다 별도 상태'가 아니라 '모드마다 별도 상태'가 문제였고, 두 상태를 하나의 실효
   판독으로 모으는 쪽이 라벨/필터/렌더 3곳의 불일치를 한 번에 없앤다. 탭은 상태를 갖지 않는다.

C. 드릴다운 준비 결과 재사용 (ui/tabler_renderer.py · _mvPkEnsurePrepared)
   - 재사용 판정을 status==='READY' 한정 → 'run_id 가 확정된 준비 상태'로 확장
     _MV_PK_REUSABLE_STATUS = { READY, PREPARING, EARLY_STOPPED, EARLY_STOPPED_HIGH_MISMATCH_ESTIMATE }
   - HOLD/FAILED/CANCELLED/INTERRUPTED_RESUMABLE 은 제외 → 재준비·'이어서 실행' 경로 보존.
   - 재사용한 run 의 store 가 서버 재기동으로 사라진 경우는 _mvPkLoadPage 의 'PK index' 자동
     재-prepare(dd455c0)가 그대로 복구한다.
   - 기존 캐시 메커니즘(_mvPkState / _mvPkPageCache)만 사용했다. 새 캐시를 만들지 않았다.
