1. 배경과 실제 결함
────────────────────────────────────────────────────────────────────────
백로그 P9: ui/grid_helpers.py `_mvBuildStatsScaleProfile()` 이 `remote: true` 를 고정 전송해
실제 접속이 로컬이든 원격이든 항상 '원격' 으로 보고했다. 같은 하드코딩을 목록 규모 셀
(`_mvComputeStatsScale`)도 공유한다.

확인 결과, 두 함수의 하드코딩은 '공유' 라기보다 단일 출처였다.
`_mvComputeStatsScale()`(ui/grid_helpers.py:1025)은 자체 profile 을 만들지 않고
`_mvBuildStatsScaleProfile()` 을 그대로 호출하며, 실행계획 카드
(`_mvRenderStrategyPlan`, ui/tabler_renderer.py:27675)도 profile 미지정 시 같은 빌더를 쓴다.
따라서 빌더 한 곳을 고치면 규모 셀·카드 두 경로가 함께 교정된다(요구사항 3 확인 완료).

2. 지침 요구사항 1·2 — 왕복 없이 판정 가능한가
────────────────────────────────────────────────────────────────────────
`remote` 의 의미는 '질의를 실제로 던지는 주체(애플리케이션 서버) 기준으로 DB 가 원격인가'다.
화면은 접속 폼 입력란 #srcHost / #tgtHost 를 이미 갖고 있으므로 왕복 없이 읽을 수 있고,
다음 두 가지는 화면 근거만으로 '로컬' 을 확정할 수 있다.

  (1) loopback host (localhost / 127.x.x.x / ::1) — 접속 주체 자신을 가리킨다.
  (2) 페이지를 서빙한 origin host 와 동일 (location.hostname) — 그 호스트가 곧 앱 서버다.

반대로 사설 IP·FQDN 이 '앱 서버 자신인지' 는 화면만으로 알 수 없다(서버만 자기 주소를 안다).
그래서 지침 2의 원칙대로 **확정 가능한 경우에만 참값으로 바꾸고, 확정 불가면 기존 보수값
true 를 그대로 유지**했다. 판정 사유는 기존 `pk_evidence` 와 같은 방식의 별도 근거 필드
`remote_evidence` 로 남긴다(StrategyProfile 에 없는 키라 서버 `_build_profile` 이 hasattr 로
걸러 무시 — 서버 계약 변경 없음).

판정 규칙(양쪽 모두 로컬 확정일 때만 remote=false):
  LOCAL_LOOPBACK_BOTH            → remote=false  (원본·목적지 모두 loopback)
  LOCAL_SAME_HOST_AS_APP_ORIGIN  → remote=false  (양쪽 모두 페이지 origin host 와 동일)
  MIXED_ONE_SIDE_REMOTE          → remote=true   (한쪽만 로컬)
  REMOTE_NON_LOCAL_HOST_BOTH     → remote=true   (양쪽 모두 비로컬)
  HOST_UNKNOWN_KEEP_CONSERVATIVE → remote=true   (host 미입력 — 근거 없음, 기존값 유지)

6. 위험·잔여 과제
────────────────────────────────────────────────────────────────────────
- 남은 판별 갭: DB host 가 사설 IP/FQDN 이면서 실제로는 앱 서버 자신인 배치(같은 장비에 앱과 DB)는
  화면 근거만으로 확정할 수 없어 계속 '원격' 으로 보고된다(보수측). 참값이 필요하면 서버가
  자기 주소와 대조해 판정 결과를 내려주는 별도 근거 필드가 필요하다 — 이번 지침 범위 밖이라 보류.
- 리버스 프록시 뒤에서 DB host 가 프록시 호스트명과 우연히 같으면 SAME_ORIGIN 을 로컬로 오판할 수
  있다. 영향은 cost 5%(등급 한 단계)에 한정되며, 근거코드 LOCAL_SAME_HOST_AS_APP_ORIGIN 으로
  추적 가능하게 남겼다.
- `choose_compare_strategy` 의 `remote` 인자가 미사용 상태로 남아 있다(설계 의도와 구현의 괴리).
  전환정책에 배선할지 여부는 정책 결정이므로 이번 수정에서 건드리지 않았다. 배선하는 순간
  전환판정이 바뀌므로, 신규 테스트가 그 변화를 즉시 잡도록 계약으로 고정해 뒀다.
- remote_evidence 는 pk_evidence 와 동일하게 화면 진단용(POST 본문에 실려 서버에서 무시)이다.
  화면 카드에 근거코드를 노출하지는 않았다 — 표시 항목 추가는 별도 판단 사항.
