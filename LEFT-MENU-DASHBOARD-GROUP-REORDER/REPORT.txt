────────────────────────────────────────────────────────────────────────
1. 배경과 요청
────────────────────────────────────────────────────────────────────────
직전 작업 JOB-DASHBOARD-STAGE3-UI-AND-MENU-REORG 에서 "현황"(검증 현황판) 그룹을 좌측
메뉴 최상단에 단독으로 신설했다. 이번 요청은 그 그룹의 성격이나 내용에 대한 변경이 아니라,
사용자 판단에 따른 배치 위치 재조정이다. 최상단이 아니라 "검증 실행" 그룹과 "결과 / 진단"
그룹 사이에 두는 것이 실제 사용 흐름(검증을 실행한 뒤 진행 현황을 본다)에 맞는다는 판단이다.

따라서 이번 작업의 범위는 명확히 "순서만 변경"으로 한정했다.
- 현황 그룹은 다른 그룹에 병합하지 않고 독립 그룹으로 유지한다.
- 그룹 내용물(검증 현황판 1개 항목)은 그대로 둔다.
- 현황판 화면 자체(#tab-job-dashboard 내용, API, 폴링 로직)는 손대지 않는다.
- 각 그룹의 펼침/접힘 기본 상태와 배지 표시 로직도 변경하지 않는다.
- 브랜드 로고 클릭 시 현황판으로 이동하는 동작은 그대로 유지한다.

────────────────────────────────────────────────────────────────────────
2. 구조 확인 — 메뉴는 "배열"이 아니라 정적 HTML 블록이었다
────────────────────────────────────────────────────────────────────────
요청서에는 "그룹 순서 배열"이라는 표현이 있었으나, 실제 코드에서 좌측 메뉴는 파이썬 리스트나
설정 배열로 정의되어 있지 않았다. ui/tabler_renderer.py 안의 f-string HTML 안에
<li class="nav-item mv-grouphead" data-grp="..."> (그룹 헤더) 와
<li class="mv-nav-subwrap" data-grpbody="..."> (그룹 본문) 이 쌍으로 나열된 정적 마크업이며,
표시 순서 = DOM 작성 순서였다.

즉 "순서 변경" = 해당 두 <li> 쌍 블록을 통째로 다른 위치로 옮기는 작업이다. 이 구조 덕분에
순서 변경이 다른 로직에 영향을 줄 여지가 원천적으로 없다는 점도 함께 확인했다.
- 그룹 접기/펴기: mvToggleGroup('<key>') 이 data-grp / data-grpbody 의 key 로 짝을 찾는다.
  → DOM 위치가 아니라 key 매칭이므로 순서와 무관하다.
- 배지 갱신: ui/js_job_dashboard.py 의 _mvRunningJobsBadge 계열이
  [data-jobbadge] / [data-jobbadge-sum] 를 querySelectorAll 로 전수 갱신한다.
  → 역시 선택자 기반이라 순서와 무관하다.
- 탭 전환/폴링: showTab(name) 이 name === 'job-dashboard' 일 때만 진입/이탈 훅을 호출한다.
  → 메뉴 위치와 무관하다.

6. 위험 평가
────────────────────────────────────────────────────────────────────────
이번 변경의 위험은 사실상 없다고 판단한다. 근거는 2항에서 확인한 대로 접기/펴기, 배지, 탭 전환,
폴링이 모두 DOM 순서가 아니라 key 또는 선택자 기반으로 동작하기 때문이며, 이를 추론으로 끝내지
않고 브라우저 실측으로 4가지 모두 직접 확인했다.

남는 사항 하나는 사용성 관점이다. 브랜드 로고와 기본 랜딩 화면이 여전히 검증 현황판이므로,
"가장 먼저 보게 되는 화면"이 좌측 메뉴에서는 네 번째 그룹에 위치하게 된다. 기능상 문제는 아니고
이번 요청이 명시적으로 지시한 배치이므로 그대로 반영했다. 다만 추후 랜딩 화면을 바꾸게 되면
로고 진입점(showTab('job-dashboard'))과 메뉴 위치를 함께 재검토하는 편이 좋다.
