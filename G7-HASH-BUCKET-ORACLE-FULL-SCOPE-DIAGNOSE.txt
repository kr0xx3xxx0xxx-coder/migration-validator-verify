2-0. 이미 존재하는 설계 확정본을 그대로 채택한다(임의 재설계 금지)
  docs/HASH_BUCKET_ORACLE_PORT_ADAPTER_DESIGN.md §1(전수표 E1~E18)·§2(신규 확정 4항목)·§3.2(Base 시그니처)가

  아직 소비되지 않았다 — 유효기간이 끝나지 않았으므로 그대로 쓴다. 이하는 그 설계를 이번 조사에서
  재확인·보강한 것이다(신규 항목은 "[신규]" 로 표시).

2-1. 해시함수 후보 비교 — STANDARD_HASH 채택(재확인, 대안 배제 사유 명시)
  후보 A) STANDARD_HASH(x,'MD5')  — 10g R2+ 내장, 결정적, extension 불필요.
      LOWER(RAWTOHEX(STANDARD_HASH(x,'MD5'))) 로 PG md5() 와 동일 hex 문자열(소문자) 생성.
      실측(설계 §1 E1): STANDARD_HASH('abc','MD5') 의 RAWTOHEX = PG md5('abc') 와 동일 32hex.
  후보 B) ORA_HASH(x)  — 32bit 해시를 **직접** 낸다(중간에 hex 문자열을 거치지 않음).
      배제 사유: (a) 알고리즘이 비공개(오라클 자체 해시, MD5 가 아님) → PG md5 와 값 자체가
      다르다. same-DBMS 페어에서는 src/tgt 가 둘 다 오라클이라 "같은 함수를 양쪽에 쓰면 무해"
      하지만, ORA_HASH 는 기본적으로 4바이트(0..4294967295 또는 지정 max_bucket) 출력이라
      우리가 원하는 "MD5 앞 8hex → TO_NUMBER" 32bit 정수화 파이프라인과 입출력 형태가 다르고,
      PG 표현식과의 구조적 대응(E1~E5 1:1 표)을 깨 이후 유지보수 시 "PG 식과 오라클 식이 왜 이렇게
      다른가"를 매번 재설명해야 한다. (b) ORA_HASH 는 버킷 수(max_bucket) 인자를 자체적으로
      갖고 있어 우리의 "hash → &(n-1)" 파이프라인과 책임이 겹친다(이중 버킷팅). → **비채택**.
      단, ORA_HASH 는 §1 이 언급 안 한 "성능" 관점에서는 STANDARD_HASH 보다 가볍다는 참고자료가
      있으나, 이번 설계는 "PG 와 1:1 대응 가능한 표현식"을 최우선 기준으로 삼으므로 채택하지 않는다.
  → **STANDARD_HASH(x,'MD5') 채택**(design.md §1 E1 그대로, 대안 검토로 재확인만 추가).

  가용 버전: STANDARD_HASH 는 Oracle 10g R2(10.2) 이상 표준 내장(패키지/extension 불필요) —
  services/db_adapters/oracle.py 가 지원 대상으로 삼는 버전대(19c/21c/23ai, 실측 asis/tobo 프리셋)에서
  전부 사용 가능. 별도 가용성 probe 불필요(PgHashContract.is_available() 이 항상 True 인 것과 대칭으로,
  OracleHashContract.is_available() 도 버전 조건 없이 True 로 설계 — 근거: exact_diff 오라클 이식이
  이미 이 버전대만 지원 대상으로 확정돼 있어(operational_focus 주석) 추가 하한 체크가 무의미).

  충돌률: MD5 128bit 전체가 아니라 앞 8hex(32bit)만 쓰므로 이론 충돌률은 이미 PG 경로와 동일한
  구조적 한계(2^-32)를 그대로 이어받는다 — 오라클 도입으로 새로 생기는 위험이 아니다(설계 §1.1 이미 실측).

2-2. 문자열 캐스팅/결합 — SUBSTR·BITAND·TO_NUMBER (설계 §1 E2·E4·E15 그대로, 재확인)
   구분          PG 현행                    오라클 대체식                      실측(설계 §1)
   앞 8자        left(h,8)                  SUBSTR(h,1,8)                      '90015098' 동일
   32bit 정수화  ('x'||hex8)::bit(32)::bigint  TO_NUMBER(hex8,'XXXXXXXX')       TO_NUMBER('ffffffff','XXXXXXXX')=4294967295
   비트 AND      h32 & (n-1)                BITAND(h32, n-1)                   BITAND(255,7)=7
  BITAND 는 오라클에 내장 함수로 존재(PL/SQL 아님, SQL 함수) — 별도 패키지 권한 불필요.
  '&' 는 오라클 SQL*Plus/일부 드라이버에서 치환변수로 오인되는 문제(ORA-00923 류)가 있어 BITAND 로
  대체가 필수이며 우회(escape)로 해결할 사안이 아니다(설계 §1 E15 사유 그대로 채택).

2-3. NLS/캐릭터셋 영향 여부 — [신규, 이번 조사 항목] M20(NLS_COMP=BINARY 세션 고정)과의 상호작용
  질문: 오늘 M20 이 세션에 고정한 NLS_COMP=BINARY 가 해시 계산에도 영향을 주는가?

  결론: **영향 없음 — 이미 무상으로 방어돼 있다.** 근거:
   (a) NLS_COMP 는 **비교 연산자**(=, LIKE, ORDER BY, GROUP BY, DISTINCT)가 문자열을 BINARY 로
       비교할지 LINGUISTIC(언어별 정렬규칙)으로 비교할지를 결정하는 세션 파라미터다. 값 자체를
       변환하는 파라미터가 아니다 — TO_CHAR()/STANDARD_HASH()/SUBSTR() 의 **출력값**은 NLS_COMP 의
       영향을 받지 않는다(오라클 공식 동작 — NLS_COMP 는 "how comparisons are performed", 값 변환과
       무관). 즉 canonical 문자열 자체, h32 정수, bucket 번호 모두 NLS_COMP 에 좌우되지 않는다.
   (b) HASH_BUCKET 이 실제로 문자열 **비교**를 수행하는 지점은 row_diff._cell_condition 의
       `exp.EQ(this=bexpr, expression=exp.Placeholder())`(bucket 번호 = bind, **숫자 비교**)와
       scope 필터의 gb_exprs 동등비교(문자 컬럼 포함 가능)다. 후자는 오라클에서 실제로 NLS_COMP 영향권
       (LINGUISTIC 이면 대소문자/발음부호 무시 비교로 거짓 일치 가능)이나, services/db_adapters/oracle.py:220
       (_pin_session_nls_comp)가 **연결(connection) 단위로 1회** BINARY 를 고정하므로 HASH_BUCKET 이 쓰는
       커넥션도 자동으로 이 고정을 상속한다(오라클 어댑터가 만드는 모든 커넥션이 대상 — HASH_BUCKET 전용
       조치가 추가로 필요 없다).
   (c) 실제로 값 변환에 영향을 주는 것은 NLS_NUMERIC_CHARACTERS(소수점 문자, R3)와 NLS_DATE_FORMAT/
       NLS_TIMESTAMP_FORMAT 계열이며, 이 둘은 M20 의 대상이 아니다(M20 은 COUNT(DISTINCT) 캐릭터셋
       노출 대응). 이 두 파라미터에 대한 방어는 design.md §2.3 R3 가 이미 "3인자 TO_CHAR(x,'TM9',
       'NLS_NUMERIC_CHARACTERS=''.,''')" 로 식 자체에 고정하는 방식을 규정해 뒀고, 날짜도 명시 서식
       ('YYYY-MM-DD"T"HH24:MI:SS.FF6', 로케일 의존 토큰 'MON' 등 미사용)이라 NLS_LANGUAGE/NLS_TERRITORY
       에도 좌우되지 않는다. → **③ 구현 시 세션 파라미터에 의존하지 말고 식에 3인자로 고정**하는
       design.md 원안을 그대로 따르면 되고, M20 과 별도의 추가 조치는 불필요하다.
  → M20 은 HASH_BUCKET 구현체 설계를 바꾸지 않는다. 다만 §5(테스트) 단계에서 "M20 이 없다고 가정한
    별도 세션에서도 hash 결과가 같은가"를 회귀 대상에 넣을 필요는 없다 — HASH_BUCKET 이 쓰는 커넥션은
    항상 오라클 어댑터를 경유하므로 NLS_COMP 미고정 세션 자체가 존재하지 않는다(구조적으로 발생 불가).

2-4. 오라클 전용 리스크 4종 — design.md §2.3 재확인 + precheck 배치 지점 확정
  R1(빈문자열=NULL, P0)     : same-DBMS 한정에서 무해(§2-4 재확인). cross-DBMS 는 애초에 L3 가 차단.
  R3(NLS_NUMERIC_CHARACTERS): 3인자 TO_CHAR 로 식에 고정(§2-3 에서 위 확인대로 M20 과 무관하게 별도 필요).
  R4(VARCHAR2 4000자, ORA-01489): OracleHashContract.precheck(exprs, compare_exprs) 에서 canonical
      결합의 최대 바이트 길이를 추정해 상한 초과 시 HOLD 문자열 반환 — BaseHashContract.precheck 시그니처
      (hash_contract.py:98-100) 를 그대로 구현하면 된다(신규 메서드 아님, override 만).
  R5(STANDARD_HASH 가 CLOB 거부, ORA-00902) : 같은 precheck 에서 ntype/컬럼 메타로 LOB 감지 시 HOLD.
      단, key_evidence._norm_type 이 3종(NUMBER/DATE_TIME/TEXT)만 내려주므로 LOB 판별을 위해서는
      compare_exprs 의 원본 컬럼 메타(길이/타입)가 precheck 호출부까지 전달돼야 한다 — 이는 현재
      build_hash_bucket_agg_sql 시그니처에 없는 정보이므로, **④ 소비측 배선에서 컬럼 메타 전달 경로를
      새로 뚫어야 하는지, 아니면 "LOB 은애초에 MATCH_KEY 후보 경로에 오지 않는다"(F1-G7 §5-2-(4) 근거)는
      전제로 방어적 HOLD 를 생략할지"를 ③ 착수 시 확정해야 한다** — 이번 조사에서는 §1 의 표현식
      설계만으로는 결정할 수 없는 유일한 열린 지점으로 남긴다(구현 규모에 영향 작음, 위험도 낮음).

2-5. Base 인터페이스 대비 구현 매핑 (hash_contract.py:44-100 시그니처 그대로 채움)
  db_type = "oracle" / version = "hashv1-md5-lenpfx-ora" / cross_db_comparable = False
  is_available()      → True(버전 하한 불필요, §2-1)
  h32(canon_sql)       → "TO_NUMBER(SUBSTR(LOWER(RAWTOHEX(STANDARD_HASH(%s,'MD5'))),1,8),'XXXXXXXX')"
  canon_component(e,nt)→ NUMBER: TO_CHAR(e,'TM9','NLS_NUMERIC_CHARACTERS=''.,''') + 선행0 복원 regex(E7c)
                         DATE_TIME: TO_CHAR(CAST(e AS TIMESTAMP),'YYYY-MM-DD"T"HH24:MI:SS.FF6')
                         TEXT: TO_CHAR(e)
                         길이/NULL 마커 뼈대는 PG 와 동일 문법('||' · CASE WHEN) — Base.key_canonical/
                         row_canonical(방언 무관 조합, hash_contract.py:74-87)을 오버라이드 없이 그대로 상속.
  bucket_expr(kc,n,salt)→ "BITAND(" + h32(salted) + ", " + str(pow2_floor(n)-1) + ")"
  precheck(exprs,ce)    → R4/R5(§2-4) 반환. Base 기본값(:98-100)은 None 이므로 override 필수.

3-1. row_diff.py 안전 수정 — "파라미터 추가"만으로는 불충분(F1-G7 §7-1 이 이미 지적, 재확인)

3-3. multi_scope.py 위반③(db_type 미배선) 도 같은 배선 작업의 일부로 함께 처리

3-4. 안전성 근거 — 이 수정은 phase① 과 달리 "PG 결과가 즉시 바뀌지 않는다"

  PgHashContract 를 반환하므로, 3-1/3-2 수정 후에도 PG 경로는 여전히 PgHashContract 를 쓴다

  시 그대로 재사용할 것을 권고(§5 에서 다시 언급).

3-5. ④ 는 ③(오라클 구현체) 없이도 완결 가능 — 이것이 §5 의 순서 판단 근거
  contract 가 None 인 경우(=L3 가 계약을 못 준 경우, 지금은 oracle 미등록이라 여기 해당)의 처리는
  이미 L2(resolve_hash_contract)가 상위에서 HOLD_UNSUPPORTED_DB 로 반환해 row_diff/match_key_evidence
  까지 호출 자체가 도달하지 않는다(L2 가 게이트). 즉 3-1~3-3 배선은 "PG contract 를 명시적으로 주입"
  하는 것이 전부이며, 이 변경의 정답 여부는 **오라클 구현체 존재와 무관하게** PG 골든셋만으로 검증된다.

§5. 착수 순서 및 검증 계획
═══════════════════════════════════════════════════════════════════════════════

5-1. "③(오라클 구현체)이 ④(안전 배선)보다 먼저 가야 하는가" — 아니다, ④ 를 먼저/독립적으로 넣을 것을 권고

  design.md §6.3 원안 순서는 ①②(완료)→③→④→⑤→⑥ 이지만, §3-5 에서 확인했듯 ④(row_diff/
  match_key_evidence/multi_scope 안전 배선)는 **③ 없이도 PG 골든셋만으로 완결·검증 가능**하고,
  ④ 가 먼저 들어가면 "PG 전용 재수출 무조건 위임"이라는 구조적 결함 자체가 코드에서 사라진다 —
  이후 언제 ③(오라클 구현체)이나 ⑥(G7 등록)이 잘못된 순서로 시도돼도, row_diff/match_key_evidence 가
  더 이상 "묻지도 따지지도 않고 PG" 를 방출하지 않으므로 §4-3 의 [치명] 위험이 **구조적으로 재발
  불가능**해진다(등록만 하면 L3 가 None 을 주고, 계약이 없으면 애초에 SQL 을 못 만든다 —
  bfda564 가 hash_bucket.py 에 이미 적용한 것과 동일한 안전망을 row_diff/match_key_evidence 에도
  같은 방식으로 확장하는 것뿐이다).

  ③(오라클 구현체 파일 3개 신규)은 ④ 와 파일이 겹치지 않아(§2-5 는 신규 파일, §3 은 기존 파일 수정)
  **병행 착수 가능**하다 — 순서 제약이 아니라 "④ 는 반드시 ⑤⑥ 이전에 끝나 있어야 한다"는 제약만 있다.

  → **권장 순서: ④(안전 배선, 최우선) ∥ ③(오라클 구현체, 병행) → ⑤(capabilities+L1 개방) → ⑥(G7 등록
  + 라이브 실측)**. design.md 의 ③→④ 순서를 뒤집는 것이 이번 조사의 유일한 정정 사항이며, 근거는
  "④ 는 구조적 위험 제거이고 ③ 존재 여부와 무관하게 검증 가능하다"(§3-5) 는 점 — 위험이 가장 큰
  수정을 가장 먼저, 가장 작은 단위로 넣어 되돌림 비용을 낮추는 phase① 의 방법론과 동일하다.

5-2. ⑥ 라이브 검증 계획 — 자기일치성만으로는 부족, 타 전략 대조 방식 제안(지시서 요청 그대로)

  기존 phase① 의 골든셋 방법(BEFORE/AFTER sha256 대조)은 "개명 전후 동일 코드 로직의 회귀 없음"을
  보는 것이라 ⑥ 에는 그대로 못 쓴다 — ⑥ 은 **신규 로직(오라클 canonical)이 정답인지**를 봐야 하므로
  자기 자신과 비교해서는 검증되지 않는다(설계가 틀려도 재현은 됨). 지시서가 제안한 대로
  **독립적으로 이미 오라클 검증된 다른 전략과 결과를 대조**하는 방식을 아래와 같이 구체화한다.

  대조 대상: DIRECT_STREAM_COMPARE(services/strategy/strategy_models.py:24) — exact_diff 계층의
  오라클 이식(F1-G7 §5-3 이 지적한 "오라클 row_diff 는 이미 SUPPORTED" 의 그 계층)으로 이미 라이브
  검증된 전체 스트림 비교. HASH_BUCKET 은 이 결과를 "빠르게 좁히는" 수단일 뿐, 최종 판정 기준은
  둘 다 "같은 두 테이블의 실제 행 차이"여야 한다.

  절차:
   1) 오라클 asis/tobe 프리셋(db_presets_{src,tgt}.json, "Oracle_asis"/오라클 tgt 확인됨)으로
      의도적 불일치 3케이스 구성(F1-PHASE1 §4-3 이 쓴 것과 같은 패턴 — 전량일치/값변경/행누락 3종,
      오라클 스키마로 재현).
   2) 같은 스코프를 DIRECT_STREAM_COMPARE 로 먼저 실행 — "정답"으로 삼을 불일치 행 PK 집합을 확보.
   3) 동일 스코프를 HASH_BUCKET(오라클↔오라클, ⑥ 등록 이후) 로 실행 — 활성 bucket → row_diff 로
      좁혀진 불일치 행 PK 집합을 확보.
   4) 두 PK 집합이 **완전히 일치**해야 PASS(부분집합/초과집합 모두 실패 — 누락은 거짓판정 은폐,
      과다는 §2.4 R1/R3 미방어를 의미).
   5) 일치 케이스(불일치 0건)도 별도로 포함 — HASH_BUCKET 이 "활성 cell 0" 을 정확히 내는지
      (오탐 없음)까지 확인해야 완결(phase① §4-2 의 "전량 일치" 케이스와 동일한 목적).
   6) R3(NLS_NUMERIC_CHARACTERS) 검증은 두 오라클 인스턴스(asis/tobe)의 세션 NLS 값이 실제로
      다른 상태에서 3)을 재실행해 그래도 4)가 성립하는지로 실측한다(세션 값이 우연히 같으면
      §2-3 방어가 검증되지 않은 채 통과할 수 있으므로, 최소 한쪽 세션에서 ALTER SESSION 으로
