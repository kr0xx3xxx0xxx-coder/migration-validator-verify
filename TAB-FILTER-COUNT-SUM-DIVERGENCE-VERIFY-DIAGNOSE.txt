6. 판정 ① — 탭 필터링 정상 여부
────────────────────────────────────────────────────────────────────────
**정상 동작.** "필터링이 무시되고 항상 같은 결과만 나온다"는 아니다.

- 근거 A(데이터): 짝수 그룹의 diffCols 가 [AMT, QTY] 로 CNT 가 빠져 있고, 홀수 그룹만
  [CNT, AMT, QTY] 다. 판정 근거 자체가 지표별로 정확히 갈려 있다.
- 근거 B(화면): COUNT 탭은 정확히 5개(홀수만), AMT/QTY 탭은 10개(짝수 포함).
- 근거 C(탭 배지): [전체 10][COUNT 5][AMT 10][QTY 10] 로 배지 숫자부터 다르다.

**사용자가 "전부 똑같은 그룹만 보인다"고 느낀 이유(추정)**:
이번 픽스처는 AMT 와 QTY 가 항상 함께 틀어지도록 만들어져 있어 AMT 탭과 QTY 탭 목록이
100% 같다(둘 다 10개). 3개 탭 중 2개가 같으니 "다 똑같다"로 보이기 쉽다. 실제로 갈리는
탭은 COUNT 하나뿐이며, 그것은 정확히 갈린다. 아래 7~9항의 페이지 결함도 같은 인상을 준다.

7. 재현 조건 만들기 · 그 과정에서 나온 부수 결함
────────────────────────────────────────────────────────────────────────
이번 픽스처는 그룹이 10개뿐이라 기본 표시건수(50건)로는 모든 탭이 1페이지다(1차 실행에서
COUNT 탭 "총 5건 · 1/1 페이지" 확인 — 스크린샷 run1_b_pg1_A_COUNT_5_p2.png).
페이지를 여러 개 만들려고 화면의 '표시 건수' 드롭다운을 내렸더니 **부수 결함**이 드러났다.

[부수 결함] 표시 건수 드롭다운이 지표 탭에는 전혀 먹지 않는다.
  1차 실행 실측(스크린샷 run1_b_pg0_size2_after_change.png):
    _execSetPageSize('2') 호출 후 → srv_page_size = 2 로 바뀜, client_page_size = 50 그대로.
  근거 코드 ui/execute_result_renderer.py:175
    function _execSetPageSize(v) {
      if (window._execSrv) { window._execSrv.page_size = ...; _execSrvGo(1); return; }   ← 여기서 return
      window._execResultPageSize = ...;                                                  ← 지표 탭이 쓰는 값
    }
  서버 페이지 모드(_execSrv 존재)에서는 첫 줄에서 return 하므로 클라이언트 렌더 값
  (_execResultPageSize)이 영원히 50 으로 남는다. 지표 탭은 클라이언트 렌더를 쓰므로
  드롭다운을 20/50/100 어느 값으로 바꿔도 지표 탭 표시 건수는 바뀌지 않는다.

2차 실행에서는 진단을 위해 두 상태를 모두 2건으로 내린 뒤 측정했다(코드 수정 아님,
런타임 상태 조정). 그 결과 탭별 페이지 수가 다음처럼 갈렸다:
  전체  : 5페이지 (서버 페이징 "1 / 5 페이지(전체 무절단)")
  COUNT : 3페이지 (클라이언트 페이징 "총 5건 · 1 / 3 페이지 (1–2)")
  AMT   : 5페이지 (클라이언트 페이징 "총 10건 · 1 / 5 페이지 (1–2)")
  QTY   : 5페이지 (클라이언트 페이징 "총 10건 · 1 / 5 페이지 (1–2)")
  스크린샷: b_pg0census_전체_10.png / b_pg0census_COUNT_5.png / b_pg0census_AMT_10.png /
            b_pg0census_QTY_10.png

8. A탭 N페이지 → B탭 전환 실측
────────────────────────────────────────────────────────────────────────
[시나리오 ① 범위 밖] A = AMT 탭(5페이지) 5페이지 → B = 다른 탭
  A: AMT 5페이지 클릭   → 표시 G09,G10 · 페이징 "5 / 5 페이지(전체 무절단)"
                          (스크린샷 b_pg_범위밖_A_AMT_10_p5.png)
  B1: 전체 탭  → 화면 그대로 5페이지 유지. srv_page=5, 표시 G09,G10
                 페이징 "5 / 5 페이지(전체 무절단)"  (b_pg_범위밖_B_전체_10_from_p5.png)
  B2: COUNT 탭(최대 3페이지) → **1페이지로 리셋**. client_page=1, 활성버튼=1,
                 표시 G05,G03, 페이징 "총 5건 · 1 / 3 페이지 (1–2)"
                 → 빈 화면·에러 없음. 범위 밖 페이지가 넘어오지 않는다.
                 (b_pg_범위밖_B_COUNT_5_from_p5.png)
  B3: QTY 탭(최대 5페이지) → **1페이지로 리셋**. 5페이지가 유지되지 않음.
                 표시 G05,G03, 페이징 "총 10건 · 1 / 5 페이지 (1–2)"
                 (b_pg_범위밖_B_QTY_10_from_p5.png)

[시나리오 ② 범위 안] A = COUNT 탭(3페이지) 3페이지 → B = 다른 탭
  A: COUNT 3페이지 클릭 → **여기서 필터가 풀린다.**
     표시 G05, **G06** · 페이징 "3 / 5 페이지(전체 무절단)" · 문구 "현재 불일치 그룹 5~6 표시 · 3/5페이지"
     G06 은 COUNT 가 99,000 = 99,000 으로 완전히 같은 그룹이라 COUNT 탭에 절대 나오면 안 되는
     그룹이다. 그런데 COUNT 탭 버튼은 여전히 주황색 활성 상태다.
     (스크린샷 b_pg_범위안_A_COUNT_5_p3.png — 이번 진단의 핵심 증거)
  B1: 전체 탭  → 3페이지 유지(srv_page=3), 표시 G05,G06 (b_pg_범위안_B_전체_10_from_p3.png)
  B2: AMT 탭   → 1페이지로 리셋, 표시 G05,G03 (b_pg_범위안_B_AMT_10_from_p3.png)
  B3: QTY 탭   → 1페이지로 리셋, 표시 G05,G03 (b_pg_범위안_B_QTY_10_from_p3.png)

정리:
  · 지표 탭 → 지표 탭 : 페이지 번호 유지 안 됨(항상 1페이지). 범위 밖 페이지 유입 없음.
  · 어느 탭 → 전체 탭 : 직전에 눌렀던 페이지 번호가 그대로 복원됨(서버 페이지 srv.page).
  · 지표 탭에서 페이지 번호를 누르는 순간 : 지표 필터가 조용히 풀리고 전체(서버) 페이지로 이동.

────────────────────────────────────────────────────────────────────────
**별개 메커니즘이다. 페이지 번호를 일부러 유지시키는 코드는 없다.**

(1) 지표 탭 전환은 항상 1페이지로 되감는다

(2) 지표 탭에서 페이지 번호를 누르면 필터가 풀리는 원인

    페이징 버튼은 _execRenderResultPaging() 이 그리는데(:148-170) onclick 이 전부
    _execGoResultPage(i) 다. 서버 페이지 모드에서는 지표 필터가 걸려 있어도 첫 줄에서
    _execSrvGo(p) 로 빠져 서버 저장 결과의 p 페이지를 통째로 tbody 에 덮어쓴다
    (_execSrvGo 는 mismatch_only 만 넘기고 col filter 를 넘기지 않는다 — :188-191).
    그래서 COUNT 탭에서 3페이지를 누르면 COUNT 와 무관한 G06 이 나타난다.

(3) '그룹 펼침 상태 유지'(오늘 고친 기능)와의 관계 — 무관
    ui/tabler_renderer.py:16795-16843 window._mvPkExpandState / _mvPkExpandRemember /
    _mvPkRestoreExpandedRow.
    이 상태가 들고 있는 page 는 **드릴다운 안쪽 재이관 PK 목록의 페이지**(_mvPkGo_<uid>(page,view))
    이지, 결과표의 페이지(_execResultPage / _execSrv.page)가 아니다. 저장 키도 data-row-key
    (그룹 1개) 기준이고, 복원도 _mvToggleRowAggDiff 재호출로만 이뤄진다.
    결과표 페이지 번호를 읽거나 쓰는 코드는 전혀 없다.

10. 판정 ② — 페이지 번호 유지 동작
────────────────────────────────────────────────────────────────────────
제시된 3지선다 중 **"유지는 되지만 범위 밖 페이지에서 이상 동작함(버그)"** 에 가장 가깝다.
다만 실측 결과가 사용자 관찰과 조금 다르므로 정확히 쪼개면 다음과 같다.

 (a) 지표 탭 A → 지표 탭 B 로 페이지 번호가 넘어가는 현상 : **재현되지 않음.**
     _execSetColFilter 가 무조건 _execResultPage=1 로 되감기 때문. 범위 밖 페이지가
     넘어와 빈 화면/에러가 되는 일도 없었다(항상 1페이지 정상 표시).
 (b) 페이지 번호가 실제로 유지되는 경로 : **'전체' 탭으로 돌아갈 때만.** 의도적으로 넣은
     분기(_execSrv.page 복원)이며 그 자체는 정상 동작한다(범위 초과도 발생하지 않는다 —
     서버 페이지 수는 항상 전체 기준으로 가장 크기 때문).
 (c) 진짜 결함 : **지표 탭에서 페이지 번호를 누르면 그 탭의 필터가 조용히 풀리고
     전체(서버) 결과의 해당 페이지로 바뀐다.** 탭 버튼은 계속 활성 상태라 사용자는
     여전히 그 지표로 걸러진 목록을 보고 있다고 오해한다. COUNT 탭 3페이지에서 COUNT 가
     완전히 일치하는 G06 이 표시된 것이 그 증거다(b_pg_범위안_A_COUNT_5_p3.png).
     이 상태에서 탭을 옮겨 다니면 "페이지 번호가 탭 간에 따라다닌다"는 인상을 그대로 준다 —
     사용자가 본 현상의 실체는 (c)일 가능성이 높다.
 (d) 부수 결함 : 표시 건수 드롭다운(20/50/100)이 지표 탭에는 아무 영향이 없다(7항).

권장 대응(참고 — 이번 지침은 진단 전용이라 구현하지 않음):
  · _execGoResultPage 에 `if (window._execSrv && !window._execColFilter)` 가드를 넣어
    지표 필터가 걸린 상태의 페이지 이동은 클라이언트 렌더로 보내는 것이 최소 수정이다
    (_execSetColFilter 가 이미 쓰는 동일 조건 — 새 분기 어휘 증식 없음).
  · _execSetPageSize 도 같은 조건으로 _execResultPageSize 를 함께 갱신해야 드롭다운이
    지표 탭에도 반영된다.
  · 위 2건은 완료 모듈 수정이라 사용자 승인 후 별도 작업으로 진행할 사안이다.
