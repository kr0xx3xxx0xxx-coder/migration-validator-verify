4. (b) INNER JOIN vs (c) OUTER JOIN — 검출건수 차이가 기대대로 관측됨 (최우선 확인항목)

  항목               | (b) INNER JOIN | (c) LEFT OUTER JOIN | 차이
  -------------------|----------------|---------------------|----------
  원본 COUNT         |     49,750,000 |          50,000,000 | +250,000
  목적 COUNT         |     49,500,000 |          49,500,000 |        0
  COUNT 차이         |       +250,000 |            +500,000 | +250,000
  그룹Δ합계          |        250,000 |             500,000 | +250,000

  · 차이 250,000 = 차원 미대응(R99) 행수 250,000 과 정확히 일치.
  · 화면이 생성한 통계검증 SQL 에 조인 타입이 그대로 반영됐다(산출 JSON 원문):
      (b) FROM NXDNP.MV_SCATTER50M_SRC S
          INNER JOIN NXDNP.MV_SCATTER50M_DIM D ON s.REGION_CD = d.REGION_CD
      (c) FROM NXDNP.MV_SCATTER50M_SRC S
          LEFT OUTER JOIN NXDNP.MV_SCATTER50M_DIM D ON s.REGION_CD = d.REGION_CD
  · 그룹별로 보면 차이가 어디서 오는지 더 분명하다.
    (b)에서 짝수 그룹(G02·G04·G06·G08·G10)은 INNER 로 R99 50,000행이 탈락해
    원본이 4,950,000 이 되고, 목적 4,950,000 과 만나 **COUNT Δ가 0** 이 된다
    (단 SUM 은 여전히 불일치라 '집계값 불일치'로 검출된다 — 예: G02 Δ -135).
    홀수 그룹 5개만 Δ +50,000 → 5 × 50,000 = 250,000.
  · **결론: 조인 타입이 무시되고 있다는 신호는 없다.** 지침이 최우선 보고 대상으로 지정한
    "INNER/OUTER 무차이" 상황은 5,000만행에서도 발생하지 않았다.
    100만행에서 관측된 것과 완전히 같은 구조가 50배 규모에서 그대로 재현됐다.

5-4. 해석

  · **규모의 주된 병목은 COUNT 단계다.** 평균 ×100.2 로 유일하게 뚜렷한 초선형이고,
    절대값도 9.7~32.6초로 사용자가 체감하는 대기의 대부분을 차지한다.
  · 통계검증(집계)은 ×42.7 로 거의 정확히 선형이다. GROUP BY 대상 그룹 수가
    10개로 고정이라 스캔량에만 비례하기 때문으로 보인다.
  · 재이관 수집의 ×64.3 은 **처리 행수가 늘어서가 아니다.** 응답의
    counts.passed 는 100만행과 5,000만행이 9,999 로 **완전히 같다**(§5【이상-3】의
    101건 상한 때문에 스캔이 조기중단되므로). 실제로 늘어난 것은 stage_timings 의
    prepare_ms 로, (a) 기준 51,710ms 중 42,350ms(82%)가 prepare 다.
    즉 "더 많이 비교해서"가 아니라 "50배 큰 테이블에서 정렬된 스트림을 여는 비용"이
    커진 것이다. merge_judge_ms 는 134.6ms, store_save_ms 는 26.5ms 에 불과하다.
  · 드릴다운 1회차가 선형미만(×20.7)인 것도 같은 이유다 — 스캔량이 상한에 묶여 있다.
  · Excel 이 사실상 상수(×1.19)인 것은 성능이 좋아서가 아니라 담기는 내용이
    그룹 10행 + 레코드 101행으로 고정이기 때문이다. 성능 지표로 읽으면 안 된다.


6. 이상 징후 (발견된 것 전부)

【이상-1】(e) CTE 의 COUNT 이 ×204 로 초선형 — 100만행에서 가장 빨랐던 변형이 역전
  · 100만행: (e) 159.9ms 로 6종 중 **최속**. 5,000만행: 32,627.8ms 로 6종 중 **최저속**.
  · 대조군 직접 SQL 로는 단순 COUNT 이 13.5초(콜드)·INNER 5.9초·OUTER 1.8초였으므로,
    32.6초는 DB 자체 한계가 아니라 CTE 로 감싼 형태에서 실행계획이 나빠진 결과로 보인다.
  · **운영상 의미**: 통계검증 실행 상한은 기본 60초다
    (services/stats_execute_service.py: EXECUTE_STATEMENT_TIMEOUT_MS=60000,
     오라클은 services/db_adapters/oracle.py 의 conn.call_timeout 으로 적용).
    (e)의 32.6초는 그 상한의 54% 지점이다. 같은 추세라면 **1억행 규모에서는
    CTE 형태의 COUNT 이 기본 상한에 걸릴 가능성이 높다.**
  · 이번 측정에서는 6종 전부 상한 미만이라 실제 타임아웃은 발생하지 않았다
    (측정 전 대조군 프로브로 60초 초과 항목 0건을 확인하고 기본 정책 그대로 측정했다).
  · 판정: 지금 당장의 장애는 아니지만 규모 확대 시 1순위 위험. 코드 수정 없음(측정 범위 밖).

【이상-2】드릴다운 화면 계측 문구가 실제 대기시간을 크게 과소표현 — 규모가 커질수록 악화
  · (a) 1회차: 실제 벽시계 54.46초인데 화면 계측 문구는
    "준비확인 2,524ms · scope 조회 22ms · 렌더 1ms" 로 약 2.5초만 표시한다.
  · 변형별 (실측초 / 화면표시초): (a) 54.46/2.5  (b) 39.36/8.6  (c) 41.42/9.2
    (d) 64.85/11.4  (e) 35.11/10.6  (f) 81.56/9.6
  · 100만행에서는 벽시계 2.17~2.94초 / 화면 0.46~1.02초로 격차가 2~3배였는데,
    5,000만행에서는 4~22배로 벌어졌다.
  · 원인 구조: /agg-diff/prepare 는 드릴다운 클릭이 트리거하는 **비동기** 준비 작업이고,
    화면 계측 문구는 준비가 끝난 뒤의 **최종 확인 왕복**만 잰다. 준비 자체의
    대기시간(응답 stage_timings.prepare_ms — (a) 기준 42,350ms)은 문구에 들어가지 않는다.
  · 영향: 사용자는 "1분 가까이 기다렸는데 화면은 2.5초 걸렸다고 한다"를 보게 된다.
    성능 회귀를 화면 숫자로 판단하면 놓친다.
  · 판정: 화면 표시 신뢰성 문제. 코드 수정 없음(측정 범위 밖).

【이상-3】재이관 "레코드" 수집이 101건에서 조기중단 — 참값 500,000건 (과소표현 폭 50배 악화)
  · 6종 전부 동일: counts = {reimport_pks: 101, passed: 9,999, missing_migration: 101},
    early_stopped=true, 그룹당 10~11건만 저장. Excel '재이관 대상 레코드' 시트도 101행.
  · **100만행 때와 수치가 글자 그대로 동일하다**(101건 / passed 9,999). 즉 이 상한은
    데이터 규모와 무관하게 고정이며, 원인은 이미 규명된 그룹 표시정책의 수집 상한이다:
    per_group_policy = {per_group_full_list_max: 100, per_group_early_stop_abs: 101,
    per_group_partial_display_max: 100} (services/per_group_display_policy.py).
  · 문제는 **참값이 10,000 → 500,000 으로 50배 커졌는데 수집량은 101 로 그대로**라는 점이다.
    - 100만행: 101 / 10,000  = 1.01% 확보
    - 5,000만행: 101 / 500,000 = 0.02% 확보
  · 화면은 조용한 실패가 아니다 — display_tier_info 가
    display_tier="D4", display_mode="SUMMARY_ONLY", display_reason_code="EARLY_STOPPED" 이고
    "불일치 10건 이상(그룹 10개) — 수집이 조기중단되어 정확한 총 건수는 확인하지 않았습니다"
    배너를 붉게 띄운다.
  · 그러나 같은 응답의 display_tier_info.total_mismatch_count 는 **10** 이고,
    드릴다운 패널 머리말도 "재이관 대상 전체 10건"으로 표시된다. 참값 500,000 대비
    5만분의 1 이다. 배너를 읽지 않으면 10건으로 오독할 여지가 100만행 때보다 훨씬 크다.
  · 지침의 "검출건수 참값 일치(전부 500,000건)" 는 **그룹 단위 검출에서는 충족**한다(§3-2).
    충족하지 않는 것은 레코드 단위 전량 추출이며, 이는 성능이 아니라 상한 정책의
    구조적 제약이다(clamp_per_group_thresholds HARD CAP 500 — 이미 100만행 보고서에서
    상한을 500으로 올려 대조 측정해 도달 불가를 확인한 바 있다).
  · 판정: 정책 변경이 필요한 사안이므로 이번 측정에서는 사실만 보고한다(코드/정책 수정 없음).

【이상-4】(f) 복합에서 ORA-00904: "REGION_NM": invalid identifier — 100만행과 동일하게 재현
  · (f)에서만 3단계·4단계 진입 시 각 1회씩 "profile DB 실행 실패 (join=False):
    ORA-00904: "REGION_NM": invalid identifier" 가 서버 로그에 찍힌다(총 2회 관측).
  · 100만행 보고서【이상-2】와 완전히 동일한 현상이 5,000만행에서도 그대로 나타났다
    → **규모와 무관한 기존 결함**임이 추가 확인됐다.
  · 화면에는 오류가 표시되지 않고 후보 컬럼 선정·통계검증은 정상 완료되며 결과값도 정확하다
    (검출 500,000건 일치). 후보 프로파일 수집 경로가 조용히 실패하고 폴백으로 진행되는 형태다.
  · (c) LEFT OUTER JOIN 단독에서는 발생하지 않는다.

9. 종합 판정

  · 정확성: 그룹 단위 검출은 5,000만행에서도 **완벽하다**. (a)(c)(d)(e)(f) 전부
    500,000건, (b)는 설계대로 250,000건. 쿼리 형태가 달라도 정답이 같고,
    INNER/OUTER 차이가 R99 250,000행만큼 정확히 나타난다.
  · 전략 선택: 6종·50배 규모에서도 DIRECT_STREAM_COMPARE / DIRECT_COMPOSITE_PK 로 불변.
  · 스케일링: 단일 결론으로 말할 수 없고 항목마다 갈린다.
      - 초선형(악화)  : COUNT ×100.2  · 재이관 수집 ×64.3
      - ≈선형         : 통계검증 ×42.7
      - 선형미만(이득): 드릴다운 1회차 ×20.7 · 드릴다운 2·3회차 ×1.0(상수) · Excel ×1.19
    다만 선형미만인 항목들은 "빠르다"기보다 **수집 상한(101건) 때문에 일이 늘지 않은 것**이며,
    그 상한이 곧 §6【이상-3】의 한계다. 순수하게 규모에 비례해 일한 항목은 통계검증뿐이고
    그것이 정확히 선형이라는 점이 이번 측정의 가장 건강한 결과다.
  · 실사용 관점 최대 위험 2가지
      (1) COUNT 초선형 — (e) CTE 32.6초는 기본 상한 60초의 54% 지점.
          1억행 규모에서는 타임아웃 위험이 현실화될 수 있다.
      (2) 재이관 레코드 전량 추출 불가 — 참값 500,000 중 101건(0.02%)만 확보되고,
          화면 요약은 "10건"으로 표시된다.
    둘 다 성능 튜닝이 아니라 정책/구조 결정이 필요한 사안이라 사실만 보고했다.
