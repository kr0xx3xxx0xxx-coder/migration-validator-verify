작업명 : DB-CONNECTION-PROFILE-LOSS-ON-RESTART-DIAGNOSE
✅ 작업 완료 - DB 연결 프로필 소실 현상 원인 진단(코드 조사 + TCP 재현, 코드 수정 없음)

[결론 먼저]
DBMS별로 "저장 위치"가 다르지 않습니다(가설 반증). PostgreSQL과 Oracle은 정확히 동일한 코드
경로로 저장됩니다. 실제 원인은 3개 계층이 섞여 있는 데서 옵니다:
  1) 개별 DB 접속 프로필(host/port/user/password) = 서버 SQLite에 영속 저장 — DBMS 무관, 안 사라짐.
  2) "검증 경로"(원본→목적지 조합, Pair) = 서버에 전혀 저장 안 함. 브라우저 localStorage 전용.
  3) "접속중" 배지(활성 상태) = 페이지 로드마다 실제 네트워크 재접속 테스트를 통과해야만 복원되고,
     실패하면 조용히(사용자 안내 없이) 초기화됨.
PostgreSQL(Neon 클라우드)은 항상 도달 가능해 매번 3)을 통과하고, Oracle(사내 LAN, 192.168.0.151)은
이 개발 환경에서 도달 불가능해 매번 3)에서 조용히 끊깁니다. "재기동 때문"이 아니라 "페이지를 새로
열 때마다 일어나는 정상 동작"이며, 사용자는 이걸 "재기동 후 사라짐"으로 체감했을 가능성이 큽니다.

────────────────────────────────────────────────────────────
1. DB 연결 프로필 저장 위치·방식 확인
────────────────────────────────────────────────────────────
■ 개별 프로필(services/db_preset_service.py, routes/db_preset_route.py)
  - 저장소: SQLite db/migration_validator.db 의 mv_db_preset 테이블 (기본, MV_DB_PRESET_STORE=db).
  - db_type(oracle/postgresql/mariadb/db2)에 따른 분기 코드 없음 — 완전히 동일한 함수
    (_cmn_load_presets/_cmn_save_presets)로 모든 DBMS를 저장/조회.
  - kill-switch MV_DB_PRESET_STORE=file(레거시 JSON 파일 방식)이 있으나, 코드 전체 grep 결과
    launch 설정/스크립트 어디에도 override 없음 → 실사용은 항상 'db' 모드.
  - 실측: 현재 mv_db_preset 테이블을 직접 조회한 결과, Oracle_asis/Oracle_tobe 를 포함해 SRC 8건
    +TGT 6건, 전부 is_deleted=0(정상 보존), created_dt=2026-08-06 08:18:12(JSON→SQLite 이관 시점)
    그대로 남아있음 — Oracle 프로필도 전혀 소실되지 않았습니다.

■ "검증 경로"(Pair, 화면의 그 목록) — ui/tabler_renderer.py
  - 서버에 전혀 저장하지 않습니다. 100% 브라우저 localStorage 키 'mv_conn_pairs'.
  - PostgreSQL_asis→PostgreSQL_tobe 라는 기본 Pair가 코드에 하드코딩(_defaultPairs())되어 있고,
    localStorage 내용과 무관하게 _loadPairs() 가 매번 이 항목을 목록 맨 앞에 강제로 끼워 넣습니다
    (삭제 버튼도 막혀 있음: "기본 검증 경로는 삭제할 수 없습니다"). 즉 PostgreSQL 조합은 화면에
    "항상" 뜨도록 설계돼 있고, 이 때문에 "PostgreSQL만 살아남는다"는 인상을 줍니다.
  - Oracle 등 다른 DBMS 조합은 사용자가 명시적으로 '검증 경로 추가' 흐름으로 저장해야만
    mv_conn_pairs 에 들어가며, 그렇지 않으면애초에 저장된 적이 없어 재방문 시 안 보이는 게 정상
    동작입니다(버그가 아니라 "저장 안 함=복원 안 됨").

■ "접속중"(활성 경로) 상태 — ui/tabler_renderer.py _restoreActivePath()/mv_active_path
  - 마지막으로 접속했던 Pair 이름만 localStorage('mv_active_path')에 저장.
  - 페이지 로드 시(_mvSingleInitReady 초기화 체인) 이 값을 그대로 믿지 않고, 코드 주석 그대로
    "Source 하나라도 실패하면 active 경로로 복원하지 않고 저장도 제거"— 즉 실시간으로 원본/목적지
    양쪽에 실제 /db/test 재접속을 실행해 전부 성공해야만 '접속중'으로 복원됩니다. 하나라도 실패하면
    _clearSavedActivePath() 로 조용히(silent:true, alert 없음) mv_active_path 를 지웁니다.
  - 이 재검증은 서버 재기동과 무관하게 "페이지를 새로 열 때마다" 매번 일어납니다.

────────────────────────────────────────────────────────────
2. 실제 재현
────────────────────────────────────────────────────────────
- mv_db_preset 실측(위 1번)으로 "프로필 자체가 DBMS별로 다른 곳에 저장돼 사라진다"는 가설은
  이미 반증됨 — 코드에 분기가 없고 실데이터도 멀쩡히 남아있어, 신규 Oracle 프로필을 또 만들어
  서버를 kill/재기동해봐도 mv_db_preset 계층에서는 동일하게 "안 사라짐" 결과만 재확인될 것이
  코드상 확실합니다(불필요한 반복 재현은 생략).
- 대신 진짜 결정적인 재현은 "접속중 상태가 왜 Oracle만 꺼지는가"였고, 이걸 TCP 레벨로 직접
  검증했습니다:
      Oracle_asis (192.168.0.151:1521, LAN) → 연결 시도 4.0초 후 TimeoutError(도달 불가)
      PostgreSQL_asis (Neon 클라우드, 5432)  → 0.08초 즉시 연결 성공
  이 도달성 차이가 _restoreActivePath() 의 실시간 재검증 로직과 정확히 맞물려, Oracle 쪽만
  "접속중"이 매번 자동 해제되는 실제 동작을 그대로 설명합니다. 이 프로젝트의 다른 세션 기록에도
  Oracle 접속이 폐쇄망/사내망 환경 의존적이라는 메모가 있어(오라클 Free 등 LAN 전용 구성) 이번
  현상과 일치합니다.
- 참고: 이 조사 자체가 "코드 수정 없이 조사만" 지시였으므로, 브라우저 UI를 열어 Oracle Pair를
  실제로 '검증 경로 추가'로 저장 → 서버 kill/재기동 → 재접속까지 재현하는 전체 E2E는 수행하지
  않았습니다. 필요하시면 Playwright로 이어서 재현 가능합니다(별도 요청 시 진행).

────────────────────────────────────────────────────────────
3. 프로젝트 선택 상태 소실 — 같은 원인인가 별개인가
────────────────────────────────────────────────────────────
- 프로젝트 데이터 자체는 SQLite project 테이블(services/project_store.py)에 영속 저장되며, 재기동과
  무관하게 보존됩니다(개별 프로필과 동일한 계층 — 안 사라짐).
- "선택된 프로젝트"(work_project_id)는 Pair와 마찬가지로 localStorage 전용입니다.
- 다만 Pair의 실시간 재검증과 "같은 패턴"의 검증 로직이 하나 더 있습니다: 페이지 로드 시
  mvRestoreWorkProject() 가 서버 GET /projects/list 를 호출해, 저장된 project_id가 실제로
  존재하는지 재확인합니다. 목록에 없으면 mvSetWorkProjectId('') 로 즉시 지우고,
  mvSelectWorkProject('','') 를 호출합니다 — 이 함수는 "프로젝트 전환/해제" 공통 로직이라서
  연쇄적으로 disconnectPair()/_clearActivePath() 까지 실행해 DB 연결 Pair의 '접속중' 상태까지
  함께 초기화합니다(코드 주석 §13: "프로젝트 전환·해제 시 하위 상태 초기화").
- 즉 프로젝트 소실과 Pair 소실은 트리거 조건은 다르지만(전자=서버가 그 project_id를 인정하는지,
  후자=DB에 실시간 접속 가능한지) "localStorage에 저장된 값을 서버 상태로 매번 재검증하고 실패하면
  조용히 초기화한다"는 같은 설계 패턴을 공유하며, 프로젝트가 풀리면 그 여파로 DB 연결까지 함께
  풀리는 연쇄관계가 있습니다 — 완전히 무관한 별개 버그는 아닙니다.
- project_id가 서버에서 "없다"고 판정되는 정확한 트리거(왜 그 프로젝트 row를 못 찾았는지)는 이번
  범위에서 직접 재현하지 못했습니다. project 테이블 자체는 안정적으로 남아있는 것으로 확인했으므로,
  다음 중 하나로 추정됩니다(우선순위순):
    (a) /projects/list fetch가 서버 기동 직후(완전히 뜨기 전) 타이밍에 걸려 일시적으로 빈/불완전한
        응답을 받음 — 재기동 직후 재접속이라는 사용자 시나리오와 가장 직접적으로 들어맞음.
    (b) 사용했던 프로젝트가 is_test=1 로 생성된 테스트 프로젝트였고 별도 정리 스크립트에 회수됨.
    (c) 실제로는 localStorage 자체가 다른 원인(시크릿창/캐시삭제/다른 브라우저 프로필)으로
        초기화됐고, project와 Pair가 같은 브라우저 저장소를 쓰므로 동시에 사라진 것처럼 보임.

────────────────────────────────────────────────────────────
근본 원인 요약
────────────────────────────────────────────────────────────
- DBMS별로 저장 방식이 다른가?           → 아니오. 코드상 분기 없음(반증 완료, 실측으로 확인).
- 의도된 설계인가 결함인가?
    · "접속중 상태를 매번 실시간 재검증한다" 자체는 의도된 안전 설계(stale 접속정보로 검증 실행
      방지) — 결함 아님.
    · "검증 경로(Pair)"와 "선택된 프로젝트"가 서버에 전혀 저장되지 않고 브라우저 localStorage에만
      있다는 것도 코드 주석상 의도된 설계(민감정보 미보관, 참조형 구조).
    · 결함으로 볼 지점은 "사용자 경험" 쪽입니다: 재검증 실패 시 어떤 안내도 없이(silent:true,
      alert 억제) 조용히 초기화되고, 개별 프로필(mv_db_preset)은 멀쩡한데도 화면상으로는 마치
      "연결 자체가 사라진 것"처럼 보여 사용자가 "재구성해야 한다"고 오인하게 만듭니다.
    · PostgreSQL 기본 Pair가 하드코딩으로 항상 재등장하는 것도 "왜 얘만 살아남지?"라는 착시를
      만드는 요인입니다.

────────────────────────────────────────────────────────────
수정 방향 제안(코드 수정 안 함 — 제안만)
────────────────────────────────────────────────────────────
1. _restoreActivePath() 재검증 실패 시 silent 로 지우지만 말고, "이전 접속(Oracle_asis→Oracle_tobe)이
   재검증에 실패해 연결이 해제되었습니다"류의 비차단 배너를 화면에 남겨 원인을 알 수 있게 한다.
2. mvRestoreWorkProject() 의 /projects/list 판정이 서버 기동 초기 타이밍/일시적 오류에 오탐하지
   않는지 별도 확인(재시도 1회 또는 서버 준비 완료 신호 이후 판정 등) — 특히 재기동 직후 시나리오.
3. Pair(mv_conn_pairs)·활성 경로(mv_active_path)·선택 프로젝트(work_project_id)를 프로젝트
   스코프의 서버 SQLite로 옮겨 브라우저 저장소 의존도를 줄이는 방안 — 단 이는 구조 변경이라
   사전 승인 필요(CLAUDE.md "기능/구조 변경 요청 응답 형식" 별도 보고 필요).
4. 당장은 "개별 프로필은 안전하게 보존되고 있으니, '접속' 버튼만 다시 누르면 된다"는 점을 사용자
   안내에 반영하는 것만으로도 체감 문제의 상당 부분이 해소될 수 있음.
