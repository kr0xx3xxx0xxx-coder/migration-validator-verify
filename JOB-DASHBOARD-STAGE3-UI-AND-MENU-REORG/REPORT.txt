실측 대조(Before/After, 실제 서빙 DOM 추출):

Before 수치는 진단 보고서와 100% 일치했고(그룹 8/항목 28/준비중 15/죽은 링크 14),
After 는 재배치 후 같은 스크립트로 다시 뽑았다.

최종 구조는 시안 그대로다:
  현황(검증 현황판) / 프로젝트(2) / 데이터 준비(3) / 검증 실행(3) /
  결과·진단(3) / 검증 기준(2) / 기반정보·설정(1)

여기서 정직하게 짚어야 할 두 가지가 있다.

(가) 항목 수는 15이지 17이 아니다.
     진단 보고서 §7 은 "항목 28→17(-11)"이라고 적었지만, 같은 문단에 열거된 시안
     항목을 실제로 세면 1+2+3+3+3+2+1 = 15다. 즉 보고서의 17은 산술 오기다.
     구현은 "열거된 시안" 쪽을 따랐다(제거 14 + 신설 1 = 28-14+1 = 15).

(나) 죽은 링크는 0이 아니라 1이다.
     시안은 "죽은 링크 14→0"이라고 적었지만, 동시에 "시맨틱 사전은 최장 방치(66일)
     이지만 후보추천 explainability 부채를 드러내는 유일한 표식이므로 존치"라고도
     적었다. 시맨틱 사전은 화면이 없으므로 존치하는 한 클릭 무반응인 채로 남는다.
     두 지시가 서로 배타적이어서 "존치" 쪽을 따랐고, 그 결과 죽은 링크는 1개다.
     (전수검증은 빈 셸이나마 실화면이 있어 화면 전환이 일어나므로 죽은 링크가 아니다.)

제거한 항목은 전부 진단에서 "클릭해도 화면 전환이 전혀 없음"으로 실측된 것이고,
기능 코드는 한 줄도 지우지 않았다. 오표기였던 4건과 흡수한 3건이 여전히 도달
가능한지는 브라우저에서 실제로 showTab 을 태워 DOM 존재를 확인했다(§5 회귀 항목):

  업로드 배치 이력   → 이관쿼리 업로드 화면 #quHistoryCard        도달 OK
  최신 검증대상      → 일괄검증 화면 #batchLatestCard             도달 OK
  증적 다운로드      → 검증 결과 상세의 CSV/XLSX 버튼             도달 OK
  검증 그룹          → 프로젝트 > 검증 그룹 관리                  도달 OK
  자동진단           → 화면 코드(tab-diagnosis) 그대로 존치       도달 OK
  드라이버/준비현황  → DBMS 실행 지원 화면이 흡수                 도달 OK
  후보추천 감사 리포트 → 후보추천 정책 화면 내부 탭으로 이동      도달 OK

자동진단은 특히 조심해서 다뤘다. 진단이 경고한 대로 개별검증 불일치 행을 클릭하면
인라인으로 펼쳐지는 별도 경로가 이 화면 코드를 쓰기 때문에, 메뉴 진입점만 없애고
tab-diagnosis 자체는 손대지 않았다. 회귀 테스트가 이를 강제한다.

DBMS 실행 지원 흡수는 실제로는 "라벨 정정"에 가깝다. 그 화면의 로더는 이미
dbms-capabilities + dbms-execute-readiness + dbms-execute-contract 3종을 함께
조회하고 있었는데, 준비현황 부분이 "고급: 타 DBMS 실행 준비 상세"라는 접힌
details 안에 숨어 있었다. 새 API 를 만들지 않고 기본 펼침으로 올리고 라벨을 실제
내용에 맞췄다.

후보추천 감사 리포트는 구현이 아예 없다. 그래서 메뉴에서 빼되 정책 화면 안에 탭을
만들고, 그 안에서 "왜 아직 없는지(근거가 실행 응답과 후보 표에만 남고 실행을
가로질러 모으는 저장·집계 계층이 없음)"와 "지금 확인 가능한 대체 경로"를 문장으로
적었다. 죽은 링크를 화면 안으로 옮겨 심지 않기 위해, 탭 자체는 정상 동작하고
내용이 정직하게 준비중이라고 말하는 형태로 만들었다.

tab-home 은 제거했다. 좌측 메뉴에 진입점이 없어 로고로만 도달했고, 표시 숫자가
전부 하드코딩 sample(그룹 28건)이라 실데이터(15건)와 어긋나 있었다. 랜딩과 브랜드
로고를 모두 검증 현황판으로 연결하고, #tab-home 전용 CSS 92줄도 함께 지웠다.
(.mv-home-top 등 검증 그룹 화면이 재사용 중인 클래스는 남겼다.)


3. 검증 현황판 — 표시 원칙을 코드로 강제한 부분
--------------------------------------------------------------------------------
선행 진단들이 이미 확정한 원칙을 화면에서 다시 정하지 않고 그대로 구현했다.

잔여시간(ETA)은 표시하지 않는다. 실행 시간의 대부분이 DB read 대기이고 그 편차가
커서(동일 작업 wall 2.2배 실측) 남은 시간을 예측할 근거가 없다. 화면에는 "잔여시간은
예측 근거가 없어 표시하지 않습니다"라는 안내만 있다.

분모를 모르는 job 은 가짜 진행률을 만들지 않는다. job_registry 가 percent=None 으로
내려준 job 은 Tabler 의 무한 스피너(progress-bar-indeterminate) + "처리 147,000건
(전체 미상) · 분모를 모르는 job 이라 진행률을 계산하지 않습니다"로만 표시된다.
상단 전체 비율에서도 이런 job 은 분자·분모 양쪽에서 빼고, 대신 "분모 미상 1건"을
따로 밝힌다. 실측 스크린샷에서 확인된다.

정체는 판정하지 않는다. stall_seconds/progress_signal 을 참고 문구로만 쓰고 경고
색상이나 자동 개입은 없다. 근거 종류도 함께 밝힌다 — 진행 시각이 실재하면
"방금 갱신됨 / N분째 갱신 없음", 일괄검증처럼 진행 시각 컬럼 자체가 없으면
"진행 신호 없음 · 시작 후 13초 경과"처럼 시작 시각 기준임을 드러낸다.
임계값(STALL_TTL)은 여전히 미정이고, 이번에도 정하지 않았다.

제어는 기존 API 만 호출한다. 개별검증은 /single/active-run/pause·cancel,
일괄검증은 /api/batch-runs/{batch_run_id}/pause·cancel(batch_pause_control),
통계검증은 stats-validation-plans/execute/{run_id}/cancel 이다. 제어에 필요한 키가
DTO 에 없으면 버튼을 만들지 않고 "batch_run_id 없음 — 제어 불가"라고 사유를 적는다.
임의 추론으로 버튼을 만들지 않았다.

부모-자식 2단 목록은 일괄/통계는 group_id, 개별검증은 session 을 부모로 묶었다.
여기에는 한계가 있다 — 통합 조회 API 는 job 단위 목록만 제공하므로 "배치 안의
테이블별 자식 목록"은 현재 처리 대상(current_target) 1건까지만 알 수 있다. 없는
세부를 지어내지 않았고, 그래서 자식 행은 job 이고 테이블은 그 job 의 현재 대상으로
표시된다.

도넛 차트는 지시와 다르게 구현했다(의도된 이탈, 아래 §6).


4. 폴링 — 단일 타이머임을 네트워크로 증명
--------------------------------------------------------------------------------
화면당 타이머는 정확히 1개다(_MV_JD.timer, setTimeout 체인). setInterval 이 아니라
체인이라 응답이 늦어도 요청이 겹치지 않는다. 브라우저 네트워크 요청을 12초간
전수 기록해 확인했다:

  /jobs/active 요청 4회, 간격 [3.07s, 3.07s, 3.08s] — 설정값 3초와 일치
  같은 구간에서 3회 이상 반복 호출된 다른 endpoint: 없음 ({})

주기는 하드코딩하지 않았다. execution_settings.polling 에 3개 필드를 새로 넣고
화면이 /api/execution/settings 로 1회만 읽는다.
  job_dashboard_poll_interval_ms = 3000   현황판 표시 중
  job_badge_poll_interval_ms     = 15000  이탈 후 좌측 배지만 갱신
  job_poll_stop_when_idle        = True   이탈 + 활성 job 0 이면 정지

이탈 동작도 실측했다. showTab('batch')로 현황판을 벗어난 뒤 9초간 /jobs/active
요청은 0회였다(배지 주기 15초로 낮아짐). 모든 job 이 끝나면 타이머 자체가 멈춘다.

좌측 메뉴 배지는 별도 폴링을 만들지 않고 같은 응답을 재사용한다. 항목 배지
(개별검증/일괄검증/전수검증)와, 그룹이 접혀 있을 때를 위한 "검증 실행" 그룹 헤더
합계 배지 둘 다 이 한 번의 응답으로 갱신된다. 개별검증의 기존 "진행 중이던 검증
작업이 있습니다" 팝업은 지시대로 손대지 않았다 — 배지와 공존한다.


5. 실측 결과 (34/34 PASS)
--------------------------------------------------------------------------------
내부망 DB 가 이번에도 미가용이라 STAGE2 와 같은 전략을 썼다. 다만 STAGE2 와 다른

6. 지시와 다르게 한 것 — Chart.js 도넛
--------------------------------------------------------------------------------
지시는 "전체 진행률: Chart.js 도넛/링 차트"였다. 구현은 **의존성 없는 인라인 SVG 링**
으로 했다. 이유는 세 가지다.

  · Chart.js 는 이 저장소에 vendoring 돼 있지 않다(static/vendor 에는 tabulator 뿐).
  · CLAUDE.md 상 외부 패키지 도입은 사용자 승인 사항이고, Chart.js 승인 이력이 없다.
  · 폐쇄망 전제라 CDN 을 쓸 수 없어, 도입하려면 정적 파일을 새로 vendoring 해야 한다.

형태(가운데 비율이 뚫린 링)와 역할(전체 대비 완료 비율)은 동일하고, 라이브러리는
0개 추가했다. 실제 Chart.js 자체가 필요하다면 vendoring 승인이 선행돼야 한다 —
그때 이 SVG 를 교체하는 건 한 함수(_jdRenderOverall)만 바꾸면 된다.

8. 남은 것 / 다음 단계에 넘기는 것
--------------------------------------------------------------------------------
· 정체 경고 임계(STALL_TTL)는 여전히 미정이다. 내부망 복구 후 heartbeat gap 실측이
  선행돼야 하며, 그 전까지 stall 은 숫자·문구 표시만 하고 경고로 승격하지 않는다.
· 일괄검증의 진행 시각 부재는 통합 계층에서도 화면에서도 메울 수 없다. 원본 저장소에
  updated_at 을 추가하는 것은 별도 단계다. 현재는 "시작 시각 기준"임을 화면이 밝힌다.
· 배치 안의 테이블별 자식 목록은 API 가 제공하지 않아 현재 대상 1건까지만 보인다.
  진짜 테이블 단위 2단이 필요하면 job_registry 에 자식 목록을 추가하는 단계가 필요하다.
· 개별검증의 "진행 중이던 검증 작업이 있습니다" 팝업을 배지로 완전 대체하는 것은
  이번 범위 밖(별도 승인 필요)이라 공존 상태로 뒀다.
· 시맨틱 사전은 화면이 없어 여전히 클릭 무반응이다(로드맵 표식으로 의도적 존치).
· 고객 공유(현황판 외부 공개)는 사용자가 명시적으로 보류했고 이번 범위가 아니다.
