      을 그대로 노출해, 화면에서 본 배지 문구와 에러 문구 사이에 **어휘 불일치**가 있다 — 이것이
      사용자가 "실제 상황과 안 맞아 보인다"고 느낀 근본 원인이다. 원인(조건) 자체가 틀린 것은
      아니다 — REGION_NM은 실제로, 확정적으로 HOLD 상태였다.

■ 4. REGION_NM이 "관리컬럼 미확인"으로 남은 이유 (조사범위 3)
  판정: **관리컬럼 자동판정 로직이 "조인으로 가져온 컬럼"을 제대로 처리하지 못했다** — 정확히는
  판정에 필요한 값 샘플(sample_values)이 애초에 배선되지 않아 A축(값) 판정이 "판정불가(None)"로
  고정된 것이 원인이다.
  (1) 판정표(services/candidate_subtype_service.py:710-734 `evaluate_admin_audit_crosscheck`
      docstring) — "B=False + A=None + 값 미배선(N1) → NOT_AUDIT_AMBIGUOUS". REGION_NM 은
      B축(명칭/코멘트가 관리컬럼 표준사전과 매칭)이 False(REGION_NM 은 REG_DT/BATCH_ID 류 감사
      컬럼명 사전과 무관)이고, A축(값)이 판정불가(None)였다.
  (2) A축이 None 이 된 경로 — `candidate_system_audit_value_verdict()`
      (candidate_subtype_service.py:661-676) 는 `_candidate_sample_values(candidate)` 가 None
      이면(즉 `candidate['sample_values']`/`['value_samples']` 가 비어 있으면) 곧바로 None 을
      반환한다(295-302행). REGION_NM 의 sample_values 가 비어 있었다는 뜻이다.
  (3) sample_values 배선이 안 된 이유 — services/column_profile_service.py:155-238
      `resolve_candidate_sample_values()`:
        ① column_profiles 재사용(199-206행) — `collect_column_profiles` 가 미리 만들어 둔
           프로필 맵에서 값을 가져오는 경로다. 이 프로필은 이관 SELECT의 **from_table(기준
           테이블) 자체 컬럼**을 대상으로 하는 것이 정상 동작이며(스키마상 REGION_NM 은 SRC
           테이블에 없고 DIM 테이블 JOIN 으로만 존재 — MV-SCATTER50M-SCHEMA-QUICK-CHECK 기존
           조사 확인), 그 프로필 맵에 REGION_NM 항목이 아예 없다면 이 경로는 값을 못 찾는다.
        ② mv_column_sample(SQLite) 캐시 재사용 — 이 테이블/컬럼을 처음 분석하는 시나리오라면
           캐시도 비어 있다.
        ③ 실DB LIMIT 100 라이브 조회(211행) — 유일하게 새로 값을 떠올 수 있는 경로이지만
             `if allow_db_fetch and src_db_info and not has_join:`
           **JOIN 이 있으면(`has_join=True`) 이 경로 전체가 통째로 비활성화된다.** 실제 호출부인
           services/candidate_postcount_finalize.py:791-806 은
             has_join=bool(join_clauses)
           로 넘긴다 — MV_SCATTER50M 이관 SQL 은 DIM 테이블과 JOIN 하므로 `join_clauses` 가
           비어 있지 않고, 따라서 `has_join=True` → ③ 경로가 이 테이블의 **모든 후보(REGION_CD/
           STATUS_CD/REGION_NM 전부)에 대해** 꺼진다. 다만 REGION_CD/STATUS_CD는 SRC 테이블
           자신의 컬럼이라 ①(column_profiles, from_table 단일 테이블 기준 프로파일링)에서
           정상적으로 값을 확보하므로 문제가 드러나지 않고, REGION_NM 만 애초에 SRC 테이블에
           없는 컬럼이라 ①에서도 항목 자체가 없어 두 경로(①③) 모두에서 값을 못 얻는다.
      ③ 경로가 `has_join` 전체를 끄는 이유는 방어적 설계다(211행 인접 주석,
      PROFILE-COLLECTION-CTE-JOIN-COLUMN-REFERENCE-FIX) — "base 테이블에 없는 컬럼을 섞어
      조회하면 값 샘플 SELECT 한 건이 통째로 실패해(ORA-00904) 정상 컬럼 샘플까지 같이 잃는다"는
      과거 결함의 재발 방지책이다. 즉 "JOIN 파생 컬럼이 있으면 그 배치 전체의 라이브 조회를
      끈다"는 **의도된 안전장치**이지만, 그 부작용으로 "JOIN 파생 컬럼 자신은 어떤 경로로도 값을
      영영 못 받는다"는 사각지대가 생겼다 — CTE_FLATTENED 화이트리스트(192-196행)로 이 사각지대를
      메우는 장치가 이미 같은 함수에 있지만, candidate_postcount_finalize.py 호출부는 CTE(WITH절)
      평탄화 케이스만 `source_scope`를 채워 넘기고(804-805행 주석), 일반 JOIN(비-CTE) 파생 컬럼인
      REGION_NM 케이스는 그 화이트리스트 대상이 아니라서 구제되지 않는다.
  (4) 결론 — REGION_NM 이 "관리컬럼 미확인"으로 남은 것은 REGION_NM 의 실제 데이터 성격과 무관하게,
      "JOIN 으로 가져온 컬럼"이라는 구조적 이유만으로 값 샘플이 원천적으로 배선되지 않아
      A축이 항상 판정불가(None)로 고정되기 때문이다 — 관리컬럼 자동판정 로직이 JOIN 파생 컬럼을
      제대로 처리하지 못한다는 지시서의 가설이 코드로 확정됐다.

■ 5. 종합 결론 (조사범위 4)
  ① 3축 UI 출처: 신규/부활 기능 아님 — 조합PAIR 체크박스 라벨의 축 이름 나열 오기(기존 조사가
     이미 예견) + 참고용 결합SQL(기존 기능) + 3단계 비용예측 칩(단일축 합산치, 조합과 무관)
     3개가 "3축 후보 선택 + 대형 테이블"에서 처음으로 함께 노출된 것. 실제 실행 세트 구성은
     여전히 단일축 N개 + PAIR 1개뿐이며 이는 오늘 재확인(§2)으로 무변경 확정.
  ② 에러 문구: 발동 조건(REGION_NM=REC_HOLD)은 정확하고 재현 가능한 결정론적 원인
     (_RE_NAME_DESC 의 `_NM` 접미사 매칭 → NAME_DESC_CANDIDATE → REC_HOLD)이 있다. 다만 문구가
     쓰는 "제외/보류"라는 단어가 실제 화면 배지("보조확인후보")에는 등장하지 않아, 사용자가
     화면에서 본 것(관리컬럼 미확인 배지)과 에러가 지목하는 것(HOLD, 별개 축)이 다르다는 데서
     오는 오인 소지가 실재한다 — "부정확"이 아니라 "배지 문구와 에러 문구 간 어휘 불일치"로 판정.
  ③ REGION_NM 미확인 원인: JOIN 파생 컬럼에 대한 값 샘플 배선 경로 공백(has_join 게이트 +
     CTE_FLATTENED 화이트리스트가 일반 JOIN은 커버 안 함)이 원인 — 코드로 확정.
  ④ 판단불가 항목 없음 — 3가지 모두 파일:라인 근거로 확정했다. 코드 수정은 지시서 원칙대로
     수행하지 않았다(조사 전용).
  ⑤ (참고, 조사범위 밖 — 기록만) 실행 안전 게이트(groupby_execution_safety_gate)가 SQL
     미리보기/비용추정 단계가 아니라 실제 실행 요청 시점에만 발동해, 사용자가 문제없어 보이는
     화면(SQL+비용추정)을 다 확인한 뒤에야 뒤늦게 차단을 만난 것도 이번 혼란에 기여했다 — 조사
     범위 밖이라 개선 여부는 판단하지 않았다.
