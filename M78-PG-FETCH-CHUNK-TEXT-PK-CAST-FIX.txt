────────────────────────────────────────────────────────────────
1. 배경/증상
────────────────────────────────────────────────────────────────
BACKLOG.md M78 항목(2026-08-12 발견): PostgreSQL make_pg_fetch_chunk()
(services/exact_diff/dialects/postgresql.py:479 부근)가 "숫자로 노출된 문자
PK"(varchar 컬럼에 '1'..'N' 같은 숫자문자열) 청크 조회 시, WHERE절 바인드
파라미터(int)와 컬럼(varchar) 사이 암묵 캐스트가 없어
`character varying >= integer` 쿼리 오류 즉시 발생.

────────────────────────────────────────────────────────────────
2. 수정 내용
────────────────────────────────────────────────────────────────
파일:라인   services/exact_diff/dialects/postgresql.py:458-506
             (make_pg_fetch_chunk 함수)

make_pg_fetch_chunk() 생성 시점에 LIMIT 0 메타 probe(1회, N+1 아님)로 key
컬럼의 실제 PG 타입(OID)을 확인 → CAT_TEXT/CAT_CHAR(문자 타입)일 때만
컬럼측을 `(_q.key)::numeric` 캐스트해 비교(WHERE·ORDER BY 동일 적용).
숫자 PK(정수/numeric 컬럼)는 캐스트를 붙이지 않아 기존 동작·실행계획 그대로.

바인드 파라미터(start/end)가 아니라 컬럼측을 numeric 캐스트한 이유: 호출측
build_chunk_bounds() 가 넘기는 start/end 는 이미 축A(_pg_numeric_min_max)가
산정한 "숫자 의미" 경계(정수)라서, 컬럼측을 텍스트로 캐스트해 파라미터와
맞추면(예: '1'..'50') 텍스트 사전식 비교가 되어 순서가 완전히 틀어진다
(예: '9' > '50'). 축A 가 이미 전 행 숫자 변환 성공을 보장한 뒤에만 이
경로가 호출되므로(비숫자 문자는 HOLD_NON_NUMERIC_PK 로 사전 차단) 컬럼측
numeric 캐스트는 안전하다.
