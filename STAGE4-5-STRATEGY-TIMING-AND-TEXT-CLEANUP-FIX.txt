■ 요구사항 1 — 4단계 '통계전략' 표시 시점 정정 (실행 후 → SQL 생성 후)

  판단 근거: '통계전략'은 3단계에서 이미 정해져 그 전략으로 SQL 을 만드는 **계획(plan)**
  정보이지 실행 결과가 아니다. 같은 성격의 값(목적그룹/원본그룹/목적집계/원본집계/조합검증)이
  모두 SQL 생성 시점에 채워지므로 같은 시점에 함께 채운다. 진짜 실행 결과인 '실행시간'·'상태'
  만 계속 실행 후에만 채운다.

  신호: 새 신호를 만들지 않고, 같은 함수가 이미 쓰고 있는 `generated`
        (= gbSel/sumSel 둘 다 null 이 아님 = renderSQL 이 생성에 쓴 선택값이 도착)를 재사용.
        직전 작업이 쓰던 window._mvStage4ExecResult(실행 응답) 게이트를 걷어냈다.

  코드: ui/grid_helpers.py `_mvStage4TileRow`
        before: statsStrategy: (_ex ? _statsStrat : null)
        after : statsStrategy: (generated ? _statsStrat : null)

  실측(SQL 생성 직후, 실행 전):
        before  통계전략 '—' / 실행시간 '—' / 상태 '—'
        after   통계전략 '직접 집계 STATS_DIRECT_AGG' / 실행시간 '—' / 상태 '—'   ← 의도대로

■ 요구사항 4 — 5단계 '처리시간' 표시 시점 조사 및 조정

  [조사 1] 이 값이 재는 구간
    window._mvStage5ProcMs = /execute 응답의 processing_ms 이며, **통계검증 세트 실행
    루프가 끝난 시각까지**만 잰다. 그 직후 비동기로 시작하는 재이관 대상 상세 추출
    (/agg-diff/prepare → pk-records 폴링)은 포함하지 않는다. 이 사실은 이미 라벨에
    드러나 있다 — '5단계 통계검증 실행(상세 추출 별도)'. 즉 사용자가 본 21.57초는
    '통계검증 실행시간'이 맞고 값 자체는 정확했다. 문제는 **표시 시점**이었다.

  [조사 2] '실행/상세' 2줄이 1줄로만 보인 이유
    오늘 ④-2 로 만든 2줄 표기의 '상세' 줄은 window._mvStage5DetailMs 를 읽는데, 이 값은
    **불일치 그룹 상세 패널을 사용자가 펼칠 때**(_mvPkLoadPage) 기록된다. 화면 아래의
    '상세비교 진행 중' / '재이관 대상 준비 중'(= /agg-diff/prepare 백그라운드 수집)과는
    다른 것이다. 그룹을 아직 펼치지 않았으므로 '상세' 줄이 없어 1줄로 보인 것이고,
    이는 결함이 아니라 설계대로다(자동 펼침 미발생 문제도 아님).

  [조정] 표시 시점을 상세비교 완료 시점으로 늦춤 — 가능했고, 적용했다.
    · 진행 여부 판정은 **새 신호를 만들지 않고**, 같은 화면의 '재이관PK' 타일이 '준비 중'
      을 그릴 때 쓰는 상태(window._mvPkState)와 그 확정/미확정 구분식을 그대로 쓴다
      (_mvPkPrepRunning — ui/tabler_renderer.py, _mvUpdatePkSummaryCell 바로 위).
    · 상세비교가 진행 중이면 처리시간 칸을 '—' 로 두고, 사유를 툴팁으로 밝힌다
      ("상세비교(재이관 대상 레코드 수집)가 진행 중입니다 — 완료 후 표시합니다. …").
    · 완료를 화면이 처음 아는 지점(_mvPkAdoptDetail, 폴링 종료 분기, prepare 응답 도착)
      에서 기존 _mvRepaintStage5Tiles 를 불러 값이 '—' 로 굳지 않게 한다(새 렌더 경로 없음).
    · 값 자체(계측·보관·라벨·변환기)는 전혀 손대지 않았다.

    ★ 영구 미표시 방지(중요): 상세비교가 **아예 시작되지 않는** 경로가 있다 —
      불일치 0건(prewarm 조기 return), 자동 준비 상한 초과(deferred), 계획 HOLD,
      일괄/이력 상세 복원 화면. 이 경우 진행 신호가 없으므로 종전대로 값을 그린다.
      또 stream 경로는 prepare 가 PREPARING 으로만 응답하고 완료는 폴링으로만 오므로,
      폴링이 종료를 이미 본 경우(_mvExecTerminal)는 진행 중으로 보지 않는다 —
      표본 조기중단처럼 종료 payload 를 채택하지 않는 상태에서 값이 영영 안 나오는 것을
      막는다. 오판은 항상 '조금 일찍 보여준다'(= 종전 동작) 쪽으로만 기운다.

  실측:
    · 실 흐름(Oracle, 원본 150건): 상세비교가 1초 안에 READY 로 끝나 '진행 중' 구간이
      화면에 잡히지 않았다 — 처리시간 0.95초가 종전처럼 표시됐다(무회귀 확인).
    · 표시규칙 프로브(상태만 강제, 서버 호출 없음):
        진행 중  → before: '0.84초' 표시  /  after: '—' + 사유 툴팁      ← 의도대로
        완료     → before: '0.84초'       /  after: '0.95초'             ← 값 복귀
        미시작   → before: '0.84초'       /  after: '0.95초'             ← 영구숨김 없음
      (스크린샷 before_11/12 · after_11/12)
      ★ before_11 은 이번 요청의 문제 화면 그 자체다 — 같은 타일 줄에서 '처리시간 0.84초'(끝난 것처럼)
        와 '재이관PK 준비 중'(아직 진행 중)이 동시에 떠 있다. after_11 은 '처리시간 —' + '재이관PK
        준비 중' 으로 두 칸이 같은 시점을 말한다.
