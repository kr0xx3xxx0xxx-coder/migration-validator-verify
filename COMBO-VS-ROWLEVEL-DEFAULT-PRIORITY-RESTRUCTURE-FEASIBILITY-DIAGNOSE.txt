[결론 1]
  · 4단계(통계검증) **이전**에 행단위를 독립 선택해 바로 돌리는 스탠드얼론 모드는 **없다.**

    버튼이 이미 있다. 즉 **엔진·API 는 스탠드얼론인데 화면 배치만 5단계 종속**이다.
  · 일괄검증(batch)에는 행단위 경로가 **아예 없다** — 엔진 호출부(run_pk_range_chunk_compare /
    prepare_reimport_pk_index)는 routes/agg_diff_route.py **단 1곳**뿐이고,
    services/batch_*.py 는 batch_stats_execute_service(통계검증)만 있다.

조사 4. M79(이기종 DBMS)와의 공존
════════════════════════════════════════════════════════════════════════

  · 조합(통계검증) : M79(2026-08-12, 커밋 06842d88)로 **PG↔Oracle 이기종 개방**.
    단일 관문 services/stats_execute_service.execute_stats_validation 1곳 + 화이트리스트
    STATS_CROSS_DBMS_PAIRS + services/diagnosis/canonical_group_key/(base/pg/oracle) 어댑터.
    일괄검증도 무수정 자동 보호. mysql/mssql 은 canonicalizer 부재로 자동 미지원.
  · 행단위 :
      - exact_diff DIRECT(engine.py:247-253) : PG/Oracle **동일 방언 필수**, 다르면
        HOLD_UNSUPPORTED_DB("혼합 방언 비교는 후속 Phase").
      - chunk 경로 : 명시적 혼합방언 차단은 없으나 agg_diff_route.py:277 `_oa = _oa_src`
        주석이 "**동일 방언 가정** — 양측 tgt_col 명 공유" 라고 못박고 있다. 즉 PG↔Oracle
        혼합은 원본 방언의 alias 폴딩 규칙을 목적지에도 적용하는 미검증 영역이다.
      - services/exact_diff/dialects/ 에는 postgresql.py, oracle.py 2개뿐.
  · 비대칭의 의미 :
      검증 커버리지 = 조합 4방언 + 이기종 1쌍  ⊃  행단위 2방언 · 동일방언만.
      방향 B(행단위 기본)로 가면 MySQL·MSSQL 프로젝트와 이기종 프로젝트는 "기본 경로 자체가
      미지원 → 항상 대체경로" 가 되어 기본/예외가 뒤집힌다. M79 가 방금 넓힌 이기종 지원의
      수혜가 '기본이 아닌 경로'로 밀려나는 역행이 생긴다.
  · M79 자산의 재사용 가능성 : canonical_group_key 는 **GROUP BY 키(최대 3개)** 정규화용이다.
    행단위는 전 업무컬럼을 비교하므로, 이기종 행단위를 열려면 HASH_BUCKET 의 canonical hash
    계약 수준(전 컬럼 인코딩)의 작업이 새로 필요하다 — 그대로 재사용되지 않는다.
  · 겹치는 선결 결함(M90 역방향 갭) : 행단위는 `::text` 문자열 완전일치, 집계는 Decimal+1e-9
    허용오차. 동일 방언에서도 10.50 vs 10.5 가 거짓 불일치가 된다. 방향 B 는 이 결함을
    '기본 경로의 결함'으로 승격시키므로, 방향 B 착수 전 선해결 대상이다.

[방향 A] 조합 기본 + PK 있을 때 행단위 옵션
  실현가능성 : 높음. 사실상 **이미 구현돼 있는 것을 노출만 바꾸는 수준**이다 —
               '전체 그룹 한번에 추출'(scope 無 전체 행단위)이 이미 5단계에 있다.
  구현 규모   : 소. UI 1~2파일(ui/tabler_renderer.py 진입점 라벨·배치, 조건부 노출),
                서버 0~1파일. 엔진·토큰가드·방언·일괄검증 무변경.
  장점        : 워크플로/토큰/비용정책/이기종 커버리지를 하나도 안 건드린다.
                4방언·이기종 프로젝트에서도 기본 경로가 항상 성립한다.
  단점        : M90 이 확인한 "행단위가 상위집합" 을 기본값에 반영하지 못한다 —
                PK 있는 PG/Oracle 프로젝트에서 사용자가 옵션을 안 켜면 검출력 손실이 남는다.
  잔여 리스크 : 옵션이 '켜면 비싸다'는 성격이라 안내 문구·규모 경고가 없으면 대규모에서
                예상 외 지연을 사용자가 그대로 맞는다(현행 deferred 안내 재활용 필요).

[방향 B] 행단위 기본 + PK 없을 때만 조합
  실현가능성 : 엔진 측은 이미 가능(§2). **막는 건 엔진이 아니라 워크플로·정책·커버리지**다.
  구현 규모   : 대. 최소 아래 7덩어리.
                (i)   workflow_stage_gate.INDIVIDUAL_STAGES + workflow_stage_guard.ROUTE_STAGE
                      재정의(단계 추가) + 6-state 전이/테스트
                (ii)  routes/agg_diff_route.py 에 토큰 검증·in-flight 배선(현재 0)
                (iii) 1~5단계 화면 흐름·탭 라벨·단계힌트 재설계(ui/tabler_renderer.py 대규모)
                (iv)  fallback 분기 4종 신설 : PK 없음 / 비숫자 PK / MySQL·MSSQL / 이기종
                      → 각각 "조합으로 대체" 경로와 사유 표시
                (v)   일괄검증에 행단위 경로 신설(현재 batch 에 0건 — 신규 서비스 계층)
                (vi)  선결 : ::text 완전일치 vs Decimal 1e-9 수치비교 이원화(M90 역방향 갭)
                (vii) 선결 : _mvExecTerminal 공유 플래그, 자동준비 상한 1M 정책 반전
                파일 12~20개+, 난이도 높음. 되돌리기 어려운 구조 변경에 해당한다.
  장점        : PK 있는 PG/Oracle 프로젝트에서 기본값이 곧 최고 검출력이 된다(M90 정합).
  단점        : 4방언 중 2방언·이기종 프로젝트에서 기본 경로가 성립하지 않아 '예외가 다수'가
                되는 구조. 대규모에서 기본 지연이 규모 비례로 커진다.

[중간안(조사 중 발견 — 참고용, 선택지 확장)]
  엔진이 이미 '그룹 없이 전체 행단위'를 지원하므로, **워크플로 단계 구조를 전혀 바꾸지 않고**
  5단계 안에서 제시 순서만 뒤집는 방법이 있다(불일치 그룹 목록보다 '전체 상세비교'를 먼저,
  PK·방언·규모 조건 충족 시 자동 선택). 방향 B 의 사용자 체감 상당 부분을 방향 A 수준의
  비용으로 얻는다. 단 M90 의 "행단위가 상위집합" 을 판정 라벨에 반영하려면 결국 (vi)
  수치비교 이원화는 선결해야 한다.
