0. 한 줄 결론
═══════════════════════════════════════════════════════════════════════

일괄검증에는 '조합(COMBO)도 함께 검증' 옵션이 **어떤 형태로도 존재하지 않는다**.
include_pair 는 단일검증 화면의 클라이언트 JS 전용 배선이고, 일괄검증이 재사용하는
서버 facade 는 조합 세트를 만드는 코드 자체가 없다(kind="SINGLE" 하드코딩).

반면 **항목(테이블)별 개별 설정 구조는 이미 완비되어 있다** — 일괄검증은 row 단위
후보/계획 snapshot 을 DB에 저장하고, 실행 직전에 row 별 GROUP BY 를 실제로 읽어
주입한다. 따라서 "테이블마다 GROUP BY 개수가 달라서 못 한다"는 것은 사실이 아니고,
진짜 병목은 **facade 에 조합 실행 통로가 없다**는 점 하나다.

1. 조사 항목 1 — 일괄검증의 GROUP BY 선택은 어디서 결정되는가
═══════════════════════════════════════════════════════════════════════

결론: **업로드 엑셀이 아니라, 업로드 후 서버가 별도로 돌리는 '후보추천 → 계획생성'
단계에서 row 단위로 결정되어 SQLite 에 저장된다.**

── 1-1. 업로드 엑셀에는 GROUP BY 열이 없다 ──────────────────────────

BATCH_EXCEL_INPUT_SPEC.md §3.1 필수 컬럼 5종:
    validation_group_name / batch_name / query_id / target_table / migration_sql

BATCH_EXCEL_INPUT_SPEC.md §3.3 선택 컬럼 9종:
    source_name / target_where / owner / note / ddl_text /
    active_yn / priority / expected_row_count /
    connection_id_source / connection_id_target

→ GROUP BY 컬럼도, SUM 컬럼도, 조합 여부 플래그도 **없다**. 알 수 없는 헤더는
  item.extra_fields 로 보존되고 경고만 남는다(§3.4) — 즉 엑셀에 임의 열을 추가해도
  실행 로직에는 전달되지 않는다.

눌러 단계별로 진행하는 클라이언트 경로(_runExecutePlanSets)** 뿐이다.
→ "개별검증은 조합 가능"이라는 전제 자체가 경로 한정 조건부다. 기본값 ON 정책을

3. 조사 항목 3 — "기본값 ON" 정책을 적용할 방법이 있는가
═══════════════════════════════════════════════════════════════════════

── 3-1. 항목별 개별 설정 구조: **이미 있다** ──────────────────────

배경에서 우려한 "테이블마다 구조가 달라 개별검증 방식이 그대로 안 될 것" 이라는 가정은
저장 구조 측면에서는 성립하지 않는다. 근거:

  (a) 후보/계획 snapshot 이 모두 (group_id, row_id) 단위 — 항목별 독립 레코드
      policy_column_candidate_snapshot   UNIQUE(group_id, row_id, policy)
      policy_stats_validation_plan_snapshot UNIQUE(group_id, row_id, policy, plan_type)
  (b) row 단위 수정 API 가 이미 운영 중 — PATCH /api/column-candidate-snapshots/{id}/selection
  (c) 실행 route 가 row 단위로 plan 을 읽어 주입 — column_candidate_gen_route.py:477~481
  (d) plan_json TEXT 자유형 컬럼 존재 → **DDL 변경 없이** per-row 플래그 저장 가능
  (e) plan_type 이 이미 항목별로 다른 값을 갖는 선례
      (COUNT_ONLY / GLOBAL_COUNT_SUM / BASIC_GROUPED)

→ 부족한 것은 저장 구조가 아니라 **실행 통로(facade 의 조합 세트 생성)** 뿐이다.

── 3-2. 전역 일괄 vs 항목별 개별 — 의견 ────────────────────────────

권장: **2층 구조(전역 기본값 + 항목별 override)**. 단, 순수 전역 강제는 반대한다.

  순수 전역 방식의 문제
    · 대상 규모가 수백~수천 row(§5) → 조합 세트 1개씩 무조건 추가 = 대상 테이블
      전체 집계가 row 수만큼 추가된다. 비용을 사용자가 통제할 수단이 사라진다.
    · 개별검증에서 조합을 자동 ON 하지 않기로 한 원래 근거와 정면 충돌:
        ui/js_sql_preview.py:67~68
        "자동 ON 하지 않는 이유: 조합 세트 1개 = 대상 테이블 전체 집계 1회 추가이며,
         과세분화 가드는 예상 그룹 수만 보고 스캔 비용은 막지 못한다(진단 §4 비용 실측).
         비용은 사용자가 통제한다."
      일괄은 이 비용이 row 수만큼 곱해지므로, 개별보다 **더 보수적이어야** 정합적이다.
    · 3축 선택 row 에서는 조합 후보가 여러 쌍이 되어 어느 쌍을 고를지 판단이 필요하다
      (groupby_plan_service 는 max_pair_sets=1 로 1쌍만 채택하고 나머지는 제외 사유로 기록).

  권장 형태
    · 전역 기본값 : validation_policy_service 정책 JSON 에 키 1개
                    (batch_scheduler_config 가 같은 방식으로 정책에 얹혀 있음 — 선례 존재)
    · 항목별 override : plan_json 안에 per-row 플래그(스키마 변경 불필요)
    · 우선순위 : 항목별 override > 전역 기본값 (기존 effective_fill 우선순위 규약과 동형)
    · 기본값은 **OFF 유지**를 권장. 필요한 그룹만 켜는 opt-in 이 기존 비용 통제 철학과 일치.

── 3-3. 아키텍처 적합성 판단 ──────────────────────────────────────

  · 항목별 저장 : 기존 구조에 자연스럽게 맞음 (snapshot 이 이미 row 단위, plan_json 존재)

      docs/BATCH_VALIDATION_SPEED_IMPROVEMENT_DESIGN.md:92

      → 설계 문서가 상정하는 규모는 **수백~수천 건**.

  · 동시 실행 예산 (기본값)
      services/batch/wrapper_parallel_runner.py:49~58
        def default_parallel_budget_config() -> dict:
            """보수적 기본 병렬 예산 ... 전역 4 · 프로필당 3 · heavy 2."""

  · 조합 1세트 = 대상 테이블 전체 집계 1회 추가 (원본 + 목적지 양쪽)
      ui/js_sql_preview.py:84~85

  · 세트는 기본 순차 실행이다 — 세트 병렬은 기본 OFF
      services/single_validation_run_facade.py:420~421

── 5-3. 확인하지 못한 것 (정직한 한계) ────────────────────────────

  · **실제 등록 테이블 수의 운영 실적치는 코드·문서·과거 세션 기록에 없다.**

  · **2축 이상을 선택하는 row 의 비율 통계가 없다.** 조합 정책의 실제 비용은 이 비율에
    전적으로 좌우되는데, 이를 산출한 자료가 저장소에 존재하지 않는다.
    → 정책 결정 전에 실 그룹의 policy_stats_validation_plan_snapshot 을 집계해
      (selected_group_by_json 의 길이 분포) 확인하는 것을 선행 권장한다. 이 집계는
      DB 읽기만으로 가능하며 실행 비용이 없다.
  · 참고 규모 감각(다른 단계 수치, 통계검증 세트와 직접 비교 불가):

6. 정책 적용 방향 의견 (구현하지 않음 — 의견만)
═══════════════════════════════════════════════════════════════════════

■ 요청 요약
  개별검증의 '조합도 함께 검증' 기본값 ON 정책을 일괄검증에도 적용 가능한지 진단.

■ 긍정적 효과
  · 조합에서만 드러나는 불일치(축별 집계에서 상쇄되어 사라지는 차이)를 일괄에서도 포착.
  · F6(다중 GROUP BY 조합 판정 부재)가 일괄에서는 회피 수단조차 없는 현 상태가 해소된다.
  · 저장 구조가 이미 row 단위라 항목별 정책 표현에 스키마 변경이 필요 없다.

■ 구조적 문제점
  · facade 가 groupby_plan_service 를 쓰지 않고 세트 계획을 자체 구현(kind="SINGLE" 고정)한
    상태 — 세트 계획 로직이 사실상 2벌이다. 여기에 일괄용 3벌째를 만들면 안 된다
    (docs/PHASE_4_D8_BATCH_INDIVIDUAL_PARITY_PLAN.md §3 "일괄 전용 신설 금지").
  · 일괄 내부 두 실행 경로(run-wrapper=축별 분해 / stats-validation-plan=결합 1회)의
    축 처리 의미론이 이미 어긋나 있다. 조합 정책을 얹기 전에 이 불일치부터 정리해야 한다.
  · 파급 대상이 개별검증 완료 모듈(single_validation_run_facade.py)이다 — 승인 필요 구간.

■ 운영상 위험
  · 전역 무조건 ON 은 수백~수천 row × 전체 집계 1회 추가. 동시 실행 예산이 전역 4건이라
    큐 대기가 선형 증가하고, 세트 병렬은 기본 OFF라 가산분이 그대로 노출된다.
  · COUNT MAJOR 상태 조합 금지 가드가 **클라이언트에만** 있다. 일괄로 확장하면 서버측
    동일 가드 없이는 큰 COUNT 차이 상태에서도 조합이 실행된다(개별보다 안전성이 낮아짐).
  · 롤백성은 양호 — 정책 키 기본값 OFF 로 두면 즉시 원복 가능하다.

■ heuristic / scoring / explainability 영향
  · 신규 heuristic 은 불필요하다. 조건부 판단(그룹 수 상한·평균 행 수 하한·구분 효과 없음
    자동 제외·최대 1쌍)이 groupby_plan_service 에 이미 있고 제외 사유도 기록된다.
  · 오히려 facade 를 그 서비스로 통일하면 현재 없는 explainability(왜 조합을 넣었는지/
    왜 뺐는지)가 일괄에도 생긴다 — 하드코딩 증가가 아니라 감소 방향.
  · 반대로 route 에 `len(gb)==2` 같은 판정을 직접 넣으면 그것이 새 heuristic 하드코딩이
    되고 근거도 남지 않는다. 권장하지 않는다.

■ 권장 대응책 (순서)
  1) 선행 실측(무비용): 실 그룹의 selected_group_by_json 길이 분포를 집계해
     '2축 이상 row 비율'을 확인한다. 이 값 없이는 비용 논의가 추정에 머문다.
  2) 일괄 두 실행 경로의 축 처리 의미론 불일치를 먼저 정리(별도 과제).
  3) facade 가 build_groupby_execution_plan 을 호출하도록 통일 — 조합 통로 확보와
     세트 계획 이중화 해소를 동시에 달성. **완료 모듈 수정이므로 사용자 승인 필요.**
  4) 정책은 2층(전역 기본값 + plan_json per-row override), **기본값 OFF** 로 시작.
  5) 서버측 COUNT MAJOR 조합 금지 가드를 함께 추가.

■ 지금 구현 여부
  **보류** — 이번 지침이 진단 전용이며, 실행 통로 확보가 완료 모듈(facade) 수정을
  요구하고, 비용 판단에 필요한 '2축 이상 row 비율' 실측치가 아직 없다.
