2. 기록 위치별 부하 실측 (지시 2)
────────────────────────────────────────────────────────────────────────
[2-1] 기록 1회당 단위비용 (n=300 반복, 중앙값)

  (a) in-memory dict 갱신 (_pcb 본체 전체 — 12필드 + 분포 스냅샷)      0.600 us   p95 0.600 us
  (b) 디스크 write 현행방식 (connect+DDL+UPDATE+commit+close)          8.11 ms    p95 10.71 ms
  (b-2) 디스크 write (connection 재사용, UPDATE+commit 만)             1.39 ms    p95  1.57 ms
  (c) exact_diff_runs.db 에 progress 컬럼 갱신 (UPDATE+commit)         8.19 ms    p95  9.52 ms
  (d) 행 루프 내 throttle no-op 1회                                    136 ns

  → 메모리 대비 디스크 = 약 13,650배 (8.19ms ÷ 0.600us). 예상대로 메모리는 사실상 0.
  → 현행 디스크 write 8.11ms 중 6.7ms 는 _conn() 이 매 호출마다 하는 부대작업이다
    (chunk_checkpoint.py:62-74 — connect + CREATE TABLE IF NOT EXISTS + ALTER TABLE 3회 + PRAGMA).
    순수 UPDATE+commit 은 1.39ms. 디스크가 비싼 게 아니라 연결 방식이 비싸다.

[2-2] 엔진 A/B — 250,000행 · 불일치율 0.8% · 5청크 · 3회 중앙

  A 계측 전무                7.743 s    —          progress_cb 0회   checkpoint 0회
  B 메모리만                 7.995 s    +3.26%     progress_cb 7회   checkpoint 5회
  C 메모리 + 디스크           7.666 s    -1.00%     progress_cb 7회   checkpoint 5회

  디스크를 켠 C 가 A 보다 빨랐다 → 세 조건의 차이가 측정 노이즈 이내.
  교차 반복 검증(불일치율 50% · 5회 교차)에서도 계측 ON 이 -2.37% 로 나와,
  초기 관측된 +9.96% 는 노이즈로 확정했다.

[2-3] 청크 주기 대비 비율 (핵심 답)

  청크 주기 74 s   (CTE/JOIN push-down 실패)  → 디스크 write 1회 비중 0.011 %
  청크 주기 4.33 s (1M PG 표준, 라이브 실측)   → 0.19 %
  청크 주기 0.21 s (5,000행 소형)             → 3.9 %

  1,000,000행 검증 1건 전체: 20청크 × 8.19ms = 0.164초 / 전체 86초 = 0.19 %

  → 청크 단위라면 디스크 write 도 무시할 수 있다. 느린 케이스일수록 비중이 더 작아진다.
    유일하게 눈에 띄는 3.9% 구간은 소형 테이블이고 절대값이 8ms 라 실사용 영향 없음.

3. 재시작 내구성과의 trade-off (지시 3)
────────────────────────────────────────────────────────────────────────
[3-1] 지금 상태
  reimport_job._JOBS_BY_FP / _JOBS_BY_RUN   in-memory   재시작 시 소실
  reimport_job._RUN_TIME (실행시간)          in-memory   재시작 시 소실
  db/chunk_checkpoints.db                   디스크       보존 (청크 경계마다 write 중)
  db/exact_diff_runs.db                     디스크       보존

[3-2] 이미 디스크에 진행률이 있다 — 중요한 발견
  chunk_checkpoint 테이블은 청크마다 다음을 이미 저장하고 있다
  (pk_range_chunk.py:365-373 → agg_diff_route.py:314 → chunk_checkpoint.py:135-152):
      chunks_done, processed_src, processed_tgt, missing, value_cnt, target_only,
      last_completed_end, last_completed_pk, heartbeat, updated_at

  진행률 대시보드가 필요로 하는 '어디까지 왔는지'는 PK_RANGE_CHUNK 경로에 한해
  이미 디스크에 영속화되어 있다. 새 write 를 추가할 필요가 없고 따라서 추가 오버헤드 0 으로
  재시작 후 복구가 가능하다.
  (한계: fingerprint PK 라 run 당 1행이며, STREAM 엔진에는 checkpoint 자체가 없다)

[3-3] 비용 대 가치 (수치)
  메모리만    비용 0.6us/회(≈0)   | 재시작 시 진행률 소실. job 도 함께 소실 → 화면상 '사라진 검증'
  디스크추가  비용 0.164초/1M검증 | 마지막 완료 청크부터 재개 → 최대 청크 1개분만 손실
              (전체의 0.19%)

  재실행을 피해서 지키는 시간:
    1M 단순        재실행 약 1.7분    vs 기록 0.164s  → 약 620배
    1M CTE/JOIN    재실행 약 24.8분   vs 기록 0.164s  → 약 9,000배
    5M CTE/JOIN    재실행 약 2.1시간  vs 기록 0.8s    → 약 9,400배

  결론: trade-off 라고 부를 균형점이 아니다. 디스크 기록 비용은 보호 가치의 만분의 일 수준이고,
        게다가 PK_RANGE_CHUNK 경로는 이미 그 write 를 하고 있다. 논점은 '디스크에 쓸 것인가'가
        아니라 '이미 쓰고 있는 것을 대시보드가 읽을 것인가'다.

[4-3] #4 tracemalloc — 오늘 실측한 처리시간에 이미 포함된 비용  ← 지시 4 의 핵심 답
  두 엔진 모두 실행 전 구간 tracemalloc 을 켠다. 얻는 것은 metrics.peak_python_mb 값 하나다.
  행 단위보다 촘촘한 '할당 단위' 계측이 상시 ON 인 셈이다.

  250,000행 · 5회 교차 실행:
      tracemalloc OFF  1.052 s (중앙)
      tracemalloc ON   7.585 s (중앙)  ← 현행
      Δ +6.533 s (+620.7%)

  read 대기를 주입해 read-지배 환경을 재현한 결과가 결정적:
      chunk조회 대기   TM OFF     TM ON      Δ          증가율    read비중
      0 s             1.279s    10.732s   +9.453s     739%      0%
      0.5s ×2측       6.337s    16.069s   +9.732s     154%     31%
      2.0s ×2측      21.350s    31.007s   +9.657s      45%     65%
      4.0s ×2측      41.407s    51.838s  +10.431s      25%     77%

  → tracemalloc 의 절대 비용은 대기 시간과 무관하게 일정하다(250,000행당 +9.5~10.4초).
    read 가 길어지면 비율만 희석될 뿐 비용은 그대로 남는다. 합성 행 구조 기준 행 객체당 약 19us.

  [해석의 한계 — 정직 고지]
  라이브 행은 11컬럼이라 할당량이 더 많지만, DB read 시간에는 네트워크 대기와 드라이버 C 레벨
  처리가 섞여 있어 파이썬 할당 비중이 합성과 다르다. '1M 라이브 run 에서 정확히 몇 초'인지는
  라이브 실측 없이 확정할 수 없다. 확정된 것은 둘이다 —
    (1) 절대 비용은 대기로 희석되지 않는다
    (2) 순수 CPU 구간(compare_seconds 3.21초 등)은 전부 이 배율의 영향을 받고 있다
  하한만 잡아도 1M run 의 compare 구간에서 약 2.7초(전체의 3%)이고, read 구간의 행 객체
  생성분까지 포함하면 그보다 커진다.

  즉 지시 4 의 질문('이미 성능에 영향을 주고 있는가')에 대한 답은 예다.
  다만 그 주범은 행 단위 로깅이 아니라 상시 tracemalloc 이다.

5. 권장안 (지시 5)
────────────────────────────────────────────────────────────────────────
[5-1] 권장 기록 방식 — 청크 단위 + 메모리 우선, 디스크는 신규 write 추가 없음

  메모리 진행률    기존 _pcb 경로에 last_progress_at 필드 추가
                  근거: 갱신 1회 0.6us. 청크당 1~수회 → 실질 0
  디스크 진행률    chunk_checkpoint 테이블을 대시보드가 읽는다. 새 write 없음
                  근거: 이미 청크마다 write 중 → 추가 비용 0
  flush 주기       1 청크마다 유지(현행). N청크 배치 flush 불필요
                  근거: 1청크마다도 청크주기의 0.19%. N=10 으로 줄여도 0.019% 라
                        절감폭이 측정 노이즈보다 작다. 반면 배치화는 '마지막 flush 이후
                        진행분 손실'이라는 새 실패 모드를 만든다. 단순한 쪽이 낫다
  행 단위 기록     금지(메모리 포함)
                  근거: 디스크 250k=34분. 메모리는 무해하나 청크 단위로 동일 정보 획득 가능

  ※ 지시문이 제시한 'N청크마다 1회 배치 flush' 는 실측 결과 불필요하다.
  ※ 예외 규칙 하나만: 청크 주기가 1초 미만인 소형 검증은 write 비중이 3.9% 까지 오른다.
    chunks_total <= 2 이거나 관측 청크주기 1초 미만이면 중간 flush 생략하고 종료 시 1회만
    쓰는 편이 낫다(절대 절감은 수십 ms 라 선택 사항).

[5-2] 신규 계측보다 먼저 해야 할 것 — 우선순위 역전 경고
  신규 진행률 기록의 전체 예산은 1M 검증 1건당 0.164초다. 그런데 같은 실행에서
  tracemalloc 이 이미 그보다 최소 16배 이상(compare 구간 하한 2.7초 기준)을 쓰고 있고,
  chunk_checkpoint._conn() 의 매회 DDL 재실행이 write 비용의 82%(8.11ms 중 6.7ms)를 차지한다.

  권장 순서:
    1) tracemalloc 상시 ON 재검토 — peak_python_mb 값 1개의 대가로 지불 중.
       전역 설정 토글(기본 OFF) 또는 첫 청크만 샘플링으로 전환. 효과 추정: 순수 CPU 구간 약 7배
    2) chunk_checkpoint._conn() connection 재사용 — 8.11ms → 1.39ms (83% 절감).
       매 호출 CREATE TABLE IF NOT EXISTS + ALTER TABLE 3회 시도 제거
    3) 그 다음에 진행률 기록 추가 (5-1)

[5-3] 함께 보고할 위험 (비판적 검토)
  - STREAM 엔진에는 checkpoint 가 없다. 복합 PK 테이블은 항상 STREAM 이므로
    (strategy_transition.py:58) 디스크 진행률·재시작 복구가 원천적으로 불가하다.
    대시보드가 '청크 진행률'을 전제로 설계되면 복합 PK 대형 테이블에서 진행률이 통째로 비게 된다.
    이번 진단 범위 밖(별건)이지만 대시보드 설계 전에 반드시 결정해야 한다.
  - 측정 근거 없이 신규 계측을 늘리는 것은 execution_settings 의 죽은 설정 6개
    (병행 진단에서 사용처 0곳 확인)와 같은 실패를 반복할 위험이 있다.
    설정 추가 시 소비처 배선과 배선 단위테스트를 같은 작업에 포함해야 한다.
