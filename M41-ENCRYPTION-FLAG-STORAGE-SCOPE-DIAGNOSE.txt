작업명 : M41-ENCRYPTION-FLAG-STORAGE-SCOPE-DIAGNOSE
✅ 작업 완료 - 암호화여부 필드 저장 여부 전수 확인 + 거짓불일치 재현 + 저장 옵션 비교 + 권장안 제시(코드 변경 없음)

■ 0. BACKLOG.md M41 원문 요약
  나이스/에듀파인 컬럼매핑정의서(엑셀)의 '암호화여부' 필드가 저장소(파일/테이블) 어디에도
  영속화되지 않아, 재검증 시 정의서를 다시 안 실으면 암호화 컬럼 제외가 "조용히 풀린다"는 의심
  (발견일 2026-08-05, F1-G7-HASH-BUCKET-ORACLE-SCOPE-DIAGNOSE 조사 중 부수 발견, 미진단 상태).

■ 1. 조사 결과 — 전수 확인(정의서 업로드/파싱 경로부터 추적)

  1-1. 정책 로직 자체는 완비돼 있다.
    services/analysis/encrypted_column_policy.py 에 로더(load_encrypted_columns_from_definition),
    parse_result 부착기(attach_encrypted_columns / attach_encrypted_columns_from_request),
    생산자(resolve_encrypted_columns)가 모두 구현돼 있고, 소비 측(exact_diff/engine.py,
    routes/agg_diff_route.py::_derive_row_compare_cols, candidate_engine.py 후보 원천배제)도
    정상 배선돼 있다 — "명시필드만, 자동탐지 없음, 미지정=안전기본값 False" 원칙 그대로.

  1-2. 그러나 이 정보를 담아 서버로 보내는 입구(request 스키마)가 존재하지 않는다.
    attach_encrypted_columns_from_request(parse_result, req) 는
    getattr(req, "encrypted_columns", None) / getattr(req, "column_mapping", None) 로 값을
    읽는데, 실제 호출부는 services/single_validation_analyze_service.py:1451
    run_single_validation_analyze(req: AnalyzeRequest) — req 타입이 schemas/request_models.py
    의 AnalyzeRequest(Pydantic v2 BaseModel) 다. 이 클래스(및 이를 상속하는
    SingleRunStandardRequest, /single/run-standard 요청 바디)에는 column_mapping /
    encrypted_columns 필드가 **정의돼 있지 않다**. model_config 오버라이드도 없어 기본값
    extra='ignore' 가 적용된다.

  1-3. UI 에도 입력 위젯이 없다.
    ui/tabler_renderer.py 전체에서 '암호화여부'/'정의서' 관련 문구는 딱 한 곳
    (라인 3136 근처) — "매핑정의서 '암호화여부' 명시 컬럼은 값 검증에서 제외되고 사유가
    결과에 표시됩니다" 라는 **정적 안내 텍스트**뿐이다. 파일 업로드 input, textarea,
    JS fetch 페이로드에 column_mapping/encrypted_columns 를 실어보내는 코드는 전무하다.
    라인 16772 근처는 서버가 이미 계산해 돌려준 encrypted_excluded_columns 를 "표시"만 한다.

  1-4. 유일하게 이 값이 채워지는 경로는 production 진입점이 아니다.
    - tests/test_encrypted_column_exclusion.py 는 SimpleNamespace(column_mapping=...) 로
      req 를 흉내내 함수를 직접 단위테스트한다(Pydantic 모델이 아님 → 필드 부재 문제가
      테스트에서는 가려짐).
    - scripts/dev_e2e/encrypted_col_browser_shot.py 는 브라우저 JS state 에
      parse_result.encrypted_columns 를 **직접 주입**해 화면 렌더링만 검증한다
      (analyze 요청 경로를 거치지 않음).
    실사용 흐름(/analyze, /single/run-standard HTTP 호출)으로는 어떤 경로로도
    이 값이 parse_result 에 도달할 수 없다.

  결론: BACKLOG 서술("정의서 로드를 빠뜨리면 조용히 풀린다")은 실제보다 상황을 낙관적으로
  본 것이다. "가끔 깜빡하면 위험"이 아니라, **현재 시스템에는 이 필드를 실어보낼 방법 자체가
  없다** — 정책 로직·소비 로직은 완성돼 있으나 입력 경로(요청 스키마 필드 + UI 위젯)가
  통째로 미배선인 상태다. 저장(persist) 여부를 논하기 이전에 애초에 매 요청마다 100%
  비어있다(자체 진단 문서에 나온 "잊으면 풀리는 휘발성"이 아니라 "지금은 켜진 적이 없는
  상시 OFF" 상태).

■ 2. 재현 결과

  2-1. 스키마 드롭 실측 (코드 변경 없이 실행, 결과만 관찰)
    AnalyzeRequest(sql=..., column_mapping={...}, encrypted_columns=["RRN"]) 로 인스턴스를
    만든 뒤 확인:
      hasattr(req, "column_mapping")     → False
      hasattr(req, "encrypted_columns")  → False
      req.model_dump().keys() 에 두 필드 모두 없음
      getattr(req, "column_mapping", <MISSING>) → <MISSING> 그대로 반환
    → attach_encrypted_columns_from_request 내부에서 이 두 getattr 이 항상 None 을 받으므로
      함수는 매번 조용히 no-op 된다(예외도 안 남는다 — 사유 로그 없음).

  2-2. 거짓불일치 재현 (기존 회귀 테스트로 확인, 신규 코드 작성 없이 실행만)
    python -m pytest tests/test_encrypted_column_exclusion.py -q → 16 passed
    - test_before_exclusion_encrypted_col_causes_false_mismatch:
      같은 PK·같은 평문 AMT/NOTE, GRADE(암호화 컬럼)만 원본/목적 암호문이 다른 30건 데이터셋을
      encrypted_cols 지정 없이 비교 → value_different == 30건 전부(거짓 불일치), is_matched=False.
      이것이 오늘 실제 /analyze 흐름이 항상 만드는 상태와 동일하다(1-4 결론에 따라
      encrypted_cols 는 실사용 경로에서 항상 빈 값이므로).
    - test_after_exclusion_encrypted_col_resolves_to_match:
      동일 데이터셋을 encrypted_cols=["GRADE"] 로 명시하면 value_different==0, is_matched=True,
      제외 사유(ENCRYPTED_REASON_CODE)까지 노출.
    → 정책이 "꺼져있을 때"와 "켜져있을 때"의 대조가 재현 가능함을 확인했고, 오늘 운영 경로는
      영구히 "꺼져있는 쪽"에 고정돼 있다.

■ 3. 저장 방식 옵션 비교

  (a) 신규 테이블 column_semantic_meta (가칭)
    스키마 변경 범위 : 신규 테이블 1개. db/schema.sql 중앙 정의 대신, 최근 추가된
      admin_column_override / source_owner_binding 패턴(모듈 자체 ensure_schema, 같은
      db/migration_validator.db 재사용)을 그대로 답습 가능 — 중앙 schema.sql 을 건드리지
      않아도 됨.
      권장 키 축(admin_column_override_store.py 의 기존 검증된 축과 동일 사상):
        UNIQUE(project_id, table_key, column_name) — "프로젝트 × 테이블 × 컬럼" 축.
        admin_column_override 가 이미 "REG_DT 가 A테이블은 배치스탬프, B테이블은
        업무일자일 수 있다"는 이유로 이 축을 채택했고(§1-3 근거), 암호화여부도 동일하게
        같은 컬럼명이 테이블마다 다른 값일 수 있다(정의서가 테이블 단위로 작성되므로).
    기존 코드 영향면 : encrypted_column_policy.py 는 이미 "생산자→소비자" 인터페이스
      (resolve_encrypted_columns 가 parse_result 를 읽음)로 분리돼 있어, 신규 테이블은
      "요청에 없으면 저장소에서 project_id+table_key 로 조회해 parse_result 에 병합"하는
      새 함수 하나만 추가하면 된다. 기존 함수 시그니처 변경 불필요.
    마이그레이션 필요 여부 : 없음(신규 테이블, 기존 데이터 없음. CREATE TABLE IF NOT EXISTS
      멱등 — M42 idempotent guard 패턴 그대로 재사용 가능).
    단점 : 새 저장소 모듈 하나가 늘어난다(구조 비대화 우려는 있으나 admin_column_override 와
      거의 동형이라 패턴 재사용 비용은 낮음).

  (b) M39 semantic_dictionary_entry 확장(risk_flags_json 재사용)
    스키마 변경 범위 : 0(컬럼 추가 불필요, 기존 risk_flags_json 에 "ENCRYPTED" 태그를 얹는
      방식이라 얼핏 매력적).
    치명적 불일치 — 키 축이 근본적으로 다르다:
      semantic_dictionary_entry 는 (dictionary_id, term) 단위의 **전역/사전 term 사전**이다.
      services/semantic_dictionary_service.py::match_semantic_dictionary 는 컬럼명을 토큰화해
      EXACT/TOKEN/COMMENT/STANDARD_TERM 같은 **퍼지 매칭**으로 term 사전과 대조하는 구조이며,
      project_id 는 NULL(전역) 아니면 override 용도이지 **table_key 축 자체가 없다**.
      즉 "RRN" 이라는 term 이 한 번 risk_flags_json 에 ENCRYPTED 로 박히면, 그 term 과
      매칭되는 **모든 프로젝트·모든 테이블**의 RRN 계열 컬럼에 전부 적용돼 버린다.
      그런데 M41 이 다루는 정보는 "이번 이관 정의서에 명시된 이 테이블의 이 컬럼"이라는
      **결정적(deterministic) 사실**이지, "RRN 이라는 이름이면 대개 암호화됐을 것"이라는
      **추정(heuristic)** 이 아니다. 같은 기관 안에서도 시스템별로 암호화 적용 여부가 다를 수
      있어(정의서가 시스템/이관 건별로 별도 작성됨), 전역 term 사전에 얹으면
      "이번 이관에서는 암호화 안 했는데 예전 다른 이관 정의서에서 ENCRYPTED 로 박아놨던 term"
      때문에 엉뚱한 컬럼이 조용히 검증 대상에서 빠지는 **새로운 종류의 조용한 오탐**(과다제외)
      을 만든다 — 지금 문제(과소제외/거짓불일치)를 고치려다 반대 방향 결함(과다제외/거짓매칭)
      을 심는 셈이다.
    기존 코드 영향면 : match_semantic_dictionary 소비자(컬럼 시맨틱 분류/후보 스코어링)가
      risk_flags 를 "정보성 참고 태그"로만 다루는데, 이를 "값검증 자동제외 게이트"로도
      쓰려면 소비자 코드 자체를 분기해야 해 결합도가 오히려 올라간다(CLAUDE.md 비판적 검토
      의무 항목 중 "heuristic 하드코딩 증가" 위험에 해당).
    마이그레이션 필요 여부 : 스키마상은 불필요하지만, 실제로는 "term 사전 확장"이 아니라
      "다른 성격의 데이터를 같은 컬럼에 억지로 얹는" 재해석이라 개념적 부채가 더 크다.

■ 4. 권장안 + 근거

  권장 : (a) 신규 테이블(admin_column_override 와 동형 패턴) 채택. semantic_dictionary_entry
  확장(b)은 기각.
  근거 : ①키 축 불일치가 근본적(전역 term 사전 vs 프로젝트×테이블×컬럼 결정적 사실) —
  이는 스키마 컬럼 추가로 메워지지 않는 구조적 문제다. ②(a)는 이미 검증된 저장소 패턴
  (admin_column_override_store.py)을 그대로 재사용할 수 있어 신규 설계 위험이 낮다.
  ③(b)는 지금 없는 "거짓 불일치"를 고치려다 "거짓 매칭(과다제외)"이라는 다른 조용한 오탐
  계열을 새로 만들 위험이 있다 — CLAUDE.md 비판적 검토 의무의 "heuristic 하드코딩 증가" /
  "explainability 누락"에 정면으로 걸린다.

  단, (a) 채택만으로는 M41 이 완전히 해소되지 않는다는 점을 분명히 알린다: 1절에서 확인한
  대로 **입력 경로(요청 스키마 필드 + UI 업로드 위젯) 자체가 없다.** 저장 테이블을 만들어도
  거기에 값을 채워 넣을 방법이 없으면 여전히 상시 OFF 다. 즉 M41 실제 해결에는 최소
  (1)저장 테이블, (2)정의서 업로드/입력 UI, (3)AnalyzeRequest 스키마 필드 추가 및
  attach_encrypted_columns_from_request 배선 확장(요청 없으면 저장소 폴백 조회) 세 가지가
  함께 필요하다. 이 세 가지는 이번 진단 범위 밖이며 별도 착수 승인이 필요하다.
