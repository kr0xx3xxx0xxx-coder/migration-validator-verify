1-4. 추가 발견 — A1은 적용해도 지침의 목적(실효수용량 위험 노출)을 달성하지 못한다

_applyCsrBadges(:26346~26430)가 만드는 배지의 **눈에 보이는 텍스트**는
selection_status 라벨 + 점수뿐이다(:26358~26364, :26403).

compatibility_status 와 risk_flags 는 **마우스 hover 시 title 툴팁**에만 들어가고,
risk_flags 는 앞 2개만 잘라서 표시한다(:26394~26395). 붉은 강조(cs-csr-critical)는
critical_fail_flags 가 있을 때만 붙는다(:26401).

실효수용량 위험 컬럼(VARCHAR2, char_used='B', 목적지 실효 수용량 축소)의 실제 값은
    compatibility_status = PRECISION_LOSS_RISK, risk_gate_blocked = False
    risk_flags = [CHAR_CAPACITY_SHRINK_RISK, PRECISION_LOSS_RISK]   (runner:459~463)
이고, 이는 critical_fail 이 아니며 3번 게이트도 통과한다. 따라서 배지를 되살려도
    · GROUP BY 축 배지 표시 = '추천'(파란색) ← 조용한 절단 위험이 있는 컬럼에 '추천'이 붙음
    · SUM 축 배지 표시     = '해당없음'(문자형이므로 :497에서 즉시 NOT_APPLICABLE)
    · 위험 문구는 hover 툴팁 안에서만, 그것도 다른 항목들과 섞여 노출
→ "위험을 사용자 화면에 노출"이라는 목적 대비 효과가 거의 없고, 오히려 위험 컬럼에
  '추천' 라벨을 새로 붙이는 역효과가 난다. 이 점만으로도 A1 을 그대로 되살리는 것은
  부적절하다.

3-2. 이 조건이 설계 의도임을 보이는 3중 일치
--------------------------------------------------------------------------------
[일치1] 상수 집합이 애초에 PRECISION_LOSS_RISK 를 제외하고 정의돼 있다.
  candidate_scoring_runner.py:56~61
    # risk_gate_blocked = True인 compatibility_status
    RISK_GATE_BLOCKED_STATUSES = {
        "CAST_REQUIRED", "SCALE_MISMATCH", "DATE_FORMAT_TRANSFORM_REQUIRED",
        "NORMALIZATION_RULE_REQUIRED", "MANUAL_REQUIRED", "UNKNOWN_COMPATIBILITY",
        "TYPE_MISMATCH",
    }
  → PRECISION_LOSS_RISK 와 COMPATIBLE 은 처음부터 차단 대상이 아니다. 즉 :697 조건문의
    `not in ("COMPATIBLE","PRECISION_LOSS_RISK")` 부분은 구조상 **중복 방어**이고,
    같은 정책을 두 곳에 이중으로 못박은 형태다(우연한 누락과 정반대 형태).

[일치2] 설계 문서가 표로 명시한다 — "False (경고)".
  docs/CANDIDATE_SCORING_RUNNER_DESIGN.md §9.2 compatibility_status 후보 정의(원문 표)
    | compatibility_status | 의미                              | risk_gate_blocked | 예시 |
    | PRECISION_LOSS_RISK  | 정밀도 축소로 SUM 결과값 차이 발생 가능 | **False (경고)**  | NUMERIC(15,2)→NUMERIC(10,2) |
  같은 표의 다른 7개 상태는 모두 True 로 적혀 있다. 즉 "경고이되 차단은 아님"이 문서화된
  단일 예외로 설계돼 있다.

[일치3] GROUP BY 기본선택 금지 조건 목록에 애초에 없다.
  docs/CANDIDATE_SCORING_RUNNER_DESIGN.md §8.5 "GROUP BY 기본 선택 금지 조건" 표의 8개 조건
  (is_pk / is_unique / n_distinct / 고카디널리티 / IDENTIFIER / SORT_ORDER / CONSTANT /
   datetime / stats+semantic 부재) 중 compatibility 계열 위험은 TYPE_MISMATCH 만 별도
  처리(:686~689)되고 PRECISION_LOSS_RISK 는 목록에 존재하지 않는다.

3-3. 위험이 다른 축에서 처리되고 있다는 방증
--------------------------------------------------------------------------------
PRECISION_LOSS_RISK 를 "그냥 통과시키고 끝"이 아니라, SUM 축에서는 별도 Critical FAIL
규칙으로 잡는다.
  candidate_scoring_runner.py:895~897
    # CF-SUM-03: PRECISION_LOSS_RISK → SUM SELECTED_DEFAULT
    if "PRECISION_LOSS_RISK" in rflags and sum_ss == "SELECTED_DEFAULT":
        fails.append("CF-SUM-03")
→ 즉 "정밀도 손실 위험이 있는데 SUM 자동선정까지 됐다면 그건 Critical"이라는 별도 안전망이
  설계돼 있다. 게이트를 통과시키는 것이 위험 무시가 아니라, 축별로 다른 장치를 둔 설계다.
