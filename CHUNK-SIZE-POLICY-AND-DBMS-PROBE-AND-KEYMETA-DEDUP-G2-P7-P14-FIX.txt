1. [파트 A / G2] 청크 크기 min/max 상한이 사장돼 있다

1-1. 위치 확인 결과
────────────────────────────────────────────────────────────────────────
선언 (소비처 0건 확인):
  services/exact_diff/execution_settings.py:29-31
      default_chunk_size = 50000 / min_chunk_size = 10000 / max_chunk_size = 200000

청크 크기가 '결정'되는 지점은 코드 전체에서 2곳이었다:
  ① services/strategy/strategy_transition.py `_out()`        → 계획·전환판정 출력 selected_chunk_size
       (호출부: routes/strategy_route.py:65 실행계획 카드, routes/agg_diff_route.py:63 실행 전략 확정)
  ② routes/agg_diff_route.py:164 `_pk_range_chunk_size(req)` → **엔진 입력 단일 지점**
       우선순위: 요청 파라미터 req.chunk_size > 정책 override(strategy_resource_weights.pk_range_chunk_size)
                > 코드 기본 50000
엔진 `services/exact_diff/pk_range_chunk.py:248` 의 `max(1, int(chunk_size))` 는
**동시 진행 지침의 대상 파일이라 미접촉**(지침 지시대로). 위 ②에서 강제하면 엔진에 도달하기 전에 걸린다.

1-2. 판단 — '제거'가 아니라 '연결'
────────────────────────────────────────────────────────────────────────
죽은 코드로 제거하지 않고 연결하는 쪽을 택했다. 근거:
  · 청크 크기는 이미 **외부에서 3경로로 주입 가능**하다(요청 파라미터 / 정책 override / 전환판정 config).
    강제 지점이 없다는 것은 '상한이 안 쓰인다'가 아니라 '상한이 없다'는 뜻이다.
  · 상수를 지우면 상·하한이라는 정책 개념 자체가 사라져, 청크 1(=고정비 폭증) / 10,000,000(=메모리·재개
    단위 붕괴)을 막을 근거가 코드에서 없어진다.
  · 연결 비용이 작다 — 새 정책 판단을 만들지 않고 기존 선언값을 강제하기만 한다.

────────────────────────────────────────────────────────────────────────

2-2. 근본원인 실측 — '순차 누적'이 아니라 '드라이버가 타임아웃을 안 지킨다'
────────────────────────────────────────────────────────────────────────
실 PostgreSQL 엔드포인트(192.168.0.150:5433)에 timeout=5 로 드라이버별 개별 probe:

    postgresql       71.2 ms   ← 서버 인증 거부(=서버가 응답, DBMS 확정)
    oracle            0.6 ms   ← cx_Oracle 미설치(즉시)
    mysql        60,071.3 ms   ★ 지연 전량
    mssql             2.9 ms   ← pyodbc 미설치(즉시)

  pymysql 단독 대조:
    connect_timeout=5 만                          → 60,026.7 ms
    connect_timeout+read_timeout+write_timeout=5  →  5,020.0 ms
  즉 `connect_timeout` 은 **TCP 연결까지만** 덮는다. 상대가 MySQL 이 아니면 핸드셰이크 응답이 오지 않아
  **읽기에서 60초 블로킹**된다. 순차 누적은 그 위에 얹힌 2차 요인이었다.

2-3. 수정 3종
────────────────────────────────────────────────────────────────────────
  ① 드라이버 타임아웃 실전파 (근본원인)
       mysql : `read_timeout` / `write_timeout` 추가 (`_connect_and_fetch_version`, `_test_mariadb` 양쪽)
       mssql : 연결문자열에 `Connection Timeout=` 추가 — pyodbc 의 connect(timeout=) 은 '쿼리' 타임아웃이라
               로그인 단계를 덮지 못한다 (pyodbc 미설치 환경이라 코드 리뷰 근거만, 실측 불가)
  ② 서버 식별 시 fallback 생략 (`SERVER_IDENTIFIED_SKIP`)
       selected 드라이버가 **서버가 응답한 에러**로 실패하면 그 엔드포인트의 DBMS 는 이미 확정이므로
       나머지 드라이버 probe 를 하지 않는다. 판정은 `_server_identified_dbms()` 한 곳:
         postgresql : psycopg2 pgcode/diag.sqlstate, 없으면 libpq 심각도 표기(FATAL:/ERROR:/PANIC:)
                      — 실측상 psycopg2 는 **접속 단계** 실패에 pgcode 를 채우지 않는다(둘 다 None).
                        이 표기는 libpq 가 서버 ErrorResponse 패킷을 해석했을 때만 붙는 프로토콜 증거다.
         mysql      : 서버 에러번호(1000~1999). 클라이언트측 2000번대(2003 접속불가 등)는 제외
         oracle     : ORA-nnnnn 코드. 리스너/네트워크 단계 코드(12154/12514/12541/12545/12560/3113/3114) 제외
         mssql      : SQLSTATE 28xxx(인증)·42xxx(권한) 만. 08xxx(연결실패) 제외
       근거가 없으면 False → 종전처럼 fallback 을 돈다(감지 기회를 잃지 않는 쪽으로 보수 판정).
  ③ 남은 드라이버 병렬 시도 (`PARALLEL_FALLBACK`, 기본 ON · kill-switch `MV_DBMS_PROBE_PARALLEL=0`)
       selected 는 **단독으로 먼저** 시도한다 → 성공 경로는 예전 그대로 1회 접속으로 끝난다
       (성공하는 실 DB 에 투기적 접속을 추가로 던지지 않기 위한 의도적 설계).
       성공 선택은 완료 순서가 아니라 항상 `_DBMS_PROBE_ORDER` 우선순위 — 병렬이 결과를 바꾸지 못한다.

  진단 필드 추가(표시 전용, 판정 미사용): `DetectedDbmsInfo.probe_mode` / `probe_attempt_count`
    SELECTED_OK / SELECTED_ONLY / SERVER_IDENTIFIED_SKIP / PARALLEL_FALLBACK / SEQUENTIAL_FALLBACK

3-2. '단순 통합이 안전한가' 판단 — 안전하지 않다. 그래서 값이 아니라 결과를 캐시했다
────────────────────────────────────────────────────────────────────────
두 호출부의 **실패 처리 의미가 실제로 다르다**(백로그 지적 확인됨):
  · `_cmn_fetch_tgt_col_meta` : 조회 실패 → 컬럼 메타 **전체를 포기하지 않는다.** is_pk 를 전부 False 로
    두고 진행한다(PK 정보만 없을 뿐 메타는 유효).
  · `_build_target_pk_evidence`: 조회 실패 → **근거 부재**로 귀결돼야 한다.
    available=False + reason 을 남겨 소비측(3단계 실행계획 카드)이 낙관적으로 'PK 있음'을 단정하지 않게 한다.
    나아가 이 호출부는 **'조회 실패'(KEY_METADATA_LOOKUP_FAILED)와 '조회는 됐으나 키 없음'
    (KEY_METADATA_UNAVAILABLE)을 구분**한다 — 한쪽 의미로 뭉치면 이 구분이 깨진다.

따라서 "한쪽이 다른 쪽 결과를 재사용" 하는 단순 통합은 하지 않고,
**결과(성공/실패 + 예외)를 통째로 캐시하고 해석은 각 호출부에 그대로 남기는** 방식으로 통합했다.
판정 로직은 한 줄도 이동하지 않았다.

     cx_Oracle 설치 환경에서 오라클 감지 불가 — 이 PC 는 미설치라 재현 불가로 손대지 않았다(§2-5).
  3) [B 미실측] mssql `Connection Timeout=` 는 pyodbc 미설치로 코드 리뷰 근거만 있다.
  4) [C 잔존] 원본 키메타 조회 1건(analyze:1259)은 예외 전파 흐름이 달라 통합에서 제외했다(§3-5).
  5) [A 잔존] 엔진 직접 호출(pk_range_chunk.build_chunk_bounds)은 여전히 상·하한 밖 — 동시 진행 지침
     대상 파일이라 미접촉. 그 파일 작업이 끝난 뒤 배선 여부를 별도 판단하는 것이 안전하다.
  6) 전체 스위트의 사전 실패 989건(대부분 PROD-DB-WRITE 가드·HTML 문구 단언)은 별도 정리 대상이다.
