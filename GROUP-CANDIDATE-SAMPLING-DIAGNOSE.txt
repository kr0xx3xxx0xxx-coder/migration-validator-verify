--------------------------------------------------------------------------------
① 카디널리티(n_distinct) 판정 — 전체 스캔 아님 · 샘플링 아님(카탈로그 추정치)
--------------------------------------------------------------------------------
경로: candidate_engine.build_column_candidates()
  → normalized_metadata 의 stats.n_distinct 를 그대로 사용
  → 이 값의 출처는 services/db_statistics_service.py 의 pg_stats 조회

핵심 사실:
  - candidate_engine.py:642~681, 466~467 에서 GROUP BY 후보의 카디널리티 게이트는
    stats.n_distinct(2~50 등) 로 판정한다.
  - 이 n_distinct 는 실제 데이터를 COUNT(DISTINCT) 스캔해 구한 값이 아니다.
    db_statistics_service.py:291 `FROM pg_stats` — PostgreSQL 이 ANALYZE 시점에
    미리 만들어 둔 통계 카탈로그 뷰에서 읽기만 한다(우리 쿼리는 카탈로그 조회 1회).
  - n_distinct < 0 이면 '전체 행 대비 비율'이라, pg_class.reltuples(추정 행수,
    db_statistics_service.py:314~320)와 곱해 절대 distinct 추정값으로 환산한다
    (_resolve_distinct_count, :633~647). reltuples 도 추정치(정확 COUNT 아님).

25만행에서의 실제 동작:
  - 25만행이든 4200만행이든 이 경로는 데이터를 스캔하지 않으므로 테이블 크기와
    무관하게 즉시 응답한다(카탈로그 read 1~2회). 성능 부담 없음.
  - 대신 정확도는 'DB 가 마지막 ANALYZE 때 만든 추정치'에 의존한다.
    · PostgreSQL 의 n_distinct 자체가 내부적으로 default_statistics_target(기본 100)
      × 300 ≈ 3만행 랜덤 표본으로 추정한 값이다(이건 DB 내부 사정이며 우리 코드는
      그 추정치를 읽을 뿐 표본 크기를 제어하지 않는다).
    · stats 신선도(FRESH/STALE/UNANALYZED)는 db_statistics_service.py:602~626 에서
      pg_stat_all_tables 의 마지막 ANALYZE 시각으로 판정한다. UNANALYZED 면 n_distinct
      자체가 없어(None) 카디널리티 게이트가 발동하지 않는다.

--------------------------------------------------------------------------------
② profile 보조 signal 수집 — 5만행 샘플 CTE(전체 스캔 아님)
--------------------------------------------------------------------------------
경로: services/column_profile_service.py collect_column_profiles()
  - 단일 테이블·JOIN 모두 WITH SRC AS (원본 SELECT) → SAMPLE_SRC(5만행 LIMIT) CTE 로
    감싼 뒤 COUNT(*)/COUNT(col)/COUNT(DISTINCT col) 을 집계한다.
    (column_profile_service.py:47 `_SAMPLE_LIMIT = 50_000`, :305~375 _build_join_profile_sql)
  - 샘플 크기 5만행은 고정(테이블 규모에 따라 변하지 않음). 25만행이면 상위 5만행(약 20%)만 본다.
  - statement_timeout 15초(:53 `_PROFILE_STATEMENT_TIMEOUT_MS = 15_000`).
  - 오늘 언급된 'GAP-C: 단일 테이블 profile 에 5만행 샘플 CTE 가 없다' 백로그는
    이미 해소된 상태다(:502~510 SYSTEM-AUDIT-GAP-C-...FIX 주석 — 단일 테이블도
    JOIN 과 동일 SAMPLE_SRC 경로로 통일). 즉 지금은 단일/JOIN 모두 5만행 샘플이다.
  - 이 profile 은 candidate_scoring 의 '보조 signal'이며, ①의 카탈로그 카디널리티를
    대체하지 않는다(별도 축).

③ 값 패턴 판정(sample_values) — LIMIT 100 샘플  ← C_TS3 오판정 위험 지점
--------------------------------------------------------------------------------
경로: column_profile_service._collect_sample_values_bounded() → 값 100건
  - column_profile_service.py:66 `_SAMPLE_VALUE_LIMIT = 100`
  - :125 실제 SQL = `SELECT [TOP n] col1, col2 ... FROM from_table [LIMIT n]`
    ★ ORDER BY 없음 · WHERE 없음 → 테이블 물리적 '앞부분 100건'만 가져온다.
  - mv_column_sample(SQLite 캐시) 우선 재사용, 없을 때만 DB 에서 100건 조회(실측 ~5ms).
    캐시는 과거 다른 SQL 조회 때 담긴 100건일 수 있다(대표성은 그때 조건에 종속).
  - JOIN(복수 테이블)이면 추가 DB 조회 없이 캐시만 사용한다(:115).

이 100건이 쓰이는 곳(값 기반 구조 판정 — 컬럼명 무관):
  - detect_date_value_pattern (candidate_subtype_service.py:276) → 'YYYYMMDD'/'YYYYMM'/None
  - detect_datetime_value_format (:878) → 구분자 있는 날짜/시각 문자열 여부
  - detect_system_audit_value_pattern (:500) → 배치 적재 스탬프 여부
  - 판정 방식: 100건(NULL 제외) 중 90% 이상(_DATE_VALUE_MATCH_RATIO=0.90,
    candidate_subtype_service.py:256)이 유효 날짜 형식이면 '날짜'로 확정.

--------------------------------------------------------------------------------
④ 날짜 버킷 정확 distinct — 경계 컬럼만 전체 스캔(예산 제한)
--------------------------------------------------------------------------------
경로: candidate_postcount_finalize.py:389~468 (date_bucket_evidence 3단계)
  - L1 CATALOG_ESTIMATE : pg_stats/pg_class 읽기(스캔 없음)
  - L2 RANGE_DERIVED    : MIN/MAX 1회 → 월/분기/연 버킷 수 '상한'(인덱스 있으면 index scan)
  - L4 EXACT            : COUNT(DISTINCT DATE_TRUNC(...)) — 이것만 '전체 스캔'.
    단 범위 상한이 적합 경계에 걸린 컬럼만, 예산 _MAX_EXACT_DATE_COLS=2 컬럼,
    profile statement_timeout 재사용. timeout/실패 시 그 컬럼만 범위추정으로 fallback.
  - 대량 테이블에서 정확집계 부담은 '경계 컬럼 2개'로 국한되도록 설계돼 있다.

■ C_TS3 오판정과의 연관 가능성 — 연관 높음(값 기반 = LIMIT 100 샘플)
================================================================================
C_TS3 같은 컬럼의 '날짜 파싱 가능 여부' 판정은 ③ 값 기반(sample_values) 경로다.
즉 전체 데이터가 아니라 'ORDER BY 없는 LIMIT 100' 표본으로 판정한다.
아래 세 가지가 겹쳐 '변환 필요 컬럼이 대체 기본추천에 잘못 포함'되는 결과로 이어질 수 있다.

  1) 표본 편향(대표성):
     LIMIT 100 에 ORDER BY 가 없어 테이블 물리적 앞부분 100건만 본다. 파싱 불가한
     이상치(형식 깨진 값, 예외 코드값)가 뒤쪽 행에만 있으면 표본에 잡히지 않는다.
     → 100건이 우연히 깨끗한 날짜값만 담으면 '정상 날짜 → 절단 가능'으로 오판.

  2) 90% 임계의 관용치:
     detect_date_value_pattern/detect_datetime_value_format 는 90% 매치면 확정이라,
     100건 중 최대 10건이 비날짜여도 '날짜'로 판정된다(_DATE_VALUE_MATCH_RATIO=0.90).

  3) 캐시 재사용:
     mv_column_sample 캐시가 있으면 그 100건을 재사용한다. 과거 다른 SQL(다른 WHERE)
     조회 때 담긴 표본이면 현재 검증 대상 집합과 대표성이 더 어긋날 수 있다.

연결 고리(왜 '대체 기본추천'까지 가는가):
  값이 '날짜'로 오판되면 date_bucket 후보(_is_day_date_bucket 등, candidate_subtype
  _service.py:953~965)로 분류되고, 일반 GROUP BY 기본추천이 0개일 때
  promote_fallback_date_candidate(date_bucket_evidence.py:733~)가 이 후보를
  '대체 기본추천'으로 승격할 수 있다. 표본 기반 날짜 오판이 그대로 승격까지 전파된다.

주의(반대 방향 안전장치는 있음):
  값이 '날짜가 아님/파싱 불가'로 판정되면 date_bucket_direct_trunc_block
  (date_bucket_evidence.py:439) 및 needs_parse/prebucketed 게이트가 절단 SQL 을 막는다.
  문제는 '실제로는 파싱 불가인데 100건 표본에서 날짜로 보이는' 위양성(false positive)
  쪽이며, 이때는 이 안전장치가 발동하지 않는다.
