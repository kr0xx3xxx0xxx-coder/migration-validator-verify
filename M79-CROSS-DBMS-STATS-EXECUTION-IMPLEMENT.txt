BACKLOG M79(=CROSS-DBMS-STATS-EXECUTION-LIMITATION-RATIONALE-DIAGNOSE 진단서) 결론대로
"SQL 생성 계층은 이미 이기종 지원, 진짜 공백은 결과비교 GROUP BY 키 정규화"를 그대로 구현했다.
canonical 키 정규화 유틸(어댑터 패턴)을 신설하고, 게이트를 단일 출처로 통일해 개별검증(수동
4단계 버튼) · 원클릭 표준실행 · 일괄 통계검증 3경로 모두 동일 판정을 쓰게 했다. COUNT 는
방언차가 없어 클라이언트 가드에서 이기종을 항상 허용한다(서버는 원래도 무가드).

1. 조사 중 확인된 사실(진단서 대비 갱신)
────────────────────────────────────────────────────────────
- 진단서가 지목한 facade 게이트(services/single_validation_run_facade.py:1266~1284)는
  "원클릭 표준실행"(routes/single_run_route.py·batch_route.py) 전용이며, CLAUDE.md 가 문서화한
  수동 4단계 "▶ 통계검증 SQL 생성+실행" 버튼(routes/execute_route.py → orchestrator →
  single_validation_core.execute_single_validation → stats_execute_service.execute_stats_validation)
  과 "일괄 통계검증"(batch_stats_execute_service._execute_one_plan → 동일 execute_stats_validation
  직접호출)은 **이 facade 게이트를 타지 않는다** — 즉 실제 UI 4단계 버튼과 일괄 통계검증 경로는
  기존에 서버측 이기종 차단이 전혀 없었고, 클라이언트 JS alert(_singleExecGuard)만이 유일한
  방어선이었다(우회 시 구버전 str() 캐스팅 버그가 그대로 실행될 수 있었던 잠재 위험).
  → 그래서 새 게이트는 3곳에 각각 다시 심지 않고, 3경로가 모두 실제로 수렴하는 **단일 지점**
    (stats_execute_service.execute_stats_validation)에 한 번만 심었다(구조 단순화, 중복 배선 회피).
- 일괄 통계검증(batch_stats_execute_service.py)은 별도 게이트 코드 추가 없이 위 단일 지점 수정만으로
  자동으로 보호된다(실측으로 확인 — §4).
- 부수발견(COUNT-클라가드 비대칭): 서버(routes/count_route.py)는 원래도 방언 가드가 전혀 없어
  이기종 COUNT 가 이미 정상 동작했는데, 클라이언트 _singleExecGuard() 는 COUNT 버튼에도 걸려
  불필요하게 이기종 COUNT 를 막고 있었다 — action 파라미터를 추가해 COUNT 는 항상 허용, 통계검증
  실행만 아래 §2 조건을 적용하도록 분리했다.
  드롭다운 dbms 값 vs 실제 접속 프로필 dbms 어긋남 가능성(진단서가 "범위 밖"으로 남긴 항목)은
  이번에도 범위 밖으로 유지한다 — 전체 앱의 드롭다운/바인딩 동기화 아키텍처 재조사가 필요한
  별개 주제라 이번 스코프(결과비교 canonical 키 정규화)에 포함하지 않았다.

2. 어댑터 구조(파일별 역할)
────────────────────────────────────────────────────────────
신규 패키지 services/diagnosis/canonical_group_key/ (dialects_hash 어댑터 패턴 준용):
  - __init__.py   : 패키지 docstring(설계 의도) + 공개 API 재수출
  - base.py       : BaseGroupKeyCanonicalizer(계약) + canon_component() 기본구현(방언 무관 — 숫자
                    scale 통일/CHAR 우측공백 제거/날짜 canonical ISO/NULL·빈문자열 타입태그 분리) +
                    위임표(_CANONICALIZERS) + 팩토리(get_group_key_canonicalizer/_pair)
  - postgresql.py : PgGroupKeyCanonicalizer(db_type="postgresql")
  - oracle.py     : OracleGroupKeyCanonicalizer(db_type="oracle")
  (mysql/mssql 미구현 — 팩토리가 None 반환, 상위 게이트가 "미지원"으로 판정)

  설계 메모: 이 계층은 hash_contract/exact_diff.canonical 과 달리 "이미 fetch 된 파이썬 값"을
  정규화한다(SQL fragment 미생성). 규칙 자체(숫자/날짜/CHAR 처리)는 드라이버 반환 타입에만
  의존해 방언 무관이지만, CLAUDE.md 8번 규칙(어댑터 패턴, 인라인 if/elif 금지)을 그대로 따라
  DBMS 별 파일로 나눴다 — 오늘은 각 구현체가 base 를 그대로 상속하지만, 향후 특정 드라이버 전용
  보정이 필요해지면 해당 파일만 override 하면 된다(호출측 인라인 분기 없이).
  NULL/빈문자열은 "병합"하지 않는다(의도적 설계 결정, __init__.py 에 근거 문서화) — Oracle 은
  물리적으로 ''을 저장 못해 NULL 로 접히므로, 정상 이관이면 병합 없이도 양쪽 다 NULL 로 키가
  일치한다. 병합했다면 "NULL 이 실제로 다른 값으로 이관된" 진짜 결함을 검증 도구 스스로 가릴
  위험이 있어 채택하지 않았다.
