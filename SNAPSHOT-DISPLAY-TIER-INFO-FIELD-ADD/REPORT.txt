■ 배경

직전 작업(SINGLE-SNAPSHOT-TOTAL-COUNTS-FIELDS-ADD) 완료 시 발견된 별개 갭이다.
개별검증 마법사 5단계 결과 화면에는 '표시 등급 D1 · 전체 레코드 나열' 같은 배너가
뜬다. 이 배너는 규모가 커질수록(D2~D4) 화면이 왜 '그룹부터 / 대표만 / 요약만'으로
바뀌는지를 설명하는 유일한 문구다. 표시가 줄어드는데 이유가 없으면 사용자에게는
'검증 결과를 숨긴 것'으로 읽힌다.

그런데 이 배너의 입력인 display_tier_info 가 snapshot 에 저장되지 않아, 같은 run 을
재조회한 화면에서는 배너가 통째로 사라졌다. A/B/C 스크린샷에서 실제로 확인된 증상이다.
오늘 진행된 두 SNAPSHOT 보강 작업과 동일한 패턴(저장 whitelist 확장)으로 처리했다.

■ 등급이 갈리는 케이스를 어떻게 만들었는가 (부수 실측)

  표시 등급 판정은 두 축의 무거운 쪽으로 결정된다.
    축 A — 불일치 그룹 수(diff+src_only+tgt_only) : 1,000 / 10,000 / 60,000
    축 B — 전체 그룹 수(total_groups)             : 1,000 / 10,000 / 100,000

  D2 를 만들려면 그룹이 1,000개를 넘어야 한다. 처음에는 grp 컬럼 하나에 1,200 그룹을
  넣었는데 /generate 가 이렇게 막혔다.

    "선택한 GROUP BY 컬럼을 후보에서 찾을 수 없습니다: GRP"
    gb_candidacy_summary → {"tgt_col":"GRP", "reason_code":"HIGH_CARDINALITY",
                            "reason_label":"고카디널리티(고유값 1200) — 그룹 과다"}

  GROUP BY 후보 게이트는 고유값 50개 이하만 저카디로 통과시킨다
  (services/candidate_engine.py:1114 _GB_CARD_LOW_MAX=50). 즉 단일 컬럼으로는 구조상
  D2 이상에 도달할 수 없다. 그래서 각 40종(저카디 통과)인 컬럼 2개를 조합해
  40 × 40 = 1,600 그룹으로 만들었다. 이 제약은 이번 수정과 무관한 기존 정책이며,
  픽스처 파일 주석에 근거와 함께 남겨두었다.

■ 검증 3 — ablation

  저장된 snapshot 에서 display_tier_info 만 제거하고 같은 run 을 렌더하면

  import 해 같은 실행 결과로 snapshot 을 재구성하면, 두 케이스 모두
  display_tier_info 키 자체가 존재하지 않는다(has_display_tier_info=False).
