  (_log.exception 으로 traceback 도 남긴다), 폴백이 그 원문을 error_message 에 싣는다.

7. GROUP BY 없는 plan 회귀 확인 (07_global_count_sum_regression.txt)
════════════════════════════════════════════════════════════════════════════════

먼저 밝혀둘 제약: 운영 DB 의 selected_group_by=[] 계획 636건은 전부
source/target SQL preview 가 비어 있는 테스트 잔재라, 그대로 실행하면 SQL 부재
early-return 에 걸린다. 회귀 확인용으로 쓸 수 없다.

그래서 실제 실행 가능한 plan 2740 의 SQL 을 전체집계 형태(GROUP BY 제거)로 바꿔
동일 서비스 함수(_execute_one_plan_with_timeout)에 실 Inter DB 연결로 통과시켰다.
운영 DB plan 행은 조회만 하고 수정하지 않았다.

  A. GROUP BY 문자열 리스트  → SUCCESS_MATCHED  matched=3  groups=3  gb_keys=['REGION']
  B. GROUP BY dict 리스트    → SUCCESS_MATCHED  matched=3  groups=3  gb_keys=['REGION']
  C. GROUP BY 없음           → SUCCESS_MATCHED  matched=1  groups=1  gb_keys=[]

  판정 A==B (str/dict 동등)     : ✅
  판정 C  (GROUP BY 없음 정상)  : ✅

A 와 B 가 상태·건수·그룹수·gb_keys 까지 완전히 같다는 것이 이번 정규화의 핵심 근거다.
C 는 GROUP BY 없는 전체집계가 기존대로 1그룹으로 정상 동작함을 보인다.
다만 이 3종은 HTTP/UI 계층을 타지 않는다 — 그 계층은 GROUP BY 보유 케이스의
브라우저 실측(5절)에서 이미 확인했으므로 중복하지 않았다.

■ 이번 수정이 해결하지 못한 것 (정직하게)
  - 저장 형식 이원화 자체는 그대로다. 소비 쪽에서 흡수했을 뿐, writer 두 곳은

    없지만, 향후 실행 단계에서 period(월/분기 절단) 를 계획에서 읽어야 한다면
    문자열 형식 계획은 그 정보를 담을 수 없다. 형식 통일이 필요해지는 지점이다.
  - 폴백에서 BaseException 을 잡으므로 KeyboardInterrupt/SystemExit 도 결과 dict 로
    바뀐다. 데몬 스레드 안이라 실질 영향은 없다고 판단했지만, 무해하다고 단정하지 않고
    적어 둔다.

    baseline 이 이미 빨간 상태라는 사실 자체는 별개 부채다.

  - heuristic 하드코딩 증가: 없음. 컬럼명 substring 판단 등 추가 없음.
