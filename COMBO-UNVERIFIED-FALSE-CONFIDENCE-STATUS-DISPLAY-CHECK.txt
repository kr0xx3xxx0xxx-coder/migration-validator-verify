9. §3 판단 — 위험은 실재한다 (등급: 높음)

결론 : 사용자 우려는 타당하며, 현재 화면은 이 위험을 방지하지 못한다.

근거 요약
  (1) 상단 '상태' 타일은 4·5단계 모두 조합 미검증을 값·색·아이콘·툴팁 어디에도 반영하지
      않는다(§1 코드 + §4 실측 일치). 5단계 '상태' 툴팁은 "정상" 한 단어로 정보량이 0이다.
  (2) 그 '정상' 은 사실과 다르다. 같은 데이터에 조합 체크박스만 켜면 불일치 4그룹·재이관
      대상 4건이 즉시 드러난다(대조군 C). '표현이 불친절한 정도'가 아니라 오표시다.
  (3) 표시 라벨이 '일치'가 아니라 '정상' 이고 색이 파랑(#2563eb)이라, 유보나 주의를
      암시하는 시각 신호가 전무하다(§5).
  (4) 반대 신호(배너)는 4단계에서 567px 아래, 통계검증 SQL 카드 뒤에 있고, 5단계에서는
      기본 접힌 <details> 한 줄이다. '상태' 만 훑는 사용법에서는 구조적으로 놓치기 쉽다.
  (5) 배너가 유일한 구제책으로 안내한 상세비교는, 정확히 이 경우에 항상 비어 있고
      오히려 녹색으로 "상세 비교할 대상이 없습니다" 라고 안심시킨다(§6).
  → 안심 신호 4중(정상 / 0개 / 0건 / 대상 없음) vs 경고 신호 1개(접힌 한 줄).
     신호 비대칭이 명백하며, 이 상태의 결과를 검증 그룹에 공식 등록하면 '조합 미검증'
     사실은 등록물에 남지 않고 '정상' 만 남는다.

단, 오탐 측면은 현재 설계가 건전하다
  · 단일 축이면 배너가 뜨지 않고(axes<2 → null), 조합을 실제로 실행하면 사라진다(대조군 C).
  · 일괄검증(batch) 경로는 plan 증적이 없어 항상 null 이라 잘못된 꼬리표가 붙지 않는다.
  → 판정 함수 _mvComboUnverifiedAxes 자체는 신뢰할 수 있고, 개선안은 이 함수를
    재사용하기만 하면 되며 새 판정축을 만들 필요가 없다.

10. §3 개선 제안 (제안만 · 구현하지 않음)
────────────────────────────────────────────────────────────────────────────
[방향 A] 상태 타일의 판정 자체에 조합 미검증을 섞는다

  개요
    _mvStage4StatusInfo (grid_helpers.py:1043-1044) 와 _mvStage5TileRow (1342줄) 에서
    PASS 로 확정하기 직전에 _mvComboUnverifiedAxes(r) 를 한 번 호출하고, null 이 아니면
    PASS 대신 별도 코드(가칭 'PASS_PARTIAL')와 라벨 '정상(조합 미검증)' 을 쓴다.
    툴팁에는 이미 완성돼 있는 comboTip 문구를 그대로 재사용한다.

  장점
    · 상단 타일만 봐도 즉시 인지된다 — 사용자 우려에 대한 직접적·정면 대응.
    · 판정 소스가 한 곳(_mvComboUnverifiedAxes)으로 유지돼 배너·셀 꼬리표와 절대 어긋나지 않는다.
    · 새 서버 왕복·새 계산·새 판정축이 없다(이미 있는 함수와 문구의 재사용).

  단점 / 리스크 (비판적 검토)
    · status 코드 팔레트 확장이 필요하다. _mvStatusShort(176-188줄)·_mvIconColor·_mvBadgeCls
      3개 공용 함수를 손대야 하고, 이들은 1~5단계 전 화면과 일괄검증 그리드가 공유한다
      → 영향 범위가 이 화면에 국한되지 않는다. 회귀 표면이 가장 넓은 지점이다.
    · 색 설계 난이도: PASS(파랑)와 구분되면서 MISMATCH(빨강)로 오인되지 않아야 한다.
      앰버 계열(#F59E0B — 배너가 이미 쓰는 색)로 배너와 시각적으로 짝지어 두면
      "위의 앰버 = 아래 앰버 배너" 로 연결돼 학습 비용이 낮다.
    · 라벨 길이: 타일 폭이 minmax(118px,1fr) 라 '정상(조합 미검증)' 은 줄바꿈된다.
      타일 값은 짧게(예: '조합 미검증') 두고 전체 문장은 툴팁으로 미는 편이 안전하다.
    · 5단계는 CHECKING(확인 중) 분기(1343-1348줄)와 우선순위 충돌을 정리해야 한다
      — 상세비교 진행 중 표시가 조합 미검증 표시를 덮을지 말지 결정 필요.
    · 상태 코드 문자열을 그대로 읽는 기존 테스트·스냅샷이 있으면 함께 갱신해야 한다.
    · [주의] 이 방향은 '검증 결과 상태값은 PASS/WARNING/SKIP 외로 추가 금지'라는
      CLAUDE.md 절대 금지 조항과의 관계를 먼저 정리해야 한다. 여기서 다루는 것은
      서버 판정 상태값이 아니라 UI 표시용 아이콘 코드이므로 저촉되지 않는다고 보이나,
      구현 착수 전 사용자 확인이 필요한 지점이다.

[방향 B] 판정은 그대로 두고 배너의 물리적 가시성만 높인다

  개요
    #mvStage4ComboNotice 를 #mvStage4CtxGrid 바로 아래로 옮기고(현재 567px 아래),
    5단계 <details> 도 타일 바로 밑에 붙인다. 필요하면 기본 펼침(open) 또는 sticky 로.
    판정 로직·status 코드·색 팔레트는 일절 건드리지 않는다.

  장점
    · 공용 상태 함수(_mvStatusShort/_mvIconColor/_mvBadgeCls)를 건드리지 않아 회귀 표면이 최소다.
    · 레이아웃 변경뿐이라 롤백이 쉽고, 실패해도 판정값이 오염되지 않는다.
    · 오늘 만든 배너 자산을 그대로 살린다(문구 신설 없음).

  단점 / 리스크 (비판적 검토)
    · 근본 해결이 아니다. '상태' 칸 자체는 여전히 '정상' 이라, 상태만 읽거나 결과를
      캡처·전달하는 사용법(스크린샷 공유, 검증 그룹 등록 결과)에서는 위험이 남는다.
    · 화면 캡처나 목록형 화면(일괄검증 그리드 등 타일만 나오는 뷰)으로 결과가 유통되면
      배너는 따라가지 않는다.
    · 4단계는 SQL 카드가 타일과 배너 사이의 주 콘텐츠라, 배너를 타일 밑으로 올리면
      "실행 결과 안내가 실행 버튼보다 위" 라는 읽기 순서 역전이 생긴다 — 배치 재설계 필요.
    · 기본 펼침(open)으로 바꾸면 GROUPBY-COMBO-NOTICE-RELOCATE 가 방금 축약판으로
      줄여 놓은 결정을 되돌리는 셈이라, 그 작업의 취지와 충돌한다.

  §1 상태 칸에 조합 미검증이 반영되는가
