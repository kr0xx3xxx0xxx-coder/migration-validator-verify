1. 무엇을 왜 했는가
--------------------------------------------------------------------------------
선행 단계(AMBIGUOUS-ADMIN-COLUMN-MANUAL-OVERRIDE-STORE-IMPLEMENT, 커밋 13cc873)는 관리컬럼
자동판정에 대한 사용자 수동 확정(override)의 저장소/API 계층만 만들고 끝났다. 그 계층은
"아직 아무도 소비하지 않는다"고 스스로 명시했을 만큼 화면·판정과 완전히 분리돼 있었다.
이번 작업은 그 두 계층을 잇는다.

문제의 실체는 이렇다. 관리컬럼(시스템 감사·배치 적재 스탬프) 판정은 B축(명칭·코멘트 = 가설)과
A축(실측 값 = 검증)의 교차확인으로 이뤄지는데, A축이 답할 수 없는 경우(값이 타임스탬프가 아니거나
미수집)에는 B축 단독으로 하드 배제가 성립한다. candidate_subtype_service.py 가 스스로 '알려진
한계'로 적어둔 지점이며, 이번 실측에서도 그대로 재현됐다 — 오라클 CREATED_BY 는
SYS_CONTEXT 로 채워진 업무성 컬럼인데 표준사전 명칭매칭 하나로 GROUP BY 후보에서 배제되고,
화면에는 '⚠ 이름 매칭만 — 재검토 권장'이라는 경고만 뜰 뿐 사용자가 그 판단을 뒤집을 방법이
없었다. 반대 방향(자동판정이 놓친 관리컬럼을 사용자가 지목하는 것)도 마찬가지로 불가능했다.

이번 연결로 사람이 최종 판단을 내리고, 그 판단이 프로젝트 단위 영속 지식으로 남아 재검증 때마다
다시 적용된다.

3. 판단이 갈릴 수 있었던 지점과 선택 근거
--------------------------------------------------------------------------------
(1) 저장 성공 후 화면 갱신 — '재조회' vs '낙관적 업데이트' → 낙관적 업데이트 채택
    /analyze 재실행은 DB 재접속·프로파일 재수집을 동반하고 workflow_token 이 재발급되어 2단계
    COUNT 확인 상태까지 초기화된다(서버 단계 가드). 확정 버튼 한 번에 치를 비용이 아니다.
    반대로 낙관적 반영에서 대입하는 값은 서버가 방금 확정해 돌려준 결과의 미러이며, decision →
    verdict 매핑은 서버 apply_admin_column_overrides 와 동일한 2:1 대응 하나뿐이라 화면이 판정을
    새로 만들어내지 않는다.
    다만 자동선정 pool 재배치(상위 N 기본추천)는 서버 계산이라 이 자리에서 바꾸지 않았고, 그래서
    성공 안내에 "기본추천 재배치는 다음 분석 실행 시 반영됩니다"를 명시했다. 조용한 불일치를
    남기지 않기 위한 문구다.

(2) 재렌더 방식 — morph 부분갱신 vs 통째 교체 → 통째 교체 + 체크 복원
    처음에는 체크박스 보존을 위해 morph 경로(_mvCandPaneMorph)를 켰다. 1차 실측에서 DEPT_CD 를
    AUDIT 확정하자 그 행이 화면에서 아예 사라졌다. 원인은 확정/해제가 행을 기본 후보표와
    '참고/제외 후보' 표(details) 사이로 옮긴다는 것이다 — morph 는 같은 자리의 노드를 비교·재사용
    하는 방식이라 이 구조 이동을 따라가지 못한다. 통째 교체로 바꾸고, 교체로 잃는 '사용자가 손으로
    켠 체크'는 재렌더 전후로 직접 수집·복원하도록 했다(cap 3 정합화는 기존 공용
    sanitizeCandidateCheckboxes 에 위임).

(3) 확정 컬럼의 배지·사유 — 자동 근거를 함께 띄울 것인가 → 억제
    1차 실측에서 DEPT_CD 를 AUDIT 확정하니 사유가 "관리컬럼(시스템 감사 · 배치 적재 스탬프)이므로
    …"로 나왔다. 이 컬럼은 값으로 확인된 적이 없다(축 근거가 없어 UNKNOWN 분기로 떨어진 결과다).
    사람이 확정한 자리에 시스템이 근거를 지어내는 셈이라, 확정이 있으면 자동 근거 배지
    (_adminAuditExclusionBadge)와 자동 사유를 억제하고 서버가 확정과 함께 만든 reason_text 만
    표시하도록 했다. 확정이 없는 컬럼(UPD_YMD 등)은 종전 표시 그대로다.

(4) 이미 확정된 관리컬럼도 참고표에 노출되는 기존 정책과의 공존
    기본 후보표와 참고/제외 표가 같은 buildRow 를 공유하므로(NON-TARGET-COLUMNS-MERGE-INTO-
    REFERENCE-TABLE) 별도 처리 없이 공존한다. AUDIT 확정으로 참고표에 밀려난 컬럼도 그 자리에서
    바로 '확정 해제'를 누를 수 있다 — 되돌릴 수 없는 조작이 되지 않도록 하는 것이 중요했다.

(5) project_id 미선택 처리
    서버 API 는 sentinel/미실재 프로젝트를 400 으로 거부한다(고아 확정 방지). 이 정책을 그대로
    두고, 화면에서는 버튼을 애초에 disabled 로 두고 서버가 내려준 사유 문구를 title 에 그대로
    쓴다. 누르고 나서 실패를 보는 것보다 못 누르게 하고 이유를 붙이는 편이 정직하다.
