✅ 작업 완료 - 오라클/MySQL/MSSQL 정확 COUNT를 EXACT로 라벨해 불필요한 안전계수(×2.0)를 제거. 오라클 정확 86,472 → SAFE(계수 미적용) 실측 확인, PostgreSQL은 계수 유지(회귀 없음). 커밋 c17f931, 서버 8000 재기동(2026-07-23 22:56:02).

1. 배경(수정 대상 결함 P2)
────────────────────────────────────────────────────────────
GROUPBY-JUDGMENT-VALUE-OVERESTIMATE-DIAGNOSE 에서 확인된 결함:
services/groupby_execution_safety.py 의 우선순위2(EXPLAIN) 경로가 explain_fn 결과를
방언 구분 없이 무조건 PLANNER_ESTIMATE 로 라벨 → 오라클/MySQL/MSSQL 의 COUNT(*) 래핑
(정확 그룹 수)에도 안전계수(×2.0)가 적용되어, 실제 그룹 수가 한도(100,000) 이내인데도
2배(예: 86,472→172,944)로 부풀려져 부당하게 차단.
정확값에는 과소추정 위험이 없으므로 계수를 적용할 이유가 없음.

2. 수정 내용(코드)
────────────────────────────────────────────────────────────
(1) services/groupby_explain_estimator.py
    · _EXACT_ESTIMATE_DBMS = {oracle, mysql, mssql} + _is_exact_estimate_dbms() 추가.
    · build_explain_estimate_fn() 반환 계약 확장:
        기존:  _fn() -> int | None  (더 큰 값만)
        변경:  _fn() -> (value:int, is_exact:bool) | None
      - is_exact = 값에 기여한 방언이 '모두' 정확 COUNT(oracle/mysql/mssql)면 True.
      - 하나라도 PostgreSQL 플래너 추정이 섞이면 False(그 쪽 과소추정 대비, 보수적).

(2) services/groupby_execution_safety.py
    · reason_code EXACT_COUNT_WITHIN_LIMIT 추가(정확 COUNT 한도 이내, 계수 미적용).
    · 우선순위2 경로(구 라인 224):
        기존:  _judge(int(rows), PLANNER_ESTIMATE, "explain", PLAN_ESTIMATE_WITHIN_LIMIT)
        변경:  value, is_exact = rows if isinstance(rows, tuple) else (rows, False)
               kind        = EXACT if is_exact else PLANNER_ESTIMATE
               reason_safe = EXACT_COUNT_WITHIN_LIMIT if is_exact else PLAN_ESTIMATE_WITHIN_LIMIT
               _judge(int(value), kind, "explain", reason_safe)
      - bare int(레거시/직접 호출)은 비정확(PLANNER_ESTIMATE)으로 하위호환 유지.
    · (P1 개선) _judge 의 detail 에 안전계수 적용 시 "(안전계수 ×N 적용 · 추정값 실효 상한 M)"
      문구 추가 → 표시 한도(100,000)와 추정값 실효 상한(50,000) 괴리를 명시.

※ _effective_count / _EXACT_KINDS(안전계수 로직 자체)는 변경하지 않음 — 라벨링만 방언별로
  정확히 구분되도록 배선(이미 정당한 설계는 그대로 유지).
