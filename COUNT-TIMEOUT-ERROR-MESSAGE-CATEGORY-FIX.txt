✅ 작업 완료 - COUNT-TIMEOUT-ERROR-MESSAGE-CATEGORY-FIX - COUNT 쿼리 실행 타임아웃을 '연결 시간 초과'(접속 문제)로 오분류하던 오류 문구 정정

[문제]
services/count_common_service.py 의 categorize_conn_error 가 오류 메시지에 'timeout' 문자열만
있으면 무조건 '연결 시간 초과'로 분류했다. 오늘 추가된 COUNT_STATEMENT_TIMEOUT_MS 가 발화하면
접속 자체는 성공했고 쿼리 실행 시간만 초과한 것인데, 사용자에게는 '접속 문제'로 안내됐다.

[수정 내용 — services/count_common_service.py 단일 파일]
- _is_query_timeout(msg, exc, db_type) 신설
  · 쿼리 타임아웃 판별은 db_adapter_registry.is_query_timeout_error 에 위임(재구현 없음)
  · exc 가 없는 호출 경로(일괄검증)는 메시지를 예외로 감싸 동일 판별기에 전달
  · db_type 미지정이면 지원 4개 방언(postgresql/oracle/mysql/mssql) 판별기를 모두 적용
  · 접속 단계 표지(_CONNECT_PHASE_MARKERS)가 있으면 위임 판정보다 먼저 접속 실패로 확정
    (실측 근거: PG connect 실패 = 'connection to server at "…" failed: timeout expired',
     MSSQL = 'Login timeout expired' → 어댑터 판별기만 쓰면 접속 실패가 쿼리 타임아웃으로 오탐)
- _query_timeout_message() 신설 — 정정 문구
- categorize_conn_error 시그니처 확장: (msg, exc=None, db_type=None) — 1인자 호출 하위호환 유지
- run_count_pair 의 두 호출부(원본/목적지)에서 예외 객체와 db_type 을 함께 전달
- 타임아웃 판정 로직(is_query_timeout_error)·타임아웃 값 자체는 불변(분류/문구 전용)

[문구 판단 — '재시도해도 동일 실패' 안내를 이쪽에도 반영함]
반영했다. 근거 3가지.
 ① 성격이 동일하다. COUNT statement timeout 도 4단계 통계 SQL 과 같이 '실행마다 적용되는
    고정 상한'이라 같은 SQL·같은 데이터로 재시도하면 같은 지점에서 잘린다.
 ② 사용자 행동을 바꾼다. '연결 시간 초과'로 보이면 재시도·접속정보 점검이라는 잘못된 조치로
    유도되는데, 실제 해법은 제한 상향 또는 대상 축소다.
 ③ 재시도 억제가 시스템에도 이롭다. db_query_service.is_connection_lost_error 는 '연결 시간
    초과' 카테고리를 '재시도 가능한 연결 장애'로 취급한다. 정정 문구에는 그 패턴이 없어
    무의미한 재접속·재시도 대상에서 빠진다(전용 테스트로 고정).
단, 4단계 문구는 여러 줄이지만 COUNT 오류 문구는 일괄검증 그리드 셀·200자 절단 경로에도
표시되므로 톤은 동일하게 유지하되 한 줄로 압축했다(제한값 + 환경변수 + 재시도 무의미 + 대안).
