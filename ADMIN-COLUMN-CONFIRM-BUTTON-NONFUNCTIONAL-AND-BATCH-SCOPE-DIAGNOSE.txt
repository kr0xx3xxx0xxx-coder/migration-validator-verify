0. 결론 요약
════════════════════════════════════════════════════════════════════════════════
증상이 두 개 섞여 있었고, 원인은 서로 다르다.

  [증상 1] "잠정 중형"이 그대로 뜬다        → 원인: 운영 서버 재기동 누락 (확정)
  [증상 2] "관리컬럼 맞음/아님" 버튼이 안 눌린다 → 원인: 작업 프로젝트 미선택 → 버튼이
                                              disabled 로 렌더 (재기동과 무관, 확정)

사용자의 정황 추론("둘 다 반영이 안 된 것처럼 보이니 재기동 누락일 것")은 증상 1에 대해서는
정확했다. 다만 증상 2는 재기동 누락으로 설명되지 않는다 — 버튼 시각분리 커밋(1862899)의 코드는
재기동 전 서버에도 **이미 로드되어 있었다**(아래 §1-2 근거). 재기동 후에도 프로젝트를 선택하지
않으면 버튼은 여전히 눌리지 않는다.

일괄검증에는 이 기능이 아예 없다(설계 의도). 더 중요한 사실은, 개별검증에서 저장한 확정이
일괄검증 판정에 **적용조차 되지 않는다**는 것이다(§3).

2-3. 왜 사용자가 사유를 알 수 없었나
─────────────────────────────────────────────────────────────
  서버는 사유 문구를 정확히 만들어 title 속성에 실어 보낸다(§2-2 [A] title 참조).
  그런데 disabled 버튼은 브라우저가 포인터 상호작용 자체를 주지 않는다 — 실제 마우스 클릭이
  "element is not enabled" 로 timeout 난 것이 그 증거다. 그래서 화면에는
    · 눌리지 않는다는 사실만 있고
    · 왜 눌리지 않는지(프로젝트를 먼저 선택하라)는 도달할 수 없다.
  1862899 가 개선한 것은 "무엇이 클릭 가능한가"의 구분이었고, "왜 지금 클릭할 수 없는가"는
  여전히 화면에 드러나지 않는다. (이번 지침은 진단만이므로 수정하지 않았다 — §5 권고 참조.)

    · 즉 배선 지점은 열려 있고 batch 호출부만 값을 넘기지 않는다

3-3. 일괄검증에서 자동판정이 틀렸을 때 개입할 다른 수단이 있는가 — 없다
─────────────────────────────────────────────────────────────

  항목을 찾았으나 0건이다. 일괄검증 경로에서 관리컬럼 자동판정을 사람이 교정할 수단은
  현재 존재하지 않는다. 남은 우회는 "해당 테이블만 개별검증으로 다시 도는 것"뿐이며,

3-4. 이 기능이 일괄검증 규모(수십~수백 테이블)에서 쓸 만한 UX인가
─────────────────────────────────────────────────────────────
  판단: 현재 형태(개별 컬럼 × 개별 테이블 클릭)는 일괄 규모에 부적합하다. 다만 그것은
  "이 기능이 불필요하다"가 아니라 "대량 적용 축이 화면에 노출되지 않았다"는 뜻이다.

  근거 — 저장소와 API 는 이미 프로젝트 전체 범위를 완전히 구현해 두었다:

    끝날 수 있는 구조인데, 지금은 테이블마다 반복 클릭해야 한다. 수백 테이블에서는 사실상

    일괄 규모로 확장할 자리(PROJECT_COLUMN)는 이미 백엔드에 마련돼 있으나 화면에 없다.**

5. 권고 (구현하지 않음 — 사용자 판단 대기)

  P1  버튼 옆에 사유를 '보이게' 노출한다. disabled 버튼의 title 은 브라우저가 포인터 이벤트를
      주지 않아 도달 불가하다(§2-3 실측). 컨트롤을 감싸는 span 에 title 을 달거나, 짧은 안내
      문구("프로젝트 선택 필요")를 텍스트로 병기하면 "왜 안 눌리는지"가 화면에서 닫힌다.
      — 위험: 비고 셀 chip 과다. 문구는 1개로 제한할 것.

  P2  batch_runner._build_core_candidates → enrich_candidates_for_display 에 project_id /
      override_table_key 를 배선한다(§3-2). 인자는 이미 존재하므로 호출부만 값을 넘기면 되고,
      project_id 가 없는 일괄 실행은 지금과 완전히 동일하게 동작한다(회귀 없음).
      — 이 배선 없이는 "개별에서 고쳐도 일괄에서 되살아나는" 모순이 남는다.
      — 위험: batch 항목마다 저장소 조회 1회가 추가된다. 테이블 수가 많으면 프로젝트 단위
        일괄 조회 후 메모리 매칭으로 바꿔야 한다(현재 resolve_override 는 컬럼당 1회 조회).

  P3  화면에 PROJECT_COLUMN 범위 선택을 노출한다(§3-4). 저장소·API·STALE 계산은 이미 완비돼
      있어 UI 한 곳만 열면 된다. 다만 '프로젝트 전체 적용'은 되돌리기 부담이 큰 조작이므로
      확인 단계와 적용 대상 미리보기가 함께 필요하다.

  P4  UI 검증 하니스가 '초기 상태'를 재현하도록 한다(§2-4). 최소한 (a) 프로젝트 미선택,
      (b) programmatic click 대신 실제 마우스 클릭 두 가지는 회귀 검증에 포함시킬 것.
