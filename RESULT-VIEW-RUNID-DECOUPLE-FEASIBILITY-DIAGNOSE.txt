✅ 작업 완료 - RESULT-VIEW-RUNID-DECOUPLE-FEASIBILITY-DIAGNOSE (코드 수정 0 · 진단만)

■ 결론
  부분 분리 가능. "요약 계열"은 run_id 하나로 완전 분리 가능하고, "그룹별 결과표"는 조건부(저장소 휘발성 +
  DOM/전역 충돌 선결), "드릴다운 신규 준비 · 불일치 행 클릭 분석 · 저장/등록"은 DB 접속정보가 필수라 분리 불가.
  결정적 사실 2개:
   (1) 5단계 렌더 진입점 _mvRenderValidationDetail 은 **이미 host/ctx 파라미터화**돼 있고, 일괄검증 상세가
       이미 마법사 상태 0 의존으로 그 경로를 쓰고 있다(선례 존재 — 새 패턴 아님).
   (2) 막는 것은 렌더러가 아니라 **입력**이다. r._execEvidence(클라 전용)와 _analyzeData 파생 표시값이 서버
       계약에 없다. 그중 대부분은 서버 snapshot 으로 복원 가능하나, 2개 필드는 저장 whitelist 에 없어
       "화면 간 판정 표기 불일치"를 만든다.

6. job_registry DTO 충분성 — **부족하다(핵심 미해결 지점)**
────────────────────────────────────────────────────────────────────────────
 · 개별(single) DTO 의 id = **exact_diff 재이관 run_id**(services/job_registry.py:242 `st.get("run_id")`).

 · 통계(stats) DTO — id=batch_stats_execute_run.run_id. stats_execute_result 테이블
   (services/batch_stats_execute_service.py:161-185)에 요약 카운트는 있으나 result_id / 그룹행 링크 없음
   → **요약까지만 가능**.

 필요 추가 필드(전부 extra 안 — DTO 기본 9필드 불변):
   validation_run_id   snapshot 조회 키
   result_ids          그룹행 페이징 / Excel
   plan_fingerprint    stale 차단(/stats-result/page 의 fp)
   target_table        라벨 · 파일명
   result_available    위 3개 유무로 '결과 보기' 버튼 활성 판정

 ★ 선결 리스크: 위 값들을 원천(services/exact_diff/reimport_job)이 보관하는지 별도 확인이 필요하다.

7. 기존 "진행 중이던 검증 작업이 있습니다" 복원 팝업과의 겹침 — 의견(실행 안 함)

현행 3요소:
 (가) 새로고침 복원 팝업 — tabler_renderer.py:28316 _mvRefreshActiveRunChoice
      트리거 :28296 _mvSingleAutoRestore (페이지 로드당 1회, _mvCurrentTab==='analyze' 일 때만,
      GET /single/active-run 조회). 선택지 [이어서 보기] / [중단하고 새로 시작].
 (나) 동일 완료이력 선택창 — routes/single_completed_history_route.py
      active run 이 없을 때 조건지문(single_condition_fingerprint)으로 완료 run 을 찾아
      [기존 결과 보기] / [최신 데이터로 다시 실행].
 (다) 복원 실체 — ui/js_restore_individual_adapter.py (MvRestoreCore 'individual')
      fetchRestoreEnvelope(/single/restore-envelope) → restoreStepState(1~4탭 잠금해제 플래그만)
      → restoreStepPayload(SQL·COUNT 만 채움 :183-200) → openCurrentView('result') → _reconnectReimport.

겹침 판정: **목적은 겹치지만 대상 데이터가 다르다.**
 · (가)/(나)/(다)의 복원 본체는 **재이관(상세비교) run** 이다. 통계검증 결과표는 복원 대상이 아니다
   (restoreStepPayload 는 SQL 과 COUNT 만 채운다). 그래서 복원 후 5단계에 뜨는 것은 재이관 상세 뷰다.
 · 이번 설계는 **통계검증 결과(요약 + 그룹표)** 를 run_id 로 여는 것 — (가)/(나)가 못 채우는 빈칸이다.
 · 진짜 중복은 "세션 소유" 축이다. (가)/(다)는 owner_session_id 를 검증해 남의 run 복원을 차단하지만
   (routes/single_restore_route.py 정책), 현황판은 전역 목록이다.

의견:
 1. **역할 고정 분리** — (가)/(나) = "내 진행 중/직전 작업을 마법사로 되돌린다"(쓰기 컨텍스트 복구),
    현황판 결과보기 = "임의 run 의 결과를 읽기 전용으로 본다".
    현황판 뷰에는 재실행 · 저장 · 그룹등록 버튼을 **넣지 않는다**. 이러면 기능이 겹치지 않는다.
 2. 현황판 뷰에는 "마법사에서 이어서 작업" 링크 1개만 두고, 그 링크가 기존 (가) 경로
    (_mvViewExistingRun / MvRestoreCore.restore)를 호출하게 한다 — **복원 로직 2벌 금지**.
 3. (나) 동일 완료이력의 [기존 결과 보기]는 장기적으로 현황판 뷰로 흡수 가능하나, 지금 통합하면
    조건지문 매칭까지 끌고 와야 해 범위가 커진다 → 이번엔 손대지 않는 쪽 권고.
 4. 세션 정책 — 1단계는 **내 세션 소유 run 만** 결과보기 허용(현행 restore-envelope 와 동일 기준).
    전역 공개 여부는 별도 결정 사항으로 분리.

8. 기능/구조 변경 요청 응답 형식
────────────────────────────────────────────────────────────────────────────
· 요청 요약: 5단계 결과 렌더링을 마법사 세션 상태와 분리해 run_id 로 독립 호출 가능하게 하고,
             현황판에서 완료 job 클릭 시 탭 이동 없이 같은 렌더링을 그 자리에서 호출한다.
· 긍정적 효과: 탭 전환 시 현황판이 사라지는 SPA 제약을 우회. _mvRenderValidationDetail 이 이미
             파라미터화돼 있어 렌더러 중복 신설 없이 재사용 가능(일괄 상세가 이미 그렇게 쓰고 있음).
· 구조적 문제점: (1) renderExecute 의 고정 DOM id 6종 + window._exec* 전역 17종 → 동시 2곳 렌더 불가.
             (2) _execEvidence 가 서버 계약에 없어 "클라 조립기"라는 새 결합점이 생긴다.
             (3) tabler_renderer.py 는 이미 2MB — 조립기는 반드시 별도 모듈로 둬야 한다.
· 운영상 위험: (1) stats_result_store 가 in-memory·LRU 24 → 현황판에서 결과 보기를 눌렀는데 그룹표만
             비는 상황이 **정상 동작으로** 발생한다. 사유 표기가 없으면 결함으로 오인된다.
             (2) 재이관 store 도 재기동 시 소멸(기존 실측). (3) 완료 job 목록 API 신설 시 폴링 부하 증가.
· heuristic / scoring / explainability 영향: heuristic 추가 없음. scoring 변경 없음.
             **explainability 손실이 실질 위험**이다 — column_comment(한글 헤더)와
             null_value_transform_evidence 가 snapshot whitelist 에 없어, 같은 run 이 마법사에서는
             '값 변환 감지 · 확인 필요', 현황판에서는 '일치' 로 표시된다
             (ui/execute_result_renderer.py:1028-1031). 근거 미저장이 화면 간 판정 표기 불일치로 드러나는 사례.
· 권장 대응책: ① 서버 조회 라우트 1개 + 클라 조립기 1개. 렌더러는 손대지 않는다.
             ② 1차 범위를 **요약 전용**으로 확정 — 4단계식 성공요약 + 5단계 요약 Grid + 실행 기준 +
                불일치 한 줄 요약 + Excel + "마법사에서 상세 보기" 링크. 결과표/드릴다운 제외.
                이러면 DOM/전역 충돌과 판정 표기 불일치가 **둘 다 발생하지 않는다**.
             ③ 그룹표까지 원하면 snapshot whitelist 2필드 추가 + 배타 렌더 정책 + 저장소 휘발성 안내를 선결.
· 지금 구현 여부: **문서화 우선**.
             선결 3건 — (i) job DTO 가 검증 run_id/result_id 를 확보할 경로(reimport_job 수정 필요 여부),
             (ii) 완료 job 목록 API 신설, (iii) snapshot whitelist 확장 — 이 확정되기 전 착수하면
             재작업 위험이 크다.
