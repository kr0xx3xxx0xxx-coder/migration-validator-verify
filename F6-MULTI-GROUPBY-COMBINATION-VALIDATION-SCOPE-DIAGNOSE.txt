0. 요약 — 지침 전제 2건을 실측으로 정정합니다
════════════════════════════════════════════════════════════════════════

지침 배경에 "조합 실제 검증 기능 자체는 여전히 없고, 안내조차 없는 상태로
남아있음" 이라고 적혀 있으나, 현재 코드 기준으로 **두 진술 모두 사실과
다릅니다.** 조사의 출발점이 되는 사실이므로 먼저 정정합니다.

(1) 조합 검증 기능은 **이미 있습니다.**
    커밋 7d94b99 `feat(step4): 4단계 SQL 카드에 조합(PAIR) 검증 opt-in 진입점
    복원 (COMBO-PAIR-ENTRY-POINT-RESTORE-IMPLEMENT)` 로 2026-07-28 에
    구현·라이브 검증까지 끝났습니다. 4단계 SQL 카드의 체크박스
    `#gbIncludePair` ('조합(A + B)도 함께 검증 — 세트 1개 추가 실행') 를 켜면
    `/groupby-plan` 에 `include_pair=true` 가 전달되어 조합(PAIR) 세트 1개가
    실제로 생성·실행·판정됩니다. 기본값은 OFF 입니다.

(2) 안내도 **완전히 없는 상태가 아닙니다.**
    2026-08-05 §2-5 10번으로 삭제된 것은 미체크(OFF) 상태에서 뜨던 경고박스
    (`#genSqlComboOffText`, "⚠️ 이 SQL은 참고용입니다 …") **하나뿐**이고,
    다음 3가지는 현재도 살아 있습니다(정적 렌더 실측 — §3-2):
      · 4단계 SQL 카드의 opt-in 체크박스 라벨 자체
      · 4단계 상단 '조합검증' 타일 — 값 '미포함' + 툴팁
        ("단일 축 N세트로만 분해 실행합니다 — 조합(…)에서만 드러나는 불일치는
          검증되지 않습니다. 4단계 SQL 영역의 '조합도 함께 검증' 을 켜면 포함됩니다.")
      · 5단계 '조합 미검증' 경고 배너 (실행 후, 조합 세트 미실행 시에만)

    즉 §2-5 10번의 삭제는 '중복 안내 1개 제거' 였지 '안내 전면 삭제' 가
    아니었습니다. 사용자가 그때 밝힌 거부 사유("대체 UI 없음") 역시, 대체 UI
    (체크박스)가 이미 존재하므로 **당시 시점에 이미 해소돼 있던 사유**입니다.

그렇다면 실제 문제는 무엇인가 — 조사로 확인된 진짜 결함은 아래 1건입니다.

  ★ **조합 검증은 켤 수 있지만, 실무 규모 테이블에서는 켜도 실행되지 않습니다.**
    자동계획 상한(`PLAN_TARGET_MAX_GROUPS = 100`)이 조합 세트를 자동 제외하기
    때문입니다. 5천만행 픽스처 실측에서 예상 조합 그룹 210개 > 상한 100 →
    체크박스를 켜도 조합 세트가 만들어지지 않았습니다(§4-4). 이 상한을 화면이나
    API 로 조정할 방법은 **없습니다** — 코드 상수 수정이 유일한 경로입니다.

  그리고 이 상한의 근거가 되는 '비용' 가정 자체가 이 프로젝트의 자체 실측과
  어긋납니다. 조합 1세트 추가 비용은 단일축 1세트와 **같은 수준**이며(§4-5
  실측 4.02초 vs 3.60/6.19초), 그룹 수가 아니라 스캔량이 비용을 지배한다는
  것은 이미 `stats_strategy_planner.py` 가 41건 실측으로 확정해 둔 사실입니다
  (가중치 scan 2.0 vs group 0.17).

2. 현재 구조 — 조합 검증이 실제로 도는 경로
════════════════════════════════════════════════════════════════════════

2-1. 실행 흐름 (GROUP BY 2축 이상 선택 시)

  [3단계] GROUP BY 후보 2개 이상 체크
      ↓
  [4단계] ▶ 통계검증 SQL 생성
      · renderSQL() 이 조합 SQL(GROUP BY A, B) 1개를 화면에 표시
        ※ 이 표시 SQL 은 참고용 — 실제 실행 SQL 은 세트별로 다시 생성된다
      · 같은 카드에 opt-in 체크박스 #gbIncludePair 렌더 (기본 OFF)
        → 체크 상태는 window._mvIncludePairChecked 에 보존
      · 상단 '조합검증' 타일이 그 플래그를 읽어 '포함(+1세트)' / '미포함' 표시
      ↓
  [4단계] ▶ 통계검증 실행 → gbSel.length >= 2 → _runExecutePlanSets(ctx)
      · POST /groupby-plan { candidates, total_rows, include_pair }
        → build_groupby_execution_plan() 이 세트 목록 결정
           - 축마다 SINGLE 세트 1개 (항상)
           - include_pair=true 이고 가드 5종 전부 통과 시 PAIR 세트 1개 추가
      · 세트마다 POST /generate (selected_groupby = 그 세트의 cols)
      · 세트마다 POST /execute  (groupby_cols  = 그 세트의 cols)
      · 결과를 agg 로 합산 (matched/diff/src_only/tgt_only/total_groups/rows)
      ↓
  [5단계] 세트 합산 요약 + 조합 세트가 없으면 '조합 미검증' 배너

2-2. 각 계층이 이미 해주는 일 — **새로 만들 것이 없습니다**

  · SQL 생성 방식: 새 빌더 불필요. `/generate` 에 `selected_groupby=[A,B]` 를
    넘기면 조합 GROUP BY SQL 이 그대로 생성됩니다(generator/sql_generator.py).
    조합 세트는 단일축 세트와 완전히 같은 코드 경로를 씁니다.

  · 결과 대조 로직: 새 대조기 불필요. 조합 세트도 `/execute` 의 동일 판정
    (matched / diff / src_only / tgt_only)을 그대로 받습니다. 조합 키는
    `gb_keys` 에 2개 컬럼으로 실려 그룹 단위 비교가 그대로 성립합니다.

  · UI 표시 위치: 이미 3곳에 배선돼 있습니다.
      4단계 SQL 카드   → opt-in 체크박스 + ON 문구
      4단계 상단 타일  → '조합검증' 포함/미포함
      5단계 요약       → 조합 세트가 실행됐으면 '조합 미검증' 배너 자동 소거
                         (`_mvComboUnverifiedAxes` 가 '선택 축 전부를 동시에
                          GROUP BY 한 세트'의 실재를 보고 판단)

  결론: **조합 검증을 "켜기 위해" 새로 구현할 계층은 없습니다.** 남은 것은
  가드 정책값과 표시 결함뿐입니다(§3).

2-3. 단일검증 vs 일괄검증 비대칭 (기존 사실 — 이번 조사에서도 유지 확인)

  축별 분해는 **개별검증 경로만**입니다. 일괄검증(batch)은
  `services/batch_runner.py` 가 선택 축 전체를 한 SQL 의 GROUP BY 로 묶어
  실행하므로 조합이 항상 검증됩니다. 따라서 '조합 미검증' 류 경고를 일괄
  결과에 적용하면 오탐이며, 현재 `_mvComboUnverifiedAxes` 는 plan 증적을
  요구하는 방식으로 이 오탐을 이미 차단하고 있습니다.

3. 조합 검증을 실제로 켜려면 — 범위 조사 결과
════════════════════════════════════════════════════════════════════════

3-1. 조합 세트를 막는 가드 7종 (services/groupby_plan_service.py)

  ①  distinct 근거 부족           양 축 모두 distinct 값이 있어야 함
                                  → 2026-07-28 클라이언트 중첩경로 fallback
                                    (`_mvCandDistinct`)으로 **해소됨**
  ②  업무 evidence 부족           `_has_business_evidence(a) and (b)` 양쪽 필요
  ③  예상 그룹 수 상한 초과       est > PLAN_TARGET_MAX_GROUPS(100) → 제외
                                  ★ 실무 규모에서 실제로 걸리는 가드 (§4-4)
  ④  평균 그룹 행 수 미달         avg < PLAN_MIN_AVG_ROWS_PER_GROUP(100)
  ⑤  추가 구분 효과 없음          est <= max(distinct_a, distinct_b)
  ⑥  COUNT MAJOR 상태             `_gateSt === 'COUNT_MAJOR_DIFF'` → 강제 OFF
                                  (tabler_renderer.py:26655, alert 후 단일축만)
  ⑦  세트 수 상한                 PLAN_MAX_AUTO_PAIR_SETS = 1 → 조합은 최대 1개

  ③~⑤ 는 `build_groupby_execution_plan()` 의 기본 인자로만 존재하고,
  `/groupby-plan` 라우트가 이 값들을 **요청에서 받지 않습니다**
  (routes/groupby_plan_route.py 의 요청 모델 필드는 candidates / total_rows /
  include_pair 3개뿐). 즉 운영 중 조정 수단이 전무하며 코드 상수 수정이
  유일한 변경 경로입니다.

3-2. 3축 이상 조합은 경로 자체가 없습니다

  · `PLAN_MAX_AUTO_TRIPLE_SETS = 0` (자동 3축 0개)
  · EXPLICIT_MULTI(명시 복합) 세트 생성이 D7-17 로 제거됨
    (groupby_plan_service.py:138 — 생성 코드 자체가 없음)
  · 클라이언트도 방어적으로 항상 필터
    (tabler_renderer.py:26674 `filter(s => s.kind !== 'EXPLICIT_MULTI')`)
  · PAIR 는 최대 1세트라, GB 3개 선택 시 가능한 3개 조합쌍 중 1개만 검증됨
    (그것도 '예상 그룹 수가 가장 큰' 1쌍)

  따라서 "REGION_CD + STATUS_CD + DEPT_CD 3축 동시" 검증은 현재 **불가능**하며,
  이를 켜려면 EXPLICIT_MULTI 계열 복원(설계 되돌리기)이 필요합니다.

3-3. 표시·저장 결함 3건 (이번 조사에서 새로 확인)

  [결함 A] 조합 세트 자동 제외 사유가 화면에 표시되지 않습니다.
    · 서버는 제외 사유를 정확히 만들어 보냅니다.
      예: "예상 1,600그룹 — 자동계획 상한(100) 초과, 과세분화 방지를 위해
           단일 축 계획으로 분리"
    · 클라이언트도 그 값을 받아 보관합니다
      (tabler_renderer.py:26783 `plan: { … excluded: planResp.excluded || [] … }`)
    · 그런데 **`plan.excluded` 를 읽어 렌더하는 코드가 ui/ 전체에 0건**입니다
      (grep 결과: 저장 1곳, 소비 0곳).
    · 반면 체크박스 툴팁은 이렇게 안내합니다 —
      "데이터 조건 …에 따라 조합 세트가 자동 제외될 수 있으며, 그 경우
       5단계에 제외 사유와 '조합 미검증' 경고가 그대로 표시됩니다."
      → 배너는 표시되지만 **제외 사유는 표시되지 않습니다.** 안내와 구현 불일치.
    · 참고: 2026-07-28 라이브 검증의 판정 "GUARD-2 제외 사유(상한 초과) 노출:
      true" 는 DOM 이 아니라 JS 증적 객체(`_execEvidence.plan.excluded`)를 읽어
      판정한 것이라, 화면 표시 여부를 증명하지 않습니다.
      (combo_pair_entry_point_restore_live_verify.py:562)
    · 사용자 체감: 체크박스를 켜고 실행했는데 아무 설명 없이 '조합 미검증'
      배너만 다시 뜹니다 — 왜 안 됐는지 알 방법이 화면에 없습니다.

  [결함 B] 조합 세트를 실행해도 5단계 '실행계획' 표기에 반영되지 않습니다.
    · grid_helpers.py:1933 이 `plan.sets.filter(s => s.kind === 'SINGLE').length`
      로만 세트 수를 셉니다.
    · 결과: 단일축 2세트 + 조합 1세트(총 3세트)를 실행해도 화면 표기는
      "단일축 2세트 · N그룹" — 조합 세트가 표기에서 사라집니다.
    · 배너는 정상 소거되므로 판정은 맞지만, 무엇을 실행했는지의 기록이 부정확합니다.

  [결함 C] 저장된 결과를 재조회하면 '조합 미검증' 경고가 사라집니다.
    · 배너 판정 `_mvComboUnverifiedAxes(r)` 는 `r._execEvidence.plan.sets` 를
      필요로 하는데, 이는 **클라이언트 세션 메모리에만** 존재합니다.
    · 재조회(복원) 경로 `ui/js_restore_individual_adapter.py` 는 `_execEvidence`
      를 전혀 구성하지 않습니다(grep: 해당 파일 내 0건).
    · 결과: 축별 분해로만 검증한 결과를 나중에 다시 열면 경고 없이
      '일치 · 정상' 으로만 보입니다 — 시간이 지날수록 위험한 표시입니다.

  세 결함 모두 **표시/증적 계층**이며 판정 로직과 무관합니다.

4. 5천만행 재현 실측 — 재현 성공
════════════════════════════════════════════════════════════════════════

4-1. 재현 가능 여부: **가능하며, 실제로 재현했습니다.**

4-2. 방법 (데이터 쓰기 0 — 순수 SELECT)

  대상: NXDNP.MV_SCATTER50M_SRC · 50,000,000행 (Oracle_asis, 실측 확인)

  기존 50M 픽스처의 목적지(MV_SCATTER50M_TGT)는 1% 행 누락 형태라
  '조합에서만 드러나는 불일치' 시나리오가 아닙니다. 새 픽스처를 만들면
  데이터 쓰기가 되므로, **원본을 가상 목적지와 대조하는 읽기 전용 방식**을
  택했습니다 — 목적지 = 원본 + 라틴 상쇄 오차(SELECT 식으로만 표현).

    adj = AMT + CASE
            WHEN REGION_CD='R03' AND STATUS_CD='G01' THEN +10
            WHEN REGION_CD='R04' AND STATUS_CD='G02' THEN +10
            WHEN REGION_CD='R03' AND STATUS_CD='G02' THEN -10
            WHEN REGION_CD='R04' AND STATUS_CD='G01' THEN -10
            ELSE 0 END

  네 셀의 행 수가 정확히 같으면(실측 각 250,000행 — 아래) 축별 합계는 완전히
  상쇄되고 조합 4칸만 어긋납니다. 이는 이미 검증된 오라클 소형 픽스처
  (MV_COMBO_SRC/TGT, 1,200행 2×2 라틴 상쇄)와 **동일한 구조를 5천만행으로
  확대한 것**입니다.

  실행: GROUP BY REGION_CD, STATUS_CD 1회 (전체 1스캔) → 205개 셀을 받아
        축별 합계·조합 합계를 클라이언트에서 롤업

4-4. ★ 가장 중요한 발견 — 이 테이블은 체크박스를 켜도 조합 검증이 안 됩니다

  `build_groupby_execution_plan()` 의 조합 그룹 수 추정:
      est = min(distinct_a × distinct_b, total) = min(21 × 10, 50,000,000) = 210
      가드 ③: est(210) > PLAN_TARGET_MAX_GROUPS(100)  → **자동 제외**

  즉 §4-3 에서 실증한 그 불일치는, 사용자가 '조합도 함께 검증' 을 켜더라도
  검출되지 않습니다. 그리고 §3-3 [결함 A] 때문에 **왜 제외됐는지도 화면에
  나오지 않습니다.**

  참고로 다른 가드는 전부 통과합니다:
      평균 그룹 행 수 = 50,000,000 / 210 ≈ 238,095행  ≫ 하한 100  (통과)
      구분 효과 210 > max(21, 10)                       (통과)

  걸리는 가드는 오직 상한 100 하나입니다.

4-5. 조합 세트의 실제 추가 비용 — 상한 100 의 근거를 반박합니다

  같은 50M 테이블에서 측정한 GROUP BY 소요(각 전체 스캔 1회):

      단일축 REGION_CD              21그룹      3.60초
      단일축 STATUS_CD              10그룹      6.19초
      조합 REGION_CD + STATUS_CD   205그룹      4.02초

  조합 세트는 그룹 수가 10~20배 많지만 **소요시간은 단일축 세트와 같은
  수준**입니다. 비용을 결정하는 것은 결과 그룹 수가 아니라 전체 스캔 1회이기
  때문입니다.

  이는 이 프로젝트가 이미 41건 실측으로 확정해 둔 사실과 정확히 일치합니다
  (services/strategy/stats_strategy_planner.py):
      DEFAULT_STATS_COST_WEIGHTS = { scan: 2.0, group: 0.17, cardinality: 0.08 }
      회귀식: log10(ms) = 0.819·log10(scan) + 0.189·log10(groups+1) + …
      → scan : groups ≈ 4.3 : 1, 스캔량이 지배 요인

  그런데 조합 세트를 막는 가드 ③ 은 **그룹 수만** 봅니다. 프로젝트 자체
  cost 모델이 "그룹 수는 비용에 거의 영향이 없다"고 결론 낸 지표를,
  조합 계획에서는 유일한 차단 기준으로 쓰고 있는 셈입니다.

  덧붙여 시스템의 다른 그룹 수 한도와 비교하면 격차가 큽니다:
      실행 결과 그룹 hard cap  = 100,000 (INTERACTIVE_GROUPBY_MAX_GROUPS,
                                 services/stats_execute_service.py:_result_group_limit)
      조합 계획 상한            =     100
      → **1,000배 차이.** 조합 계획 상한만 유독 보수적입니다.

  다만 상한 100 이 무의미한 것은 아닙니다. 원래 목적은 비용이 아니라
  '과세분화 방지'(그룹당 행이 너무 적어 통계 비교의 의미가 사라지는 것)이며,
  그 목적에는 이미 평균 그룹 행 수 하한(가드 ④)이라는 **더 직접적인 지표**가
  따로 있습니다. 그룹 수 상한은 화면 표시량·결과 저장량 관점에서만 남는 근거이고,
  그 관점의 실제 한도는 위의 100,000 입니다.
