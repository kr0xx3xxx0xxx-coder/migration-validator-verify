지침에 적힌 트리거 가설은 "오라클 방언 + FROM 절 뒤에 WITH" 였다. 이 가설을 그대로 코드로
옮기지 않고, 먼저 (변형 × 방언) 격자를 자식 프로세스에서 격리 실측했다.

  실측 도구 : scripts/dev_e2e/sqlglot_pre_parse_pattern_scope_probe.py (신규)
  안전 설계 : 파싱은 자식 프로세스에서만, 6초 안에 안 끝나면 taskkill /F /T 로 트리 강제 종료
  환경      : C:\Python314\python.exe / sqlglot 30.7.0

■ 1-A. 방언 축 — 오라클에서만 hang 한다

    변형              oracle        mysql        postgres      tsql
    ----------------  ------------  -----------  ------------  -----------
    V1 FROM 뒤 WITH   HANG(6초+)    PARSED 10ms  PARSED  8ms   PARSED 11ms
    V2 INSERT 형태    HANG(6초+)    PARSED  6ms  PARSED  5ms   PARSED  7ms
    V3 실제 사고 SQL  HANG(6초+)    PARSED  7ms  PARSED  5ms   PARSED  6ms
    V4 컬럼목록 형태  HANG(6초+)    PARSED  6ms  PARSED  5ms   PARSED  6ms
    V5 WHERE 뒤       HANG(6초+)    PARSED  7ms  PARSED  5ms   PARSED  6ms
    V6 JOIN 뒤        HANG(6초+)    PARSED  8ms  PARSED  6ms   PARSED  6ms

    추가로 방언 미지정(dialect=None)도 0.4ms 에 정상 종료했다.
    → 차단 범위를 **오라클 방언 한정**으로 좁혔다. 나머지 3방언은 같은 SQL 이라도 차단하지
      않는다(불필요한 동작 변경을 만들지 않기 위함).

■ 1-B. 문법 축 — 트리거는 "FROM 뒤"보다 넓다(가설 수정)

    N1 SELECT 1 FROM dual WITH x AS (...)                    → HANG
    N2 SELECT 1 WITH x AS (...)          ← FROM 이 아예 없음  → HANG
    N3 SELECT * FROM (SELECT * FROM t WITH x AS (...)) v     → HANG (서브쿼리 안 같은 깊이)
    N4 INSERT ... SELECT * FROM t WITH x AS (...)  ← 꼬리 없음 → HANG
    N10 ... UNION ALL SELECT a FROM u WITH x AS (...)        → HANG

    특히 N2 가 결정적이다 — FROM 이 없는데도 hang 한다. 지침의 "FROM 절 뒤" 규칙을 그대로
    구현했다면 이 패턴이 그대로 새어나갔다.
    → 규칙을 "**본문(SELECT)이 시작된 뒤, 같은 괄호 깊이에 오는 `WITH <별칭> [ (컬럼) ] AS (`**"
      으로 확장·정정했다.

■ 1-C. 대조군 — 정상 SQL 은 오라클에서도 전부 정상 종료(차단하면 안 되는 목록 확정)

    S1 표준 CTE / S2 INSERT+CTE / S3 서브쿼리 안 CTE / S4 다중 CTE / S5 IN 서브쿼리 /
    S6 리터럴 위장 / N5 WITH (NOLOCK) / N6 다중 statement / N7 WITH FUNCTION /
    N8 주석 위장 / N9 WITH READ ONLY   →  전부 PARSED 4~7ms

[2] 구현 내용

■ parser/sqlglot_safe_parse.py (+246줄)

  · SqlParseBlocked(Exception)          — 사전 차단 전용 예외. Exception 하위라 기존
                                          `except Exception` 폴백 경로는 수정 없이 동작한다.
  · detect_unsupported_sql_shape(sql, dialect) -> str|None
        차단 사유 문자열 또는 None. 판정 3단계:
          (1) kill-switch(MV_SQL_PREPARSE_BLOCK=0) 이면 즉시 None
          (2) 오라클 방언이 아니면 즉시 None (실측 범위 밖)
          (3) 원문에 후보 정규식이 없으면 즉시 None  ← 값싼 fast-path
          (4) 리터럴·주석 제거 후 괄호 깊이 스캔으로 확정
  · _strip_literals_and_comments()      — 지침대로 **기존 함수 재사용**:
        services.analyze_service._strip_sql_literals_and_comments 를 **호출 시점 지연 import**
        한다(파서 계층이 import 시점에 services 를 끌어오지 않도록 — 계층 역전 방지).
        import 불가 시에만 동일 규칙의 최소 대체 구현으로 폴백한다.
  · _scan_misplaced_with()              — 괄호 깊이별로 "이 스코프에서 SELECT 가 이미 나왔는가"
        를 추적. 여는 괄호마다 새 스코프를 쌓으므로 서브쿼리 안의 정상 CTE 는 걸리지 않고,
        최상위 세미콜론에서 상태를 초기화하므로 다중 statement 의 두 번째 CTE 도 안 걸린다.
        큰따옴표 식별자 내부는 토큰으로 보지 않는다.
  · blocked_parse_count()               — 차단 누적 건수(관측용). 어느 진입점으로 들어오든
                                          집계되도록 검출기 내부에서 증가시킨다.
  · _guarded_call() 선두에 검사 삽입     — parse_one_guarded / parse_guarded 양쪽,
                                          즉 **가드를 쓰는 모든 호출부(운영 25파일 53곳)** 가
                                          자동으로 1차 방어선을 얻는다.

■ 4-A. 오탐 점검 — 판정 오류 0건

    위험 패턴 11종(V1~V6, N1~N4, N10) → **11/11 전부 차단**
    정상 SQL 16종 → **16/16 전부 통과**
      표준 CTE, INSERT+CTE, 서브쿼리 안 CTE, 다중 CTE, EXISTS 안 CTE, IN 서브쿼리,
      문자열 리터럴 위장('FROM t WITH x AS (SELECT 1)'), 라인주석 위장, 블록주석 위장,
      WITH (NOLOCK) 힌트, WITH READ ONLY, WITH FUNCTION(오라클 12c), 다중 statement,
      따옴표 별칭 WITH "X" AS, 따옴표 키워드 SELECT "WITH", CTAS + CTE
    비오라클 방언(mysql/postgres/tsql/postgresql/mssql/미지정) → 위험 SQL 이라도 **차단 안 함**

    보강 근거: 차단 대상 형태(같은 괄호 깊이에서 본문 SELECT 뒤에 오는 CTE)는 오라클 문법상
    **애초에 유효하지 않은 SQL** 이다. 차단하지 않았어도 파싱은 실패했을 SQL 이므로, 차단이
    '동작하던 기능'을 막을 수 없다. 이것이 오탐 위험이 구조적으로 낮은 이유다.

■ 4-B. 무회귀 — 4방언 × 6형태 = 24케이스, 차단 ON/OFF 결과 **완전 동일**

    도구: scripts/dev_e2e/sqlglot_pre_parse_block_overhead.py (신규)
    방법: kill-switch 로 검사만 껐다 켰다 하며 같은 SQL 을 파싱해 ParseResult 요약
          (error / src / tgt / 컬럼수 / where)을 비교.

      oracle / mysql / postgresql / mssql  ×
      plain, cte, multi_cte, nested_cte, union, literal
      → **차이 건수 = 0 / 24**, 오탐 차단 0건

■ 4-C. 오버헤드 — 유의미한 지연 없음 (200회 반복 평균)

    SQL 형태             검사 단독   parse OFF → ON        증감
    -------------------  ---------  --------------------  --------
    plain (WITH 없음)      1.99us   0.713ms → 0.734ms     +2.94%
    cte                   31.61us   0.826ms → 0.874ms     +5.74%
    multi_cte             51.49us   1.157ms → 1.201ms     +3.78%
    nested_cte            34.39us   1.116ms → 1.176ms     +5.41%
    union                  2.17us   0.811ms → 0.804ms     -0.90%
    literal               15.13us   0.698ms → 0.745ms     +6.74%
    big_300cols(3,430B)   74.63us  16.643ms →16.009ms     -3.81%

    · WITH 가 없는 SQL 은 정규식 fast-path 로 **약 2us** — 사실상 0.
    · CTE 가 있어도 절대값은 0.02~0.05ms 이고, 대형 SQL(3.4KB)은 파싱 16.6ms 대비 0.45%.
    · union / big 의 음수(-0.9%, -3.8%)는 측정 노이즈 범위(검사 비용보다 실행 편차가 큼).
    · 최초 1회만 전처리 함수 지연 import 비용이 붙는다(이 스크립트 5.88ms / 콜드 캐시 자식
      프로세스 121.69ms). 운영 서버는 web_server 가 이미 analyze_service 를 import 하므로
      실사용 시 이 비용은 발생하지 않는다.

[7] 잔여 한계 — 이 수정으로 해결되지 **않은** 것 (지침 5항 필수 명시)
════════════════════════════════════════════════════════════════════════════════

이 사전 검사는 **완전한 해결이 아니라, 가장 흔한 위험 패턴을 값싸게 막는 1차 방어선**이다.
아래는 여전히 남아 있는 구멍이며, 숨기지 않고 명시한다.

 (1) 아직 이 검사에 안 걸리는 hang 패턴이 남아 있을 수 있다.
     차단 규칙은 이번에 실측한 "오라클 + 본문 이후 같은 깊이의 WITH ... AS (" 하나뿐이다.
     sqlglot 파서의 다른 무한루프 경로(다른 문법 조합, 향후 버전에서 새로 생기는 결함)는
     전혀 다루지 않는다. 그런 SQL 이 들어오면 사전 검사를 그냥 통과한다.

 (2) 통과한 SQL 이 hang 하면 메모리 폭주는 그대로 재현된다.
     2차 방어선인 타임아웃 가드는 '응답'만 되돌려줄 뿐 버려진 스레드를 회수하지 못한다
     (이번 대조군 실측에서도 가드가 켜진 상태로 165.1MB/s 로 계속 늘었다).
     → 근본 해결(파싱을 별도 프로세스로 격리해 강제 종료 가능하게 만들기)은 **미해결 과제**이고
       이번 범위 밖이다. 사전 차단은 그 설계가 나올 때까지의 값싼 완충재로 봐야 한다.

 (3) 비오라클 방언은 사전 차단 대상이 아니다.
     이번 실측에서 mysql/postgres/tsql/미지정은 hang 하지 않았기 때문에 의도적으로 제외했다.
     추후 다른 방언에서 hang 이 관측되면 범위를 다시 실측해 넓혀야 한다.

 (4) 규칙은 '본문 SELECT 선행'을 조건으로 삼는다.
     SELECT 없이(예: VALUES 절 뒤 등) 잘못된 위치의 WITH 가 오는 조합은 이번에 재현하지 못해
     규칙에 넣지 않았다. 확신할 수 없는 것은 차단하지 않는다는 원칙(양방향 안전)에 따른 것이고,
     그만큼 잠재적 누출로 남는다.

 (5) 운영 중 오탐이 발견되면 즉시 끌 수 있게 kill-switch 를 뒀다.
     MV_SQL_PREPARSE_BLOCK=0 → 사전 차단 전면 해제(타임아웃 가드는 계속 동작).
     다만 끄면 (2)의 메모리 폭주 위험이 그대로 돌아온다는 점을 함께 인지해야 한다.
