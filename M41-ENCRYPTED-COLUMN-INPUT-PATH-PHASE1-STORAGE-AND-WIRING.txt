작업명: M41-ENCRYPTED-COLUMN-INPUT-PATH-PHASE1-STORAGE-AND-WIRING
✅ 작업 완료 - 암호화여부 저장 테이블 신설 + AnalyzeRequest 스키마 필드 배선 + 저장소 폴백 함수 연결(UI 위젯 제외)

■ 0. 착수 전 사전검토(CLAUDE.md 기능/구조 변경 응답 형식)

  - 요청 요약 : M41 진단이 확인한 "정의서 암호화여부가 어디에도 저장 안 됨" 문제 중, 저장
    테이블 신설 + 스키마 필드 배선(요청 우선/저장소 폴백)만 이번 단계에서 반영. 업로드 UI
    위젯은 범위 제외(별도 승인 대상).
  - 긍정적 효과 : 매핑정의서 '암호화여부'를 명시한 API 직접 호출 요청이 이제 서버에 정상
    도달한다(기존엔 Pydantic extra='ignore' 로 100% 드롭). 저장소 폴백 경로가 생겨 관리자
    스크립트로 한 번 저장해두면 재검증 시마다 정의서를 다시 실을 필요가 없다.
  - 구조적 문제점 : 저장소 모듈이 하나 늘어난다(admin_column_override_store.py 와 동형이라
    패턴 재사용 비용은 낮음). web_server.py 는 건드리지 않았다(비대화 없음).
  - 운영상 위험 : 낮음 — 신규 테이블 1개(CREATE TABLE IF NOT EXISTS 멱등), 기존 함수
    시그니처 불변, try/except 로 감싸 조회 실패 시 안전 기본값(no-op) 유지. 회귀 위험 낮음.
  - heuristic/scoring/explainability 영향 : heuristic 하드코딩 증가 없음(명시필드만, 자동
    탐지 없음 — 기존 원칙 그대로). explainability 는 source 컬럼(정의서/수동)으로 유지.
    scoring 영향 없음.
  - 권장 대응책 : (이미 반영) 요청 필드 우선 > 저장소 폴백 > 안전기본값(OFF) 순서로 계층화.
    UI 업로드는 별도 지침으로 분리해 기능 추가 제한 규정을 지킨다.
  - 지금 구현 여부 : 진행(저장소+스키마배선만, 위 범위 내에서 완료)

■ 2. 이번 단계에서 저장소에 값을 넣는 방법(정상 — UI는 다음 단계)

  UI 업로드 위젯이 없으므로, 이번 단계에서 column_encryption_flag 에 값을 채우는 유일한
  방법은 services.column_encryption_flag_store.save_flag(project_id=, table_key=,
  column_name=, is_encrypted=True, source="정의서" 또는 "수동") 를 직접 호출하는 관리자
  스크립트뿐이다. HTTP 라우트는 이번 지침 범위(저장테이블+스키마배선)에 없어 신설하지
  않았다(진단서 §5 파일범위 중 routes/column_encryption_flag_route.py 는 "향후 예상"이지
  이번 지침 본문 1/2절에 없는 항목이라 이번 단계에 포함하지 않음).
