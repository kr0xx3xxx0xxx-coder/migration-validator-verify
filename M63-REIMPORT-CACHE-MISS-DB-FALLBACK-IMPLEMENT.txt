[배경]
BACKLOG.md M63 — services/exact_diff/reimport_job.py 의 "재사용 가능?" 판정이 메모리 캐시
(_JOBS_BY_FP, 개수상한16·TTL없음·재기동시소실) 하나뿐이라, 캐시만 사라지면 파일(exact_diff_run/
exact_diff_record)에 데이터가 그대로 남아있어도 처음부터 재스캔하던 문제.

[구현 범위]
지시서 범위대로 services/exact_diff/reimport_job.py 안에서만 해결. routes/agg_diff_route.py 는
건드리지 않음(다른 작업이 동시 수정 중이라는 지시서 안내 준수).

[스키마 변경 여부] 없음
exact_diff_run 테이블에 fingerprint 컬럼이 이미 존재했다(services/exact_diff/store.py:34,
CREATE TABLE 시점부터 있던 컬럼). ALTER/신규 테이블/신규 인덱스 전혀 추가하지 않았다 — 기존
컬럼을 SELECT 로 조회하는 최소 로직만 추가했다. (참고: 조회는 fingerprint 위 인덱스 없이 풀스캔
이지만, M64 정리 작업으로 exact_diff_run 이 보관기간(기본 7일) 초과분을 자동 삭제하게 되어 있어
행 수가 무한정 늘지 않는다 — 향후 규모가 커지면 인덱스 추가를 검토할 수 있다는 점만 남겨둔다.)

[비판적 검토 — 위험/한계]
- rehydrate 된 summary 는 실제 실행 시 만들어지는 summary(engine/strategy/passed_keys 등 세부
  필드 포함)와 100% 동일하지 않다 — basis_json/counts_json/metrics_json 에 저장된 필드만
  재구성 가능하다. 다만 재사용 소비처(routes/agg_diff_route.py 의 _with_evidence)는 run_id/
  status/gb_cols/sum_labels/source_count/target_count/ratios/missing_migration/value_mismatch/
  excluded_target_only/metrics 등 basis_json·counts_json 이 이미 저장하고 있는 필드만 참조하므로
  화면 표시에는 지장이 없을 것으로 판단했다(라우트 파일은 이번 범위가 아니라 실제 화면 테스트는
  하지 못했다 — 다음 세션에서 routes 작업이 끝난 뒤 클릭스루 확인 권장).
- fingerprint 컬럼에 인덱스가 없어 매 캐시미스마다 exact_diff_run 전체 스캔이 발생한다. 현재
  M64(EXACT-DIFF-RUNS-RETENTION-CLEANUP) 덕분에 테이블이 무기한 누적되지 않으므로 지금 규모에서는
  무해하다고 판단해 인덱스를 추가하지 않았다(새 스키마 변경 최소화 지시 준수) — 회귀 관찰 필요시
  후속 작업으로 인덱스 추가를 검토할 것.
