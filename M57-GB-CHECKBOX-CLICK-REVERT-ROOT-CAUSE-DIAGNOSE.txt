2. 원인 특정
────────────────────────────────────────────────────────────
가설 확인 결과(지시된 순서대로):

- 가설A(재렌더가 사용자 변경을 덮어씀) — **부분 기각, 근접 원인 확인**: "매 polling마다 다시
  그린다"는 아니었다(로그상 renderColSelect/_mvRepaintPlanTiles 등 어떤 재렌더 함수도 호출 자체가
  없었음). 다만 지시에서 의심 대상으로 지목한 `_mvSyncRunLockedControls`가 정확히 이 결함의
  당사자였다 — 다시 그리는 것이 아니라 **body 잠금 CSS 클래스를 stale 상태로 남기는 것**이었다.

- 가설B(의도된 잠금 — 실행에 쓰인 후보는 재선택 전까지 불변) — **기각**. 잠금 자체(`body.
  mv-run-locked`, ui/tabler_renderer.py:440-449)는 실제로 존재하는 의도된 설계이지만, 그 의도는
  주석에 명시된 대로 "실행 **중**(COUNT/재검증/SQL생성/통계검증)"에만 켜는 것이다("[STAGE-EXEC-
  CONTROL-LOCK-IMPLEMENT] 실행 중 … 선택 컨트롤 오버레이 락"). "실행이 끝난 뒤에도 그 축은
  재선택 전까지 잠근다"는 의도는 주석·커밋 이력 어디에도 없다. 오히려 `_mvAnyRunActive()`와
  `_mvSyncRunLockedControls()`를 지금 다시 호출하면 정확히 "잠금 해제"가 나온다 — 즉 설계가
  의도한 목표 상태(실행 종료 시 잠금 해제)와 실제 화면 상태가 어긋난 것으로, 설계 위반이다.

- 가설C(체크박스 change와 별개 경로의 경합/자동복원) — **기각**. 경합·복원 로직이 아니라, 애초에
  체크박스가 마우스 클릭의 이벤트 타겟이 되지 못하는 CSS 문제였다.

★ 근본 원인(코드 레벨, 4개 지점 모두 동일한 순서 결함) ─────────────────────
`_mvSyncRunLockedControls()`(ui/tabler_renderer.py:16025-16036)는 `_mvAnyRunActive()`의 판정
근거 중 하나로 "실행 버튼 HTML에 스피너 span이 남아있는지"를 본다(28472-28477,
`ids=['countRunBtn','genColBtn','execBtn','runBtn']`, `b.innerHTML.indexOf('spinner')>=0`이면
실행 중으로 간주). 그런데 각 실행 함수의 종료 처리(finally)에서 "잠금 재계산" 호출이
"버튼 스피너 제거"보다 **먼저** 실행된다 — 재계산 시점엔 아직 스피너가 남아 있어
`_mvAnyRunActive()`가 true를 반환하고, 그 결과 `body.mv-run-locked`가 다시(또는 계속) true로
설정된다. 그 직후 버튼 스피너는 정상적으로 제거되지만, 잠금을 다시 계산하는 호출이 그 뒤에는
없어 `mv-run-locked`가 영구적으로 stale true 상태로 남는다. 4개 실행 경로 모두 같은 순서
결함을 갖고 있다(모두 재현 확인은 아니고 코드 대조로 확인 — 실제 재현은 통계검증 실행 경로만):

  1) runCount() 종료(COUNT 비교) — 25191~25197행:
     25193 `_mvSyncRunLockedControls()` (countRunBtn 스피너 아직 있음) → 25196
     `btn.innerHTML = '▶ COUNT 다시 실행'` (스피너 제거, 재계산 없음)
  2) runGenerate() 종료(통계검증 SQL 생성) — 26845~26854행:
     26847 `_mvSyncRunLockedControls()` → 26850 `b2.innerHTML = '▶ 통계검증 SQL 생성'`
  3) runExecute() 단일 세트 종료(통계검증 실행, GB 1개) — 30315~30336행:
     30321 `_mvSyncRunLockedControls()` → 30333 `btn.innerHTML = '▶ 통계검증 실행'`
  4) _runExecutePlanSets() 다중 세트 종료(GB 2개 이상 — **이번 재현이 실제로 탄 경로**,
     STATUS_CD+DEPT_CD 2축) — 30136~30167행:
     30144 `_mvSyncRunLockedControls()` → 30166 `btn.innerHTML = '▶ 통계검증 실행'`

즉 "실행 종료"라는 사건 자체는 정상 처리되지만, 잠금 CSS 클래스를 실제 최종 상태(스피너 제거
후)로 다시 계산하는 호출이 빠져 있다. 이 프로젝트의 COMBO 픽스처는 항상 GB 2개(STATUS_CD+
DEPT_CD)가 기본추천이라 4번 경로를 타고, 통계검증을 한 번이라도 실행하면 그 순간부터 3단계의
모든 후보 체크박스·조합검증 체크박스(#gbIncludePair)·목적지 WHERE(#tgtWhere)·관리컬럼 확정
버튼(.mv-adm-ovr-btn 등, 모두 같은 CSS 선택자 대상)이 재분석/재로드 전까지 클릭 불가 상태가
된다(단, opacity:0.5로 흐리게 보이므로 완전히 무징후는 아니다 — 화면을 자세히 보면 후보표가
옅게 흐려져 있다).

3. 판정
────────────────────────────────────────────────────────────
(b) 진짜 결함이다. 의도된 설계(주석이 명시)는 "실행 중에만 잠근다"인데, 종료 처리 함수 4곳
모두에서 "잠금 재계산"과 "버튼 스피너 제거(=사실상 실행 종료를 알리는 마지막 신호)" 순서가
뒤바뀌어 있어 실행이 끝나도 잠금이 stale하게 유지된다. 사용자에게 이 상태가 화면에 안내되지도
않는다(체크박스가 옅게 흐려지고 커서가 not-allowed로 바뀌는 것 외에는 별도 배너·툴팁 없음 —
클릭이 왜 안 먹히는지 설명이 없다). Playwright가 "Clicking the checkbox did not change its
state"로 자가진단한 것도 이 결함의 정확한 증상이다(클릭은 갔지만 pointer-events:none이라 체크박스가
이벤트를 받지 못해 checked가 안 바뀜).

4. 대응 방향(제안 — 이번 작업 범위 아님, 코드 미수정)
────────────────────────────────────────────────────────────
새 상태·새 판정 로직 없이, 위 4개 지점에서 "버튼 스피너 제거" 다음 줄에
`_mvSyncRunLockedControls()` 재호출을 한 번씩 추가(또는 기존 재계산 호출을 버튼 스피너 제거
다음으로 옮기는 순서 교정)하면 될 것으로 판단된다 — 판정 함수(`_mvAnyRunActive`)나 CSS는 그대로
두고 "언제 재계산을 부르는가"만 고친다. 4곳이 동일한 순서 결함을 공유하므로 한 번에 같이 고치는
편이 회귀 검증도 단순하다(각 경로 종료 후 `document.body.classList.contains('mv-run-locked')`가
false인지 실측 확인). 영향 범위는 "그 클래스가 잠그는 selector 전부"(GB/SUM 후보 체크박스,
#gbIncludePair, #tgtWhere, 관리컬럼 확정/범위 버튼)로, 통계검증을 한 번이라도 실행한 뒤의
모든 3단계 재선택 흐름이 대상이다 — 파급 범위가 좁지 않으므로 수정 후 3단계 재선택 흐름
전반(단일축/다중축, COUNT만 실행하고 멈춘 경우, SQL만 생성하고 멈춘 경우 등)을 함께 재검증할
필요가 있다.
