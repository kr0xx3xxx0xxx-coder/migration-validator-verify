■ 0. 착수 전 사전검토(CLAUDE.md 기능/구조 변경 응답 형식)

  - 요청 요약 : 지금까지 127.0.0.1:8000 로컬 전용으로만 개발해온 도구를 다른 장비에 설치하고
    사용자가 그 장비의 실제 네트워크 IP 로 접속하는 구조로 배포할 때, 어디에 127.0.0.1/localhost/
    고정 IP 가 박혀 있어 접속 불가 또는 조용한 API 실패가 나는지 전수 조사. 조사만 수행했고
    코드는 한 줄도 바꾸지 않았다.

  - 긍정적 효과 : (조사로 확인된 것) 예상보다 결과가 훨씬 좋다. 배포를 실제로 막는 지점은
    uvicorn.run(host=...) 단 2곳뿐이고, 흔히 가장 많이 터지는 축인 "프론트엔드가 절대 URL 로
    API 를 부르는 문제"가 이 프로젝트에는 0건이다(fetch 213건 전수 확인, 아래 2절). CORS·쿠키·

    즉 "코드 2줄 + 방화벽 + 인증 확인"으로 배포가 성립하는 상태다.

  - 구조적 문제점 : 바인딩 주소가 리터럴이라 배포 때마다 소스를 고쳐야 한다. 이 코드베이스는

    두 개라 한쪽만 고치고 배포하면 일괄검증 독립 실행만 조용히 접속 불가가 된다 — 놓치기 쉬운
    비대칭이다.

  - 운영상 위험 : 최대 위험은 "접속 불가"가 아니라 그 반대다. 현재 루프백 고정이 사실상 유일한

      "주의: Basic Auth 자격증명은 평문 인코딩(base64)으로 전송된다. 신뢰할 수 없는 네트워크로
       개방한다면 리버스 프록시(nginx 등) TLS 종단 또는 사설망/VPN 을 함께 쓴다."

    이번 조사로 확인된 "얼마나 가까워졌는가" :
      - 현재 이 위험은 잠재 상태다. 이유는 오직 하나 — 루프백 바인딩이 외부 노출을 물리적으로
        막고 있기 때문이다. 인증 계층에는 평문 노출을 막는 장치가 전혀 없다(TLS 관련 배선 0건 :
        uvicorn ssl_keyfile/ssl_certfile 인자 없음, HTTPS 리다이렉트 없음, HSTS 없음).
      - 즉 1절의 수정(host → 0.0.0.0)은 단순한 배포 설정 변경이 아니라, 그 자체가 평문 노출을
        실제로 개방하는 스위치다. 방어선이 2겹에서 0겹이 되는 것이 아니라, 1겹(루프백)에서
        0겹으로 가는 것이다.
      - 노출되는 것 : 로그인 자격증명(base64), 그리고 이 도구가 다루는 내용 전체 — DB 접속정보
        입력 폼, 실행 SQL, 불일치 레코드 원문(운영 데이터 실값). 동일 사내망 내 패킷 캡처로
        전부 평문 판독 가능하다. 자격증명보다 후자의 노출량이 더 크다.
      - 완화 요인 : (a) 인증은 fail-safe 하게 강제되고(3-3), (b) 배포 대상이 사내망이라면
        AUTH_SETUP.md 가 말한 "사설망" 조건에 부분적으로 해당한다.
      - 반드시 함께 확인할 것 : MV_AUTH_DISABLED 가 운영 장비 환경에 남아 있으면 인증이 통째로
        우회된다(middleware.py:40-45, AUTH_SETUP.md 4절). 이 변수는 pytest 하니스가 쓰는 값이라
        개발 장비 환경변수에 남아있을 가능성이 있다 — 배포 체크리스트 필수 항목.
