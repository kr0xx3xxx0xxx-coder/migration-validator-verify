1. 배경과 문제
--------------------------------------------------------------------------------
STATS-VALIDATION-CHUNKED-VS-SINGLE-TRADEOFF-DIAGNOSE 진단의 4순위 권고 항목이다.
개별검증 4단계(통계검증 SQL 실행)에는 EXECUTE_STATEMENT_TIMEOUT_MS = 60,000ms 상한이
있는 반면, 2단계 COUNT 비교 SQL 을 실행하는 services/db_query_service.py 의
_cmn_db_fetch_count() 에는 timeout 인자 자체가 없었다. 즉 COUNT 는 무제한이었다.

이 비대칭이 실제로 위험한 이유는 두 가지다.

첫째, COUNT 는 4단계보다 먼저 실행되는 '사전검증'이라 사용자가 대량 테이블을 걸었을 때
가장 먼저 오래 붙잡히는 지점이다. /count 는 sync 함수라 FastAPI threadpool 워커를 점유하며,
브라우저가 이탈해도 서버는 쿼리를 끝까지 수행한다(취소 경로 없음). 상한이 없으면 워커가
쿼리 완주 시점까지 무기한 묶인다.

둘째, 상한이 없다는 사실이 문서(docs/STATS_VALIDATION_CHUNKED_VS_SINGLE_TRADEOFF.md
2-1절)에만 적혀 있고 코드에는 아무 방어가 없어서, DB 서버측 statement_timeout 이
0(무제한)인 내부망 환경에서는 어떤 계층도 이 쿼리를 끊지 못했다.


2. 원인 — 두 겹이었다
--------------------------------------------------------------------------------
(가) 1차 원인: _cmn_db_fetch_count() 가 커서를 열고 바로 execute 만 한다. 같은 파일의
     _cmn_db_fetch_all() 은 statement_timeout_ms 를 받아 어댑터에 위임하는데 COUNT 만
     그 배선이 없었다. 단순 누락이다.

(나) 2차 원인(작업 중 발견): request_connection_scope 안에서 연결은 _NoCloseConn 프록시로
     감싸져 재사용된다. 이 프록시는 __getattr__(읽기)만 실제 연결로 위임하고 __setattr__
     (쓰기)는 위임하지 않았다. PostgreSQL 은 커서로 SET statement_timeout 을 실행하므로
     영향이 없지만, Oracle 어댑터는 conn.call_timeout = ms 로 '속성 대입'을 한다.
     따라서 scope 안에서는 Oracle timeout 이 프록시 객체에만 붙고 실제 연결에는 닿지 않아
     조용히 무효가 되었다. 이 갭은 이번 COUNT 뿐 아니라 기존 _cmn_db_fetch_all 의 Oracle
     timeout 에도 동일하게 존재했다.


3. 조치 내용 (services/db_query_service.py 단일 파일)
--------------------------------------------------------------------------------
(1) COUNT_STATEMENT_TIMEOUT_MS 상수 추가
    env MV_COUNT_STATEMENT_TIMEOUT_MS 로 주입, 미설정 시 60000.
    4단계의 EXECUTE_STATEMENT_TIMEOUT_MS(env MV_EXECUTE_STATEMENT_TIMEOUT_MS, 기본 60000)와
    같은 형태·같은 기본값이다. 새 설정 체계를 만들지 않았다.

(2) _cmn_db_fetch_count(db_info, sql, *, statement_timeout_ms=None)
    커서 생성 직후 get_adapter(db_type).apply_query_timeout(conn, cur, budget) 로 위임한다.
    DBMS 분기는 어댑터에 캡슐화되어 있으므로 이 파일에는 방언 분기가 늘지 않는다
    (PostgreSQL=SET statement_timeout, Oracle=call_timeout, MySQL/MariaDB/MSSQL 은
    각 어댑터 구현을 그대로 따른다). 초과 시 드라이버 예외가 그대로 올라가
    count_common_service 의 기존 실행오류 경로(status=ERROR, count_error_code=EXEC_ERROR)로
    처리된다 — 새 결과 상태값을 만들지 않았다.

(3) _restore_scope_query_timeout() 추가 — finally 에서 호출
    PostgreSQL 의 SET statement_timeout 은 세션 단위, Oracle 의 call_timeout 은 연결 단위라
    scope 안에서 재사용되는 연결에 COUNT 의 상한이 그대로 남는다. 그러면 같은 scope 의 후속
    analyze/profile 쿼리가 COUNT 의 60초를 물려받아 오탐 취소된다(COUNT-EXEC-TIMEOUT-
    LARGE-TABLE-DIAGNOSE 에서 이미 겪은 유형의 사고다). 그래서 COUNT 종료 시 연결을 scope
    기준값(_req_conn.stmt_timeout_ms, 없으면 0=무제한)으로 되돌린다.

(4) _NoCloseConn.__setattr__ 위임 추가
    2-(나) 갭 해소. 속성 쓰기도 실제 연결로 위임한다.


4. 값 선택 — 왜 4단계와 같은 60초인가 (실측 근거)
--------------------------------------------------------------------------------
지시에 따라 "4단계와 같은 60초" 와 "COUNT 는 빠르니 더 짧게" 를 실측으로 비교했다.

  · 정상적인(문제 없는) 대용량 COUNT 도 수십 초가 걸린다.
    내부망 PostgreSQL mvbench.bench_30m(3,000만 행 / 3.7GB) 의 단순 COUNT(*) 실측:
    19.4초 · 22.7초 · 22.6초 · 23.5초 · 24.6초 (반복 측정). 즉 20초대가 '정상'이다.
    상한을 30초로 잡으면 마진이 20% 남짓이라 캐시 콜드/동시부하에서 정상 COUNT 가
    오탐 취소된다. 이 도구의 대상은 이관 검증이라 억 단위 원본도 정상 범주다.

  · 반대로 60초보다 크게 잡을 이유도 없다. COUNT 는 같은 테이블에 대한 GROUP BY 집계
    (4단계)보다 항상 가벼우므로, COUNT 가 60초를 넘겼다면 뒤따르는 통계검증은 확실히
    60초 상한에 걸린다. COUNT 상한을 통계검증보다 크게 두면 "COUNT 는 통과했는데
    통계검증은 어차피 못 하는" 무의미한 대기만 늘어난다.

  → 하한(정상 20초대 COUNT 보호)과 상한(통계검증 60초 초과분은 무의미) 양쪽에서
    60초가 타당하다. 결과적으로 4단계와 같은 값이며, 이것이 곧 지시된 'parity' 다.
    더 짧은 값이 필요한 환경(예: 대화형 응답성 우선)은 env 로만 조정한다.

6. 알려진 한계 · 잔여 과제 (이번 범위 밖)
--------------------------------------------------------------------------------
(1) 오류 문구가 부정확하다. count_common_service.categorize_conn_error 는 메시지에
    'timeout' 이 있으면 무조건 "연결 시간 초과" 로 분류한다. 실제로는 '연결'이 아니라
    '쿼리 실행 시간 초과'다. 사용자는 접속 문제로 오인할 수 있다.
    이번 지시가 db_query_service.py 단일 파일 수정이라 손대지 않았다.
    → 별도 작업 권고: 쿼리 timeout 전용 분류/문구 분리.

(2) stats_execute_service.py:41 주석이 "COUNT 사전검증(_cmn_db_fetch_count, timeout 인자
    없음)" 이라고 적혀 있어 이제 사실과 다르다. docs/STATS_VALIDATION_CHUNKED_VS_SINGLE_
    TRADEOFF.md 2-1 표의 "2단계 COUNT 비교 SQL = 없음" 행도 마찬가지다. 문서/주석 동기화 필요.

(3) MySQL/MariaDB/MSSQL 은 어댑터의 apply_query_timeout 구현에 전적으로 의존한다.
    본 작업 중 타 세션이 DIALECT-TIMEOUT-NOOP-FIX 로 이 세 어댑터에 실제 구현을 넣고 있어
    (작업 트리 미커밋 상태) COUNT 도 자동으로 그 구현을 따라간다. 세 방언 실 DB 발화 검증은
    그 작업의 범위다. 이번 실측은 PostgreSQL·Oracle 두 방언으로 수행했다.

(4) timeout 이 걸려도 서버측 쿼리는 취소 신호를 보낼 뿐이고, /count 요청 자체는 여전히
    취소 토큰(CancelToken)을 쓰지 않는다. 즉 브라우저 이탈 시 즉시 중단은 아니고
    '최대 60초 후 해제'가 된다. 구조적 취소는 별도 과제다.

(5) UI 변경 없음. 백엔드 실행 상한만 추가했으므로 화면 캡처 증적은 없다.
    2단계 화면에는 기존 COUNT 실행오류 표시 경로가 그대로 쓰인다.
