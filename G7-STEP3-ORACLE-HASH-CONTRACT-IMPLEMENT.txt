2. E1~E18 전수 대응표 구현 여부 (design.md §1 기준)
════════════════════════════════════════════════════════════════════════
  E1  md5(x) → LOWER(RAWTOHEX(STANDARD_HASH(x,'MD5')))          구현(h32)         실측 일치 확인(§4)
  E2  left(h,8) → SUBSTR(h,1,8)                                  구현(h32)         실측 '90015098' 확인 안함(§4 전체식으로 대체 확인)
  E3  'x'||hex8 (제거)                                            불필요(설계대로 미구현)
  E4  ::bit(32) → TO_NUMBER(hex8,'XXXXXXXX')                     구현(h32)         실측 4294967295류 벡터 일치(§4)
  E5  ::bigint (불필요)                                           불필요(TO_NUMBER 결과가 NUMBER)
  E6  괄호                                                        구현(canon_component, e="("+expr+")")
  E7a (expr)::numeric (불필요)                                    불필요(TO_CHAR가 숫자 직접 수신)
  E7b trim_scale → TO_CHAR(x,'TM9')                               구현(canon_component NUMBER 분기)
  E7c 선행0 복원 regex                                            구현(REGEXP_REPLACE 2단)
  E8  DATE_TIME → TO_CHAR(CAST(x AS TIMESTAMP),'…FF6')            구현(ORA-01821 회피, §4 실측 확인)
  E9  TEXT → TO_CHAR(x)                                           구현
  E10 CASE WHEN…NULL 마커                                         구현(길이/NULL 뼈대 Base 상속 아님 — canon_component 자체에 내장, PG와 동일 구조)
  E11a LENGTH(val)                                                구현
  E11b TO_CHAR(LENGTH(val),'TM9')                                 구현(부호자리 혼입 방지)
  E11c '<tag>:'||…||':'||val                                      구현
  E12 키 canonical || 결합                                        구현(Base.key_canonical 상속)
  E13 키+비교 canonical || 결합                                   구현(Base.row_canonical 상속)
  E14 salt||canonical                                             구현(bucket_expr)
  E15 & → BITAND                                                  구현, 실측 확인(§4)
  E16 _H32 재사용                                                 구현(key_hash_expr/row_hash_expr, Base 상속)
  E17 sum(h32) (strategy 계층, 이번 파일 범위 아님)                해당 없음(hash_bucket.py가 이미 contract.key_hash_expr 등을 sum()으로 감쌈 — 무수정)
  E18 별칭 개명 (phase①에서 이미 완료)                             해당 없음(이번 파일 범위 아님)

  R3(NLS_NUMERIC_CHARACTERS)  → nlsparam 3인자로 식 자체에 고정   구현, 실측: 세션 NLS를 ', '로 바꿔도
                                                                   canon_component(12.5,NUMBER) 그대로 'D:4:12.5' 확인
  R4(VARCHAR2 4000자 상한)    → precheck() 구성요소 개수 상한(20, 잠정치)로 방어
                                 [비판적 검토] 실제 바이트 길이는 컬럼 데이터에 의존해 SQL 표현식 문자열만으로는
                                 정확히 알 수 없음 — "개수 상한"은 근사 방어일 뿐이며, 큰 TEXT 컬럼 1~2개만으로도
                                 실제 4000자를 넘는 조합이 이 방어를 통과할 수 있음. design.md도 "라이브 테스트로
                                 임계 실측"을 요구했고, 이번 단계는 라이브 실측을 하지 않았으므로(스코프 밖) 20이라는
                                 값은 검증된 임계가 아니라 "상한 존재" 골격만 갖춘 잠정치임을 명시한다. 실제 임계
                                 보정은 G7 diagnose §5-2-7이 지시한 별도 라이브 검증 작업으로 넘긴다.
  R5(LOB, STANDARD_HASH 거부) → 능동 감지 미구현(열린 지점, diagnose §2-4가 이미 이렇게 결론)
                                 [비판적 검토] precheck(exprs, compare_exprs) 시그니처가 SQL 표현식 문자열만
                                 받고 컬럼 타입/길이 메타를 받지 않아 이 파일 단독으로는 LOB 여부를 판별할 수
                                 없다. build_hash_bucket_agg_sql 시그니처 확장(컬럼 메타 관통 전달)이 필요하며
                                 이는 ④ 소비측 배선의 확장 범위이지 이번 ③ 신규 파일 범위가 아니다. 현재는
                                 F1-G7 §5-2-(4)의 상위 불변조건("LOB은 MATCH_KEY/HASH_COMPARE 후보 경로에
                                 오지 않는다")에 의존한다 — 이 불변조건이 깨지면 STANDARD_HASH가 ORA-00902로
                                 즉시(조용하지 않게) 실패하므로 거짓 일치는 아니지만, 사전 HOLD로 걸러지지도
                                 않는다는 잔여 위험을 다음 단계 담당자에게 명시적으로 인계한다.

3. 오라클 라이브 실측 (Oracle_asis 프리셋, 192.168.0.151:1523/xepdb1, 읽기전용 SELECT ... FROM DUAL만 사용)
════════════════════════════════════════════════════════════════════════
db_presets_src.json의 Oracle_asis 프리셋으로 실제 오라클에 접속해 DUAL 조회로 표현식을 직접 실행했다
(단위테스트는 DB 없이 문자열만 고정하므로, "실제로 그 SQL이 오라클에서 문법 오류 없이 실행되고 값이
설계 문서 벡터와 일치하는가"는 별도 실측이 필요 — 이 부분을 수행했다).

  [1] STANDARD_HASH RAWTOHEX vs PG md5('abc')
      오라클: 900150983cd24fb0d6963f7d28e17f72
      PG(python md5): 900150983cd24fb0d6963f7d28e17f72
      → 일치 (E1 근거 확인)

  [2] h32 실측 vs design.md §1.1 벡터표 (5건 전부 일치)
      'S:3:abc'                              -> 3276922494  (기대 3276922494)  일치
      'S#N'                                  -> 10499643    (기대 10499643)    일치
      'D:4:12.5'                             -> 584801104   (기대 584801104)   일치
      'T:26:2026-07-26T00:00:00.000000'      -> 1817468297  (기대 1817468297)  일치
      'hbw1S:3:abc'(salt)                    -> 976348671   (기대 976348671)   일치

  [3] bucket_expr(BITAND) 실측
      bucket('S:3:abc', 128)  -> 126  (기대 126)  일치
      bucket('S#N', 128)      -> 59   (기대 59)   일치

  [4] canon_component 실측(문법 실행 가능성 + 값 확인)
      canon_component(0.5, NUMBER)   -> D:3:0.5    (선행0 복원 확인)
      canon_component(-0.5, NUMBER)  -> D:4:-0.5   (선행0 복원 확인)
      canon_component(NULL, NUMBER)  -> D#N
      canon_component('', TEXT)      -> S#N        (오라클 빈문자열=NULL 발산, design §2.2가 예고한 그대로)
      canon_component(SYSDATE, DATE_TIME)                 -> T:26:2026-08-07T20:16:23.000000
      canon_component(TO_DATE 리터럴(DATE형), DATE_TIME)    -> T:26:2026-07-26T00:00:00.000000
                                                             (ORA-01821 없이 정상 실행 — E8 CAST AS TIMESTAMP 회피 확인)

  [5] R3 방어 실측 — 세션 NLS_NUMERIC_CHARACTERS를 ', '(콤마 소수점)로 바꾼 뒤 재실행
      canon_component(12.5, NUMBER) -> D:4:12.5  (세션 NLS와 무관하게 불변 — nlsparam 고정 방어 확인)

  결론: E1~E18 중 구현 대상 전부, R3, DATE_TIME(ORA-01821 회피) 모두 실측으로 확인됨.
        R4/R5는 §2의 비판적 검토대로 이번 단계에서는 골격만(정확한 임계·능동감지는 후속 과제).
