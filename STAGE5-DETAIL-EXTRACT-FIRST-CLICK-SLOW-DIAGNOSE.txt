[조사 범위]
- 코드: ui/tabler_renderer.py(그룹 클릭 핸들러 _mvStage5OpenGroup/_mvPkEnsurePrepared),
  routes/agg_diff_route.py(POST /agg-diff/prepare), services/exact_diff/agg_contribution.py
  (pk_index_fingerprint)
- 실측 근거: scripts/dev_e2e/_scatter50m_measure.log · _scatter50m_scaling_compare.json
  (2026-08-01, MV_SCATTER50M 5,000만행 픽스처, 실 브라우저 클릭스루 기록 — 코드 추정이 아닌
  이미 저장돼 있던 실측 로그)
- 코드 수정 없음, 신규 실행도 하지 않음(기존 저장된 실측 산출물만 사용)

[1] R01 "상세추출"이 실제로 하는 일
  routes/agg_diff_route.py:1271~1293 — 그룹 클릭 시 scope(col/val 쌍)를 받아 원본/목적 SQL
  양쪽에 "WHERE 그룹조건" 을 pushdown 한 뒤(같은 함수 내에서) fingerprint를 계산한다
  (agg_diff_route.py:1352, pk_index_fingerprint는 src_sql/tgt_sql 문자열을 그대로 해시에 포함
  — agg_contribution.py:76~93). 즉 그룹마다 SQL이 달라지므로 fingerprint도 그룹마다 다르고,
  서버는 그룹별로 별개의 job/run_id/store를 새로 만든다.
  ⇒ "R01 클릭 시 전체(또는 더 넓은 범위) 사전계산이 함께 돈다"는 구조가 아니다.
     앱 코드 상으로는 R01 스코프만 스캔하는 게 맞다.

[2] 다음 그룹(R02 등)이 왜 거의 즉시 나오는가
  클라이언트 캐시(_mvPkEnsurePrepared, tabler_renderer.py:17579~17610)와 서버 fingerprint
  캐시(_JOBS_BY_FP/_PK_RUNS) 둘 다 "scope가 같을 때만" 재사용한다(scopeKey 불일치 시
  즉시 폐기 — tabler_renderer.py:17590~17591). R02는 R01과 scope가 다르므로 이 두 캐시
  어느 쪽도 R01의 결과를 R02에 재사용하지 않는다 — 즉 "앱이 R01 때 만든 걸 R02가 몰래
  재사용"하는 코드 경로는 없다(코드로 배제됨).

  대신 이미 저장돼 있던 실측 로그(같은 50,000,000행 픽스처, 같은 코드 경로)에서 동일 패턴이
  그대로 재현돼 있었다:
    4단계 처리시간(변형 d_union) exec_wall_sec = 17.42s  ← 사용자 보고값과 정확히 일치
    드릴다운 1회차(그룹 G01, 서로 다른 그룹 조건) : 35.11~81.56s (변형별)
      - 서버측 "재이관 수집" 실제 소요만 24.2~70.7s (준비확인 자체는 9.5~11.4s, 나머지는
        서버 job 폴링 대기)
    드릴다운 2·3회차(그룹 G02, G03 — 실제로 다른 그룹, 반복클릭 아님) : 6개 SQL 변형
      전부 예외 없이 0.41~0.43s, 준비확인 0~1ms
  ⇒ 그룹이 달라져도(=fingerprint가 달라져도) 2번째부터는 일관되게 즉시 응답 — 이는
     "앱이 R01 결과를 재사용해서"가 아니라(코드로 배제) "R01(첫 스캔)이 그 테이블의
     데이터 블록을 디스크에서 물리적으로 읽어들이는 비용을 이미 치른 뒤라, 그룹 컬럼에
     인덱스가 없어 사실상 넓은 범위를 훑어야 하는 이후 스캔들이 DB/OS 버퍼캐시(웜 캐시)
     적중으로 사실상 메모리 조회가 되기 때문"으로 보는 것이 가장 설명력이 높다.
     (Oracle V$ 대기이벤트/물리읽기 수치까지 직접 추적하지는 않았음 — 아래 [불확실성] 참고)

[3] 실측 근거(로그·타임스탬프, 코드 추정 아님)
  파일: scripts/dev_e2e/_scatter50m_measure.log (2026-08-01 실행분, 6개 SQL 형태 a~f 반복)
  변형별 [드릴다운1 wall] → [드릴다운2 wall] → [드릴다운3 wall]:
    a_simple  54.46s → 0.42s → 0.42s
    b_inner   39.36s → 0.42s → 0.42s
    c_outer   41.42s → 0.42s → 0.41s
    d_union   64.85s → 0.42s → 0.41s   (4단계=17.42s, 사용자 보고값과 정확 일치)
    e_cte     35.11s → 0.43s → 0.42s
    f_complex 81.56s → 0.42s → 0.42s
  6개 변형 모두에서 "1회차만 수십 초, 2·3회차는 항상 0.4초대"가 예외 없이 재현됨.

[4] 결론
  - "23.22초가 R01 하나만의 순수 작업 시간이 맞는가" → 예. 앱이 R01 클릭에 전체/광역
    사전계산을 얹어서 그 시간을 R01에 잘못 귀속시키는 구조는 아니다(코드로 확인 — scope
    pushdown이 fingerprint 계산 이전에 적용되어 그룹별 독립 job).
  - 다만 그 23초의 대부분은 "R01이라는 그룹의 본질적 특성"(예: R01만 데이터가 유독 많음)
    때문이 아니라, 그 세션에서 R01이 "해당 테이블에 대한 첫 스캔"이었기 때문일 가능성이
    실측 로그상 가장 유력하다 — 로그에서 그룹 값이 매번 다른데도 2·3번째는 SQL 형태
    6종 전부 균일하게 0.4초대였다는 점이, "그룹별 데이터량 차이" 가설보다 "콜드→웜 캐시"
    가설을 더 강하게 지지한다. 즉 사용자가 R02를 먼저 열었다면 R02가 23초, 이후 R01이
    빨랐을 것으로 추정된다.

[불확실성 / 후속 확인 여지]
  - 사용자가 실제로 본 정확한 수치(23.22초/R01)는 위 저장 로그의 리터럴 값과 100% 동일하지
    않음(로그는 그룹축 STATUS_CD/G01, 4단계 17.42초만 정확 일치) — 같은 코드경로·같은 규모의
    "재현 사례"로 제시하는 것이며 사용자 화면의 그 세션 자체를 되짚은 것은 아님.
  - "웜 캐시" 설명은 Oracle V$SESSION_EVENT/물리읽기 카운터 등 DB엔진 레벨 계측까지는
    하지 않아 100% 확정은 아니다(코드가 앱 차원 캐시 재사용을 하지 않는다는 것은 확정,
    그 이상의 근본 메커니즘은 정황 근거).
