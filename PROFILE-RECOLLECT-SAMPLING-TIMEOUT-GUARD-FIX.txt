0. 결론 요약
════════════════════════════════════════════════════════════════════════════════
백로그 P2(진단서 LARGE-DATA-SORT-EXPOSURE-DIAGNOSE §4 / §5 A-3) 대로,
후보추천 profile 재수집 경로의 무제한 COUNT(DISTINCT) 전체 스캔에
3단계 후보추천 profile 이 이미 쓰는 방어를 **그대로 재사용**해 적용했다.

  ① 표본  : SAMPLE_SRC(_SAMPLE_LIMIT = 50,000행) CTE — services/column_profile_service 재사용
  ② 상한  : statement timeout 15,000ms — 동일 어댑터 경로(apply_query_timeout) 위임
  ③ scope : side 전용 WHERE 절 제한(호출부가 줄 때만 · 원본 조건의 목적지 누수 금지)
  ④ 근거  : 표본이 실제로 잘린 경우에만 '표본 5만행 기준' 표기 저장(조용한 과소추정 방지)
  ⑤ 컬럼 상한 30 은 요구대로 그대로 유지 — 새 샘플링 로직 신설 0건

실측 결과(요약) — 42M×8컬럼은 20분 상한에서도 못 끝나던 것이 0.24초가 됐다.

  대상                                     before        after      비율
  ───────────────────────────────────────  ───────────   ────────   ────────
  asis01.t_as_n_etl01  42,000,024행 × 8컬럼  >1200s(취소)   0.24s     측정불가(>5000배)
  mvbench.bench_30m    30,000,000행 × 3컬럼    64.13s       0.06s     x1069
  ntb.gt_budget_ledger     38,000행 × 8컬럼     0.86s       0.66s     동일 수준(무회귀)

추가로, 이 경로에서 **고유값 수집이 PostgreSQL 에서 사실상 항상 조용히 실패하고 있던
선행 결함**을 실측으로 발견해 같은 파일 안에서 함께 해소했다(§5).

1. 수정 내용 (services/profile_recollect_service.py — 지정된 이 파일만)
════════════════════════════════════════════════════════════════════════════════
[1-1] _sampling_guard() 신설 — 3단계 자산 재사용 chokepoint
      services/column_profile_service 의 _SAMPLE_LIMIT(50,000) /
      _PROFILE_STATEMENT_TIMEOUT_MS(15,000) / _build_sample_cte_select 를 그대로 가져온다.
      → 상수를 복제하지 않으므로 3단계 값이 바뀌면 재수집도 같이 바뀐다(단일 출처).
      → import 실패 시 (None,None,None) 을 돌려 **수집을 생략**한다. 무제한 스캔으로
        되돌아가는 폴백은 두지 않았다(이 방어의 존재 이유가 사라지므로).

[1-2] _build_sampled_distinct_sql() — 3단계 _build_join_profile_sql 과 동형 구조

      before(수정 전):
        SELECT COUNT(*) AS pr_rc, COUNT(DISTINCT "c1") AS pr_d0, ... FROM "schema"."table"

      after(수정 후):
        WITH SRC AS (
          SELECT "c1", "c2", ...
          FROM "schema"."table"
          [WHERE <side 전용 조건>]
        ),
        SAMPLE_SRC AS (
          SELECT * FROM SRC LIMIT 50000        ← _build_sample_cte_select(방언 위임)
        )
        SELECT COUNT(*) AS pr_rc, COUNT(DISTINCT "c1") AS pr_d0, ...
        FROM SAMPLE_SRC

      별칭 'pr_' 문자 시작 컨벤션(ORA-00911 회피)은 그대로 유지했다.

[1-3] statement timeout — get_adapter(dialect).apply_query_timeout(conn, cur, 15000)
      3단계 profile 과 동일한 어댑터 경로. 미지원 방언은 조용히 건너뛴다(비치명적).

[1-4] WHERE scope 제한
      _collect_distinct_counts(..., where_clause=...) 파라미터 추가.
      _recollect_one_side 는 side 전용 키만 읽는다 —
        source → target["src_where_clause"] / target → target["tgt_where_clause"]
      (원본 조건을 목적지에 복사하지 않는다. 현행 호출부는 이 키를 주지 않으므로 동작 불변.)
      _sanitize_where(): 선행 'WHERE' 제거, 세미콜론 포함 시 통째 폐기(다중문 주입 차단).

[1-5] 표본 근거 표기 — '표본 5만행 기준'
      판정: 수집행수(rc) >= 표본 상한(50,000) 일 때만 '표본 절단'으로 본다.
        · rc < 50,000 → 표본 = 전수이므로 값이 정확 → 표기 없음(기존과 완전 동일한 dict)
        · rc >= 50,000 → 표본 기반 → 근거 표기 부착
      저장 위치(재수집 snapshot 의 column_profiles / column_profiles_json):
        "sampled": true, "sample_limit": 50000,
        "distinct_basis": "표본 5만행 기준", "row_count_basis": "표본 5만행 기준"
      row_count 도 표본 건수이므로 함께 표기한다.

[1-6] 컬럼 상한(max_cols=30) — 변경 없음(요구사항 4).

   "30M×8컬럼 158초"와 같은 부하 형태다. 이 PostgreSQL 인스턴스에서는 158초가 아니라
   **20분 상한을 넘겨 취소**됐다(취소 시점까지 병렬 워커 3개가 계속 물려 있었다 —

   측정치이므로, 절대값은 인스턴스마다 다르고 **노출의 크기는 진단서보다 크다**.
 · bench_30m 은 30M행 규모의 직접 대조군이다. 64.13초 → 0.06초(x1069).
 · 진단서 외삽(30컬럼이면 500초 이상)은 이제 컬럼 수와 무관하게 표본 5만행으로 상한된다.

5. 부수 발견 및 함께 처리 — 고유값 수집이 PG 에서 조용히 전멸하고 있었다
════════════════════════════════════════════════════════════════════════════════
현상 : 재수집 실경로에서 고유값 수집 결과가 항상 0컬럼이고
       _last_error = "테이블 식별자 해소 실패(information_schema 미발견)" 로 남았다.
원인 : _recollect_one_side 는 MetaCollector().collect() 를 먼저 호출한다. MetaCollector 의
       샘플 조회(_fetch_samples)는 **스키마 미한정** `SELECT ... FROM <table> LIMIT 100` 을
       발행하고, 대상 테이블이 search_path 밖 스키마(예: ntb, asis01)면 실패한다.
       MetaCollector 는 이 예외를 삼키지만(except: pass), PostgreSQL 트랜잭션은 abort 상태로
       남아 **같은 커넥션의 이후 모든 쿼리가 InFailedSqlTransaction 으로 죽는다**.
       그래서 뒤따르는 information_schema 조회와 distinct 쿼리가 통째로 실패했다.
       (실측 재현: search_path = "$user", public / 대상 스키마 ntb → relation does not exist
        → 직후 information_schema 조회가 InFailedSqlTransaction)
조치 : distinct 수집 직전 conn.rollback() (SELECT 전용 경로라 되돌릴 변경 없음, 실패해도 무시).
       수정 대상 파일(services/profile_recollect_service.py) 안에서만 처리했다.
영향 : 이 조치로 고유값 수집이 실제로 **처음 동작**하게 되므로, 표본/타임아웃 방어가
       먼저 들어간 지금 순서로 적용하는 것이 맞다(방어 없이 먼저 살렸다면 §2 의 20분 스캔이
       그대로 발화했을 것이다).

7. 남는 위험 / 후속 필요
════════════════════════════════════════════════════════════════════════════════
 · [표시 배선 미완] '표본 5만행 기준'은 snapshot 의 column_profiles(_json)와 재수집 반환
   자료구조에 저장되지만, 화면 렌더러는 아직 이 키를 읽지 않는다
   (get_profile_stats_from_snapshot 이 고정 5개 키로 평탄화하며 추가 키를 버린다).
   → UI 노출은 ui/ 및 services/profile_snapshot_service.py 수정이 필요해 이번 범위
     ("이 파일만 수정") 밖이다. **후속 작업 필요**로 명시한다.

   스키마 미한정 SELECT)는 그대로 남아 있다. rollback 으로 후속 쿼리 오염만 차단했다.
   → 별도 작업 필요(파일 범위 밖).
