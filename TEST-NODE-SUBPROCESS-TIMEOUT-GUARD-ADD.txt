3. 구현
════════════════════════════════════════════════════════════════════════════
【tests/node_timeout_guard.py (신규)】
  · NODE_SUBPROCESS_TIMEOUT — 기본 60초, env MV_TEST_NODE_TIMEOUT 로 조정
  · run_node_guarded(cmd, **kw) — 호출부에서 명시적으로 쓰는 헬퍼. subprocess.run 과
    인자·반환값이 같아 기존 호출을 그대로 옮길 수 있다.
  · _guarded_run — subprocess.run 래퍼. **node 실행이면서 timeout 이 없을 때만** 상한을
    주입한다. node 아닌 호출(python·git 등)과 이미 timeout 을 명시한 141곳은 원본 동작 그대로.
  · install_node_subprocess_timeout_guard() — 설치. 중복 설치는 무시.

【tests/conftest.py】
  pytest_configure 에서 가드 설치. 기존 '운영 SQLite 쓰기 차단 가드'와 동일한 패턴·위치라
  구조가 새로 복잡해지지 않는다. 실서버 실행에는 영향 없다(conftest 는 pytest 에서만 로드).

【멈췄던 3개 파일】 subprocess.run → run_node_guarded 로 명시 전환(4곳)
  호출부만 봐도 보호 사실이 드러나고, pytest 밖에서 직접 실행할 때도 보호된다.

【상한값 60초 근거】
  이미 timeout 이 있는 141곳의 관행값이 30초이고 그 값으로 문제없이 통과해 왔다. 동시 세션이
  여러 개 도는 개발 PC 의 부하 여유를 위해 2배인 60초로 두되, 무한루프가 26시간이 아니라
  1분 안에 명확한 실패로 끝나게 한다. 느린 환경은 env 로 조정한다.

【실패 메시지 — 조용히 죽지 않는다】
  [NODE-SUBPROCESS-TIMEOUT] node 실행이 상한 60초를 초과해 강제 종료했습니다.
    명령: node C:\...\tmpXXXX.harness.js C:\...\tmpYYYY.asm.js
    원인: harness JS 가 끝나지 않았을 가능성이 높습니다(무한루프/대기).
    조치: 해당 harness 의 종료 조건을 확인하세요. 상한 조정은 env MV_TEST_NODE_TIMEOUT(초).
  subprocess.run 은 만료 시 자식을 kill 하므로, '고아 node 가 CPU 를 계속 태우는' 2차 피해도
  함께 막힌다(오늘 멈춘 3건 모두 자식 node 가 코어를 100% 점유 중이었다).

4. 검증
════════════════════════════════════════════════════════════════════════════
【4-1 가드 자체 계약 테스트 — 신규 8건 전부 통과】 tests/test_node_timeout_guard.py
  ① 무한루프 JS(`while(true){}`)가 상한에서 강제 종료되고, 메시지에 명령·초과시간이 담긴다
  ② timeout 미지정 node 호출에 기본 상한이 실제로 주입된다
  ③ 정상 node 실행은 결과가 기존과 동일하다(회귀 없음)
  ④ 호출부가 명시한 timeout 은 덮어쓰지 않는다(기존 141곳 계약 무변경)
  ⑤ node 아닌 서브프로세스에는 상한을 주입하지 않는다
  ⑥ 명령 판정 규칙(리스트/문자열/절대경로/.exe)
  ⑦ 기본 상한이 무한이 아니고 합리적 범위다
  ⑧ 가드 설치 후 모듈 reload 해도 재귀하지 않는다

  ★ 구현 중 실제 결함 1건을 이 테스트가 잡았다: 최초 구현은 `_REAL_RUN = subprocess.run` 을
    import 시점에 잡아뒀는데, 가드가 이미 설치된 상태에서 모듈이 reload 되면 **가드가 가드를
    감싸 RecursionError** 가 났다. 원본을 가드 함수에 보관해 되찾도록 수정하고 ⑧로 고정했다.
