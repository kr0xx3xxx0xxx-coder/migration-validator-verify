■ 1. 이번 작업이 무엇을 고쳤나

ROUTES-DIAGNOSIS-LIMIT-DIALECT-SECONDARY-CHECK 가 P1 으로 확정한 대로,
routes/count_gate_route.py 한 파일 안에 서로 다른 4개의 결함 계열이 겹쳐 있었고, 그 결과
COUNT 게이트의 후속 진단 3개 엔드포인트가 오라클에서 통째로 무력화돼 있었다.

  · POST /count-gate/range-diagnosis   (범위 이상 진단 §28~§30)
  · POST /count-gate/one-side-preview  (한쪽 0 대표 레코드 §19·§20)
  · POST /count-gate/one-side-export   (한쪽 0 전체 CSV §19·§20·§53)

네 계열은 각각 다음과 같다.

  (1) L56 방언 미위임
      resolve_confirmed_chunk_key() 를 dialect 인자 없이 호출했다. 이 함수의 기본값은
      'postgres' 라서, 오라클 접속이어도 내부 contract/NULL probe 가 PostgreSQL 문법으로
      렌더된다. probe 가 실패하면 CHUNK_KEY 가 확정되지 않고(match_key.confirmed=False),
      확정 전제로만 실행되는 '대표 키 상/하위' 조회가 통째로 생략된다. 즉 이 결함 하나만으로도
      진단 결과의 절반이 조용히 비게 된다.

  (2) 서브쿼리 별칭 '__cg' 7곳
      오라클의 비인용(unquoted) 식별자는 문자로 시작해야 한다. '__cg' 는 규칙 위반이라
      ORA-00911 로 문장 자체가 깨진다. COUNT·MIN/MAX·대표 키·미리보기·CSV 등 이 파일이
      만드는 거의 모든 SQL 에 이 별칭이 붙어 있었다.

  (3) L95/98/136 LIMIT 하드코딩
      'LIMIT n' 은 PostgreSQL/MySQL 문법이다. 오라클은 FETCH FIRST n ROWS ONLY,
      MSSQL 은 TOP (n) 접두를 써야 한다. 오라클에서는 ORA-03049 로 실패한다.

  (4) L163/164 psycopg2 전용 서버 커서 API
      CSV 스트리밍이 real.cursor(name=...) + cur.itersize 로 구현돼 있었다. 이는 psycopg2
      고유 API 로, oracledb 커서에는 name 인자 자체가 없어 오라클에서는 SQL 을 보내보기도 전에
      TypeError 로 깨진다.

■ 2. 어떻게 고쳤나 — 새 패턴을 만들지 않고 기존 위임 구조에 얹었다

(1) 방언 전달
    _routing_dialect(req) 헬퍼를 추가했다. 도출 방식은 이미 같은 결함을 해소한
    routes/diagnosis_route.py 의 동명 헬퍼와 동일하다 — 공통 매핑
    services.sql_dependency_pruning._to_sqlglot_dialect 를 재사용하고, src/tgt 방언이 다르면
    (혼합 방언은 상위 하드게이트가 차단한다) 기존 기본값 'postgres' 를 그대로 둔다.
    피호출 함수(resolve_confirmed_chunk_key 등)는 한 줄도 건드리지 않았다 — 배선만 했다.

(2) 별칭 개명
    '__cg' 7곳을 모듈 상수 SUBQUERY_ALIAS = "cg1" 로 통일했다. 문자로 시작하므로 4개 방언
    모두에서 유효하고, 상수 하나라 다음에 또 흩어질 여지가 없다.

(3) 행 제한
    지시는 sample_route.py 의 3분기 패턴을 재사용하라는 것이었는데, 실제로는 그보다
    한 단계 위의 기존 패턴을 썼다. 이유를 밝혀 둔다.
      · sample_route 의 오라클 분기는 WHERE ROWNUM <= n 이다. 이 구문은 ORDER BY 가 없을 때만
        옳다. ROWNUM 은 정렬 '전'에 매겨지므로, 대표 키 조회(L95/98)처럼 ORDER BY 1 이 붙은
        자리에 그대로 쓰면 '아무 5건을 뽑아 정렬'하게 되어 결과가 조용히 틀린다.
        문법 오류가 아니라 오답이 나오는 쪽이라 더 위험하다.
      · 그래서 프로젝트에 이미 있는 dialect 위임(services.dialects 의 row_limit_suffix /
        row_limit_top_prefix)을 썼다. count_diagnostic_sql_service.py 와
        column_profile_service.py 가 쓰는 바로 그 패턴이며, 새로 발명한 것이 아니다.
        오라클은 FETCH FIRST(정렬 후 상위 n 을 보장), MSSQL 은 TOP 접두, PG/MySQL 은 LIMIT 이
        자동으로 나온다. CLAUDE.md 의 '4개 방언 모두 처리' 규칙도 분기 없이 충족된다.
    조립은 _limited_select() 한 함수에 모았다.

(4) 스트리밍
    HOLD 로 도망가지 않고 오라클도 실제로 지원하도록 고쳤다. oracledb 커서는 arraysize 단위로
    서버에서 배치 fetch 하므로, cursor() + arraysize + fetchmany 만으로 psycopg2 named cursor 와
    동등한 스트리밍이 된다(전량 메모리 적재 없음). read-only 도 공통 실행 경로와 같은 방식
    (SET TRANSACTION READ ONLY)으로 강제했다. 즉 이번 지시의 "대안이 크면 HOLD" 예외는
    쓰지 않았다 — 대안이 크지 않았기 때문이다.
    다만 read-only 보장과 스트리밍 등가성을 확인하지 못한 mysql/mssql/db2 는 정직하게 막았다.
    reason_code = EXPORT_DIALECT_UNSUPPORTED 로 JSON 응답을 돌려준다. 이 판정은 반드시
    StreamingResponse 를 반환하기 '전'에 한다 — 스트림이 시작된 뒤에는 오류를 JSON 으로 알릴
    방법이 없어 브라우저에 빈 CSV 가 내려가기 때문이다.

■ 3. 가드 공백을 함께 메웠다 (지시 5)

진단서가 지적한 대로, 기존 정적 회귀 테스트
tests/test_underscore_alias_oracle_regression_static.py 는 services/ 만 훑고 routes/ 는 보지
않았다. 그런데 범위만 넓혀서는 이번 결함을 여전히 못 잡는다. 검출기가 `AS _x` 형태만 보고
있었는데, count_gate 의 '__cg' 는 `FROM (…) __cg` 처럼 AS 가 없는 테이블 별칭 위치였기
때문이다. 게다가 f-string 은 조각으로 쪼개지면 별칭과 SELECT 가 서로 다른 Constant 로 흩어져
문맥 판정마저 실패한다. 그래서 세 가지를 함께 넓혔다.

  · 스캔 범위: services/ + routes/  (_SCAN_DIRS)
  · 검출기 D3: `) _x` (AS 생략형 서브쿼리/테이블 별칭)
  · f-string(JoinedStr) 템플릿 복원 후 검사

효과는 실제로 확인했다. git 에서 수정 전 파일을 꺼내 새 스캐너로 훑으니 '__cg' 가 잡혔고,
수정 후 파일은 깨끗하다.

    수정 전 count_gate_route.py 스캔: ['__cg']
    수정 후 count_gate_route.py 스캔: (없음)

범위를 넓히자 그동안 안 보이던 것 세 가지가 새로 드러났고, 전부 분류해 상태를 고정했다.

  · routes/agg_diff_route.py 의 '__m'  → KNOWN_ORACLE_UNSAFE (오라클 도달·미수정)
      rename 매핑 해소용 재래핑 별칭인데, 이 SQL 이 resolve_confirmed_match_key 로
      dialect=오라클 가능 상태로 넘어간다. 같은 파일 L565 독스트링도 이미 "'__m' 이
      ORA-00911 을 유발한다"고 적고 있다. 수정은 agg_diff_route 소관이라 이번 작업 범위
      (count_gate_route.py 만 수정)에서 제외하고 상태만 고정했다 — 별도 작업 권고.
  · services/exact_diff/agg_contribution.py 의 '__agg', '__sc' → KNOWN_DIALECT_SCOPED
      같은 파일의 기존 분류 항목과 동일 계열의 PostgreSQL 전용 경로다('__sc' 는 ::text
      캐스팅을 동반해 PG 전용임이 코드상 명시적).

회귀 가드 테스트 3개도 추가했다: routes/ 가 실제로 스캔되는지, count_gate_route.py 에 밑줄
별칭이 다시 들어오지 않았는지, D3 검출기가 무력화되지 않았는지.

[4-2] Before / After — 오라클 방출 SQL

  BEFORE (commit f54c957) : 오라클 위험 판정 12건 / dialect 전달값 = (미전달)

    SELECT (ORDER_ID) FROM (…) __cg ORDER BY 1 LIMIT 5             → ORA-00911 + ORA-03049

[4-3] PostgreSQL 회귀 없음

  PG 방출 SQL 은 별칭 이름(__cg → cg1)을 빼면 BEFORE 와 문자열이 동일하다. 별칭은 SQL 의미에
  영향이 없다(어디에서도 참조되지 않는 서브쿼리 별칭). LIMIT 절도 그대로 'LIMIT n' 이고,
  export 도 여전히 named cursor + itersize 경로를 탄다 — 즉 PG 경로는 실질 무변경이다.
  MySQL 도 LIMIT 유지, MSSQL 은 TOP (n) 으로 정상 전환된다.

      (누수 위험). 이번엔 손대지 않았다 — 별도 판단 사안으로 남긴다.

  (d) 비판적 검토: 이번 변경은 heuristic 을 늘리지 않았고(방언 분기를 라우트에 새로 만들지

      114줄 증가했지만 그중 상당수가 결함 배경 주석과 위임 헬퍼다. explainability 측면에서는
