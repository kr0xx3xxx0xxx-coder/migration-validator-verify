작업명 : SMALL-SYNC-VS-LARGE-ASYNC-EXTRACT-PATH-DIFFERENCE-DIAGNOSE
✅ 작업 완료 - 소규모/동기 vs 대규모/비동기 상세추출 경로 분기 기준·진입점·화면 구분성·설계 이유·오늘 사례를 코드 근거로 확인(코드 수정 없음)

────────────────────────────────────────────────────────────
1. 갈리는 기준(정확한 조건)
────────────────────────────────────────────────────────────
"전략 종류"나 "버튼 종류"가 직접 기준이 아니라, 다음 단일 조건이다.

  useStream = (totalRows > detail_stream_min_rows)

  - totalRows      : 그룹 scope(window._mvPkScope.col)가 있으면 "그 그룹의 원본 COUNT"
                      (_scope.rows), 없으면 "테이블 전체 원본 COUNT"(_lastCountResult.src_count)
  - detail_stream_min_rows : 서버 정책 단일 출처, 기본값 50,000행
                      (services/strategy/strategy_transition.py:36 DEFAULT_TRANSITION)

계산 위치(클라이언트, JS): ui/tabler_renderer.py:17683-17691 (_mvPkPayload 내부)
  - 정책 미도착 시에도 동일 기본값(50000)으로 안전 폴백
  - 이 useStream 값이 그대로 POST /agg-diff/prepare 요청 바디의 stream: bool 필드가 된다
    (routes/agg_diff_route.py:509-522 PkPrepareRequest.stream, 기본 False)
  - 서버는 이 stream 값을 그대로 신뢰한다 — 서버 자체의 독립 재검증 로직 없음
    (routes/agg_diff_route.py 안에서 req.stream 참조는 1368 라인 단 1곳)

즉 "행수 임계값(기본 5만) 초과 여부"가 유일한 분기 기준이며, 그 행수는 "전체 실행이면 테이블
전체 COUNT, 그룹 드릴다운이면 그 그룹만의 COUNT"로 해석된다(뒤 §4 참고 — 원래는 테이블 전체
기준이었다가 그룹 단위로 좁혀진 이력이 있음).

부수적으로 stream=True 이면 compare_strategy도 함께 'PK_RANGE_CHUNK_COMPARE'로 세팅되지만
(ui/tabler_renderer.py:17714), 이는 useStream 판정의 "결과"이지 별도 분기 기준이 아니다.

2. 각 경로의 정확한 진입점
────────────────────────────────────────────────────────────
공통 엔드포인트: POST /agg-diff/prepare (routes/agg_diff_route.py:1272 agg_diff_prepare,
                 request model PkPrepareRequest)

[소규모/동기] stream=False
  agg_diff_route.py:1511  →  prepare_reimport_pk_index(...) 호출 시 store= 인자를 넘기지 않음
  services/exact_diff/agg_contribution.py:178  def prepare_reimport_pk_index(...)
    - 원본/목적 SQL을 ThreadPoolExecutor로 동시에 "한 번에 fetch"(라인 214-225, fetchall 방식)
    - 라인 247: store = store if store is not None else default_exact_diff_store(False)
      → ExactDiffRunStore(memory=True) — 프로세스 내 in-memory SQLite, 서버 재시작 시 소멸

[대규모/비동기] stream=True
  agg_diff_route.py:1368  if req.stream: ...  →  rj.start_or_attach(run_fn=_run_fn, ...)
    _run_fn(job) (agg_diff_route.py:1427) 내부 분기:
      (a) req.compare_strategy=='PK_RANGE_CHUNK_COMPARE' (useStream=True 면 항상 이 값)
          → _run_pk_range_chunk(...) (agg_diff_route.py:247)
          → services.exact_diff.pk_range_chunk.run_pk_range_chunk_compare(
               store=default_exact_diff_store(True), ...)  (agg_diff_route.py:385)
      (b) 그 외 → prepare_reimport_pk_index_stream(...) (agg_contribution.py:439)
          → store=default_exact_diff_store(True) 명시 전달 (agg_diff_route.py:1448)
    두 경로 모두 default_exact_diff_store(True) → ExactDiffRunStore(memory=False)
      → db/exact_diff_runs.db 파일에 run_id 기준 영속 저장(재시작 후도 조회 가능)
    엔진은 서버측 커서로 배치 단위 스트리밍 append(services/exact_diff/store.py:6 주석 —
      "메모리 전체 적재 금지"), PK_RANGE_CHUNK는 chunk_checkpoint로 재개(resume)도 지원.

정리: 저장소 선택은 services/exact_diff/store.py:615 default_exact_diff_store(persist: bool)
      한 곳으로 수렴하며, persist 인자에 True/False를 넘기는 것은 오직 위 두 호출 경로뿐이다.

3. 화면에서 "지금 어느 경로인지" 구분 가능한가
────────────────────────────────────────────────────────────
결론: 전체(비그룹) 추출에서는 구분 가능하지만, 그룹 드릴다운(오늘 문제된 그 케이스)에서는
      화면에 어떤 지표도 없다 — 사용자는 알 수 없다.

- 전체 추출 화면에는 "_pathHtml"(ui/tabler_renderer.py:28630-28639)이
  "실행경로 <b>{execution_path}</b> · 전략 <code>{actual_strategy_id}</code>
  (· chunk {chunk_size})" 및 "계획≠실행" 불일치 경고까지 표시된다.
  단, 이 줄은 head += _pathHtml (28641)에서 "!_inlineGrp" 조건일 때만 붙는다.

- 그룹 드릴다운에서는 _inlineGrp = !!(window._mvPkScope && window._mvPkScope.col) 가
  true가 되어(28499) 위 조건이 거짓이 되므로 _pathHtml 자체가 렌더되지 않는다(28641).
  → 실행경로/전략/chunk 배지, 계획≠실행 경고 모두 그룹 단위에서는 화면에 없음.

- 유일한 간접 단서: "세부 성능정보"(접힌 <details>) 안에서 tm.source_chunk_read_seconds나
  tm.chunks_total 값이 존재할 때만 "— PK_RANGE_CHUNK 단계 —" 소제목과 chunk 수/크기 행이
  추가로 나타난다(28683-28694). 이 값이 아예 없으면 청크(대규모/비동기)가 아니었다는 뜻이지만,
  ① 접힌 절을 사용자가 직접 펼쳐야 하고 ② "메모리 저장이라 재시작 시 사라진다"는 직접적
  경고 문구는 어디에도 없다.

────────────────────────────────────────────────────────────
4. 왜 이렇게 두 경로로 설계됐는가
────────────────────────────────────────────────────────────
services/exact_diff/store.py:9-12 헤더 주석(저장 정책 §5)은 다음과 같이 설명한다:
  "test-only(그룹 미선택): 프로세스 공유 in-memory ... 세션 종료 시 자동 폐기.
   공식(그룹 실행): db/exact_diff_runs.db 파일에 영속."
→ 그러나 실제 분기 트리거는 "그룹 선택 여부"가 아니라 "req.stream(행수 임계값 초과 여부)"이다.
  즉 이 헤더 주석은 실제 코드 분기 기준과 어긋나 있다 — "그룹 실행"이라도 그 그룹 행수가
  임계값(5만) 이하면 여전히 in-memory로 빠진다(오늘 STAGE5-CARD-REMOVE-ITEM24 검증에서 실측된
  바로 그 현상). 코드 수정 지시가 아니므로 고치지 않았고, 사실 확인만 남긴다.

실질적 설계 근거(주석 인용 기반):
  - TASK34 §2·§9(ui/tabler_renderer.py:17668-17669): "대량(원본 COUNT 큰 경우)은
    merge-join 스트리밍 준비를 요청한다(fetchall 없이 서버측 named cursor로 비교·bulk
    저장). 임계값 이하 소량은 기존 해시 경로 유지." → 성능/메모리 이유: 큰 결과셋을
    프로세스 메모리에 한 번에 fetchall 하지 않기 위해 배치 스트리밍 저장이 필요하고
    (store.py:6 "엔진이 발견 즉시 배치 단위로 append(메모리 전체 적재 금지)"), 이 배치
    저장은 안정적 재조회·재개(resume)를 전제로 하므로 파일 영속이어야 한다.
  - PK_RANGE_CHUNK 경로는 chunk_checkpoint로 일시중지·재개(resume=true)를 지원한다
    (agg_diff_route.py 주석 "[Phase4-D4 §1] checkpoint 시작/갱신/종료"). 재개는 서버
    재시작 이후에도 이어져야 하므로 파일 영속이 필수 전제조건이다.
  - 반대로 소량 경로(prepare_reimport_pk_index)는 스레드풀로 원본/목적을 한 번에 fetch해
    끝내는 단발성 계산(agg_contribution.py:214-225)이라 재개 개념이 없고, 저장은 페이지
    재조회용 캐시 성격뿐이다 — 파일에 영속시켜야 할 강한 이유가 코드/커밋 코멘트에
    명시적으로 남아있지는 않지만(추정), "test-only 소규모 캐시라 매번 새로 만들어도 무해"
    라는 판단으로 보인다.
  - STAGE5-GROUP-DRILLDOWN-ARCHITECTURE 3항 주석(ui/tabler_renderer.py:17671-17674):
    원래는 테이블 전체 COUNT 기준으로만 useStream을 판단했는데, "테이블 전체가 5만을
    넘는다는 이유만으로 수백 행짜리 그룹까지 stream/PK청크 경로로 몰면 그룹 하나 여는 데
    오히려 더 오래 걸린다"는 이유로 그룹 scope가 있으면 그 그룹의 COUNT로 판단 기준을
    좁혔다 — 이것이 "같은 테이블 안에서도 그룹마다 저장 방식이 갈리는" 오늘 현상의 직접
    원인이다.

5. 오늘 실제 사례(MV_SCATTER50M, 5천만행) 적용 결과
────────────────────────────────────────────────────────────
[확인 결과] db/exact_diff_runs.db 최근 레코드, scripts/dev_e2e 산출물, scratchpad 어디에서도
오늘 날짜(2026-08-12)로 MV_SCATTER50M을 그룹 드릴다운(POST /agg-diff/prepare)에 직접 실행한
실측 로그는 찾지 못했다. 오늘 실행된 STAGE5-CARD-REMOVE-ITEM24-AND-PER-GROUP-STORAGE-VERIFY
검증 스크립트(scripts/dev_e2e/stage5_card_item24_remove_and_pergroup_storage_verify.py)는
NXDNP.MV_COMBO_SRC/TGT(조합축 STATUS_CD+DEPT_CD, 실불일치 4그룹)를 사용했으며, 그 스크립트
자체 주석(191-193줄)에 "이 스크립트가 거친 경로는 소규모 동기이며 default_exact_diff_store
(False) in-memory 라 파일에 없는 게 정상"이라고 명시돼 있다 — 즉 오늘 실제로 클릭·검증된
4개 그룹은 전부 in-memory(소규모/동기) 경로였다(파일 DB 미기록이 오류가 아니라 정상 동작).

MV_SCATTER50M에 대해서는 실측 대신 코드/픽스처 정의 근거로 답한다:
  scripts/dev_e2e/scatter50m_fixture_build.py가 정의하는 MV_SCATTER50M_SRC는 STATUS_CD 기준
  G01~G10 10개 그룹으로 나뉘고, 각 그룹은 정확히 5,000,000행(50,000,000 / 10)으로 완전
  균등하다(STATUS_CD = 'G'||LPAD(TRUNC(g/100) MOD 10 + 1,2,'0') 산식이 1000-g 주기마다
  10개 코드를 균등 순환시킴 — 라인 28,138). 임계값(detail_stream_min_rows) 기본 50,000행
  대비 각 그룹은 100배 초과한다.

  → 결론: "몇 번째 그룹부터"가 아니라, 처음 클릭하는 그룹(1번째, G01)부터 이미 예외 없이
    대규모/비동기(스트리밍 또는 PK_RANGE_CHUNK) 경로를 타며, 10개 그룹 전부가 파일영속
    (db/exact_diff_runs.db)으로 저장된다. 이 픽스처 구조상 그룹 단위로 in-memory(소규모/
    동기) 경로가 나타날 조건 자체가 존재하지 않는다(모든 그룹이 임계값을 큰 폭으로 초과).
