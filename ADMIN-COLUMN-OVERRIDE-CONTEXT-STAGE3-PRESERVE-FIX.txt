0. 한 줄 결론
════════════════════════════════════════════════════════════════════════
3단계 후보 재확정이 서버로 project_id/table_key 를 보내지 않아 관리컬럼 확정 컨텍스트가
빈 값으로 덮이던 4단 배선 공백을 모두 이었다. 실 DB + 실제 브라우저 + 실제 마우스 클릭으로
수정 전(버튼 disabled 재현) / 수정 후(버튼 활성 유지 + 확정→해제 전 과정 동작)를 각각 실측했다.

1. 배경 — 무엇이 왜 깨졌나
════════════════════════════════════════════════════════════════════════
선행 진단서(E:\verify_reports\ADMIN-COLUMN-OVERRIDE-BUTTON-STILL-DISABLED-WITH-
PROJECT-SELECTED-DIAGNOSE.txt §3/§4)가 확정한 인과는 다음과 같다.

  [1] 1단계 /analyze 는 project_id 를 정상 전달 → 후보에 ctx{project_id:'957',
      table_key:'MV_ORA_DEMO_TGT'} 부착 → 관리컬럼 확정 버튼 활성.
  [2] 3단계 후보 계산은 POST /validation-sets/preview 를 호출하는데, 이 요청은
      project_id 를 아예 싣지 않는다.
  [3] 서버가 authoritative 재확정(_maybe_finalize_postcount → enrich_candidates_for_display)
      을 project_id 없이 다시 돌리면서 후보의 admin_column_override_context 를
      {project_id:'', table_key:'', project_id_present:false} 로 무조건 덮는다.
  [4] 클라이언트는 그 authoritative 후보로 all_groupby_candidates 를 통째 교체하고
      후보표를 재렌더 → 버튼이 disabled 로 되돌아간다.

즉 '프로젝트를 안 골라서'가 아니라 **정상 순서(1→2→3단계)로 진행하는 행위 자체가
프로젝트 컨텍스트를 지우는** 결함이었다. 실사용에서는 거의 항상 발생한다.

파급의 실제 모습도 진단서가 정정해 두었다: override 값은 setdefault 로 보존되고 ctx 만
덮이므로 **확정 배지는 남고 [확정 해제] 버튼만 비활성**이 된다 — 한 번 확정하면 그
화면에서는 되돌릴 수 없다.

2. 수정 내용 — 4단 배선(요청→스키마→라우트→서비스)
════════════════════════════════════════════════════════════════════════
새 상태를 만들지 않았다. 1단계 analyze 가 이미 쓰는 소스를 그대로 재사용한다.

■ ① ui/validation_plan_renderer.py — 요청 본문에 조회 키 동봉
  공통 헬퍼 _previewOverrideKeyFields(ad) 를 기존 _previewSrcConnFields() 옆에 신설:
      project_id -> mvGetWorkProjectId()        (tabler_renderer.py 의 /analyze 요청과 동일)
      table_key  -> parse_result.tgt_table      (서버 analyze 의 override_table_key 와 동일 값)
  typeof 가드로 함수 부재 시에도 빈 문자열을 반환한다(하니스/부분 로드 안전).

  ★ 지침이 지목한 871-885행(_refreshValidationPlanWithRowCount) 외에,
    **같은 파일의 두 번째 호출부 _refreshVspOnCheckChange('선택 적용 후 다시 검증' 경로)도
    같은 엔드포인트를 타므로 함께 배선**했다. 여기를 빼면 체크박스를 한 번만 건드려도
    버튼이 다시 죽어 수정이 무의미해진다(실측 S5 로 확인).

■ ② schemas/request_models.py — ValidationSetPreviewRequest
      project_id: str | None = None
      table_key:  str | None = None
  둘 다 선택. 미전달이면 기존과 완전히 동일하게 동작한다(다른 호출부 무영향).
  타입은 이 파일의 기존 관례(project_id: str | None = None, 7곳)를 따랐다.

■ ③ routes/validation_set_preview_route.py — 재확정 서비스로 전달
      project_id=(req.project_id or ""), override_table_key=_tbl_key
  _tbl_key 는 req.table_key 우선, 없으면 parse_result.tgt_table / target_table 폴백.
  폴백을 둔 이유: 확정 저장 키는 '프로젝트 × 테이블 × 컬럼' 3축이라 테이블 축이
  analyze 와 어긋나면 확정이 조회되지 않는다. analyze 는 서버에서 tgt_table 을 쓰므로
  같은 출처로 수렴시켜 두 경로의 키가 문자열까지 동일해지게 했다.

■ ④ services/candidate_postcount_finalize.py — enrich 재실행에 키 전달
  finalize_recommendation_postcount() 에 project_id / override_table_key 키워드 추가,
  ③ 단계의 enrich_candidates_for_display 호출에 그대로 넘긴다
  (single_validation_analyze_service.py:1614-1615 와 동일 패턴 재사용).

■ 이번 범위 밖(지침대로 손대지 않음)
  services/validation_job_core.py:314(원클릭/전체검증), services/batch_runner.py:139(일괄검증),
  services/column_candidate_gen_service.py:845 의 같은 미배선 — 별도 백로그(F36 등).
  disabled 사유 화면 노출(M34) 도 별도 항목.

7. 비판적 검토
════════════════════════════════════════════════════════════════════════
