(1) 3안 재검토 근거와 확정 설계
────────────────────────────────────────────────────────────────────────
선행 진단서 2건의 3안을 오늘 시점에서 재평가했다.

  [옵션 A] 화면만(경과시간 카운트업 · 추정 진행바 · '세트 i/N' 표시)
     → 이미 적용됨(SINGLE-STEP4-EXEC-STATUS-DISPLAY-IMPLEMENT, #mvExecStepProgress 실재 확인).
       그러나 A 는 "요청이 끝날 때까지 브라우저가 붙어 있어야 한다"는 전제를 못 깬다.
       지시의 핵심 요구(브라우저를 닫아도 서버가 계속 실행)는 A 로 달성 불가 → 단독 채택 불가.
  [옵션 B] 서버 단계명 신호(원본/목적/비교 구간 표시)
     → 진단 실측상 서버 총 처리시간이 0.6~1.7초(25만행)였기에 '실익 작음'으로 보류됐었다.
       그러나 이번 5,000만행 실측에서는 /execute 왕복이 14.07초였다. 실익이 커진 것은 맞지만,
       얻는 것은 여전히 %가 아니라 '단계명'이고 상태 저장소가 1개 더 늘어난다.
       비동기 job 화(Phase 0)를 하면 job 상태 저장소가 이미 생기므로 B 는 그 위에 얹을 후속 과제로 남긴다.
  [옵션 C] 진짜 %(청크 분할)
     → 비채택 유지. 통계검증은 GROUP BY 집계 SQL 1문이라 완료 전 부분 결과가 존재하지 않는다.
       임의 형태 원본 SQL(CTE/JOIN/UNION)을 PK 범위로 감싸 N회 재실행하면 전체 스캔 N회 위험 +
       청크 키 부재 케이스가 실재한다. 가짜 %/추정 진행바는 만들지 않는다는 원칙 그대로 유지.

  ▶ 확정: 진단서 [설계안] Phase 0 — '4단계 실행의 비동기 job 화'를 **단일 세트 경로에 한해** 구현.
     · 선례 services/batch/wrapper_async_job.py(요청 스레드 즉시 반환 + 데몬 스레드 + thread_starter
       테스트 주입 + 환경변수→정책→기본값 3단 롤백 토글)를 그대로 본떴다.
     · job 저장소 TTL/evict 는 services/exact_diff/reimport_job.py 패턴을 따랐다.
     · 진행률은 만들지 않는다. 상태는 PENDING/RUNNING/COMPLETED/FAILED 4개뿐이고
       폴링은 '완료 여부 확인' 용도다(진단서 결론 그대로).
     · 5단계 자동 진입은 넣지 않았다 — 오늘 M56/M58 로 확정된 "5단계는 사용자가 명시적으로
       들어가야 시작" 원칙과 08c2119 '완료 후 자동 탭 이동 전면 제거' 정책을 그대로 지킨다.
       완료를 명확히 보여주고 [결과 보기] 버튼을 제공하는 데서 멈춘다(무성 전환 금지).

  ▶ 위험 판단(구현 강행 여부): workflow_stage_guard 의 begin/end 를 스레드 경계로 넘기는 것이
     안전한지 실제 코드를 읽고 판정했다. begin_execution 은 ctx_key 기준 marker 를 남기고
     end_execution 은 '자기 marker 일 때만' 해제하며, TTL 만료는 fail-open 방향이다.
     즉 해제 주체가 요청 스레드일 필요가 없고, 스레드 종료 finally 에서 해제해도 계약이 깨지지 않는다.
     다만 기본 TTL 180초는 '요청 1건 상한' 기준이라 장기 job 에는 짧아 먼저 만료될 수 있으므로
     job 전용 TTL(기본 3,600초)을 설정으로 분리해 넘겼다. → 근거 있는 안전 판단으로 구현 진행.

 ■ 프론트엔드 안전 설계(기존 상태머신 보호)
   · runExecute() 본문은 손대지 않았다 — 재클릭 방지·S16 409·M57 stale lock·세션버전·abort signal
     등 상호의존 가드가 밀집한 영역이라 분기 삽입 자체가 회귀 위험이다.
     대신 순수 판정/유틸 함수만 호출해 재사용했다(_singleExecGuard / _singleExecPreflight /
     _mvGateBlocked('stats')+_mvOfferStage3ForceProceed / _isRegenerateRequired /
     _mvBuildConnPayload / _buildCountContext / _mvSelectionMode).
   · 전역 네임스페이스 분리 — window._singleAsyncExecJobId / _singleAsyncExecPollTimer /
     _singleAsyncExecTickTimer / _singleAsyncExecState / _singleAsyncExecCtx 만 사용.
     _executeInProgress·_singleValidationExecuted·_singleLastExecResult 는 **읽기만** 하고,
     사용자가 [결과 보기]를 눌러 결과를 실제로 화면에 올린 시점에만 채운다
     (그래야 '검증 결과 확정 저장' 등 하위 기능이 정상 동작한다).
   · DOM 도 분리 — 4단계·상세비교가 공용해 충돌 이력이 있는 #executeOut/#mvExecStepResult/
     #mvExecStepError 를 재사용하지 않고 #mvAsyncExecStatus 를 새로 뒀다(4단계 pane 소속 등록).
   · 폴링 주기는 서버가 내려준 poll_interval_ms 를 그대로 쓴다(클라이언트 하드코딩 없음).
   · 탭 이탈 후 이어보기는 sessionStorage + 4단계 재진입 훅(_applySinglePane 의 validation 분기).
     새로고침으로 소멸하는 것은 진단서에서 이미 확인·수용된 한계이며 이번 범위 밖이다.
