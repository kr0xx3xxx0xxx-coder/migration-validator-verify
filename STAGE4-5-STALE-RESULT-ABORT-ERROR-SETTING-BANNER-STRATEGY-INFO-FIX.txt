2순위 — 3단계 중단 후 4단계 실행 시 원시 AbortError 노출 (버그, 원인 조사 완료)
────────────────────────────────────────────────────────────
원인: window._singleInflightAbort 컨트롤러가 재분석 시(§41 resetIndividualValidationWorkSession)
에만 새로 발급되고 runCount/runRevalidateFromCandidate/runGenerate/runExecute 는 그 signal을
재사용만 했다. 한 단계에서 '■ 중단'을 누르면 컨트롤러가 abort() 상태로 굳어, 재분석 없이 넘어간
다음 단계의 새 실행이 요청을 보내기도 전에 AbortError로 즉시 거부되고 원시 DOMException 문구
("signal is aborted without reason")가 alert에 그대로 노출됐다.
수정: ui/tabler_renderer.py — 실행이 확정되는 시점(모든 동기 가드 통과 직후)에 4개 함수
(runCount:15581, runRevalidateFromCandidate:16487, runGenerate:25051, runExecute:29703)
모두 _singleNewAbortSignal()로 새 컨트롤러 발급. runGenerate의 catch 블록(:25152)도
AbortError를 원시 메시지 대신 "이전 요청이 취소되어 SQL 생성이 중단되었습니다" 중립 안내로
처리, 진짜 오류(그 외 err)는 기존과 동일하게 alert('SQL 생성 오류: '+err.message) 유지.
검증(실 브라우저 PROBE — window.fetch를 실제 AbortError로 모킹한 뒤 실 runGenerate() 호출,
그 외 전부 실 코드): after 서버 — p2_dialogs_on_abort_error = []( 다이얼로그 없음, 원시노출 无).
before 서버(동일 시나리오) — p2_dialogs_on_abort_error = ["SQL 생성 오류: signal is aborted
without reason"](재현 성공, 원시 노출 확인). 컨트롤러 갱신 메커니즘 자체도 실측
(_mvSingleAbortRun 호출 후 aborted:true → _singleNewAbortSignal 호출 후 새 컨트롤러+
aborted:false, before/after 공통 동작 확인 — 메커니즘은 같고 "언제 새로 발급하는가"만 다름).
진짜 SQL 생성 오류가 여전히 alert로 뜨는지는 소스 레벨 테스트로 검증
(tests/test_stage_exec_stop_button_fix.py::test_run_generate_catch_handles_abort_error_not_raw_message
— catch 블록에서 AbortError 분기가 alert('SQL 생성 오류: '+err.message) 분기보다 먼저 나오고,
그 일반 오류 alert 라인 자체는 그대로 존재함을 소스 문자열로 확인). 이 부분은 실 DB 연동
없이는 진짜 SQL 문법오류를 라이브로 유발하기 어려워 대체(원인·범위는 위와 같이 명시).
