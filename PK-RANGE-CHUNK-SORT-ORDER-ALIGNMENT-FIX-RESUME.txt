────────────────────────────────────────────────────────────────────────
1. 무엇이 문제였나
────────────────────────────────────────────────────────────────────────

PK_RANGE_CHUNK 전략은 원본과 목적지를 같은 PK 구간으로 잘라 구간마다 merge-join 한다. 이 merge 는
"두 목록이 PK 오름차순으로 정렬되어 있다"를 전제로 하는데, 코드 어디에서도 그 전제를 확인하지
않았다. 그런데 청크 조회 SQL 은

    SELECT ... FROM (원본 SQL) Q0 WHERE Q0."키" >= :1 AND Q0."키" < :2 ORDER BY Q0."키"

이고, 바인드 값은 정수다. 키가 문자 컬럼이면 오라클의 암묵 형변환 때문에 WHERE 는 "숫자 의미"로
걸리는 반면 ORDER BY 는 "문자 정렬"로 나온다. 즉 구간에 담긴 행 집합은 정확한데 순서만 틀린 목록이
merge 로 들어간다. merge 는 키를 정수로 바꿔 비교하므로 비교 자체는 숫자로 하고, 순서만 어긋난 채
진행된다. 그 결과 실제로는 양쪽에 다 있는 행이 "원본에만 있음 / 목적에만 있음" 쌍으로 갈라져 대량
날조된다. 오류도 경고도 나지 않고 화면상 정상 완료(READY)로 끝난다는 점이 가장 나쁘다.

100만행 픽스처 실측에서는 참값 누락 10,000건짜리 데이터가 "재이관 대상 64,997건 + 목적 단독
54,998건"으로 보고됐다. 25만행 사례에서는 반대 방향(거짓 "일치")으로 나타났다. 방향은 데이터에
따라 갈리지만 성격은 같다 — 조용히 틀린 판정이다.

여기에 더해 경계 산정 자체도 어긋나 있었다. 청크 경계는 MIN/MAX 로 잡는데, 문자 키의 MIN/MAX 는
문자 정렬 결과다. 실제 최대가 1,000,000 인데 문자 MAX 는 '999999' 라서 상한을 넘는 행이 조회 대상에
아예 들어오지 못한다.


────────────────────────────────────────────────────────────────────────
2. 어떤 대응안을 골랐고, 왜 그렇게 골랐나
────────────────────────────────────────────────────────────────────────

지시가 준 선택지는 두 가지였다.

  A안 — 청크 조회의 정렬을 키의 "비교 의미"(숫자)와 일치시킨다.
  B안 — 문자 키는 PK_RANGE_CHUNK 진입 자체를 막고(HOLD) DIRECT_STREAM 으로 보낸다.

A안을 골랐다. 다만 A안을 문자 그대로 "ORDER BY 에 숫자 캐스트를 건다"로 구현하지 않고, merge 입력
경계에서 정렬을 보장하는 형태로 구현했다. 판단 근거를 순서대로 적는다.

첫째, B안은 이번 작업의 파일 제약 안에서 정직하게 구현할 수 없다. HOLD 판정을 내리는 주체는
routes/agg_diff_route.py 인데 그 파일은 이번 범위 밖이고 다른 세션이 만지고 있을 수 있었다. 엔진이나
방언 어댑터에서 예외를 던져 HOLD 를 흉내낼 수는 있지만, 그건 "에러는 raise 하지 말고 결과 객체에
담는다"는 프로젝트 규칙과도 어긋나고, 사용자에게는 HOLD 가 아니라 실행 실패로 보인다. 즉 B안은
범위 밖 파일을 건드려야만 제대로 완성되는 안이었다.

둘째, B안은 고칠 수 있는 것을 포기하는 안이다. 오늘 대조군으로 확인했듯 zero-pad 문자 키
(LPAD(...,7,'0'))는 문자 정렬 순서가 숫자 정렬과 일치해서 아무 문제 없이 정확한 결과를 낸다.
"문자 키면 무조건 차단"은 이런 정상 케이스까지 함께 막는다.

셋째, A안을 SQL 의 ORDER BY 에 캐스트를 거는 방식으로 구현하면 정상 경로가 망가진다. 이 전략의
존재 이유가 "전체 정렬 없이 좁은 구간을 PK 인덱스 순서로만 읽는 것"인데, 정렬식에 캐스트를 걸면
인덱스 순서를 쓸 수 없어 매 청크마다 정렬 연산이 새로 생긴다. 캐스트를 문자 키에만 선택적으로
걸려면 키의 실제 타입을 미리 알아야 하는데, 여기서 키는 임의 파생 SQL 의 출력 별칭이라 사전 판정이
어렵다.

넷째, merge 입력 경계에서 보장하면 위 문제가 전부 사라진다. 청크 행은 어차피 방언 어댑터가
fetchall 로 전량 메모리에 올려놓은 상태이므로 추가 DB 왕복이 0회다. SQL 은 한 글자도 바뀌지 않아
실행계획이 그대로다. 그리고 이 지점은 방언 중립이라 PostgreSQL·Oracle·앞으로 추가될 방언까지 한
번에 보장된다. 무엇보다 "정렬되어 있을 것"이라는 검증되지 않는 전제가 "정렬되어 있음을 보장한다"는
불변식으로 바뀐다.

축 A(경계 절단)도 함께 고쳤다. 지시는 이번 범위 밖이라고 했고 원한다면 근거를 밝히라고 했으므로
근거를 적는다. (1) 수정 대상이 허용된 두 방언 파일 안에서 끝난다. (2) 축 B 만 고치면 이번 픽스처
기준으로 참값 10,000건 중 1건이 여전히 조회 범위 밖이라 "정확히 10,000건"이라는 검증 기준을 채울 수
없다. (3) 무엇보다 두 결함의 뿌리가 같다 — 경계·필터·정렬·비교 네 곳이 같은 "숫자 비교 의미"를 써야
하는데 경계만 문자 의미로 남겨두면 원칙이 반쪽이 된다.

축 A 수정에는 안전 규칙을 뒀다. MIN/MAX 결과가 문자열일 때만(=키가 문자 컬럼일 때만) 숫자 의미로
다시 계산하고, 그마저도 전 행이 숫자로 변환될 때만 채택한다. 한 행이라도 변환 불가면 원래 문자
MIN/MAX 를 그대로 돌려줘서 기존 int() 게이트가 HOLD_NON_NUMERIC_PK 판정을 내리게 둔다. 경계를
조용히 좁혀 행을 누락시키는 일이 절대 없도록 한 것이다. 숫자 키는 이 분기를 아예 타지 않으므로
추가 쿼리가 0회이고 기존 실행계획도 그대로다(실측으로도 확인 — 아래 4절).

7. 남은 것 / 한계 (정직 고지)
────────────────────────────────────────────────────────────────────────

· PostgreSQL 은 라이브로 확인하지 못했다. PG 인스턴스(5433/5434)는 접속 불가, Neon 은 쿼터 소진
  상태였다. 축 B 수정은 방언 중립 지점(merge_chunk)에 있어 PG 에서도 동일하게 동작하며 단위
  테스트로 고정돼 있다. 축 A 의 PG 판(_pg_numeric_min_max)은 Oracle 판과 같은 계약으로 작성했지만
  라이브 실행은 하지 못했다 — 이 부분은 실측이 아니라 코드 대칭성에 근거한 것임을 밝힌다.

· 축 A 는 "전 행이 숫자로 변환 가능한 문자 키"까지만 해소한다. 숫자와 비숫자가 섞인 키는 여전히
  기존 동작(문자 MIN/MAX + int() 게이트)에 맡긴다. 경계를 조용히 좁히는 것보다 기존 동작을
  유지하는 쪽이 안전하다고 판단했다.

· 진단서가 지적한 다른 항목들은 이번 범위 밖으로 그대로 남아 있다 — 청크 불균형(값 범위 균등
  분할이라 행 수 균등이 아님), pushdown 불가 형태에서의 청크당 전체 정렬 재실행, PK 이상치 1건에
  의한 청크 폭증, 3단계 실행계획 카드의 pk_kind 하드코딩. 각각 별도 작업이 필요하다.

· 이번 재현·검증은 모두 "키를 명시 지정한" 경로다. HTTP 자동 경로는 문자 PK 를 chunk 키로 확정하지
  않으므로(네이티브 키 → DIRECT merge 강제 + int() 게이트) 자동 경로에서 곧바로 터지는 결함이라고
  주장하지 않는다. 다만 명시 지정 경로가 열려 있는 한 결함은 실재했고, 이번 수정으로 그 경로에서도
  조용히 틀린 판정이 나오지 않는다.

· asis/tobe 는 읽기 전용으로만 접근했다. 데이터 변경은 없다. 검증 run(PKSOAA*/PKSOAB*/PS50346785F3D2)
  이 exact_diff store 에 남는다.
