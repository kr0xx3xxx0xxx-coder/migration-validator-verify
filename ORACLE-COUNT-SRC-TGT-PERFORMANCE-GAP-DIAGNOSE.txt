작업명 : ORACLE-COUNT-SRC-TGT-PERFORMANCE-GAP-DIAGNOSE

조사일시 : 2026-08-05
조사범위 : 읽기 전용(SELECT / EXPLAIN PLAN / DBMS_XPLAN / v$·dba_* 조회)만 수행.
           INSERT/UPDATE/DELETE/DDL/DBMS_STATS/ALTER SYSTEM 일절 실행하지 않음.
대상     : NXDNP.MV_SCATTER50M_SRC (asis 192.168.0.151:1523/xepdb1, 5,000만행)
           NXDNP.MV_SCATTER50M_TGT (tobe 192.168.0.151:1524/xepdb1, 4,950만행)

════════════════════════════════════════════════════════════════════════════
■ 결론 요약 (먼저)
════════════════════════════════════════════════════════════════════════════
목적지 테이블 쪽에 **구조적 원인은 없다**. 실행계획·옵티마이저 통계·물리 저장구조
어느 축에서도 3~4배를 설명할 차이가 나오지 않았고, 오히려 목적지가 원본보다
**실제로 읽는 블록이 1.0% 더 적다**.

원인은 "테이블 속성"이 아니라 **호스트 공유 디스크의 I/O 상태(콜드 캐시 최초 1회 접근)**
이다. 근거는 아래 두 가지가 결정적이다.

  (1) 격차를 1회 재현하는 데 성공했으나(목적지 14.97초 vs 원본 2.67초),
      **바로 그 다음 실행에서 같은 SQL이 1.66초**로 떨어졌다. 테이블 속성이라면
      2회차도 느려야 한다.
  (2) 이후 순서를 뒤집고(목적지 먼저) 총 22회를 교차·병렬·순차 3조건으로 측정한 결과
      격차가 사라졌다. 중앙값 **원본 2.368초 / 목적지 2.325초** — 목적지가 더 빠르다.
      원본이 5.765초로 가장 느렸던 라운드도 나왔다.

대응 필요 없음. 특히 **통계 재수집(DBMS_STATS)은 효과가 없다** — 통계는 이미 최신이며
실제 행수와 정확히 일치한다(아래 §2). 재수집을 실행했더라도 아무 변화가 없었을 것이다.

  판정: 연산 구조 완전 동일(SORT AGGREGATE ← INDEX FAST FULL SCAN).

     컬럼 1개(REGION_NM VARCHAR2(50))가 더 많아 테이블이 6.4% 큰 것은
     **COUNT 성능과 무관**하다.

         재수집 대상이나, 성능 격차와는 무관하다.

■ 6. 결론과 대응방안 (이번 지침에서는 실행하지 않음)
════════════════════════════════════════════════════════════════════════════
[원인]
  목적지 테이블의 결함이 아니다. 다음이 모두 반증되었다.
    ✗ 실행계획 차이       → 양측 INDEX FAST FULL SCAN 동일, cost +1.3%
    ✗ 통계 stale          → 양측 전수 수집·NUM_ROWS 실제와 정확히 일치
    ✗ 물리구조 불리       → 인덱스 세그먼트 +0.09%, 실제 읽은 블록은 TGT가 1.0% 적음
    ✗ 파티션/압축 차이    → 양측 없음/DISABLED 동일
    ✗ 락 대기             → 양측 최상위 대기는 User I/O, Concurrency는 미미
    ✗ 인스턴스 리소스 차이→ cpu_count·SGA·파라미터 양측 동일

  실제 원인은 **환경 요인**이다.
    ① 버퍼 캐시 약 500MB < 스캔 대상 인덱스 1.13GB → direct path read 로
       매 실행마다 1.1GB를 디스크에서 전량 재읽기(v$bh 캐시 점유 0건으로 확인).
    ② 두 인스턴스가 같은 호스트의 같은 물리 디스크를 공유하고,
       filesystemio_options=none 이라 호스트 OS page cache 잔존 여부에 좌우된다.
       원본은 모든 테스트가 상시 읽어 잔존 확률이 높고, 목적지는 접근 빈도가
       낮아 최초 1회 접근이 콜드가 되기 쉽다.
    ③ cpu_count=2, parallel_max_servers=1 로 병렬 완화 수단이 없어
       디스크 상태가 그대로 실행 시간이 된다.
    → 결과적으로 "원본 빠름 / 목적지 첫 실행 느림" 패턴이 반복 관측될 수 있으나,
      2회차부터는 사라진다(프로브 1에서 그대로 재현).

[대응방안 — 실행하지 않음, 권장도 아래 순서]
  1) (권장) 조치 없음 + 측정 방법 개선
     - 통계 재수집 불필요. 근거: 통계가 이미 전수·정확(§2). 재수집해도 계획과
       성능이 바뀌지 않는다. 비용만 발생한다.
       (참고 비용: DBMS_STATS.GATHER_TABLE_STATS(cascade) 전수 = 테이블 3.4GB +
        인덱스 1.2GB 스캔, cpu_count=2·병렬 불가 환경에서 수 분~십수 분,
        수집 중 해당 인스턴스 I/O 포화. 효과는 0으로 예상.)
     - 성능 비교 시 첫 회 측정치는 버리고 2회차 이상을 쓰거나, 원본/목적지
       실행 순서를 교대로 바꿔 측정한다(이번 프로브 2·3 방식).
  2) (선택) 인덱스 통계만 정확도 보정
     - 인덱스 NUM_ROWS 가 생성 시점 추정치로 남아 있다(SRC 48.27M, TGT 50.96M).
       계획에 영향은 없었으나 정확도를 맞추려면 인덱스 통계만 재수집.
       비용: 인덱스 1.2GB 스캔, 1~3분 예상. 성능 개선 효과는 없음.
  3) (비권장) 버퍼 캐시 확대
     - sga_max_size 1.5GB 안에서 shared pool 이 940MB로 과대 배정되어 있다.
       shared pool 축소 + db_cache_size 확대로 캐시를 늘릴 수 있으나,
       ⓐ Oracle Free 는 SGA 상한이 있어 1.13GB 인덱스를 담기 빠듯하고
       ⓑ INDEX FAST FULL SCAN 은 direct path read 로 버퍼 캐시를 우회하므로
         추가로 _serial_direct_read 조정까지 필요하다(내부 파라미터, 위험).
       → 재기동 필요 + 회귀 위험 대비 이득이 불확실. 권장하지 않는다.
  4) (근본) 두 컨테이너를 서로 다른 물리 디스크로 분리
     - 동시 병렬 COUNT 시 양측이 같은 디스크를 경합하는 구조를 해소한다
       (프로브 3에서 병렬 시 양측 모두 ~1초 지연 확인).
       인프라 변경이므로 별도 판단 필요.
