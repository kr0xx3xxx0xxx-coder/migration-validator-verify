성격   : 읽기 전용 조사 + 제안 (코드 변경 없음)

════════════════════════════════════════════════════════════════════════════
0. 결론 요약
════════════════════════════════════════════════════════════════════════════
"검증항목: COUNT" 타일은 섹션 제목("COUNT 사전검증")과 중복이며 정보량 0 이 맞다.
그러나 그 자리에 넣을 값은 **이미 서버 응답에 존재한다** — 새 계측·새 서버 왕복 없이
교체 가능하다. 실측으로 값 존재를 확인한 유력 후보는 3개다.

  ① 원본/목적지 개별 COUNT 소요시간 (source_count_elapsed_ms / target_count_elapsed_ms)
     → 실측값 존재, 화면 어디에도 미표시, 매 실행마다 변동. **1순위 권장**
  ② COUNT 실행 방식 (count_generation_method — 3값)
     → 실측값 존재, 미표시, SQL 형태에 따라 변동. **2순위(툴팁/추가 타일 권장)**
  ③ 원본/목적지 DBMS 조합 (source_profile_display / target_profile_display)
     → 실측값 존재("postgresql:asisdb" / "oracle:tobedb"), 2단계엔 미표시.
       단 상단 DB 접속 설정 영역과 의미 중복 → 3순위

반대로 "적재율"은 **승격 부적절**이다 — 타일 바로 아래 COUNT 게이트 카드가 이미
같은 값을 표시하고 있어(같은 화면·같은 스크롤 위치) 순수 중복이 된다.

1. 조사 방법 (실측 근거)
════════════════════════════════════════════════════════════════════════════
정적 코드 추적만으로는 "필드가 정의돼 있다"까지만 확인되고 "실제 값이 들어오는가"는
확인되지 않는다. 그래서 DB 무접속 스텁 실측을 했다.

  · services.db_query_service._cmn_db_fetch_count 를 스텁으로 교체
    (원본 1,200ms / 목적지 300ms 지연 후 각각 1000건 / 940건 반환)

  · 응답 dict 의 최상위 키/값 전수 덤프
  · 실 DB 접속·서버 기동 없음, 코드 변경 없음(스텁은 임시 스크립트 내 monkeypatch)

3. 지침이 지목한 후보별 실제 값 존재 여부
════════════════════════════════════════════════════════════════════════════

[후보 A] SQL 방언 / DBMS 종류 (원본·목적지가 다를 수 있음)
  값 존재   : ○ 있음
  필드      : source_profile_display / target_profile_display
  실측값    : "postgresql:asisdb" / "oracle:tobedb"
  생성 위치 : count_common_service.py::_profile_display (459~471행)
              db_type 과 dbname 만 조합한다 — host/user/password 는 절대 미포함(설계상 보안 분리).
  변동성    : 원본·목적지가 서로 다른 DBMS 면(이기종 이관) 즉시 드러난다.
  주의      : db_type·dbname 이 둘 다 비면 null 이 된다(프리셋 미선택·수동입력 누락 시).
  중복도    : 상단 "DB 접속 설정" 영역(srcDb/tgtDb select, 프리셋 배지)과 의미 중복.
              다만 2단계 결과를 볼 때 접속 영역은 위로 스크롤돼 있는 경우가 많다.

[후보 B] 원본/목적지 각각의 COUNT 개별 소요시간
  값 존재   : ○ 있음 — **실측으로 병렬 동작까지 확인**
  필드      : source_count_elapsed_ms / target_count_elapsed_ms
  실측값    : 원본 1200.1ms / 목적지 300.9ms (스텁 지연 1200/300 과 일치 — 실계측)
  생성 위치 : count_common_service.py::_run_one_count_side (perf_counter 계측),
              _make_result (951~952행, 소수 1자리 반올림)
  병렬 검증 : 양쪽 스텁을 각 1,500ms 로 맞춰 재실행
                → source_count_elapsed_ms=1501.0 / target_count_elapsed_ms=1500.6
                → 전체 wall 1836.8ms, processing_ms 1821.6ms
              순차라면 3,000ms 를 넘어야 하므로 **병렬 실행이 실제로 적용됨**을 확인
              (COUNT-PAIR-PARALLEL-EXECUTION-FIX 정상 동작).
  해석 가치 : 현재 타일의 "처리시간"(processing_ms)은 병렬 실행 이후
              ≈ max(원본, 목적지) + 서버 오버헤드(파싱·COUNT SQL 생성, 실측 약 320~340ms)다.
              즉 총시간만 봐서는 **어느 쪽 DB 가 병목인지 알 수 없다.**
              개별값이 있으면 "원본이 느린가 / 목적지가 느린가 / 서버 오버헤드가 큰가"가
              한 눈에 구분된다 — 3단계 규모 등급·통계검증 비용 예측과 직접 연결된다.
  미표시 확인: ui/ 전체에서 source_count_elapsed_ms 를 소비하는 코드 없음.

[후보 C] WHERE 조건 적용 여부(목적지 검증범위 조건)
  값 존재   : △ **전용 필드 없음 — 유도만 가능**
  서버      : 응답에 target_where 를 되돌려주는 필드가 없다.
              다만 target_count_sql 안에 실제 적용된 WHERE 가 그대로 들어있다
              (실측: "SELECT COUNT(*) AS CNT FROM tgt_schema.t_target WHERE use_yn = 'Y'").
              원본 WHERE 는 목적지로 전파하지 않는 설계(single_validation_core.py 250행 주석)
              이므로, 목적지 COUNT SQL 의 WHERE 존재 = 검증범위 조건 적용 여부와 동치다.
  클라이언트: #tgtWhere 입력값을 언제든 읽을 수 있다(tabler_renderer.py 2535행).
              단 이 값은 실행 후에도 사용자가 편집 가능 → "실행 시점에 적용된 조건"과
              어긋날 수 있다. 신뢰 가능한 출처는 서버가 돌려준 target_count_sql 이다.
  중복 위험 : 1단계 타일에 이미 "조건문(있음/없음)" 타일이 있다(원본 SQL 의 WHERE).
              2단계에 비슷한 라벨을 두면 "어느 쪽 조건인가" 혼동이 생긴다.
              쓴다면 라벨을 "검증범위"처럼 명확히 구분해야 한다.

[후보 D] 실행 전략(단순 COUNT(*) 인가, 다른 방식인가)
  값 존재   : ○ 있음
  필드      : count_generation_method
  실측값    : "PARSED_MODEL_COUNT_SQL"
  가능한 값 : 3종 (services/count_sql_builder.py 48·49·174행)
                PARSED_MODEL_COUNT_SQL              — 파싱 모델 기반 재구성 COUNT(가장 흔함)
                PARSED_MODEL_CTE_SUBQUERY_COUNT_SQL — 원본 SELECT 통째 래핑 COUNT
                                                       (CTE/GROUP BY/UNION 포함 SQL)
                LEGACY_PARSE_RESULT_FALLBACK        — 레거시 파싱 폴백
  해석 가치 : 래핑 COUNT 는 원본 SELECT 전체를 실행한 뒤 행 수를 세므로 비용 성격이 다르고,
              세는 대상도 "테이블 행 수"가 아니라 "이관 결과 행 수"다. 이 구분이 화면에
              전혀 없어서, 지금은 왜 원본 COUNT 만 유독 느린지 사용자가 알 수 없다.
  변동성    : SQL 형태에 종속 — 단순 INSERT…SELECT 위주 현장이면 사실상 한 값에 고정될 수 있다.
              (그래도 "항상 고정"인 현재 검증항목과는 성격이 다르다.)

[후보 E] 적재율(%)
  값 존재   : ○ 있음 — count_gate.target_load_ratio (실측 0.94)
  **승격 비권장**. 이유:
    · 이미 같은 화면 타일 바로 아래 COUNT 게이트 카드(#countGateBox)가
      "원본 N · 목적 M · 순 차이 D · 목적지 적재율 X%" 를 표시한다
      (tabler_renderer.py 25219~25222행). 스크롤 없이 동시에 보인다 → 순수 중복.
    · 게이트 카드는 소규모 차이 안내 박스가 아니라 **모든 COUNT 결과에 항상** 렌더된다.
    · 게다가 타일에 이미 목적건수·원본건수·차이가 있어 적재율은 그 셋의 파생값이다.

4. 다른 화면에서 옮겨올 만한 항목 (지침 3번)
════════════════════════════════════════════════════════════════════════════
· 3단계 실행계획 타일(9개: 목적/원본 테이블·통계검증규모·목적그룹/원본그룹·목적집계/원본집계·
  처리시간·상태) — 여기서 2단계로 옮길 만한 항목은 없다. 규모 등급은 GROUP BY/SUM 선택이
  끝나야 산정되므로 2단계 시점에는 값 자체가 존재하지 않는다.
· 1단계 타일(9개) — "조건문" 타일이 유일한 유사 항목이나 원본 SQL 의 WHERE 이며 2단계의
  목적지 검증범위와 다르다(위 후보 C 참조).
· 오늘 완료된 P7(DBMS probe 병렬화, c0ef0e5) — 산출물은 접속 프로브 지연 해소이며
  2단계 응답에 새 필드를 추가하지 않는다. 다만 그 결과로 확정되는 db_type 이
  후보 A(profile_display)의 원천이다. 즉 P7 이 후보 A 의 신뢰도를 높였을 뿐,
  옮겨올 신규 표시 항목은 없다.
· 오늘 완료된 COUNT-PAIR-PARALLEL-EXECUTION-FIX — 후보 B 의 가치를 **새로 만들어낸** 변경이다.
  병렬화 이전에는 총시간 = 원본+목적지 합이라 개별값을 총시간에서 뺄셈으로 짐작할 수 있었지만,
  병렬화 이후에는 총시간 ≈ max 라 **개별값을 총시간에서 복원할 수 없다.**

5. 최종 제안 (구현하지 않음)
════════════════════════════════════════════════════════════════════════════

■ 권장안 : "검증항목" 타일 → **"COUNT 소요(원본/목적)"** 타일로 교체 (1개 교체, 개수 유지 8개)

  표시 예 :   라벨  COUNT 소요
              값    원본 1.20초
                    목적 0.30초        ← 3단계 GROUP BY 타일이 쓰는 <br> 다줄 값 규격 재사용
              툴팁  "원본 1200.1ms / 목적지 300.9ms · 총 1541.6ms(병렬 실행, 차액은 서버 파싱·
                     COUNT SQL 생성 오버헤드)"

  선정 이유 :
    1) 값이 이미 서버에 있고(실측 확인), 새 계측·새 왕복·새 CSS 가 전혀 필요 없다.
    2) 화면 어디에도 없는 정보다(ui/ 전수 확인 — 소비 코드 0곳).
    3) 매 실행마다 변한다 — 현재 검증항목(상수 'COUNT')의 정반대 성격.
    4) 오늘 병렬화로 총시간에서 개별값을 복원할 수 없게 됐다 → 지금 가장 필요한 정보다.
    5) 옆 타일 "처리시간"(총)과 나란히 놓이면 "총 ≈ max + 서버 오버헤드" 관계가 자명해져,
       두 타일이 서로를 설명한다(중복이 아니라 보완).

■ 차선 : "COUNT 방식"(count_generation_method) 타일
  값 3종 한글 매핑 예 — 단순 COUNT / 원본SELECT 래핑 / 레거시 폴백.
  단순 SQL 위주 환경에서는 한 값에 고정될 수 있어 1순위에서 뺐다.
  권장 절충: 별도 타일 대신 **"COUNT 소요" 타일 툴팁 뒤에 방식 한 줄을 덧붙이는** 방식.

■ "검증항목 타일을 없애고 나머지가 공간을 나눠 쓰는" 안에 대한 의견
  기술적으로는 가장 싸다 — .mv-qr-tiles 가 grid-template-columns: repeat(auto-fit,
  minmax(118px,1fr)) 이므로(tabler_renderer.py 999행) 타일 하나를 빼면 나머지 7개가
  자동으로 폭을 나눠 갖는다. 레이아웃 손상 없음.
  그럼에도 **제거보다 교체를 권한다.** 제거는 "정보 0 을 없앤" 것뿐이고, 교체는 같은 비용으로
  없던 정보를 얻는다. 위 실측대로 넣을 값이 실재하므로 빈 자리를 만들 이유가 없다.
  (넣을 값이 하나도 없었다면 제거가 정답이었을 것이다 — 그 조건이 성립하지 않는다.)
