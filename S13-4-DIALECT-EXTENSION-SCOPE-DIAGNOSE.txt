1. PostgreSQL — 위험 없음 (byte/char 모호성이 설계상 존재 불가)
================================================================================
PostgreSQL 공식 문서(8.3 Character Types) 확인 결과: `varchar(n)`/`character varying(n)`의 n은
**인코딩과 무관하게 항상 "문자 수"**다. 오라클처럼 "BYTE 의미로 선언할 수도 있는" 별도 문법
자체가 없다 — VARCHAR2(50 BYTE)에 대응하는 PG 구문이 없다. PG가 n의 상한(10,485,760)을 굳이
고정해 둔 이유 자체가 "인코딩에 따라 상한이 달라지는 걸 피하기 위해서"라고 문서/메일링리스트에
명시돼 있다. 즉 **선언 길이가 인코딩에 따라 달라지는 시나리오가 설계상 봉쇄돼 있다.**

따라서 "정의는 같은데 실제 저장 가능한 글자 수가 다르다"는 A1'과 동형의 위험은 PG↔PG,
PG↔(타 방언 무관)를 막론하고 성립하지 않는다. char_used 상당값은 PG에서 항상 'C'(문자 의미)로
고정될 수밖에 없고, 이는 `_effective_char_capacity`의 'C' 분기(char_length 그대로, 캐릭터셋
무관)와 정확히 일치 — **PG는 원래부터 "이미 안전한 선언 방식"으로 분류되는 케이스**다.

단, 이것과는 **다른 종류의 위험**이 하나 있다: 인코딩이 다른 두 PG 인스턴스 간 문자열 이관 시
(예: SQL_ASCII ↔ UTF8, 또는 EUC_KR ↔ UTF8) source 인코딩의 바이트 시퀀스가 target 인코딩으로
디코딩 불가능하면 **INSERT 자체가 인코딩 오류로 실패**한다(용량 축소로 인한 절단이 아니라
변환 실패로 인한 전체 거부). 이는 "실효수용량 축소"가 아니라 "문자 레퍼토리/인코딩 변환 실패"
범주라 A1'의 판정 모델(선언 길이를 캐릭터셋별 바이트/글자 환산으로 비교)과 형태가 다르다.
현재 이 도구가 다루는 COUNT/통계검증 파이프라인은 INSERT 실패 자체를 이미 별도 실행 오류로
드러내므로(SQL 실행 단계에서 예외로 표면화), 이 조사 범위(A1' 계열 "조용한 절단" 위험)에서는
제외한다.

결론: **PG 위험 실존하지 않음.** 설계 확장 불필요 — MetadataProvider를 만들어도 char_used가
항상 'C'라 위험 배지는 구조적으로 절대 안 뜬다(오탐/누락 걱정 없이 "해당 없음"으로 확정 가능).

2. MySQL — 위험 실존하지만 A1'의 판정 모델과 형태가 다르다
================================================================================
MySQL VARCHAR(n)도 n이 "문자 수"로 고정(4.1 이후)이고, CHAR_USED류의 BYTE/CHAR 선언 분기
자체가 없다 — 이 점은 PG와 동일하다. 하지만 **캐릭터셋(utf8mb3 vs utf8mb4)에 따라 "같은
컬럼 정의(VARCHAR(n))가 실제로 표현 가능한 문자 집합"이 달라지는 것이 아니라 "표현 자체가
아예 불가능한 문자가 생긴다"**는 오라클/MSSQL과는 다른 형태의 위험이 실존한다(MySQL
공식 문서 12.9.8 확인):
  · utf8mb3("utf8", 최대 3바이트/문자) → 4바이트가 필요한 supplementary 문자(이모지, 일부
    희귀 한자/고어 등)를 **아예 저장할 수 없다**. utf8mb4는 최대 4바이트/문자로 전체
    유니코드를 담는다.
  · 순방향(utf8mb3 → utf8mb4, 좁은 캐릭터셋 → 넓은 캐릭터셋): 안전. 기존에 표현 가능했던
    모든 문자는 target에서도 표현 가능(directive 예상과 일치).
  · 역방향(utf8mb4 → utf8mb3, 넓은 캐릭터셋 → 좁은 캐릭터셋): 위험. supplementary 문자가
    포함된 값은 오라클처럼 "뒤가 잘리는" 게 아니라 **해당 문자 자체가 저장 불가**(엄격 모드면
    INSERT 오류, 비엄격/변환 경로면 '?' 로 치환되어 데이터가 조용히 손상)한다.
  · 참고로 바이트 상한 자체도 같이 움직인다: VARCHAR 컬럼의 바이트 상한은 그대로인데 문자
    상한이 달라지는 효과(utf8mb3는 최대 21,845자, utf8mb4는 같은 바이트 상한에서 16,383자)도
    있으나, 이는 DDL 단계(CREATE TABLE 시 컬럼 길이 자체가 너무 크면 에러)의 문제이고, "이미
    선언된 기존 스키마의 실효 저장 가능 문자 수"가 이관 중 조용히 줄어드는 A1'류 위험과는
    별개다.

동일 DBMS 페어(MySQL↔MySQL) 성립 여부(directive §4 핵심 질문): **성립한다.** 오히려 이 도구가
다루는 "레거시 시스템 현대화 이관" 특성상 실사용 빈도가 낮지 않을 수 있다 — MySQL은 과거
기본 캐릭터셋이 latin1/utf8(mb3)였고 5.5.3(2010) 이후에야 utf8mb4가 도입돼, "오래된 as-is
MySQL(utf8mb3 스키마) → 새로 구축한 to-be MySQL(utf8mb4 스키마)"처럼 **같은 MySQL끼리도
캐릭터셋 세대차가 실무에서 흔히 발생**한다.

구조적 결론(중요): **현재 A1'의 `_effective_char_capacity` 판정 모델은 MySQL 위험을 애초에
잡을 수 없는 형태다.** 그 함수는 "char_used='B'(바이트 의미)일 때만" data_length를
캐릭터셋별 바이트/글자 수로 환산해 비교한다. MySQL은 char_used가 구조적으로 항상 'C'이므로
`_evaluate_compatibility`의 `byte_semantics = "B" in (...)` 게이트를 절대 통과하지 못한다.
즉 MySqlMetadataProvider를 그대로 만들어 끼워 넣어도(F14와 대칭으로) 위험은 여전히 0건으로
나온다 — **오라클과 판정 로직을 공유할 수 없고, "선언 문자 수 비교"가 아니라 "캐릭터셋
레퍼토리(최대 바이트/문자) 비교"라는 별도 판정 함수가 필요하다**(예: tgt 캐릭터셋의
최대 바이트/문자 < src 캐릭터셋의 최대 바이트/문자 이면 위험 플래그 — 산술 환산이 아니라
이진 비교).

결론: **MySQL 위험 실존.** 단, A1'을 "그대로 재사용"은 불가 — 판정 함수는 신규, 메타데이터
조회(캐릭터셋 조회는 `information_schema.tables`/`SHOW CREATE TABLE` 등으로 가능, DB 어댑터
자체엔 아직 build_db_charset_query 미구현)와 배지/게이팅 UI(risk_flags 포함 여부 검사)는
재사용 가능.

3. MSSQL — 위험 실존, 오라클과 동형 구조 (A1' 그대로 재사용 가능)
================================================================================
directive가 언급한 F14/F15 배경대로, MSSQL은 PG/MySQL과 근본적으로 다르다: **VARCHAR(n)의
n이 처음부터 "바이트 수"**다(Microsoft 공식 문서 확인 — "In char and varchar, n defines the
string size in bytes"). 이는 오라클의 VARCHAR2(n BYTE)처럼 선택적 옵션이 아니라 VARCHAR라는
타입 자체에 내장된 의미다. 반면 NVARCHAR(n)은 항상 UTF-16(고정 2바이트/코드유닛)이라 n이
사실상 "문자 수"로 안전하게 동작한다(오라클의 CHAR 의미와 동형).

이 비대칭이 만드는 위험 시나리오:
  · 레거시 코드페이지(예: Korean_Wansung_CI_AS, CP949 계열)에서 한글은 보통 2바이트/문자다.
    VARCHAR(100)은 한글 약 50자를 담는다.
  · SQL Server 2019+ 의 `_UTF8` 계열 collation으로 옮기면(예: Korean_100_CI_AS_SC_UTF8) 같은
    VARCHAR 타입이 내부적으로 UTF-8 가변 인코딩을 쓰게 되는데, 한글은 UTF-8에서 3바이트다.
    같은 VARCHAR(100)이 이제 한글 약 33자만 담는다 — **선언(100)은 그대로인데 실효 수용량이
    조용히 줄어든다.** 이는 오라클 VARCHAR2 BYTE 케이스와 수학적으로 완전히 동일한 구조다
    (선언 바이트 수 ÷ 문자당 바이트 수, 캐릭터셋/collation이 바뀌면 분모가 바뀐다).
  · NVARCHAR는 항상 UTF-16 고정이라 이 위험에서 자유롭다 — 오라클 CHAR 의미와 동일하게
    "이미 안전한 선언 방식".

동일 DBMS 페어(MSSQL↔MSSQL) 성립 여부: **성립한다.** 위 시나리오 자체가 "같은 SQL Server
끼리, collation만 레거시 코드페이지 → 최신 UTF8 collation으로 바뀌는" 케이스이고, 이는 MS가
SQL Server 2019에서 UTF-8 collation을 도입한 이래 실제로 권장되는 마이그레이션 방향이라
현실성이 낮지 않다. (참고로 코드페이지가 다른 두 레거시 collation 간 이관, 예: 한국어
코드페이지 ↔ 서유럽 코드페이지처럼 아예 문자 자체가 그 코드페이지에 없는 경우는 MySQL형
"표현 불가" 위험과 겹친다 — MSSQL은 두 형태의 위험을 다 가질 수 있다는 뜻.)

구조적 결론(중요): **F15가 이미 준비해 둔 스키마(char_used 상당값 B/C 구분 + 컬럼별
COLLATION_NAME)는 A1'의 `_effective_char_capacity`/`_evaluate_compatibility`가 요구하는
입력 shape와 이름까지 그대로 일치한다.** 오라클과 달리 새 판정 함수가 필요 없다 — 아래 3곳만
채우면 A1' 배지가 MSSQL에도 그대로 뜬다(UI/게이팅 코드는 무수정):
  ① `services/mssql_metadata_provider.py` 신설 — `OracleMetadataProvider`와 동일 인터페이스
     (`get_column_metadata`/`get_table_metadata`), `build_tgt_column_meta_query` 결과의
     6·7·9번째 값(char_used 상당값/character_octet_length/collation_name)을
     CandidateColumnMetadata.char_used/data_length/charset에 매핑.
     (DB 단위 캐릭터셋 하나만 조회하는 오라클과 달리, MSSQL은 컬럼별 COLLATE 오버라이드가
     가능하므로 `_get_charset()` 같은 "연결당 1회 캐시" 방식이 아니라 컬럼별 값을 그대로
     통과시키면 된다 — F15 주석에 이미 이 설계 의도가 적혀 있다.)
  ② `services/analyze_to_csr_adapter.py::_build_oracle_metadata_provider`를 대칭으로 확장하는
     `_build_mssql_metadata_provider`(또는 dialect 분기를 갖는 공용 팩토리) 추가, db_type이
     mssql/pyodbc 계열일 때 연결.
  ③ `services/candidate_scoring_runner.py::_CHARSET_CJK_BYTES_PER_CHAR`에 MSSQL collation
     이름 키 추가(예: `KOREAN_WANSUNG_CI_AS`/`KOREAN_100_CI_AS`류 DBCS 계열 → 2,
     `..._SC_UTF8`류 UTF-8 collation → 3). 현재 이 표는 오라클 NLS_CHARACTERSET 이름만
     등록돼 있어, MSSQL Provider를 연결해도 collation_name이 표에 없으면 `bpc` 조회 실패로
     또 None이 되어 위험이 조용히 0건 처리된다 — **①②만으로는 부족하고 반드시 같이 가야
     하는 항목.**

결론: **MSSQL 위험 실존, A1' 판정 로직 재사용 가능(신규 판정 함수 불필요).** 다만 F15가
"실 SQL Server 인스턴스 부재로 라이브 미검증" 상태였다는 점(BACKLOG F15 원문)은 그대로
유효 — ①②③을 구현해도 이번 조사와 마찬가지로 실접속 검증은 별도 과제로 남는다.

  1. 오늘(2026-08-08) 확인된 고객사 실사용 패턴이 "전부 동일 DBMS끼리 이관"이라는 전제 하에,
     MSSQL은 F15가 이미 컬럼 메타 조회 SQL까지 완성해 둔 상태라 남은 작업이 배선(①②③) 뿐이고
     기존 A1' 판정/UI 코드를 전혀 건드리지 않는다 — 구현 리스크와 회귀 리스크가 가장 낮다.
  2. MySQL은 새 판정 함수가 필요해 구현 범위가 더 크고, "레거시 시스템 현대화" 고객 특성상
     utf8mb3→utf8mb4류 캐릭터셋 세대차가 실제로 발생할 개연성은 있으나, 현재 이 프로젝트의
     MySQL 어댑터에는 charset 조회 경로 자체가 아직 없어(build_db_charset_query 미구현)
     선행 배선이 MSSQL보다 한 단계 더 필요하다.
  3. PostgreSQL은 설계상 위험이 존재할 수 없음이 문서(8.3 Character Types) 기준으로 명확히
     확인됐으므로, MetadataProvider를 만들어도 얻을 게 없다 — 이 조사로 종결하고 별도
     구현 항목을 만들지 않는 것을 권장한다(**S13 원문의 "4방언 원칙" 완수 관점에서도, PG는
     "조사 결과 해당없음"으로 명시적으로 닫아 두는 것이 "미착수"로 방치하는 것보다 낫다**).

비판적 검토(CLAUDE.md 의무 사항):
  · heuristic 하드코딩 증가 위험: MSSQL 확장은 `_CHARSET_CJK_BYTES_PER_CHAR`에 문자열 키를
    추가하는 것뿐이라 기존 오라클 패턴과 동일한 수준의(신규 증가 아닌) 하드코딩이다. 다만
    SQL Server collation 이름은 오라클 NLS_CHARACTERSET보다 종류가 훨씬 많다(언어별 수백 종) —
    전부 등록은 비현실적이므로 "미등록 collation은 None(위험 판단 보류)"이라는 기존 안전
    폴백 원칙을 반드시 유지해야 하고, 등록 대상은 고객사 실사용 collation으로 한정해야 한다.
  · scoring 미성숙: 해당 없음(이 위험은 애초에 가중치 점수가 아니라 이진 배지).
  · explainability: MSSQL Provider도 오라클과 동일하게 ProviderWarning 누적 방식을 그대로
    따르면 근거 미저장 문제는 발생하지 않는다.
  · MySQL 신규 판정 함수는 "레퍼토리 비교"라는 새 판정 축이 하나 늘어나는 것이므로, 착수 시
    S13 배지 문구("⚠ 길이 축소 위험")를 그대로 쓰면 사용자가 오인할 수 있다(MySQL 위험은
    "길이가 줄어드는" 게 아니라 "특정 문자가 아예 저장 안 되는" 것) — 착수한다면 배지
    문구/설명을 MySQL 전용으로 분리해야 한다는 점을 설계 단계에서부터 반영 필요.
