0. 배경 — 왜 재확인이 필요했나
────────────────────────────────────────────────────────────────────────
2026-07-29 같은 날 같은 조사 스레드에서 "문자 PK 경계값(축A) 수정 완료(100만행 실측,
참값 10,000건까지 확인)" 기록과 "여전히 미해결"이라는 진단 문서(BACKLOG M68 §5)가 동시에
존재해, git 커밋 순서만으로는 어느 쪽이 현재 코드에서 유효한지 판단 불가했다. 코드 수정 없이
당시와 동일한 시나리오를 실 DB 로 재실행해 지금 이 순간의 코드 상태를 실측으로 매듭짓는다.

────────────────────────────────────────────────────────────────────────
1. 픽스처 상태 재확인 — 그대로 잔존
────────────────────────────────────────────────────────────────────────
- NXDNP.MV_CSPK_SRC(원본) 1,000,000행 · MV_CSPK_TGT(목적) 990,000행 · 차이 10,000행 —
  2026-07-29 당시와 동일(변형 없음).
- 목적에 남은 MOD(g,100)=0 행 0건(참값 누락 규칙 정상), 목적 g 범위 1~999,999 — 참값 규칙 그대로.

────────────────────────────────────────────────────────────────────────
2. 축 A(경계 절단) — 정상, 오히려 당시보다 개선
────────────────────────────────────────────────────────────────────────
운영 함수 ora_pk_min_max() 를 V2(문자로 노출된 유일 숫자 PK, int() 로 파싱 가능한 문자 키)에
그대로 호출.

  당시(2026-07-29, 수정 후) : MIN/MAX 숫자 재산정 통과, 커버 밖 1건(0.0001%)
  이번(2026-08-10)          : MIN/MAX 원본 1~1,000,000 · 목적 1~999,999(파이썬 타입 int로 반환
                               — 숫자 재산정 로직 동작 확인), 커버 밖 원본 0건 · 목적 0건(0.0%)

문자 정렬이었다면 MAX 는 '999999'(문자열) 로 나와 int() 게이트가 HOLD 로 막히거나 경계가
잘렸어야 하나, 실제로는 숫자로 정상 재산정됨을 재확인. V1(실제 자연 문자 PK, `A001-000001`
형태)은 이번에도 int() 게이트에서 HOLD_NON_NUMERIC_PK 로 안전하게 막힘(변동 없음).

────────────────────────────────────────────────────────────────────────
3. 축 B(merge-join 정렬 전제 위반) — 원인은 그대로, 결과는 정상 (수정이 실제로 작동 중)
────────────────────────────────────────────────────────────────────────
F-1(chunk 조회 반환 순서 직접 검사) — 원인이 되는 현상 자체는 이번에도 재현된다:
  V2 문자키 : 50,000행 중 역전(내림 전이) 4,500회 — 2026-07-29 실측과 동일 횟수, 정렬전제 "위반"
  V3 숫자키(대조군) : 역전 0회
  V5 zero-pad 문자키(대조군) : 역전 0회

즉 chunk 조회의 ORDER BY 는 지금도 문자 정렬이며(SQL 자체는 안 바뀜, 커밋 설명과 일치),
merge_chunk 진입 이전 단계만 보면 "정렬 전제 위반"은 여전히 발생한다. 하지만 이건 커밋
934c293a 가 고친 지점이 SQL의 ORDER BY 가 아니라 merge_chunk 진입점의 `_ensure_pk_ascending`
불변식 강제였다는 설계와 정확히 일치 — 관건은 이 위반이 최종 판정까지 전파되는지 여부다.

C 단계(run_pk_range_chunk_compare 직접 호출, end-to-end):
  V2_G_CHAR(문자키) : 재이관 대상 10,000건(목적 미존재 10,000 · 값 불일치 0) · 목적 단독 0건 · 86.4s
  V3_G_NUM(숫자키, 대조군) : 재이관 대상 10,000건 · 목적 단독 0건 · 78.6s

참값 대조 — 실제 누락 10,000건 대비:
  V2_G_CHAR 검출 10,000건 · 미검출 0건 → **정확히 일치**
  V3_G_NUM  검출 10,000건 · 미검출 0건 → **정확히 일치**

2026-07-29 당시 수정 전 재현값이었던 "재이관 64,997건 + 목적 단독 54,998건"(참값의 6.5배,
날조된 미존재/목적단독 쌍) 은 이번에 재현되지 않았다. chunk 조회 단계의 역전(4,500회)이
그대로 존재함에도 최종 결과가 참값과 정확히 일치한다는 것은, merge 진입 전 재정렬 보정이
지금도 실제로 작동해 위반을 흡수하고 있다는 뜻이다.

F-2(zero-pad 문자키 대조군, 문자 정렬=숫자 정렬인 케이스) : 재이관 10,000건 · 목적 단독 0건 ·
"참값 10,000건 대비 → 일치" — 대조군도 그대로 정상.

4. 결론
────────────────────────────────────────────────────────────────────────
재현 결과 — 참값(10,000건)과 문자키·숫자키·zero-pad 문자키 3가지 변종 모두 정확히 일치,

**"완료 상태 유지"로 확정한다.** 커밋 934c293a(축A 숫자 재산정 + 축B merge 전 재정렬)와
783b9f17(별칭 정합)은 지금 이 순간의 코드에서도 실제로 유효하다. BACKLOG M68 §5 의 "축A
여전히 미해결"이라는 8/9 채팅 진단은 이번 재실측 결과와 배치되며, 그 진단 시점에 축A 를
가리키는 별도 회귀가 있었다는 근거는 이번 조사에서 나오지 않았다(재현 실패 = 회귀 없음).
다만 그 진단 문서가 정확히 어떤 근거로 "미해결"이라 적었는지(코드 재검토였는지 실측이었는지)는
이번 지침 범위 밖이라 별도 확인은 하지 않았다 — 필요 시 후속 지침으로 진행.

  회귀 자체가 없어 후속 수정 지침도 불필요.
