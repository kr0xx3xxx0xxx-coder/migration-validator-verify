1. 배경 / 원인
────────────────────────────────────────────────────────────────────────
services/diagnosis/key_evidence.py::_table_key_meta 의 컬럼 타입/nullable 조회가
information_schema.columns 로 PostgreSQL 전용 하드코딩돼 있었다. 오라클에는
information_schema 가 없어 이 조회가 항상 빈 결과가 되고, 그 결과

  build_chunk_key_evidence_snapshot
    → tmeta = {} / smeta = {}
    → source_exists=false / target_exists=false
    → verdict=NOT_TRUSTED, reason=SCHEMA_META_MISSING

로 고정됐다. PK 제약 조회는 선행 작업(MATCH-KEY-ORACLE-DIALECT-DELEGATION-FIX)에서
이미 어댑터(get_adapter(db_type).fetch_key_metadata)로 방언 위임된 상태였고,
컬럼 조회만 PG 전용으로 남아 있었다.

근거: verify 저장소 STRATEGY-PLAN-PK-KIND-HARDCODE-FIX.txt (§2-(b) / §9-(c)), BACKLOG.md S11

8. 잔여 한계 / 후속 (비판적 검토)
────────────────────────────────────────────────────────────────────────
(a) 폴백 경로에서 비-PK 컬럼의 NOT NULL 을 알 수 없다(어댑터 계약에 nullable 부재).
    현재 소비처가 PK 컬럼만 후보로 삼아 실무 영향은 없지만, 향후 비-PK 컬럼의
    NOT NULL 이 판정에 필요해지면 어댑터 컬럼메타 계약에 nullable 을 추가해야 한다
    (오라클 ALL_TAB_COLUMNS.nullable, PG information_schema.is_nullable).
    → 어댑터 파일 수정이 필요하므로 이번 지침 범위(key_evidence.py 만) 밖. 후속 항목.
(b) 같은 파일의 _column_meta_full(:198) 도 information_schema 하드코딩이 남아 있다.
    현재 파일 내 호출부가 없어(사용처 0) 이번 범위에서 건드리지 않았다. 정리 대상 후보.
(c) MySQL/MSSQL 은 이번 범위 밖(지침 명시). 두 어댑터는 build_column_meta_query 를
    제공하므로 이 폴백 구조를 그대로 타지만, 실 DB 실측은 하지 않았다(미검증으로 남김).
(d) 폴백은 1차 조회가 빈 결과일 때만 진입하므로, PG 에서 테이블이 실제로 존재하지 않는
    경우에만 어댑터 조회 1회가 추가로 발생한다. 최종 반환값은 {} 로 동일하다(결과 불변).
