4. (b) INNER JOIN vs (c) OUTER JOIN — 검출건수 차이가 기대대로 관측됨 (최우선 확인항목)

  항목               | (b) INNER JOIN | (c) LEFT OUTER JOIN | 차이
  -------------------|----------------|---------------------|--------
  원본 COUNT         |        995,000 |           1,000,000 | +5,000
  목적 COUNT         |        990,000 |             990,000 |      0
  COUNT 차이         |         +5,000 |             +10,000 | +5,000
  처리된 원본 행수   |          9,949 |               9,999 |    (수집 상한 도달 시점 기준)

  · 화면이 생성한 원본 COUNT SQL 에 조인 타입이 그대로 반영되었다(스크린샷으로 확인):
      (b) SELECT COUNT(*) AS CNT FROM NXDNP.MV_SCATTER_SRC S
          INNER JOIN NXDNP.MV_SCATTER_DIM D ON s.REGION_CD = d.REGION_CD
      (c) SELECT COUNT(*) AS CNT FROM NXDNP.MV_SCATTER_SRC S
          LEFT OUTER JOIN NXDNP.MV_SCATTER_DIM D ON s.REGION_CD = d.REGION_CD
  · 차이 5,000 = 차원 미대응(R99) 행수 5,000 과 정확히 일치.
  · **결론: 조인 타입이 무시되고 있다는 신호는 없다.** 지침이 최우선 보고 대상으로 지정한
    "INNER/OUTER 무차이" 상황은 발생하지 않았다.


5. 이상 징후 (발견된 것 전부)

【이상-1】재이관 대상 "레코드" 수집이 101건에서 조기중단 — 참값 10,000건 (영향 큼)
  · 6종 전부 동일: counts = {reimport_pks: 101, passed: 9,999, missing_migration: 101},
    early_stopped=true, 그룹당 10~11건만 저장.
  · 원인은 **표본 조기중단(sample_early_stop) 정책이 아니다** — 응답의 sampling 필드가
    전 구간 null 이었고, 정책을 OFF 로 바꿔 6종을 재측정해도 결과가 완전히 동일했다
    (대조군 _gateOFF). 즉 이 시나리오에서 표본 게이트는 무관하다.
  · 실제 원인은 **그룹 표시정책의 수집 상한**이다: per_group_policy 가
    per_group_full_list_max=100 → per_group_early_stop_abs=101 을 만들고,
    누적 101건째에서 수집을 멈춘다(services/per_group_display_policy.py).
  · 상한을 최대치로 올려 대조 측정(_cap500, full_list_max=500)한 결과:
        수집 501건 / 처리 원본 49,599행 / 수집 1,217ms / Excel 레코드 시트 501행
    → 상한에 정확히 비례해 수집량과 스캔량이 늘 뿐, **10,000건 전량 추출은 도달 불가**.
      clamp_per_group_thresholds() 의 HARD CAP 이 500 이라 그룹당 1,000건(총 10,000건)
      규모에서는 구조적으로 전량 추출이 불가능하다.
  · 화면은 조용한 실패가 아니다 — "표시 등급 D4 · 요약 전용" 붉은 배너로
    "수집이 조기중단되어 정확한 총 건수는 확인하지 않았습니다"를 명시한다.
  · 다만 같은 화면의 요약표는 "재이관 대상 10건"이라는 숫자를 그대로 노출한다(참값 10,000).
    배너를 읽지 않으면 10건으로 오독할 여지가 있다.
  · 판정: 대량·흩어진 불일치에서 통계검증(그룹 단위 검출)은 정확하지만,
    재이관 레코드 전량 확보는 현재 상한 정책상 불가능하다. 정책 변경이 필요한 사안이므로
    이번 측정 범위에서는 사실만 보고한다(코드/정책 수정 없음 — 값은 원복 완료, §8).

【이상-2】(f) 복합 쿼리에서 ORA-00904: "REGION_NM": invalid identifier (서버 로그에만 노출)
  · (f)에서만 3단계·4단계 진입 시 각 1회씩 "profile DB 실행 실패 (join=False):
    ORA-00904: "REGION_NM": invalid identifier" 가 서버 로그에 찍힌다.
  · gate_on / gate_off / final 세 세트에서 모두 동일하게 재현(6회 관측) — 우발적 오류 아님.
  · 화면에는 오류가 표시되지 않고 후보 컬럼 선정·통계검증은 정상 완료된다(결과값도 정확).
    즉 후보 프로파일 수집 경로가 조용히 실패하고 폴백으로 진행되는 형태다.
  · (c) LEFT OUTER JOIN 단독에서는 발생하지 않는다 → CTE 안에서 조인한 결과를 UNION ALL 로
    묶은 형태에서 CTE 밖으로 컬럼(REGION_NM)을 참조할 때 깨지는 것으로 보인다.

    측정값에 들어갔다. 어제 912초는 "912초가 걸렸다"가 아니라
    "3회×300초 폴링 상한 안에서 끝내 실행되지 못했다"에 가깝다.
  · 이번에는 1차/2차 클릭을 구분하고 실제 /count 요청 발생 시점부터 재도록 고쳤다
    → 같은 작업이 2.7초(응답 155~330ms)로 측정된다.
  · 어제 3단계 616초(후보 체크박스 렌더 타임아웃)는 오늘 4.8초로 정상화됐다. 이쪽은
    드라이버 결함으로 설명되지 않으므로 당시 DB/디스크 상태의 영향일 가능성이 남아 있다.
  · 결론: 어제 값 폐기는 타당하다. 다만 폐기 사유는 "디스크 정체"만이 아니라
    "계측 드라이버 결함 + 당시 환경 이상"의 복합으로 기록해 둔다.

【참고】계측 드라이버에서 함께 바로잡은 아티팩트(운영 코드 아님, dev_e2e 전용)
  (1) 2단계 트리거 미인지 → 위 【이상-5】
