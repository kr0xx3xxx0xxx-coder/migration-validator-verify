[2-A] 코드 구조 분석 — 수집과 trim 은 서로 다른 레버가 지배한다
  services/exact_diff/pk_range_chunk.py 수집 루프(§710):
    `if limit is not None and ... (m["missing"]+m["value"]) >= limit: limit_hit=True; break`
  → 루프 중단 조건은 mismatch_limit_count(=limit, 원본COUNT×rate% 로 산출)뿐이다.
    representative_limit 은 이 루프 안 어디에도 등장하지 않는다.
  trim 호출(§742): `if limit_hit: store.trim_kind(run_id, REIMPORT_KIND, int(representative_limit))`
  → representative_limit 은 **수집이 끝난 뒤 1회**, "이미 SQLite 에 쓰인 mismatch_limit_count 건
    중 앞 N건만 남기고 지운다"는 후처리에만 관여한다.
  즉 20→100 은 "이미 다 쓴 데이터에서 얼마나 지울지"를 20건 덜 지우는 것으로 바꿀 뿐 —
  수집 단계(가장 비용이 큰 구간, 실측상 수만~수백만 건 INSERT)에는 원천적으로 영향이 없다.
  이 구조 분석이 §2-B 실측 설계의 근거다.

[2-B] 실측 방법
  스크립트: scripts/dev_e2e/f2_representative_limit_raise_perf_diagnose.py (신규, 코드 무변경 —
  기존 services/exact_diff/store.py 를 그대로 호출만 함).
  services.exact_diff.store.ExactDiffRunStore(코드 무수정, 실제 저장 엔진 그대로)를 사용해
  pre_trim_n(=수집 종료 시점 실제 저장 건수, mismatch_limit_count 시뮬레이션) 규모별로
  동일 데이터를 2개 run(run_20 / run_100)에 적재한 뒤, trim_kind(20) vs trim_kind(100) 을 각각
  실행해 (INSERT 시간, trim DELETE 시간, 대표행 SELECT 시간, tracemalloc peak, 저장 후 바이트)를
  비교. in-memory(test-only) 모드로 4개 규모(1,000 / 20,000 / 500,000 / 2,000,000건)를 측정하고,
  최대 규모(2,000,000건 — 20,000,000행 테이블이 10%에서 강제중단되는 시나리오에 해당)는 파일
  (영속 WAL) 모드로 1회 추가 실측해 디스크 I/O 를 포함한 실제 저장 경로 비용까지 확인했다.
  파일모드 측정용 run 은 측정 직후 delete_run() 으로 정리해 영속 DB(db/exact_diff_runs.db)를
  오염시키지 않았다.

  해석:
  - INSERT(수집) 시간은 §2-A 구조 분석대로 representative_limit 과 무관 — 모든 규모에서 20/100
    두 값 사이 차이가 ±4~17% 범위의 실행 간 노이즈일 뿐, representative_limit 이 커질수록
    체계적으로 느려지는 패턴이 전혀 없다(오히려 500,000·FILE-SELECT 에서는 100 쪽이 더 빠름).
  - trim(DELETE)·SELECT·peak 메모리는 100 쪽이 대체로 근소하게 더 걸리지만 절대값이 전부
    수 ms~수 초 수준이고, 유일하게 유의미해 보이는 메모리(2M 티어 trim +1.2초)조차 전체 run
    소요시간(수집만 68초) 대비 2% 미만이다.
  - **가장 결정적인 반증**: 실제 디스크 I/O 가 개입하는 FILE(영속) 모드·2,000,000건 규모에서는
    trim·SELECT 모두 **20 쪽이 100 쪽보다 오래 걸렸다**(trim 199초 vs 139초). representative_limit
    이 비용의 지배 요인이었다면 100(더 많이 남김)이 항상 더 오래 걸려야 하는데 정반대 — 이는
    DELETE 비용이 '남기는 건수(20 vs 100)'가 아니라 '지우는 건수(약 2,000,000건, 둘 다 거의 동일)'
    에 의해 지배되고, 나머지는 WAL 체크포인트·디스크 스케줄링 노이즈임을 뒷받침한다.
  - 저장 후 바이트(9,410 → 47,890, +38,480바이트)·peak 메모리(0.07MB → 0.35MB)는 늘어난 80건의
    JSON 직렬화 비용일 뿐이며, 같은 run 이 수집 단계에서 이미 다뤘던 데이터량(2,000,000건 규모면
    수백 MB~수 GB)에 비하면 무시 가능한 수준이다.

[2-D] "첫 20건 자동표시" 기능과의 독립성 확인
  §1-A 에서 대표저장수(20)가 애초에 "첫 20건 자동표시" UI 숫자와 맞춰 고른 값으로 보인다고
  판단했는데, 두 기능이 실제로 같은 변수를 공유하는지 확인했다. "첫 20건 자동표시"는
  routes 폴링이 `committed_first`(§5.8, `early_flush_n` 파라미터 — 기본값 20이지만
  representative_limit 과는 별개 함수 인자)에 의해 결정되는 별도 메커니즘으로, representative_limit
  값을 올려도 이 로직에는 영향이 없다(같은 커밋에서 함께 도입돼 숫자만 우연히 같을 뿐, 코드상
  의존관계 없음 — pk_range_chunk.py 함수 시그니처의 early_flush_n=20 과 representative_limit=20 은
  서로 다른 매개변수).

[2-E] EARLY_STOPPED 표준 경로(101건 상한)와 값을 맞출지
  두 경로는 메커니즘이 다르다:
  - EARLY_STOPPED 표준 경로(agg_contribution.py): walk 가 "100건 표시 + 101번째 도달 시 초과를
    감지"하는 방식 — 몇 건이 있는지 스스로 모르는 상태에서 걷다가 101에서 멈추므로 101이 필요
    (100까지 다 채웠는데 초과인지 아닌지 구분하려면 1건 더 봐야 한다).
  - CHUNK/표본 경로(이번 대상): trim 시점에 이미 mismatch_limit_count 만큼 전량 수집을 마친 뒤
    "그 중 앞 N건만 남긴다"는 사후 절단이라, 초과 여부를 이미 알고 있다(m["missing"]+m["value"]
    >= limit 로 이미 판정됨). +1 트릭이 필요 없다.
  → **101 로 맞출 필요 없음**. "100건 표시 보장"이라는 사용자 체감 목표는 값을 그냥 100 으로
    맞추면 충족되고, 두 경로 모두 문구에 실제 값을 그대로 삽입하므로("표시 N건") 100 과 101 이
    같은 화면에서 병존해도 각자 정확한 숫자를 보여줘 혼란이 없다(기존에도 storage_kind 별로
    문구가 이미 분기돼 있음, §8-(b) 참고).

    `_pgCap = min(d.total, _pgDec.pm)`  (d.total = trim 후 실제 저장 건수, _pgDec.pm =
    partial_display_max = per_group_full_list_max, 서버 기본값 100)
    `_pgKind = (_pgCap < _pgDec.pm) ? 'STORED_CAP' : ''`
  현재(20): d.total=20, pm=100 → _pgCap=20 < 100 → 'STORED_CAP' → "저장분이 20건뿐이라 그 이상은
  표시할 수 없습니다(저장 상한)" 배너가 CHUNK/표본 조기중단이 걸릴 때마다(사실상 매번) 뜬다.
  100으로 상향 후: d.total=100, pm=100 → _pgCap=100, **100 < 100 은 거짓** → 'STORED_CAP' 아님 →
  이 배너 문구는 CHUNK/표본 경로에서 **사실상 나오지 않게 된다**(non-STORED_CAP 분기 —
  "실제 불일치 레코드 중 확보된 저장분의 앞 100건을 표시합니다" 로 대체). 즉 지시가 예상한 대로
  "문구가 뜨는 빈도 자체가 줄어든다"가 아니라 **경계값이 정확히 일치해 사실상 소거**되는 결과다
  (단, per_group_full_list_max 자체를 admin 이 100 초과로 올리면 다시 STORED_CAP 조건이 살아난다
  — 두 값이 서로 다른 정책 항목이라는 기존 갭은 이번 상향으로도 해소되지 않음, 참고만).

[3-4] 잔여 위험/주의사항
  - **기존 배포본 데이터 마이그레이션 필요**: representative_sample_limit·sample_representative_store_n
    은 이미 validation_policy_settings 테이블에 20으로 저장돼 있는 배포본이 있을 수 있다
    (services/validation_policy_service.py 의 ALTER TABLE DEFAULT 는 **신규 설치에만** 적용되고,
    이미 저장된 행은 코드 기본값을 바꿔도 갱신되지 않는다 — get_validation_policy() 는 항상 저장된
    실제값을 읽는다). 착수 시 (a) 코드 기본값 변경 + (b) 기존 저장 행에 대한 1회성 UPDATE 마이그레이션
    (또는 관리자 재저장 안내) 두 가지를 함께 진행해야 값이 실제로 반영된다.
  - representative_sample_limit·sample_representative_store_n 은 현재 **admin 설정 화면(UI 폼)에
    노출되지 않는다** — global_settings_gate.py 에 라벨만 등록돼 있고(조회용 audit 텍스트),
    저장은 API(POST 정책 저장 엔드포인트) 직접 호출로만 가능하다. 이번 조사 범위는 아니지만
    "값을 나중에 운영자가 조정하고 싶어도 UI 로는 못 한다"는 기존 갭이 그대로 남아있음을 참고로
    남긴다(F2 와는 별개 사안, 코드 변경 없이 발견만 기록).
  - 값 상한은 이번 조사에서 별도로 두지 않는다 — 100은 이미 실측으로 안전이 확인된 값이고,
    per_group_full_list_max 처럼 500 clamp 를 강제할 근거(운영 관찰)는 아직 없다. 향후 더 큰 값
    (예: 500)을 원하면 §2 방법론 그대로 재실측 권고.
