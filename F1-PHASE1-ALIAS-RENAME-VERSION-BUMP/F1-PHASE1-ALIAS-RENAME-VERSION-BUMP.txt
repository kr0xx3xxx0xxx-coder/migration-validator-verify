§3. 저장된 resume 상태 호환성 — '마이그레이션' 이 아니라 '무효화' 를 택했다
═══════════════════════════════════════════════════════════════════════════════

3-1. 무엇이 깨지는가(실측)
  영속화 대상은 SQLite db/migration_validator.db 의 multi_scope_run 1테이블이고,
  그 run_json 안의 pending_region.active[].key 와 pending_cells 가 bucket level 키 이름을
  문자 그대로 담는다(개명 전 "__HB1").
  개명 후 row_diff._cell_condition 의 `while (hb.BUCKET_ALIAS + str(lvl)) in cell_key` 는
  "HB1" 을 찾으므로 옛 키에서 **한 번도 매치되지 않는다** → bucket 제한 없이 조용히 진행.
  실측(tests/test_hash_alias_rename_resume_guard.py::test_old_cell_key_produces_no_bucket_predicate):
      옛 키 {"GRP":"A","__HB1":"0"} → bind params 1개(scope 만, bucket 조건 없음)
      새 키 {"GRP":"A","HB1":"0"}   → bind params 2개(scope + bucket)
  이것이 F1-G7 §7-2 가 [높음]으로 분류한 "오류 없는 오답" 이다.

3-2. 처리 방식과 사유
  **무효화**한다. 별칭 개명과 **같은 커밋**에서 계약 version 을 올렸고, 그 값이
  routes/diagnosis_route.py 의 두 재개 경로에서 저장값과 대조된다.
      /diagnosis/multi-resume         : cur.version != st["hash_contract_version"] → EVIDENCE_CHANGED
      /diagnosis/multi-row-diff-resume: 동일 검사(무조건 수행)
  version 은 match_key fingerprint 계산식의 입력이기도 해서 fingerprint 도 함께 바뀐다 → 이중 방어.

  마이그레이션(저장 JSON 의 "__HB1" 키를 "HB1" 로 치환)을 택하지 않은 이유:
    (a) 키 이름만 바꿔서는 그 상태가 **같은 canonical 계약으로 산출된 bucket 인지** 확인할 수 없다.
        틀린 상태를 그럴듯하게 이어붙이면 다시 '오류 없는 오답' 이 된다.
    (b) 무효화의 최대 비용은 재분석 1회다(중단된 run 한정). 마이그레이션의 최악은 잘못된 판정 결과다.
    (c) 설계 §3.5·§5.3-3 이 이미 이 방식(EVIDENCE_CHANGED 를 resume 안전장치로 활용)을 규정하고 있다.

3-3. 마이그레이션 대상 데이터 존재 여부(실측)
  개발 DB db/migration_validator.db 의 multi_scope_run = **0행**.
  즉 이 저장소 환경에는 무효화될 옛 run 자체가 없다. (운영 배포본에는 있을 수 있으므로
  위 차단 경로가 실제로 동작하는지는 아래 3-4 로 별도 실증했다.)

3-4. 차단이 실제로 동작하는지 실증 (DB 접속 없이, 임시 SQLite + MATCH_KEY 복원 스텁)

3-5. 검사 공백 점검
  /diagnosis/multi-resume 의 version 검사는 `if saved_mk:` 안에 있다(저장된 match_key 가 있을 때만).
  HASH 전략 run 은 match_key 없이는 애초에 진입하지 못하고(_run_hash_bucket_waves 가
  PLAN_HOLD_NO_MATCH_KEY 로 반환), match_key 가 None 인 run 은 CHUNK_KEY(KEY_RANGE) 경로라
  pending_region.strategy 가 "HASH" 가 될 수 없다. → HASH resume 이 검사를 우회하는 경로는 없다.
  row-diff resume 은 검사가 무조건 수행된다.
