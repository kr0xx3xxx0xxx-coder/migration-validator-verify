■ 2-1. _reimport_source_needs_wrapping (agg_diff_route.py:759)  ★최우선

  케이스                                     기대   문자열판정  sqlglot AST 판정
  --------------------------------------------------------------------------
  A1 동일테이블 UNION ALL / 줄바꿈 구분        True   False ✗    True  ✓
  A2 동일테이블 UNION / 줄바꿈 구분            True   False ✗    True  ✓
  A3 동일테이블 UNION / 한 줄(공백 구분)       True   True  ✓    True  ✓
  A4 리터럴 안 UNION (' UNION ')              False  True  ✗    False ✓
  A5 주석 안 UNION (-- UNION 처리 예정)        False  True  ✗    False ✓
  A6 컬럼명 credit_union_cd                   False  False ✓    False ✓
  A7 단순 1:1                                 False  False ✓    False ✓
                                            문자열 3/7 정답, AST 7/7 정답

  ▶ 누락(FN)의 근본 원인 2단 결합 — 실측으로 확인
    ① " UNION " 은 **양쪽 공백**을 요구한다. 실무 표준 포맷인
       "...WHERE GB='A'\nUNION ALL\nSELECT..." 은 앞뒤가 줄바꿈이라 **매칭 안 됨**.
    ② 앞단 가드 len(phys)>=2 도 못 잡는다. extract_physical_source_tables 가 **대문자 dedup**
       하므로 동일 테이블 UNION 은 ['T_SRC'] 1개 → 통과.
    실측: extract_cte_names=set() / extract_physical_source_tables=['T_SRC']
          ' UNION ' in raw.upper() = False → _reimport_source_needs_wrapping = False

  ▶ FN 이 실제로 만드는 오답(조용한 잘못된 결과 — 크래시 아님)
    실 파서(SqlglotParser) 산출: union_type='UNION_ALL', union_branches 2개,
      단 최상위 where_clause 는 **첫 브랜치만** = "GB = 'A'"
    → _pk_resolve 가 _derive_row_sqls 로 분기, 생성 결과:
        src = SELECT (C_NUM) AS C_NUM, (C_NM) AS C_NM FROM T_SRC WHERE GB = 'A'
        err = 없음   ← HOLD 도 아니고 오류도 아님
      두 번째 브랜치 GB='B' 포함 여부 = False  (전량 소실)
    → 재이관 상세가 원본 결과셋의 절반만 보고 "재이관 대상"을 산출한다. 정직한 HOLD 가 아니라
      **정상처럼 보이는 과소 집계**라 오늘 발견한 '문자 PK 오판정'과 동일 계열이다.

  ▶ 같은 FN 이 부수적으로 무력화하는 안전장치 2개
    agg_diff_route.py:620  _native_pk_fanout_present (fan-out 유일성 게이트)
      — 판정이 False 라 검사 자체를 건너뛴다. 하필 **동일 테이블 UNION ALL 은 PK 중복을
        만들 수 있는 대표 shape** 이므로, 게이트가 가장 필요한 곳에서 꺼진다.
    agg_diff_route.py:368  표본 preflight skip — 성능만(무해).

  ▶ 오탐(FP, A4/A5)의 영향: wrapping 경로로 감. wrapping 은 검증된 안전 경로라 결과는 정확하나,
    _derive_row_sqls_wrapped 가 _extract_aliased_inner_select 실패 시 HOLD 를 반환하므로
    **정상 동작하던 단순 SQL 이 HOLD 로 바뀔 수 있다**(리터럴에 ' UNION ' 이 있다는 이유만으로).

[6] 사용자 제안 원칙에 대한 비판적 검토
────────────────────────────────────────────────────────────────────────────
 ▶ 원칙 자체는 실측으로 뒷받침됨: 동일 7케이스에서 문자열 3/7 vs AST 7/7.
 ▶ 다만 "감지는 전부 sqlglot 으로" 를 일괄 적용하는 데는 3가지 유의점이 있다.
   ① sqlglot 은 **선택적 의존**이다(is_available→LegacyParser 폴백). AST 전환 지점마다
      폴백을 반드시 함께 설계해야 하며, 폴백 방향이 안전측인지 지점별로 다르다.
      특히 P1-1 은 현재 폴백이 False(=위험한 단순파생 경로)라 전환 시 방향 재검토 필요.
   ② 전면 전환은 파싱 비용을 늘린다. batch_route.py:1361 은 업로드 row 마다 호출되므로
      AST 전환 시 파싱 횟수가 row 수만큼 늘어난다(현재는 정규식). 캐시 또는 기존 parse_result
      재사용 여부를 함께 봐야 한다.
   ③ 더 저렴한 중간 대안이 존재한다 — analyze_service._strip_sql_literals_and_comments(378-431)를
      P2 계열(count_execution_planner / stats_validation_plan_service / select_star_expansion)에
      적용하면 오탐 9건 중 상당수가 파싱 없이 사라진다. 실측상 이 전처리를 가진 2곳은 오탐 0.
      P1(정합성)은 AST 로, P2(차단 오탐)는 우선 전처리 재사용으로 — 라는 2단 대응이
      구조 변경 폭 대비 효과가 크다.
 ▶ heuristic/explainability 영향: 이번 감사는 하드코딩을 늘리지 않는다. 오히려 UNION/CTE 판정이
   현재 5곳에 서로 다른 규칙으로 흩어져 있다(문자열 2 / 정규식 3). 단일 출처(_raw_shape 계열)로
   모으면 규칙 중복이 줄고 판정 근거도 한 곳에서 설명 가능해진다.
