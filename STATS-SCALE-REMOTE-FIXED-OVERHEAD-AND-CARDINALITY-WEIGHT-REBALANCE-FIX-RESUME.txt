작업명 : STATS-SCALE-REMOTE-FIXED-OVERHEAD-AND-CARDINALITY-WEIGHT-REBALANCE-FIX-RESUME
✅ 작업 완료 - STATS-SCALE-REMOTE-FIXED-OVERHEAD-AND-CARDINALITY-WEIGHT-REBALANCE-FIX-RESUME - 중단된 원지침은 코드 반영 0건 상태였고(파트 A·B·C 전부 미착수) 처음부터가 아니라 그 지점에서 이어서 완료했다. 원격 보정을 ×1.05 비례에서 고정 가산(+1,549ms)으로 바꾸고, 화면이 가진 축별 카디널리티를 추가 왕복 0회로 배선하면서 그룹 계열 가중치를 5.0 → 0.25(group 0.17 + cardinality 0.08)로 낮췄다. 실측 41건 시간대 일치율 80.0% → 85.0%(LOO 교차검증 70.0% → 85.0%, 순위상관 +0.853 → +0.891)로 개선이 확인되어 **'잠정' 접두를 제거**했다(등급 문자열 '잠정 중형' → '중형'). 전략 ID 는 화면 경로 41/41 무회귀 — 게이트 입력을 cost 보정값과 분리했다.

0. 요약 (결론 먼저)
════════════════════════════════════════════════════════════════════════════
 [결론 1] 재개 시점 온전성 — 원지침은 **코드에 한 줄도 반영되지 않은 상태**였다.
   워킹트리에 대상 파일 변경 0건, 관련 커밋 0건, 남은 산출물 0건이었다(§1).
   따라서 파트 A·B·C 를 이번에 전부 새로 구현했다.

 [결론 2] 파트A — 원격은 배율이 아니라 고정 가산이 맞다(실측 재현).
   1,549ms 를 '예상 소요시간' 축에서 더한다. 그 결과 1만행에서는 +4,083 cost point
   에 해당하는 큰 보정이, 5,000만행에서는 +0.044 로 사실상 0 이 된다. 종전 ×1.05 는
   정확히 반대로 규모가 클수록 가산량이 커졌다(1만행 +0.431 → 5,000만행 +0.801).

 [결론 3] 파트B — 카디널리티는 '전송 + 가중치 재조정'을 반드시 같이 해야 한다(재확인).
   현행 가중치 그대로 전송하면 일치율 62.5% · 순위상관 +0.532 로 크게 나빠진다(반증 실측).
   재조정 후에는 85.0% · +0.891 이다.
   지침이 제시한 회귀 비례값 0.46 은 실측에서 77.5%(LOO 62.5%)로 **수정 전보다 나빴고**,
   같은 41건으로 재검증해 총합 0.25 를 채택했다(지침이 허용한 미세조정 범위 §4-2).

 [결론 4] 파트C — '잠정' 제거 조건(85% 이상)을 실제로 충족해서 제거했다.
   중앙 측정치 85.0% / 최소 측정치 82.5% / 최대 측정치 75.0% / LOO 85.0% —
   네 지표 전부 수정 전보다 높다. 어느 하나라도 하락했으면 접두를 유지할 계획이었다.

 [결론 5] 전략 ID 는 화면 경로에서 전건 불변이다.
   화면이 보내기 시작한 카디널리티는 '상한 추정'이라 cost 는 기울이되 실행 차단(STATS_HOLD)·
   표본전환(STATS_SAMPLE_ONLY) 판정에는 쓰지 않도록 게이트 입력을 분리했다(§5).

3. 파트A — 원격 배율(×1.05) → 고정 가산
════════════════════════════════════════════════════════════════════════════
[3-1] 무엇을 바꿨나
  remote_overhead_ms = 2 × ((접속 465.0 − 34.5) + 5 × (RTT 71.3 − 2.5)) = 1,549ms
    · 2       = 원본·목적지 두 번
    · 5왕복   = SET TRANSACTION READ ONLY / SET LOCAL timeout / SHOW / 본쿼리 / ROLLBACK
    · 상수    = 벤치마크 §5-1 실측(원격 접속 472.7·457.3ms / 1왕복 71.58·71.00ms,
                로컬 접속 34.5ms / 1왕복 2.51ms). 로컬 기준선은 cost↔시간 보정이 이미
                흡수하므로 '초과분'만 더한다.
    · profile.remote_connect_ms / remote_rtt_ms 가 오면 그 값을 쓴다(추가 왕복 0회).
      이 값을 얻으려고 새 왕복을 만들지 말 것을 필드 주석에 못박았다.

  cost 는 log 합이라 여기에 상수를 더하면 시간 축에서는 '배율'이 되어 버린다. 그래서
  cost → 예상 ms → + overhead → cost 로 되돌린다. 보정식은 현재 가중치로 계산한 cost 와
  실측 소요시간(로컬 37건)의 최소자승 적합이다:
      log10(ms) = 0.4100 · cost − 2.0076      (R² = 0.771)

[3-2] 실측 — 가산분은 규모와 무관, 상대영향은 규모가 커질수록 감소
        규모(행)   로컬예상(ms)  원격예상(ms)   가산분(ms)   상대영향   전 방식Δcost  후 방식Δcost
          10,000          34        1,583        1,549    4621.0%        0.431        4.083
         100,000         221        1,771        1,549     699.5%        0.531        2.202
       1,000,000       1,463        3,013        1,550     105.9%        0.631        0.765
      10,000,000       9,669       11,213        1,545      16.0%        0.731        0.157
      50,000,000      36,187       37,722        1,535       4.2%        0.801        0.044
  → 가산분 일정(1,535~1,550ms) · 상대영향 단조 감소 ✅ (벤치마크 §5-2 의 +2,179~2,465ms 와
    같은 자릿수. 공식값이 실측보다 다소 작은 이유는 TLS·드라이버 오버헤드가 공식에 없기
    때문이며, 이는 벤치마크 §5-3 이 이미 지적한 차이다.)
  → 전 방식(×1.05)은 Δcost 가 0.431 → 0.801 로 **커진다**. 실측과 정반대였다.

[3-3] 계약 테스트로 고정
  tests/test_strategy_remote_flag_evidence.py 를 '5% 배율' 계약에서
    · cost_remote == _ms_to_cost(_cost_to_ms(cost_local) + overhead_ms)  (정확 일치)
    · gap(1만행) > gap(100만행) > gap(5,000만행)                          (가산 특성)
  으로 바꿨다. 비례 보정이 되살아나면 이 테스트가 깨진다.

4. 파트B — 카디널리티 전송 + 가중치 재조정
════════════════════════════════════════════════════════════════════════════
[4-1] 배선 (추가 DB 왕복 0회)
  ui/grid_helpers.py `_mvGbAxisCardinalities(effGb)` 신설 →
  `_mvBuildStatsScaleProfile()` 이 group_cardinalities 로 실어 보낸다.
    · 근거 필드는 화면이 이미 쓰는 것과 동일: 후보표 체크박스의 data-distinct(=_candDistinctCount)
      와 data-nullp(NULL 존재 → SQL GROUP BY 는 NULL 도 한 그룹 → +1).
      _updateGroupCountEstimate 와 같은 규칙을 재사용했다(단일 출처).
    · 대상은 최종 선택(_collectCheckedCols('gb'))에 남은 축뿐 — 기간 미선택 날짜형 후보처럼
      실행 계획에서 빠지는 체크는 여기서도 뺀다.
    · distinct 근거가 없는 축은 값을 지어내지 않고 뺀다(과소추정 쪽으로 안전).
    · estimated_group_count 는 따로 보내지 않는다 — 서버 _axis_group_sum 이 이 배열의 합으로
      같은 값을 만든다. 두 곳에서 계산하면 갈라지므로 배열 하나만 보낸다.
  node 로 번들을 실제 실행해 확인(문자열 검사 아님, §7-2).

[4-2] 가중치 — 왜 0.46 이 아니라 0.25 인가
  지침의 0.46 은 회귀식 scan:groups = 0.819:0.189 를 scan 가중치 2.0 에 비례시킨 값이다.
  같은 41건으로 총합 0.0~1.0 을 재검증한 결과:
        총합    최적밴드                 중앙 일치율   LOO 교차검증
        0.00   (12.59,13.62,14.76)        80.0%        70.0%      ← 카디널리티 미반영(파트A만)
        0.15   (12.76,14.10,15.42)        85.0%        80.0%
        0.20   (12.81,14.13,15.45)        85.0%        82.5%
        0.25   (12.87,14.14,15.50)        85.0%        85.0%      ← 채택
        0.30   (12.93,14.21,15.52)        82.5%        72.5%
        0.46   (13.13,14.59,15.73)        77.5%        62.5%      ← 지침 제시값(수정 전보다 나쁨)
        0.70   (13.45,14.23,17.93)        80.0%        67.5%
  0.46 이 나쁜 이유는 실측으로 설명된다. 회귀식의 groups 는 '실제 결과 그룹 수'인데 cost 가
  받는 값은 '축별 예상 distinct 합'으로 변수가 다르고, 회귀에서 groups 계수는 scan·sets 와
  섞여 부풀려져 있다. 조건을 고정한 대조 측정이 더 깨끗한 근거다 —
    · 같은 1,000만행에서 카디널리티 20 → 100,000: 26,459ms → 29,792ms (+12.6%)
      → 이 대조에서 역산한 계수는 0.034 수준으로 회귀값(0.46)보다 훨씬 작다.
  채택값 0.25 는 대조 측정(0.034)과 회귀(0.46) 사이이며, 두 지표(중앙 일치율·LOO)가 동시에
  최고인 구간이다. group : cardinality = 0.17 : 0.08(2:1) 분배는 단일축에서 두 값이 사실상
  같은 양이라 결과에 영향이 없다 — 어느 쪽도 죽은 필드가 되지 않도록 둘 다 살려 뒀다.

[4-3] 반증 재현 — 가중치 재조정 없이 전송하면 나빠진다(지침 B-3 확인)
        모델                                일치율   LOO    순위상관
        수정 전(현행)                        80.0%   70.0%   +0.853
        파트A만(원격 고정가산)                80.0%   70.0%   +0.853
        파트B만(카디널리티+가중치, ×1.05 유지)  77.5%   60.0%   +0.885
        파트A+B (채택)                       85.0%   85.0%   +0.891
        (반증) 가중치 그대로 + 카디널리티 전송  62.5%   57.5%   +0.532
  → 파트A 단독은 이 데이터셋에서 등급 개선이 0 이다(원격 케이스가 3건뿐이고 셋 다 원래도
    맞았다). 개선은 A+B 결합에서 나온다. 이 사실을 숨기지 않고 그대로 적는다.

5. 전략 선택 게이트 영향 확인 (지침 B-4)
════════════════════════════════════════════════════════════════════════════
[5-1] 배선만 하면 전략 ID 가 바뀐다 — 실제로 재현됐다
  카디널리티를 그대로 게이트에 넣으면 지금까지 한 번도 발화한 적 없는 분기가 켜진다:
        카디널리티     스캔          배선 전              배선 그대로 넣었을 때
         5,000,000   10,000,000   STATS_DIRECT_AGG    STATS_SAMPLE_ONLY
         9,000,000   10,000,000   STATS_DIRECT_AGG    STATS_HOLD
        49,000,000   50,000,000   STATS_SAMPLE_ONLY   STATS_HOLD
         6,000,000   20,000,000   STATS_DIRECT_AGG    STATS_HOLD

[5-2] 그래서 cost 보정값과 게이트 입력을 분리했다
  화면이 보내는 distinct 는 후보표의 **상한 추정**이다(표현식 근거 추정 포함, 날짜축은
  기간 단위가 아니라 원본 컬럼 distinct 라 과대추정). cost 를 기울이는 근거로는 충분하지만
  실행을 차단(STATS_HOLD)하거나 표본검증으로 돌리는(STATS_SAMPLE_ONLY) 판정 근거로 쓰기에는
  신뢰도가 부족하다. 그래서 전략 선택 조건은 호출자가 estimated_group_count 를 **명시 선언**
  했을 때만 그룹/카디널리티 근거를 인정하도록 했다(grade_basis.gate_* 로 근거도 남긴다).
    · 화면 경로(배열만 전송)  → 게이트 입력 없음 = 종전과 동일 → 전략 ID 불변
    · 확정 근거 경로(명시)     → 종전대로 HOLD/SAMPLE_ONLY 도달 가능(기존 계약 보존)

[5-3] 결과
  실측 41건 전건 전략 ID 불변(41/41). 고카디널리티 합성 4건도 화면 경로에서 전건 불변.
  ※ 부수 변화 1건(무해): stats_plan.confidence 가 LOW → HIGH 가 된다(예상 그룹 수 근거가
    생겼으므로 정의상 맞다). 이 필드를 읽는 화면은 없다(실행계획 카드는 표시하지 않는다).
