2. reclaim_stale() 결함 A 수정
────────────────────────────────────────────────────────────
대상: `services/batch/validation_scheduler.py`

- `ValidationScheduler.__init__` 에 `heartbeat_interval_sec: float = 5.0` 파라미터 추가.
- `_run_job()` 에서 worker 실행 직전 배경 heartbeat 스레드(`_heartbeat_loop`)를 시작 —
  `threading.Event.wait(interval)` 로 실제 벽시계 시간마다 `self.heartbeat(job_id)` 를 호출해
  `last_heartbeat` 를 갱신한다. `execute_fn()` 이 끝나면 `finally` 블록에서 `stop_hb.set()` 으로
  즉시 정지(불필요한 갱신 방지).
- 가짜 clock(테스트 주입용)은 heartbeat 값 자체(`self._now()`)에는 그대로 반영되지만,
  스레드 tick 간격은 실제 wall-clock 을 쓴다 — stale 판정(reclaim_stale)의 "정지 여부"는
  clock 축이고, tick 주기는 스케줄링 축이라 서로 다른 시간 개념임을 주석으로 명시.

검증(실측):
- 신규 테스트 `test_heartbeat_wired_keeps_long_running_job_alive`
  (`tests/test_validation_scheduler.py`): heartbeat_interval_sec=0.05 로 job 을 0.3초 동안
  실행 상태로 유지한 뒤 `reclaim_stale(lease_timeout_sec=0.15)` 호출 — 결함A 수정 전이면
  0.3s > 0.15s 이므로 반드시 STALE 판정됐을 상황인데, 자동 heartbeat 덕분에
  `stale == []`(STALE 0건), job 은 계속 RUNNING 으로 확인됨.
- 기존 `test_stale_job_reclaim`(가짜 clock 사용, heartbeat 정지 시나리오)도 그대로 통과 —
  배경 스레드의 기본 간격(5초)이 테스트 실행시간(<1.5초)보다 길어 간섭 없음을 실측으로 확인.

3. reclaim_stale() 결함 B / 실배선
────────────────────────────────────────────────────────────
지침대로 손대지 않았다. `_finish()` 비멱등 문제(결함B, budget 이중 반환 위험)는 완료 모듈
수정이라 이번 범위 밖으로 남겨두었고, `reclaim_stale()` 자체를 폴링 루프에 연결하는 작업도
결함B 해결 전까지 보류했다. `reclaim_stale` 은 현재도 프로덕션 호출처 0건(routes/ 전체 grep
재확인)이라 이번 변경이 기존 동작을 바꾸지 않는다.
