작업명 : PK-RANGE-CHUNK-BOUNDARY-ORDERING-ASSUMPTION-DIAGNOSE
⚠️ 추가 작업 필요 - 청크 전제는 "윈도우 유무"가 아니라 "청크 키가 PARTITION BY 컬럼에 있는가"로 갈리며, 코드는 이 전제를 전혀 검증하지 않는다 — 문자 PK 지정 시 60% 미조회 후 "일치" 오판정까지 실측 재현

────────────────────────────────────────────────────────────────────────────
0. 한 줄 결론
────────────────────────────────────────────────────────────────────────────
pk_range_chunk.py 헤더가 선언한 "전체 테이블 global ORDER BY 없이 chunk 로 나눠 읽는다"는
전제는 원본 SQL 형태에 따라 성립하기도 하고 완전히 깨진다. 갈림길은 윈도우 함수의 유무가
아니라 **청크 키가 그 윈도우의 PARTITION BY 컬럼 집합에 포함되는가**였다(실행계획으로 확정).
그리고 이 전제는 코드 어디에서도 검증되지 않는다 — 확인 없이 가정하고 실행한다.

지시 4의 가설("청크를 키우면 정렬 비용도 비례해 커지나?")은 방향이 반대로 확정됐다:
정렬 비용은 청크 크기와 무관한 고정비용이고, 총 정렬 비용은 청크 개수에 비례한다.

────────────────────────────────────────────────────────────────────────────

  ▶ 불균형 재현됨(최대/평균 4.95배). 값 범위만 균등 분할하므로 행 수 균등은 보장되지 않는다.

[이상치 PK 1건이 만드는 chunk 폭증]
  목적지에 PK 이상치 1건(99,999,999) → 합집합 범위가 그대로 늘어 chunk 6개 → 2,000개,
  그중 1,994개가 빈 chunk. WRAPPED 고정비용 0.343s/chunk 적용 시 순수 낭비 약 684초(11.4분).

[불균형이 실제로 해치는 것 — 코드 근거]
  · 메모리 스파이크 : chunk 조회는 cur.fetchall() 전량 적재(oracle.py:518 / postgresql.py:405)
  · 진행률 왜곡    : 진행률 메인 축이 chunks_done/chunks_total(pk_range_chunk.py:364)
  · 재개 단위 왜곡  : checkpoint 는 chunk 경계마다(pk_range_chunk.py:453-458) → 과대 chunk 통째 재실행
  · 조기중단 편향   : min_decision_count 는 처리 '행 수' 기준인데 표본이 한 chunk 에 몰릴 수 있음

[비숫자 PK — 자동 경로는 막혀 있고, 명시 지정 경로는 뚫려 있다]
  방어되는 쪽: services/diagnosis/key_evidence.py:320·334(양측 norm_type != NUMBER → continue),
              :111·:177(NUMBER/DATE_TIME 만) → 문자 PK 는 chunk key 로 확정되지 않는다.
              뚫려도 agg_diff_route.py:274-280 의 int() 실패 → HOLD_NON_NUMERIC_PK.
  뚫리는 쪽 : agg_diff_route.py:801-802 — req.key_src/key_tgt 를 호출자가 지정하면
              위 타입 게이트를 전부 건너뛰고 그대로 사용한다.

  ★ 실측 재현(키 = TO_CHAR(ID), 운영 엔진 함수 직접 호출)
      ora_pk_min_max      → MIN='1'  MAX='99999'   ← 문자 정렬(실제 숫자 최대는 250,050)
      route 의 int()      → 성공(1, 99999)          ← HOLD 발동 안 함
      build_chunk_bounds  → chunk 2개, 커버 1~99,999
      249,950행 중 커버 99,959 · 커버 밖 149,991행(60.0%)가 조회 자체에서 제외
      make_ora_fetch_chunk(1,51) → 오류 없이 성공(오라클 암묵 형변환)

  ★ 판정까지의 영향(목적지 ID>150,000 구간에 값 불일치를 심고 run_pk_range_chunk_compare 호출)
      키                     chunk  상태                            판정
      ────────────────────  ─────  ─────────────────────────────  ─────────────────────────
      문자 PK(TO_CHAR(ID))      2   READY                          재이관 0건·ratio 0.0 (거짓 일치)
      숫자 PK(대조군, 동일 조건)  6   EARLY_STOPPED_MISMATCH_LIMIT   값 불일치 500건 검출
      → 같은 데이터·같은 불일치인데 키 표현만 문자로 바뀌면 오류도 경고도 없이 "일치"가 된다.

[부수 발견 — int() 0방향 절단]
  실제 범위 -250050.5 ~ -1.5 → int() 후 -250050 ~ -1 → 하한 미만 1건이 조회 범위 밖.
  (상한은 build_chunk_bounds 가 pk_max+1 반열림으로 감싸 안전. 하한만 취약.)

3. 지시 3 — 청크 경계(ID)와 원본 내부 정렬(PARTITION BY 다른 컬럼) 재확인
────────────────────────────────────────────────────────────────────────────
[운영 chunk 조회 SQL 실행계획]  oracle.py:515 / postgresql.py:402 형태 그대로 측정

  원본     계획(요약)                                                    최상위 card  chunk 1개  전체
  ──────  ───────────────────────────────────────────────────────────  ──────────  ────────  ───────
  PLAIN   TABLE ACCESS BY INDEX ROWID ← INDEX RANGE SCAN (정렬 없음)        49,980    1.684s   14.045s
  WRAPPED SORT ORDER BY ← VIEW ← WINDOW SORT ← HASH JOIN
          ← TABLE ACCESS FULL                                             249,950    2.060s    8.923s

  ▶ WRAPPED 는 5만행 chunk 를 요청해도 계획의 모든 단계 card 가 249,950 — 청크 술어가 뷰 안으로
    전혀 내려가지 못한다. "청크로 나눠도 내부 정렬은 여전히 전체 필요"가 실행계획으로 확인됐다.

[★ 정확한 갈림길 확정 — PARTITION BY 컬럼만 바꾼 대조 실험]

  원본                                  계획                                        최상위 card  빈 chunk 1개
  ───────────────────────────────────  ─────────────────────────────────────────  ──────────  ──────────
  PARTITION BY C_CHAR (청크키와 다름)    SORT ORDER BY ← WINDOW SORT ← TABLE FULL     249,950     0.327s
  PARTITION BY ID     (청크키와 같음)    VIEW ← WINDOW NOSORT ← INDEX RANGE SCAN       49,980     0.003s
  윈도우 없음(CTE+JOIN만)                NESTED LOOPS ← INDEX RANGE SCAN               49,980     0.003s

  ▶ 윈도우 함수의 존재 자체가 barrier 가 아니다. 청크 키가 PARTITION BY 컬럼 집합에 포함되면
    옵티마이저가 술어를 윈도우 아래로 밀 수 있고(파티션 경계를 바꾸지 않으므로), 결과는
    WINDOW NOSORT — 정렬 자체가 사라진다. 다르면 청크마다 원본 전체를 다시 스캔·정렬한다.
    오늘 실측 원본은 ROW_NUMBER() OVER (PARTITION BY C_CHAR ORDER BY ID) + 청크 키 ID
    = 정확히 pushdown 불가 조합이다.

4. 지시 4 — 청크 크기와 정렬 비용의 관계(확정)
────────────────────────────────────────────────────────────────────────────
[청크 1개당 고정비용 분리 측정 — 0행 반환 chunk 로 행 전송 비용 제거]
  PLAIN    빈 chunk 1회 0.002~0.003s   (인덱스 range scan 이 즉시 0행)
  WRAPPED  빈 chunk 1회 0.257~0.343s   (0행을 돌려주려고 25만행 full scan + window sort 완주)

[전 chunk 순회 실측 — 동일 25만행 전량 처리]
  원본      250,050(1개)   125,025(2개)   50,000(6개)    25,000(11개)
  ───────  ────────────  ────────────  ────────────  ─────────────
  PLAIN     8.33s(기준)    7.86s(0.94×)  7.97s(0.96×)   7.89s(0.95×)
  WRAPPED   8.26s(기준)    8.54s(1.03×)  10.29s(1.25×)  12.07s(1.46×)

[모델 검증]  총시간 ≈ 단일chunk시간 + (chunk수-1) × 고정비용(0.273s)
  chunk 2개 예측 8.54s / 실측 8.54s · 6개 예측 9.63s / 실측 10.29s · 11개 예측 10.99s / 실측 12.07s
  → 방향·차수 일치(실측이 조금 높은 건 chunk 마다 붙는 왕복·파싱 오버헤드).

  ★ 확정 답: 정렬 비용은 청크 크기에 비례해 커지지 않는다. 청크 크기와 무관하게
    "매 청크마다 원본 전체 정렬 1회"가 고정으로 발생하고, 총 정렬 비용은 청크 개수에 비례
    (= 청크 크기에 반비례)한다. 따라서 "규모에 비례해 청크를 키우면 정렬 비용도 커진다"는
    우려는 방향이 반대다 — 키울수록 총 정렬 비용은 줄고, 하한은 "청크 1개 = 청크 미사용"이다.
    PG 교차근거: STATS_VALIDATION_CHUNKED_VS_SINGLE_TRADEOFF.md §4 — CTEWIN 은 청크당 시간이
    N 과 무관하게 21~24초로 일정, 청크 200개면 단일 대비 약 150배.

6. 대응 방향 제안(구현하지 않음 — 각각 별도 승인 필요)
────────────────────────────────────────────────────────────────────────────
  1) 경계 신뢰성 게이트(정합성·필수) — MIN/MAX 반환값의 실제 타입이 숫자인지 확인(문자면 HOLD),
     커버 범위 밖 행 수를 사전 확인해 0 이 아니면 HOLD. int() 절단 대신 floor/ceil 로 범위 확장.
  2) pushdown 사전 판정(전략) — sqlglot 파싱으로 (a) 윈도우 PARTITION BY 컬럼에 청크 키가 있는지,
     (b) 파생 안에 DISTINCT/GROUP BY/집계/UNION 이 있는지 검사. 불가면 청크 전략을 선택하지 않는다.
  3) 불균형 노출(관측성) — chunk 별 실제 행 수·빈 chunk 비율·최대 chunk 배수를 metrics/진행률에 표기.
  4) 경계 산정 비용 회피(성능) — pushdown 불가 형태에서 목적지 물리 테이블 기준 경계 취득 검토
     (원본 필터와 범위가 달라질 수 있어 커버리지 재확인 필수).
  5) 이상치 방어(운영) — chunk 수가 정책 임계를 넘으면 실행 전 HOLD + 사유 표시.

  ✗ 하지 말 것: "청크 크기를 규모에 비례해 키운다"를 정렬 비용 대책으로 삼는 것.
    pushdown 가능 형태엔 애초에 정렬 비용이 없고, 불가 형태에선 종착점이 "청크 1개 = 청크 미사용"이다.
    규모 비례 확장은 부분 결과 노출 주기를 정하는 문제지 정렬 비용 문제가 아니다.

    문자 PK 를 먼저 차단하므로, 재현 조건은 "key_src/key_tgt 명시 지정" 경로다.
    자동 경로에서 곧바로 발생하는 결함이라고 주장하지 않는다.

    exact_diff store 에 남는다.
  · 코드 수정이 없으므로 회귀 테스트는 수행하지 않았다(운영 모듈 무변경).
