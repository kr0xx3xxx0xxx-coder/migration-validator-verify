================================================================================
1. 문제 (수정 전)
================================================================================
routes/exact_diff_route.py 의 _derive_row_sqls 는 parse_result 로 행 수준 원본 SELECT 를
재조립한다. select_items 의 src_expr 은 원본 별칭을 그대로 달고 오는데(FROM T s → 's.ID'),
FROM 절에는 from_alias 를 반영하지 않아 존재하지 않는 상관자를 참조했다.

  수정 전 산출:
    SELECT (s.ID) AS ID, (s.DEPT_CD) AS DEPT_CD, (s.AMT) AS AMT FROM NXDNP.MV_ORA_DEMO_SRC
                                                                 ^^^ 별칭 s 없음

UI 의 재이관 prepare payload 에는 src_sql/tgt_sql 이 없어 서버가 항상 이 재파생 경로를 타므로,
별칭을 쓴 단순 1:1 이관 SQL 은 재이관 상세 조회에서 그대로 크래시했다(방언 무관, WHERE 의 별칭
참조도 동일한 원인). 형제 빌더 4곳(source_count_sql_builder:32, pre_validator._build_from,
stats_sql_builder:84, column_profile_service:264)은 모두 별칭을 보존하고 있어 이 경로만의 결함.

================================================================================
2. 수정 내용 (방식 B — 기존 wrapping 처리 경로 재사용)
================================================================================
지침대로 FROM 절 alias 반영을 새 로직으로 만들지 않고, '별칭 유무' 단일 판정으로 이미 검증된
wrapping 산출 형태로 넘겼다. 판단 로직은 한 곳(_derive_row_sqls 내 fa 분기)에만 둔다.

(a) _wrap_as_derived_src(inner_select)  [신규 · 단일 정의]
    행 수준 원본 SELECT 를 파생 테이블로 감싸는 형태의 단일 출처.
      SELECT * FROM (\n <원본 SELECT> \n) mv_reimport_src
    기존 wrapping 경로 _derive_row_sqls_wrapped 의 인라인 문자열을 이 함수 호출로 치환했다
    (출력 문자열 동일 — 별칭 규약 mv_reimport_src / 밑줄 시작 금지(ORA-00911)도 그대로 승계).

(b) _derive_row_sqls 의 별칭 분기  [신규]
      fa = pr['from_alias']
      if fa:  src = _wrap_as_derived_src(f"SELECT {sel} FROM {ft} {alias}" + WHERE...)
      else :  src = 기존 문자열 그대로(무회귀)
    별칭이 살아 있는 원본 SELECT 를 파생 테이블로 감싸 최상위를 평범한 SELECT 로 유지하므로,
    하위 소비처(키 재확인 probe · scope pushdown · chunk 어댑터)가 상관자 별칭을 볼 일이 없다.
    wrapping 의 성능 페널티는 0 으로 이미 실측됨(PLAIN-JOIN-WRAPPING-EXPLAIN-PLANS).

(c) _alias_as_used(items, from_alias)  [신규 · 안전장치]
    파서는 from_alias 를 대문자로 정규화('S')하는 반면 src_expr 은 원본 표기('s.ID')를 유지한다.
    Oracle/PostgreSQL/MSSQL 은 비인용 식별자 대소문자를 구분하지 않아 무해하지만 MySQL 은
    테이블 별칭이 대소문자를 구분하므로, src_expr 에 실제로 쓰인 접두사 표기를 우선 사용한다
    (4개 방언 공통 안전값). 접두사를 못 찾으면 파서 값 그대로 폴백. 유사 이름(ss.)은 오탐하지 않음.

  수정 후 산출(별칭 케이스):
    SELECT * FROM (
    SELECT (s.ID) AS ID, (s.DEPT_CD) AS DEPT_CD, (s.AMT) AS AMT FROM NXDNP.MV_ORA_DEMO_SRC s
    ) mv_reimport_src

  ※ 별칭 없는 경로는 문자열 단위로 수정 전과 완전히 동일(테스트로 고정, 아래 4-2 fingerprint 로도 확인).
  ※ agg_diff_route.py 는 손대지 않았다(병행 작업과 파일 미충돌). 수정 지점이 재파생 함수 자체라
     세 호출부(_pk_resolve, /exact-diff/run, agg_diff_route:1430) 전부에 동일하게 적용된다.

5. 구조 검토 (CLAUDE.md 비판적 검토 의무)
================================================================================
- 긍정적 효과: 별칭을 쓴 가장 흔한 형태의 이관 SQL에서 재이관 상세가 조용히 막히던 문제 해소.
  수정 지점이 재파생 함수 자체라 세 호출부에 일괄 적용된다.
- 구조적 문제점: 감싸기 형태 문자열이 두 곳에 흩어질 뻔했으나 _wrap_as_derived_src 단일 정의로
  통합했다(_derive_row_sqls_wrapped 도 이 함수를 쓰도록 치환 — 출력 동일).
- heuristic 영향: _alias_as_used 의 정규식 접두사 탐색이 새 heuristic 이다. 다만 파서가 별칭을
  대문자로 정규화하는 알려진 사실에 대한 좁은 보정이고, 실패 시 파서 값 그대로 폴백이라 위험이 낮다.
- 잔여 위험: parse_result 의 from_alias 가 비어 있는데 src_expr 에는 별칭이 남는 shape(파서가 CTE
  평탄화 시 from_alias 를 비우는 경로 등)는 여전히 구 경로를 탄다. 다만 그 shape 는
  _reimport_source_needs_wrapping 이 True 로 잡아 wrapping 경로로 가므로 실사용상 겹치지 않는다.
- 운영상 위험: 낮음. 별칭 없는 경로는 산출 SQL 이 바이트 단위로 동일해 롤백 없이도 기존 동작 보존.
