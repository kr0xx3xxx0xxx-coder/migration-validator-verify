1. 결론 (셋 중 택1)
──────────────────────────────────────────────────────────────────────────
▶ "이미 안전하게 HOLD됨 (추가조치 불요)"
  - 이관 SELECT 목록에서 PK(ID)를 빼고, 대체 유일키도 없을 때(C_NUM 중복) 시스템은
    안정적 비교키(MATCH KEY) 확정 실패 → 정직한 HOLD 로 처리한다.
      status=HOLD · stop_reason=MATCH_KEY_HOLD
      error_message="안정적인 비교키(MATCH KEY)가 확인되지 않아 재이관 PK 계산을 보류합니다."
  - 조용히 틀린 결과를 반환하지 않는다(가장 위험한 케이스 아님). 서버 500/크래시도 아니다.
  - 단순 1:1(_derive_row_sqls)·CTE/JOIN(_derive_row_sqls_wrapped) 두 형태 모두 동일하게 HOLD.

▷ 부수 관찰(긴급 아님 · 별도 제안): 대용량(>5만행) stream 경로에서는 동일한 HOLD 사유가
  '계산'은 되지만 화면 표출 문구가 저하된다(아래 4항). 조용히 틀린 결과·500 은 아니다.

2. 재현 픽스처 (실 오라클, 신규 전용 테이블 — 기존 데이터 미변경)
──────────────────────────────────────────────────────────────────────────
  asis  NXDNP.MV_ORA_NOPK_SRC : ID NUMBER PK, C_NUM NUMBER, C_VARCHAR2 VARCHAR2(50)  총 30행
        · C_NUM = MOD(ID,5)  → distinct 5개(대량 중복 = 유일키 후보 아님)
  tobe  NXDNP.MV_ORA_NOPK_TGT : C_NUM, C_VARCHAR2 만 (ID 컬럼·PK 없음)             총 27행
        · 원본 30행 중 3건(ID 11,12,13) 미이관 → COUNT 30 vs 27 (재이관 대상 유발)

  이관 SQL — PK(ID)를 의도적으로 SELECT 목록에서 제외:
   A) 단순 1:1 : INSERT INTO ...MV_ORA_NOPK_TGT (C_NUM,C_VARCHAR2)
                 SELECT C_NUM, C_VARCHAR2 FROM ...MV_ORA_NOPK_SRC            (ID 없음)
   B) CTE/JOIN : INSERT INTO ...(C_NUM,C_VARCHAR2) WITH ranked AS (
                   SELECT s.ID, s.C_NUM, s.C_VARCHAR2,
                          ROW_NUMBER() OVER (PARTITION BY s.C_NUM ORDER BY s.ID) rn
                   FROM ...NOPK_SRC s LEFT JOIN ...NOPK_SRC t ON s.ID=t.ID )
                 SELECT C_NUM, C_VARCHAR2 FROM ranked WHERE rn>=1            (최종 투영에 ID 없음)

3. 실측 결과 (서버 응답 원문 · 두 케이스 동일)

                     msg="안정적인 비교키(MATCH KEY)가 확인되지 않아 재이관 PK 계산을 보류합니다."
     B_cte_join    : HTTP 200 · status=HOLD · stop_reason=MATCH_KEY_HOLD  (동일 문구)

     → 브라우저 인증 세션(포트 8000)에서 UI 드릴다운이 호출하는 바로 그 엔드포인트로 호출해도 동일 HOLD.

  [대용량 stream 경로(>5만행)] POST /agg-diff/prepare (stream=true, PK_RANGE_CHUNK_COMPARE)
     A/B 공통 : prepare → HTTP 200 status=PREPARING + run_id
               이후 GET /agg-diff/pk-records → ok=false, error="재이관 PK index 를 찾을 수 없습니다."
     → HOLD 사유(MATCH_KEY_HOLD)가 계산은 되나(엔진 가드), 비동기 job 구조상 그 사유가 조회 API 로
       전달되지 않고 일반 문구로 표출된다. (조용히 틀린 결과·500 아님)

  인프로세스 _pk_resolve 프로브(실 오라클 메타데이터): 세 키 경로 모두 확정 거부 →
     key_src="", key_tgt="" (빈 키) · err="" · unique_native=false · chunk_key_trusted=false
     ※ C_NUM(NUMBER NOT NULL이지만 중복)이 비교키로 '승격되지 않음'을 실측 확인 = 유일성 보호 정상 작동.

4. 감지/방어 코드 위치 (파일:라인) — 지시 3·4 응답
──────────────────────────────────────────────────────────────────────────
  Q. `_reimport_source_needs_wrapping` / `_derive_row_sqls_wrapped` 근방에 'PK 컬럼 부재'를
     사전 체크하는 코드가 있는가?
  A. 없다(명시적 'PK가 SELECT에서 빠짐' 이름/사전 체크는 그 두 함수에 없음).
     · routes/agg_diff_route.py:613  _reimport_source_needs_wrapping → 형태(CTE/JOIN/UNION)만 판정
     · routes/exact_diff_route.py:89 _derive_row_sqls_wrapped → raw/cols/tgt 존재 + inner-select 추출만.
       SELECT*/INSERT 컬럼수 불일치는 잡지만 'PK 부재' 자체는 검사하지 않음.
       ('SELECT * FROM (원본) mv_reimport_src' 로 원본 투영을 보존 → ID 없으면 없는 채로 통과)
     · routes/exact_diff_route.py:61 _derive_row_sqls(단순 1:1) → len(items)==len(cols) 등만.

  대신 PK 부재 방어는 '비교키 확정 계층'에서 이뤄진다(정직 HOLD 로 귀결):
     · routes/agg_diff_route.py:564  _resolve_native_pk_key ① 정식PK
         all(pk_col in insert_cols) — PK가 매핑에 모두 없으면 스킵.
     · services/diagnosis/key_evidence.py:314-316  resolve_trusted_chunk_key
         target 물리 PK 가 select_item 으로 lineage 매핑돼야 TRUSTED — ID 미투영 시 NOT_TRUSTED.
     · routes/agg_diff_route.py:494  _resolve_matchkey_via_diagnosis ②UK/③업무키
         결과집합 재확인(NULL 없음 + 중복 없음 _dup_present) 통과해야 확정 — C_NUM 중복이라 거부.
     · services/diagnosis/key_evidence.py:371 resolve_confirmed_chunk_key
         목적 테이블 contract 후보 — 저카디널리티/비유일 컬럼 EXCLUDED(실측상 C_NUM 배제됨).
     ▶ 종단 가드(빈 키 → HOLD):
         services/exact_diff/agg_contribution.py:194-196  prepare_reimport_pk_index(동기)
         services/exact_diff/agg_contribution.py:472-474  prepare_reimport_pk_index_stream(스트림)
             if not (key_src and key_tgt): return status=HOLD, stop_reason=MATCH_KEY_HOLD

  단순 1:1 경로(_derive_row_sqls)와 CTE/JOIN 경로(_derive_row_sqls_wrapped)는 파생 SQL 만 다르고
  이후 동일한 _pk_resolve → 동일 종단 가드를 타므로, 두 경로의 PK 부재 처리에 갭 차이가 없다(동일 HOLD).

  주의(설계 뉘앙스): confirm_chunk_key(key_evidence.py:382)는 NULL 부재만 검사하고 유일성은 재검사하지
  않는다. 유일성 보호는 (a) contract 의 비유일 컬럼 EXCLUDED 와 (b) 경로②③의 _dup_present 중복검사에
  의존한다. 이번 실측에서 중복 C_NUM 이 확정되지 않아 end-to-end 로는 안전함을 확인했다.
