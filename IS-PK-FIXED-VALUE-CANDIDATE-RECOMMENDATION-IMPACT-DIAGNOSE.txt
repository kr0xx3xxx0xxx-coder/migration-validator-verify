작업일 : 2026-07-31
유형   : 진단 전용 (코드 수정 없음 / read-only 조회만 수행)
대상   : services/db_query_service.py:1274 `_cmn_fetch_tgt_col_meta` 의 `'is_pk': False` 고정값

================================================================================
0. 요약 결론
================================================================================
- `is_pk` 를 실제로 읽는 지점은 두 개의 **서로 다른 계보**로 갈라진다. 배경 문서(S10)가
  지목한 "후보추천이 목적지 PK를 모르는 상태로 동작해왔다"는 진술은 **절반만 맞다**.
    · 축 B (analyze_result.validated[].is_pk) — `_cmn_fetch_tgt_col_meta` 가 직접 채우는 값.
      목적지 접속이 있으면 **전 방언 항상 False** 가 맞다. UI 표시·SUM 기본체크가 여기 걸려있다.
    · 축 A (normalized_metadata.is_pk) — 후보 생성 엔진(candidate_engine)이 읽는 값.
      **원본(src) 테이블의 fetch_key_metadata 로 이미 정확히 채워지는 경로가 존재**한다
      (단일 테이블 + JOIN 없음 + 통계 조회 성공 시). 즉 "후보추천이 PK를 전혀 모른다"는
      전제는 단일테이블 SQL에서는 성립하지 않는다. JOIN/파생 SQL에서만 전부 False다.
- 영향받는 소비처: **총 24개 위치**(축 B 14 / 축 A 10). 이 중 사용자 체감 변화(a) 12개,
  다른 조건에 가려져 무변화(b) 9개, 실측 필요(c) 3개.
- 가장 큰 체감 변화는 UI 가 아니라 **candidate_engine 진입 관문**이다. is_pk=True 가 되면
  해당 컬럼은 SUM/GROUP BY 후보 목록에서 **생성 자체가 되지 않고** 비후보 사유
  "PK/유니크 식별자 — 행마다 고유값이라 그룹 기준 부적합" 으로 떨어진다.
- ★ 최대 회귀 위험: **복합 PK 구성원**. 오라클 실측 결과 목적지 PK 보유 테이블 21개 중
  **8개(38%)가 복합 PK** 이고, 그 구성원에는 CD_LOAD_NO / CO_CD / DEPT_CD 처럼
  전형적인 저카디널리티 코드성 컬럼이 포함된다. 어댑터는 복합 PK 구성원에게도
  is_pk=True 를 부여하므로, 아무 보정 없이 값만 채우면 **지금 잘 뽑히던 GROUP BY 축이
  통째로 사라진다**. 이는 결함 수정이 아니라 후퇴다. 대응책은 §5 에 기재.
