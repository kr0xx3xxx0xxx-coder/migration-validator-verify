[시나리오] 의도적 fan-out(중복제거 없음) — 1:N JOIN 으로 원본 PK 가 결과셋에서 유일성 붕괴
────────────────────────────────────────────────────────────────────────
이관 SQL:
  INSERT INTO NXDNP.MV_FANOUT_TGT (ID, COL_A, DETAIL_COL)
  SELECT x.ID, x.COL_A, m.DETAIL_COL
  FROM NXDNP.MV_FANOUT_SRC x JOIN NXDNP.MV_FANOUT_DETAIL m ON x.ID = m.SRC_ID
픽스처(신규 테스트 테이블만, 기존 미접촉):
  asis MV_FANOUT_SRC   : ID NUMBER PK, COL_A — 5행(ID 1..5, COL_A 100..500)
  asis MV_FANOUT_DETAIL: SRC_ID, DETAIL_COL — 8행(1:N; ID 1→3건, 2→2건, 3~5→각1건)
  tobe MV_FANOUT_TGT   : ID NUMBER PK, COL_A, DETAIL_COL — 5행(ID PK 라 dedup)
  → 결과셋에서 x.ID 가 유일하지 않음(ID 1,2 중복). ROW_NUMBER/DISTINCT 등 중복제거 없음.

[정상 샘플(XDIFF)과의 차이 — '원본 작성 책임' vs '도구 경고 책임' 판단]
────────────────────────────────────────────────────────────────────────
  기존 실측 XDIFF SQL 의 ROW_NUMBER() OVER(...) WHERE rn>=1 은 rn>=1 이라 전 행을 남겨 실제 중복제거
  효과가 없었다. 그 샘플이 안전했던 진짜 이유는 JOIN 조건(MOD(x.ID,300)+1=t.ORDER_ID, ORDER_ID 유일)이
  사실상 1:1 이라 결과셋에 fan-out 이 없었기 때문이다. 즉 현재 도구는 '조인이 1:1 이라는 원본 작성자의
  암묵 전제'에만 의존하며, 네이티브 PK 고속경로는 물리 제약(베이스 테이블 PK)만 보고 '결과셋에서도 유일'
  이라고 단정한다 → 이는 도구가 사전 경고해야 할 문제이며 원본 작성 책임으로만 미룰 수 없다.

[결론 — 요청 분류]
────────────────────────────────────────────────────────────────────────
  → "감지 안 되고 조용히 틀린 결과 반환" (재이관 드릴다운 한정).
     · 위험 경로는 '목적지 정식 PK + 1:N JOIN 원본'의 네이티브 고속경로(unique_key=True) 하나로 특정됨.
     · 정식 PK 없는 UK/업무키 경로(②③)는 _dup_present 로 fan-out 을 차단(HOLD)하므로 안전.
     · 단, 동일 시나리오에서 목적지가 dedup 되어 2단계 COUNT(8 vs 5)와 통계검증 SUM(1900 vs 1500)이
       상위 단계에서 각각 불일치로 표시되므로 '시스템 전면 은폐'는 아니다. '조용히 틀림'은 드릴다운 단계
       (재이관 대상 산정)에 국한되며, 위험의 본질은 상위 신호와 모순되게 '재이관 0건/모두 정상'이라
       안심시키는 데 있다(잠재적으로 실제 fan-out 이 목적지에도 적재된 무-PK 케이스는 ②③ 가 HOLD).
