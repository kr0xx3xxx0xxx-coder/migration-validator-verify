1. 요청 요약
────────────────────────────────────────────────────────────────────────
5단계 '결과 확인' 화면의 "일치 행 숨기기/보기" 버튼(_execToggleMatched)이,
바로 앞 작업(EXEC-RESULT-TAB-FILTER-PAGE-NAV-AND-PAGESIZE-FIX)에서 고친
_execGoResultPage / _execSetPageSize 와 완전히 같은 결함을 그대로 갖고 있었다.

  세 함수 모두 "서버 페이지 모드인가"만 window._execSrv 하나로 판단했고,
  "지표 탭(항목 필터)이 걸려 있는가"(window._execColFilter)는 보지 않았다.

그래서 COUNT/AMT/QTY 같은 지표 탭이 걸린 상태에서 이 버튼을 누르면
_execSrvGo(1) 로 빠져 서버가 '전체' 결과 1페이지를 내려주고, 그 응답이 결과표
tbody 를 통째로 덮어써 화면상 필터가 조용히 풀렸다. 탭 버튼은 계속 활성(주황
좌측선)으로 남아 사용자는 여전히 필터가 걸려 있다고 오인한다.

근거: verify 저장소 EXEC-RESULT-TAB-FILTER-PAGE-NAV-AND-PAGESIZE-FIX.txt §6-(1)

설계 원칙 (요구사항 그대로 준수)
 (1) 새 조건 어휘를 만들지 않았다. 분기 조건은 오늘 이미 고친
     _execGoResultPage / _execSetPageSize 및 그 이전부터 있던 _execSetColFilter 가
     쓰는 `window._execSrv && !window._execColFilter` 를 **글자 그대로** 재사용했다.
     이제 결과표의 렌더 경로를 가르는 네 함수의 조건식이 모두 동일 문자열이다.
 (2) 서버 모드 상태값 window._execSrv.includeMatched 는 **두 경로 모두에서 그대로
     토글**한다. 상태 보관 위치를 바꾸지 않았으므로 '전체' 탭으로 돌아갔을 때의
     서버 요청(mismatch_only)도 사용자가 마지막에 고른 값을 그대로 따른다.
 (3) 필터가 걸린 동안에는 렌더만 클라이언트로 돌린다. 보고서가 짚은 대로
     _execHideMatchedEffective() 가 서버 모드에서 _execSrv.includeMatched 를 읽는
     구조(:106~109)라, 상태만 정확히 갱신되면 클라이언트 렌더 경로가 같은 실효
     상태를 본다 — 실측으로 사실임을 확인했다(§5-A1: includeMatched 가 뒤집히고
     라벨도 '일치 행 보기'↔'일치 행 숨기기' 로 정상 전환).
 (4) '전체' 탭(필터 없음)의 기존 동작(서버 왕복)은 한 줄도 건드리지 않았다.
     클라이언트 전용 모드(_execSrv 없음)의 기존 분기도 그대로다.

  1차 실행에서 토글 버튼이 아예 렌더되지 않아 측정이 무효였다. 원인은 렌더러가
  `matched > 0` 일 때만 버튼을 그리기 때문이다(execute_result_renderer.py:1390).
  SUM AMT,QTY 를 넣으면 이 픽스처는 10개 그룹이 **전부** 불일치(matched=0)라
  '일치 행'이 없어 버튼 자체가 없다.
  SUM 없이 COUNT 만 비교하면 짝수 그룹(G02·G04·G06·G08·G10)은 COUNT 가 같아
  일치 행이 5건 생기고 버튼이 렌더된다. 나머지 조건(테이블·JOIN·GROUP BY·
  G01~G10)은 선행 작업과 동일하다. 결함이 발생하는 코드 경로는 탭 개수와 무관
  하므로 이 조정이 검증의 유효성을 해치지 않는다.

  4단계 실행 결과: 전체 10그룹 · 일치 5 · 불일치 5 (처리시간 0.30초)
  탭 구성: [전체 10] [COUNT 5]
  기준값(DB 직접 SELECT): G01·G03·G05·G07·G09 = COUNT 다름 / 짝수 5개 = COUNT 같음

6. 숨기지 않고 보고하는 사항
────────────────────────────────────────────────────────────────────────
(1) BEFORE 에서 '짝수 그룹(일치 행) 노출'은 관측되지 않았다 — 판정 1건 ❌
    결함이 재현되지 않은 것이 아니다. 이 픽스처를 COUNT 전용으로 돌리면
    '전체 불일치 그룹'과 'COUNT 탭 필터 결과'가 **같은 5개 그룹**이라, 필터가
    풀려 서버 결과로 덮여도 그룹 목록만으로는 차이가 드러나지 않는다.
    필터 유실은 대신 더 직접적인 두 증거로 확인했다:
      · 표시 행 집합 2행 → 5행 교체(클라이언트 페이지가 서버 렌더로 대체)
      · 페이징 문구 '총 5건 · 1/3 페이지' → '1 / 1 페이지(전체 무절단)'
      · /stats-result/page 요청 1회 발생(수정 후 0회)
    §3에서 적었듯 SUM 을 넣으면 그룹 식별 차이는 드러나지만 matched=0 이라
    토글 버튼 자체가 사라진다. 이 픽스처에서 두 조건은 동시 성립이 불가능하다.

(2) 이번 수정과 무관한 별개 관측 — '전체' 탭에서 '일치 행 보기'를 눌러도
    일치 행이 표시되지 않는다.
    A4 에서 mismatch_only=false 로 서버 요청이 정상 전송됐는데도 응답 렌더 결과는
    불일치 5행 그대로였다(표시 5행, 상단 문구 '1/1 페이지(전체 무절단)').
    즉 저장 결과 서버 페이지 경로가 이 케이스에서 일치 행을 돌려주지 않는다.
    · 이번 수정이 만든 문제가 아니다 — 요청/응답 경로(_execSrvGo, /stats-result/page)는
      한 줄도 건드리지 않았고, 수정 전 코드에서도 동일하게 관측된다.
    · 다만 사용자 눈에는 '일치 행 보기'가 아무 일도 안 하는 것으로 보이므로
      별도 작업으로 다룰 가치가 있다. 이번 작업 범위 밖이라 수정하지 않았다.

(3) 스크린샷 폴더의 _superseded_run2/ 3개 파일은 중간 실행(토글 버튼 미렌더 조건
    보정 전) 산출물이다. 최종 판정 근거가 아니며 추적용으로만 남겼다.
