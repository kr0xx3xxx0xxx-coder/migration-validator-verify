1. 무엇을 왜 고쳤는가
────────────────────────────────────────────────────────────────────────────
ROUTES-DIAGNOSIS-LIMIT-DIALECT-SECONDARY-CHECK 의 P4 항목으로 남아 있던 지점이다.
routes/diagnosis_route.py 의 두 헬퍼

  _contract_chunk_key(515)  → services.diagnosis.key_evidence.resolve_confirmed_chunk_key
  _contract_match_key(527)  → services.diagnosis.match_key_evidence.resolve_confirmed_match_key

는 contract 에서 CHUNK_KEY / MATCH_KEY 를 복원하면서 dialect 인자를 넘기지 않았다. 두 복원
함수의 기본값은 'postgres' 이므로, 오라클 접속이라도 내부 probe SQL 이 PostgreSQL 문법으로
렌더된다. 실제 귀결은 NULL probe 의 행 제한 구문이다.

  postgres 렌더 : SELECT 1 FROM ... WHERE ID IS NULL LIMIT 1              ← 오라클 실행 불가
  oracle   렌더 : SELECT 1 FROM ... WHERE ID IS NULL FETCH FIRST 1 ROWS ONLY

즉 오라클에서는 키 확인이 예외로 떨어지고, 두 헬퍼는 예외를 삼켜 None 을 돌려준다. 그러면
호출부(size-strategy / drilldown-strategy / strategy-orchestrate)는 key_range_available=False,
hash_bucket_available=False 로 판단해 "키가 없다"는 결론에 도달한다. 키가 있는데도 없다고
읽는, 조용한 오판이다. 화면 주경로(/diagnosis/analyze)는 이미 07cd4d0 에서 _confirm_routing 에
방언을 위임해 같은 결함을 해소했고, 이번 작업은 남아 있던 나머지 두 지점을 같은 방식으로
맞춘 것이다. 새 방식을 만들지 않고 기존 _routing_dialect 헬퍼를 그대로 재사용했다.

2. 먼저 확인한 것 — 이 두 지점이 화면에서 도달 가능한가
────────────────────────────────────────────────────────────────────────────
지시 1번 항목이다. 두 헬퍼를 태우는 route 는 다음 7개다.

  /diagnosis/multi-analyze, /diagnosis/multi-resume, /diagnosis/multi-row-diff,
  /diagnosis/multi-row-diff-resume, /diagnosis/size-strategy,
  /diagnosis/drilldown-strategy, /diagnosis/strategy-orchestrate

UI 소스(ui/tabler_renderer.py, ui/grid_helpers.py) 전수 검색 결과, 앞의 6개는 호출 문자열이
0회다. 유일하게 /diagnosis/strategy-orchestrate 만 1회 등장하는데, 그 호출자는
_mvLoadStrategyPreview(el) 함수 하나뿐이고 이 함수는 정의만 있고 호출부가 0회다. 실 서비스
포트(8000, 인증 ON)에서 내려받은 HTML 에서도 등장 횟수는 1회(정의) 뿐이라, 사용자가 클릭으로
도달할 수 있는 진입점은 존재하지 않는다. 참고로 이 함수를 참조하는 곳은 테스트 6종
(_FULL_HTML 에 함수 원문이 들어있는지 확인하는 정적 검사)뿐이다.

결론: 두 지점은 현재 UI 에서 도달 불가다. 실제 호출자는 테스트·samples(cloud_sandbox_e2e,
scope_delegate_live_e2e)와 문서화된 운영자 수동 호출 절차(docs/POSTGRES_OPERATOR_GUIDE.md)다.

그럼에도 수정한 판단 근거:
  · 위험이 0에 가깝다 — 배선 2줄이고, 방언 도출은 이미 같은 파일에서 검증된 헬퍼 재사용이다.
    PG 접속은 도출값이 'postgres' 로 기본값과 같아 렌더 결과가 완전히 동일하다.
  · 반대로 방치 비용은 조용하다 — 이 결함은 오류가 아니라 "키 없음" 이라는 그럴듯한 결론으로
    나타난다. 나중에 _mvLoadStrategyPreview 에 진입점이 붙거나 운영자가 문서 절차대로 호출하는
    순간, 오라클에서 전략이 HOLD 로 잘못 내려가고 그 원인은 로그에 남지 않는다.
  · 같은 계열 결함이 이미 4개 route(count_gate, exact_diff, agg_diff, diagnosis analyze)에서
    실측으로 확인·수정됐다. 마지막 하나만 다른 규약으로 남겨 두면 다음 감사 때 또 같은 비용을
    치른다.
낮은 우선순위로 보류하지 않고 지금 정리하되, "화면 동작 변화 없음"을 명시하는 쪽을 택했다.

3. 검증 방식 — 실 DB 를 쓰지 못한 사정과 대체
────────────────────────────────────────────────────────────────────────────
지시대로 내부망 복구 여부를 먼저 확인했다. 결과는 전부 단절이다.

  Oracle_asis            20,233ms  DPY-6005: cannot connect to database
  Oracle_tobe            20,009ms  DPY-6005: cannot connect to database
  PostgreSQL_Inter_asis  10,029ms  192.168.0.150:5433 timeout expired
  PostgreSQL_Inter_tobe  10,013ms  192.168.0.150:5434 timeout expired
  ping 192.168.0.150 → 대상 호스트에 연결할 수 없습니다(2/2)
  Neon 프리셋 4종도 서버측 거부(기존 quota 소진 건과 동일)

따라서 오라클 라이브 Before/After 는 불가능하다. 이전 진단과 같은 대체 방식을 썼다 —
DB 왕복만 캡처 stub 으로 치환하고, 두 헬퍼가 "어떤 dialect 인자로 복원 함수를 호출하는지"를
직접 포착한다. Before 는 작업트리를 되돌리지 않고 `git show HEAD:routes/diagnosis_route.py`
소스를 같은 프로세스에 별도 모듈로 로드해 나란히 비교했다(stash 금지 규칙 준수).

  BEFORE(HEAD)    접속=oracle      chunk_key dialect=(미전달→기본 postgres)  match_key=(미전달)
  BEFORE(HEAD)    접속=postgresql  chunk_key dialect=(미전달→기본 postgres)  match_key=(미전달)
  AFTER(작업트리)  접속=oracle      chunk_key dialect=oracle                  match_key=oracle
  AFTER(작업트리)  접속=postgresql  chunk_key dialect=postgres                match_key=postgres

그 dialect 로 실제 렌더되는 NULL probe SQL 까지 이어서 확인해, 배선이 문법 차이로 이어지는
것을 보였다(위 1절의 LIMIT / FETCH FIRST 대조). 혼합 방언(src=oracle, tgt=postgresql)은
기존 _routing_dialect 규약대로 'postgres' 를 유지하는 것도 확인했다 — 이번 수정이 동일 방언
경우로만 영향 범위를 한정한다는 뜻이다.

한계는 분명히 적어 둔다: 오라클 DB 에서 CHUNK_KEY 가 실제로 확정되는지(=After 가 의도한
효과를 내는지)는 이번에 실측하지 못했다. 다만 같은 함수·같은 probe 에 대한 오라클 실측은
07cd4d0(ROUTES-DIAGNOSIS-CONFIRM-ROUTING-DIALECT-DELEGATION-FIX)에서 이미 완료됐고, 이번
변경은 그 호출 지점을 2곳 더 맞춘 것이라 새 미지수를 만들지 않는다.
