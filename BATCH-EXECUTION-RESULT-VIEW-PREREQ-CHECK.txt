1. 기존 tab-results 조회 함수의 독립성
────────────────────────────────────────────────────────────────────────
전제 정정: 지시문은 "batch_execution_state(또는 관련 결과 저장소)"라 했으나,
tab-results 는 batch_execution_state 를 **전혀 읽지 않는다**. 결과 본문은
batch_wrapper_result 라는 별개 테이블에서 온다. 두 저장소는 같은 SQLite 파일에
있을 뿐 서로 FK 가 없다.

계층별 독립성(3층):

  ① JS  ui/tabler_renderer.py:29882  loadResultsDetail()
     → 재사용 불가. run_id 를 인자로 받지 않고 DOM 입력(#resBatchRunId)과
       필터 5개 엘리먼트, mvGetWorkProjectId() 전역을 직접 읽는다.
       현황판이 부르려면 goToResultsDetail(bid, filters)(:30059)로 값을
       주입 후 showTab('results') 하는 화면 전환 방식뿐이다.

  ② HTTP routes/batch_route.py:2479  GET /batch/runs/{batch_run_id}/wrapper-results/page
     → 준독립. 세션·워크플로 토큰과는 완전히 분리돼 있으나 **파라미터 2개**가 필수다.
       batch_run_id(path) + project_id(query). project_id 누락 시 scope guard 차단.
       실측: HTTP 400 {"code":"PROJECT_NOT_SELECTED","error":"작업 프로젝트를 먼저 선택하세요."}
       (routes/scope_guard_response.py:60 guard_source_batch → require_work_project=True)

  ③ 서비스 services/batch_wrapper_result_store.py:485  get_paged_wrapper_results()
     → 완전 독립. 순수 SQLite 조회 함수. 세션/전역/워크플로 상태 의존 0.
       시그니처: (batch_run_id, *, execution_run_id, result_type, status,
                  target_table, source_table, page, page_size, sort_by, sort_dir)
       COUNT/통계검증 재실행 없음(저장본 조회만). 현황판이 재사용하기 가장 적합한 층.

  결론: "run_id 만 받아 독립 호출 가능한가" → **아니오, 두 가지 이유로.**
        (a) 필요한 키가 run_id 가 아니라 batch_run_id 이고,
        (b) HTTP 층은 project_id 를 추가로 요구한다.

2. ★ 결정적 결함 — execution_run_id 가 서로 다른 두 체계다
────────────────────────────────────────────────────────────────────────
현황판 완료 job 의 id 는 batch_execution_state.execution_run_id 인데,
결과 저장소의 execution_run_id 는 생성 규칙 자체가 다르다.

  batch_execution_state.execution_run_id
    = "exec_" + uuid4().hex[:16]            (batch_execution_state_service.py:145)
    실측값: exec_a2c0630406254adf

  batch_wrapper_result.execution_run_id
    = f"{batch_run_id}-{YYYYMMDDHHMMSS}"    (batch_wrapper_result_store.py:188)
    실측값: 20260619161749683354-20260623010023

  실측(운영 DB 전수): 종료 exec 행 386건 중 execution_run_id 가 결과 저장소와
                      직접 일치하는 건수 = **0건 (0.0%)**

  라이브 확인 — 현황판 job id 를 그대로 넘겨봄:
    GET /batch/runs/20260619161749683354/wrapper-results/page
        ?project_id=2&execution_run_id=exec_325ce1715fac408e
      → found=False, message="아직 실행 결과가 없습니다."
    GET ... &execution_run_id=exec_a475588ccdba4762
      → found=False, message="아직 실행 결과가 없습니다."

  즉 현황판 job → 결과 화면을 잇는 유일한 키는 execution_run_id 가 아니라
  **batch_run_id** 이며, 이는 batch_execution_state 에 컬럼으로 존재한다
  (job_registry DTO 의 extra.batch_run_id 로 이미 노출됨 — services/job_registry.py:417).

3. batch_run_id 로 잇는 경우의 잔여 위험(운영 DB 386건 전수 실측)
────────────────────────────────────────────────────────────────────────
job_registry 는 완료 batch job 전량에 result_viewable=True 를 내려주지만
(job_registry.py:800), 실제로 열리는 비율은 절반뿐이다. 배타 분류:

  A. batch_run_id 가 빈 값 → 조회 자체 불가(죽은 링크)        3건 ( 0.8%)
  B. batch_run_id 는 있으나 저장 결과 없음 → 빈 화면         57건 (14.8%)
  C. 같은 batch_run_id 에 완료 exec 2건+ → 회차 오배정      125건 (32.4%)
  D. 1:1 로 안전하게 열림                                201건 (52.1%)
  ───────────────────────────────────────────────────────────────
     문제 있음(A+B+C)                                  185건 (47.9%)

  C(회차 오배정)의 메커니즘: get_paged_wrapper_results 는 execution_run_id 를
  주지 않으면 해당 batch_run_id 의 **최신 1회분**을 연다(:546-550).
  현황판에서 과거 회차 job 을 눌러도 최신 회차 결과가 뜬다 — 조용히 틀린 결과.

  라이브 재현(현황판 완료 목록 상위 3건이 전부 동일 batch_run_id):
    exec_a2c0630406254adf  COMPLETED  brid=20260724182533091358
    exec_9b6a2a2374f04c2d  COMPLETED  brid=20260724182533091358
    exec_727fe5923da448bc  COMPLETED  brid=20260724182533091358
    → 세 job 모두 같은 화면(최신 회차)으로 귀결. 구분 불가.

  극단 사례: batch_run_id='RUN1' 에 완료 exec 109건, 'NOPE_GCS' 에 50건.
             실이력 20260619161749683354 에도 9건(COUNT_ONLY/FULL 혼재).

  참고 — completed_at 과 wrapper execution_run_id 의 초 단위가 사실상 일치하지만
  (exec completed_at 09:25:56 ↔ wrapper …-20260724092556), 이는 저장된 FK 가 아니라
  우연한 타임스탬프 근접이다. 이걸로 매칭하는 것은 권장하지 않는다.

  A/B 의 성격: run_type 이 CANDIDATE_SELECTION(3건, batch_run_id 전부 빈 값)과
  PROFILE_RECOLLECT(1건, batch_run_id='GROUP_GRP_…' 합성 id)인 job 은 애초에
  wrapper 결과를 만들지 않는다. 그런데도 result_viewable=True 로 내려간다.
  (job_registry.BATCH_ACTIVE_STATUSES 주석은 run_type 을 3종으로 적었으나
   실 데이터에는 PROFILE_RECOLLECT 가 존재 — 문서/실데이터 불일치)

6. 사전조건 판정
────────────────────────────────────────────────────────────────────────
  질문: "현황판에서 재사용하기 충분한 형태인가?"
  답  : **불충분하다.** 조회 경로 자체는 존재하고 서비스 함수는 독립적이지만,
        현황판 job 을 그 경로로 잇는 데 3개의 결손이 있다.

  결손 1(치명) — id 체계 분리. job id(exec_…)로는 결과를 못 찾는다(실측 0/386).
                 batch_run_id 로 우회 가능하나 회차 특정 불가 → 32.4% 오배정 위험.
  결손 2(차단) — project_id 부재. job DTO 에 없어 HTTP 호출 시 400.
                 group_id→validation_batch_group.project_id 로 유도는 가능
                 (GRP_202606170243184996→'2' 확인). 단 조회 1회 추가.
  결손 3(표시) — 그룹수는 배치 수준 집계에 없음. row 순회 파생만 가능하고
                 compare 보유율이 낮다(실측 1/20).

  판정: **문서화 우선** — 지금 현황판에 결과요약을 배선하면 절반 가까이가
        빈 화면이거나 다른 회차 결과를 보여준다. 배선 전에 최소한
        결손 1(회차 식별)의 해소 방향이 정해져야 한다.

  권장 대응 방향(구현 아님, 선택지만):
    (가) batch_execution_state 에 결과 회차 FK 컬럼 1개 추가
         (wrapper 저장 시점의 execution_run_id 를 기록) — 가장 정확.
         저장소 스키마 변경이므로 별도 승인 필요.
    (나) job_registry DTO extra 에 project_id 를 채우고(그룹 조회 1회),
         result_viewable 을 '실제 결과 존재 + 회차 유일'일 때만 True 로 좁힌다
         — 읽기 전용 계층 내에서 가능. 오배정은 못 막고 죽은 링크만 제거.
    (다) 현황판 요약은 batch_summary 7필드까지만 표시하고 그룹수는 제외,
         상세는 기존 tab-results 화면 전환(goToResultsDetail)에 위임.
