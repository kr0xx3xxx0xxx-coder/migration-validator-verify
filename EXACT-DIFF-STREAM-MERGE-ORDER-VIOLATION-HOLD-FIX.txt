지침은 "services/exact_diff/stream_merge.py 이 파일만 수정" 이었으나, **실제로는 3개 파일을
수정했다.** 사유는 다음과 같다. 되돌리기 원하시면 커밋 f1a31a0 에서 engine/contracts 변경만
분리 revert 하면 된다(stream_merge 단독으로도 탐지는 동작한다).

  · 왜 stream_merge 단독으로는 요구사항을 만족할 수 없었는가
    요구사항 중 "HOLD 사유 메시지에 '정렬 순서 위반(캐릭터셋 불일치 가능성)' 문구 포함" 은
    stream_merge 안에서 완결되지 않는다. HOLD 사유 문구를 실제로 만들어 결과 객체에 넣는 곳은
    engine.py:437~ 이고, 그 문구는 하드코딩돼 있다.

      engine.py (수정 전)
          if out.aborted:
              res.status, res.stop_reason = STATUS_HOLD, HOLD_SIZE_OVER_LIMIT
              res.error_message = f"행 수가 소형 상한(...)을 초과해 보류합니다..."

    · stream_merge 만 고쳐 order_violation 플래그만 세우면 → engine 은 그 플래그를 모르므로
      부분 집계된 건수를 그대로 들고 4)~5) 단계로 내려간다. expected_count 가 없는 호출 경로
      에서는 그대로 STATUS_DONE 확정까지 간다 — **날조가 그대로 남는다.**
    · 그렇다고 aborted 만 세우면 → HOLD 는 나지만 사용자에게는
      "행 수가 소형 상한(50,000)을 초과해 보류합니다" 라는 **사실과 다른 사유**가 표시된다.
      사용자는 행 수를 확인하러 가게 되고, 정작 확인해야 할 캐릭터셋은 영영 못 본다.

    즉 "조용한 날조"를 "거짓 사유 HOLD"로 바꾸는 선택지밖에 없어서, engine 에 분기 1개
    (7줄)와 contracts 에 상수 1줄을 추가했다. 아래 3개 파일 외에는 손대지 않았다.

  · 병행 작업 충돌 여부 : 없음
    M15(ui/tabler_renderer.py) — 미수정. S9(코드수정 없음) — 무관.
    UI 는 손대지 않아도 된다. tabler_renderer.py:16606 의 HOLD 라벨 조회가
    `_MV_ED_HOLD_LABELS[d.stop_reason] || [d.stop_reason, '']` 폴백을 갖고 있고, 표시 문구는

■ 1. 무엇이 문제였나
================================================================================

merge_compare 는 "양쪽 스트림이 파이썬 키 비교(_key_lt)와 같은 순서로 정렬돼 있다"는 전제
위에서만 정확하다. 그런데 정렬은 파이썬이 아니라 DB 서버가 한다.

  services/exact_diff/dialects/oracle.py key_hash_stream_sql
      ORDER BY NLSSORT(<key>, 'NLS_SORT=BINARY')

NLSSORT BINARY 는 "DB 캐릭터셋의 바이트 순서"다. 원본이 KO16MSWIN949/EUC-KR 계열이고
목적지가 AL32UTF8 이면 한글 키의 정렬 순서가 서로 달라진다(CP949 는 확장 8,822자를 상용
2,350자보다 낮은 코드 대역에 배치한다). merge 는 그 어긋남을 "한쪽에만 있는 키"로 오인하고,
예외도 경고도 없이 거짓 불일치를 확정 결과로 보고한다.

  · 같은 증상의 선례 : PK-RANGE-CHUNK-SORT-ORDER-ALIGNMENT-FIX(트리거만 다름 — 그쪽은
    "WHERE 숫자 바인드 vs ORDER BY 문자 정렬", 이번 건은 "서버 charset 바이트순 vs 파이썬
    코드포인트순"). chunk 경로는 _ensure_pk_ascending 으로 이미 면역이었고, 스트림 경로만
    무방비였다.

■ 2. 어떻게 고쳤나
================================================================================

── 2-1. services/exact_diff/stream_merge.py (주 수정)

  · MergeOutcome 에 4개 필드 추가
        order_violation: bool          # 키가 직전 키보다 작음(정렬 전제 붕괴)
        order_violation_side: str      # 'src' / 'tgt'
        order_violation_at: int        # 위반 시점의 해당 측 스캔 행 번호(1-base)
        order_violation_detail: str    # 사용자 노출용 사유 문구

  · 모든 스트림 읽기가 통과하는 단일 지점(_next)에 오름차순 검사(_check_order) 삽입.
    위반이면 내부 전용 예외 _OrderViolation 으로 즉시 탈출한다 — _drain 의 중첩 루프
    한가운데서도 한 번에 빠져나오기 위한 것이며, merge_compare 가 반드시 잡아서
    MergeOutcome 필드로 변환해 반환한다(공개 API 로 raise 되지 않는다 — 프로젝트 규칙 준수).

  · **재정렬은 하지 않는다.** pk_range_chunk 는 chunk 가 이미 fetchall 로 메모리에 있어서
    보정이 가능했지만, 스트림 경로는 전량 메모리 적재가 금지 경로다. 그래서 이번엔
    "탐지 + 중단" 만 한다(지침과 동일).

  · aborted / abort_reason=ORDER_VIOLATION 도 함께 세운다.
    order_violation 을 모르는 소비자라도 최소한 "중단(결과 미확정)" 으로는 인지하게 하는
    안전망이다 — 부분 건수를 확정 결과로 오인하는 경로를 원천 차단한다.

  · 관할 분리(중요)
      - 첫 행 : 비교 대상 없음 → 검사 생략(_MISSING 센티널로 None 과 구분)
      - NULL 키 : 검사하지 않는다. NULL 은 정렬 말미 규약(PG NULLS LAST)이 따로 있고
                  기존 null_key_found 경로가 HOLD 로 처리한다(관할 중복 금지)
      - 같은 키 연속(중복) : 위반 아님. 오름차순 위반은 "작아질 때"만이다
      - 비교 규칙 : merge 본체가 쓰는 _key_lt 를 그대로 사용 — "이 merge 가 실제로 전제한
                    순서"만 검사한다(다른 잣대로 오탐하지 않는다)

■ 6. 비판적 검토 — 이 수정의 한계와 남는 위험
================================================================================

  · [한계] 탐지는 "위반이 실제로 스트림에 나타났을 때"만 작동한다. PK 가 순수 ASCII 면
    CP949 와 AL32UTF8 의 순서가 같으므로 위반이 없고, 따라서 아무 신호도 안 난다 — 이건
    정상이다(그 경우 결과도 실제로 옳다). 다만 "캐릭터셋이 다른데 통과했다"를 사전에
    알려주는 기능은 아니다. **사전 경고가 필요하면 별건으로 캐릭터셋 probe 가 필요하다.**

  · [한계] 우연히 위반이 스트림 후반에만 나타나면, 그 전까지는 스캔 비용을 이미 쓴다.
    조기 중단이라 낭비는 줄지만 0 은 아니다.

  · [남는 위험] 위반이 있는 환경에서는 이제 exact_diff 가 **결과를 내지 못한다**(HOLD).
    이는 의도된 것이다 — 틀린 결과보다 결과 없음이 낫다. 다만 운영에서 "왜 갑자기 보류가
    나느냐" 는 문의가 생길 수 있으므로 사유 문구에 다음 조치(NLS_CHARACTERSET / NLS_SORT
    확인)를 넣었다.

  · [heuristic 증가] 없음. 새 규칙은 "직전 키보다 작으면 중단" 단 하나이고, 비교 잣대는
    merge 본체가 이미 쓰던 _key_lt 를 그대로 재사용한다(별도 잣대·임계값·가중치 없음).

  · [explainability] 위반 측·행 번호·양쪽 키를 결과 객체에 남긴다(무증적 중단 아님).

  · [보안] 사유 문구에 PK 값 일부가 노출된다(40자 절단). 불일치 레코드 화면이 이미 키를
    표시하므로 노출 수준은 동일하다. 비밀번호 등 인증정보는 관여하지 않는다.

  · [권장 후속] 진단서 §5-P1 에 남은 별건 2개는 이번 범위 밖이다 —
      (a) oracle.py:128 주석의 캐릭터셋 전제 누락 정정
      (b) VARCHAR2 byte/char 의미 구분(CHAR_USED 미조회) 사각지대
