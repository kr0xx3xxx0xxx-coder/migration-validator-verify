■ 한 줄 요약

  부분 적재(COUNT_CRITICAL_DIFF) 상태에서 강행한 개별검증 결과를 재조회할 때 통째로
  사라지던 "건수 격차(부분 적재) 상태에서 진행된 결과입니다" 맥락 배너를, 실행 시점
  게이트 근거를 snapshot 에 보존하는 방식으로 복원했다. 판정 로직은 손대지 않았다.

■ 배경 — 무엇이 사라졌고 왜 사라졌나

  SNAPSHOT-DOWNGRADE-REACHABILITY-CONSOLIDATE-DIAGNOSE 에서 확인된 L1 항목이다.

  마법사 5단계는 결과표 위에 파란 맥락 배너를 그린다. 내용은 "아래 불일치는 값이 손상된
  것이 아니라, 데이터가 어디까지 옮겨졌는지(누락 범위)를 보여줍니다" 이고, 적재율·순
  차이·관측 패턴(편중/균등/혼합)과 원본만·값불일치 범례가 따라붙는다. 부분 적재 상태에서
  사용자가 강행한 결과를 '값이 깨진 것'으로 오해하지 않게 하는 설명 장치다.

  그런데 이 배너의 발화 조건이 결과 객체(r)가 아니라 브라우저 전역에 있었다.

      ui/execute_result_renderer.py:751  _execCriticalDiffContext(r)
        window._countGate.count_status === 'COUNT_CRITICAL_DIFF'
        AND window._mvCountGateForceAccepted (사용자 강제진행 동의)

  두 신호 모두 마법사 실행 세션에만 존재한다. window._countGate 는 /count 응답의
  count_gate 를 받아 화면이 들고 있는 값이고(ui/tabler_renderer.py:24017), 강제진행
  동의도 그 세션의 클릭으로만 세워진다. 그래서 같은 run 을 다시 열면 두 신호가 모두
  없어 배너가 통째로 사라졌다. 표시가 줄어드는 게 아니라 '왜 이렇게 보이는지'에 대한
  설명 자체가 없어지는 종류의 결손이다.

  저장 쪽에도 근거가 없었다. snapshot 의 count_precheck_status 는
  NOT_RUN/PASSED/FAILED/ERROR/SKIPPED_BY_USER 5값 화이트리스트라, CRITICAL 이든
  MINOR 든 건수 불일치는 전부 FAILED 한 칸으로 뭉개졌다. 즉 재조회 화면이 참고할
  '이 run 은 부분 적재였다'는 사실이 어디에도 남아 있지 않았다.

  실측으로도 확인했다. /execute 응답에는 count_gate 도 count_status 도 없다
  (verify_result.json 의 execute.has_count_gate_in_response = false). 게이트 판정은
  /count 응답에만 실려 화면 전역으로 들어갔다가 세션과 함께 사라진다.

■ 실측 픽스처

  COUNT 게이트의 CRITICAL 조건은 (큰쪽 ≥ 100,000 AND coverage ≤ 20%) 또는
  (절대 ≥ 1,000,000 AND 상대 ≥ 10%) 이다. 소형 테이블은 비율만으로 CRITICAL 이 되지
  않으므로(§16 소형 보호) 원본을 15만행으로 만들었다.

    asis01.t_critdiff_src   150,000행 · region_cd 10종(저카디 — GB 후보 게이트 ≤50 통과)
    tobe01.t_critdiff_tgt    15,000행 · R001 그룹만 적재
                             → 적재율 10% · 순 차이 135,000 → COUNT_CRITICAL_DIFF
                             → 10그룹 중 9그룹 통째 누락 = 편중 부분 적재
    tobe01.t_critdiff_ctl   149,500행 · 500행만 빠짐(대조군)
                             → 상대 0.33% → COUNT_MINOR_DIFF (게이트가 stats 를 막지 않음)

  대조군을 같이 둔 이유는 저장 필드가 고정값이 아니라 실제로 갈린다는 것과, CRITICAL 이
  아닌 run 에 거짓 배너가 생기지 않는다는 것을 같은 실행으로 보이기 위해서다.
