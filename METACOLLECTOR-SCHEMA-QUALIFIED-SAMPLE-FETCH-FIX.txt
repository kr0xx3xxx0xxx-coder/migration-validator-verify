──────────────────────────────────────────────────────────────────────────────
§1. 배경과 실제 원인
──────────────────────────────────────────────────────────────────────────────
백로그 F28. db/meta_collector.py 의 _fetch_samples 는 샘플 100건 조회 SQL 을
스키마 없이 테이블명만으로 만들었다.

  (수정 전)
    tbl = table_name
    sql = f"SELECT {col_list} FROM {tbl} LIMIT 100"      # postgresql/mysql
    sql = f"SELECT {col_list} FROM {tbl} WHERE ROWNUM <= 100"   # oracle
    sql = f"SELECT TOP 100 {col_list} FROM {tbl}"        # mssql

메타 조회(_fetch_meta)는 information_schema/all_tab_columns 를 스키마 무관하게
검색하므로 테이블을 찾아낸다. 그런데 샘플 조회는 세션의 search_path(PostgreSQL) /
현재 스키마에 의존하므로, search_path 밖 스키마의 테이블이면 relation 미존재로 실패한다.
collect() 는 그 예외를 `except Exception: pass` 로 삼켰기 때문에

  - 샘플이 조용히 0건이 되고(품질 저하가 겉으로 안 드러남),
  - PostgreSQL 에서는 실패 문장이 트랜잭션을 abort 상태로 남겨
    같은 커넥션의 후속 쿼리(재수집 distinct 등)까지 전멸시켰다.

PROFILE-RECOLLECT-SAMPLING-TIMEOUT-GUARD-FIX(§5,§7)의 P2 는 호출부
(services/profile_recollect_service.py `_recollect_one_side`)에서 rollback 을 넣어
"후속 오염"만 막았고, 조회 자체는 미수정으로 남아 있었다. 이번 작업이 그 조회를 고쳤다.

추가로 드러난 인접 결함(같은 함수 계열, 함께 수정):
  - table_name 이 'schema.table' 로 들어오면 _fetch_meta 가 그 문자열을 통째로
    테이블명과 비교(LOWER(c.table_name) = 'ntb.gt_hr_employee')해서 메타가 0건이 됐다.
    호출부(routes/batch_route.py, services/profile_recollect_service.py)는 파싱된
    원본/목적 테이블명을 그대로 넘기므로 스키마가 붙은 값이 실제로 올 수 있다.

§3. 수정 내용 (db/meta_collector.py 1개 파일)
──────────────────────────────────────────────────────────────────────────────
1) `_quote_ident(name, dialect)` 신설 — mysql/mariadb 백틱, mssql 대괄호, 그 외 큰따옴표.
   인용부호는 이스케이프(`a"b` → `"a""b"`, `a]b` → `[a]]b]`).
2) `_split_schema_table(table_name)` 신설 — 'schema.table' / bare / 인용부호 / 3-part 분리.
3) `_fetch_meta` : 반환을 (meta, schema, real_table) 튜플로 확장.
   - SELECT 에 스키마/테이블 실제 표기 추가 (pg: table_schema·table_name,
     oracle: owner·table_name, mysql: table_schema·table_name, mssql: TABLE_SCHEMA·TABLE_NAME)
   - table_name 에 스키마가 붙어 있으면 그 스키마를 WHERE 조건으로 한정
     (pg/mssql: `(%s = '' OR LOWER(table_schema) = %s)`, oracle: `(:sch IS NULL OR UPPER(owner) = :sch)`,
      mysql: `table_schema = COALESCE(NULLIF(%s,''), DATABASE())`) — 전부 바인드 파라미터, 문자열 결합 없음.
   - 결과 row 의 스키마/테이블이 **하나로 확정될 때만** 반환한다.
     동명 테이블이 여러 스키마에 있으면 임의 선택하지 않고 ''(기존 bare 동작 유지).
4) `_fetch_samples(..., schema='')` : schema 가 있으면
   `"스키마"."테이블"`(방언 인용) 로 한정 조회, 없으면 종전과 동일한 bare 조회.
   테이블 표기는 호출부가 준 문자열이 아니라 **카탈로그의 실제 표기**를 쓴다
   (대문자로 넘겨도 PG 소문자 실제명으로 조회).
5) `_safe_rollback(conn)` 신설 + collect() 의 메타 실패/샘플 실패 두 경로에서 호출.
   읽기 전용 수집 경로라 되돌릴 변경이 없고, PostgreSQL 트랜잭션 abort 전파를 근원에서 차단한다.
   (호출부 P2 rollback 과 중복되어도 무해)

의도적으로 하지 않은 것:
  - 컬럼명은 종전대로 인용하지 않는다(대문자 bare → PG 소문자 폴딩 동작 유지, 회귀 위험 최소화).
  - 동명 테이블 모호 케이스는 스키마를 임의 선택하지 않는다(조용한 오답 방지). 이 경우
    정답 경로는 호출부가 'schema.table' 을 넘기는 것이고, 그 경로가 이번에 동작하게 됐다.

§8. 남은 한계 / 후속 후보
──────────────────────────────────────────────────────────────────────────────
1. 동명 테이블이 여러 스키마에 있고 호출부가 bare 이름만 주면 여전히 샘플 0건이다
   (임의 선택 금지 정책). 메타도 두 스키마 컬럼이 섞여 반환되는 기존 성질은 그대로다.
   근본 해소는 호출부가 스키마를 붙여 넘기는 것이며, 그 경로는 이번에 동작하게 됐다.
2. 컬럼 식별자는 여전히 인용하지 않는다(예약어/특수문자 컬럼은 기존과 동일하게 취약).
3. mssql 은 실 DB 실측 미도달(드라이버 부재) — 유닛 테스트 수준까지만 검증됐다.
4. collect() 는 여전히 샘플 실패를 조용히 삼킨다(메타만 반환). 이제 트랜잭션은 오염되지
   않지만, "샘플 0건" 사유가 결과 객체에 남지 않는 explainability 갭은 남아 있다.
