작업명 : PLAIN-JOIN-WRAPPING-NECESSITY-DIAGNOSE
⚠️ 추가 작업 필요 - 순수 JOIN wrapping 은 완화 불필요로 확정(비용 0), 단 진단 중 별도 결함 1건 발견

[결론 먼저]
① 순수 JOIN 을 감싸는 것은 성능상 무해하다 — 감싸도 predicate pushdown 이 100% 성립하고,
   옵티마이저 추정 Cost 가 감싼 것/안 감싼 것이 완전히 동일하다(실측 전 케이스).
   따라서 "보수적 규칙이라 완화하면 빨라진다"는 전제는 거짓이다. 완화 이득 = 0.
② 규칙이 CTE/JOIN/UNION 을 한 묶음으로 둔 이유는 "셋 다 위험해서"가 아니라
   "단순 1:1 재파생(_derive_row_sqls)이 충실하지 못한 형태 전부"를 한 우회로로 보냈기 때문이다.
③ 과거 "JOIN 파서 크래시" 전례는 최상위 JOIN 이 아니라 CTE 안에 숨은 JOIN 에서 났다.
   최상위 JOIN 은 크래시한 적이 없고 정직한 HOLD 였다(실측 확인).
④ 오늘 확정된 CTE+윈도우함수의 비용은 wrapping 탓이 아니다 — 감싸기를 제거해도(DIRECT 주입)
   실행계획·Cost·소요가 그대로다. 원인은 윈도우함수 자체다(정정 필요 사항).
⑤ 부수 발견(신규·실 서비스 재현): 별칭을 쓴 '단순 1:1' 이관 SQL 은 wrapping 대상에서 빠져
   재이관 상세가 ORA-00904 로 HOLD 된다. 이 케이스는 오히려 wrapping 이 필요하다.

4) 대량(250,000행) 실제 비용 — CTE+윈도우 케이스와의 대비 (지시 4)
------------------------------------------------------------------------------
250,000행 전량을 5 chunk 로 순회한 총 소요(1차 측정):
  순수 JOIN 계열(J1/J2/J3/J5/J6) · CTE(윈도우없음) C1 · UNION U1 : 총 0.61 ~ 0.80초 (chunk당 0.12~0.16초)
  단순 1:1 S0                                                   : 총 0.57 ~ 0.73초
  CTE+윈도우함수 C2                                              : 총 2.58 ~ 3.85초 (chunk당 0.41~0.49초)

확연히 다르다 — chunk 단위로 약 3.3배, 옵티마이저 Cost 로는 49 대 7396 으로 151배다.
그러나 그 차이는 감싸기와 무관하다: C2 는 DIRECT(감싸기 없이 직접 주입)에서도 Cost 7396 · 0.492s 로 동일하다.

[중요 정정] "CTE+윈도우함수 케이스의 심각한 비용"의 원인 귀속
  오늘 실측된 471.5초(anchor 2,000개 표본 preflight, REIMPORT-COUNTONLY-CHUNK-SIZE-DIAGNOSE)는
  'wrapping 때문에 느린 것'이 아니라 '윈도우함수 때문에 pushdown 이 불가능해 anchor 1건당 원본 전체
  재스캔이 되고, 그것이 2,000회 반복된 것'이다. chunk 순회(5회)로 환산하면 5 × 전체스캔 ≈ 2.6~3.9초로
  현재 측정치와 정합한다. 즉 비용의 곱셈 인자는 '감싸기 유무'가 아니라 '조회 횟수 × pushdown 실패'다.
  agg_diff_route.py:360-369 의 표본 게이트 skip 주석이 이 현상을 'wrapping 소스'로 서술하는데,
  실제 인과는 'wrapping 판정에 걸리는 형태 중 윈도우함수를 포함한 것'이다(주석 정확도 개선 여지 — 이번엔 미수정).

5) 과거 크래시의 정확한 형태 특정 — 파서 + 실 오라클 실행 (지시 5)
------------------------------------------------------------------------------
스크립트: scripts/dev_e2e/plain_join_wrapping_parser_shape.py
방법: 실제 이관 SQL(INSERT INTO … SELECT)을 SqlglotParser 로 파싱 → 운영과 동일한 parse_result 조립
      (services/single_validation_analyze_service.py:552-569 와 같은 키 구성) → _derive_row_sqls 산출물을
      실 오라클에서 1행 실행. 읽기 전용.

  케이스                        joins   wrap판정   _derive_row_sqls        실 오라클 실행
  S0 단순 1:1 (별칭 x. 사용)      0      False     SQL 생성                실패 ORA-00904 "X"."C_NUM"  ← 6절
  J1 LEFT · 함수조인             1      True      HOLD(Phase 1-B 미지원)   -
  J2 INNER · 함수조인            1      True      HOLD                    -
  J3 LEFT · 단순동등조인          1      True      HOLD                    -
  J5 LEFT · 문자마스터조인        1      True      HOLD                    -
  J6 2단 JOIN                   2      True      HOLD                    -
  J7 JOIN + WHERE               1      True      HOLD                    -
  J8 서브쿼리(파생테이블) 조인     1      True      HOLD                    -
  C1 CTE(윈도우 없음) + JOIN      0      True      SQL 생성 FROM BASE      실패 ORA-00942 (BASE 없음)
  C2 CTE + 윈도우 + JOIN         0      True      SQL 생성 FROM RANKED
                                                  WHERE rn >= 1          실패 ORA-00942 (RANKED 없음)

읽는 법:
  - 최상위 JOIN(J1~J8)은 파서가 joins 를 1~2개로 정상 노출한다 → joins 가드가 걸려 '정직한 HOLD'.
    INNER/LEFT, 함수조인, 단순 동등조인, 문자 조인, 2단 조인, 서브쿼리(파생테이블) 조인 전부 동일.
    → 모든 JOIN 이 위험한 것도, 특정 JOIN 형태만 위험한 것도 아니다. 최상위 JOIN 은 애초에 크래시 경로가 아니다.
  - 위험한 것은 CTE 다. CTE 가 있으면 파서가 joins=0 으로 평탄화하고 from_table 을 CTE 이름(BASE/RANKED)으로
    잡아 joins 가드가 무력화되고, 존재하지 않는 객체를 참조하는 SQL 이 생성돼 실제로 실행에 실패한다.
    C2 는 여기에 더해 외부 WHERE 'rn >= 1' 까지 복사한다(fdd6ee9 가 서술한 ORA-00904 "RN" 의 정확한 기전).
  - C1(윈도우함수 없는 CTE)도 똑같이 크래시한다 → CTE 는 윈도우 유무와 무관하게 재파생 불가.

별칭을 쓴 단순 1:1 이관 SQL 은 CTE 없음·물리원본 1개·UNION 없음이라 wrapping 판정이 False → 이 경로를 그대로 탄다.

                        error_message: 재이관 PK 계산 조회 오류: ORA-00904: "S"."AMT": invalid identifier

  [별칭 없음]  같은 테이블·같은 컬럼, 별칭만 제거
    /analyze        → from_alias=''  src_expr[0]='ID'

  두 케이스의 유일한 차이는 별칭 유무다 → 원인 확정. 방언 무관 결함(PG 도 동일 구조로 실패할 것이나 미검증).

이 발견은 이번 과제의 결론을 강화한다 — 문제는 '감싸기가 과하다'가 아니라 '감싸지 않는 경로가 취약하다'이다.

7) 완화 가능 여부 판단 (지시 6)
------------------------------------------------------------------------------
결론: 완화하지 말 것(현행 유지 권고). 근거 3가지.

  (가) 성능 이득이 0 이다. Cost 동일 · 시간 배율 0.83~1.07x(노이즈). 얻을 것이 없다.
  (나) 순수 JOIN 에는 대체 경로가 아예 없다. wrapping 을 걷어내면 _derive_row_sqls 의 joins 가드에 걸려
       "JOIN 이관은 Phase 1-B 미지원" HOLD 로 되돌아간다 = ad185bc 이전 상태 = 재이관 상세 기능 상실.
       즉 '완화'는 성능 최적화가 아니라 기능 후퇴다. 완화하려면 JOIN 재조립 파싱 경로를 새로 만들어야 하는데,
       그 방식의 취약성은 6절에서 이미 실증됐다(별칭 하나에 ORA-00904).
  (다) 위험 대비 이득 비대칭. 이득 0 · 위험은 크래시(ORA-00904)와 조용한 오판정(fan-out 등).

권고 방향(구현은 별도 승인 후):
  - 유지: _reimport_source_needs_wrapping 의 CTE/다중원본/UNION 판정 3조건 그대로.
  - 개선(우선순위 높음): 6절 결함. 두 선택지 —
      A안 _derive_row_sqls 가 from_alias 를 FROM 절에 반영(예: FROM {ft} {alias}). 최소 변경이나
          완료 모듈(Phase 1-B) 수정이라 사용자 확인 필요, 회귀 범위는 재이관/scope 파생 전반.
      B안 별칭이 있으면 wrapping 대상으로 넘긴다(판정 조건 추가). 이미 안전성이 실증된 경로를 재사용하고
          성능 페널티가 0 임이 이번에 확인됐다 → 구조적으로 더 안전. 권장.
  - 개선(문서): agg_diff_route.py:360-369 표본 게이트 skip 주석의 인과 서술을 'wrapping 소스'에서
    '윈도우함수로 pushdown 불가한 소스'로 정정(4절). 코드 동작 변경 없음.
  - 안전 조건: 어떤 완화도 조건부 폴백(파싱 실패·shape 불일치 시 wrapping 또는 정직한 HOLD)을 유지해야 한다.
