■ 2-4. 확장 가능성과 걸림돌

확장 가능한 근거:
- override_group() 이 이미 그룹 단위 부분 교체를 지원 → 모드별 override 는 같은 메커니즘으로 표현 가능
- validation_policy_settings 테이블은 policy_name TEXT NOT NULL UNIQUE, get/save/restore(policy_name=...)
  가 이미 파라미터화(:302,:325,:470). 단 37개 호출부 전부가 인자 없이 default만 사용 - 스키마는
  준비됐고 배선만 없음.
- global_settings_gate.build_display_schema() 는 "새 설정이 정책에 추가되면 자동으로 확인창에
  포함" - 미분류 키는 '기타' 구역 자동 편입, UI 작업 없이 신규 키 노출.
- tests/test_d7_20_execution_settings.py:22-24 는 그룹을 "for g in (...): assert g in d" 멤버십으로만
  검사 - 그룹 추가는 테스트를 깨지 않음(직접확인).

걸림돌(심각도순):
1. [상] 선언만 하고 배선하지 않는 실패 패턴이 이미 이 파일의 지배적 상태. 14그룹 71필드 중
   실제 소비처가 있는 것은 약 12필드(17%)뿐. clamp_chunk_size docstring(:267-269)이 자백:
   "min_chunk_size/max_chunk_size 는 선언만 되어 있고 소비처가 0건이었다 ... 정책 override나
   요청 파라미터로 1이나 10,000,000을 넣어도 사실상 무제한이었다." 같은 실수 반복이 최대 리스크.
2. [상] 그룹 경계를 무엇으로 잡을지가 이미 충돌. 현행 14그룹은 기능축(pause/recovery/checkpoint)
   인데, 이번 요구는 모드축(개별/일괄/전수). SingleExecuteAsync 는 그 사이에 낀 기능x모드
   혼합축(개별 x 4단계async). 축을 섞으면 그룹이 곱셈으로 늘어남.
3. [중] SETTINGS_VERSION="d7-20" 이 테스트 2곳(:25,:46)에 하드코딩 - 구조 변경시 버전 bump+테스트
   수정 필수(단 2줄, 비용은 작음).
4. [중] D계통은 영속화가 없음. _CURRENT 는 프로세스 메모리 전역이라 재기동시 소실, 멀티프로세스면
   워커별로 갈림. C계통은 SQLite 영속. 모드별 override를 D에만 두면 운영 중 조정이 불가능.
5. [하] to_dict() 전체가 /api/execution/settings 로 브라우저에 나감 - 그룹 추가시 payload 자동
   증가(민감정보는 없으나 계약 확대).

■ 3-3. 권장 계층 구조

  [1] 코드 기본값  execution_settings.py - 기능축 dataclass 그룹(현행 14그룹 유지, 손대지 않음)
          v 병합
  [2] 모드 기본값  ModeDefaults(INDIVIDUAL/BATCH/EXHAUSTIVE)  <- 신규, 코드
          v 병합
  [3] 정책 저장소  validation_policy_settings(SQLite, 화면편집)  <- 기존 C계통 재사용
          v 병합
  [4] 환경변수     MV_*(운영 즉시 토글)
          v
     resolve_setting(group, field, mode) -> 최종값 + 적용출처(explainability)

핵심 설계 결정 4가지:

1. 그룹 축은 기능축을 유지하고, 모드는 "차원"으로 붙인다. SingleExecuteAsync 같은 모드x기능
   혼합 그룹을 더 만들지 않는다. 대신 기존 그룹에 대해 모드별 부분 override 사전만 둔다:
     MODE_OVERRIDES = {
         ExecutionMode.BATCH_ROW:   {"concurrency": {...}, "sampling": {...}},
         ExecutionMode.EXHAUSTIVE:  {},          # 빈 틀
     }
   -> 그룹 수가 모드 배수로 늘지 않고, override_group()과 동일한 dataclasses.replace로 구현.

2. 모드는 SharedExecutionContext.mode 에서 읽고, 없으면 INDIVIDUAL로 폴백한다. 함수 시그니처를
   바꾸지 않으므로 batch_single_core_wrapper의 "일괄 전용 로직 금지" 규약과 충돌하지 않는다.

3. 정책 저장소는 policy_name 축을 쓴다 - 'default'/'batch'/'exhaustive'. 스키마·함수 시그니처가
   이미 준비돼 있어 DDL 변경이 불필요하고, 무엇보다 fingerprint 폭발을 피한다(섹션4 참조).
   키 접두어(batch_*) 방식은 키 수가 모드 배수로 늘어 확인창과 fingerprint를 함께 오염시키므로
   권장하지 않는다.

4. 모든 값 조회는 resolve_setting() 단일 함수를 통과시키고, 반환에 적용 출처(ENV/POLICY:batch/
   MODE_DEFAULT/CODE_DEFAULT)를 함께 실어 explainability를 확보한다. clamp_chunk_size_ex() 가
   사유코드를 함께 돌려주는 기존 패턴과 동일하다.

HARD CAP은 계층과 무관하게 코드가 강제한다 - per_group_display_policy.clamp_per_group_thresholds()
처럼 어느 계층에서 무슨 값이 오든 상한을 넘지 못하게 한다. "정책으로 조정 가능"과 "운영 안전"을
동시에 만족시키는 유일한 방법이며 이미 검증된 패턴.

비판적 소견 (CLAUDE.md 비판적 검토 의무)
================================================================

요청대로 설계는 제시했으나 짚어둘 점이 있다. 이 코드베이스의 진짜 문제는 "값이 하드코딩되어
있다"가 아니라 "설정 계통이 이미 4개이고, 만든 설정의 83%가 배선되지 않았다"는 것이다.
다섯 번째 계통을 추가하는 것은 상황을 악화시킬 수 있다.

따라서 0단계를 "새 계통 신설"이 아니라 "기존 D계통(execution_settings.py)에 모드 차원을
붙이고, 동시에 dead 필드를 배선하거나 삭제하는 정리 작업"으로 규정할 것을 권한다. 순수하게
값을 더 옮기는 것보다, 선언과 배선의 간극을 좁히는 것이 우선이다. 이 관점이 반영되지 않으면
1년 뒤 "모드별 설정 71필드 중 12개만 동작함" 상태가 재현된다.

요청/응답 형식(CLAUDE.md "기능/구조 변경 요청 응답 형식"):
- 요청 요약: 3개 검증 모드에 흩어진 하드코딩 설정값을 전역/모드별 계층 구조로 재편하기 위한
  사전 조사·설계
- 긍정적 효과: 모드별 안전한 조정(개별=응답성, 일괄=보수적) 가능, 중복 상수 제거로 "바꿨는데
  안 바뀜" 류 결함 예방
- 구조적 문제점: execution_settings.py 이미 17%만 배선(83% 죽은 필드) - 새 축 추가시 동일
  패턴 재발 위험. 그룹축(기능)과 모드축이 교차하면 그룹 수 폭발 위험
- 운영상 위험: 정책 키를 잘못 추가하면 global_settings_gate fingerprint 불일치로 전 세션
  실행이 즉시 차단됨(policy_name 축으로 회피 가능)
- heuristic/scoring/explainability 영향: 없음(순수 설정값 재배치). resolve_setting()의
  적용출처 반환으로 explainability는 오히려 개선
- 권장 대응책: 0단계=인프라+dead필드 정리, 1단계=SQL타임아웃(이미 모드별로 갈라진 값을
  구조로 옮기기만), 이후 순차 진행. 표본전환 임계값(검증판정 직결)은 최종 단계로 미룸
- 지금 구현 여부: 보류(문서화 우선) - 본 진단은 조사·설계만이며, 구현 착수는 사용자 승인
  이후 0단계부터 별도 확인 절차를 거쳐야 함
