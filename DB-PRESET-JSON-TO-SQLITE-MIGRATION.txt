2. 요구사항 1 — 스키마 마이그레이션
════════════════════════════════════════════════════════════════════
기존 컬럼은 하나도 건드리지 않고 추가만 했습니다(멱등, ALTER TABLE ADD COLUMN).

  + is_deleted            INTEGER NOT NULL DEFAULT 0   (soft delete)
  + last_used_at          TEXT                          (load_preset_conn 경유 접속 시 갱신)
  + advanced_options_json TEXT                          ← 지시서에 없던 추가 컬럼(사유 아래)
  + UNIQUE INDEX ux_mv_db_preset_key
        ON mv_db_preset(IFNULL(project_id,-1), preset_nm, preset_type) WHERE is_deleted=0

■ advanced_options_json 을 추가한 이유(무손실 이관의 필수 조건)
  기존 mv_db_preset 에는 sslmode / sid / schema / charset / connect_timeout /
  connect_type / driver_mode / encoding / nencoding 을 담을 컬럼이 아예 없었습니다.
  JSON 14건 중 12건이 advanced_options 를 갖고 있어(SRC 7 / TGT 5), 이 컬럼 없이
  이관하면 오라클 sid·PG sslmode 가 통째로 사라져 접속 자체가 깨집니다.
  기존 컬럼 변경이 아니라 추가이므로 지시의 "기존 컬럼 변경 없음" 은 지켰습니다.

■ UNIQUE 를 부분 인덱스로 만든 이유(그냥 UNIQUE 로 하면 무효였습니다)
  SQLite 는 UNIQUE 제약에서 NULL 을 서로 다른 값으로 취급합니다. 요구사항 2 에 따라
  project_id 를 전부 NULL 로 넣으므로, UNIQUE(project_id, preset_nm, preset_type) 을
  그대로 걸면 14건 전부가 "서로 다른 키" 로 판정돼 **중복이 전혀 막히지 않습니다**.
  IFNULL(project_id,-1) 식 인덱스로 만들어 의도한 유일성을 실제로 강제했습니다.
  soft delete 행은 WHERE is_deleted=0 으로 제외해, 삭제 후 같은 이름 재생성이 막히지
  않게 했습니다(재생성 시 죽은 행을 되살려 재사용하므로 행이 누적되지도 않습니다).

4. 요구사항 3 — 내부 구현만 교체(시그니처 불변) + 동시저장 유실 제거
════════════════════════════════════════════════════════════════════
■ 시그니처·반환형 불변
  _cmn_load_presets(path) -> list  /  _cmn_save_presets(path, presets) -> None
  반환 dict 키·순서까지 종전과 동일합니다(name, db_type, host, port, dbname, user,
  password + advanced_options 는 비어 있으면 키 자체를 넣지 않음).
  호출자 30여 곳 무수정, routes/db_preset_route.py 도 0줄 변경으로 동작합니다.

  ▶ 여기서 걸린 함정 하나: `path` 인자는 단순 경로가 아니라 **src/tgt 판별자**로 쓰이고 있고,
    테스트 4개(test_db_presets_password_masking / test_db2_mariadb_profile_connectivity /
    test_db_connection_finalize_guard / test_profile_role_edit_and_duplicate_conn)가
    `_PRESETS_SRC/_TGT` 를 임시 JSON 파일 경로로 monkeypatch 합니다.
    무조건 DB 로 보내면 이 테스트들이 자기 픽스처 대신 운영 DB 를 읽어 전부 깨집니다.
    → import 시점에 정경로를 _CANON_SRC/_CANON_TGT 로 얼려두고, 들어온 path 가
      **정경로일 때만** DB 로 보냅니다. monkeypatch 된 임시 경로는 자동으로 JSON 파일 처리 →
      기존 테스트 무수정 통과(실측 확인, §6).

■ lost update 제거 방식
  '통째 덮어쓰기' 를 버리고 **직전 load 스냅샷 대비 delta** 를 단일 BEGIN IMMEDIATE
  트랜잭션으로 적용합니다.
    - 스냅샷에 있었는데 저장 목록에 없다 → soft delete
    - 저장 목록의 프리셋 → upsert (내용 동일하면 write 자체를 생략)
  삭제는 **스냅샷 시점 내용과 현재 DB 내용이 같을 때만** 수행합니다(compare-and-swap).
  그 사이 다른 요청이 그 프리셋을 바꿨다면 삭제를 건너뜁니다 — 남의 변경을 조용히 지우지 않습니다.

■ 동시저장 2건 실측 재현 (요구사항: 실제로 재현해서 확인할 것)
  시나리오: 시드 [A,B,C] → 두 스레드가 동시에 목록을 읽고(barrier 로 읽기 시점 정렬)
            각각 D / E 를 추가해 저장.

    [이관 전(JSON 파일 통째 덮어쓰기)]
       최종 목록 : ['A', 'B', 'C', 'E']   (총 4건)
       유실      : ['D']                  ← 결함 재현됨
    [이관 후(SQLite 트랜잭션 delta)]
       최종 목록 : ['A', 'B', 'C', 'E', 'D']  (총 5건)
       유실      : 없음

    판정: PASS — 재현되던 유실이 이관 후 사라졌다

10. 결론

프리셋 14건이 mv_db_preset 으로 무손실 이관됐고, 화면 3종이 이관 전과 픽셀 단위로 동일합니다.
이번 작업의 실질 이득은 '저장 위치 이동' 자체가 아니라 두 가지입니다. 첫째, 실제로 재현되던
동시저장 유실(D 유실)이 사라졌습니다 — 트랜잭션만 씌운 게 아니라 저장 의미를 통째 덮어쓰기에서
delta 로 바꿨기 때문이며, 단순히 BEGIN 으로 감싸기만 했다면 유실은 그대로 재현됐을 것입니다.
둘째, group_hard_reset_service 의 삭제금지 보호(mv_db_preset)가 빈 테이블이 아니라 실데이터를
지키게 됐습니다.

반면 이번 작업으로 새로 생긴 부담도 분명합니다. 평문 비밀번호가 JSON 과 SQLite 두 곳에 존재하게
됐고(롤백을 위해 의도한 것이지만 롤백 창이 닫히면 정리 대상), 개발 스크립트 292개가 조용히
낡아가는 시한이 시작됐습니다. 둘 다 지금은 무해하지만 방치하면 "왜 스크립트만 옛 접속정보로
붙지" 라는 형태로 되돌아옵니다.

지시 범위를 벗어난 파일 2개를 고친 점은 §0 에 따로 적었습니다. 요구사항 5 를 지키려면 불가피했고,
