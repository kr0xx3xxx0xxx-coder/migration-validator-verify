✅ 작업 완료 - COUNT-TIMEOUT-ERROR-MESSAGE-CATEGORY-FIX - 서술형 완료보고서

■ 무엇이 문제였나

이 작업은 앞선 STATS-COUNT-STEP-TIMEOUT-PARITY-FIX 를 마치면서 별건으로 남겨둔 항목에서
출발했다. 그 작업으로 2단계 COUNT 비교 SQL 에도 statement timeout(COUNT_STATEMENT_TIMEOUT_MS,
기본 60초)이 걸리게 되었는데, 정작 그 타임아웃이 발화했을 때 사용자에게 보이는 문구가
현실과 어긋나 있었다.

services/count_common_service.py 의 categorize_conn_error 는 DB 오류 메시지를 사람이 읽을 수
있는 카테고리로 바꾸는 함수다. 이 함수는 오류 문자열에 'timeout' 또는 'timed out' 이 들어
있으면 그 외 맥락을 보지 않고 '연결 시간 초과'를 반환하고 있었다. 접속 자체가 실패한 경우라면
맞는 안내지만, statement timeout 은 접속이 정상적으로 이루어진 뒤 쿼리 실행이 상한을 넘겨
서버가 문장을 취소한 것이다. 즉 원인은 네트워크나 접속정보가 아니라 데이터 규모와 실행 시간
상한인데, 사용자는 '접속 문제'라는 잘못된 방향으로 안내받고 있었다.

실제로 그런지부터 확인했다. 코드를 고치기 전에, 이전 작업이 남긴 픽스처(mvbench.bench_30m,
3,000만 행)에 statement_timeout 2초를 걸어 COUNT 를 강제로 끊었다. 2.1초 만에 발화했고 원본
메시지는 'canceling statement due to statement timeout' 이었으며, 어댑터 판별기
is_query_timeout_error 는 이를 True(쿼리 타임아웃)로 정확히 판정했다. 그런데 같은 메시지를
categorize_conn_error 에 넣으면 '연결 시간 초과' 가 나왔다. 오분류가 문서상 추정이 아니라
실측으로 확인된 것이다.


■ 어떻게 고쳤나

원칙은 명확했다. 타임아웃인지 아닌지를 '판정'하는 로직은 이미 DBMS 어댑터
(db_adapter_registry.is_query_timeout_error)가 단일 진실원천으로 갖고 있으므로 손대지 않고,
이 파일에서는 그 판정 결과를 받아 '분류와 문구'만 정정하기로 했다. 판별을 다시 구현하면
방언별 규칙이 두 곳으로 갈라지는 전형적인 기술부채가 생긴다.

그래서 _is_query_timeout(msg, exc, db_type) 헬퍼를 두고 판정을 어댑터에 위임했다. 여기서 두
가지 현실적인 제약을 처리해야 했다.

첫째, 호출 경로마다 가진 정보가 다르다. 개별검증(run_count_pair)은 예외 객체와 접속정보를
모두 갖고 있지만, 일괄검증(count_precheck_service)은 예외 문자열만 넘긴다. 그래서
categorize_conn_error 의 시그니처를 (msg, exc=None, db_type=None) 으로 확장해 기존 1인자
호출과의 하위호환을 지키면서, 예외 객체가 있으면 PostgreSQL pgcode(57014)나 MySQL errno 같은
정밀한 근거까지 쓰도록 했다. db_type 이 없을 때는 지원 4개 방언 판별기를 모두 적용한다.
이것도 판정의 재구현이 아니라 위임을 반복하는 것이다. 덕분에 이 파일만 고치고도 일괄검증
경로까지 함께 정정됐다.

둘째, 실측하다 발견한 함정이 있었다. 접속 단계 실패 메시지에도 'timeout expired' 같은 문자열이
들어간다. PostgreSQL 로 도달 불가능한 IP 에 접속을 시도하니 'connection to server at
"10.255.255.1", port 5432 failed: timeout expired' 가 나왔는데, 이 문자열은 MSSQL 어댑터의
쿼리 타임아웃 시그니처('timeout expired')와 겹친다. MSSQL 의 'Login timeout expired' 도
마찬가지다. 어댑터 판정만 그대로 믿었다면 진짜 접속 실패를 쿼리 타임아웃으로 안내하는,
방향만 반대인 같은 종류의 오분류를 새로 만들 뻔했다. 그래서 접속 단계임을 드러내는 표지
목록(_CONNECT_PHASE_MARKERS: 'connection to server', 'login timeout', "can't connect to",
'could not connect', 'tns:connect timeout' 등)을 두고, 이 표지가 있으면 위임 판정보다 먼저
접속 실패로 확정하도록 했다. 이 표지는 '어느 단계에서 난 오류인가'만 가르는 것이지 타임아웃
판정 규칙이 아니므로, 판정 로직 불가침 원칙과 충돌하지 않는다.


■ 문구를 어떻게 정했나 — '재시도해도 동일 실패' 안내 반영 여부

지시받은 판단 항목이다. 결론은 반영이고, 근거는 셋이다.

첫째, 성격이 같다. COUNT statement timeout 도 4단계 통계 SQL 타임아웃과 마찬가지로 실행마다
동일하게 적용되는 고정 상한이다. 일시적 장애가 아니므로 같은 SQL·같은 데이터로 재시도하면
같은 지점에서 잘린다.

둘째, 안내가 사용자의 다음 행동을 바꾼다. '연결 시간 초과'로 보이면 재시도하거나 접속정보를
점검하게 되는데, 실제 해법은 제한 상향이나 검증 대상 축소다. 잘못된 카테고리는 잘못된 조치로
이어진다.

셋째, 시스템 동작과도 맞아떨어진다. db_query_service.is_connection_lost_error 는 '연결 시간
초과' 카테고리 문자열을 '재시도 가능한 연결 장애'로 취급한다. 즉 기존 오분류는 문구만 틀린
것이 아니라, 재접속해도 같은 상한에 걸릴 오류를 재시도 후보로 분류하고 있었던 셈이다. 정정
문구에는 그 패턴이 들어 있지 않아 재시도 대상에서 빠지며, 이 성질이 깨지지 않도록 전용
테스트를 따로 만들어 고정했다.

다만 4단계 문구를 그대로 복사하지는 않았다. 4단계 문구는 여러 줄로 ①②를 나열하는데, COUNT
오류 문구는 일괄검증 그리드 셀에 그대로 표시되고 하위 경로에 200자 절단도 있다. 그래서 톤과
구성요소(현재 제한값, 환경변수명과 ms 원값, 재시도 무의미, 대안 두 가지)는 동일하게 유지하되
한 줄로 압축했다.

  쿼리 실행 시간 초과 (접속은 정상 — 실행 시간이 제한을 초과했습니다). 현재 제한: 60초
  (환경변수 MV_COUNT_STATEMENT_TIMEOUT_MS = 60000 ms). 이 제한은 실행마다 적용되는 고정값이라
  재시도해도 동일하게 실패할 가능성이 높습니다. 제한 상향(환경변수 조정 후 서버 재기동) 또는
  대상 축소(WHERE 조건)를 권장합니다.


■ 검증 결과

수정 전후를 같은 하니스로 실측했다(before_categorize.log / after_categorize.log).

쿼리 타임아웃 케이스는 '연결 시간 초과' 에서 위 정정 문구로 바뀌었다. 접속 실패 케이스는
전부 그대로다. 존재하지 않는 호스트는 '호스트명 조회 실패 (DNS 오류)', 닫힌 포트는 '포트 연결
거부', 도달 불가 IP 로의 접속 타임아웃은 '연결 시간 초과' 를 유지했다. 마지막 케이스가 특히
중요한데, 앞서 말한 표지 가드가 없었다면 오탐될 자리였다. MSSQL 로그인 타임아웃도 같은
이유로 '연결 시간 초과' 를 지킨다.

함수 단위만이 아니라 실제 실행 경로도 확인했다(after_run_count_pair_e2e.log). 환경변수로
제한을 1.5초로 낮추고 run_count_pair 를 태우니 status=ERROR, code=EXEC_ERROR 와 함께
source_count_error 와 count_error_message 에 정정 문구가 그대로 실려 나왔다. 같은 경로에서
접속 실패 케이스는 기존 DNS 오류 문구를 유지했다.

테스트는 신규 14건을 포함해 94건이 통과했다. 유일한 실패인
TestCountConnSeparation::test_TC_COUNT_CONN_01 은 conftest 의 운영 SQLite 쓰기 차단 가드에서
나는 기존 실패다. 같은 저장소에서 count_common_service.py 만 HEAD 버전으로 되돌려 재실행해도
동일하게 실패해 사전 존재 실패임을 확정했다(worktree 는 db 파일이 없어 통과해버리므로
baseline 으로 쓰지 않았다). 기존 회귀 스위트인 samples/test_virtual_cases.py 8/8,
samples/test_complex_cases.py 5/5 도 통과했다.

기동 확인은 HTTP 401 응답으로 했다(Basic Auth 미들웨어가 응답한 것이므로 정상 기동이다).

■ 남겨둔 것

ORA-03136(inbound connection timed out)은 의미상 접속 단계 오류에 가깝지만 Oracle 어댑터가
timeout 으로 판정한다. 이를 바로잡으려면 판별기 자체를 고쳐야 하는데 이번 작업의 불가침
범위여서 손대지 않았고, 오해를 남기지 않도록 테스트 픽스처에서도 제외했다.

db_type 을 알 수 없는 경로의 방언 probe 는 접속 단계 표지 목록에 의존한다. 표지가 없는 새
드라이버 메시지가 등장하면 목록 보강이 필요하다.
