■ 배경/문제
  드롭다운 방언 차단(GROUP-REGISTER-DROPDOWN-DIALECT-MISMATCH-FIX)은 클라이언트 표시까지만이라,
  최종 저장 엔드포인트 /single/save 를 직접 POST 하면 다른 방언으로 바인딩된 그룹에 등록하는
  우회가 이론상 가능했다(defense-in-depth 누락). 이번 과제로 서버측 하드 게이트를 추가.

■ Before/After 실측 (실 파이프라인·실 토큰, 인증 ON, 단계가드 ON)
  방식: PostgreSQL(Inter, 192.168.0.150) 세션으로 analyze→count→generate→execute 실제 구동해
        유효 workflow_token 발급 후, 같은 토큰으로 oracle 바인딩 / postgresql 바인딩 두 그룹에
        /single/save 직접 POST. 세션 방언 db_type=postgresql.

  [Before] baseline 서버(게이트 없음)  http://localhost:8010
    - oracle 그룹 저장 → http=200, code=REGISTER_FAILED
      = 방언으로 차단되지 않고 등록 단계까지 진입(409 DIALECT_MISMATCH 부재) → 우회 표면 실증.
  [After]  메인 서버(게이트 적용)  http://localhost:8000  (재기동 KST 2026-07-26 09:18:49)
    - oracle 그룹 저장 → http=409, code=DIALECT_MISMATCH
      error: "선택한 그룹의 DB 방언과 현재 검증 세션의 방언이 일치하지 않아 공식 저장할 수 없습니다.
             (원본 Oracle 그룹 · 현재 PostgreSQL / 목적지 Oracle 그룹 · 현재 PostgreSQL)"
      run_id=None history_run_id=None target_table=None → 식별자 미발급, 등록/이력 0.
  [회귀] postgresql 그룹 저장 → 두 서버 모두 방언 차단 없음(게이트 통과).
        = 게이트는 '방언'으로만 판정, 정상(동일 방언) 등록 흐름을 막지 않음.
  ※ 양쪽 A/B 공통으로 나타난 REGISTER_FAILED(metadata)는 게이트 무관 하류 단계
    (HTTP 본문 sources 미포함 → 단일 Source metadata SKIP)로 방언 결론에 영향 없음.
    metadata 를 갖춘 in-process 경로에서는 불일치 방언이 실제 등록 성공함을 단위/worktree 테스트로 확인.
