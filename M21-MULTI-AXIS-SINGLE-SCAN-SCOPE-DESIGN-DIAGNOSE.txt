작업명 : M21-MULTI-AXIS-SINGLE-SCAN-SCOPE-DESIGN-DIAGNOSE
✅ 작업 완료 - M21 다축 통계검증 통합쿼리(UNION ALL/GROUPING SETS) 범위·설계 조사 — 실측 결과 두 방식 모두
   유의미한 이득이 없어(UNION ALL 사실상 무변화, GROUPING SETS 오히려 56% 느려짐) 착수를 권하지 않는다

===============================================================================
0. 결론 먼저
===============================================================================
BACKLOG.md M21 항목("장기·지금 권하지 않음")을 실측으로 재검증했다. 결과는 원래 판단을 강하게
뒷받침한다 — 오히려 더 명확한 근거로 "지금 착수 안 함"을 재확인했다.

  (1) GROUPING SETS: NXDNP.MV_SCATTER50M(원본 50M/목적 49.5M)에서 실측 결과 순차 방식보다
      **56.3% 더 느리다**(28,241ms → 44,136ms). 원인은 EXPLAIN PLAN으로 확인했다 — 오라클이
      GROUPING SETS를 "TEMP TABLE TRANSFORMATION"으로 실행한다: 원본 테이블을 1회 풀스캔해
      임시 세그먼트에 통째로 복사한 뒤, 그 임시 세그먼트를 축 개수만큼 다시 읽는다. "스캔 1회"는
      원본 테이블 기준으로는 사실이지만, 570~760MB를 임시 세그먼트에 쓰고 다시 읽는 비용이
      직접 재스캔보다 더 크다. 이 백로그 항목의 핵심 전제("GROUPING SETS로 스캔을 1회로 줄인다")가
      이 오라클 인스턴스에서는 성립하지 않는다.

  (2) UNION ALL: EXPLAIN PLAN상 스캔 횟수가 **줄지 않는다**(축마다 별도 TABLE ACCESS FULL 그대로,
      2회). 실행시간도 "execute 구간만" 보면 44.9% 개선처럼 보이지만, 이는 측정 함정이다 —
      오라클이 UNION ALL의 첫 branch만 execute() 구간에서 완성하고 둘째 branch(축2) 집계는
      fetch() 구간에서 지연 실행한다. execute+fetch를 정직하게 합산하면 원본+목적지 합계가
      **28,241ms → 30,264ms로 오히려 7.2% 느려진다**(§4-4 참조). "스캔을 줄인다"는 원래 아이디어의
      근거 자체가 이 실측에서 없어졌다.

  → 두 방식 모두 이 오라클 인스턴스에서는 채택 근거가 없다. 코드 착수는 권하지 않는다.
    (단, 이 결론은 Oracle Free 23ai/26ai 단일 인스턴스·병렬 실행 옵션 없음이라는 조건에 묶여 있다 —
    §4-5 한계 참조. 이미 실측으로 확인된 더 확실한 레버는 "세트 병렬"이며 이건 이번 조사 범위 밖의
    기존 진단 결과다: 2축 22.2초→10.0초(-55.2%), 20.4초→12.0초(-41.2%). M21보다 그 활용을
    먼저 검토하는 편이 합리적이다.)

2. [통합 쿼리 방식 비교] UNION ALL vs GROUPING SETS
===============================================================================

2-1. 4방언 지원 여부
  · UNION ALL — 완전 표준 SQL, 4방언 모두 문법 차이 없음(dialect-agnostic). 축마다 타입이 다른
    GROUP BY 컬럼값을 하나의 컬럼에 합치려면 문자열 캐스팅이 필요(오라클 TO_CHAR, PG ::text,
    MySQL CAST(...AS CHAR), MSSQL CAST(...AS VARCHAR)) — sqlglot이 이미 4방언 매핑을 갖고 있어
    (source_stats_sql_builder.py:21-23) 문자열 생성 자체는 어렵지 않다.
  · GROUPING SETS — 표준 SQL(SQL:1999)이지만 지원 시점이 다르다: 오라클 9i+, PostgreSQL 9.5+,
    MSSQL 2008+는 문제없다. **MySQL은 명시적 GROUPING SETS 문법이 8.0.31(2022)부터**다(그 전엔
    ROLLUP만 가능). 이 저장소는 실제로 MySQL 5.7 호환을 유지 중이라는 근거를 코드에서 확인했다
    — services/db_adapters/mysql.py:161 주석 "복합키 판정용 제약 컬럼 수는 파생테이블 GROUP BY로
    센다(윈도우함수 미사용 — **MySQL 5.7 호환**)". 즉 GROUPING SETS를 채택하면 MySQL 5.7~8.0.30
    고객 환경에서 파싱 에러(1064)로 전면 실패할 위험이 있다 — "4방언 완전지원"이 아니라 조건부다.

2-2. 결과 파싱 복잡도
  · UNION ALL — branch마다 리터럴 AXIS 태그 컬럼을 추가하면 축 구분이 트리비얼하다(WHERE/CASE
    불필요). 항목4 스크립트가 실제로 이 방식으로 만들어 순차 결과와 완전 일치를 확인했다.
  · GROUPING SETS — 그룹 대상이 아닌 축의 컬럼엔 NULL이 들어가므로, "원본 데이터의 NULL"과
    "GROUPING SETS가 채운 NULL"을 구분하려면 `GROUPING()` 함수로 별도 판별 컬럼이 필수다(항목4
    스크립트도 `CASE WHEN GROUPING(REGION_CD)=0 ...`으로 이렇게 처리했다). GROUP BY 후보 컬럼이
    원래 NULL 값을 가질 수 있는 케이스(nullable 컬럼)에서는 이 판별 로직 없이는 오분류가
    발생하는 치명적 결함이 된다 — UNION ALL 대비 신규 로직이 명확히 더 크다.

2-3. 기존 판정 로직에 미치는 영향 범위
  · UNION ALL — §1-5에서 확인한 대로, "AXIS 기준으로 먼저 결과를 나눈 뒤" 넘기면 지금의 diff/
    src_only/tgt_only 비교 엔진은 사실상 무변경으로 재사용 가능. 영향 범위가 "결과 분배(split)
    단계" 신규 추가로 국한된다.
  · GROUPING SETS — 마찬가지로 AXIS 판별 후 분배가 필요하지만, 추가로 "여러 축 컬럼을 한
    SELECT-list에 넣으면 표시용/실행용 builder의 'GROUP BY 컬럼명 = SELECT 컬럼명 1:1' 관례가
    깨진다"는 문제가 있다 — 이건 UNION ALL엔 없는 추가 설계 부담이다.

2-4. 권장안(설계 단계 판단)
  UNION ALL이 이식성·파싱복잡도·판정영향범위 전부에서 GROUPING SETS보다 안전하다는 게 설계상
  결론이지만, **§4 실측이 두 방식 모두를 성능 근거에서 기각**했다 — GROUPING SETS는 이 오라클에서
  스캔 수가 안 줄고(오히려 임시세그먼트 왕복이 추가돼 더 나쁨), UNION ALL은 스캔 수 자체가
  그대로다(EXPLAIN 확인). 설계상 "그나마 나은 방식"이 UNION ALL이라는 것과, "지금 착수할
  가치가 있는 방식"이 있다는 것은 별개 결론이다 — 후자는 §0의 결론대로 "없다".

4. [성능 이득 사전 추정] 실측(NXDNP.MV_SCATTER50M_SRC/TGT, Oracle Free 23ai/26ai)
===============================================================================

4-1. 방법
  대상: NXDNP.MV_SCATTER50M_SRC(50,000,000행)/MV_SCATTER50M_TGT(49,500,000행), GROUP BY
  REGION_CD(21그룹)+STATUS_CD(10그룹) 2축, SUM(AMT)/SUM(QTY) — LARGE-TABLE-STATS-EXECUTION-
  PERFORMANCE-DIAGNOSE-AND-OPTIMIZE.txt(2026-08-01)와 동일 픽스처·동일 축(재현성 확보).
  세 가지를 같은 세션·연속으로 측정(각 3회 반복, 원본/목적지 각각):
    (1) 현재 방식 — 축별 독립 SQL 2개(REGION_CD, STATUS_CD 순차)
    (2) UNION ALL 통합 SQL 1개(AXIS 판별 컬럼 포함)
    (3) GROUPING SETS 통합 SQL 1개(GROUPING() 판별)
  전 과정 SELECT 전용, DDL/DML 0건. 코드 저장소에 파일을 추가하지 않았다(scratchpad 임시
  스크립트로 실행). 결과값은 3방식 모두 순차 결과와 완전 일치 확인(정합성 문제 없음).

4-2. 원시 측정값(중앙값, ms)

  구분                execute만    execute+fetch(정직한 총합)    EXPLAIN 상 풀스캔 횟수
  ────────────────────────────────────────────────────────────────────────────────
  [asis] 순차 REGION_CD    9,534.1        9,536.6                      1
  [asis] 순차 STATUS_CD    6,343.6        6,345.9                      1
  [asis] 순차 합계         15,877.7       15,882.5                     2
  [asis] UNION ALL          5,746.9       12,920.6*                    2
  [asis] GROUPING SETS     21,802.0       21,804.9                     4(임시세그먼트 재읽기 포함)

  구분                execute만    execute+fetch(정직한 총합)    EXPLAIN 상 풀스캔 횟수
  ────────────────────────────────────────────────────────────────────────────────
  [tobe] 순차 합계         12,363.5       12,368.9                     2
  [tobe] UNION ALL          9,811.8       17,343.4*                    2
  [tobe] GROUPING SETS     22,334.0       22,356.9                     4(임시세그먼트 재읽기 포함)

  * UNION ALL의 execute+fetch는 3회 run의 (execute_ms+fetch_ms) 개별 합산 후 중앙값을 다시 계산한
    값 — execute_median과 fetch_median을 따로 더한 값이 아니다(정직한 합산 방식).

4-3. 요약(원본+목적지 합계)

  방식                  execute만 기준      execute+fetch 기준(정직)   판정
  ─────────────────────────────────────────────────────────────────────────
  현재(순차)             28,241.2ms          28,251.4ms                 기준
  UNION ALL              15,558.7ms(-44.9%)   30,264.0ms(**+7.2%**)     개선 없음
  GROUPING SETS          44,136.0ms(+56.3%)   44,161.8ms(+56.3%)        더 나쁨

4-4. 왜 "execute만" 기준이 틀렸는가(측정 함정 — 반드시 반영해야 할 내용)
  오라클 드라이버(oracledb)의 `cur.execute()`는 UNION ALL의 **첫 branch가 결과를 만들 때까지만**
  블록되고, 둘째 branch(축2)의 실제 집계 스캔은 `fetchall()` 구간에서 지연 실행된다(파이프라인
  실행). 그래서 "execute만" 잰 44.9% 개선은 **실제로 줄어든 일이 아니라 어디서 재는지에 따라
  달라진 착시**다 — fetch까지 정직하게 합치면 오히려 순차보다 7.2% 느리다. 이 프로젝트의
  운영 코드(services/stats_execute_service.py)는 결과를 반드시 fetchall()까지 받아야 판정이
  가능하므로, 사용자 체감 시간은 "execute+fetch 총합" 쪽이 맞는 지표다.

4-5. GROUPING SETS가 느린 이유(EXPLAIN PLAN 확인)
  Oracle이 GROUPING SETS를 "TEMP TABLE TRANSFORMATION"으로 실행한다:
    1) 원본 테이블 1회 풀스캔 → 임시 세그먼트(SYS_TEMP_...)에 적재(LOAD AS SELECT)
    2) 그 임시 세그먼트를 축(그룹핑셋) 개수만큼 다시 풀스캔(REGION_CD용 1회, STATUS_CD용 1회)
    3) 최종 VIEW 단계에서 작은 결과셋을 다시 읽음(21행, 비용 미미)
  즉 "베이스 테이블 스캔은 1회"라는 광고는 지켜지지만, 570~760MB를 임시 세그먼트에 쓰고
  두 번 다시 읽는 총 I/O가 그냥 직접 2번 스캔하는 것보다 크다 — 이 오라클 인스턴스에서는
  명백한 역효과다.

4-6. 측정의 한계(정직하게 밝힘)
  · 이 인스턴스는 버퍼 캐시 온도에 크게 흔들린다(기존 진단서가 이미 1.4~18배 편차를 보고함).
    이번 측정은 (1)→(2)→(3) 순서로 **같은 세션에서 연속 실행**했다 — UNION ALL은 순차 측정
    직후라 캐시가 이미 데워진 상태에서 쟀을 가능성이 있다(execute+fetch 기준으로도 +7.2%에
    그친 것이 오히려 그 온기 덕분일 수 있다 — 무작위 순서였다면 더 나쁘게 나왔을 가능성도
    배제 못 한다). 반대로 GROUPING SETS는 가장 나중에(가장 캐시가 따뜻한 시점에) 쟀는데도
    가장 느렸다 — 이건 캐시 효과로 설명이 안 되고, TEMP TABLE 재작성이라는 구조적 비용임을
    뒷받침한다.
  · 이 결과는 **Oracle Free 23ai/26ai, 병렬 실행 옵션 없음, 단일 인스턴스** 조건에 한정된다
    (기존 진단서 확인 사실). 병렬 실행이 가능한 고객 운영 오라클(EE)이나 PostgreSQL에서는
    옵티마이저 전략이 달라 결과가 달라질 수 있다 — 이번 조사는 "지금 이 환경에서 착수할
    근거가 없다"까지만 확정한다.
