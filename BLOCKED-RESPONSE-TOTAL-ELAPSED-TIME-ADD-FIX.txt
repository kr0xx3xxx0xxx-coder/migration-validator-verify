1. 배경 · 요청
────────────────────────────────────────────────────────────────────────
백로그 M32 — 결과 그룹 상한 초과로 차단(BLOCKED)된 케이스는 query_timing 이 성공 경로에서만
채워져 DB 구간이 0ms 로 기록되고 전체 소요가 통째로 '앱 구간'으로 잡힌다. 차단은 보통 가장
오래 걸린 실행에서 발생하므로, 이 필드로 성능 회귀를 추적하면 최악 케이스가 조용히 통계에서
사라진다.
근거: E:\verify_reports\STATS-SCALE-COST-BAND-BENCHMARK-MEASURE.txt §7-2

요구사항
  ① query_timing 을 채우는 코드가 성공 경로에만 있는지 확인
  ② BLOCKED 응답에도 실제 소요시간 기록(구간 분리가 어려우면 총 소요시간만이라도)
  ③ 기존 성공 경로 query_timing 동작 무회귀

────────────────────────────────────────────────────────────────────────
2. 위치 확인 결과 (요구사항 ①)
────────────────────────────────────────────────────────────────────────
query_timing 을 만드는 지점은 제품 코드에서 단 한 곳이었다.

  services/stats_execute_service.py : execute_stats_validation()
    - 543~552행(수정 전) : 성공 반환 직전에서만 query_timing 조립
    - 603행(수정 전)     : 성공 응답 dict 에만 "query_timing" 키 포함

반면 BLOCKED 응답을 만드는 _exec_blocked_result() 는 query_timing 키 자체를 넣지 않았다.
호출부는 3곳이며 전부 '실행 후' 차단이다.

  (a) 결과 그룹 상한 초과      STATISTICS_RESULT_LIMIT_EXCEEDED   ← 양쪽 fetch 완료 후 차단
  (b) 목적지 read-only 강제 실패 READ_ONLY_SESSION_ENFORCEMENT_FAILED
  (c) 원본 read-only 강제 실패  READ_ONLY_SESSION_ENFORCEMENT_FAILED

즉 (a)는 DB 조회를 이미 다 끝낸 뒤 차단하면서도 그 구간 시간을 응답에 남기지 않았다.
소비처: 저장 스냅샷(services/single_validation_result_store.py `_query_timing_for_snapshot`,
8개 키 whitelist)과 성능 측정 하니스(scripts/dev_e2e/stats_scale_cost_band_benchmark.py 의
db_ms/app_ms 분해)가 이 필드를 읽는다. → 차단 케이스는 db_ms=0 으로 집계됐다.

3. 수정 내용 (요구사항 ②·③)
────────────────────────────────────────────────────────────────────────
services/stats_execute_service.py

  [신설] _blocked_query_timing(total_elapsed_ms, src_timing=None, tgt_timing=None)
      성공 경로와 동일한 8개 키 + 차단 전용 total_elapsed_ms(총 소요시간, ms).
      gap 규칙(target 시작 − source 종료, 한쪽이라도 없으면 None)도 성공 경로와 동일.
      구간 timing 이 없는 경우 시각을 임의로 만들지 않고 성공 경로와 같은 '빈 값' 형태를 유지한다.

  [확장] _exec_blocked_result(..., query_timing=None)
      dict 가 전달된 경우에만 응답에 "query_timing" 키를 넣는다(None 이면 과거 계약 그대로).

  [배선] execute_stats_validation() 진입 시점(_t_entry)을 기준으로 _elapsed_ms() 계산 후
      차단 3경로에 각각 전달
        (a) 결과 상한 초과       → src/tgt DB 구간 + 총 소요시간 모두 실측값
        (b) 목적지 read-only 실패 → 원본 구간(실측) 보존 + 총 소요시간
        (c) 원본 read-only 실패   → 총 소요시간만(예외로 끝나 구간 분리 불가)

  [무변경] 성공 경로 query_timing 조립 코드(540~552행)는 한 줄도 바꾸지 않았다.
           공식 스냅샷의 8개 키 whitelist 도 그대로다 → 저장 계약 영향 0
           (total_elapsed_ms 는 whitelist 밖이라 저장 스냅샷에 섞이지 않는다).

판정 로직·상한값·타임아웃·비교 결과는 일절 변경하지 않았다(계측 필드 추가 전용).

      기록되지 않는다.
[7-3] total_elapsed_ms 는 공식 스냅샷 whitelist(8개 키) 밖이라 저장·재조회로는 보존되지 않는다.
