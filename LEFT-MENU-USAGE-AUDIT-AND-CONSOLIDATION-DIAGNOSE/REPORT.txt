■ 0. 요약

  "검증 현황판" 신설을 앞두고 기존 좌측 메뉴를 감이 아닌 실측으로 진단했다.
  코드(ui/tabler_renderer.py 2218~2379행)와 실제 서빙 DOM 을 대조한 결과 8개 그룹
  28개 항목으로 완전히 일치했고, 이 중 15개가 "준비중" 배지 항목이다. 즉 메뉴의
  53.6% 가 클릭해도 아무 일이 일어나지 않는 항목이다.

  가장 중요한 발견은 "준비중이라 표시돼 있지만 실제로는 이미 다른 화면에 구현이
  끝난" 항목이 4건이라는 점이다. 이들은 미구현이 아니라 오표기이며, 사용자에게는
  "이 제품은 절반이 미완성"이라는 잘못된 신호를 준다.

  두 번째 발견은 "검증 현황판" 신설이 곧바로 3중 중복을 만든다는 점이다. 현재
  홈 대시보드(tab-home)가 메뉴에는 없이 좌상단 브랜드 로고 클릭으로만 도달 가능한
  상태로 존재하고, 그 내용은 전부 sample 하드코딩이며, 동시에 "준비중/HOLD" 그룹
  안에 "대시보드"라는 죽은 항목이 또 있다. 현황판을 신설하기 전에 이 둘을 먼저
  정리하지 않으면 같은 성격의 화면이 3개가 된다.

  정리 결론 : 28항목 → 17항목 (준비중 15 → 2). 제거 9, 통합 3, 존치 16.

■ 3. 준비중 표기와 실제 구현의 모순 (핵심 발견)

  "준비중"이라 표시돼 있지만 실제로는 구현이 끝나 다른 화면에서 매일 쓰이고 있는
  항목이 4건이다. DOM 실측으로 각 기능의 실제 소재지를 확정했다.

  (1) "업로드 배치 이력" [HOLD, 62일 방치]
      실제 구현 : #quHistoryCard — 이관쿼리 업로드 화면(tab-queryupload) 안에
      "업로드 관리 · 품질점검" 카드로 존재. /batch/group-upload-history API 로
      그룹별 전체 업로드 차수를 조회하며, 품질점검·활성파일 관리까지 붙어 있다.
      → 미구현이 아니라 이미 완성된 기능의 오표기.

  (2) "최신 검증대상" [HOLD, 62일 방치]
      실제 구현 : #batchLatestCard — 일괄검증 화면(tab-batch) 안에 존재.
      batchLoadLatestTargets() 로 페이징·상태필터·검색까지 갖춘 목록이 동작한다.
      → 오표기. 과거 개별검증 화면에 있던 것이 TASK29 에서 일괄검증으로 이동했고,
        메뉴 항목만 준비중 상태로 남았다.

  (3) "증적 다운로드" [55일 방치]
      실제 구현 : 검증 결과 상세 화면에 "전체 결과 다운로드(CSV)", "전체 결과
      다운로드(XLSX)" 버튼이 실재하며 동작한다(실측 캡처 07번).
      → 오표기.

  (4) "검증 그룹" [HOLD, 49일 방치]
      실제 구현 : 최상단 "프로젝트 > 검증 그룹 관리"가 완전 동작하며 현재 15개
      그룹이 등록돼 있다. 생성/수정/삭제/복구까지 갖췄다.
      → 명백한 중복 항목.

  이 4건은 "아직 안 만든 기능"이 아니라 "이미 만들었는데 메뉴가 못 따라온 기능"
  이다. 방치 기간이 길수록 사용자는 제품 완성도를 실제보다 낮게 인식한다.


■ 4. 기능 중복 여부 검증 (겹치는 것 / 겹치지 않는 것)

  겹치지 않아 둘 다 존치해야 하는 쌍 :

  · "실행 이력" vs "검증 결과 상세" — 서로 다른 데이터다.
    실행 이력은 /history/runs 기반으로 개별검증 run 단위 이력을 보여주고(200건+),
    검증 결과 상세는 batch_run_id 입력이 필수인 일괄검증 결과 조회 화면이다.
    batch_run_id 없이는 "batch_run_id를 입력하고 [조회]를 누르세요"만 표시된다.
    → 성격이 다르므로 통합하면 오히려 개별검증 이력 접근이 막힌다. 둘 다 존치.

  · "검증 기준" vs "검증 결과" — 완전히 별개다.
    검증 기준(후보추천 정책)은 후보 컬럼 자동선정 기준을 설정하는 입력 화면이고,
    검증 결과는 실행 결과를 조회하는 출력 화면이다. 중복 아님.

  겹쳐서 정리가 필요한 쌍 :

  · "자동진단" vs "진단 이력" — 자동진단은 독립 화면이 아니다.
    실측 결과 자동진단에 직접 들어가면 항상 "이 화면은 공식 저장된 진단 상세
    조회용입니다. 진단 이력에서 항목을 선택하면 여기에 표시됩니다"라는 안내문만
    뜨고 본문(#diagBody)은 숨김 상태다. 즉 진단 이력을 먼저 거치지 않으면 절대
    내용이 표시되지 않는 종속 화면이며, 사실상 진단 이력의 상세 뷰다.
    게다가 진단 이력은 전체 저장분이 2건뿐이라 실사용도 거의 없다.

  · "대시보드"(HOLD) vs tab-home vs 신설 예정 "검증 현황판" — 3중 중복 위험.
    tab-home 은 실재하지만 메뉴 진입점이 없고, 화면 스스로 "위 요약·활동·프로젝트·
    도넛은 홈 화면 예시(sample)이며 실제 데이터 연동은 후속 작업입니다"라고 명시
    한다. 프로젝트 12개·검증그룹 28개 같은 숫자가 전부 하드코딩이다(실 데이터는
    그룹 15개). 여기에 HOLD 의 죽은 "대시보드" 항목까지 더해 같은 성격이 3개다.

  · "전수/정밀검증"(HOLD) vs "전수검증"(주요 검증) vs "전수/정밀검증 결과"(검증 결과)
    → 아직 하나도 구현되지 않은 기능이 메뉴에 3개 항목으로 존재한다.

  · "드라이버 / 환경설정" vs "환경설정" — 같은 그룹 안에서 라벨이 사실상 중복이다.

            구현되는 시점에 그 화면 안에서 결과를 보여주는 것이 자연스럽다.
  9. 기반정보 > 환경설정
     근거 : 같은 그룹의 "드라이버 / 환경설정"과 라벨 중복.

  15. 검증 기준 > 전수검증 전략 정책 [준비중]
      근거 : 13번(전수검증)과 한 세트다. 전수검증을 존치하는 이상 그 실행 전략을

■ 7. 위험 / 주의사항

  · 이번 작업은 진단만 수행했다. 코드와 메뉴는 전혀 수정하지 않았다.
  · 제거 대상 9개는 전부 메뉴 항목(<li>) 삭제만으로 끝나며 기능 코드 삭제가
    아니다. 실제 구현이 있는 4건(업로드 배치 이력·최신 검증대상·증적 다운로드·
    검증 그룹)은 각자의 화면에서 계속 동작한다.
  · 통합 3건(자동진단·드라이버 환경설정·감사 리포트)은 메뉴 레벨 통합이므로
    tab-diagnosis 등의 화면 코드는 남겨두고 진입 경로만 바꾸는 것을 권고한다.
    특히 자동진단은 개별검증 불일치 행 클릭 시 인라인으로 펼쳐지는 경로가 따로
    있으므로, 화면 자체를 지우면 그 경로가 깨질 수 있다. 반드시 메뉴만 손댈 것.
  · 홈 대시보드(tab-home)의 sample 하드코딩 숫자는 실제 데이터(그룹 15건)와
    크게 어긋난다(화면 표시 28건). 현황판 신설 시 이 화면을 그대로 두면 서로 다른
    숫자를 보여주는 화면이 둘이 되므로, 현황판 작업과 함께 정리해야 한다.
  · 진단 이력이 2건뿐인 점은 불일치 진단 기능 자체의 실사용이 거의 없다는 뜻이다.
    메뉴에서 지울 근거로는 부족하지만(기능은 정상 동작), 현황판 설계 시 진단
    관련 지표에 큰 면적을 배정할 필요는 없어 보인다.
