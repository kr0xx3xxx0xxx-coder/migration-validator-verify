[결론 한 줄]
"원래 탭이 자기 job 완료를 백그라운드로 감시" 방식 자체는 타당하고 팝업 통신(BroadcastChannel)보다
확실히 단순하다. 그러나 지금 감시할 job 이 없다 — 4단계 실행은 job 이 아니라 단일 blocking HTTP
요청이다. 이 기능의 본체는 자동전환이 아니라 '4단계 실행의 비동기 job 화'이며 그것이 공수의 대부분이다.

[지시의 전제 1건 정정]
지시 3의 "기존 정책은 시작 시 자동전환 금지였고 완료 시는 정책이 없었다"는 사실과 다르다.
08c2119(2026-07-08) "단계 버튼 성공 후 자동 탭 이동 전면 제거"가 바로 '완료 시' 정책이며,
runExecute·_runExecutePlanSets 성공 경로를 명시 대상으로 삼았다. 테스트가 정책 문구까지 잠가 놨다.

  → 재사용 가능한 것은 L3 골격과 배지 인프라(data-jobbadge)뿐. 새로 필요한 것은 서버 job + 상태 API.

[지시 2] 완료 판정 기준 — 기존 /jobs API 로는 감지 불가

  실측 GET /jobs/active → counts.by_source = {"single":0,"batch":0,"stats":0,"full":0}
    single = 개별검증 '재이관 상세'(exact_diff) — 4단계 통계검증 실행이 아니다
    batch  = 일괄검증 batch_execution_state
    stats  = **일괄** 통계검증 계획 실행(batch_stats_execute_run)
    full   = 전수검증(실행 구조 없음)
  개별검증 4단계 실행은 네 소스 어디에도 없다 → GET /jobs/{id} 로 완료를 감지할 수 없다.

  다만 확장 비용은 작다:
    · terminal 판정이 화이트리스트가 아닌 여집합으로 정의돼 새 상태가 조용히 누락되지 않음
    · 복합키 source:id 체계가 있어 single_exec:<run_id> 로 자연 확장
    · 제약: job_registry 는 read-only·원본 무수정 원칙 → '저장소 신설 → 어댑터 추가' 순서 필수

[지시 4] 탭 이탈 후 감시 지속 — SPA 는 살지만, 다른 검증으로 이동하면 실행이 죽는다

  실측(증적 feasibility_probe.json / timer_persistence_probe.json):
    · SPA 내부 탭 이동(현황판→개별검증): 문서 유지 → 타이머 생존. 이탈 상태에서 폴링 1회 실제 발생
      (pollCount 2→3). 새로고침은 문서 파괴로 소멸(재개 없음).
    · 이탈 + 활성 job 0: 정지 — _jdSchedule 의 (!visible && stopWhenIdle && activeCount===0)
    · 가짜 활성 job 주입: 첫 폴링 응답이 서버 목록(활성 0)으로 덮어써 즉시 정지
      → 서버가 활성으로 인정하는 job 이 있어야만 백그라운드 감시가 지속된다(핵심)
    · 폴링 주기: 표시 중 3,000ms / 이탈 후 배지 15,000ms (execution_settings.polling — 하드코딩 아님)
    · 브라우저 hidden throttling: 미측정. headless Chromium 에 Emulation.setPageVisibilityState 가 없어
      hidden 을 만들지 못했다(visible 상태 1초 tick gap 993~1016ms 정상). 추정값을 만들지 않고 미확보로 남긴다.

  결정적 발견 — 실측 { "outcome": "ABORTED", "verBumped": 3 }
    resetIndividualValidationWorkSession(15068)이 _singleNewAbortSignal() 로 진행 중 fetch 를 abort 한다.
    호출 지점: DB 프로필/경로 변경(PROFILE_CHANGE) · runAnalyze 진입(ANALYZE = 다른 테이블 검증 시작)
              · 전체검증(FULL_RUN) · 수동 초기화/새로고침(MANUAL_OR_RELOAD)
    → "실행 걸어놓고 다른 검증 진행" 시나리오가 현재 구조에서 아예 성립하지 않는다.
      서버는 계속 실행되지만(클라 이탈 미감지) persist=False 라 결과는 버려진다.

[지시 6] 다중 감시 / 다른 화면 방해 — 조건부 전환 필수

  개별검증 화면은 단일 작업-세션이다(_analyzeData·_singleLastExecResult·_singleViewStep·
  _singleWorkflowToken 이 전역 1세트). job A 완료로 5단계를 렌더하면 사용자가 보던 job B 의 화면을
  탭 전환이 아니라 데이터까지 덮어쓴다.
    완료 감지 시 3중 일치(세션 버전 + workflow_token + job_id)일 때만 자동전환,
    그 외에는 비침습 알림만(현황판 배지 data-jobbadge + '결과 보기' 링크).
  동시 여러 job 이어도 타이머는 화면당 1개 — GET /jobs/active 한 번이 N 개를 내려준다.
  (L2 가 패널마다 독립 루프를 만들어 체감 60ms 폭주를 낳은 전례 있음)

[지시 7] 오늘의 스냅샷 3작업과의 관계 — 별개다

  같은 문서·같은 탭이므로 세션 상태가 끊기지 않는다. 결과는 이미 _singleLastExecResult 에 있고
  _mvRenderValidationDetail 이 5단계 DOM 에 렌더해 둔 상태(.mv-pane-hidden 으로 가려져 있을 뿐)라,
  5단계 전환은 pane 표시 전환이지 결과 재구성이 아니다 → 스냅샷 필드가 개입할 지점이 없다.
  오늘 3작업(표시 등급 D1~D4 근거 필드 / 원본·목적 그룹 수 2필드 / preset sslmode 복원)은
  이 기능과 무관하게 독립적 가치로 남는다.
  스냅샷/복원이 필요해지는 경우는 (a) 새로고침·브라우저 재시작 후 결과 복원, (b) 현황판 완료 목록에서
  열기 두 가지뿐이며, 비동기 job 화만 놓고 보면 job 객체에 /execute 응답 dict 를 그대로 담으면 된다.
