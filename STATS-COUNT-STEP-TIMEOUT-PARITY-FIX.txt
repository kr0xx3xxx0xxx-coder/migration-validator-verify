✅ 작업 완료 - STATS-COUNT-STEP-TIMEOUT-PARITY-FIX : 2단계 COUNT 비교 SQL 에 실행 시간 상한(60초) 적용, 4단계와 비대칭 해소

■ 요청 요약
2단계 COUNT 비교 SQL 에는 타임아웃이 없어(무제한) 60초 상한이 있는 4단계와 비대칭이던 것을,
services/db_query_service.py 단일 파일 수정으로 4단계와 동일한 메커니즘을 재사용해 해소.

■ 조치 내용 (services/db_query_service.py 만 수정)
1) COUNT_STATEMENT_TIMEOUT_MS 추가 — env MV_COUNT_STATEMENT_TIMEOUT_MS, 기본 60000
   (4단계 EXECUTE_STATEMENT_TIMEOUT_MS 와 동일 형태·동일 기본값. 새 설정 체계 없음)
2) _cmn_db_fetch_count(..., *, statement_timeout_ms=None) — 커서 생성 직후
   get_adapter(db_type).apply_query_timeout 위임 (방언 분기는 어댑터에 캡슐화, 이 파일 미증가)
3) _restore_scope_query_timeout() — finally 에서 scope 기준값(없으면 0=무제한)으로 복귀.
   PG(세션 SET)·Oracle(call_timeout) 모두 연결에 남으므로, COUNT 상한이 같은 scope 의
   후속 analyze/profile 쿼리를 오탐 취소하지 않게 막는다.
4) _NoCloseConn.__setattr__ 위임 — 작업 중 발견한 2차 갭. 프록시가 읽기만 위임해
   Oracle 의 conn.call_timeout 대입이 실제 연결에 닿지 않아 조용히 무효였다(ablation 실증).
   기존 _cmn_db_fetch_all 의 Oracle timeout 에도 있던 갭이 함께 해소된다.

■ 값 선택 근거 — 별도 값(더 짧게) 대신 4단계와 같은 60초
- 하한: 정상 대용량 COUNT 도 수십 초다. mvbench.bench_30m(3,000만 행/3.7GB) 단순 COUNT(*)
  반복 실측 19.4 / 22.6 / 22.7 / 23.5 / 24.6초. 30초로 줄이면 마진 20% 남짓이라
  캐시 콜드·동시부하에서 정상 COUNT 를 오탐 취소한다.
- 상한: COUNT 는 같은 테이블 GROUP BY(4단계)보다 항상 가볍다. COUNT 가 60초를 넘겼다면
  뒤따르는 통계검증은 확실히 60초에 걸리므로, 60초보다 크게 두면 무의미한 대기만 늘어난다.
→ 양쪽 근거가 같은 값을 가리킨다. 결과적으로 4단계와 동일(=parity). 더 짧게 쓰려면 env 로 조정.

■ 실측 검증 (내부망 PostgreSQL_Inter_asis · mvbench 3,000만 행 픽스처, read-only)
[Before / After]  느린 COUNT = bench_30m(3,000만) × bench_dim(50) × 3 = 45억 행
  Before(수정 전 코드, worktree 68c75ae) : 168.4초 완주 — 상한 없음
  After (기본 60초)                      : 60.2초 중단 · is_query_timeout_error=True
                                           "canceling statement due to statement timeout"
[정상 케이스 회귀 없음]
  3,000만 행 plain COUNT → 22.7초 정상 반환(30,000,000)
  100만 행 plain COUNT   → 0.1초 정상 반환(1,000,000)
[scope 누수 가드]
  scope 안 COUNT 실행 후 같은 연결 statement_timeout = 0 (무제한 복귀)
[단계 경로 E2E — count_common_service.run_count_pair]
  env 1500ms → source COUNT 1,671ms 중단, status=ERROR / count_error_code=EXEC_ERROR,
               목적지 COUNT 는 이어서 82ms 정상(연결 오염 없음)
  기본 60초  → source COUNT 23.5초 정상, status=FAILED / COUNT_MISMATCH(실행오류 아님)
[Oracle — 방언 확장 + 프록시 갭 ablation]
  O1 scope 없음 3000ms → DPY-4024 발화(3.5초) / O2 scope 안 → 3.1초 발화
  O2b ablation(__setattr__ 위임 제거=수정 전) → 상한 미적용, 11.6초 완주 (갭 실증)
  O3 기본 60초 정상 COUNT 0.1초 / O4 scope 종료 후 call_timeout=0 복귀
