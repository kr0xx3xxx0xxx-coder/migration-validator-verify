■ 원인(실측 확정)
  runAnalyze 는 시작 시 _mvClearStageProcessingTime(1) 로 1단계 슬롯에
  '· 1단계 계산 중...'을 걸어둔다. 이 문구는 성공 렌더
  (_mvShowStageProcessingTime(1, diagnostics.total_ms))에서만 교체되는데,
  SQL 형식 사전검증이 CRITICAL/UNSUPPORTED 로 차단하면 /analyze 를 호출하지 않고
  그 자리에서 return 하므로 교체가 영영 일어나지 않는다.
  2단계(runCount finally)·5단계(plan-sets finally)에는 이미 같은 청소가 있었다.

■ 수정
  차단 분기에 2·5단계와 동일한 조건식·구조의 청소를 붙였다(표시 전용, 판정 불변):
    var _s1pt = document.getElementById('mvStage1ProcessingTime');
    if (_s1pt && (_s1pt.textContent || '').indexOf('계산 중') >= 0) _s1pt.textContent = '';
  이미 처리시간이 도착한 경우에는 '계산 중'이 없어 no-op 다.

  숨긴 조상 0개 · 높이 66px · innerHTML 존재.

    1600x1200 뷰포트: top=854  → 보임

  패턴(scrollIntoView)만 재사용해 차단 시 배너 위치로 스크롤한다(새 UI 없음).

[파트 B] M31 — '허용 N분'이 60초 미만에서 '0분'       ✅ 대상 부재(이미 해소) · 가드만 추가
────────────────────────────────────────────────────────────────────────
■ 결론
  지적된 코드(_ageTxt + Math.round(profile_max_age_seconds / 60) + '분')는
  현재 코드베이스에 없다. '실행 기준' 요약 박스(_mvExecBasisHtml) 전체와 함께
  커밋 a1e4b7c (STAGE5-MISMATCH-GRID-HEADER-CLEANUP-FIX, 2026-08-05)에서 이미
  삭제됐다. 삭제된 원본 diff 에서 지적된 두 줄을 그대로 확인했다:
    -  var _ageTxt = (_ageS < 60) ? (Math.round(_ageS) + '초')
    -              : (_ageS < 3600) ? (Math.round(_ageS / 60) + '분') : ...
    -    + ' — 허용 ' + E(String(Math.round((gs.profile_max_age_seconds || 0) / 60))) + '분 초과 ...'

■ 실측 (scripts/dev_e2e/stage15_profile_age_allowance_text_probe.py)
  · 렌더된 페이지(2,445,567자) 내 잔존:
      _ageTxt 0건 / profile_max_age_seconds 0건 / profile_age_seconds 0건
      _mvExecBasisHtml 정의 0건 / 조건 없는 '분' 반올림 식 0건
  · 임계값을 60초 미만(30초)으로 낮춰 stale 을 강제한 실측:
      허용   30초 · 경과   90초 → stale=True  "후보 프로파일 경과 90초 > 허용 30초"
      허용   30초 · 경과   10초 → stale=False (문구 없음)
      허용 1800초 · 경과   90초 → stale=False (운영 기본값, 종전과 동일)
      허용 1800초 · 경과 2400초 → stale=True  "경과 2400초 > 허용 1800초"
      → '0분' 표시 발생 0건. 서버 문구는 초 단위라 오표시 경로 자체가 없다.
  · 브라우저 화면에서도 재확인: 4단계 실행 완료 화면 본문 텍스트에
    /허용\s*\d+\s*분/ 매치 False (파트 C 드라이버가 함께 측정).

■ 지시하신 '헬퍼 추출·재사용'을 하지 않은 이유
  화면에 남은 시간 문구 헬퍼는 2개이고 둘 다 이미 60초 미만 '초' 분기를 갖고 있다:
    _mvExecStepProgressFmt : s < 60 → '45초' / 이상 → '1분 05초'
    _jdAgo(job 대시보드)    : s < 60 → '초' / < 3600 → '분' / 이상 → '시간'
  재사용할 중복 로직이 남아 있지 않아 새 헬퍼를 만들면 오히려 미사용 코드가 된다.
  대신 이 상태가 되돌아가지 않도록 회귀 가드만 추가했다(코드 변경 없음).

■ 비판적 검토(정보 손실 여부)
  '후보 프로파일 경과/허용' 표기가 화면에서 사라진 것은 a1e4b7c 의 의도된 정리다.
  판정 자체(EXPLAIN 강제·safety 계약 필드)는 서버에 그대로 있고 증적에도 남는다.
  다만 사용자가 '왜 EXPLAIN 이 강제됐는지'를 화면에서 볼 수 없다는 점은 남아 있다 —
  이번 작업 범위 밖이라 수정하지 않았고, 필요하면 별도 항목으로 다루는 것을 권한다.

■ 재현 방법(타이밍 의존 없음)

  본문으로 workflow_stage_guard.begin_execution('execute', req) 를 직접 호출해
  in-flight 표식을 심었다 = '다른 탭이 같은 문맥을 실행 중' 상태의 결정적 재현.
  그 뒤 화면에서 [통계검증 실행]을 정상 클릭 → 클라이언트 가드는 통과, 서버만 409.

■ before 실측 결과(= M30 지적의 실제 상태)
  · 화면 알림(alert/toast) 0건
  · 사유는 4단계 오류 패널(#mvExecStepError)에는 표시됐다:
      "같은 검증 문맥의 '통계검증 실행' 이(가) 이미 실행 중입니다(2초 경과). ..."
  · 즉 '콘솔에만 기록'은 아니었고, '즉시 눈에 띄는 알림이 없다'가 정확한 상태다.
  · 409 응답 2건 수신 확인.

■ 수정
  1) /execute(runExecute): 409 + code EXECUTION_ALREADY_IN_PROGRESS 이면
     클라이언트 가드가 이미 쓰는 같은 컴포넌트 _mvNotifyRunActiveBlocked 로
     서버 문구를 띄운다. 새 알림 UI 발명 없음. 오류 패널 표시는 종전대로 유지.
  2) _mvNotifyRunActiveBlocked(subject, detail) — detail 선택 인자 추가.
     미지정(기존 호출부 전부)이면 종전 문구 그대로임을 node 하니스로 3경로 고정.
  3) /execute/set(runValidationSet, ui/validation_plan_renderer.py): 종전에는
     `throw new Error('서버 오류 ' + resp.status)` 로 응답 본문을 통째로 버려
     서버 사유가 사라지고, catch 가 '이 검증 set 실행 중 오류 — GROUP BY/SUM
     컬럼 구성을 확인하세요'로 오도했다. 본문을 읽어 사유를 살리고 같은 컴포넌트로
     알리며, 안내 문구를 원인별로 갈랐다(일반 오류 안내는 유지).
     ※ 지시서의 수정 대상 파일(ui/tabler_renderer.py) 범위를 넘는 변경이라 명시한다.
       같은 S16 409 를 받는 두 번째 사용자 경로여서 함께 고쳤다.
