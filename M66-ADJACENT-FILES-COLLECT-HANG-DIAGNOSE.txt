작업명: M66-ADJACENT-FILES-COLLECT-HANG-DIAGNOSE
✅ 작업 완료 - M66: "hang"은 실제 무한대기가 아니었다 — pytest 인자수(140개 개별 파일) × tests/ 디렉토리 크기(1,248개) 조합이 만든 정상 지연(35~74초)으로 원인 규명, 특정 원인 파일 없음, 코드/테스트 무수정

────────────────────────────────────────────────────────────────────────
0. 결론 요약
────────────────────────────────────────────────────────────────────────
- 지시대로 파일군을 절반씩 나누며 이분탐색했으나 "원인 파일 1개"로 수렴하지 않았다 —
  140→70+70 은 각 25초 타임아웃에서 둘 다 timeout 이었는데, 70을 35+35로 쪼개자 둘 다
  20.9~21.4초에 정상 종료(ok)했다. 특정 파일의 결함이 아니라 "건수 임계치형 지연"
  패턴이라는 뜻이다.
- 타임아웃을 넉넉히(120~300초) 주고 재실행하자 140개 전부(1,946케이스) 매번 정상
  종료(rc=0)했다 — 39.5초/766케이스(70개), 73.3초·72.1초/1,946케이스(140개, 2회
  반복 재현). 즉 **무한대기(deadlock)가 아니라, 예전 60초 patience 기준보다 살짝 긴
  정상 소요시간**이었다.
- 근본 원인은 DB 접속이 아니다. 140개 파일 전체를 AST로 스캔해 모듈 최상위 스코프의
  `.connect(` 호출을 찾았으나 0건. cProfile 로 --collect-only 를 프로파일링한 결과
  상위 소모는 전부 pytest 내부 collection 순회
  (`_pytest.main.collect`/`pytest_ignore_collect`/`_in_venv`)와 그 하부의
  `pathlib.is_file()` → `nt._path_isfile`(459,256회 호출, 18.0초)였다. DB
  드라이버·소켓·sqlglot 파싱 관련 함수는 상위 30위 안에 전혀 없었다.
- 결정적 대조 실험: 같은 tests/ 디렉토리(1,248개 파일, __pycache__ 1,043개 포함)를
  "디렉토리 하나"로 넘기면 12,378개 테스트를 35.2초에 수집(테스트당 2.8ms). 반면 그
  부분집합인 140개 파일을 "개별 CLI 인자 140개"로 넘기면 1,946개 테스트 수집에
  72~74초(테스트당 37ms, 약 13배 느림). 즉 **원인은 특정 파일이 아니라 "개별 파일
  인자를 많이 나열하는 호출 방식 + tests/ 디렉토리 비대화(1,248개 파일)" 조합**이다
  — pytest 가 인자마다 rootdir 기준 ignore-collect 판정을 반복 수행해 인자수×디렉토리
  크기로 파일시스템 stat 호출이 폭증한다.
- 판정: 테스트 코드 문제 아님(모듈 레벨 접속 코드 없음, 특정 파일로 수렴 안 함).
  좁은 의미의 "환경 문제"(DB 미응답·방화벽 등)도 아님(접속 시도 자체가 없어 배제).
  굳이 분류하면 "테스트 실행 도구 호출 방식 × 프로젝트 tests/ 디렉토리 비대화"가 만든
  pytest 자체의 성능 특성 — 예전 60초 patience 기준이 이 환경의 정상 소요시간(71~74초)
  보다 짧아 "무응답"으로 오판된 것이다.

1. 이분탐색 결과 (지시 1)
────────────────────────────────────────────────────────────────────────
방법: 140개 파일을 순서대로 절반씩 나눠 각 --collect-only(-q)를 서로 다른 타임아웃으로
반복 실행.

  단계                          결과(25~30초 타임아웃 기준)
  ──────────────────────────────────────────────────────────
  전체(140개)                   timeout (30초)
  왼쪽 70개                     timeout (25초)
    → 왼쪽 35개                 ok, 20.9초
    → 오른쪽 35개                ok, 20.9초
  오른쪽 70개                   timeout (25초)
    → 왼쪽 35개                 ok, 21.4초
    → 오른쪽 35개                ok, 20.2초
  ──────────────────────────────────────────────────────────

35개짜리 4묶음이 전부 정상 종료해 "원인 파일"로 더 좁혀지지 않았다 — 이 패턴 자체가

시사했다. 이후 같은 70개/140개 세트를 타임아웃만 120~300초로 늘려 재실행하자 매번
정상 종료를 확인했다(2절).

2. 근본 원인 상세 (지시 2, 3)
────────────────────────────────────────────────────────────────────────
(1) 재현 재확인 — "hang" 아님
  - 70개(왼쪽): 39.47초, rc=0, 766 tests collected (pytest 자체 보고 37.90초)
  - 140개 전체: 73.27초, rc=0, 1,946 tests collected (pytest 자체 보고 71.40초)
  - 140개 전체 재반복(warm .pyc 캐시): 73.98초, rc=0, 1,946 tests, pytest 보고 72.07초
    → 캐시 워밍과 무관하게 매번 71~74초로 일관 — 우연한 1회성 느려짐이 아니라 이
      환경에서의 정상적/반복 가능한 소요시간이다.

(2) DB 접속 여부
  - 140개 파일 전체를 Python ast 모듈로 파싱해, 모듈 최상위 스코프(함수/클래스 내부
    제외)에서 실행되는 `*.connect(` 호출을 탐지 — 0건.
  - 즉 "모듈 레벨에서 실 DB에 접속하면 안 되는데 그렇게 짜여 있다"는 가설은 기각.

(3) 무엇이 시간을 먹는가 — cProfile 결과 (scratchpad_m66_profile.out, 세션 임시 파일)
  140개 전체를 `python -m cProfile -m pytest --collect-only -q <140개>` 로 실행,
  cumulative time 상위 함수:
    - `_pytest.main.collect`(141회 호출) — 122.28초 누적
    - `_pytest.main.pytest_ignore_collect`(155,458회 호출) — 50.16초 누적
    - `pathlib.Path.is_file()`(459,247회) → `nt._path_isfile`(459,256회, tottime
      18.04초, 순수 실행시간만) — 23.66초 누적
    - `_pytest.main._in_venv`(155,177회) — 20.46초 누적
  DB 드라이버(oracledb/pymysql/psycopg2/pyodbc/sqlite3.connect), 소켓, sqlglot
  파서 관련 함수는 상위 30위 안에 전혀 등장하지 않았다.

(4) 결정적 대조 실험 — "개별 인자 수"가 변수임을 확인
  같은 tests/ 디렉토리는 실제로 1,248개의 최상위 파일 + __pycache__ 하위 1,043개
  파일(합계 2,290개)로 이미 비대해져 있다(git status 의 방대한 scratchpad 잔재와는
  별개로, tests/ 디렉토리 자체가 큼).
    - tests/ 를 "디렉토리 1개"로 넘김 → 1,248개 파일, 12,378개 테스트 수집,
      35.2초 (pytest 자체 보고 35.23초) → 테스트당 2.8ms
    - 그 부분집합인 140개 파일을 "개별 인자 140개"로 나열 → 1,946개 테스트 수집,
      72~74초 → 테스트당 37ms (약 13배 느림)
  이는 프로파일 결과와 정합한다 — pytest 는 CLI 인자를 하나씩 rootdir 부터 다시
  resolve 하며 ignore-collect 판정(`_in_venv` 등)을 인자마다 반복하므로, "적은
  테스트를 많은 개별 파일 인자로" 요청할수록 "많은 테스트를 디렉토리 하나로" 요청할
  때보다 구조적으로 더 느려진다. 인자 개수(140) × 디렉토리 항목 수(1,248) 규모의
  파일시스템 stat 호출이 그 결과다.

3. 테스트 코드 문제 vs 환경 문제 판단 (지시 요구사항)
────────────────────────────────────────────────────────────────────────
- 테스트 코드 자체의 문제 아님: 모듈 레벨 DB 접속 코드가 없고(AST 스캔 0건), 원인이
  특정 파일 하나로 수렴하지도 않았다(1절 — 35개씩 4묶음 전부 정상).
- (좁은 의미의) 환경 문제(잘못된 접속정보·방화벽·응답 없는 DB)도 아니다 — 애초에
  접속 시도 자체가 없었으므로 배제된다.
- 가장 가까운 분류: "테스트 실행 도구 호출 방식(140개 파일을 개별 CLI 인자로 나열) ×
  프로젝트 tests/ 디렉토리 비대화(1,248개 파일)" 조합이 만든 pytest 자체의 성능
  특성이다. 진짜 무한대기가 아니라 60초 patience 기준을 살짝 넘는(71~74초) 정상
  종료였다 — 3회 반복 모두 rc=0.
- F5-TIER2-BATCH3-IMPLEMENT.txt §5의 "test_batch_row_snapshot_realdb_smoke.py 를
  --ignore 해도 동일했다"는 관찰과도 정합한다: 파일 1개를 빼도 인자 개수가 140→139로
  거의 그대로이므로 인자수×디렉토리크기 구조의 지연은 거의 줄지 않는다 — "특정
  파일 탓이 아니다"라는 이번 결론과 일치.
- 배치1·2 시점엔 60초 안에 끝났을 가능성이 있다(예: 그때는 tests/ 디렉토리 파일 수가
  더 적었거나 시스템 부하가 달랐을 수 있음) — 이번 조사 범위 밖이라 확인하지 않았다.

4. 코드 수정 여부
────────────────────────────────────────────────────────────────────────
지시서 원칙("애매하면 진단만 하고 멈춰라")에 따라 **코드/테스트 무수정**으로 종료한다.
이유: "모듈 레벨 접속을 fixture로 옮기는" 것 같은 국소적이고 명백한 수정으로 해결되는
성격이 아니다 — 근본 원인이 (a) pytest 호출 방식(140개 개별 파일 인자)과 (b) tests/
디렉토리 크기(1,248개 파일) 조합이라, 안전한 해결은 운영/관행 변경(5절)이나 디렉토리
정리를 요구해 "사소한 수정" 범주를 벗어난다.

5. 향후 인접 회귀 대조 시 권장 방법 (문서화만, 미적용)
────────────────────────────────────────────────────────────────────────
- 개별 파일 140개 나열 대신, tests/ 디렉토리를 **단일 인자**로 넘기고 `-k` 표현식으로
  이름 필터링할 것을 권고:
    python -m pytest tests/ -k "test_batch_ or test_wrapper_results or test_candidate_ or test_column_candidate_" --collect-only
  실측상 8~13배 빠르다(테스트당 2.8ms vs 37ms).
- 단, `-k` 는 파일명이 아니라 pytest nodeid(파일명+클래스명+함수명 전체) 부분일치라
  오탐 가능성이 있다 — 실제 적용 전 수집된 케이스 수(이번 글롭 기준 1,946)가 일치하는지
  반드시 재확인해야 한다.
- 대안으로 `--co --collect-only` 후 `python -m pytest tests/` 전체(2절의 12,378개
  테스트, 35초)를 한 번에 돌리고 결과에서 원하는 파일군만 필터링하는 방법도 있으나,
  무관한 파일(~1,100개)까지 매번 import 하므로 5절의 `-k` 방식이 더 낫다.

────────────────────────────────────────────────────────────────────────

  특정.
- 긍정적 효과: "hang(무한대기)"이 아니라 "정상이지만 patience 기준보다 긴 지연"이라는
  오판을 바로잡았다 — 다음 F 계열 작업이 "hang 때문에 인접 회귀 대조 불가"로 잘못
  보고하는 것을 방지한다.

- 운영상 위험: 낮음(조사만 수행, 코드/테스트 무수정). 다만 앞으로도 파일을 개별
  나열하는 호출 관행을 반복하면 매번 71~74초가 걸려 "hang으로 오인 → 인접 대조 포기"가
  재발할 위험이 있다.
- heuristic/scoring/explainability 영향: 없음(조사 전용, 프로덕션·테스트 코드
  무수정).
- 권장 대응책: (1) 향후 인접 회귀 대조 시 5절의 "단일 디렉토리 인자 + `-k` 필터"

  지침으로 문서화 우선 검토할 것.
