0. 한 줄 요약
────────────────────────────────────────────────────────────────────────────
개별검증 3·4단계 상단 표시를 "이 단계가 실제로 실행한 결과만 보여준다"는 원칙에 맞게
정리했다 — 계산 전에 미리 채워져 있던 값 2개(3단계 '상태' · 4단계 '통계전략')를 실행
시점으로 늦추고, 정보가 중복이던 안내박스 2개와 표시 줄 1개를 코드째 제거했으며,
'참고/제외 후보 보기' 소제목의 오해 소지(링크색+삼각형)를 없애고, 4단계에만 없던
'상태' 타일을 신설해 2·3·4·5단계의 마지막 칸 규격을 통일했다.

착수 전 확인: 선행 작업 STAGE4-COMPLETION-BANNER-REMOVE-FIX 는 85ca345 로 커밋 완료된
상태였고, ui/ 아래에 남의 미커밋 변경이 없음을 git status 로 확인한 뒤 시작했다.
(작업 도중 다른 세션이 86865a1 을 커밋했다 — 내 커밋 4개는 그 위에 쌓였고, baseline
대조도 86865a1 기준으로 다시 맞췄다.)

[파트 A] 3단계 '상태' 타일 — 후보 계산 실행 후에만 표시
  파일: ui/grid_helpers.py (_mvCandidateTileRow)

  무엇이 문제였나.
    3단계 타일 9칸 중 '통계검증규모'와 '상태'는 실행계획 카드(/strategy/plan)가 만들어
    window._mvStage3PlanInfo 에 보관해 둔 값을 읽는다. 이 보관값은 한 번 만들어지면
    지워지지 않는데, 후보표(체크박스)는 2단계 COUNT 재실행 등으로 무효화되면 사라진다.
    그 결과 '아직 아무것도 계산하지 않은 화면'인데 '상태 ● 정상'만 떠 있었다.

  왜 '규모'는 그대로 두고 '상태'만 늦추는가.
    규모는 원본 건수·컬럼 구성만으로 산정되는, 계산 없이도 아는 값이다(요청에서도 즉시
    표시가 정상이라고 명시했다). 반면 '상태'는 그 계획을 실제 후보 구성에 적용해 본 뒤에야 의미가 생기는
    계산 결과다. 그래서 목적그룹/원본그룹/목적집계/원본집계/처리시간과 같은 시점에
    채워져야 한다.

  어떻게 고쳤나.
    새 상태 플래그를 만들지 않고, 이 함수가 이미 쓰고 있는 신호를 그대로 재사용했다 —
    gbCols === null(후보표 체크박스가 화면에 없음) = runRevalidateFromCandidate 미실행.
    그룹/집계 타일이 '—' 로 남는 판정과 완전히 같은 축이라, 한 화면 안에서 서로 어긋날 수
    없다.

  실측 재현 경로(before 에서 결함이 실제로 재현되는 경로).
    1~5단계 정상 수행 → 2단계로 돌아가 COUNT 재실행 → 3단계 재진입.
    이 시점 상태: window._mvStage3PlanInfo 존재, 후보표 체크박스 0개, #colSelectOut 비어 있음.
      before : 통계검증규모 '소형 (cost 12.68)' / 상태 '● 정상' / 그룹·집계 전부 '—'
      after  : 통계검증규모 '소형 (cost 12.68)' / 상태 '—'      / 그룹·집계 전부 '—'
    후보 계산을 실행하면 after 에서도 상태가 '● 정상'으로 채워진다(무회귀 확인).

[파트 B] 3단계 'COUNT 불일치 상태입니다…' 안내박스 삭제
  파일: ui/tabler_renderer.py

  삭제 대상: 렌더 함수 _singleRenderCandidatePaneNotice · DOM #singleCandidateCountNotice ·
            _applySinglePane 안의 호출부 — 전부 제거(화면 숨김이 아니라 코드/DOM 부재).

  삭제 근거.
    문구는 두 가지를 말한다. ⓐ COUNT 불일치 사실 — 상단 단계 탭 배지와 2단계 COUNT 타일이
    이미 수치와 함께 보여준다. ⓑ '후보 선정 후 통계검증으로 원인을 좁힌다' — 3단계에 와
    있다는 것 자체가 그 흐름이다. 새 정보가 없었다.

  안전성.
    표시 전용 함수였고 판정에 관여하지 않는다. _countState('MISMATCH'/'MISMATCH_ACCEPTED')
    와 그에 딸린 진행 허용 규칙은 전혀 건드리지 않았다(회귀 가드 테스트로 확인).

  실측(강제 표시 시도까지 해서 '부재'를 증명).
      before : 함수 존재(function) → 호출하니 박스가 display:block, 높이 39px 로 실제 표시됨
      after  : 함수 자체가 undefined → 호출 불가('no-function'), DOM 없음, 화면 문구 없음

[파트 C] 3단계 '참고/제외 후보 보기 · 기본계획 미포함 (N개)' 시각 정리
  파일: ui/tabler_renderer.py (CSS 1블록 + summary 마크업)

  진단.
    이 <details> 는 후보가 1개 이상이면 open 속성으로 렌더돼 화면상 '항상 펼쳐진' 상태다.
    그런데 문구가 파란 링크색이고 앞에 삼각형까지 붙어 "눌러야 열리는 숨은 영역"으로 읽혔다.
    인라인 스타일은 color:#555(회색)였는데 실제 렌더 색은 rgb(37,99,235) — 원인은
    '#tab-analyze details > summary { color:var(--primary)!important; … }' 규칙이었다.
    원래 고급옵션(DDL 직접입력) summary 용으로 만든 규칙인데 #tab-analyze 안의 모든
    details>summary 에 걸린다. !important 라 인라인 스타일로는 이길 수 없다.

  조치(동작은 손대지 않음).
    새 클래스 ict-ref-cands-flat 를 그 details 에만 붙이고, 같은 ID 특이도 + !important 로
      · color:var(--text) (= .card-title 과 같은 본문 소제목 색)
      · list-style:none + ::-webkit-details-marker/::marker 억제 (삼각형 제거)
    만 덮어썼다. open 속성·details/summary 구조·클릭 토글은 그대로다. 다른 details>summary
    (고급옵션, 일괄검증 기본 접힘 영역 등)의 표기는 종전 그대로다.

  실측.
      before : color rgb(37,99,235) · list-style-type 'disclosure-open' · open=true
      after  : color rgb(16,35,63)  · list-style-type 'none'            · open=true
      토글 무회귀: summary 클릭 1회 → open=false, 2회 → open=true (before/after 동일)

5. 남는 판단·위험
────────────────────────────────────────────────────────────────────────────
· 4단계 타일이 10칸이 되면서 한 줄 상한(9칸)을 넘었다. 공용 CSS 를 건드리지 않고 4단계
  호스트에만 최소폭 규칙을 준 것은 blast radius 를 0으로 만들기 위해서다. 대신 4단계
  타일 한 칸의 실제 폭이 130.6px → 116.5px 로 줄어든다. 값이 가장 긴 '통계전략' 칸은
  종전에도 코드 배지가 줄바꿈되던 칸이라 표기 규칙 자체는 달라지지 않았다(캡처 확인).
  앞으로 4단계에 타일을 더 붙이면 다시 줄이 갈라진다 — 11칸부터는 최소폭 조정이 아니라
  칸 정리(중복 제거)로 가야 한다.
· 파트 A 의 판정 신호는 '후보표 체크박스 존재'다. 이는 3단계 완료 신호로 이 저장소가
  이미 쓰고 있는 유일한 축이지만, 체크박스 없이 후보 계산 결과만 존재하는 화면이 미래에
  생기면 상태가 '—' 로 남는다. 그런 화면이 생기면 완료 플래그를 별도로 들고 오는 편이
  맞다(지금 만들면 축이 둘로 갈라져 어긋난다).
· 파트 D 는 배너만 없앴을 뿐 '참고용 계획인데 실제 실행은 전체스캔' 이라는 사실 자체는
  4단계 타일 배지·툴팁에만 남는다. 툴팁을 열지 않는 사용자에게는 노출 강도가 낮아진다 —
  의도된 축소이며, 정보 자체는 보존된다.
· 파트 B·D 로 삭제한 문구는 '왜 지웠는지' 를 남기려고 주석 안에 그대로 인용해 뒀다.
  그래서 회귀 가드 테스트는 원문이 아니라 '주석을 걷어낸 소스' 로 판정한다.
