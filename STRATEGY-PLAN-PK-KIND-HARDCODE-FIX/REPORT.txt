작업명 : STRATEGY-PLAN-PK-KIND-HARDCODE-FIX
✅ 작업 완료 - STRATEGY-PLAN-PK-KIND-HARDCODE-FIX - 3단계 실행계획 카드의 PK 구조 고정값(has_pk/pk_kind/pk_indexed)을 제거하고, 기존 방언 위임 어댑터를 재사용한 추가 전용 근거 필드(target_pk_evidence)로 판정하도록 바꿔 오라클 실 DB 3종(숫자/문자/복합 PK)이 각각 '숫자 단일 PK·실행 가능' / '문자 단일 PK·HOLD' / '복합 PK·HOLD' 로 정확히 표시됨을 화면 렌더로 확인했다(기존 응답 필드·판정 불변, 신규 회귀 0건)

실검증 상태: 완료 (오라클 라이브 실 DB — asis 192.168.0.151:1523 / tobe 192.168.0.151:1524, 스키마 NXDNP, PK 구조 3종 픽스처 각 300행, 개별검증 1~3단계 실제 브라우저 클릭스루)

────────────────────────────────────────────────────────────────────────
1. 요청 요약 / 수정 범위
────────────────────────────────────────────────────────────────────────
`ui/grid_helpers.py` 의 `_mvBuildStatsScaleProfile()` 이 실제 PK 구조를 조사하지 않고
`has_pk=true / pk_kind='SINGLE_NUMERIC' / pk_indexed=true` 를 고정 전송해, 3단계 실행계획
카드가 문자 PK·복합 PK 테이블까지 "숫자 단일 PK · 실행 가능" 으로 잘못 표시하던 결함을
근거 기반 판정으로 교체한다. 표시 전용 결함이며 실행 엔진은 이 값을 쓰지 않는다.

지시 범위는 `ui/grid_helpers.py` 1파일이었고, 지시문에 "실제 PK 근거를 가져오는 기존
API/서비스를 먼저 조사하고, 근거 제공 엔드포인트가 전혀 없으면 코드 변경 전에 보고하고
사용자 확인을 받을 것" 이라는 조건이 있었다. 조사 결과 근거 제공자(어댑터)는 이미 있으나
화면까지 배선돼 있지 않아 UI 만으로는 읽을 근거가 없었고, 이 사실을 실측과 함께 보고한 뒤
사용자가 **"신규 필드 추가(기존 필드·판정 불변)"** 방향을 선택해 백엔드 1파일을 추가 수정했다.

2. 근거 조사 결과 — 왜 UI 1파일로는 불가능했는가 (실측)
────────────────────────────────────────────────────────────────────────
PK 근거 '제공자' 는 이미 존재하고 오라클에서도 정확히 동작한다.
어댑터 `get_adapter(db_type).fetch_key_metadata()` 직접 호출 실측(오라클 tobe 1524):

    T_SPKFIX_NUM_TGT → {"ID":   {is_pk:true, key_column_count:1, is_composite_key_member:false}}
    T_SPKFIX_TXT_TGT → {"CODE": {is_pk:true, key_column_count:1, is_composite_key_member:false}}
    T_SPKFIX_CMP_TGT → {"CO_CD":{is_pk:true, key_column_count:2, is_composite_key_member:true},
                        "SEQ":  {is_pk:true, key_column_count:2, is_composite_key_member:true}}

그런데 그 결과가 화면(analyze 응답)까지 배선돼 있지 않았다. 실측으로 확인한 3가지 차단 지점:

 (a) `services/db_query_service.py:1248` — `_cmn_fetch_tgt_col_meta` 가 반환 row 마다
     `'is_pk': False` 를 **고정**으로 넣는다. 목적지 접속이 있으면 이 결과가 DDL 메타를
     통째로 교체하므로, `analyze_result.validated[].is_pk` 는 **전 방언에서 항상 false** 다.
     → 실측: 3종 모두 `validated PK cols = []`

 (b) `services/diagnosis/key_evidence.py:228` — `_table_key_meta` 의 컬럼 조회가
     `information_schema.columns`(PostgreSQL 전용) 하드코딩이라 오라클에서는 빈 결과가 되고,
     `chunk_key_evidence_snapshot` 이 `SCHEMA_META_MISSING` 으로 떨어진다.
     → 실측: 3종 모두 verdict=NOT_TRUSTED / reason=SCHEMA_META_MISSING
     (PG 에서는 동작하지만, 이 snapshot 은 '신뢰 가능한 단일 숫자 PK 인가' 만 판정하므로
      문자 단일 PK 와 복합 PK 를 구분하지 못한다 — 요구된 3종 구분에 원리적으로 부족)

 (c) DDL 입력 경로도 대안이 못 된다. 목적지 접속이 있으면 (a)의 실 DB 메타가 DDL 메타를
     교체하므로 is_pk 가 다시 false 가 된다. → 실측: ddl_text 동봉해도 `validated PK cols = []`

 (d) PK 구조를 돌려주는 read-only 엔드포인트는 없다.
     · `/metadata-inventory/collect` — 그룹·품질확정 snapshot 선행 필요 + 수집(쓰기) 작업
     · `/diagnosis/candidate-recommend` — 컬럼 메타를 **입력으로 받는** 순수 계산 API

즉 화면이 읽을 수 있는 PK 근거가 응답에 하나도 없었다. UI 만 고치면 라이브 DB 경로에서는
3종 모두 "PK 없음 · 상세비교 보류(HOLD)" 로 떨어져(안전측이지만) 숫자 PK 정탐까지 사라진다.
이 실측을 근거로 보고했고, 사용자가 '신규 필드 추가' 를 선택했다.

9. 비판적 검토 — 남은 위험 / 미해결
────────────────────────────────────────────────────────────────────────
(a) '확인 불가' 와 'PK 없음' 이 화면에서 같은 문구로 보인다.
    서버 라벨 맵(routes/strategy_route.py:75-76)에 PK_NONE 밖에 없어, 근거를 못 구한 경우도
    판정근거에 "PK 없음" 으로 찍힌다. 판정(HOLD)은 안전측으로 맞지만 사유는 정확하지 않다.
    화면에는 `pk_evidence` 근거코드(UNKNOWN / KEY_METADATA_UNAVAILABLE 등)를 함께 보내 두었으므로,
    라벨 분리는 strategy_route 를 수정 대상에 포함할 때 후속으로 처리할 수 있다. (이번 범위 밖)

(b) `remote: true` 는 여전히 하드코딩이다.
    이번 지시 범위(has_pk/pk_kind/pk_indexed) 밖이라 손대지 않았다. remote 는 DIRECT↔CHUNK
    전환 정책(strategy_transition)에 쓰이므로, 값을 바꾸면 표시 전략이 함께 바뀐다.
    현행 유지 = 기존 동작 보존(보수적)이며, 별도 작업으로 다루는 편이 안전하다.

(c) 근본 원인 2건은 그대로 남아 있다(이번 작업이 우회한 것이지 고친 게 아니다).
    · `services/db_query_service.py:1248` — `_cmn_fetch_tgt_col_meta` 의 `'is_pk': False` 고정.
      실 DB 접속이 있으면 전 방언에서 `validated[].is_pk` 가 항상 false 다. 이 값을 소비하는
      SUM 후보 제외·기본체크·후보 점수 로직이 '목적지 PK 를 모르는 상태' 로 동작하고 있다.
      고치면 후보추천 결과가 바뀌므로 별도 승인·별도 실측이 필요하다(그래서 이번엔 손대지 않았다).
    · `services/diagnosis/key_evidence.py:228` — `_table_key_meta` 의 컬럼 조회가
      `information_schema.columns` PG 전용. 오라클/MSSQL 에서 chunk_key_evidence_snapshot 이
      항상 SCHEMA_META_MISSING 이다(PK 위임은 이미 방언화됐는데 컬럼 조회 절반이 남았다).

(d) 표시 전용이라는 성격은 그대로다.
    실행 엔진은 이 profile 을 쓰지 않으므로, 이번 수정으로 잘못된 실행이 막히는 것은 아니다.
    반대로 카드가 이제 HOLD 를 정확히 표시하므로, '카드는 HOLD 인데 실제로는 실행된다' 는
    괴리가 눈에 띌 수 있다. 이는 표시/엔진 분리라는 기존 구조에서 오는 것이고 판정은 불변이다.

(e) 픽스처는 검증 종료 후에도 남겨 두었다(T_SPKFIX_* 6개, 각 300행).
    재현·재검증에 필요하고 운영 데이터와 이름이 겹치지 않는다. 삭제가 필요하면 알려 달라.
