1. 요청 요약
════════════════════════════════════════════════════════════════════════
"헤더는 즉시 표시, 값은 실제로 알게 된 시점에만 채운다"는 원칙이 2·3단계에서 서로 반대
방향으로 어긋나 있었다.

  · 2단계(COUNT 사전검증) : 탭 진입 직후 목적/원본 테이블명까지 전부 '—' — 1단계에서 이미
    확정된 정보인데 숨기고 있었다(부족).
  · 3단계(후보 컬럼 선정) : 탭 진입 직후 목적그룹/원본그룹/목적집계/원본집계까지 이미
    채워져 보였다 — 후보 계산이 아직 실행되지 않았는데 값이 있었다(과잉).

두 단계를 같은 원칙으로 통일했다: 이미 확정된 정보(목적/원본 테이블명, 2단계 고정 상수
'검증항목')는 탭 진입 즉시 표시, 그 외 모든 값은 그 단계의 실제 계산/실행이 끝난 뒤에만 표시.

2. 파트 B 원인 판정 — (a)/(b) 중 무엇이었나
════════════════════════════════════════════════════════════════════════
판정 : (b) — 탭 렌더 시점에 실제 계산 없이 이전 상태(1단계 응답 잔여 pool)를 재사용했다.
       (a) '계산이 매우 빨라 즉시 끝난 정상값' 이 아니다.

근거(실 브라우저 실측 · 내부망 PostgreSQL asis→tobe · 케이스 etl02):

 근거①  3단계 진입 직후 상태 플래그가 모두 '미계산'
         _analyzeData._candidateComputed = false
         _analyzeData._candidateEverComputed = false
         후보표 체크박스 gb 0개 / sum 0개 · 후보표 DOM 없음
         후보 계산 안내 게이트(candCalcGate) 노출 중
 근거②  진입 시점 서버 요청 0건 (fetch 후킹 계측 — 계산이 돌았다면 요청이 있어야 한다)
 근거③  값의 출처가 1단계 /analyze 응답의 후보 pool 그대로였다
         _analyzeData.all_groupby_candidates
           = [SCHOOL_CODE, SUBJECT, UPDATED_AT, HIRE_DATE, RETIRE_DATE]
         → 진입 직후 목적그룹 타일 표시값과 정확히 일치(5개 전량)
 근거④  결정적 — 계산 전 값과 실제 계산 결과가 다르다
         '후보 계산' 클릭 → 실제 계산 소요 391ms, 서버 왕복 5회
           (/validation-sets/preview · /strategy/plan ×2 · /csr-preview ×2)
         계산 후 목적그룹 = [SCHOOL_CODE, SUBJECT] (2개)
         즉 진입 직후 화면은 '아직 계산되지 않은, 그리고 결과와도 다른 값'을 계산 결과처럼
         보여주고 있었다. (a) 라면 두 값이 같아야 한다.

코드상 위치 : ui/grid_helpers.py _mvCandidateTileRow() 의 폴백 2단
  체크박스가 없으면 → ① candidate_recommendation.recommended → ② all_*_candidates 전량
  두 폴백 모두 1단계 응답에 실려 온 '예비 목록'이지 3단계 계산 결과가 아니다.

3. 수정 내용
════════════════════════════════════════════════════════════════════════
[파트 A] ui/tabler_renderer.py — 2단계 확정 정보 즉시 표시
  · _mvCountPreknownRow(srcT, tgtT) 신설
      - 목적/원본 테이블명 : 기존 _mvTablesOf(_analyzeData) 재사용(1단계 확정값).
      - 검증항목 : 2단계 고정 상수 'COUNT'(_mvCountRows 의 base.check 와 같은 값).
      - 새 계산·서버 왕복 없음. 1단계 분석 전(테이블 미확정)이면 검증항목도 비운다.
  · _mvCountTilesHtml(c=null) 이 위 값을 채우고, 나머지 5칸(목적건수/원본 건수/차이/
    처리시간/상태)은 COUNT 실행 전까지 '—' 유지 — 판정 로직 무수정.
  · 다중 원본(JOIN/UNION) 합쳐 표시(srcAll)도 c 유무와 무관하게 적용 — 실행 전/후 표기 일치.
  · 실행 후라도 테이블명/검증항목이 비었거나 '-' 면 확정 정보로 보완(표시 일관성만 보정).

[파트 B] ui/grid_helpers.py — 3단계 미계산 값 노출 제거
  · _mvCandidateTileRow : 폴백 2단(rec / pool) 제거. 체크박스 미존재 = 후보 계산 전이므로
    gbCols/sumCols 를 null 로 유지하고, _split() 이 null 을 그대로 돌려준다.
  · _mvCandidateTilesHtml : kind='multi' 값이
      null      → '—'  (미계산)
      빈 배열   → '없음'(계산 결과가 0개)
    로 구분 표시 — 두 상태가 섞이지 않게 했다.
  · 목적/원본 테이블명은 2단계와 동일 원칙으로 계속 즉시 표시.
  · 계산 완료 후 표시(라이브 체크박스 단일 출처)와 판정 로직은 전혀 건드리지 않았다.

7. 비판적 검토
════════════════════════════════════════════════════════════════════════
 · 긍정적 효과 : 화면이 '아직 모르는 값'과 '계산된 값'을 구분해 말하게 됐다. 특히 3단계는
   계산 결과와 다른 값을 결과처럼 보여주던 상태여서, 사용자가 계산 전 목록을 최종 선정으로
   오인할 여지가 있었다(실측상 5개 vs 2개).
 · 구조 영향 : 두 파일 모두 표시 계층 내부에서만 변경했고 web_server.py 는 건드리지 않았다.
   신규 헬퍼 1개(_mvCountPreknownRow)만 늘었고, 3단계는 오히려 폴백 분기 2단이 제거돼
   코드가 줄었다(-18줄).
 · heuristic/scoring/explainability : 새 규칙·가중치·판정 없음. 값 계산·판정 로직 무수정.
 · 남은 위험 : 3단계 '미계산' 판정 근거가 '후보표 체크박스가 DOM 에 있는가' 라는 간접 신호다.
   체크박스를 렌더하지 않는 새 표시 경로가 생기면 값이 '—' 로 남을 수 있다. 다만 현재
   후보 계산 완료의 유일한 가시적 산출물이 그 표이고, _candidateComputed 는 체크 변경 시
   무효화(false)되므로 그것을 기준으로 쓰면 사용자가 체크를 바꾸는 순간 값이 사라지는 더 큰
   회귀가 생긴다 — 체크박스 존재 기준이 현 구조에서 가장 안정적이다(실측으로 확인).
 · 미해결(범위 밖) : 2단계 '검증항목'은 항상 'COUNT' 인 고정 상수이며, 값이 하나뿐인 타일을
   계속 유지할지는 표시 정책 판단 사항으로 남겼다(이번엔 요구대로 즉시 표시만 적용).
