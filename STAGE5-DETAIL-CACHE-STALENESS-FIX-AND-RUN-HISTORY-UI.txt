1. 감지 원리 (추가 DB 스캔 0회)
────────────────────────────────────────────────────────────────────────────
  4단계(통계검증)는 결과 캐시가 전혀 없어 매번 실제 쿼리를 새로 실행한다 = 그룹별 원본/목적
  COUNT·SUM 이 항상 최신이다. 이 최신 요약값을 그룹 클릭 시 /agg-diff/prepare 요청에 함께 실어
  보내고(화면이 이미 갖고 있는 값이라 추가 조회 0), 서버는 캐시된 run 이 '캐시 생성 당시' 저장해 둔
  같은 그룹의 요약값과 대조한다. 하나라도 다르면 데이터가 실제로 바뀐 것으로 보고 캐시를 버리고
  새로 스캔한다. fingerprint 자체는 건드리지 않았다(차수 이력이 fingerprint 로 묶이므로 지문을
  바꾸면 과거 차수가 통째로 끊긴다).

  비교 항목 : source_count / target_count(그룹 행수) + 4단계 집계값 dict 의 교집합 컬럼
              (CNT + 선택 SUM). 양쪽에 모두 값이 있는 항목만 대조한다.
  값 정규화 : '100'과 100, '99299.00'과 '99299' 를 같은 값으로 취급(표기 차이 오탐 방지).

3. [1번] 데이터 변경 감지 실측 (실브라우저 클릭 · 실 오라클)
────────────────────────────────────────────────────────────────────────────
 환경 : 포트 8000, Oracle asis→tobe, NXDNP.MV_COMBO_SRC/TGT(각 1,200행),
        GROUP BY = STATUS_CD + DEPT_CD(조합), SUM = AMT.
 대상 그룹 : STATUS_CD='A' · DEPT_CD='D01'
        원본 CNT=100 / SUM=100,299   목적 CNT=100 / SUM=99,299
        → COUNT 는 완전히 같고 SUM 만 다르다. COUNT 만 비교했다면 절대 감지 못 했을 형태다.

 시나리오 : 이관팀이 목적 데이터를 실제로 수정(재이관) → 검증팀이 동일 조건으로 재검증.

   +----+--------------------------------------+------------------+----------+---------+--------+
   | 단 | 동작                                 | 목적 SUM(실 DB)  | run_id   | reused  | 재이관 |
   +----+--------------------------------------+------------------+----------+---------+--------+
   |1-a | 그룹 최초 클릭(새 스캔)              | 99,299           | R1       | false   | 100건  |
   |1-b | 접었다 다시 펴기                     | 99,299           | R1(동일) | 캐시적중| 100건  |
   |1-c | 목적 데이터 수정(ID 401~450 AMT+10)  | 99,299 → 99,799  | -        | -       | -      |
   |1-d | 4단계 통계검증 재실행(항상 새 실행)  | 화면 요약 99,799 | -        | -       | -      |
   |1-e | [대조군] group_summary 없이 prepare  | 99,799           | R1(예전) | true    | 100건  |
   |1-f | [실제 클릭] 같은 그룹 클릭           | 99,799           | R2(신규) | false   | 50건   |
   +----+--------------------------------------+------------------+----------+---------+--------+

   · 1-b : 클라이언트 준비 캐시 적중으로 요청 자체가 나가지 않음(run_id 동일) — 기존 재사용 보존.
   · 1-e = 수정 전 코드의 동작을 같은 서버에서 그대로 재현한 대조군이다(수정 전 서버는 이 필드를
     아예 몰랐으므로 동일). 데이터가 바뀐 뒤에도 reused=true·source=memory_cache 로 이관 전 결과
     100건을 그대로 돌려준다 = 이번에 고친 결함 그 자체.
   · 1-f = 수정 후 실제 클릭. 서버 응답에 아래가 실렸다.
        cache_invalidated_by_data_change : true
        data_change_detail.changed       : [{"field":"tgt.AMT","cached":"99299","current":"99799"}]
        data_change_message              : "4단계가 방금 계산한 이 그룹의 요약값이 이전 상세추출
                                            당시와 달라 데이터가 변경된 것으로 판단했습니다. 예전
                                            상세 레코드를 그대로 보여주지 않고 새로 스캔합니다."
     화면 : 그리드 위에 '데이터 변경 감지 · 캐시 자동 무효화' 배너가 실제로 표시됐고
            (runHistHtmlHasNotice=true), 하단 문구가 '전체 재이관 대상 : 50건 (0.18초 · 새로 스캔)'
            으로 바뀌었다. 즉 수정 50건이 해소된 최신 결과가 정확히 반영됐다.

 전/후 요약 :  BEFORE(수정 전 동작 재현) = 100건(이관 전 stale)  /  AFTER(수정 후) = 50건(최신)

 픽스처 원상복구 : 검증 후 목적 AMT 를 되돌려 SUM 99,299 로 복원 완료(스크립트 finally 블록).

5. 감지 방식의 한계 (은폐하지 않고 명시)
────────────────────────────────────────────────────────────────────────────
 L1  COUNT·선택 SUM 이 모두 그대로인 변경은 감지하지 못한다. 예: 같은 그룹 안에서 서로 상쇄되는
     값 교정(+10/-10), 통계검증에 선택되지 않은 비집계 컬럼만 수정. 완전 감지는 데이터 체크섬이
     필요하고 그건 매 클릭 전수 스캔이라 이번 범위(저비용)를 벗어난다.
     → 그래도 '아예 감지 안 함'보다 훨씬 낫다는 지시서 원칙대로 진행했다. 실제 픽스처가
       COUNT 동일·SUM 상이 형태였고 이 가드가 그것을 잡아냈다.
 L2  4단계 요약값을 전달하지 않는 경로에서는 판정 자체를 하지 않고 기존 동작(무조건 재사용)을
     유지한다 : '전체 그룹 한번에 추출'(스코프 없음), 통계검증 직후 prewarm, COUNT-only 드릴다운,
     복원(_mvRestore) 경로. 이 가드는 '가능할 때만 작동하는 이중 방어선'이며 기존 캐시 재사용
     로직을 대체하지 않는다.
 L3  스냅샷이 없는 구 캐시(이번 수정 이전에 만들어진 run)는 basis 의 source_count/target_count
     로 COUNT 만 대조하는 하위호환 폴백을 쓴다(SUM 대조 불가). 그 run 이 한 번 새로 스캔되면
     이후로는 완전한 기준값을 갖는다.
 L4  진행 중(PREPARING) job 은 판정 대상에서 제외한다. '지금 스캔 중'이라 낡을 수 없고, 끊으면
     중복 스캔이 되기 때문이다.
 L5  비-stream(소량) 경로의 run 은 test-only in-memory store 에 저장되는 기존 구조 그대로라,
     서버 재기동 시 그 차수 이력이 사라진다(파일 영속은 stream/chunk 경로 run 만). 이번 작업이
     만든 제약이 아니라 원래 저장 정책이며, run-history 엔드포인트는 파일·메모리 두 store 를
     모두 조회해 있는 것은 전부 보여준다.
 L6  MismatchGroup(stage5_group_store) 조회는 쓰지 않았다. 4단계가 방금 만든 같은 값을 화면이
     그대로 갖고 있어(그 저장소에 넣는 값과 동일 출처) 서버 조회·그룹 재매칭 없이 비교가 되고,
     매칭 실패(저장 안 된 그룹·키 불일치) 위험도 원천적으로 없어지기 때문이다.

6. 구조/운영 검토
────────────────────────────────────────────────────────────────────────────
 구조     : 판정 로직을 라우트에 흩뿌리지 않고 신규 모듈 1개(detail_cache_guard)로 분리했다.

            오탐은 차단했다. 가드 예외 발생 시 false-safe(기존 재사용 유지)라 장애 전파 없음.

 heuristic : 새 하드코딩 규칙 없음(임계값·가중치 없이 '같다/다르다' 동등비교만).
 보안      : 접속정보·비밀번호를 새로 다루지 않는다. 검증 드라이버도 프리셋 단일 출처만 사용.
