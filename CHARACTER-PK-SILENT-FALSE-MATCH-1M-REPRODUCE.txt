────────────────────────────────────────────────────────────────────────
0. 한 줄 결론
────────────────────────────────────────────────────────────────────────
  100만행 픽스처에서 문자 PK 결함이 재현됐다. 다만 원인이 2축임이 새로 확정됐다.
    축 A (기존에 알던 것) 경계 절단  — 이번 규모에선 커버 밖 1건(0.0001%)에 그침
    축 B (이번에 새로 확인) merge-join 정렬 전제 위반 — 참값 10,000건이
         재이관 64,997건 + 목적 단독 54,998건으로 뒤집힘. 오류·경고 0건, status=READY.

  판정 방향이 기존과 반대다. 25만행 사례는 거짓 "일치"(0건), 이번은 거짓 "불일치"(6.5배).
  성격은 같다 — 오류도 경고도 없이 틀린 판정.

1. 실측 환경
────────────────────────────────────────────────────────────────────────
  원본 asis  NXDNP.MV_CSPK_SRC  1,000,000행 (복합 PK: REGION_CD VARCHAR2(4) + SEQ_NO NUMBER)
  목적 tobe  NXDNP.MV_CSPK_TGT    990,000행 (단일 문자 PK: PK_STR VARCHAR2(20))
  참값 누락  10,000행 — 전역순번 g=(a-1)*1000+b 에서 MOD(g,100)=0, 전 범위 균등

                      run_pk_range_chunk_compare / _pk_resolve / strategy_plan
  UI 클릭 없음(지침 준수). 재이관 준비 버튼 미클릭. 데이터 변경 없음(읽기 전용).

  드라이버 : scripts/dev_e2e/character_pk_silent_false_match_1m_reproduce.py
  결과 원본: scripts/dev_e2e/_character_pk_silent_false_match_1m_{be,c,d,f}.json

2. 지시 1 — 문자 PK 명시 지정 경로 실측
────────────────────────────────────────────────────────────────────────
  [경계 산정 — ora_pk_min_max + route 의 int() 게이트 그대로]

  변종  키 표현                        MIN/MAX(원본)              int()게이트        커버 밖
  ----  -----------------------------  -------------------------  -----------------  --------
  V1    PK_STR (실제 자연 문자 PK)     'A001-000001'~'Z038-001000' HOLD_NON_NUMERIC   —
  V2    TO_CHAR(g) 유일값 문자화       '1' ~ '999999'              통과               1건
  V3    g 숫자 (대조군)                1 ~ 1000000                 통과               0건
  V4    TO_CHAR(SEQ_NO) 비유일(참고)   '1' ~ '999'                 통과               1,000건
  V5    LPAD(TO_CHAR(g),7,'0') zero-pad '0000001'~'1000000'        통과               0건

  → V1(실제 PK 를 그대로 지정)은 int() 게이트가 HOLD 로 안전하게 막는다.
    이 픽스처의 PK 는 'A001-000001' 형태라 int() 파싱 자체가 실패하기 때문.
    재현 조건은 여전히 "문자인데 int() 로 파싱되는 키"(V2)다.

  [축 A 심각도는 규모에 비례하지 않는다]
    25만행(기존) 최대 250,050 → 문자 MAX '99999'  → 커버 밖 60.0%
    100만행(이번) 최대 1,000,000 → 문자 MAX '999999' → 커버 밖 0.0001%
    절단 폭을 정하는 건 행 수가 아니라 "최대값과 아래쪽 10^k-1 사이의 거리"다.
    최대값이 10^k 를 갓 넘으면 최악, 정확히 10^k 면 최선. 예측 불가.

3. 지시 3 — 참값(1만행 누락) 대비 검출 결과 (end-to-end, chunk 50,000 · 20 chunk)
────────────────────────────────────────────────────────────────────────
  키                     상태   재이관   목적미존재  목적단독  소요     참값 10,000 대비
  ---------------------  -----  -------  ----------  --------  -------  -------------------
  V2 문자키              READY   64,997     64,997    54,998   96.9s    6.5배 과다 · 경고 0
  V3 숫자키(대조군)      READY   10,000     10,000         0   88.0s    정확히 일치
  V5 zero-pad 문자키     READY   10,000     10,000         0  107.1s    정확히 일치

  64,997 - 54,998 = 9,999 (참값 10,000 - 커버 밖 1건)
  → 순 차이는 보존되고, 미존재/목적단독 쌍 54,998건이 통째로 날조됐다. 합계만 우연히 맞는다.

  [원인 — merge-join 정렬 전제 위반 (직접 증적)]
    services/exact_diff/pk_range_chunk.py:34-35
      def merge_chunk(...):
          """정렬된(PK 오름차순) chunk 두 목록의 merge-join. ..."""
    그런데 chunk 조회는 ORDER BY Q0."<키>" 를 컬럼 그대로 건다(dialects/oracle.py:515).
    문자 컬럼이면 문자 정렬이다. 반면 WHERE 의 바인드는 숫자(oracle.py:517 [int(start),int(end)])라
    오라클 암묵 형변환으로 필터는 숫자 의미로 걸린다.
    → 범위는 맞는데 순서만 문자 정렬인 목록이 merge 에 들어간다.
      key 는 _as_int 로 정수화되므로(pk_range_chunk.py:123) 비교는 숫자, 순서만 어긋난다. 조용히 틀린다.

    chunk 1개(1~50,001) 실제 조회 — 순서 검사
      V2 문자        50,000행 · 역전 4,500회 · 앞 20개: 1,10,100,1000,10000,10001,...,1001,10010,...
      V3 숫자        50,000행 · 역전 0회     · 앞 20개: 1,2,3,...,20
      V5 zero-pad    50,000행 · 역전 0회     · 앞 20개: 1,2,3,...,20

    결정적 대조(V5): 같은 문자 타입인데 zero-pad 로 문자 정렬 순서를 숫자 정렬과 맞추자
    결과가 참값과 정확히 일치(10,000건). 즉 문자 '타입' 이 아니라
    "문자 정렬 순서 ≠ 숫자 정렬 순서" 가 원인임이 확정.

4. 지시 2 — HTTP 자동 경로는 이 문자 PK 를 어떻게 분류하는가
────────────────────────────────────────────────────────────────────────
  _pk_resolve(routes/agg_diff_route.py:801-849) 를 운영 그대로 직접 호출
  (1단계 analyze 는 routes/analyze_route.stats_analyze 그대로 호출, HTTP 계층만 생략).

    1) resolve_trusted_chunk_key   → 미확정(None). 타입 게이트가 NUMBER/DATE_TIME 만 허용
                                     (key_evidence.py:111,177,320,334)                     0.44s
    2) resolve_confirmed_chunk_key → 미확정(None)                                          0.30s
    3) _resolve_native_pk_key      → PK_STR 을 네이티브 키로 확정 · _unique_native_key=True 0.70s
    4) (참고) 그 키의 MIN/MAX      → 'A001-000001'~'Z038-001000' → int() HOLD_NON_NUMERIC_PK

  확정 답: 자동 경로는 이 문자 PK 를 chunk 키로 확정하지 않는다.
    agg_diff_route.py:903-905 가 _unique_native_key 를 보고 req.compare_strategy="" 로 덮어
    범위분할 대신 DIRECT merge(agg_contribution)로 강제한다.
    설령 chunk 경로로 흘러도 int() 게이트가 HOLD 로 막는다(이중 방어).
  → §2·§3 의 재현은 key_src/key_tgt 명시 지정 경로 한정. 100만행에서도 이 한계는 그대로다.

      - 같은 하드코딩을 _mvComputeStatsScale(목록 규모 셀)도 공유한다
