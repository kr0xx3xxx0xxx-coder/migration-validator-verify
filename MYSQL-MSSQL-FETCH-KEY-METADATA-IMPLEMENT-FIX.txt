================================================================================
1. 배경 / 문제
================================================================================
백로그 F23. 어댑터 계층에서 목적지 PK/UNIQUE 메타를 조회하는 fetch_key_metadata 가
oracle / postgresql 에만 구현돼 있고 mysql / mssql 은 BaseDbmsAdapter 의 no-op({}) 이었다.

  services/db_adapters/base.py:161
      def fetch_key_metadata(self, conn_info, table) -> dict:
          """PK/유니크 등 키 메타 조회. 기본 no-op({}) — 미지원 DBMS."""
          return {}

그 결과 소비처(services/db_query_service._cmn_fetch_tgt_col_meta)에서 목적지 컬럼 메타의
is_pk 가 MySQL/MSSQL 목적지에서는 **항상 False** 였다(방언 비대칭). 같은 파일의 주석도
"mysql/mssql 은 base no-op({}) 이라 값이 안 채워져 기존 동작(전부 False)이 유지된다"고
그 상태를 명시하고 있었다(db_query_service.py:1347~1348, 수정 전).

선행 결정: 오늘(2026-08-05) IS-PK-FIXED-VALUE-CANDIDATE-RECOMMENDATION-FIX 작업 시
사용자 결정으로 "오라클만 먼저, MySQL/MSSQL 은 별도(Q3)" 로 분리했고, 이번이 그 별도 작업이다.

(3) 공통 규칙 — 오라클/PG impl 과 완전히 동일하게 맞춘 부분
    - 반환 shape: {COLUMN_NAME(대문자): {is_pk, is_unique, is_composite_key_member,
                   key_column_count, constraint_name, constraint_type}}
    - constraint_type 문자열: 'PRIMARY KEY' / 'UNIQUE'
      (오라클만 'P'/'U' → 정규화가 필요했고, MySQL/MSSQL 카탈로그는 이미 이 문자열을 준다)
    - 컬럼별 최우선 제약: PRIMARY KEY > UNIQUE (행 순서와 무관하게 PK 로 덮어씀)
    - 단일/복합 구분: key_column_count > 1 → is_composite_key_member=True
      · 소비처(db_query_service._cmn_fetch_tgt_col_meta)가 `is_pk and not is_composite` 로
        **단일 컬럼 PK 만 is_pk=True** 를 싣고, 복합 PK 구성원은 is_composite_key_member(+
        key_column_count)로만 사실을 보존한다 → 오늘 S10(오라클)에서 확정한 원칙 그대로 적용.
        어댑터는 사실만 담고 정책은 소비처가 적용하는 기존 구조를 유지했다(정책 중복 구현 없음).
    - 안전 폴백: 비대상 db_type / 파생 SQL('(' 시작) / 빈 테이블명은 **연결조차 하지 않고** {},

      소비처에서 수정 전(전부 False)과 동일하게 흐른다.

[방법] db_type='mysql' 로 analyze(run_single_validation_analyze)를 라이브 실행.
       '전(前)' 은 S10 하니스와 동일한 legacy shim(=목적지 컬럼 메타에서 is_pk/

[잔존 제약 1 — 운영 경로에서 실제로 값이 흐르려면 connect() 가 필요하다]
   MySQLAdapter / MSSQLAdapter 는 connect() 가 여전히 미구현이다(BaseDbmsAdapter.connect →
   RuntimeError "connect 미지원"). 실측:
       get_adapter('mysql').connect({...}) → RuntimeError: mysql: connect 미지원(어댑터 미구현)
   fetch_key_metadata 는 _cmn_db_connect → 어댑터 connect 를 타므로, 운영 경로에서는 지금도
   연결 단계에서 실패해 {} 로 폴백한다(= 사용자 관점 동작은 수정 전과 동일).
   즉 이번 작업은 "카탈로그 조회·판정 계층"을 오라클과 대칭으로 맞춘 것이고, 두 방언의 값이
   실제 화면까지 흐르려면 별도 작업(어댑터 connect 이식)이 선행돼야 한다. 이번 지침의 수정
   대상 파일 범위(어댑터의 fetch_key_metadata)를 넘어서므로 여기서는 구현하지 않았다.
   ※ 그래서 §3 하니스는 connect 만 주입해 라이브 검증을 성립시켰다 — 조회 SQL/집계/폴백은
     운영 코드 그대로이므로, connect 가 이식되는 즉시 §3 값이 그대로 운영에서 재현된다.

[잔존 제약 2 — MSSQL 라이브 미검증]
   인스턴스/pyodbc 부재로 실 서버 실행은 못 했다(§4). 어댑터 docstring 에 같은 문구로 명시.

[잔존 제약 3 — MariaDB 는 범위 밖]
   MariaDBAdapter 는 여전히 base no-op({})이다. 지침이 MySQL/MSSQL 2방언으로 한정했고,
   지원 DB 4종(oracle/mysql/postgresql/mssql) 목록에도 MariaDB 는 없다.
   (테스트 test_untouched_dialects_still_noop 로 이 상태를 고정했다)
