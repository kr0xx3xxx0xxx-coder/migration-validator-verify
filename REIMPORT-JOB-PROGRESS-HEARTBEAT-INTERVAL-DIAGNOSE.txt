[추정 C] 실사용 규모 — 비정상 케이스 (여기가 진짜 위험)
  chunk 조회 SQL 실제 모양(dialects/oracle.py:515-517):
    SELECT ... FROM ( <사용자 이관 SELECT 원문> ) Q0 WHERE Q0."PK" >= :1 AND Q0."PK" < :2 ORDER BY Q0."PK"
  사용자 SQL 이 인라인 뷰로 감싸진다. range 조건 push-down 여부는 옵티마이저 소관이다.
    - 단순 테이블 SELECT → push-down 성공 → 청크 = O(청크 행수)  [정상]
    - CTE+윈도우(ROW_NUMBER rn) / GROUP BY / DISTINCT / UNION → push-down 실패
      → 청크마다 전체 쿼리를 통째로 재실행 → 청크 1개 = O(전체 테이블)
  이 페널티는 이미 실측된 적 있다:
    오라클 25만행 단순 테이블   약 11~14 초
    오라클 25만행 CTE/JOIN 파생 약 6.2 분(372초)   ← 같은 행수, 약 30배
  환산: 500만행 push-down 실패 파생 = 372s × 20 ≈ 청크 1개당 약 2.1 시간
        1:N JOIN fan-out(N=5) 겹치면 추가 5배

[추정 D] STREAM 엔진(복합 PK 경로)의 최대 공백
  정상 merge 구간   20,000행 / (45µs×2) ≈ 0.9초 — 매우 촘촘, 문제 없음
  양측 ORDER BY 정렬 대기  인덱스 타면 초 단위, 실제 정렬 발생 시 수 분~수십 분(500만행 디스크 정렬)
  → STREAM 은 "돌기 시작하면 안전, 시작하기까지가 위험"한 형태

4. STALL_TTL 권장값 + 근거 (지시 3)
────────────────────────────────────────────────────────────────────────
[먼저] 단일 고정 kill 임계는 채택하면 안 된다.
  청크 1개 최악의 범위가 10초 ~ 2시간+ (4자리수 배율)이다. 하나의 숫자로 덮으려면 2시간대를 잡아야
  하는데 그러면 좀비 회수 목적이 무의미해진다. 반대로 좀비 회수에 쓸모 있는 값(30분)을 잡으면
  push-down 실패 케이스를 오살한다. 단일값으로는 두 목적을 동시에 만족할 수 없다.

[권장] 3계층 분리
  착안 — reimport_job.py:133 에서 job dict 에 thread 객체를 이미 보관 중이다.
         job["thread"].is_alive() 는 시간 추정 없이 결정적으로 답을 준다.
         시간 임계가 필요한 범위를 크게 줄일 수 있다.

  L1 확정  status ∈ _ACTIVE AND thread.is_alive()==False
           임계 30초(상태갱신 race 흡수용)
           → ORPHAN 확정 + store.finish_run (디스크 RUNNING 잔재도 종료)
           오살 위험 0 (추정이 아니라 사실 판정)
  L2 의심  진행신호 정지 & thread 는 살아 있음
           임계 max(FLOOR, K × 이 run 의 관측 최대 청크주기), FLOOR=1,800초(30분), K=10
           → 죽이지 않는다. stalled_suspect=True 만 세워 UI 경고 + 운영 로그. 종료는 사람이 결정
           오살 위험 0 (kill 안 함)
  L3 상한  진행신호 정지가 절대 상한 초과
           CEILING = 21,600초(6시간)
           → 자동 FAILED + finish_run.  오살 위험 매우 낮음

[각 값의 근거]
  L1 유예 30초 — 시간 추정이 아니라 _runner() finally 블록(reimport_job.py:122-130)이 status 를
    확정하기 전 찰나의 race 만 흡수하면 된다.
  L2 FLOOR 30분 — 정상 케이스를 절대 건드리지 않는 여유:
      청크당 관측 최대 10.24s          → 176배
      첫 결과 관측 최대 18.98s         →  95배
      100컬럼급 청크 최악 추정 93s     →  19배
      오라클 25만행 CTE/JOIN 전체 372s → 4.8배
  L2 K=10 — 이 run 에서 이미 관측된 최대 청크주기의 10배. 실측 환경편차가 2.32배였으므로
      4배 이상 추가 여유. FLOOR 와 max() 로 묶어 관측치가 작을 때 TTL 이 위험하게 줄지 않게 한다.
  L3 CEILING 6시간 — push-down 실패 500만행(약 2.1시간/청크)의 2.9배. 이보다 오래 걸리는 규모면
      청크 전략 선택 자체가 잘못된 것이므로 TTL 이 아니라 사전 계획 단계에서 막는 게 맞다.
      6시간이면 48시간짜리 대형 검증도 진행신호가 계속 찍히는 한 절대 걸리지 않는다.

[이 설계가 원래 목적(좀비 회수)을 달성하는가]
  좀비 실체가 "thread 죽었는데 PREPARING" 이면 → L1 이 30초 안에 전부 회수(기존안 30분보다 빠름)
  좀비 실체가 "thread 살아서 계속 DB 를 긁는 중" 이면 → 회수 대상이 아니다. 그건 정상 진행이고
    회수 사유는 "사람이 안 본다"뿐인데 그건 STALL 이 아니라 client-idle 축이다
  디스크 status='RUNNING' 34건 잔재 → L1/L3 가 finish_run 을 부르므로 더는 안 쌓인다
  → 3계층이 단일 STALL_TTL 보다 낫다. 좀비 회수는 오히려 빨라지고 오살 위험은 0 에 수렴한다.

[별건 제안 — 근본 개선]
  dialects/oracle.py:518 cur.fetchall() 을 fetchmany 루프로 바꾸면 조회 중에도 진행신호를 낼 수 있다.
  최대 공백이 "청크 전체 시간"에서 "fetch 배치 1개 시간"으로 줄어 2시간짜리 청크도 heartbeat 를 유지한다.
  P0 구간(연결/PK min-max/표본/정렬대기)에 단계명만 찍는 heartbeat 를 넣으면 그 구간 오판이 사라진다.
  엔진 변경이라 이번 범위 밖이지만, 이걸 먼저 하면 STALL_TTL 을 분 단위로 훨씬 작게 잡을 수 있다.

5. 동적 조정 필요 여부에 대한 의견 (지시 3 후단)
────────────────────────────────────────────────────────────────────────
필요하다. 단 지시문이 예로 든 "테이블 행수 / 복합 PK 개수 기반 자동 조정"은 권장하지 않는다.

  전체 테이블 행수     ✗ 틀린 축 — 청크 시간은 행수가 아니라 chunk_size 에 비례(실측표).
                            행수 10배면 청크 개수가 10배일 뿐 청크 1개는 그대로다.
                            행수 기반 TTL 은 정상 케이스를 과대보호하면서 push-down 실패는 여전히 못 막는다
  복합 PK 개수         ✗ 틀린 축 — 복합 PK 는 청크 시간의 변수가 아니라 엔진 선택의 변수다
                            (복합 PK → chunk 불가 → STREAM). STREAM 은 20,000행 간격이라 오히려 촘촘하다
  chunk_size           △ 유효하나 부분적 — 선형 관계 확인됨. 단 push-down 실패 케이스에선 무의미
  이 run 의 관측 최대 청크주기  ○ 권장 — 행폭·push-down 성공 여부·환경 부하를 전부 이미 반영한 실측치.
                            사전 예측이 어려운 세 요인을 한 값으로 흡수한다

  결론: 사전 계산형이 아니라 실행 중 관측 기반 적응형(L2 = max(FLOOR, K × 관측최대)).
  남는 공백: 첫 청크에는 관측치가 없다. FLOOR 가 그 구간을 덮어야 하고,
            chunks_done == 0 인 동안은 L2 판정을 아예 보류하는 편이 더 안전하다(P0 = 진행신호 0 구간).

────────────────────────────────────────────────────────────────────────
6. PAUSED(last_client_seen) 와 STALL(last_progress_at) 독립성 재확인 (지시 4)
────────────────────────────────────────────────────────────────────────
[6-1] 시각 갱신 경로는 코드상 완전히 독립 — 지시문 논리 맞다
  last_progress_at (신설예정)  ← worker 스레드
        pk_range_chunk.py:323/354/356/380 → agg_diff_route.py:282 _pcb → reimport_job.update_progress
  last_client_seen (신설예정)  ← HTTP 요청 스레드
        routes/agg_diff_route.py pk-records, routes/single_active_run_route.py active-run
  두 경로는 서로를 전혀 호출하지 않는다. "사용자가 자리를 비워도 job 이 돌고 있으면 진행신호는
  계속 찍힌다"는 지시문 논리는 코드 구조상 정확하다. 48시간 검증이 진행 중이면 last_progress_at 이
  계속 갱신되고 L2·L3 는 매번 리셋된다.
  단, P0 구간에는 진행신호가 0회다. 이 구간이 STALL 임계보다 길면 "작업은 정상인데 신호가 없는"
  상태가 된다. → chunks_done==0 동안 판정 보류로 막아야 한다.

[6-2] 그러나 "따라서 PAUSED 전환과 무관하게 안전"은 성립하지 않는다  ← 치명적
  지시문 논리는 "PAUSED 는 진행 여부를 보고 결정된다"를 암묵 전제하는데, 선행 설계(§5(b)-1)는 다르다:
      now - last_client_seen > CLIENT_IDLE_TTL(예 10~15분) → PAUSED 로 정지
  여기엔 진행 여부 조건이 없다. 즉 48시간 job 이 정상 진행 중이어도 운영자가 밤에 퇴근해 15분간
  화면을 안 보면 PAUSED 로 정지된다. 진행신호가 아무리 잘 찍혀도 막아주지 않는다.

  그게 "안전"하려면 resume 이 진행분을 보존해야 하는데 엔진에 따라 다르다:
    PK_RANGE_CHUNK_COMPARE   checkpoint 있음(agg_diff_route.py:301/:314/:320)
                             → 마지막 완료 청크 다음부터 재개, 최대 1청크 손실
    REIMPORT_PK_INDEX_STREAM checkpoint 전혀 없음 → 처음부터 전량 재실행
  검증: chunk_checkpoint 의 start/checkpoint/finish 호출자 전수 grep → _run_pk_range_chunk 한 곳뿐.
        prepare_reimport_pk_index_stream 에는 checkpoint_cb 인자 자체가 없다.

  그리고 어느 엔진을 쓰는지는 PK 모양이 정한다 (services/strategy/strategy_transition.py:58):
      chunk_capable = (pk_kind in (PK_SINGLE_NUMERIC, PK_SINGLE_DATE) and pk_indexed)
  → 복합 PK 는 chunk_capable=False → 항상 DIRECT_STREAM → checkpoint 없음.
    (_run_pk_range_chunk 도 agg_diff_route.py:269 에서 비숫자 PK 를 HOLD_NON_NUMERIC_PK 로 되돌린다)

  정리 — 지시문이 걱정한 바로 그 시나리오(수백만 행 + 복합 PK 다수, 48시간급)가
  "checkpoint 없는 STREAM 엔진" + "client-idle 만으로 PAUSED" 조합에 정확히 걸린다.
  20시간 진행한 검증이 "사람이 15분 자리를 비웠다"는 이유로 통째로 폐기된다.
  이건 지시문이 막으려 한 사고(STALL_TTL 오판)와 동급이거나 더 나쁘다.

[6-3] 권장 보정
  1) idle 회수에 진행 조건을 AND 로 묶는다 — client_idle AND (지금 진행신호가 멈춰 있음) 일 때만 PAUSED.
     진행 중인 job 은 아무도 안 봐도 절대 건드리지 않는다. (두 축 = 독립 측정 + 결합 판정)
  2) checkpoint 없는 엔진에는 idle-pause 를 적용하지 않는다 — STREAM 은 PAUSED 이득 0, 손실 100%
  3) 또는 STREAM 엔진에도 checkpoint 를 넣는다(별건·큰 작업). 그 전까지는 1·2 가 필수

────────────────────────────────────────────────────────────────────────
7. execution_settings 관리가 안전마진 확보에 유효한가 (지시 5)
────────────────────────────────────────────────────────────────────────
위치는 맞다. 그러나 현재 패턴 그대로면 유효하지 않다. 실측 근거 —
services/exact_diff/execution_settings.py 의 시간 설정 소비처 전수 grep 결과:

  stale_running_after_sec            : 사용처 0 곳   ← "RUNNING heartbeat 없음 → stale 판정"
  orphan_running_after_sec           : 사용처 0 곳   ← "thread 없음 orphan 판정 유예"
  recoverable_checkpoint_max_age_sec : 사용처 0 곳
  paused_run_keep_sec                : 사용처 0 곳
  pause_request_timeout_sec          : 사용처 0 곳
  resume_claim_ttl_sec               : 사용처 0 곳

6개 전부 선언만 되어 있고 아무도 읽지 않는다. 특히 앞의 두 개는 이번에 설계하려는 것과 개념이
정확히 같다(stale_running_after_sec = STALL_TTL, orphan_running_after_sec = L1).
여기에 STALL_TTL 을 새로 추가하면 같은 이름의 죽은 설정이 하나 더 늘어날 뿐이다.

유효하게 만들려면 함께 가야 할 것:
  ① 기존 stale_running_after_sec / orphan_running_after_sec 재사용(신규 이름 추가 금지) — 동의어 난립 방지
  ② 소비처 배선 + 배선 단위테스트 — 안 하면 ①도 죽은 설정이 된다
  ③ 영속화 — 현재는 in-memory override 뿐(파일 주석에 "DB 저장 없이 코드 기본값만" 명시).
     오살 사고 시 TTL 을 긴급히 늘리려면 지금은 서버 재시작이 필요하다. 사고 대응에 치명적
  ④ 환경변수 즉시 override + 조회 API 노출 — 재시작 없이 조정 / 현재 적용값 확인
  ⑤ 기능 토글(stall_detection_enabled 기본 False) — 실환경 관측 후 켠다. 기본 ON 은 위험

⑤ 를 특히 권장한다. push-down 실패 2시간 청크는 아직 실제 나이스/에듀파인 환경에서 관측된 적이 없다
(25만행 CTE/JOIN 372초에서 선형 외삽한 값이다). 기본 OFF 로 넣고 last_progress_at 을 기록·노출만
먼저 한 다음, 실환경 분포를 몇 주 모아 FLOOR 를 확정하는 게 순서상 맞다.
