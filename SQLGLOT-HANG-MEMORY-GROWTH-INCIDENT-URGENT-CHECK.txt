■ "3회차"의 의미와 negative cache 가 막지 못한 이유 → **두 겹으로 무력화됐다**

  (1) 회차 간 — 캐시는 프로세스 메모리 안에만 있다
      negative cache(_timeout_cache)는 sqlglot_safe_parse 모듈의 프로세스 내 OrderedDict 다.
      parse 케이스는 매 회차가 **새 python 프로세스**이므로 1·2회차의 타임아웃 기억이
      3회차로 전달되지 않는다. 설계상 당연하지만, 반복 실행 시 방어가 0회부터 다시 시작된다.

  (2) 회차 내 — 캐시 키가 (방언, SQL) 이라 SQL 이 다르면 통과한다
      직전 회차 산출물(_s15_s16_s18_live_parse.json)을 보면 한 회차 안에서 **서로 다른
      hang SQL 3건**을 제출한다.

        raw    : SELECT * FROM t WITH x AS (SELECT 1) SELECT * FROM x
                 → 183.17초 (analyze 요청조차 도달 못함)
        insert : INSERT INTO tgt (a) SELECT * FROM t WITH x AS (...) ...
                 → 3.65초 (metadata 부재로 사전 차단되어 파서까지 안 감)
        real   : INSERT INTO NXDNP.MV_SCATTER_TGT (...) ... WITH x AS (...) ...
                 → 310.15초, /analyze 요청 1건에 응답 없음

      _cache_key = sha256(dialect + SQL) 이므로 세 SQL 은 각각 별개 항목이다. 즉 캐시는
      "같은 SQL 재제출"만 막고, 사고 케이스처럼 변형 SQL 을 연달아 넣으면 매번 새 hang
      스레드가 생긴다.

■ 원인 특정 — sqlglot 자체 결함이며, 가드는 원인이 아니지만 방어도 못 된다

      → 원인은 이 저장소의 daemon 스레드 가드가 아니라 **sqlglot 파서 무한루프가 매 반복
        새 객체를 할당하는 패턴** 그 자체다.
    · 가드 코드는 스스로 문서화한 대로(파일 상단 주석 19-22행) 스레드를 회수할 수 없다.

    · 오히려 가드가 응답을 되돌려주는 탓에 사용자는 계속 조작할 수 있고, 변형 SQL 을

  1) 스레드 방식으로는 근본 해결이 불가능하다 — 회수 불가가 곧 메모리 누수다.
     파싱을 별도 **프로세스**로 격리하면 타임아웃 시 강제 종료가 가능해 누수가 0이 된다.
     (비용: 프로세스 생성 오버헤드 — 정상 파싱이 1~10ms 이므로 상시 적용은 부담. 캐시된
      "위험 패턴"에만 적용하거나 워커 프로세스를 상주시키는 절충이 필요.)
  2) 파서에 넣기 전에 차단하는 사전 검사(예: FROM 절 뒤에 WITH 가 오는 형태)를 두면
     비용 없이 대부분을 막을 수 있다. 다만 heuristic 증가이므로 근거 저장이 필요하다.
  3) negative cache 를 SQL 정규화 키(공백·리터럴 제거) 기반으로 넓히면 회차 내 변형 SQL
     반복은 줄일 수 있으나, 첫 1회의 폭주는 여전히 막지 못한다.
  4) sqlglot 버전 상향(30.13.0)은 이 특정 입력에는 유효하나, 30.7.0·30.8.0 이 동일하게
     터진 것에서 보듯 "파서가 안 끝나는" 부류는 재발 가능하므로 1)~2)와 병행해야 한다.
     아울러 글로벌 30.7.0 / .venv 30.8.0 처럼 환경별 버전이 갈리는 상태부터 정리해야 한다.
