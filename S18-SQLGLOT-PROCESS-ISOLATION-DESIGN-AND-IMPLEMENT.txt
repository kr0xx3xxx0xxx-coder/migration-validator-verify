[1-2] 프로세스 격리 방식 후보 비교 — 실측으로 결론
  (A) multiprocessing.Process + Queue, 호출마다 생성/terminate
      → 기각. 이유 2가지.
        · 비용: 워커 부팅(프로세스 생성 + sqlglot import) 실측 **204.3ms**. 정상 파싱이
          0.05~1.5ms 이므로 호출당 격리는 최대 4,000배 느려진다(환산 206ms/호출).
        · 구조: Windows 는 spawn 방식이라 자식이 부모의 __main__(web_server.py)을 재import 한다.
          워커마다 FastAPI 앱 전체를 다시 적재하는 셈이라 부작용·비용이 크다.
  (B) 워커 프로세스 **풀 재사용** ← 채택
      · multiprocessing 대신 `sys.executable -c <워커 소스>` subprocess 를 쓴다.
        워커는 sqlglot + 표준 라이브러리만 import 하며 부모 모듈을 일절 건드리지 않는다.
      · 통신: stdin/stdout 의 4바이트 길이접두 pickle 프레임(요청 = sql+kwargs, 응답 = AST/예외).
      · 부팅 204ms 는 워커 생성 1회에만 발생하고, 이후 호출은 IPC 왕복 비용만 낸다.

[1-3] 풀의 hang 워커 감지·교체 설계
  · 응답 대기는 워커마다 전담 reader 스레드 + Queue 로 한다(Windows 는 파이프에 select 불가).
    이 스레드는 CPU 를 돌지 않고 파이프에 블록될 뿐이며, 워커가 죽으면 EOF 로 즉시 끝난다
    — 무한루프 스레드와 성격이 완전히 다르다(누수 아님).
  · 타임아웃 워커는 **반납하지 않고 폐기**한다: taskkill /F /T (venv 런처 stub 구조상 손자까지)
    + proc.kill(). 다음 호출은 자동으로 새 워커를 받는다(무상태 교체).
  · 워커 자체 감시(부모 타임아웃만으로는 늦기 때문):
      - 메모리 상한(기본 512MB) 초과 시 워커가 os._exit 로 자폭.
        근거(실측): 워커 기준선 24MB, 극단적 정상 SQL(289KB · IN 5만 항목) 파싱도 +45MB.
        정상 대비 10배 이상 여유이면서, hang 폭주는 3~4초에 차단된다
        (상한 없이 15초 타임아웃까지 두면 2GB 이상 먹는다).
      - 부모 생존 확인(0.25초 주기). 이 저장소는 "서버 시작 시 기존 포트 점유 프로세스 자동 종료"
        규칙이 있어 강제 종료가 일상적이므로 고아 워커 방지가 필요하다.
  · 하드 상한: 소프트 상한(기본 3)이 전부 점유되면 최대 7개까지 임시 워커를 만들고, 그마저
    가득이면 **실패(SqlParseBusy)**시킨다 — 여기서 in-process 로 폴백하면 hang 반복 제출 시
    회수 불가능한 스레드가 다시 쌓이므로 '실패'가 올바른 선택이다.
  · 워커 수명: 1,000 요청 처리 후 폐기·재생성(장기 구동 서버의 완만한 누수 차단).

[1-4] 기존 방어선을 대체할 것인가 — **대체하지 않고 3단으로 쌓는다**
  1차 사전 차단(detect_unsupported_sql_shape)  : 유지. 알려진 위험 패턴은 IPC 비용조차 치르지
      않고 즉시 차단되며(실측: 워커 생성 0건), 오탐 위험이 없는 무료 방어선이다.
  1.5차 negative cache                          : 유지. 같은 SQL 재제출을 즉시 동일 실패시킨다.
  2차 프로세스 격리(신규)                        : 실제 파싱 담당. 타임아웃/메모리 초과 시 kill →
      **메모리 실제 회수**. 미지의 hang 패턴을 받아내는 진짜 방어선.
  3차 스레드 타임아웃 가드(기존)                 : 삭제하지 않고 **폴백 전용**으로 남긴다.
      파이썬 실행 실패·sqlglot import 실패·직렬화 불가 인자 등 격리를 쓸 수 없는 환경에서
      기능을 잃지 않기 위한 강등 경로다(= 도입 전 수준으로만 내려감).
  ※ 안전을 위해 폴백을 **금지**하는 경우를 명시적으로 분리했다:
      - 파싱 도중 워커 사망(IsolatedParseCrashed) / 워커 포화(IsolationBusy)
        → in-process 재시도하면 같은 hang 을 회수 불가능한 스레드로 재현하게 되므로 즉시 실패.
      - 부팅 실패·결과 직렬화 불가(IsolationUnavailable)
        → 파싱을 시작 전이거나 이미 정상 종료한 뒤이므로 폴백해도 안전 → 폴백 허용.

  · 늘어난 8 passed = 이번에 추가한 테스트 8건
  · 실패 40건 + 오류 2건은 전부 **사전 존재 실패**이며 원인은 이 변경과 무관하다:

        (예: test_diagnosis_*::test_http_*, test_batch_upload_cte_precheck.py 수집 오류)
  · 실패 테스트 전체 목록은 before/after 가 동일하므로 개별 나열을 생략하지 않고 성격만 요약한다:
    전부 `test_http_*` 계열(라우트 통합) + 수집 단계 오류 2건.

5. 비판적 검토 — 이번 변경이 남기는 위험과 한계(숨기지 않고 명시)
════════════════════════════════════════════════════════════════════════════════
[5-1] 남는 위험
  · 상주 메모리 증가: 워커 1개당 32MB, 기본 풀 3개 → 최대 약 96MB(요청이 있을 때만 지연 생성).
    폭주 시 하드 상한 7개(약 224MB)까지 늘 수 있다. MV_SQL_PARSE_ISOLATION_POOL 로 조절 가능.
  · 대형 SQL 오버헤드: [3-2] 대로 수십 KB 이상에서는 배수로 커진다(직렬화 비용).
  · 메모리 상한 512MB 는 '정상 파싱 실측 +45MB' 근거의 값이다. 그보다 훨씬 큰 SQL 을
    정상 처리해야 하는 요구가 생기면 상한을 올려야 하며, 그만큼 hang 폭주 총량도 커진다.
  · 첫 파싱 1회는 워커 부팅 204ms 를 그대로 부담한다(서버 기동 시 prewarm 배선은 하지 않았다 —
    web_server.py 비대화 억제 규칙을 지키기 위함. 필요해지면 prewarm() 한 줄로 해결 가능).
  · 워커 포화 시 SqlParseBusy(=파싱 실패)로 떨어진다. 폴백보다 안전하다는 판단이지만,
    비정상 부하 상황에서 '분석 실패'가 사용자에게 보이는 것은 사실이다.

[5-2] 기존 테스트 1건의 단정을 완화했다(임의 수정이 아니라 전제가 바뀐 경우)
  tests/test_sqlglot_parse_timeout_guard.py TC-1 은 "회수 불가 스레드 카운터 ≥ 1" 을 단정했다.
  격리 도입 후에는 스레드가 누수되지 않으므로(그게 이번 개선의 목적) 이 단정은 구조적으로 실패한다.
  → "스레드 누수 **또는** 워커 생성 중 하나로 방어가 실제 동작했는가"로 바꾸고,
     격리 경로였다면 "hang 워커가 살아남지 않았는가(pool_live == 0)"를 추가로 단정했다.
     즉 검증 강도를 낮춘 것이 아니라 메커니즘 비의존으로 바꾸고 항목을 하나 더 늘렸다.

[5-3] heuristic / scoring / explainability 영향
  · heuristic 하드코딩 증가 없음 — 이번 변경은 '실행 위치'만 바꾼 것이고 판정 로직은 그대로다.
  · explainability: 관측 카운터를 남겼다(isolation_stats: workers_spawned/killed/isolated_calls/
    fallbacks/boot_failures/pool_live, isolation_fallback_count, 기존 abandoned/blocked 카운터).
  · 보안: 워커는 SQL 텍스트만 받고 DB 접속정보를 일절 취급하지 않는다(비밀번호 노출 경로 없음).

[5-4] 근본 해결인가
  sqlglot 자체의 무한루프 결함은 여전히 상류(업스트림)에 남아 있다. 이번 변경은 그 결함이
  **호스트를 죽이지 못하게** 만든 것이다(hang → 유한 시간 실패 + 메모리 전량 회수).
  파서 버전 상향은 별개 과제로 남는다(현행 30.8.0, 30.13.0 에서 해당 패턴 수정 보고됨).
