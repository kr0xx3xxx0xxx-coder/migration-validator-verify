0. 한 줄 결론
═══════════════════════════════════════════════════════════════════════

질문한 "서버에는 있는데 화면에 안 나오는가" vs "애초에 서버가 최종 점수만 계산하는가"는
**둘 다 부분적으로 참**이며, 요소별로 갈린다.

  · 카디널리티 기여분 / NULL비율 기여분 (2개)
      → 서버에 수치 필드로 **존재**한다 (profile_evidence.card_score_adj / null_score_adj).
      → 그러나 UI가 **의도적으로 숫자를 숨긴다**("내부 가산점(+N)는 UI에 노출하지 않는다" 주석).
      → 즉 "서버엔 있는데 화면에 없음" 유형.

  · 기본점수 / 타입 적합성 / 시맨틱 매칭 / 구조적 길이 / 시스템감사 페널티 / hard_rule 상한
      → 서버가 하나의 `score` 변수에 누적 가감만 하고 **각 기여분을 어디에도 보존하지 않는다**.
      → 즉 "애초에 서버가 최종 합산 점수만 남김" 유형.

  · 관리컬럼 페널티 / VARCHAR2 수용량
      → 운영 후보추천 점수에는 **애초에 반영되지 않는다**(§5 참조).

결과적으로 사람이 "이 75점이 왜 75점인가"를 응답 필드만으로 검산하는 것은 **불가능**하다.
S10(is_pk 고정값) 같은 사고가 다시 나도 점수 자체로는 드러나지 않는다.

2. [조사항목 1] 최종 점수는 몇 개 하위 요소로 구성되는가
═══════════════════════════════════════════════════════════════════════

`score_group_by_candidate()` / `score_sum_candidate()` 는 **단일 지역변수 `score` 에
순차적으로 가감만 하는 구조**다. 요소별 변수를 따로 두지 않는다.

GROUP BY 기준으로 실제 가감 지점은 다음 8종이다 (services/candidate_scoring.py).

 (1) 기본점수 — `_base_score_and_reason()` (:256-267)
        auto_selected → 40 / warn 없음 → 20 / warn 있음 → 10

 (2) 타입 적합성 (:656-665)
        비숫자형 +15 / 숫자형 +0(경고만) / 타입정보 없음 +5
        (SUM 은 숫자형 +25 / 비숫자형 +0)

 (3) 시맨틱 사전 매칭 (:670-704)
        DIMENSION 계열 STRONG +20, WEAK +10 / context_ok=False -5
        CAUTION(RATE_RATIO·UNIT_PRICE) +5 / EXCLUDE 계열 -10 / MEASURE 계열 +5 / 기타 +5
        (SUM 은 MEASURE STRONG +20, WEAK +10, EXCLUDE -30)

 (4) hard_rule 상한 (:729-736)
        hard_rule 있으면 `score = min(score, 25)` — 가감이 아니라 **천장(ceiling)**

 (5) profile 카디널리티 (`_apply_gb_profile` :332-353)
        card_ratio ≤0.005 +15 / ≤0.02 +10 / ≤0.10 +5 / ≤0.60 0 / ≤0.90 -10 / 초과 -20
        거의 고유값(>0.98) 추가 -10

 (6) profile NULL 비율 (:357-362)
        null_ratio ≥0.50 -10 / >0.20 -5

 (7) catalog 저카디 보너스 (`_catalog_lowcard_gb_bonus` :227-253)
        카디널리티 ≤+15, null 낮음 +10, 최빈값 존재 +10 → 최대 +35

 (8) 구조 신호 (:811-870)
        값기반 시스템감사 -30 (`_SYSTEM_AUDIT_VALUE_PENALTY`)
        긴 문자열(≥100) -15 (`_LONG_TEXT_PENALTY`)
        짧은코드+저카디 +5 (`_SHORT_CODE_HINT`)

 마지막에 `score = max(0, min(100, score))` (:872) 후 임계값으로 라벨링
        ≥70 HIGH / ≥40 MEDIUM / 그 외 LOW (:28-29, :874-879)

⇒ 하위 요소는 **최소 8종**. 가중치는 코드 상수로 하드코딩돼 있고 설정/문서 산출물이 아니다.

검산: 40(기본) + 15(타입) + 15(카디) + 0(NULL) + 5(짧은코드) = 75 ✅ 실측 score 와 일치.
      그러나 이 5개 중 **응답 필드로 확인 가능한 것은 15와 0 두 개뿐**이다.
      나머지 60점(40+15+5)은 코드를 읽어야만 역산된다.

핵심: 요소별 기여분을 담는 컨테이너 자체가 없다. `reasons`/`warnings` 는 사람이 읽는
      한국어 문장 배열이지 구조화된 기여도가 아니며, 대부분 점수 폭조차 적혀 있지 않다.

5. [조사항목 4] "서버엔 있는데 화면에 없음" vs "서버가 아예 안 만듦" 구분
═══════════════════════════════════════════════════════════════════════

지침이 예로 든 5개 요소를 요청대로 명확히 갈라 적는다.

┌───────────────────┬──────────┬──────────┬────────────────────────────────────────┐
│ 요소               │ 서버 보존 │ 화면 노출 │ 판정                                    │

가장 큰 비중은 B형 — 서버가 요소별 기여분을 만들지 않는다.

별도로: 6차원 `score_breakdown`(E1)이 존재하지만 **운영 점수와 완전히 분리된 관찰용**이다.
  · services/candidates/candidate_score_breakdown.py 헤더(:7-9) 원문:
        Phase E-1 experimental score_breakdown 계산.
        기존 score / selection_status / auto_selected / UI에는 일절 반영하지 않는다.
        최종 점수(final_score) 합산도 이번 단계에서는 하지 않는다.

    "이번 단계 미구현" 스텁.
  · 부착 위치는 db_statistics_service.py:1160 (`merged["score_breakdown"] = _compute_gb_breakdown(merged)`)

6. [조사항목 5] 가중치 역추적 (참고 — 코드 근거 기반, 추측 아님)
═══════════════════════════════════════════════════════════════════════

§3 에서 분해 필드가 부재하다고 판정했으므로, 지침 5항에 따라 역추적을 남긴다.
아래 표는 **코드의 상수 리터럴을 그대로 옮긴 것이므로 추측이 아니다**.
다만 "실제 후보 집단에서 어느 요소가 결정적이었는가"라는 분포는 산출 근거가 없어 미상이다.

■ GROUP BY (services/candidate_scoring.py:633-894)
    기본점수        40 / 20 / 10        (auto_selected / warn없음 / warn있음)
    타입            +15                 (비숫자형), 숫자형 0, 타입미상 +5
    시맨틱 STRONG   +20                 (DIMENSION_* 9종)
    시맨틱 WEAK     +10
    시맨틱 EXCLUDE  -10                 (IDENTIFIER/SORT_ORDER/SYSTEM_AUDIT/CONSTANT/TECH_KEY/RAW_TEXT)
    카디널리티      +15 ~ -30           (ratio ≤0.005 → +15, >0.98 → -20-10)
    NULL            0 ~ -10
    catalog 저카디  0 ~ +35             (profile 미전달 컬럼 구제 경로)
    시스템감사(값)   -30
    긴문자열(≥100)  -15
    짧은코드(≤8)    +5
    hard_rule       ceiling 25
    임계            ≥70 HIGH / ≥40 MEDIUM

■ SUM (services/candidate_scoring.py:451-630)
    기본점수        40 / 20 / 10        (GROUP BY 와 동일)
    타입            +25                 (숫자형), 비숫자형 0 + 경고
    시맨틱 STRONG   +20                 (MEASURE_* 9종)
    시맨틱 WEAK     +10
    시맨틱 EXCLUDE  -30
    시맨틱 CAUTION  +0                   (RATE_RATIO/UNIT_PRICE — 가산 없이 경고만, HIGH 진입 차단)
    NULL            +5 ~ -25
    분산(distinct)  +8 / +5 / -15       (상수컬럼 -15)
    긴문자열(≥100)  -15
    hard_rule       ceiling 25

■ 관측 (역추적으로 드러난 구조적 특징 — 사실 진술)
    · 기본점수 40 이 **전체 100점 중 40%** 를 차지한다. 즉 `auto_selected` 한 필드가
      점수의 최대 지분을 갖는다. auto_selected 가 오염되면 점수 전체가 통째로 밀린다.
    · GROUP BY 는 40(기본) + 15(타입) = 55 만으로 MEDIUM(≥40) 을 이미 통과한다.
      즉 시맨틱·통계 근거가 전혀 없어도 '확인 후 선택' 등급이 나온다.
    · 가중치 합계가 정규화돼 있지 않고 clamp(0~100) 로 잘린다. clamp 로 잘렸는지 여부도
      응답에 남지 않아, 100점 후보 2개의 실제 강도 차이를 구분할 수 없다.
