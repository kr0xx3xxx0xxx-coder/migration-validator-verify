1. 배경과 범위

요약 그리드(_mvRenderStrategyPlan, ui/tabler_renderer.py:27593)의 "상태" 열이 2026-07-23
그리드 전환 커밋(c2a8491) 이후 '실제 적용' 1행에만 배선되고 나머지는 방치됐음이 확정됐다.
진단서 결론대로 실질 수정 대상은 3개 행(1·5·7행)뿐이며, 나머지 5행은 현행 유지가 타당하다.

이번 작업은 순수 표시(display-only) 변경이다. 값 문자열·판정 로직·SQL·plan 생성 로직은
일절 건드리지 않았고, rows.push 호출에 status/statusText 필드만 추가했다.

행 번호 대응(실제 렌더 그리드는 '전역 설정' 행이 조건부로 붙어 9행이 되므로 번호가 1칸 밀린다):

2. 수정 내용
────────────────────────────────────────────────────────────────────────
(1) 7행 '상태' — 항목명이 '상태'인데 상태 열이 공백이던 가장 명백한 모순
    status     : impl === 'AVAILABLE' ? 'READY'
               : impl === 'PHASE4_B_REQUIRED' ? 'WARN' : 'HOLD'
    statusText : implTxt (실행 가능 / Phase 4-B 엔진 필요 / 상세비교 보류(HOLD))
    _mvBadgeCls(ui/grid_helpers.py:155)가 'HOLD' 접두를 이미 인식하므로 별도 매핑 없음.
    값 열의 색상 텍스트(implColor/implTxt)는 지침대로 그대로 두었다(중복이지만 기존 문자열
    검사 테스트 보호).

(2) 5행 '통계전략' — 실행가능성 한정어가 값 열에만 있던 문제
    status     : _statsAdvisoryOnly ? 'WARN' : ''   (빈 값이면 _mvKVGrid 가 배지 미표시)
    statusText : _statsAdvisoryOnly ? '참고용' : ''
    값 열의 인라인 '참고용 계획' span 은 지침대로 유지(제거는 별도 판단 사안).

(3) 1행 '통계검증 규모' — 잠정/산정 전/산정 불가 3분류
    새 조건을 발명하지 않고 ui/grid_helpers.py 의 _mvStatsScaleText(829-830) 판별 조건과
    services/strategy/strategy_models.py:47 의 PROVISIONAL_PREFIX('잠정 ')를 그대로 재사용:
      - provisional_grade 가 '잠정 ' 로 시작        → WARN  / '잠정'
      - 등급 없음 + stats_scale_estimable === false → WARN  / '산정 불가'
      - 등급 없음 + 그 외                           → MUTED / '산정 전'
      - 확정 등급(잠정 접두 없음)                   → 배지 없음
    ※ PROVISIONAL_PREFIX 는 Python 상수라 JS 쪽에 같은 리터럴을 두되 출처를 주석에 명시했다
      (지침이 이 파일만 수정하도록 제한했으므로 grid_helpers.py 에 상수 주입은 하지 않음).

미변경(진단서가 "현행 유지가 타당"으로 결론낸 행): 전역 설정 / 실제 적용 / GROUP BY /
집계컬럼 / 불일치 추출전략 / 판정근거. window._mvValidationPolicy 미로드 시 '전역 설정' 행이
사라지는 부수 문제(진단서 §6-(4))도 지침 범위 밖이므로 손대지 않았다.

[한계 명시] 1행의 '산정 전'/'산정 불가' 분기는 실 API 로 재현 불가하다. /strategy/plan 은
stats_strategy_planner._provisional_grade() 로 provisional_grade 를 항상 채우기 때문에,
API 가 성공하는 한 이 카드의 1행은 항상 '잠정 X' 다. 따라서 D/E 는 실 응답에서
provisional_grade 필드만 제거한 stub 으로 방어 분기만 확인했다(값 열은 기존과 동일하게
'산정 전' 으로 표시됨 — 값 열은 손대지 않았으므로). 즉 D/E 는 실운영 재현 케이스가 아니라
코드 경로 도달 확인이다.

또한 지침이 예시로 든 "42M·인덱스 없음 → PHASE4_B_REQUIRED" 는 실제로는 성립하지 않았다.
strategy_route 가 DIRECT↔CHUNK 전환 정책(choose_compare_strategy)으로 최종 전략을 다시
확정하면서 DIRECT_STREAM_COMPARE(=AVAILABLE)를 유지했기 때문이다. PHASE4_B_REQUIRED 는
파티션 보유 프로파일(PARTITION_BUCKET_COMPARE)로 실 API 재현했다(케이스 B2).
