작업명 : M62-TAB-LOCK-STALE-AFTER-COMPLETION-DIAGNOSE-AND-FIX
✅ 작업 완료 - COUNT 완료 후에도 상단 탭이 계속 잠겨 있던 회귀를 실측 재현하고 원인(플래그는 풀리는데 그 뒤 탭 재렌더가 없음)을 확정, runCount 종료 2경로에 단계 탭 재렌더를 배선해 실 클릭 A/B로 수정 확인(COUNT 실행 중 차단은 그대로 유지), 4단계·전 탭게이트 전수확인 결과 추가 결함 0건

■ 결론 요약
  1) 재현 성공. 수정 전 코드(HEAD 920f57ec)에서 COUNT 완료 직후(다른 버튼 클릭 없음) 1단계 '쿼리검토'
     탭은 여전히 mv-step-disabled + data-step 속성 없음 → 실제 클릭해도 _singleViewStep 이 'count' 그대로.
     같은 시점 _countInProgress=false, _mvCanNavTab('query')=true 였다 — 즉 "상태는 이미 풀렸는데 그 값을
     반영한 탭 DOM 재렌더가 일어나지 않은" 전형적 상태변경-재렌더 누락(지시서 1번 가설이 그대로 맞았다).
  2) 원인 지점 확정: runCount 의 finally 가 _countInProgress=false 로 내리지만 그 뒤에 _renderSingleStepNav()
     를 부르지 않는다. COUNT 흐름에서 nav 가 마지막으로 그려지는 곳은 renderCountResult →
     _updateProgressCard('count', …) → _updateStickyProgress → _renderStickyBarFull → _renderSingleStepNav 인데,
     이 호출은 try 블록 안(= finally 보다 앞)이라 _countInProgress 가 아직 true 인 값으로 disabled 를 그린다.
     이후 플래그만 false 가 되고 다시 그리는 지점이 없어 잠금이 DOM 에 고착됐다. 사용자가 '◀ 이전'으로
     1단계에 갔다 오면 showSingleStep 이 부르는 재렌더에 얹혀서야 풀린 것도 정확히 이 구조 때문이다.
  3) 수정은 새 상태·새 잠금 로직 없이 "플래그가 확정된 뒤 기존 렌더 함수를 한 번 더 부른다" 2줄이다.
     _mvAnyRunActive() 전체를 재렌더 트리거에 연결하지 않았으므로 M47 의 '5단계 job 중 자유이동' 예외는
     건드리지 않았다(코드 경로 자체가 다름).
  4) 전수 확인 결과 같은 유형의 stale lock 은 COUNT 한 곳뿐이었다. 4단계(_executeInProgress)는 시작·조기중단·
     plan-sets finally·메인 finally 4곳 모두 이미 재렌더가 배선돼 있었고, 실 클릭으로도 "실행 중 5단계 탭
     잠김 → 완료 즉시 클릭 가능 → 클릭 시 5단계 이동"이 확인됐다(추가 수정 불필요).
