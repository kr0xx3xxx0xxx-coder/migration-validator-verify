【1-2. CTE(WITH절) 파싱 관련】 → ★ 이번 조사 최대 발견 1건
    - v30.13.0 a7058d6  **oracle: unrecognized WITH hangs the parser [CLAUDE] (PR #7881)**
      PR 본문 인용(요지):
        "The Oracle SQL dialect parser would hang indefinitely when encountering an unrecognized
         `WITH` clause. This affected error levels IGNORE, WARN, and RAISE."
        "Oracle's `WITH` modifier wrapped its parse result in a list: `[self._parse_query_restrictions()]`.
         When `_parse_query_restrictions()` returned `None`, this became `[None]` — a truthy value.
         The falsy check `if expression:` passed, but since the `WITH` token was never consumed,
         the enclosing `while True` loop re-entered on the same token infinitely."
        "This was the only one of 25 QUERY_MODIFIER_PARSERS that wrapped results in a list."
      재현 입력(PR 제시): `sqlglot.parse_one("SELECT * FROM tbl WITH", read="oracle")`
                          현실 케이스: `"SELECT * FROM t WITH x AS (SELECT 1) SELECT * FROM x"`
                          (CTE 앞 세미콜론 누락 등 흔한 오타)
      수정: 리스트 래핑을 `ensure_list()` 로 교체. 정상 `WITH READ ONLY` / `WITH CHECK OPTION` 는
            변화 없이 round-trip.
      → 본 프로젝트 영향: **직격**. 4장에서 실측·경로 확인.

  같은 축의 나머지는 전부 optimizer 또는 타 방언 전용이라 무영향:

    - v30.13.0 bbb376d  tighten the self-referencing cte check in projection pushdown
    - v30.11.0 6ae4b49  tsql: do not bubble up CTEs in TVF DDLs with inline RETURN queries (#7721)
    - v30.9.0  c19bb4b  parser: Avoid `__tmp#` CTEs getting replaced with outer CTEs for pipe syntax

4. hang 결함의 실제 노출 경로 — 조사 중 확인된 별건 위험
────────────────────────────────────────────────────────────────────────
2장의 hang 이 서버 요청 경로에 닿는지 확인했다. **닿는다.**

  parser/sqlglot_parser.py:132-140
      sg_dialect = _DIALECT_MAP.get(dialect.lower(), 'oracle')     ← 기본값이 oracle
      try:
          tree = sqlglot.parse_one(
              sql_norm,
              dialect=sg_dialect,
              error_level=sqlglot.ErrorLevel.RAISE,                ← 2장에서 hang 확인된 조합
          )
      except Exception as e:
          return ParseResult(error_message=f"sqlglot 파싱 오류: {e}")

  이 `parse()` 는 `get_sql_parser().parse()` 공용 진입점이며 호출처가 웹 요청 경로다:
      services/validation_sql_parse_service.py:372   (개별검증 1단계 분석)
      services/sql_validation_service.py:797
      services/sql_change_detection.py:53            (/sql/change-check)

  위험의 성질:
   - **try/except 로 못 막는다.** 예외가 아니라 `while True` 무한 루프이므로 except 절에 도달하지 않는다.
   - 타임아웃 가드도 없다. FastAPI/uvicorn 워커 스레드 하나가 영구 점유되고, 요청은 응답 없이 매달린다.
   - 트리거 난도가 낮다. 사용자가 이관 SQL 을 붙여넣는 도구인데, 오라클 선택 + CTE 앞 세미콜론 누락
     같은 흔한 오타 하나면 재현된다(2장 두 번째 케이스가 정확히 그 형태).
   - 지원 4방언 중 oracle 이 주력 대상이라 노출면이 작지 않다.
   - 다만 **현재까지 이 현상이 보고된 기록은 없다.** 잠재 결함이지 발생한 장애가 아니다.
     (오늘 다룬 UNION·wrapping 문제와도 증상이 다르다 — 그쪽은 오판정, 이쪽은 무응답)

   - **오늘 다룬 "별칭 추출 실패"·"UNION 오판정"과 일치하는 이슈는 없다.** 예상된 결과다 —
     그 둘은 sqlglot 이 잘못 파싱한 게 아니라 우리 코드가 (a) 문자열 `" UNION "` 검사를 썼고
     (b) 실패 사유를 뭉뚱그려 표시했던 자체 결함이었고, 이미 각각
     UNION-SAMETABLE-WRAPPING-DETECTION-AST-FIX 와 REIMPORT-SOURCE-WRAPPING-AST-EXTRACTION-FIX 로 해결됐다.

     흡수된다. 즉 업그레이드해도 이 두 형태는 개선되지 않는다.
   - hang 결함(#7881)은 이슈로 신고된 게 아니라 기여자가 직접 발견해 PR 로 올린 건이다.
     즉 "다들 겪는데 우리만 모르는" 유형이 아니라, 트리거 조건이 좁아 아무도 신고하지 않은 잠복 결함이다.
     우리가 오라클을 주력으로 쓰기 때문에 상대적으로 노출도가 높다.

7. 업그레이드 위험도 평가 및 권고 (지침대로 의견만 — 구현하지 않음)
────────────────────────────────────────────────────────────────────────
- 요청 요약: sqlglot 30.8.0 → 30.14.0 업그레이드가 오늘 다룬 파싱 문제 해결에 도움이 되는가.

- 긍정적 효과:
    (1) 오라클 방언 무한 hang 제거(4장) — 이것만으로 업그레이드 명분이 선다. 서버 스레드 영구 점유는
        검증 오류보다 등급이 높은 가용성 문제다.
    (2) 오라클 `^=` · `TO_NUMBER(... DEFAULT ...)` · `UNPIVOT` 파싱 지원(1-5) — sqlglot 실패 후
        LegacyParser 로 떨어지던 케이스가 줄어 파싱 정확도가 올라간다.
    (3) 반면 **오늘 다룬 UNION 오판정·wrapping 별칭 추출 실패는 전혀 개선되지 않는다.**
        원인이 sqlglot 이 아니었기 때문이다(1-1, 1-4, 6장). 이 점은 분명히 해둘 필요가 있다 —
        "최신 버전이면 오늘 문제가 없었을 것"은 사실이 아니다.

- 위험도: **낮음** (근거는 추측이 아니라 실측)
    · 우리 sqlglot 사용 표면이 `parse_one` + `exp` 노드 순회로 한정되고 optimizer 를 전혀 안 쓴다(1-6).
      구간 BREAKING 의 대부분(annotate_types/qualify_outputs/merge_subqueries)이 정의상 무관하다.
    · AST 의존 테스트 10파일 168건이 두 버전에서 동일 통과(3장). 오늘 만든 AST 사전판정 함수 전용
      테스트도 포함된다.
    · 남은 미검증 영역은 방언별 `.sql()` 재생성 문자열이다. 구간 내 postgres `IS NOT NULL` 보존 변경
      (2aae7f7)이 이론상 WHERE 원문 복원 표기를 바꿀 수 있다 — 다만 이는 `NOT x IS NULL` 로 정규화하던
      것을 원문 `x IS NOT NULL` 로 **되돌리는** 방향이라 우리에겐 오히려 개선이다.

- 기존 테스트 스위트로 충분히 검증 가능한가: **대체로 가능하나, 전수 실행이 전제다.**
    · 이번엔 sqlglot 의존 10파일만 돌렸다(28초). 전체 스위트는 11,000건대·60분 규모라 이번 조사 범위를
      넘어 실행하지 않았다. 실제 업그레이드 시에는 전수 회귀가 필요하다.
    · 취약점: 현재 스위트에 **오라클 방언 파서 hang 을 잡는 테스트가 없다.** 이번 결함이 스위트를
      그대로 통과한다는 뜻이다(hang 은 실패가 아니라 무응답이라, 타임아웃 없는 pytest 는 영구 정지한다 —
      실제로 이번 조사에서도 자식 프로세스 타임아웃을 걸고서야 관측할 수 있었다).
    · 참고로 이 환경에는 pytest-timeout 이 없다(`--timeout` 미인식 확인). 파서 hang 류를 스위트에서
      잡으려면 자식 프로세스 + 타임아웃 방식의 전용 테스트가 필요하다.

- 구조적 문제점 / heuristic·scoring·explainability 영향:
    · 없음. 버전 교체이며 코드·판정 로직·근거 저장 방식이 그대로다. web_server.py 비대화와 무관.

- 운영상 위험:
    · 폐쇄망 배포 특성상 버전 교체는 오프라인 휠 재배포를 동반한다. 롤백은 이전 휠 보관으로 대응 가능.
    · 진짜 위험은 업그레이드 자체가 아니라 **5장의 버전 핀 부재**다. 핀이 없으면 이번에 30.14.0 으로
      맞춰도 다음 설치 시점에 또 달라진다. 업그레이드를 하든 안 하든 핀 고정이 선행되어야 한다.

- 권장 대응책 (우선순위 순, 전부 별도 작업 — 이번 지침 범위 밖):
    1) requirements.txt 버전 핀 고정 (`sqlglot==30.14.0` 등). 5장 문제의 유일한 해법이며 가장 싸다.
    2) sqlglot 30.14.0 으로 상향 + 전수 회귀 1회. 위험도 낮음, 이득은 hang 제거 + 오라클 문법 3종.
       1)과 함께 한 번에 처리하는 게 효율적이다.
    3) 상향 여부와 무관한 방어 — `get_sql_parser().parse()` 진입점에 파싱 타임아웃 가드.
       버전을 올려도 다른 형태의 파서 무한루프가 재발하지 않는다는 보장은 없고, 폐쇄망 고객사가
       구버전으로 설치할 가능성(5장)도 남는다. 서버가 사용자 입력 SQL 을 파싱하는 구조인 이상
       "파서는 반드시 유한 시간에 돌아온다"를 코드로 강제하는 편이 안전하다.
    4) 오라클 방언 hang 회귀 테스트 추가(자식 프로세스 + 타임아웃). 3장 방식 그대로 재사용 가능.

- 지금 구현 여부: **보류(문서화 우선)**
    이번 지침이 "조사만" 으로 명시했으므로 코드·requirements 는 일절 건드리지 않았다.
    위 1)~4)는 각각 별도 작업으로 승인받아 진행할 사안이다.
