■ 추가된 상수/기준
- config/model_config.py : GENERAL_COLUMN_MAX_GROUPS = 60 (env MV_GENERAL_COLUMN_MAX_GROUPS)
  + get_general_column_max_groups(override) — 테스트 주입용(하드코딩 금지)
- 위치 근거 : 날짜버킷 DATE_BUCKET_MAX_GROUPS(60) 바로 옆. 같은 '자동추천 실용 상한' 축이며,
  실행 안전 상한 INTERACTIVE_GROUPBY_MAX_GROUPS(10만)과는 별개 축임을 주석에 명시.
- 기본값 60은 날짜버킷과의 일관성으로 시작(요청대로). 실측 근거는 아래 '적정선 재검토' 참고.

■ 판정 로직 변경
1) services/candidate_recommendation_policy.py `_gate_verdict` (GROUP_BY 완전배제 단일 관문)
   기존 : distinct_ratio >= 0.9 → EXCLUDED
   추가 : OR distinct_count > GENERAL_COLUMN_MAX_GROUPS → EXCLUDED
   - 둘 중 하나만 걸려도 배제(요청대로 OR). 비율 기준을 먼저 판정해 기존 사유 문구 보존.
   - 판정값은 계약에 이미 확정된 distinct_count(=resolved_distinct)를 그대로 재사용(새 계산 없음).
   - 이 gate 는 analyze / facade / postcount 3경로 공통 최종 권위이므로,
     metadata 경로(n_distinct 후보)와 semantic 경로(DIMENSION_*) 모두 자동 적용됨(항목 4 확인 완료).
2) 사유 문구 구분(항목 3)
   - 비율 기준 : "고유값 비율 과도(사실상 식별자) — 자동추천 제외(§22)"  (기존 유지)
   - 절대수 기준 : "그룹 개수 과다(N개 > 상한 M개) — 집계 의미 없음"      (신규)
   - ui/tabler_renderer.py : 배제 사유 표시를 서버 계약(exclusion_reasons)에서 그대로 노출.
     임계값을 JS 에 중복 정의/재판정하지 않음(표시 전용, 판정·체크박스 불변).
     날짜형 분기보다 먼저 판정 — 그렇지 않으면 C_TS3 사유가 '기간 변환 필요'로 표시되어 모순.
3) 날짜 후보 취급(중요 설계 판단)
   - 비율 기준과 동일하게 '예외를 두지 않음'. (실측상 TIMESTAMP 인 C_TS/C_TS6 도 이미 비율 기준으로
     이 gate 에서 배제되고 있어, 날짜만 면제하면 오히려 비일관.)
   - 기간 변환이 가능한 날짜는 이후 date_bucket enrich 가 '제외' 계열 표식을 비워 되살림(기존 구제 경로 재사용).
     변환해도 그룹 축이 못 되는 날짜만 배제로 남음.
   - services/single_validation_analyze_service.py : analyze 단계는 bucket profile 이 아직 없어
     변환 적합성을 판정할 수 없으므로, '그룹 개수 과다' 사유 단독인 날짜 참고후보는 원래 상태(참고후보)로
     되돌린다. 최종 판정은 bucket profile 이 수집되는 3단계 postcount 가 담당.
     비율/PK 사유가 함께 걸린 배제는 종전대로 유지(회귀 없음).

■ 근본원인(실측으로 확인한 구조적 틈)

  영원히 None → 날짜버킷 상한(60)이 적용될 기회 자체가 없음.
→ 동시에 비율은 34.56% 라 비율 기준(0.9)에도 안 걸림.
결과적으로 두 상한 사이로 빠져 '선택가능'으로 남아 있었음. 이번 절대 그룹수 상한이 이 틈을 막음.

■ 비판적 검토 / 남은 리스크
1) 상한 60은 일반 컬럼에는 공격적일 수 있음(요청서도 재검토 여지를 명시).
   실측 참고 : 이번 테이블의 C_CHAR(1,000)·C_NVARCHAR2(5,000)는 이미 엔진 고카디널리티 규칙으로
   배제되고 있어 이번 상한의 추가 영향은 없었음. 그러나 지역코드/상품분류처럼 60~수백 그룹의
   정상 차원 컬럼이 있는 스키마에서는 이 상한이 정상 후보를 배제할 수 있음.
   → 코드 수정 없이 MV_GENERAL_COLUMN_MAX_GROUPS 로 조정 가능하게 해 둠. 운영 데이터로 분포 확인 후
     상향(예: 200~500) 검토 권장.
2) 상한 초과는 '완전배제(체크 불가)'라 사용자가 수동으로도 선택할 수 없음(요청대로 완전배제).
   대화형 대조 목적상 타당하나, 드릴다운 축으로 일부러 쓰고 싶은 경우의 우회 수단은 env 조정뿐임.
3) analyze 단계와 3단계의 날짜 후보 표시가 다를 수 있음(analyze=참고후보, 3단계=최종 판정).
   이는 bucket profile 수집 시점 차이에 따른 기존 구조를 따른 것이며, 사용자 결정 화면인
   3단계 판정은 정확함을 라이브로 확인함.
