■ 새 타임아웃 메커니즘은 만들지 않았다(지시대로 기존 것 재사용)

그래서 **타임아웃 로직은 손대지 않고** 인자 수용 범위만 넓혔다:

  - _guarded_call(...)  : 두 래퍼가 캐시/타임아웃 정책을 공유하도록 분리한 공통 경로

■ 실측 중 새로 확인한 사실 — hang 발동 조건
나머지 20경로는 같은 재현 SQL 에서 hang 하지 않고 5ms 만에 ParseError 를 냈다. 원인을 별도 실측으로
규명했다(oracle 방언, 동일 SQL):
    parse_one(sql, read='oracle')                        → ParseError 5ms
    parse_one(sql, dialect='oracle')                     → ParseError 5ms
    parse_one(sql, read='oracle', error_level=IGNORE)    → HANG(8초 초과)
    parse_one(sql, read='oracle', error_level=RAISE)     → HANG(8초 초과)
    parse_one(sql, read='postgres')                      → ParseError 6ms
  → **error_level 을 명시 전달할 때만** 무한루프에 빠진다(값은 무관). 방언 문제가 아니다.
  이 사실은 두 가지를 뜻한다:
    (a) 가드 래퍼가 error_level=None 일 때 인자를 전달하지 않도록 만든 설계가 옳았다(동작 보존).
    (b) error_level 을 넘기지 않는 20경로는 '이 SQL 로는' 재현되지 않을 뿐, 파서 루프 일반에
        안전하다는 보장이 아니다 → 그래서 ③ 강제 주입 모드로 폴백 동작을 따로 실증했다.

■ 설계안 — 제시된 [4] HMAC 서명을 채택하지 않았다
지시받은 방향은 "collected_at 을 서버 비밀키로 HMAC 서명해 위조를 검출"이다. 검토 결과 이 방향은
문제의 절반만 막는다:
  - 서명은 '시각 위조' 축만 막는다. 실제 게이트 우회는 distinct_count 를 낮추는 **값 위조**로도
    성립하며(TC-6 이 고정한 위험의 본체), 서명은 여기에 아무 영향이 없다.
  - 값까지 서명하려면 후보 pool 전체를 서명해 왕복시켜야 하고, 그러려면 UI 가 서명을 되돌려 보내도록
    클라이언트 배선을 전부 고쳐야 한다. 서명 누락 시 정상 실행이 강등되는 회귀 위험도 크다.

그래서 **왕복 자체를 없애는** 방식을 택했다. 위조를 검출하는 대신 위조가 성립하지 않게 만든다:
  1) /analyze 가 산출한 GROUP BY 후보 pool(profile_evidence 포함)을 서버가 workflow_token 에 보관한다
     (workflow_stage_guard.store_stage_artifact — stage_times 와 같은 저장소/같은 generation 규칙).
  2) 실행 안전 게이트는 토큰이 있으면 그 서버 원본을 **우선** 사용한다. 클라이언트가 보낸
     candidate_snapshot_full 은 토큰이 없을 때만 근거가 된다.
  3) 판정 계약에 근거 출처를 노출한다 — candidate_evidence_source(SERVER_TOKEN|CLIENT_PAYLOAD|NONE),
     candidate_evidence_trusted(bool).
이 방식이 서명보다 강한 이유: 판정 근거가 클라이언트를 거치지 않으므로 서명 검증 없이도 조작이
불가능하고, 클라이언트(UI) 수정이 **전혀 필요 없다**(workflow_token 은 이미 요청에 실려 온다 —
S15 의 SERVER_TOKEN 시각 우선 채택이 쓰는 채널을 그대로 확장했다).

■ [5] 서버측 재검증 — 옵트인 골격만 제공(기본 OFF)
"클라이언트 distinct_count 를 표본 재조회로 교차검증"은 이미 존재하는 EXPLAIN 강등 축과 사실상
같은 일을 한다(실 DB 에서 예상 그룹 수를 다시 확인). 새 재조회 경로를 만드는 대신 기존 축을 썼다:
  config: GROUPBY_REQUIRE_TRUSTED_EVIDENCE (env MV_GROUPBY_REQUIRE_TRUSTED_EVIDENCE, 기본 0=OFF)
  동작  : 켜면 근거 출처가 CLIENT_PAYLOAD 일 때 explain_required 로 강등(EXPLAIN 근거 없으면 차단).
기본 OFF 로 둔 근거: 토큰을 동반하지 않는 정상 경로(일괄검증 등)가 전부 EXPLAIN 필수가 되고,
EXPLAIN 을 얻지 못하는 환경에서는 실행이 통째로 차단된다 — 운영 영향이 커서 기본값으로 켤 수 없다.
