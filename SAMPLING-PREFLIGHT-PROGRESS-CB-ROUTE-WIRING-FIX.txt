3. 구조 검토(비판적 검토 의무)
────────────────────────────────────────────────────────────────────────
- 긍정적 효과: 표본 구간이 UI 에서 '멈춘 것처럼' 보이던 구간에 실제 진행 시각이 남는다
  (/jobs/active 의 progress_signal·stall_basis 가 started_at → last_progress_at 으로 전환).
- 구조 부채: 새 메커니즘/새 엔드포인트/새 상태를 만들지 않았다. 페이로드 키 규약이 chunk 경로와 같아
  기존 `rj.update_progress` 소비자를 그대로 쓴다. web_server.py 무변경.
- 위험: 콜백이 예외를 던지면 게이트가 깨질 수 있다 → 엔진 `_emit_progress` 가 모든 예외를 삼키므로(관측 전용)
  판정 경로에 영향이 없다. 이번 실측에서도 Before/After 판정이 완전히 동일함을 4절에서 확인했다.
- heuristic/scoring: 추가 없음. explainability: 진행 시각·처리 anchor 수가 API 응답에 남는다(오히려 개선).
- 남는 한계(정직 고지): 신호 촘촘함은 '표본 단계 단위'가 상한이다. 확장 단계 내부는 batch 쿼리 1회라
  단계 중간에는 신호가 없다 — 아래 4-2 After 케이스에서 t=30.29s 의 stall_seconds 가 24.9 로 찍히는 이유다
  (선행 보고서 §7-(b)와 동일 항목, 이번 범위 밖).
