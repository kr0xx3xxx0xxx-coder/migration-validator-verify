작업명 : RESULT-GROUP-LIMIT-PRECHECK-FIX
✅ 작업 완료 - RESULT-GROUP-LIMIT-PRECHECK-FIX - 결과 그룹 상한 초과를 통계 SELECT 발행 전에 차단하도록 실행 core 에 사전 판정을 넣어, 재현 케이스가 58,308ms 소모 후 사후차단에서 170~214ms 즉시 사전차단으로 바뀌었다. 기존 사후 안전망은 그대로 유지(이중 방어)하며, 정상 케이스는 무회귀다.

════════════════════════════════════════════════════════════════════════
1. 요청 요약 · 결론
════════════════════════════════════════════════════════════════════════
요청: 백로그 P15 — 결과 그룹이 허용 한도(100,000)를 넘는 케이스가 56,255ms 를 전부 소모한 뒤에야
      BLOCKED 된다. F31(가중치 재조정) 완료로 카디널리티가 프로필에 실렸으니 이를 이용해 실행 전에
      예상 그룹 수를 추정하고 사전 차단할 것. 사후차단(안전망)은 유지(이중 방어).

결론: 사전 차단을 실행 core(stats_execute_service.execute_stats_validation) 진입 직후 · 통계 SELECT
      발행 전에 넣었다. 새 추정식을 만들지 않고 기존 계산을 그대로 재사용한다.
        ① 요청이 실어 온 GROUP BY 후보 distinct → estimate_groupby_count 조합 판정(추가 DB 조회 0회)
        ② 근거가 없으면 실제 실행될 SQL 의 EXPLAIN 산정(ANALYZE 미사용 · 결과 1행)
      한도 초과가 확실할 때만 차단하고, 근거 없음/산정 실패/접속대상 불명은 차단하지 않고 진행한다.
      사후 결과 수신 상한(cap+1) 차단은 불변 — 사전은 '빠른 차단'이지 '유일한 차단'이 아니다.

2. 진단 — 왜 56초를 다 쓰고 나서 막혔나 (착수 전 사실 확인)

[2-2] 사후 상한의 구조상 비용
  stats_execute_service 는 GROUP BY 계획일 때 cap+1 행까지 받아오고(row_cap), 한쪽이라도 초과하면
  비교 없이 BLOCKED 한다. 행 전송은 100,001 행에서 끊기지만 **DB 의 그룹 집계 자체는 1,000만 그룹을
  전부 만든 뒤**라서, 차단이 확정될 때는 이미 비용을 다 치른 상태다.

[2-3] 요청 1항의 전제 정정(중요)
  F31(9514e2d)이 실은 카디널리티는 **화면 → 규모등급(전략 계획기) 프로파일**의 group_cardinalities 다.
  ExecuteRequest 에는 이 필드가 없다(schemas/request_models.py). 실행 경로에서 같은 의미의 근거는
  candidate_snapshot_full 의 후보 distinct 이고, 이것이 이미 안전 게이트의 '우선순위 1' 입력이다.
  → 그래서 새 필드를 신설하지 않고 그 근거와 그 계산(estimate_groupby_count)을 그대로 재사용했다.
  (F31 문서가 명시했듯 화면 distinct 는 상한 추정이라 과대추정 위험이 있다 — 4-2 의 오차단 방지 정책 참조)

4. 설계 판단 · 위험과 대응 (비판적 검토)
════════════════════════════════════════════════════════════════════════
[4-1] 한도 축을 분리했다 — 사전은 INTERACTIVE_GROUPBY_MAX_GROUPS, 사후는 MV_STATISTICS_RESULT_LIMIT
  후자는 주석이 명시하듯 "사전 차단이 아니라 실제 결과 수신 상한 경로를 타게 하기 위한" 검수 스위치다.
  사전 판정이 이 값을 읽으면, 그 스위치로 사후 경로를 재현하던 기존 테스트/검수가 전부 사전 차단에
  가로채여 **검증하려던 경로가 사라진다**. 그래서 사전은 중앙 사전 한도만 본다.

[4-2] 오차단(false block) 방지 — 안전계수를 적용하지 않는다
  게이트는 추정값에 ×2.0 안전계수를 적용한다(정책 판정). 사전 판정은 부가 방어선이므로 계수 없이
  raw 추정이 실제로 한도를 넘을 때만 차단한다 — 즉 **게이트보다 보수적으로 막지 않는다**.
  근거 없음/EXPLAIN 실패/미지원 방언/접속대상 불명은 전부 '진행'이다. 화면이 보내는 distinct 가
  상한 추정(F31 §5-2)이라는 한계는 그대로지만, 한계가 커지는 방향(과대추정→오차단)은 사후 안전망이
  아니라 사용자 손실이므로 위 정책으로 최소화했다.

[4-3] 새로 붙는 DB 왕복 — 실측 124~230ms, 그리고 그 비용을 제한한 방법
  게이트 미경유 경로(일괄·진단·core 직접)에서 구조화 근거가 없으면 EXPLAIN 왕복 1회가 새로 생긴다.
  실측 124~230ms(내부망 PG · 원본/목적지 각 1회 · 접속 포함). 25초짜리 정상 실행 대비 0.5~0.9%.
  다만 **DB 가 죽어 있으면** 이 왕복이 접속 타임아웃만큼 대기를 늘린다. 그래서
    · 접속 대상을 특정할 수 없는 요청(host/dsn/service 없음)은 probe 자체를 시도하지 않고,
    · probe 접속 대기를 안전 예산 5초로 상한하고,
    · bind parameter(%s)가 실린 SQL(진단 GROUP_SCOPE)은 값 없이 EXPLAIN 이 반드시 실패하므로 즉시 포기한다.
  이 가드가 없을 때의 실제 피해를 측정했다: tests/test_statistics_execution_safety.py 가
  2.88초 → 27.53초(+24.6초)로 늘어났고, 가드 적용 후 3.17초로 복귀했다(잔여 +0.29초).

[4-4] 게이트 경유 경로는 사전 판정을 건너뛴다 — 의미와 부작용
  중복 판정/중복 EXPLAIN 을 막기 위함이다. 부작용: 안전 게이트를 꺼 둔(gate_enabled=false) 운영에서는
  개별검증 경로에 사전 차단이 없다(사후 안전망만). 게이트 비활성은 명시적 opt-out 이므로 그대로 뒀다.

[4-5] heuristic / scoring / explainability 영향
  · heuristic 추가 없음 — 판정식은 기존 estimate_groupby_count / groupby_explain_estimator 재사용.
  · scoring 영향 없음 — 후보 추천 점수·선정 정책 불변.
  · explainability 강화 — 차단 응답에 estimated_group_count · estimate_kind · estimate_source ·
    configured_limit · post_execution(사전/사후) 을 남긴다. 종전 사후 차단은 "실제 그룹 수를 알 수 없어"
    수치를 남기지 못했다.
  · 보안 영향 없음 — 접속정보 로그/응답 노출 없음(pre-commit 비밀번호 스캔 통과).

[4-6] 미해결로 남긴 것(고지)
  · 사전 차단은 '그룹 수' 축만 본다. 스캔량이 커서 오래 걸리는 계획(그룹 수는 적음)은 여전히 끝까지 간다.
  · 진단 드릴다운(bind param 경로)은 구조화 근거가 없으면 사전 판정이 성립하지 않는다(설계상 진행).
  · 화면 distinct 의 날짜축 과대추정(F31 §5-2 한계)은 이번 범위 밖이다.
