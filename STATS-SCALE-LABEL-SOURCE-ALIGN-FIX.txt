3. F35 — 두 출처 값이 실제로 다를 수 있는가 (요구사항: 조건 명시)
────────────────────────────────────────────────────────────────────────
결론: 현재 코드 경로에서는 두 값이 다를 수 없다. 같은 profile 하나로 두 계획기가 각각
      동일한 식을 유도하기 때문이다.

  services/strategy/stats_strategy_planner.py:47
    scan = profile.estimated_scan_rows if profile.estimated_scan_rows is not None
           else profile.source_count
    → basis["estimated_scan_rows"] → StatsStrategyPlan.estimated_scan_rows (134행)

  services/strategy/full_compare_strategy_planner.py:102
    expected_scan_rows = (profile.estimated_scan_rows if profile.estimated_scan_rows is not None
                          else profile.source_count)

  routes/strategy_route.py:52-55 이 같은 profile 객체를 두 계획기에 넘기며, 각 계획기는
  단일 return 경로만 갖는다(조기 반환 없음). 이후 transition 보정(58-73)도
  compare_strategy_id/reason_codes/implementation_status 만 바꾸고 스캔값은 건드리지 않는다.

실측(하니스 ①, planner 직접 호출) — 차이를 노린 프로파일까지 넣어 확인

  프로파일                       입력                        stats_plan   full_compare_plan  일치
  ---------------------------------------------------------------------------------------------
  A_SMALL          scan=5000,      count=5000                5,000        5,000              동일
  B_42M            scan=42000000,  count=42000000            42,000,000   42,000,000         동일
  C_SCAN_NONE      scan=None,      count=777000              777,000      777,000            동일
  D_SCAN_NE_COUNT  scan=250000,    count=1000000             250,000      250,000            동일

  · C_SCAN_NONE(스캔 미지정 → source_count 폴백), D_SCAN_NE_COUNT(스캔 ≠ 건수) 처럼
    두 값이 갈릴 만한 입력을 넣어도 결과는 동일하다.
  · 값이 달라지는 조건은 "두 계획기 중 한쪽만 profile.estimated_scan_rows 유도식을
    바꾸는 변경이 생길 때" 뿐이다. 즉 지금은 무회귀이고, 앞으로 통계검증 쪽 스캔량이
    별도 추정(WHERE 선택도·파티션 프루닝 등)으로 분화되면 그때부터 두 값이 갈리며,
    이번 정렬 덕분에 '통계검증 규모' 타일은 통계검증 쪽 값을 따라가게 된다.

  참고: 이 값의 실제 출처는 ui/grid_helpers.py:1181 의 프로파일 조립이다.
        estimated_scan_rows = count.src_count (2단계 COUNT 결과 그대로) — F30 의
        "'예상'이 아니라 실측" 근거가 여기다.
