✅ 작업 완료 - LARGE-TABLE-STATS-EXECUTION-PERFORMANCE-DIAGNOSE-AND-OPTIMIZE - 병목은 순수 DB 스캔 시간(앱 0.8~2.5%)이고 (a) 병렬힌트는 개발 인스턴스가 병렬 미지원(Parallel execution=FALSE)이라 개선폭 0% — 실측된 유일한 큰 레버는 세트 병렬 -41~55%(승인 필요)

0. 요약 — 무엇을 알아냈고 무엇을 했는가
===============================================================================
지침대로 1단계(진단) → 2단계(a 구현)를 순서대로 수행했다. 결론을 먼저 적는다.

  (1) 병목은 애플리케이션이 아니라 **DB 안에서 데이터를 읽는 시간** 그 자체다.
      COUNT 사전검증의 앱 성분은 0.8%, 통계검증 2축의 앱 성분은 2.5%에 불과하다.
      네트워크 왕복(1.8ms)·결과 페치(2ms)는 병목이 아니다 — 지침 1단계 1의 4개 축 중
      3개(네트워크·페치·앱)가 모두 무죄로 판명됐다.

  (2) 지침이 (a)로 지목한 병렬 쿼리 힌트는 **이 검증 환경에서 개선폭이 0%** 다.
      개발 검증용 오라클이 Oracle Free 23ai 이고, 이 에디션은 병렬 실행 옵션 자체가 없다
      (v$option: Parallel execution = FALSE, parallel_max_servers = 1).
      힌트를 붙여도 옵티마이저가 **Unused 로 버린다** — 추측이 아니라 오라클이 EXPLAIN PLAN
      Hint Report 에 `U - PARALLEL(4)` 로 직접 출력한 사실이다(§2-4에 원문 첨부).

  (3) 그럼에도 (a)는 지침대로 구현했다. 다만 **인스턴스가 병렬을 실제로 지원할 때만**
      힌트를 붙이도록 게이트를 걸었다. 그 결과 이 인스턴스에서는 실행 SQL 이 1자도 바뀌지
      않아(무회귀가 문자열 동일성으로 증명된다) 리스크 없이 병합할 수 있고, 병렬이 가능한
      고객사 운영 오라클(EE)에서는 임계치 초과 테이블에 자동으로 적용된다.

  (4) 실측으로 확인된 **실질적인 개선 레버는 (a)가 아니라 순차 실행 구조**다.
      같은 SQL·같은 결과인데도 세트 병렬만으로 통계검증 2축이 20.4초 → 12.0초(-41.2%),
      다른 회차에서는 22.2초 → 10.0초(-55.2%)로 줄었다. 이건 (b)에 해당하므로 지침에 따라
      **구현하지 않고 근거만 제시**한다(§4). 승인 시 별도 지침으로 진행하겠다.

  ⚠ 지침의 목표 문구("18.65초 → 개선폭 명시")를 이번 (a)로는 만족시키지 못했다.
     원인은 구현 품질이 아니라 검증 환경의 DB 에디션 제약이며, 그 사실 자체가 1순위
     보고 대상이라고 판단해 우회하거나 숨기지 않고 그대로 적는다.

  애플리케이션(파싱/비교/직렬화)    141.3ms  (0.8%)      547.7ms (2.5%)    아니오
  ────────────────────────────────────────────────────────────────────────────
  구조적 증폭 요인             원본→목적지 순차      축마다 재스캔 +      ★ 예
                                                    측면(src/tgt) 순차

  한 줄 결론: **읽어야 할 데이터량 자체가 크고(3GB×N), 그것을 순차로 여러 번 읽는다.**
  SQL 튜닝(계획 변경)의 여지는 이미 옵티마이저가 다 써버렸고(COUNT=INDEX FFS), 남은 여지는

3. 2단계 (a) — 오라클 병렬 쿼리 힌트 조건부 적용 (구현 + 실측)

─────────────────────────────────────────────────────────────────────────────
3-1. 구현 내용
─────────────────────────────────────────────────────────────────────────────
■ 신설: services/dialects/oracle/parallel_hint.py  (오라클 전용 — 어댑터 패턴 준수)

  지침의 "오라클 전용 로직 분리" 요구에 따라 방언 분기를 공용 파일에 넣지 않고, 이미 존재하는
  오라클 dialect 패키지(services/dialects/oracle/) 안에 독립 모듈로 뒀다. PostgreSQL/MySQL/
  MSSQL 코드는 한 줄도 건드리지 않았다.

  게이트(전부 충족해야만 힌트 부여, 하나라도 불충족이면 **입력 SQL 을 문자 그대로 반환**):
    1) 기능 플래그가 off 가 아닐 것              MV_ORACLE_PARALLEL_HINT (기본 auto)
    2) db_type 이 오라클 계열일 것                (그 외는 not_oracle 로 즉시 반환)
    3) 최상위가 SELECT 이고 기존 힌트가 없을 것   (남의 힌트를 덮지 않음, WITH/CTE 제외)
    4) 인스턴스가 병렬 실행을 실제로 지원할 것    v$option + parallel_max_servers ≥ 2
    5) 대상 테이블 추정 행수 ≥ 임계치             MV_ORACLE_PARALLEL_MIN_ROWS (기본 1,000,000)

  DOP 는 하드코딩하지 않았다 — 기본 4 + MV_ORACLE_PARALLEL_DOP 로 조절(지침 요구사항).
  임계치도 동일하게 환경변수로 조절 가능하다.

  게이트 (4)를 추가한 이유(지침에 없던 판단):
    지침의 (a)안 그대로 '행수 임계치만' 보고 힌트를 붙이면, 이 검증 환경처럼 병렬을 지원하지
    않는 인스턴스에서 **이득 0인데 SQL 문자열만 달라진다.** 화면에 표시되는 SQL, 진단 로그,
    저장 스냅샷이 전부 흔들리면서 얻는 게 없다. 그래서 '쓸 수 있을 때만 붙인다'로 좁혔다.
    이 판단 덕분에 이번 변경은 현 환경에서 **완전 무변경**이 되어 리스크 없이 병합 가능하다.

  판단 근거 보존(explainability): 적용/미적용과 사유를 evidence dict 로 반환해 진단 로그로
  남긴다(applied/reason/dop/estimated_rows/parallel_supported/tables). CLAUDE.md 의
  "explainability 누락(근거 미저장)" 항목을 의식한 설계다.

  비용: (4) 인스턴스 옵션과 (5) 추정 행수는 엔드포인트 단위로 1회 조회 후 프로세스 수명 동안
  캐시한다. 매 쿼리마다 왕복이 붙지 않음을 단위 테스트로 못박았다.

■ 배선: services/db_query_service.py (+34줄, 기존 로직 삭제/변경 0)
    _cmn_db_fetch_count          → COUNT 사전검증(2단계) 실행 직전
    cmn_db_fetch_select_readonly → 통계검증 GROUP BY(4단계) 실행 직전, oracle 분기 안에서만

  통계검증 쪽은 힌트가 붙은 최종 SQL 을 **다시 단일 SELECT 가드에 통과**시킨다. '검사한 SQL 과
  실행하는 SQL 이 같다'는 성질을 유지하기 위함이며, 만에 하나 통과하지 못하면 힌트를 버리고
  원본으로 실행한다(안전측 폴백). 힌트 부여 자체가 실패해도 원본 SQL 로 실행한다 —
  성능 최적화가 쿼리 실행을 막아서는 안 되기 때문이다.

3-2. 적용 전/후 실측 (지침 '실측 검증' 필수 항목)
─────────────────────────────────────────────────────────────────────────────
■ 게이트 판정 결과 — 이 인스턴스에서는 항상 미적용

  상황                       적용   사유                            SQL 무변경
  ────────────────────────────────────────────────────────────────────────────
  대형 COUNT(50,000,000행)   False  instance_parallel_unavailable      True
  대형 GROUP BY(50,000,000행) False  instance_parallel_unavailable      True
  소규모 COUNT(300행)         False  instance_parallel_unavailable      True
  비-oracle(postgresql)      False  not_oracle                         True

■ 운영 경로를 실제로 통과시켰을 때 DB 로 나간 SQL (실행 직전 문자열을 가로채 확인)

  경로                                    실행 SQL 이 입력과 동일한가
  ─────────────────────────────────────────────────────────────────────
  _cmn_db_fetch_count(COUNT 50M)                    True (무변경)
  cmn_db_fetch_select_readonly(GROUP BY 50M)        True (무변경)
  결과: COUNT = 50,000,000 · 통계 그룹 21행 (정상)

  → **개선폭: 0%.** 이 인스턴스에서는 SQL 이 바뀌지 않으므로 소요시간도 바뀔 수 없다.
    지침의 "18.65초 → 개선폭 명시" 요구에 대한 정직한 답은 "0초 단축(적용 조건 미충족)"이다.

■ 힌트 강제 부여 대조 실행 — 힌트가 붙은 SQL 자체의 정상성·결과 동일성 검증

  게이트가 항상 미적용이면 '힌트가 붙은 SQL 이 실 DB 에서 올바르게 동작하는가'를 검증할 수
  없다. 그래서 가용성 캐시에 지원=True 를 주입해 강제로 힌트를 붙인 SQL 을 실 오라클에 던졌다.

  대상                    before(힌트 없음)   after(힌트 있음)   배율    결과값 동일
  ────────────────────────────────────────────────────────────────────────────
  COUNT(50M)  중앙값         1,437.5ms         1,384.8ms       x1.038      ✅
    개별 run                12257.3/1437.5/     1624.8/1384.8/
                             1401.4ms           1346.5ms
  GROUP BY(50M) 중앙값       3,853.5ms         3,686.6ms       x1.045      ✅
    개별 run                 5059.1/3853.5/     3517.2/3686.6/
                             3444.0ms           3915.6ms

  → x1.03~x1.05 는 캐시 노이즈 범위다(같은 SQL 반복만으로도 1.4~12.3초 편차가 난다).
    계획에 PX 가 없으므로 병렬은 발동하지 않았고, 힌트는 무시됐다. 즉 **의미 있는 개선 없음.**
  → 대신 확인된 것: 생성된 힌트 SQL 이 오라클에서 **구문 오류 없이 정상 실행**되고,
    **결과값이 완전히 동일**하다. 병렬 가능한 인스턴스로 옮겼을 때 안전하다는 근거다.

  생성된 SQL 예시(첫 줄만):
    COUNT   : SELECT /*+ PARALLEL(4) */ COUNT(*) AS CNT
    GROUP BY: SELECT /*+ PARALLEL(4) */

(b) 세트 병렬 실행(_stats_set_parallelism) 기본값 조정  ★ 실측 효과 1순위
─────────────────────────────────────────────────────────────────────────────
  근거   : 5,000만행 2축 통계검증이 22.2초→10.0초(-55.2%), 20.4초→12.0초(-41.2%).
           결과값은 순차와 완전 동일(§3-3). 소규모(1,200행)에서 효과가 안 보였던 것은
           규모 문제였고, 대규모에서는 이번 진단의 최대 레버다.
  제안   : 전면 기본 ON 이 아니라 **대규모 조건부 ON**. 예: 대상 테이블 추정 행수가
           임계치(예 100만) 이상이고 기존 조건(다른 물리 DB·풀 여유)을 만족할 때만 level 2.
           소규모는 지금처럼 순차 유지 — 오늘 벤치 결론(클릭→5탭 <15%)을 뒤집지 않는다.
  위험   : DB 커넥션을 동시에 2개 쓴다. 확인 필요 사항 —
           · 커넥션 풀 여유(현재 판정은 POOL_MAX_IDLE_PER_KEY ≥ 2 만 본다)
           · 오라클은 풀링을 우회해 checkout 마다 물리 연결을 새로 만든다
             (services/db_adapters/oracle.py 주석) → 동시 세션 2개가 DB 쪽 부하가 된다
           · 세트 실패 시 형제 세트 처리(현 구현은 중도취소 없이 완료시킴 — 그대로가 안전)
  판단   : **승인 필요.** 정책 변경이라 지침대로 이번에 기본값을 바꾸지 않았다.

─────────────────────────────────────────────────────────────────────────────
(c-1) 원본/목적지 COUNT 순차 → 병렬  ★ 미구현, 효과 큼
─────────────────────────────────────────────────────────────────────────────
  사실   : services/count_common_service.run_count_pair 는 원본 COUNT 완료 후 목적지 COUNT 를
           실행한다(순차). 두 COUNT 는 서로 다른 물리 DB 를 보므로 의존관계가 없다.
  효과   : run1 기준 원본 13.9초 + 목적지 3.2초 = 17.1초가 병렬이면 max(13.9, 3.2) ≈ 13.9초.
           양쪽이 비슷한 회차(run2: 4.6+4.7초)면 9.3초 → 4.7초로 거의 반감된다.
  위험   : 원본 오류 시 목적지 미실행이라는 현 동작이 바뀐다(둘 다 실행됨). 오류 보고 순서를
           지금처럼 '원본 우선'으로 유지하면 사용자 체감은 동일하게 만들 수 있다.
           통계검증 쪽에는 이미 같은 개념의 스위치(parallel_sides)가 있으므로 새 개념이 아니다.
  판단   : **승인 필요.**

─────────────────────────────────────────────────────────────────────────────
(c-2) 통계검증 src/tgt 병렬(parallel_sides) 기본값 검토 — 실측했으나 효과 애매
─────────────────────────────────────────────────────────────────────────────

  원인   : 양쪽을 동시에 돌리면 개별 쿼리 시간이 늘어난다(1회차 src 4,930→7,977ms).
           같은 물리 호스트(192.168.0.151)에 두 인스턴스가 올라가 있어 디스크 I/O 를 공유하기
           때문으로 보인다. 고객사처럼 원본/목적지가 물리적으로 분리된 환경에서는 더 나을 수 있다.
  판단   : 세트 병렬(b)보다 효과가 불안정하다. **(b) 를 먼저 적용하고 (c-2)는 그 다음에
           재측정**하는 순서를 권한다. 승인 필요.

─────────────────────────────────────────────────────────────────────────────
(c-3) 통계정보 stale / fetch 비효율 — 해당 없음(조치 불필요)
─────────────────────────────────────────────────────────────────────────────
  통계정보는 최신이고(§2-3) stale_stats=NO, 추정 행수도 실제와 일치한다.
  fetch 는 전체의 0.04% 미만이다(§2-1). 지침이 후보로 든 이 두 가설은 **기각**한다.

─────────────────────────────────────────────────────────────────────────────
(c-4) 다축 통계검증의 반복 풀스캔 — 구조적 개선 여지(장기)
─────────────────────────────────────────────────────────────────────────────
  사실   : 2축이면 같은 3GB 테이블을 2번 통째로 읽는다(§2-2). 축 수에 비례해 스캔량이 늘어난다.
  아이디어: GROUPING SETS 로 한 번의 스캔에서 축별 집계를 동시에 얻으면 스캔을 1회로 줄일 수 있다.
  위험   : 결과 shape 가 크게 바뀌고(집계 행에 NULL 축이 섞임), 세트별 result_id·저장·화면 렌더가
           전부 세트 단위로 짜여 있어 파급이 매우 크다. 정합성 리스크 대비 이득이 불확실하다.
  판단   : **지금 권하지 않는다.** (b)로 얻는 -41~55% 를 먼저 취하고, 그래도 부족할 때
           별도 설계 검토 대상으로 남긴다.
