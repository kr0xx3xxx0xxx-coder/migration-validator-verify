   후 백그라운드 스트리밍이 25만행을 스캔(fresh 371s). pk-records 는 저장분을 즉시 반환.

2) 같은 세션 서로 다른 그룹 연속 드릴다운 → 매번 재계산? 아니면 최초 1회만 느림?
   → 최초 1회만 느림(스캔). 이후 그룹 드릴다운은 91~117ms 로 균일하게 즉시 응답(재계산 없음).
     프론트 _mvPkState 가 prepare 응답을 캐시하므로 2번째부터는 prepare 호출조차 없다.

3) 새로고침/새 세션 재사용?
   - 새로고침: window._mvPkState 는 페이지 리셋되나 서버 fingerprint 잡이 같은 프로세스에 생존 →
     첫 드릴다운의 prepare 가 reused=True 로 즉시 반환(재스캔 0). 서버 '재시작' 시에만 재계산.
   - 새 세션: fingerprint 에 session_id 가 없어 다른 세션도 같은 잡 재사용. 실측 ⑧ 에서 다른
     session_id 로 prepare 시 reused=True · same_run=True(동일 run_id) 확인.

4) 캐시 저장위치/스코프/TTL/무효화
   - 저장위치: 잡·_PK_RUNS = 서버 메모리(in-memory, 프로세스 재시작 시 소실).
               결과 레코드 = 파일 SQLite db/exact_diff_runs.db(재시작 후에도 존재).
   - 스코프  : 테이블쌍 + 선택(연결좌표+SQL+key+sum+gb+plan_fp+sel_fp). 프로세스 전역, 세션/사용자 비종속.
   - 상한/축출: _JOBS_MAX=16(LRU, reimport_job.py:23,58~68), _PK_RUNS_MAX=32(초과 시 clear-all,
               agg_contribution.py:51,347~348,756~757). 시간 기반 TTL 없음.
   - 무효화  : __rec_v(레코드 구조 버전)·plan_fingerprint·selection_fingerprint 변경 시에만 새 run.
   - ★ stale 위험(실재): fingerprint 에 데이터 내용/watermark 가 없어, 동일 SQL·동일 연결·동일 선택으로
     원본/목적 데이터가 바뀌어도 같은 fingerprint 의 READY 캐시를 그대로 재사용할 수 있다.
     완화책은 드릴다운에 스냅샷 기준시각(exact_diff_run.created_at, KST 라벨) 노출뿐으로
     (agg_diff_route.py:975~980), '언제 기준 숫자인지'는 보여주나 자동 무효화는 하지 않는다.
     또한 잡/_PK_RUNS 는 서버 재시작 시 소실되고 fingerprint→run_id 역인덱스가 메모리 전용이라,
     재시작 후 기존 드릴다운은 '재이관 PK index 를 찾을 수 없습니다' 후 재-prepare(재계산)로 이어진다
     (reimport_job.py:346 주석 '후속 과제').

5) 캐시가 없다면 매 클릭 25만행 재계산인가 → 해당 없음(캐시 존재). 단 참고로 fresh 스캔은 약 6.2분이라,
   만약 재계산 구조였다면 클릭마다 6분대 부하가 반복됐을 것(현 구조는 이를 방지).
   동시 사용자: 같은 fingerprint 를 2명이 동시에 처음 열어도 중복 계산이 방지된다 — start_or_attach 가
   _LOCK 내부에서 기존 잡(PREPARING/READY)을 재확인해 연결하고, 비스트림 경로는 _PK_INFLIGHT 로 차단한다
   (reimport_job.py:75~88, agg_contribution.py:52,191~193). ⇒ '이론상 발생 가능'보다 강함(코드상 방지됨).
