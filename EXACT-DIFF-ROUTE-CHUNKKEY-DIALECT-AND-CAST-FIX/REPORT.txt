[1] 무엇을 고쳤나

ROUTES-DIAGNOSIS-LIMIT-DIALECT-SECONDARY-CHECK 가 P2 로 확정한 exact_diff_route.py
의 오라클 전용 차단 2건을 해소했다. 두 결함은 서로 독립이 아니라 SCOPE 모드에서
연쇄로 터진다 — 코드 순서상 scope 래핑(L177/178)이 먼저 일어나고, 그렇게 래핑된
SQL 을 그대로 받아 chunk key 를 확정(L179 → _resolve_key)하기 때문이다.

(1) chunk key 확정에 방언이 전달되지 않았다

    _resolve_key 는 resolve_confirmed_chunk_key 를 호출하면서 dialect 인자를
    넘기지 않았다. 이 함수의 기본값은 'postgres' 이므로, 오라클 접속이어도 후보
    재확인 probe 가 PostgreSQL 문법으로 렌더됐다.

    실측한 근본원인은 다음과 같다(null_probe_dialect_evidence.txt):

      dialect=postgres  -> SELECT 1 FROM ... WHERE SEQ_NO IS NULL LIMIT 1
      dialect=oracle    -> SELECT 1 FROM ... WHERE SEQ_NO IS NULL FETCH FIRST 1 ROWS ONLY

    오라클은 LIMIT 을 모른다(ORA-00933). 그런데 이 실패가 사용자에게 보이지
    않는다는 점이 더 중요하다. 실패 경로를 코드로 따라가면:

      _has_null 이 예외를 삼키고 None 반환 (key_evidence.py:101-102)
        → confirm_chunk_key 가 'sn is None or tn is None' 에서 None 반환 (:431-432)
        → resolve_confirmed_chunk_key 가 후보를 모두 소진하고 None
        → _resolve_key 가 ("", "") 반환
        → run_exact_diff 가 빈 키를 받아 HOLD

    즉 오라클에서는 PK 가 멀쩡히 있어도 "안정적인 키를 확인할 수 없습니다" 류의
    보류로 조용히 떨어졌고, 진짜 원인(문법 오류)은 어디에도 남지 않았다.

    수정은 배선만이다. 접속 db_type 을 공통 헬퍼(_to_sqlglot_dialect)로 sqlglot
    방언명으로 바꿔 전달한다. 매핑을 새로 만들지 않았고, resolve_confirmed_chunk_key
    내부 로직도 건드리지 않았다. diagnosis_route._routing_dialect(ROUTES-DIAGNOSIS-
    CONFIRM-ROUTING-DIALECT-DELEGATION-FIX)와 완전히 같은 도출 방식이라, 이미
    검증된 선례를 따라간 것이다.

    혼합 방언(원본≠목적)은 기존 동작(postgres)을 그대로 유지했다. 한쪽으로
    렌더하면 반대편 probe 가 반드시 실패하므로, 이번 수정의 영향 범위를 '동일
    방언'으로 한정하는 것이 안전하다. 이것도 선례와 동일한 판단이다.

(2) SCOPE 모드가 PG 전용 문법으로 고정돼 있었다

    scope pushdown 은 양측 논리 SELECT 를 서브쿼리로 감싸고 동등 조건을 거는데,
    그 표현이 `SELECT * FROM (...) __sf WHERE (col)::text = '값'` 으로 하드코딩돼
    있었다. 오라클에서 이 SQL 은 두 가지 이유로 실행 자체가 불가능하다:

      · `::text` — oracledb 드라이버가 `:text` 를 바인드 변수로 오인한다(DPY-4010)
      · `__sf`   — 비인용 식별자가 밑줄로 시작하면 ORA-00911

    캐스트는 _scope_eq_expr 로 분리해 지원 4개 방언을 모두 처리했다. 오라클 등가
    표현은 새로 발명하지 않고, 이미 실 오라클에서 검증된 exact_diff 어댑터
    (services/exact_diff/dialects/oracle.py 의 _txt: PG `(x)::text` ↔ Oracle
    `TO_CHAR((x))`)와 같은 균일 문자 정규화를 그대로 채택했다. 원본·목적 양쪽에
    같은 계열 캐스트가 걸리므로 비교는 대칭이다.

    별칭은 mv_scope_src / mv_scope_tgt 로 개명했다. 같은 파일의
    _derive_row_sqls_wrapped 가 이미 쓰고 있는 mv_reimport_src 규칙과 같은 계열이다.

[3] Before / After 실측

실 오라클/PG 로 실행하려 했으나 내부망이 전면 차단돼 있었다
(network_unreachable_evidence.txt):

  ora-asis      192.168.0.151:1523  TCP 타임아웃
  ora-tobe      192.168.0.151:1524  TCP 타임아웃
  pg-inter-asis 192.168.0.150:5433  TCP 타임아웃
  pg-inter-tobe 192.168.0.150:5434  TCP 타임아웃

그래서 이전 진단(ROUTES-DIAGNOSIS-LIMIT-DIALECT-SECONDARY-CHECK)과 같은 방식으로
대체했다. 라우트 함수를 실제로 실행하되 DB 왕복 2곳(resolve_confirmed_chunk_key ·
run_exact_diff)만 캡처 stub 으로 치환한다. 그 앞단의 SQL 렌더와 인자 배선은
운영과 완전히 동일한 코드 경로를 탄다. 측정 대상이 '만들어진 SQL 문자열'과
'전달된 dialect 값'이므로, 이 값들은 DB 접속 성공 여부와 무관하게 결정적이다.

Before 는 baseline worktree(HEAD=f54c957)에서, After 는 현재 트리에서 같은
harness 를 돌렸다(scripts/dev_e2e/exact_diff_route_dialect_cast_verify.py).

  ── 오라클 / SCOPE=ON ──
  Before:
    dialect 전달여부 : False  (미전달 → 기본 postgres)
    src_sql : SELECT * FROM (...) __sf WHERE (DEPT_CD)::text = 'A1''B'
    판정    : `::` 캐스트 잔존(DPY-4010) + 밑줄 선두 별칭 잔존(ORA-00911)
              chunk key 재확인이 오라클 방언으로 나가지 않음 → 조용한 HOLD
  After:
    dialect 전달여부 : True / 값 = oracle
    src_sql : SELECT * FROM (...) mv_scope_src WHERE TO_CHAR((DEPT_CD)) = 'A1''B'
    tgt_sql : SELECT * FROM (...) mv_scope_tgt WHERE TO_CHAR((DEPT_CD)) = 'A1''B'
    확정 key: SEQ_NO / SEQ_NO
    판정    : 오라클 실행 불가 패턴 없음 · chunk key 가 oracle 방언으로 위임됨

  따옴표 이스케이프(A1'B → 'A1''B')는 방언 분기 이후에도 그대로 유지된다.

  ── PostgreSQL / SCOPE=ON (회귀 확인) ──
  Before/After 모두: WHERE (DEPT_CD)::text = 'A1''B'
  술어 표현이 완전히 동일하다. 달라진 것은 인라인뷰 별칭(__sf → mv_scope_src)
  뿐이고, 이는 결과셋에 영향이 없는 내부 별칭이다.

  ── 오라클 / SCOPE=OFF ──
  Before 에도 SQL 자체는 문제가 없었다(scope 래핑을 안 하므로). 그러나 dialect
  미전달은 동일하게 발생해 chunk key 확정은 여전히 실패했다. After 는 oracle 로
  위임된다. 즉 (1)번 결함은 SCOPE 여부와 무관하게 오라클 전 경로에 걸려 있었다.

실제 ASGI 앱(web_server:app) 라우팅을 경유한 POST /exact-diff/run 으로도 같은
결과를 확인했다 — HTTP 200, chunk dialect=oracle, src_sql 에 TO_CHAR 렌더.
라우터 마운트/요청 파싱까지 포함한 경로에서 동일하게 동작한다.
