■ 구현 내용
1) 신규 테이블 semantic_dictionary_entry — 감사보고서 §2 후보B 제안 스키마 그대로
   entry_id PK / dictionary_id / project_id(NULL 허용) / term / normalized_term / language /
   semantic_type / confidence / source / match_type / status / description /
   allowed_context_json / risk_flags_json / created_by / version / created_at / updated_at
   인덱스 2개: (normalized_term, status), (project_id, source)
   행 순서는 rowid 로 보존 — 대표 entry 선정 tiebreak 가 원본 순서에 의존하므로 로더는
   항상 ORDER BY rowid 로 읽는다.

3) load_default_semantic_dictionary() 를 SQLite 조회로 교체
   - status='ACTIVE' AND project_id IS NULL 만 로드(= mock 164 전건 + pilot 5). PENDING 37은 제외.
   - 테이블 미구축/조회 실패 시 기존 JSON 파일로 조용히 폴백(신규 DB·이관 전 환경 호환).
   - 반환 entry dict 의 키/값은 JSON 시절과 완전 동일(project_id/created_at/updated_at 는 미포함).
   - project_id override 를 채우는 UI/API 는 만들지 않았다 — 컬럼만 준비(지시대로 별건).

4) 캐시 무효화 축 교체: 파일 mtime 조합 → 테이블 (행수, MAX(updated_at))
   성능 계약("동일 리스트 객체 재사용 → 매칭 인덱스 1회 빌드") 유지를 실측으로 확인.

5) kill-switch MV_SEMANTIC_DICT_STORE = db(기본) | file
   file 로 두면 즉시 이관 전 동작(JSON 직접 읽기)으로 복귀. 원본 JSON 2개는 삭제하지 않았고,
   db 모드에서는 런타임 읽기 대상에서 제외된다(파일 로더를 강제로 차단해도 정상 동작 확인).

6) 부수 정리: seed→entry 변환을 build_entry_from_seed() 하나로 통합(파일 폴백 경로와 이관
   스크립트가 같은 함수를 쓴다) — 저장소가 무엇이든 entry 가 같도록 강제.
   읽기는 mode=ro URI 전용이라 운영 DB 파일을 변경하지 않는다(테스트 운영DB 불변 guard 준수).

■ 비판적 검토 (문제점·위험)
- db/schema.sql 미반영: 지시가 파일 3개로 제한돼 스키마 정본에 DDL 을 넣지 않았다. 따라서
  init_db.py 로 새로 만든 DB 에는 테이블이 없고, 그 환경은 JSON 폴백으로 동작한다(장애는 아니지만
  '이관 완료' 상태가 아니다). 후속에서 schema.sql 반영 + init 시 자동 생성 권장.
- seed catalog 의 정책 메타 미보존: aliases / sum_policy / groupby_policy / auto_select_policy /
  required_profile_conditions / exclusion_conditions 는 테이블에 넣지 않았다(매칭에 쓰이는 투영만
  저장). JSON 원본이 여전히 정본이고 감사 테스트도 파일을 읽는다 — 후보C 를 '완전 흡수'로 보긴 이르다.
- PENDING 37건은 저장만 됐고 활성화 경로가 없다. 활성화는 판정이 바뀌는 정책 변경이라 별건이며,
  지금 상태에서 누군가 status 를 ACTIVE 로 바꾸면 후보 추천 결과가 즉시 달라진다(가드 없음).
- project_id override 는 쓰기 경로가 없다. 컬럼·인덱스·조회 필터(project_id IS NULL)만 준비된
  상태라, 지금 행을 수동으로 넣어도 로더가 읽지 않는다(전역만 읽음). 의도된 범위 제한이다.
- 로더 호출마다 SQLite 커넥션을 새로 연다(+1.9ms). 커넥션 재사용/스레드로컬은 Windows 에서
  파일 핸들을 붙잡아 DB 교체·백업 스크립트를 깨뜨릴 수 있어 일부러 하지 않았다.
- explainability: description / created_by / version / source 를 그대로 옮겨 근거는 보존된다.
- 보안: 사전 데이터에 자격증명 없음. 읽기는 mode=ro 라 운영 DB 를 쓰지 않는다.
- 구조: web_server.py 무변경, 신규 heuristic 0건, 신규 라우트 0건.
