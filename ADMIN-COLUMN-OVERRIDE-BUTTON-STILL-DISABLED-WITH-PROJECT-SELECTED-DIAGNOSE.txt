1. 결론 요약
════════════════════════════════════════════════════════════════════════
직전 진단(ADMIN-COLUMN-CONFIRM-BUTTON-NONFUNCTIONAL-AND-BATCH-SCOPE-DIAGNOSE)의
"작업 프로젝트 미선택이 근본원인" 은 **틀렸다**. 사용자 말이 맞다.

실측된 진짜 인과:

  [1] 프로젝트 선택 → localStorage/mvGetWorkProjectId() 모두 정상. 상단 표시와 저장값 일치.
  [2] 1단계 /analyze → 후보에 ctx{project_id:'957'} 부착 → 버튼 **활성**. 여기까지 정상.
  [3] 3단계 후보 계산(▶ 후보 컬럼 추천 / 선택 적용 후 다시 검증)
      → runRevalidateFromCandidate → _refreshValidationPlanWithRowCount
      → POST /validation-sets/preview  ← **요청 본문에 project_id 가 없다**
  [4] 서버가 authoritative 재확정(_maybe_finalize_postcount)을 수행하면서
      enrich 를 project_id 없이 다시 돌린다 → 후보의 ctx 가
      {project_id:'', table_key:'', project_id_present:false} 로 **덮어써진다**
  [5] 클라이언트는 그 authoritative 후보로 all_groupby_candidates 를 **통째 교체**하고
      후보표를 재렌더 → 버튼이 disabled 로 되돌아간다

즉 버튼 비활성은 '프로젝트를 안 골라서'가 아니라 **정상적인 3단계 진행 자체가
프로젝트 컨텍스트를 지우기 때문**이다. 사용자는 프로젝트를 고른 뒤 정상 순서로
1→2→3단계를 밟았고, 그래서 항상 비활성 버튼만 보게 된다.

직전 진단이 이걸 놓친 이유: 그 스크립트는 /analyze 응답을 곧바로 _analyzeData 에 넣고
후보표를 강제 렌더했을 뿐(위 [2] 시점), 실제 UI 흐름의 3단계 계산([3])을 한 번도
밟지 않았다. 그래서 대조군 B 가 '활성'으로 나왔고 결론이 프로젝트 선택 여부로 귀결됐다.

4. 조사항목별 답 (지침 1~5)
════════════════════════════════════════════════════════════════════════
1) 화면 '선택됨' 과 localStorage 일치 여부
   → **일치한다.** work_project_id="957", mvGetWorkProjectId()="957",
     상단 표시 "MV-ADMOVR-NONFUNC-DIAG". 불일치 가설 반증.
     (단, 직전 진단 스크립트가 지운 키 'mv_work_project_id' 는 존재하지 않는 이름이다.
      실제 키는 'work_project_id' — 그 스크립트가 A 시나리오를 만든 방식 자체가
      우연히만 맞았다. 새 브라우저 컨텍스트라 어차피 비어 있었기 때문.)

2) 서버로 전달되는 project_id 가 빈 값인가, 값은 있는데 다른 이유인가
   → **전달 자체가 없다.** 형변환/형식 불일치/서버측 존재 검증 실패가 아니다.
     /validation-sets/preview 요청 본문에 project_id 키가 없고, 요청 스키마에도
     필드가 없다. 서버는 기본값 None 으로 enrich 를 돌려 ctx 를 비활성으로 만든다.
     (반대로 /analyze 요청에는 정상적으로 실려 가고, 그 응답의 ctx 는 정상이다.)

3) '서버 재기동 후에도 옛 탭이 옛 상태' 패턴인가
   → **아니다.** 강제 새로고침 후 다시 analyze→3단계 계산을 밟아도 동일하게 재현된다.
     새로고침은 후보표를 지울 뿐 결함을 없애지 못한다.

4) 프로젝트 선택 시점과 후보표 렌더 시점 사이의 타이밍 문제인가
   → **부분적으로 맞지만 방향이 반대다.** 문제는 '선택이 늦어서'가 아니라,
     선택이 이미 반영된 정상 후보표를 **3단계 계산이 나중에 덮어써서** 생긴다.
     프로젝트를 먼저 선택하고 새로고침까지 해도 3단계 계산이 다시 지운다.

5) 사용자가 처음 본 상태의 조건 역추정
   → 특별한 조건이 필요 없다. **프로젝트 선택 + 정상 순서(1→2→3단계) = 항상 재현.**
     사용자가 3단계 후보표를 보는 시점은 대부분 '후보 컬럼 추천'을 누른 뒤이므로,
     실사용에서는 사실상 항상 비활성 버튼만 보게 된다. 버튼이 활성인 순간은
     /analyze 직후 3단계 계산 전(운영 화면에서는 거의 노출되지 않는 짧은 구간)뿐이다.

5. 영향 범위 / 추가로 드러난 사실 (미수정 — 이번 지침은 진단 전용)
════════════════════════════════════════════════════════════════════════
- table_key 도 함께 '' 로 지워진다. 확정 저장 키(프로젝트×테이블×컬럼) 중 두 축이
  동시에 사라지므로, 버튼 활성화만 고쳐서는 부족하고 table_key 도 함께 보존해야 한다.
- 한 번 확정한 행은 3단계 계산 후 [확정 해제] 가 불가능해진다(저장소에는 남음).
- 같은 형태의 미배선이 다른 3개 enrich 호출부에도 있다(**이번 실측 범위 밖 — 코드 근거만**):
    services/validation_job_core.py:314        (원클릭/전체검증 공통 core)
    services/batch_runner.py:139               (일괄검증)
    services/column_candidate_gen_service.py:845
  전부 project_id / override_table_key 를 전달하지 않는다. 반면 project_id 를 넘기는
  프로덕션 호출부는 services/single_validation_analyze_service.py:1614 한 곳뿐이다.
  → 개별검증 1단계 analyze 경로만 확정 컨트롤이 살아 있고, 나머지 경로는 구조적으로
    비활성일 가능성이 높다(BACKLOG 의 '일괄검증이 저장된 확정을 조회조차 안 함' 과 동일 뿌리).
- 조용한 무반응(요청 0건·에러 0건)이라 사용자가 원인을 알 수 없다. disabled 사유 문구는
  title 속성에만 있어 마우스를 올려야 보이고, 그나마 내용이 사실과 다르다
  ("프로젝트를 먼저 선택해야" — 사용자는 이미 선택했다).
