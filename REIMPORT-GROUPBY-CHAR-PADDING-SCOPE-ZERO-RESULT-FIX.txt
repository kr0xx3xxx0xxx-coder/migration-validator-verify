    저장 토큰(패딩 유지) vs 조회 토큰(strip) 의 값 부분이 공백 때문에 달라

2. 수정 내용 (store.py 만 최소 수정 · 라우트 무변경)
────────────────────────────────────────────────────────────────────────
- store.py 에 값 정규화 단일 헬퍼 _norm_scope_val(v) = str(v).strip() 추가.
- scope_norm_of(저장)·scope_token_of(조회) 두 토큰 빌더가 이 헬퍼 하나로 값을
  동일 정규화(양끝 공백 제거)하도록 변경 → 저장·조회 토큰이 대칭이 되어 매칭.

[수정 방향 판단 근거 — 저장·조회 어느 쪽을 맞췄나]
- 라우트(조회측)는 이미 scope_val 을 .strip() 한다(기존 동작). 즉 조회 토큰은 이미
  '공백 없는 값' 기준이다. 따라서 저장측을 같은 기준(strip)으로 맞추는 것이 자연스럽고,
  추가로 조회측 토큰 빌더에도 동일 정규화를 넣어(다축 콤마 split 공백까지 흡수) 두 빌더가
  '단일 정규화 함수'를 공유하도록 대칭화했다. → 비교 시점에 양쪽을 동일 방식으로 정규화.
- 저장측만 바꾸면 단축은 해결되나 다축 콤마 split 공백이 남으므로, 두 빌더 모두 적용이
  가장 견고(구조 안정·회귀 억제).

[하위호환 고려]
- 과거에 이미 패딩 포함으로 저장된 file-영속 run 의 scope_norm 은 여전히 패딩을 가진다.
  그러나 그런 CHAR 그룹 run 은 '수정 전에도 0건(버그 상태)'이었으므로 회귀가 아니다.
  드릴다운을 재준비(재스캔)하면 새 저장 로직이 strip 된 scope_norm 을 기록해 정상화된다.
- VARCHAR2/NUMBER 과거 run 은 값에 양끝 공백이 없어 저장·조회 토큰이 전혀 변하지 않아
  그대로 매칭된다(회귀 없음).
