    below_row_threshold / (충족 시) large_table

3. 오라클 제외 근거 (이번 작업의 최상위 안전 조건)
════════════════════════════════════════════════════════════════════════════════
services/connection_pool.py:94  _is_pg(key) → key[0] == "postgresql"
services/connection_pool.py:141 if not _is_pg(key): _open_real_connection(db_info)  # 항상 새 물리 연결

즉 오라클(및 MySQL/MSSQL/MariaDB/DB2)은 checkout 마다 물리 연결을 새로 만든다. 세트 병렬을 켜면
동시 세션 2개가 그대로 DB 물리 부하가 되고, ⑥의 '풀 여유' 판정 자체가 무의미해진다.
→ 오라클은 _STATS_SET_PARALLEL_EXCLUDED_DIALECTS 로 별도 표기(trace 사유 분리), 그 외 비풀링 방언은
   허용 방언 allowlist(_STATS_SET_PARALLEL_POOLED_DIALECTS = postgresql) 밖이라 함께 제외된다.

지시서의 조건 문구는 "둘 다 오라클이 아님(PostgreSQL 등 커넥션풀 우회 없는 방언)" 이었다. 문자
그대로면 MySQL/MSSQL 이 자동 병렬 대상이 되는데, 이들도 오라클과 똑같이 풀을 우회하므로 지시서가
든 '우회 없는 방언' 이라는 근거에 맞춰 allowlist 방식으로 구현했다. 이 판단은 오라클 제외를 더
강하게 만들 뿐 약화시키지 않는다.

5. 실측에서 드러난 사실 — 반드시 읽을 것
════════════════════════════════════════════════════════════════════════════════
① 100만행에서의 개선폭은 -6.3% 로 작다.
   백로그 P11 이 근거로 든 -41~55% 는 5,000만행 기준이다. 임계치 100만은 '해로울 것이 없는'
   수준에서 켜지는 값이지 '큰 이득이 보장되는' 값은 아니다. 이득이 뚜렷해지는 구간을 원하면
   MV_STATS_SET_PARALLEL_MIN_ROWS 로 임계치를 올리는 편이 낫다(코드 변경 불필요).

② 5,000만행 PostgreSQL 재현은 불가했다 — 그 규모의 테이블이 PG 에 없다.
   Neon PG asis/tobe 의 최대 테이블은 100만행(src_orders_a / tgt_orders)이고,
   5,000만행 테이블은 **오라클에만** 있다(Oracle_asis MV_SCATTER50M_SRC 50,000,000행 /
   Oracle_tobe MV_SCATTER50M_TGT 49,500,000행). PostgreSQL_NEW_asis/tobe 에도 100만행 초과
   테이블은 없다(조회 결과 0건).
   → 즉 백로그가 측정한 최대 이득 구간(5,000만행)은 현재 환경에서 오라클 자산이며, 이번 지시대로
     오라클을 제외하면 그 구간은 조건부 ON 의 적용 대상이 아니다. 안전(오라클 풀 우회) 판단을
     우선하라는 지시에 따라 제외를 그대로 구현했고, 이 상충을 여기 명시한다.
   → PG 대규모 이득을 실증하려면 PG 쪽에 대용량 테이블을 준비하는 후속 작업이 필요하다.

③ 조건부 ON 이 켜져도 결과값은 순차와 완전 동일함을 실 DB 로 재확인했다(A==B, A==C).
