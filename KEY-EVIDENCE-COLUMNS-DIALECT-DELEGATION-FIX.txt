2. 수정 내용 (services/diagnosis/key_evidence.py 만 수정)
────────────────────────────────────────────────────────────────────────
_columns() 를 앱 공통 컬럼메타 경로 _fetch_columns_info() 로 방언 위임:
  - 컬럼 목록/타입: _fetch_columns_info → 어댑터 build_column_meta_query
    (오라클 ALL_TAB_COLUMNS / PG information_schema). 직접 커서·요청스코프 캐시.
  - 타입 정규화: 어댑터 normalize_type (오라클 'number'→NUMBER 정확 분류).
_pk_unique 가 fetch_key_metadata 로 위임한 것과 동일한 어댑터 구조를 그대로 확장(새 방식
발명 없음).

핵심 설계 판단 — cmn_db_fetch_select_readonly(구 _columns 가 쓰던 read-only 실행)를 재사용
하면 그 안의 sqlglot 가드(assert_single_select)가 오라클 build_column_meta_query 의 `:1`
수치 바인드를 파싱 못 해 UNPARSEABLE 로 막힘(실측 확인). 앱이 이미 컬럼메타 조회에 쓰는
_fetch_columns_info 는 가드 없는 직접 커서라 `:1` 문제가 없음 → 이 공통 경로를 재사용.
케이스 무관 매칭은 어댑터 쿼리의 UPPER(table_name) + 대문자 테이블명 전달로 보존.

_column_meta_full / _table_key_meta(TRUSTED_PHYSICAL_PK 경로)는 is_nullable 이 필요한데
어댑터가 nullable 을 노출하지 않아 이번 범위(=_columns)에서 제외. 오라클에선 이 경로가 {}→
NOT_TRUSTED 로 confirmed 경로에 자동 폴백하므로 크래시 없음(별개 후속 범위).

4. 하류 차단원인 (본 작업 범위 밖 — 수정하지 않음, 후속 작업으로 분리 보고)
────────────────────────────────────────────────────────────────────────
_columns 를 열자 프로덕션 오라클 KEY_RANGE 확정을 여전히 막는 별개 결함 2건이 드러남:

 #1 dialect 미위임 (routes/diagnosis_route.py:_confirm_routing)
    resolve_confirmed_chunk_key 를 dialect 인자 없이 호출 → 기본 postgres → 오라클 NULL
    probe 가 'LIMIT'(→ORA-03049 "SQL keyword 'LIMIT' is not syntactically valid")로 렌더
    → 확정 실패. 실측: 동일 probe 를 oracle 방언(FETCH FIRST 1 ROWS ONLY)으로 렌더하면
    정상 실행. key_evidence 밖(routes 계층) + 완료된 Phase 3-B 코드라 별도 작업 권장.

 #2 __BKT/__RNG 선행 밑줄 별칭 ORA-00911 (services/diagnosis/strategies/key_range.py)
    지시 3에 따라 확인: build_bucket_agg_sql(dialect=oracle) 생성 SQL
      SELECT DEPT_CD AS G0, COUNT(*) AS CNT, WIDTH_BUCKET(ID,1,201,8) AS __BKT ...
    실행 → ORA-00911: _: invalid character after AS  (재현됨). 별칭 수정은 범위 밖 —
    사실만 명시(별도 작업). #1 이 선행 차단이라 프로덕션에선 아직 __BKT 실행 이전 단계.

권장 후속: #1(dialect 위임) → #2(별칭 개명)를 순차 별도 작업으로 진행하면 오라클 진단이
HOLD 대신 KEY_RANGE 로 완주.
