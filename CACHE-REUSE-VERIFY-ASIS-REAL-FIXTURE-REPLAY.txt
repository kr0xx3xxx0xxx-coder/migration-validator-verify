[3] 재이관 준비(prepare) 1회 — 원 지원작업과 동일 원본 SQL
--------------------------------------------------------------------------------
원본(asis): SELECT * FROM ( WITH ranked AS (
              SELECT x.ID, x.C_CHAR, x.C_NUM_PS,
                     ROW_NUMBER() OVER (PARTITION BY x.C_CHAR ORDER BY x.ID) AS rn
              FROM NXDNP.MV_ORA_XDIFF_SRC x
              LEFT JOIN NXDNP.MV_ORA_TEST_SRC t ON MOD(x.ID,300)+1 = t.ORDER_ID )
              SELECT ID, C_CHAR, C_NUM_PS FROM ranked WHERE rn >= 1 ) mv_reimport_src
목적(tobe): SELECT ID, C_CHAR, C_NUM_PS FROM NXDNP.MV_ORA_XDIFF_TGT
  · CTE + LEFT JOIN + ROW_NUMBER 원본을 서브쿼리로 감싼 행 수준 소스(원 지원작업과 동형).
  · src_conn=asis(1523), tgt_conn=tobe(1524) — 자기비교 아닌 실제 소스/타겟 분리.
  · 재이관 후보: missing 100 + value_mismatch 50 = 총 150건 (자연 불일치, 표본 조기중단 미발동 READY).

[5] 결론 — 캐시 재사용 메커니즘 동일 성립
--------------------------------------------------------------------------------
· 최초 prepare 1회만 25만행 CTE+LEFT JOIN+ROW_NUMBER 를 실제 스캔(분 단위: 이번 250.6초).
  reused=False 로 fresh 스캔임을 확인.
· 이후 서로 다른 C_CHAR 그룹 드릴다운·페이징·전체목록은 모두 저장 index(SQLite store)
  scope 조회로 sub-100ms 즉시 응답(재계산 없음).
· 동일/다른 session_id 로 prepare 재요청 시 reused=True + same_run_id=True
  → 테이블쌍 fingerprint 캐시가 세션 비종속(전역)으로 재사용(재스캔 없음).
⇒ "매 클릭 25만행 재계산 아님, 테이블당 1회 prepare 후 캐시/스토어 재사용"이라는
   선행 결론이 asis→tobe 실 fixture 로도 그대로 성립한다.
(주) fresh 시간이 tobe 자기비교 371초 → asis→tobe 251초로 짧아진 것은 코드 아닌 인스턴스/
     경로 차이(자기비교는 동일 tobe 인스턴스 read 경합, 실 fixture 는 asis·tobe 분산). 결론 불변.

[6] CHAR 패딩 그룹조회 0건 이슈 — asis 실데이터로 재현 확인(참고, 수정 안 함)
--------------------------------------------------------------------------------
· T1~T3 그룹 드릴다운 모두 0건 반환(이전 tobe 자기비교와 동일 증상).
· 근본 원인 실데이터 확인: MV_ORA_XDIFF_SRC.C_CHAR = CHAR(10) 고정폭.
    실값 예) [C0007     ] len=10  (뒤 공백 5칸 패딩), [C0012     ] len=10
  저장 store 의 scope 값은 패딩 포함, 드릴다운 scope_val 파라미터는 stripped('C0007')
  → 불일치로 0건. asis 실 fixture 로도 동일 재현. (본 작업은 재현 여부만 확인, 수정 미수행.)
