■ 1. 무엇이 문제였나

직전 작업(SINGLE-STEP5-REPRESENTATIVE-AXIS-SINGLE-SOURCE-FIX)은 5만행 이하 DIRECT 경로
(routes/agg_diff_route.py:_select_direct_rep_axis)만 '순서 무관 결정적' 대표축 선정으로 고쳤다.
5만행을 넘으면 실행 경로가 chunk(services/exact_diff/pk_range_chunk.py)로 갈리는데, 그쪽
_select_rep_axis 는 지시대로 미수정으로 남아 있었다.

그 정책은 ①2~200 그룹 축 ②후보점수(gb_candidate_scores) ③선택순서(gb_selection_order) 순으로
동점을 깨게 설계돼 있었지만, 운영 호출부(routes/agg_diff_route.py:314)는 이 두 인자를 아예 넘기지
않는다. 인자가 없으면 _sel_order 가 gb_cols 순서로 대체되므로, 실질적으로 '먼저 온 축'이 대표축이
되었다. 결과적으로 같은 데이터·같은 선택이라도

  - gb_cols 를 [status_cd, dept_cd] 로 보내면 대표축 status_cd
  - gb_cols 를 [dept_cd, status_cd] 로 보내면 대표축 dept_cd

로 뒤바뀌고, 나아가 데이터 규모가 5만행 경계를 넘나들면 같은 선택인데도 DIRECT(dept_cd)와
chunk(status_cd)가 서로 다른 축을 대표로 골랐다. 5단계 '대표 GROUP BY 불일치 분포'의 축과 그룹 수가
데이터 규모에 따라 달라 보이는 것이 사용자에게 보이는 증상이다.


■ 2. 무엇을 고쳤나 (services/exact_diff/pk_range_chunk.py 만 수정)

(1) 폴백 규칙 교체 — 후보점수·선택순서가 실제로 전달되지 않은 경우(= 현재 운영 경로)에는 DIRECT 와
    '완전히 동일한' 결정적 규칙으로 대표축을 고른다. 새 규칙은 만들지 않았고 DIRECT 규칙을 그대로 이식했다.
      ① 값이 실제 관측된 축(coverage>0) 우선 — 전부 0이면 전체 축을 후보로 둔다
      ② 불일치 distinct 그룹 수 2~200 구간 축 우선(드릴다운 실효 구간)
      ③ 그 안에서 그룹 수가 적은 축 우선
      ④ 최종 동률은 컬럼명 오름차순(입력 순서를 전혀 참조하지 않는다)
    ①을 위해 축별 '값(non-NULL) 관측 레코드 수' 누적(_grp_cover_by_axis)을 기존 분포 누적 루프에
    한 줄 얹었다(추가 DB 조회 없음).

(2) 근거 필드 동일화 — chunk 응답의 mismatch_group_distribution 에 DIRECT 와 같은 이름·형태로
    representative_axis / selection_reason / representative_axis_reason / axis_group_counts /
    axis_selection_deterministic 를 싣는다. 사유코드도 DIRECT 와 같은 값(SINGLE_AXIS /
    IN_BAND_FEWEST_GROUPS / OUT_OF_BAND_FEWEST_GROUPS)을 쓴다. 화면(ui/tabler_renderer.py
    _mvRiRenderGroupView)은 손대지 않았고, 실제로 손대지 않아도 그대로 표시된다(§5 실화면 확인).

(3) 기존 정책 보존 — gb_candidate_scores 또는 gb_selection_order 가 실제로 전달되면 기존 D7-16 C
    정책(2~200 → 후보점수 → 선택순서)이 그대로 동작한다. 그 인자들을 운영에서 채워 넣는 일은 이번
    범위 밖이라는 지시에 따라 손대지 않았다.

(4) 5만행 경계(compare_strategy 분기, ui/tabler_renderer.py:16854·16871)는 건드리지 않았다.

공통 함수 추출 여부(중복 로직 금지 원칙)에 대한 판단:
  공통 모듈로 뽑는 쪽을 먼저 검토했으나 채택하지 않았다. 이유는 두 가지다.
   (a) 이번 작업 지시가 pk_range_chunk.py 한 파일 수정으로 못박혀 있고, 상대편 파일
       routes/agg_diff_route.py 는 직전 작업으로 막 완료된 모듈이라 임의 수정 대상이 아니다.
   (b) 기술적으로도 services → routes 역방향 import 는 단방향 의존 원칙 위반이며, agg_diff_route 가
       pk_range_chunk 를 import 하고 있어 실제 순환 import 가 된다. 반대 방향(routes 가 services 의
       공통 함수를 호출)이 옳은 구조지만 그건 agg_diff_route.py 수정을 수반한다.
  따라서 규칙을 pk_range_chunk.py 에 동일 형태로 복제 구현하되, 두 구현이 시간이 지나며 어긋나는 것을
  막기 위해 회귀 테스트에서 '같은 입력 → 같은 (축·사유코드·사유문구)'를 직접 대조하도록 했다
  (tests/test_pk_range_chunk_representative_axis_unify.py::test_규칙_자체가_DIRECT_와_동치다).
  후속으로 agg_diff_route.py 수정이 허용되면 pk_range_chunk.select_deterministic_rep_axis 를
  단일 출처로 삼고 DIRECT 가 그것을 호출하도록 바꾸는 것이 정리 방향이다.
