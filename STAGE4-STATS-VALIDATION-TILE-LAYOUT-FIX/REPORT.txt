■ 1. 무엇을 바꿨나

4단계(통계검증 실행) 상단의 '통계검증 구성 요약'은 10열짜리 표였다.

  before : No | 원본 테이블 | 목적 테이블 | 쿼리검토 | COUNT | 후보컬럼 |
           GROUP BY 구성 | SUM 구성 | 검증항목 | 상태
           (GROUP BY 구성 = "status_cd ↔ STATUS_CD · dept_cd ↔ DEPT_CD" 화살표 표기)

이 표시도 '1 SQL = 1 세트 요약'이지 여러 행을 다루는 그리드가 아니다. 1~3단계가 이미 확립한
타일 디자인 시스템으로 바꿨다.

  after  : 목적테이블 | 원본테이블 | 검증항목 | 목적그룹 | 원본그룹 | 목적집계 | 원본집계 |
           처리시간 | 상태   (타일 9개)

새 CSS·새 규격은 만들지 않았다. 타일 CSS(.mv-qr-tiles/.mv-qr-tile/.mv-qr-tile-label/
.mv-qr-tile-box/.mv-qr-tile-val)와 타일 1개 빌더(_mvQrTileHtml)를 그대로 재사용했고, 값 렌더
규칙(multi 줄바꿈 / mono / statusicon / 미계산 '—')은 3단계 것을 공용부(_mvTilesHtmlFromCols)로
뽑아 두 단계가 함께 쓴다. 실측에서 4단계 타일 박스 규격이 3단계와 완전히 같음을 확인했다
(min-height 85px · padding 13px 12px — 브라우저 computed style 대조).

같은 화면에서 중복 표시를 하던 '생성된 SQL 기준' 안내박스(.gen-sql-basis, 높이 114px)도 함께
삭제했다(추가 지침).


■ 2. 컬럼 정리 판단 근거

지침이 판단을 요구한 세 항목이다. 임의로 지우지 않고 그 정보가 화면 다른 곳에 이미 있는지
먼저 확인한 뒤 결정했다.

  (a) 쿼리검토 / COUNT / 후보컬럼  →  제거
      이 셋은 1·2·3단계의 최종 상태를 4단계에서 다시 보여주는 열이다(_mvWithPrevStageStatus 가
      주입). 같은 판단을 3단계 타일이 이미 내려놓았다 — grid_helpers.py 의 3단계 타일 주석에
      "이전 단계 상태 열(쿼리검토/COUNT)은 상단 단계 탭 배지가 이미 담당하므로 타일에 넣지
      않는다(1·2단계 타일이 같은 이유로 _mvWithPrevStageStatus 를 거치지 않는 것과 동일)"고
      명시돼 있다. 4단계만 예외로 둘 이유가 없어 같은 규칙을 적용했다. 상단 1~5단계 탭 배지가
      각 단계 상태를 상시 표시하므로 정보 손실이 아니다(실측 스크린샷의 단계 탭 참조).

  (b) GROUP BY 구성 / SUM 구성  →  목적그룹·원본그룹·목적집계·원본집계 4타일로 분리
      3단계가 확립한 '화살표(↔) 대신 목적/원본 축 분리 + 줄바꿈 다중값' 규칙을 그대로 재사용
      했다(_mvColPairParts). 새 표기를 발명하지 않았다. before 의 "status_cd ↔ STATUS_CD ·
      dept_cd ↔ DEPT_CD" 한 칸이 after 에서는 목적그룹 "STATUS_CD / DEPT_CD"(줄바꿈) + 원본그룹
      "status_cd / dept_cd"(줄바꿈) 두 타일로 나뉜다.

  (c) 검증항목('COUNT · GB 1 · SUM 2')  →  유지
      GB/SUM '개수'는 위 (b) 타일에서 세면 알 수 있어 그 부분은 중복이다. 그러나 'COUNT(*) 는
      항상 포함된다'는 사실은 다른 타일 어디에서도 유추할 수 없다. 더구나 이번에 함께 삭제하는
      '생성된 SQL 기준' 안내박스가 바로 그 사실("COUNT(*): 항상 포함")을 담고 있던 유일한 자리라,
      검증항목까지 지우면 그 정보가 화면에서 완전히 사라진다. 그래서 유지하고, 툴팁에
      "COUNT(*) 는 항상 포함됩니다 · GROUP BY n개 · 집계컬럼 m개"로 근거를 붙였다.

  (d) 목적/원본 테이블  →  유지, 다른 단계와 같은 순서(목적 먼저)로 통일
      before 표는 '원본 테이블 → 목적 테이블' 순이었는데 1~3단계 타일은 '목적테이블 →
      원본테이블' 순이다. 타일로 오면서 다른 단계와 같은 순서로 맞췄다(지침 3의 "목적 먼저,
      원본 다음" 요구와도 일치).

  (e) 처리시간  →  신규 추가(지침 4), 상태 바로 앞
      값은 새로 계측하지 않는다. 기존 _mvShowStageProcessingTime(4, ...) 이 이미 재던 값을
      타일이 읽도록 보관만 추가했다. 4단계 슬롯에는 성격이 다른 두 값이 순서대로 들어오므로
      (SQL 생성 시간 → 통계검증 실행 시간) 라벨도 함께 보관해 툴팁에서 구분한다.

  (f) 원본 테이블 2개 이상(JOIN/UNION)  →  행 분할 제거
      표 시절에는 _mvExpandRowsPerSrcTable 이 원본당 한 행으로 펼쳤다. 타일은 행 개념이 없으므로
      1·2·3단계 타일과 동일하게 한 타일에 전부 합쳐 표시한다.


■ 3. '생성된 SQL 기준' 안내박스 삭제 (추가 지침)

박스가 보여주던 세 줄은 전부 타일이 대체한다 — GROUP BY/SUM 은 (b)의 4타일, 'COUNT(*) 항상
포함'은 (c)의 검증항목 타일. 따라서 껍데기와 그 여백(margin-bottom:12px · padding:9px 12px)을
통째로 걷어냈다.

다만 그 박스 '안에' 중복이 아닌 요소 셋이 함께 들어 있었다. 이들은 껍데기 없이 그대로 남겼다.
  · genSqlComboDecomposeNotice — GROUP BY 2축 이상일 때 '조합은 따로 실행된다' 경고와
    조합 opt-in 체크박스(#gbIncludePair). 실행 동작에 직접 관여하므로 지우면 기능 회귀다.
  · _wrapBadge — 원본 SELECT wrapping 적용 배지.
  · #genSqlRegenNotice — 선택 변경 시 _updateExecSelectionSummary 가 id 로 찾아 채우는
    재생성 안내 placeholder. 지우면 그 함수가 대상 DOM 을 잃는다.
실측에서 combo 케이스(GB 2축)의 조합 경고가 before/after 동일하게 표시됨을 확인했다.


■ 4. 구현 중 발견해 고친 결함 (실측이 잡아낸 것)

1차 구현 후 after 실측에서 타일 값이 전부 '—' 로 남고 처리시간만 'NaN초'로 나왔다. 브라우저
probe 로 원인을 확정했다: **전역 함수명과 window 보관 변수명 충돌**이다.

  브라우저에서 최상위 `function _mvStage4ProcMs(){...}` 는 곧 `window._mvStage4ProcMs` 다.
  그런데 처리시간을 같은 이름(`window._mvStage4ProcMs = ms`)으로 보관했더니, 값이 들어오는
  순간 함수가 숫자로 덮여 사라졌다 → `_mvStage4ProcMs is not a function` 예외 → 타일 렌더가
  통째로 죽어 이전 렌더(라벨만)가 그대로 남았고, 그 전까지는 `Number(함수)` = NaN 이 찍혔다.

헬퍼를 `_mvStage4ProcInfo()` 로 분리해 해소했다(3단계가 `_mvCandidateProcMs()` 함수 +
`window._mvStage3ProcMs` 값으로 이름을 나눠 둔 것과 같은 형태). node 하니스는 window 가 별개
객체라 이 충돌을 재현하지 못해 테스트 30건이 전부 통과하면서 놓쳤다 — 그래서 소스 수준 정적
검사(test_no_global_function_vs_window_slot_collision)를 재발 방지로 추가했다.

또한 host 를 #sqlOut 밖으로 옮기면서 생긴 stale 노출 경로 4곳을 모두 배선했다. 종전에는 표가
#sqlOut 안에 있어 `_clr('sqlOut')` 한 줄로 함께 지워졌지만, 이제는 경로마다 따로 비우지 않으면
무효화 후에도 옛 GROUP BY/SUM 구성이 남는다.
  _singleInvalidateDownstream · resetAnalysisUi · resetAfterGenerateStart ·
  _clearCountDownstreamUi · refreshFinalSelectionState(유효 SQL 미생성 분기)
이 중 resetAfterGenerateStart / _clearCountDownstreamUi 두 곳은 처음에 놓쳤는데, 'sqlOut 을
비우는 모든 경로가 타일도 처리하는가'를 검사하는 테스트가 잡아냈다.
