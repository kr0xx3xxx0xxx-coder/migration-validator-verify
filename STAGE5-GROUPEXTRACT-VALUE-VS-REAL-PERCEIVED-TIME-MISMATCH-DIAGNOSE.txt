작업명 : STAGE5-GROUPEXTRACT-VALUE-VS-REAL-PERCEIVED-TIME-MISMATCH-DIAGNOSE
✅ 작업 완료 - "캐시 재사용(reused) 값 그대로 노출"이 근본 원인임을 코드 근거+실측 재현으로 확인(코드 수정 없음)

────────────────────────────────────────────────────────────
1. 결론 요약
────────────────────────────────────────────────────────────
화면에 뜨는 11.56초/12.18초는 "지금 이 클릭에서 걸린 시간"이 아니라, "이 정확한 그룹 scope를
과거 어느 시점(오늘일 수도, 그 이전일 수도 있음)에 최초로 스캔했을 때 실제로 걸렸던 시간"이다.
사용자가 R01·G01을 클릭했을 때 서버가 fingerprint 기준 캐시 재사용(reused=true) 응답을
그대로 돌려주면서 값을 새로 재기 않았기 때문에, 클릭~응답은 1초 미만(체감과 일치)이었지만
표시값은 과거 스캔 당시의 실측치(11.56초/12.18초)를 바꾸지 않고 그대로 보여준 것이다.
이는 버그라기보다 "캐시 재사용 여부를 화면에 드러내지 않는" 표시 설계의 공백이다.

2. 값의 정의 — 코드로 추적
────────────────────────────────────────────────────────────
[화면 표시 지점] ui/tabler_renderer.py:27997-28004(_mvStage5PipelineHtml)

  그룹 상세추출 완료(!o.preparing) 콜백에서 g.detail_ms = o.detailMs 로 매번 "덮어쓴다".
  즉 클릭할 때마다 새로 세팅은 되지만, 그 값(o.detailMs=_detailMs) 자체가 서버 응답 그대로다
  (ui/tabler_renderer.py:28664 _detailMs = d.detail_elapsed_ms ?? tm.detail_elapsed_ms ?? fullMs).

[detail_elapsed_ms 원 계산] services/exact_diff/pk_range_chunk.py:625-835

[재사용(캐시 히트) 경로 — 핵심] routes/agg_diff_route.py:1382-1425
  POST /agg-diff/prepare 는 fingerprint(=원본/목적 접속+SQL+GB/SUM 선택+그룹 scope 전부 포함)로
  rj.get_by_fingerprint(fp) 를 먼저 조회한다. READY/EARLY_STOPPED 상태의 기존 job 이 있으면
  "out = dict(ex['summary']); out['reused']=True" 로 과거 summary(그 안의 metrics.detail_elapsed_ms

  소요시간이 10.59초→8.56초로 매번 달라졌다"는 과거 실사용 증상이 남아있고, 그 결함(EARLY_STOPPED
  는 재사용 안 되던 것)을 고친 기록이 바로 이 캐시 재사용 로직이다.

[캐시의 지속 범위 — TTL 없음] services/exact_diff/reimport_job.py
  - 메모리 캐시 _JOBS_BY_FP(§54 get_by_fingerprint) : LRU 16개 상한, 서버 재시작 시 소멸.
  - DB 재구성(rehydrate) _rehydrate_from_db(§64-107) : 메모리 미스 시 db/exact_diff_runs.db
    (exact_diff_run 테이블)에서 같은 fingerprint의 완료(DONE/EARLY_STOPPED) run 을 찾아 그대로
    job 을 복원해 캐시에 얹는다 — "언제 저장됐는지"에 대한 시간 제한(TTL)이 코드 어디에도 없다.
    즉 오늘이 아니라 며칠 전에 같은 조건으로 한 번이라도 스캔한 적이 있으면, 서버가 재시작됐어도
    그 예전 값이 그대로 재사용된다.

3. 실측 재현(라이브 오라클, 실 포트 8000)
────────────────────────────────────────────────────────────
방법: 한 번도 스캔된 적 없는 신규 오라클 픽스처(NXDNP.MV_TMDIAG_SRC/TGT, 900행, REGION_CD×
STATUS_CD 2축 GB → 다중세트 정책 발동으로 그룹목록 화면 재현. scratchpad/
stage5_timing_diagnose_fixture.py 로 생성 — 테이블명을 새로 지어 fingerprint 원천 신규 보장)를
만들고, scratchpad/stage5_timing_diagnose_verify.py(playwright, 기존 조작 헬퍼 재사용)로
1~5단계를 실제로 밟은 뒤 그룹 3개를 순서대로 조작했다. "실측"은 파이썬 wall-clock(클릭 시작 ~
'상세 추출 상태' 배지가 완료로 바뀌는 순간)이고, "카드값"은 화면 [고정] 카드 표시값이다.

  [A] 그룹#0 최초(콜드) 클릭      : 실측 0.31초 | 카드값 0.15초 | fromCache=False
  [B] 그룹#0 접었다 재클릭(웜)     : 실측 0.00초 | 카드값 0.15초(A와 완전 동일) | fromCache=True
  [C] 그룹#1(별개 그룹, 콜드) 클릭 : 실측 0.32초 | 카드값 0.13초 | fromCache=False

[B]가 사용자가 겪은 패턴을 그대로 재현한다 — 재클릭은 0.00초(체감 "1초 미만"과 일치)인데
카드값은 A의 콜드 스캔값(0.15초)을 한 글자도 안 바꾸고 그대로 보여줬고, 클라이언트 전역
window._mvPkPrepFromCache 가 실제로 true 로 찍혔다(재사용 경로를 탔다는 직접 증거).
이번 픽스처는 900행이라 콜드 스캔 자체도 1초 미만이라 "11초 vs 1초 미만" 같은 극적인 절대
격차까지는 재현하지 못했지만(작은 테이블은 콜드도 빠름), 매커니즘(재사용 시 값이 갱신되지
않음)은 동일 코드 경로로 확인됐다. 스크린샷: X:\Verify\verify_screenshots_only\
STAGE5-TIMING-DIAGNOSE\(0~4번 png), 원본 JSON: scratchpad/_stage5_timing_diagnose_result.json.

    "과거의 진짜 콜드 스캔값"일 개연성이 높다. (나머지 대용량 run 다수는 detail_elapsed_ms

  - 다만 group_id/target_table 컬럼이 이 경로에서 항상 빈 문자열로 저장돼(services/exact_diff/

    어느 run 이 사용자가 본 값의 "원본 스캔"이었는지는 DB만으로 특정하지 못했다 — 이 부분은
    끝까지 규명하지 못했음을 밝힌다(지시서 2번의 "추적 가능하면" 조건부 요구 — 완전 특정 불가).

────────────────────────────────────────────────────────────
4. "그룹추출"이라는 제목이 정확한가 — 사용자 의심 검증
────────────────────────────────────────────────────────────
사용자 의심이 코드 정의상 맞다. 이 값(detail_elapsed_ms)이 재는 것은 "불일치 그룹을 찾아내는
시간"이 아니라 "이미 4단계 통계검증에서 확정된 그룹 목록 중 하나를 골라, 그 그룹의 불일치
레코드(행)를 원본/목적 각각 조회해 비교하는 시간"이다(services/exact_diff/pk_range_chunk.py:625
주석 "실제 상세비교 시작 시각... prepare_ms 와 분리"). "그룹"은 5단계 진입 시점에 이미 다
정해져 있고(그 그룹을 찾는 GROUP BY 스캔은 4단계에서 이미 끝났다), 이 값은 그중 1개 그룹의
"레코드 상세비교"만 잰다. 따라서 "5단계 불일치 그룹추출"이라는 라벨은 "그룹을 추출(발견)하는
시간"으로 오독되기 쉽고, 실제로는 "선택한 그룹의 상세 레코드 추출/비교 시간"이다 — 사용자
지적대로 제목과 실제 측정 대상이 어긋난다.

────────────────────────────────────────────────────────────
5. 부가 발견 — "캐시 재사용" 표시 배선이 절반만 있다
────────────────────────────────────────────────────────────
서버 응답에는 이미 reused 플래그가 있고(routes/agg_diff_route.py:1407/1419/1425), 클라이언트도
이미 window._mvPkPrepFromCache 변수를 만들어 매 요청마다 true/false 로 채운다(ui/
tabler_renderer.py:17617/17620) — 그런데 이 값을 화면 어디에서도 읽거나 표시하지 않는다(전체
파일 grep 결과 대입 2곳뿐, 소비하는 코드 없음). 즉 "지금 이 값이 방금 새로 스캔된 것인지 예전
결과를 재사용한 것인지" 구분해 줄 데이터는 이미 만들어져 있는데 마지막 한 줄(표시)만 빠져 있다.

흥미롭게도 팀이 이 정확한 문제를 이미 한 번 인지했던 흔적이 있다 — ui/tabler_renderer.py:
28126-28128, 28323-28325 주석: [갱신] '선택 그룹 상세추출' 카드를 "카드 숫자가 캐시 재사용/
콜드·웜 캐시 여부에 따라 오해를 줌"이라는 이유로 통째로 삭제했다(STAGE5-GROUP-CARD-REMOVE).
하지만 그 삭제로 문제가 없어진 게 아니라, 완전히 동일한 숫자를 보여주는 [고정] 카드('5단계
불일치 그룹추출')로 문제가 그대로 옮겨갔을 뿐이다 — [고정] 카드는 캐시 재사용 여부와 무관하게
항상 값을 보여준다.

────────────────────────────────────────────────────────────
6. 개선 제안(구현하지 않음 — 지시서가 "어떻게 고치면 좋을지 제안"까지만 요구)
────────────────────────────────────────────────────────────
- 단기: 라벨 "5단계 불일치 그룹추출" → "선택 그룹 상세비교(레코드) 소요" 류로 정정해 "그룹을
  찾는 시간"이라는 오독 여지를 제거.
- 단기: 이미 존재하는 window._mvPkPrepFromCache(또는 서버 reused 필드)를 카드 값 옆에
  "(캐시 재사용)" 배지로 노출 — 새 계측 불필요, 이미 있는 값을 화면에 연결만 하면 됨.
- 중기: 캐시 재사용일 때는 "최초 스캔 M초 전 · 그때 소요 N초"처럼 원 스캔 시점을 함께 보여줘
  "왜 지금은 이렇게 빨랐는지"를 사용자가 스스로 설명 가능하게.

────────────────────────────────────────────────────────────
코드 수정 없음. 조사·실측 재현만 수행(신규 픽스처 테이블 NXDNP.MV_TMDIAG_SRC/TGT는 진단용으로
새로 생성했으며 기존 검증 로직/저장소는 건드리지 않았다).
