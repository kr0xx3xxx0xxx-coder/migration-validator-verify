1. 원인 분석 — 왜 이런 일이 발생했는가
════════════════════════════════════════════════════════════════════════════
핵심은 "stale 로컬 클론"이 맞지만, 정확한 발생 지점은 **작업트리가 아니라 인덱스(index)**다.

【사고의 기계적 원인】
  git commit 은 작업트리가 아니라 **인덱스를 커밋한다**. afe1c33 을 만들 때 실행한 명령은
    git add COMBO-PAIR-ENTRY-POINT-RESTORE-IMPLEMENT-RESUME.txt && git commit -m "..."
  로 파일 1개만 명시적으로 add 했고 -a / -A 는 쓰지 않았다. 그럼에도 47개 삭제가 함께
  기록된 이유는, 커밋 시점에 **인덱스에 그 47개 파일이 애초에 들어있지 않았기** 때문이다.
  HEAD(d8009b4)에는 있는데 인덱스에 없으면 그 차이는 '삭제'로 커밋된다.
  마찬가지로 인덱스에 옛 내용으로 들어있던 2개 파일은 '되돌림'으로 커밋됐다.

【인덱스가 낡아 있던 경위 — 저장소 안에 기록이 남아 있었다】
  피해 파일 중 하나인 CURRENT-RUNNING-TASKS-IDENTIFY-BY-COMMANDLINE.txt 에 앞선 세션이
  자기 push 방식을 이렇게 적어두었다(이번 사고로 잘려나간 바로 그 대목이다):

    "다른 세션이 같은 clone 에 미추적 파일을 남겨 두어 pull --rebase 가 불가능했으므로,
     작업트리를 건드리지 않는 임시 인덱스 방식으로 내 파일 1개만 origin/main 위에 얹어
     push 했다."

  즉 이 저장소는 여러 세션이 하나의 clone 을 공유하는데, pull --rebase 가 막히자 세션들이
  **작업트리와 인덱스를 갱신하지 않는 우회 push**를 반복해 왔다. 그 결과
    · origin/main 은 계속 앞으로 나갔고
    · 로컬 main 참조도 따라 움직였지만
    · 로컬 인덱스·작업트리에는 그 파일들이 **한 번도 들어온 적이 없다**
  이 상태에서 평범하게 git commit 을 하면, 인덱스에 없는 모든 파일이 삭제로 기록된다.
  afe1c33 이 정확히 그 경우다.

【뒷받침 증거】
  ① 삭제된 최상위 .txt 들이 사고 직후 디스크에는 **그대로 남아 있었다**(git status 에서
     untracked ?? 로 표시). 디스크에서 지워진 게 아니라 추적에서만 빠진 것 — 인덱스 원인의 직접 증거.
  ② 되돌아간 2개 파일의 diff 방향이 '최신 → 과거'였다. 예: SAMPLING-SKIP-TASK-SURVIVAL-CHECK.txt
     가 브라우저 검증 완료 기록(23:27:17 정상 완료, 스크린샷 7장 목록)을 잃고
     "미완 단계 : 브라우저 검증 — 지금 실행 중, 결과 파일 미생성" 상태로 후퇴했다.
     새 내용을 덮어쓴 게 아니라 낡은 내용이 다시 올라간 것이다.
  ③ 복구 착수 시점에도 **추적 파일 420개가 작업트리에 존재하지 않았다**. 이 clone 의 체크아웃이
     광범위하게 비어 있었다는 뜻이며, ①②와 같은 원인이다.
  ④ 훅·별칭·commit.all 같은 설정 요인은 없음을 확인했다(.git/hooks 활성 훅 없음, local config 정상).

【정리】
  단일 원인이 아니라 두 단계다.
    (a) 구조적 원인 : 공유 clone + pull 불가 → '임시 인덱스 우회 push' 관행이 인덱스를 낡게 만듦
    (b) 방아쇠      : 그 낡은 인덱스 위에서 평범한 git commit 을 실행
  (a)를 그대로 두면 누가 커밋하든 같은 사고가 반복된다. 그래서 이번에 (a)까지 해소했다(4항).

2. 복구 절차
════════════════════════════════════════════════════════════════════════════

4. 재발 방지 — 원인(a)까지 해소함
════════════════════════════════════════════════════════════════════════════
복구 push 직후, 이 clone 은 여전히 **추적 파일 420개가 작업트리에 없는 상태**였다. 이대로 두면
다음 세션이 git add -A 나 git commit -a 를 한 번만 실행해도 420개가 통째로 삭제된다.
실제로 push 전에 시도한 git pull --rebase 는 바로 이 미체크아웃 상태 때문에 거부됐다
  (error: cannot pull with rebase: You have unstaged changes)
— 앞선 세션들이 우회 push 를 택하게 만든 그 조건이 그대로 남아 있었던 것이다.

그래서 작업트리를 HEAD 와 일치시켜 이 뇌관을 제거했다.
    git checkout -- .          (추적 파일 420개 복원 · HEAD 와 동일한 내용이므로 이력 변화 없음)
  결과
    staged 변경 0건 / unstaged 변경 0건 (남은 것은 다른 세션의 미추적 신규 보고서 16건뿐)
    git pull --rebase origin main → "Already up to date." (정상 동작 복구)

이제 이 저장소에서 pull --rebase 가 다시 동작하므로 우회 push 관행을 쓸 이유가 없다.

【앞으로의 push 절차 — 이번 복구 커밋도 이 절차로 수행했다】
  1. git fetch origin  (또는 git pull --rebase origin main) 으로 먼저 원격과 동기화
  2. 내 파일만 add
  3. **커밋 직전 git diff --cached --name-status 로 담긴 목록을 눈으로 확인**
     — 내 파일 외에 D(삭제)나 예상 못 한 M 이 보이면 그 자리에서 중단할 것.
       이번 사고는 이 한 줄만 확인했어도 100% 막을 수 있었다.
  4. commit → push → git ls-remote origin main 으로 반영 확인
