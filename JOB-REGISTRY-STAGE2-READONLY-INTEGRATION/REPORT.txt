1. 무엇을 왜 했는가
────────────────────────────────────────────────────────────────────────────
직전 진단(BATCH-VALIDATION-PROGRESS-DASHBOARD-FEASIBILITY-DIAGNOSE)에서 확인된 사실은
"세 검증 유형의 job 저장소가 완전히 분리돼 있지만, 넷 모두 총량·완료량·현재대상·상태라는
같은 4요소를 이름만 다르게 갖고 있다"는 것이었다. 그래서 이번 2단계에서는 화면을 만들지 않고,
그 4요소를 하나의 읽기 전용 DTO 로 정규화하는 통합 계층만 만들었다.

화면을 나중으로 미룬 이유는 분명하다. 진행률 표시의 어려움은 UI 가 아니라 데이터 쪽에 있다.
저장소마다 분모의 단위가 다르고(청크/행/plan), 어떤 저장소에는 진행 시각 자체가 없다.
이 차이를 UI 에서 분기로 흡수하면 세 화면에 같은 분기가 세 번 복제된다. 통합 계층을 먼저 두면
그 분기가 한 곳에만 존재한다.

3. 설계에서 신경 쓴 지점 (그리고 그 이유)
────────────────────────────────────────────────────────────────────────────
(1) 단위 폴백을 3분기로 뒀다 — 청크 → 행 → 불확정.
    진단 §2 의 가장 중요한 발견은 "현재 기본 경로(DIRECT_STREAM_COMPARE)에서는 chunks_total 이
    아예 생기지 않는다"였다. 청크만 전제하면 정작 나이스급 복합 PK 실사용에서 진행률이 비어 보인다.
    세 번째 분기(분모 미상)에서는 total=None / percent=None 을 그대로 반환한다. 0% 로 표시하거나
    가짜 진행률을 만들지 않는다 — 이건 표시 정책이 아니라 데이터 정직성 문제다.

(2) 정체(stall)는 "참고 정보"로만 담고 판정하지 않는다.
    STAGE1 에서 추가된 last_progress_at 을 그대로 활용해 stall_seconds 를 계산하되,
    임계값 비교·상태 전환·자동 개입은 이 계층에 넣지 않았다. 진단 §7 이 경고한 대로,
    진행신호 gap 실측(내부망 필요)이 없는 상태에서 임계를 정하면 정상 job 이 '정체'로 오표시된다.
    대신 근거의 종류를 progress_signal(PROGRESS / START_ONLY / UNKNOWN)로 명시해서,
    화면이 "진행 시각이 실제로 있는 값"과 "시작 시각밖에 없어서 대신 쓴 값"을 구분할 수 있게 했다.
    일괄검증(B)은 진행 시각 컬럼 자체가 없으므로 last_progress_at=None 이고,
    extra.last_progress_at_available=false 로 그 사실을 응답에 남긴다.

(3) 읽기 전용을 '주장'이 아니라 '구조'로 보장했다.
    SQLite 접근은 전부 mode=ro URI 다. 이 연결로는 CREATE TABLE IF NOT EXISTS 를 실행할 수 없는데,
    그게 의도다 — 원본 서비스의 _connect() 는 조회할 때마다 DDL 을 실행하지만, 통합 계층은
    테이블이 없으면 "아직 실행 이력 없음"으로 처리하고 아무 흔적도 남기지 않는다.
    또한 원본 서비스의 stale 정리(6시간 초과 RUNNING → FAILED_INTERRUPTED)는 write 이므로
    여기서 수행하지 않는다. 그 결과 미정리 stale 행이 활성으로 보일 수 있다는 점은
    코드 주석에 한계로 명시했다(정리는 원본 경로의 책임).

(4) 부분 실패를 격리했다.
    한 소스 어댑터가 죽어도 나머지 소스는 그대로 반환하고, 사유는 warnings 로 노출한다.
    대시보드가 한 저장소 문제로 통째로 비는 것이 가장 나쁜 실패 모드이기 때문이다.
    에러는 raise 하지 않고 결과 객체(JobRegistrySnapshot.error_message / warnings)에 담는다(프로젝트 규칙).

(5) 전수검증(D)은 빈 목록 + 안내만 반환한다. 실행 구조가 없는데 가짜 job 을 만들어 넣지 않았다.

4. 검증 — 무엇을 실제로 확인했고, 무엇을 못 했는가
────────────────────────────────────────────────────────────────────────────
내부망 DB 는 이번에도 전 노드 TCP 타임아웃이었다(Oracle 192.168.0.151:1523/1524,
내부 PG 192.168.0.150:5433/5434 — 15:20 측정). 그래서 소스별로 가능한 최대 수준의 실측을 택했다.

  A 개별검증 — 운영과 동일한 코드 경로를 in-process 로 구동.
    reimport_job.start_or_attach 로 실제 job 을 띄우고, routes/agg_diff_route.py:282-296 의
    _pcb 배선을 그대로 재현해 진행 신호를 발행했다. 두 전략 모두 확인:
      · 청크 전략  : chunks 24/120 → unit=chunk, 20.0%, current_target=2400000(last_processed_key)
      · 행 전략    : 청크 없음 → unit=row, 72000/1200000 = 6.0%  ← 단위 폴백이 실제로 작동
    종료 후에는 active=false / stall_seconds=None(경과를 재지 않음)까지 확인.

  B 일괄검증 — **운영 SQLite 의 실 데이터**로 확인.
    운영 DB 의 batch_execution_state 에는 실제 실행 이력 386건이 있었다. 그중 최신 1건
    (exec_a2c0630406254adf · GRP_202607240925308436 · NXDNP.MV_ORA_XDIFF_TGT_2)을 읽기 전용으로
    조회해 DTO 로 정규화했다 — 5/5 = 100.0%, unit=row, last_progress_at=null(컬럼 부재).
    진행 중(RUNNING) 케이스는 운영 DB 에 활성 행이 0건이라, 임시 DB 에 원본 서비스 함수
    (acquire_run_lock + update_progress)로 실제 생성해 12/40 = 30.0% 를 확인했다.

  C 통계검증 — 운영 DB 의 batch_stats_execute_run 은 행 0건이라 실 데이터가 없다.
    임시 DB 에 원본 서비스 함수(_create_run_record + _update_run_progress)로 실제 생성.
    3/8 = 37.5%, unit=plan, updated_at → last_progress_at 매핑, progress_signal=PROGRESS 확인.
    세 소스 중 진행 시각이 실제로 존재하는 유일한 소스다.

  HTTP — 별도 인스턴스(:8011)를 **인증 ON** 으로 띄워 실 HTTP 로 호출.
    운영 auth_users.json 은 건드리지 않고 MV_AUTH_USERS_FILE 로 임시 계정 파일만 분리했다.
      · 무인증 GET /jobs/active            → 401 (인증 강제 확인)
      · 인증   GET /jobs/active            → 200, counts/warnings/notes 정상
      · 인증   GET /jobs/active?source=... → 200, 소스 필터 적용
      · 인증   GET /jobs/batch:exec_a2c0630406254adf → 200, **운영 실 데이터** DTO 반환
      · 인증   GET /jobs/stats:no_such_run → 200 found=false + 한국어 사유
    포트 8000 은 인증 ON 이라 자격증명 없이는 미들웨어가 라우팅 전에 401 을 돌려준다.
    따라서 8000 에서는 "재기동 후 정상 응답(401)"까지만 확인했고, 라우팅 200 확인은
    같은 app 객체를 인증 ON 으로 띄운 8011 인스턴스에서 수행했다. 이 점은 정직하게 밝혀 둔다.

  읽기 전용 보증 — 전 phase 전후로 운영 DB 파일의 sha256 을 비교했다.
    조회 전/후 모두 25d78ba31b025471 — 동일. 통합 계층은 운영 DB 를 변경하지 않는다.

  단위 테스트 19건 전부 통과. 그중 2건은 읽기 전용 보증 전용 테스트다
  (테이블 없는 DB 를 조회해도 DDL 부작용이 없음 / 조회 전후 행 내용 완전 동일).

7. 남은 것 / 다음 단계에 넘기는 것
────────────────────────────────────────────────────────────────────────────
  · 정체 경고 임계(STALL_TTL)는 여전히 미정이다. 내부망 복구 후 heartbeat gap 실측이
    선행돼야 한다. 그 전까지 stall_seconds 는 숫자만 표시하고 경고로 승격하면 안 된다.
  · 일괄검증(B)에 진행 시각 컬럼이 없다는 점은 통합 계층에서 메울 수 없다.
    필요하면 원본 저장소에 updated_at 을 추가하는 별도 단계가 있어야 한다(이번 범위 밖).
  · 3단계(현황판 화면)는 반드시 ui/js_job_dashboard.py 로 분리하고, 폴링은 단일 타이머
    1개로 목록을 한 번에 받아야 한다(패널별 독립 폴링 재발 금지). JS 주석에 '*/' 금지.
  · 개별검증(A)/일부 일괄검증 상태는 in-memory 라 서버 재시작 시 목록이 비워진다.
    이는 대시보드 결함이 아니라 기존 구조의 성질이며, API 가 notes 로 그 사실을 함께 반환한다.
