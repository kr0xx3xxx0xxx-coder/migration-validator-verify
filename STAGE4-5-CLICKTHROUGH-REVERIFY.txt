DB 접속 재시도 루프 대응 — 진단 결과
────────────────────────────────────────────────────────────
직전 시도가 오래 걸렸던 원인은 "DB 접속 재시도"가 아니라 **픽스처 선택 문제**였다. 최초 시도는
NXDNP.MV_ORA_XDIFF_SRC/TGT(250,000행)에 GROUP BY C_DATE(무버킷, 사실상 고유값에 가까운 컬럼)+SUM 2열을
선택해 통계검증을 실행했는데, 420초 폴링에도 완료 신호(window._execPlanRun 갱신)를 받지 못했다(무버킷
날짜 컬럼의 GROUP BY 가 행수에 근접하게 폭발 + 이 환경은 Oracle Free 라 병렬실행 불가
[[project_oracle_free_no_parallel_execution]] 이라 대량 그룹 집계가 매우 느림). 그 잔여 부하가 이후
별도 브라우저 컨텍스트의 COUNT 요청까지 지연시켜(같은 asis/tobe 페어) 연쇄 실패를 냈다(2단계 COUNT
status=null로 무응답, 3단계 "선택 적용" 클릭조차 실패).
→ NXDNP.MV_COMBO_SRC/TGT(1,200행, STATUS_CD 3종×DEPT_CD 4종)로 픽스처를 교체해 완전히 해소했다
(RUN1 실행 2.57초, 통계검증 SQL 생성 3.11초 등 전부 수 초 이내). 직접 SQL로 사전 확인한 결과 이 픽스처는
1축(STATUS_CD만)으로는 원본/목적 합계가 서로 상쇄돼 전부 일치하지만, 2축(STATUS_CD+DEPT_CD)으로 보면
4개 그룹(A/D01, A/D02, P/D01, P/D02)에서 실제 불일치가 드러난다(2026-08-08 직접 SQL 실측) — 정책 상한
미만 축 선택·실행 완료 실행결과·실불일치 드릴다운이 전부 필요한 이번 재검증에 정확히 들어맞는 실데이터.

3순위 — "설정 실행당시/현재 다름" 배너 오탐/정탐
────────────────────────────────────────────────────────────
case A(오탐 없음) 실제 클릭 시퀀스:
  1) RUN1(GB=STATUS_CD+DEPT_CD, SUM=AMT → 2/1, 정책 상한 3/3 미만) 실행 완료.
  2) 5단계 결과확인으로 실제 이동 → 배너 판정(hasBanner=false, curGb=[STATUS_CD,DEPT_CD],
     curSum=[AMT] — 실행 당시와 동일) → 배너 없음 확인.
판정: PASS — 정책 상한 미만 선택이어도 오탐이 없다(PROBE case A와 일치).

case B(정탐 — 실제로 다를 때만 뜨는지) — **실 클릭으로 완주하지 못함**:
  1) 5단계에서 3단계로 실제로 돌아가 DEPT_CD 체크박스를 실제로 해제 시도(GB 를 1/1 로 축소하려는 시도).
  2) Playwright 자체가 두 차례 독립 재현에서 **"Locator.uncheck: Clicking the checkbox did not change
     its state"** 로 실패 — 클릭 이벤트(onchange="checkLimit(...)")가 정상 발생했지만 체크 상태가 클릭
     즉시 원상복구됨(재현 스크립트 _diag_case_b2.py, 로그 첨부:
     _item3_caseB_checkbox_revert_diagnostic.log). checkLimit() 자체는 개수>3 일 때만 강제 해제하는
     코드(ui/tabler_renderer.py:24487-24496)라 이 경로가 직접 원인은 아니었고, 정확한 원인(재렌더
     타이밍/상태 동기화 등)은 이번 재검증 범위에서 추가로 파고들지 않았다(코드 수정 금지 지침).
  3) COMBO 픽스처는 GB 후보가 STATUS_CD/DEPT_CD 둘뿐(둘 다 이미 실행에 쓰임, data-default="1")이고
     SUM 후보도 AMT 하나뿐이라, 이 체크박스가 실 클릭으로 안 풀리는 한 "실행 당시와 다른 조합"을
     COMBO 안에서 만들 다른 방법이 없었다.
판정: 미확정(case B 자체는 이번 재검증 범위에서 재현 못함). **주의**: 이는 배너 판정 로직(3순위 수정
자체)의 결함이 아니다 — 직전 PROBE(window._mvStage4GbSel 직접 대입으로 "실제로 다름" 상태를 만든 뒤
_mvRenderResultGrid 재호출)는 case B 를 이미 실측 확인했고, 이번 case A 에서도 curGb/curSum 이 실제
실행값과 정확히 동기화됨을 실 클릭 경로로 재확인했다(배너 판정 자체의 입력값 배선은 정상). 이번에 새로
발견된 것은 **후보 체크박스가 실행 이후 실 클릭으로 해제되지 않는다는 별개의 현상**이며, 재검증 중 발견한
문제이므로 지침대로 고치지 않고 여기 별도 보고한다 — 의도된 잠금(실행에 쓰인 기본 후보는 재선택 없이는
불변)인지 실제 결함인지는 추가 확인이 필요.
