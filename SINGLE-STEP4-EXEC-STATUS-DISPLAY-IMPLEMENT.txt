  진단 SINGLE-STEP4-INLINE-PROGRESS-FEASIBILITY-DIAGNOSE 권장안 A-3+A-1 구현.

  4단계에 머무는 동안 화면에 안 보이던 것을 노출하고, 경과시간 카운트업을 추가.

■ 구현 (ui/tabler_renderer.py 단일 파일, 백엔드 0줄)
  1) #mvExecStepProgress 영역 신설 + SINGLE_STEP_CARDS.validation(4단계 pane) 등록.
     기존 #mvExecStepError(실패) · #mvExecStepResult(성공요약)와 같은 계열의 세 번째 영역이며
     셋은 상호배타로만 노출된다.
  2) 경과시간 1초 카운트업 — _mvShowExecStepProgress(label) / _mvClearExecStepProgress().
     60초 미만 '45초', 이상 '1분 05초'. 매초 경과 숫자만 갱신(박스 재렌더 없음 → 스피너 유지).
  3) 다중 세트 '세트 i/N' 문구를 이 영역에도 렌더(_runExecutePlanSets).
     기존 #executeOut 렌더는 그대로 유지 — 이동이 아니라 '추가 렌더'.
     세트 문구 이전 구간(무음)에 '실행 계획(GROUP BY 세트) 생성 중…' 문구 추가.
  4) 최초 노출 시 1회 scrollIntoView(block:'center') — 검증 중 발견한 갭(아래 ■추가수정).
  5) 종료 정리 6지점: runExecute finally(단일) / plan-sets finally / _execAbort /
     resetExecuteResultOnly / 오류 표시 / 성공요약 표시. 타이머(setInterval)도 함께 해제.
  6) 진행률(%)·추정 진행바는 만들지 않음 — /execute 는 집계 SQL 단일 실행이라 서버에 중간
     진행 신호가 원리적으로 없다. 근거 없는 추정치는 가짜 진행률이 되므로 A-2 는 범위 제외.
     대신 박스에 "진행률(%)은 표시하지 않습니다 — 집계 SQL 한 번의 실행이라 완료 전에는
     중간 진행 신호가 없습니다" 사유를 명시.
  7) 자동 5단계 이동 금지 정책 불변(표시만 추가, 뷰 이동 없음).

■ 비판적 검토 / 남은 위험
  1) 취소 버튼 기대 불일치: 진행 표시가 붙으면 사용자는 '중단'을 기대하지만, 4단계 실행은
     cancel_token 미전달로 중단 불가(진단서 기록). 이번 범위 밖 — 필요 시 별도 과제.
  2) 경과시간은 '클라이언트 시계' 기준이라 서버 처리시간(processing_ms)과 다르다
     (네트워크·렌더 포함). 표시는 '경과'라고만 하고 서버 시간으로 오인될 문구는 쓰지 않았다.
  3) '세트 i/N' 은 세트 단위 진행일 뿐, 세트 '내부' 진행은 여전히 무신호다(원리적 한계).
  4) A-2(추정 진행바) 미구현 — 의도적 제외. 추정 근거(직전 processing_ms) 표기 설계가
     확정되기 전에는 붙이지 않는다.
  5) 관측 하니스 주의(코드 결함 아님): 일부 증적 JSON 의 run.elapsed_sec 이 180초대인 것은
     playwright element screenshot 이 '사라진 요소'를 기다린 하니스 대기 때문이다.
     실제 실행 소요는 같은 파일의 run.exec_wall_from_frames_sec(1.3~2.9초)가 정확하다.
  6) 라이브 실행 중 COUNT 단계가 간헐 ERROR 로 떨어지는 회차가 있었다(재실행 시 정상).
     동시 세션이 같은 오라클/포트를 사용 중이라 환경 경합으로 판단 — 이번 변경과 무관하며,
     성공 회차 기준으로만 증적을 채택했다.
