작업명 : REIMPORT-DRILLDOWN-NOTICE-DEDUP-AND-TAB-EXPAND-STATE-PERSIST-FIX

════════════════════════════════════════════════════════════════════════════════
1. 무엇을 고쳤나
════════════════════════════════════════════════════════════════════════════════

개별검증 5단계(결과 확인)의 "재이관 대상 상세" 화면에서 두 가지를 고쳤다.

A) 그룹 상세 머리말 3줄 → 1줄
   조기중단(표시 상한 초과) 그룹을 펼치면 같은 사실을 세 번 말하고 있었다.

     1) 재이관 대상 전체 101건 (표시 상한 100건 · 실제는 100건 초과·총수 미확정)
        · 현재 1~5 표시 · 1/20페이지
     2) ⚠ 이 그룹 — 표시 100건 / 실제 100건 초과 · 총수 미확정(조기중단)
     3) 선택 그룹: STATUS_CD=P

   1)과 2)는 문장만 다를 뿐 같은 내용이고, 3)은 바로 위에 있는 그룹 행이 이미 보여주는
   정보였다(트리 병합 이후로는 그룹 행 → 상세가 한 표에 붙어 있다). 페이지 정보
   ("현재 1~5 표시 · 1/20페이지")도 하단 페이지 컨트롤에 그대로 또 있었다.

   → 한 줄로 합쳤다.

     ⚠ 재이관 대상 전체 101건 중 100건 표시 · 실제 100건 초과로 총수 미확정(조기중단)

   버린 것은 '중복'뿐이다. 표시 건수 / 실제 건수(확정·미확정) / 저장 경로(대표 표본만
   저장 · 저장 상한)라는 사실은 전부 이 한 줄에 남아 있고, 페이지 정보는 하단 페이지
   컨트롤에 그대로 있다. 경고가 없는 정상 케이스(그룹 불일치 ≤ 경계)는 기존 머리말을
   그대로 쓴다 — 이번 정리는 조기중단 경고 국면에만 적용된다. 다만 '선택 그룹:' 줄은
   트리로 그려지는 경로에서만 제거했고, 그룹 행이 없는 폴백 렌더(비트리)에는 식별
   정보가 필요하므로 그대로 남겼다.

B) 탭(전체/COUNT/AMT/QTY) 전환 후 그룹 펼침 상태 유지
   그룹을 펼쳐 레코드를 보다가 COUNT 탭에 갔다 전체 탭으로 돌아오면 펼침이 통째로
   사라져 매번 다시 클릭해야 했다.

   원인은 '펼침 상태'가 DOM 에만 존재했다는 것이다. 항목 필터 탭은 결과 tbody 를
   innerHTML 로 통째 교체하는데(_execSetColFilter → _execRenderResultPage / _execSrvGo),
   펼침은 "패널 <tr> 이 표 안에 꽂혀 있는가"로만 표현돼 있어 교체와 동시에 소멸했다.
   오늘 앞서 고친 '일치 행 숨기기' 라벨 문제와 계열은 같지만(재렌더가 상태를 날린다)
   근본 원인은 다르다 — 그쪽은 상태가 두 개라 라벨이 어긋난 것이었고, 이쪽은 상태가
   아예 없었다.

   → 펼친 그룹 하나를 기억했다가, 재배선 단일 지점에서 되살린다.
      - 기억: data-row-key(그룹 식별) + 그룹 내부 페이지 + 방향(재이관/목적단독)
              + 실행계획 fingerprint
      - 복원: _mvWireRowsFromCache(탭 전환·페이지 이동·서버 페이지 렌더가 모두 지나는
              단일 재배선 지점) 직후, 그 그룹 행이 '지금 탭 목록에도 있으면' 다시 펼친다.
      - 데이터 재조회 로직은 손대지 않았다. 오늘 앞서 들어간 준비 캐시 재사용
        (REIMPORT-DRILLDOWN-TAB-SCOPE-CACHE-AND-COLUMN-SPLIT-FIX) 덕분에 복원은
        _mvPkPageCache 히트로 끝난다 — 실측에서 추가 pk-records 요청 0회.

   경계 조건도 요구대로 처리했다.
      - 해당 탭 필터 결과에 그 그룹이 없으면 자연히 접힌 채로 두되 상태는 지우지 않는다
        → 원래 탭으로 돌아오면 다시 펼쳐진다.
      - 여러 그룹 중 펼친 그룹만 유지되고 나머지는 접힌 채로 남는다.
      - 사용자가 직접 접으면 상태도 지운다 → 탭을 다녀와도 되살아나지 않는다.
      - 새 통계검증 실행/설정 변경으로 캐시를 비우는 지점(5곳)에서 펼침 상태도 같이
        무효화하고, 복원 직전에 실행계획 fingerprint 를 한 번 더 대조한다(2중 방어).

· AFTER 를 라이브 오라클로 재확인하지 못했다. 원인은 코드가 아니라 내부망 호스트
  192.168.0.151 도달 불가(TCP timeout)이며, 복구되면 아래 한 줄로 그대로 재현된다.
      MV_TAG=AFTER MV_FIXTURE=cspk python scripts/dev_e2e/reimport_drilldown_notice_dedup_and_tab_expand_verify.py
      MV_TAG=AFTER MV_FIXTURE=demo python scripts/dev_e2e/reimport_drilldown_notice_dedup_and_tab_expand_verify.py
  라이브 BEFORE 와 합성 BEFORE 가 글자까지 일치하므로, 합성 AFTER 의 관측이 라이브에서
  달라질 이유는 코드상 없다(관측 대상이 전부 클라이언트 표시·상태 로직이다).

· 펼침 상태는 '한 번에 한 그룹'만 기억한다. 원래 화면이 동시에 한 그룹만 여는
  SINGLE-OPEN 정책이라 정책과 일치하지만, 나중에 다중 펼침을 허용하게 되면 이 상태를
  배열로 바꿔야 한다.

· 상태는 메모리(window)에만 둔다. 새로고침하면 사라진다 — 새로고침은 '처음 진입'이라는
  기존 화면 정책과 같은 방향이라 그대로 뒀다.
