[항목1] count_precheck_service 배치루프 scope 적용 — 물리 연결 횟수 실측
  방법: Neon 테스트 테이블 4쌍(TB_CUSTOMER/TB_ORDER/TB_STD_GRADE/TB_CODE,
  docs/handoff_backlog.md 기재 스냅샷)을 대상으로 run_count_for_row() 를
  (A) scope 미적용(수정 전 동작 재현) / (B) request_connection_scope 로 감싼
  상태(수정 후 실제 동작)로 각각 호출, count_exec_probe(MV_COUNT_EXEC_PROBE=1)
  의 real_connection_open_count(=_open_real_connection 실호출 횟수, scope
  유무와 무관하게 무조건 계측되는 단일 chokepoint)로 비교.
  결과:
    (A) scope 미적용 : 물리 연결 open 16회 (4테이블 × 4회 — row_count_estimate
        1회 + COUNT source/target 등, scope 없어 매 조회마다 신규 connect)
    (B) scope 적용   : 물리 연결 open  2회 (source 1 + target 1 — 4테이블
        전체가 단 1개씩의 연결을 재사용, connection_pool.metrics() 로도
        physical_open=2·checkout=2·returned=2 확인)
    감소량: 14회(16→2). (B)에서 항목3(_pg_fetch_scalar 풀 경유 전환)이
    누락됐다면 row 당 raw connect 가 scope 를 우회해 추가로 4회가 더
    잡혔을 것 — 정확히 2회로 수렴한 결과가 항목1·항목3 두 수정이 함께
    맞물려 동작함을 방증.
    참고: COUNT 대상 테이블(TA_CUSTOMER 등)이 현재 이 Neon 브랜치의
    실제 스키마와 달라(테이블명 상이 — 다른 Neon 브랜치/스냅샷으로 추정,
    이번 수정과 무관한 기존 문서-실DB 스냅샷 불일치) 각 row 의 COUNT 결과는
    ERROR("테이블이 존재하지 않음")였음. 단 물리 연결 자체는 실제 Neon
    서버와의 정상 TCP+인증 handshake 였고 SQL 도 실제로 서버까지 전송되어
    Postgres 가 실오류를 반환한 것으로, 연결횟수 측정치의 유효성에는
    영향 없음.
