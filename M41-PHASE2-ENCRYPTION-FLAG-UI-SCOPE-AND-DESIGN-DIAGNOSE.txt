작업명 : M41-PHASE2-ENCRYPTION-FLAG-UI-SCOPE-AND-DESIGN-DIAGNOSE
⚠️ 추가 작업 필요 - Phase2 설계 범위는 정리했으나, 착수 전 반드시 선행돼야 할 블로커(정의서 실물 구조 미확인)를 발견함(코드 변경 없음)

■ 0. 착수 전 사전검토(CLAUDE.md 기능/구조 변경 응답 형식)

  - 요청 요약 : Phase1(저장소+배선)은 완료됐으나 값을 채울 UI가 없어 상시 OFF인 상태를 풀기 위해,
    Phase2(정의서 업로드/입력 UI) 착수 전 설계 범위(기존 인프라 재사용성/정의서 구조/UI 배치/저장
    연결)를 정하는 조사. 이번 지침은 설계까지만이고 구현은 하지 않았다.
  - 긍정적 효과 : (조사로 확인된 것) 정의서 헤더 파싱 로직(load_encrypted_columns_from_definition)과
    저장 함수(save_flag)가 이미 존재해 신규 코드량이 예상보다 적다. 엑셀 바이트 로더(workbook_loader.py)도
    완전 범용이라 그대로 재사용 가능하다.
  - 구조적 문제점 : 아래 1~4절에서 상세. 요약하면 (a) 기존 "이관쿼리 업로드" 파서/이력테이블은 전용
    하드코딩이라 재사용 불가 부분이 크고, (b) 정의서의 실제 헤더 구조를 뒷받침하는 근거가 저장소
    어디에도 없으며(★가장 심각), (c) 좌측메뉴 완전 신규 그룹 신설은 F11(그룹 8→7 정리) 테스트 계약과
    충돌한다.
  - 운영상 위험 : "실물 정의서 없이 헤더 별칭을 설계"하는 것 자체가 운영 위험이다 — 실제 정의서 헤더가
    설계 시 가정과 다르면, 업로드는 "성공"하지만 파싱 결과가 0건이라 여전히 상시 OFF인 상태가 이번엔
    조용히(에러 없이) 재현된다. Phase1 진단 때와 동일한 성격의 결함이 UI 계층에서 재발할 수 있다.
  - heuristic / scoring / explainability 영향 : 목적지컬럼명/암호화여부 열 탐지는 기존에 이미
    "명시필드만, 자동탐지 없음"으로 구현돼 있어 이 부분은 안전하다. 다만 정의서에 "테이블 식별" 열이
    있는지조차 코드로 확인된 바 없어(2절), 이 축을 추측으로 설계하면 새로운 heuristic 하드코딩이 된다.
  - 권장 대응책 : Phase2를 "구현" 이전에 "정의서 실물 샘플 확보" 단계로 한 번 더 쪼갠다(아래 5절).
  - 지금 구현 여부 : 보류(정의서 실물 샘플 확보 선행 조건부) — 샘플 확보·헤더 확정 후 다음 지침으로
    구현 착수 권장. 샘플 없이 바로 구현에 들어가면 "헤더 추측 설계"가 되어 CLAUDE.md 비판적 검토
    의무의 heuristic 하드코딩 증가 항목에 정면으로 걸린다.

■ 1. 기존 업로드 인프라 재사용 가능성 (코드 조사 결과)
────────────────────────────────────────────────────────────

  1-1. "이관쿼리 업로드"가 실제 다루는 것 : SQL 텍스트가 아니라 엑셀 워크북(.xlsx/.xlsm)이다.
    시트 안에 INSERT INTO ... SELECT ... 형식 이관 SQL이 셀 값으로 들어있는 구조. 지원 포맷 3종
    (services/migration_workbook_parser.py:16-19,85) — 이관쿼리_업로드/이관SQL목록/batch_upload.

  1-2. 그대로 재사용 가능한 것
    - services/workbook_loader.py::load_workbook_view() — 엑셀 raw bytes → WorkbookView(순수
      dataclass). "openpyxl 을 직접 여는 코드는 여기서만 호출"(모듈 docstring) 원칙이 이미 있어
      엑셀 형식 자체는 완전 범용. requirements.txt:7 openpyxl==3.1.5.
    - services/analysis/encrypted_column_policy.py::load_encrypted_columns_from_definition
      (85행) — "컬럼매핑정의서 → 암호화여부" 파싱 로직이 이미 구현돼 있다. 헤더 별칭까지 포함:
        _TARGET_COL_HEADER_ALIASES(51행) : 목적지컬럼/목적지컬럼명/목적컬럼/... /column
        _ENC_HEADER_ALIASES(39행) : 암호화여부/암호화/암호화대상/암호화컬럼/encrypt/enc_yn/...
        is_encrypted_value(63행) 진리값 집합 : y/yes/true/t/1/o/on/암호화/대상/적용/encrypt/...
    - services/column_encryption_flag_store.py::save_flag() — 영속 저장 로직 완비(4절 참고).

  1-3. 재사용 불가 · 신규 필요한 것
    - services/migration_workbook_parser.py::parse_migration_workbook() — 시트탐색 로직(표준
      시트명 → 필수헤더 보유 시트 → 모호성/없음 오류, 85행 _STANDARD_SHEETS)의 "패턴"은 참고
      가치가 있으나, 8개 논리필드(target_schema/target_table/migration_sql 등, 88-98행)가
      이관쿼리 전용으로 하드코딩돼 있어 그대로는 못 쓴다. 정의서용 얇은 파서를 신규로 만들되,
      이 파일의 설계 패턴(고정 열 위치 금지, 헤더명 기준 탐색)만 따르는 것을 권장.
    - 업로드 HTTP 라우트 자체가 없다 — encrypted_column_policy.py 모듈 docstring이 명시:
      "이 저장소에 값을 채우는 방법은 이번 단계에서 UI 가 아니라 이 모듈 함수(save_flag)를
      직접 호출하는 관리자 스크립트뿐이다." 즉 업로드 API 엔드포인트가 전혀 배선돼 있지 않다.
    - 업로드 이력(history) 재사용 불가 : mv_upload_row_result(services/upload_audit_store.py:46-67)는
      migration_sql/target_schema/target_table 등 이관쿼리 전용 필드로 짜여 있어 스키마 오염 없이
      얹을 수 없다. column_encryption_flag 테이블(save_flag 대상)에는 batch_id 등 이력 축이
      전혀 없다 — "업로드 이력 화면"까지 범위에 넣으려면 이력 축을 별도로 설계해야 한다(이번
      단계는 이력 없이 단순 upsert 결과 요약만 화면에 보여주는 것으로 범위를 좁히는 것을 권장 —
      아래 3-4절).
    - ui/tabler_renderer.py 의 "이관쿼리 업로드" 탭(2287행 이하 메뉴, 탭 본문은 별도 위치)은
      이관쿼리 전용 DOM id/JS 함수와 강결합돼 있어 컴포넌트 자체 재사용은 안 되고, 시각적
      패턴(드롭존/미리보기 그리드)만 참고 가능.

■ 2. 정의서 구조 파악 — ★이번 조사에서 발견한 최우선 블로커
────────────────────────────────────────────────────────────

  이번 지침 본문이 전제한 "나이스/에듀파인 실데이터 컬럼매핑정의서가 주제영역(17개 세분류),
  컬럼한글명, 암호화여부, DEFAULT/변환규칙 컬럼을 보유한다"는 구조 기록을, docs/ 전체(docs/archive/
  세션로그 22개 전수 포함), BACKLOG.md(저장소에 파일 자체 없음), docs/handoff_backlog.md 어디에서도
  찾지 못했다. "02-migration-validator-session.md" 라는 파일명도 저장소에 존재하지 않는다
  (docs/archive/의 "02." 번호 파일은 migration_validator_driver_connection_notes.md 로 무관 내용).

  오히려 유일하게 이 주제를 다루는 기록은 사용자 홈 디렉터리 에이전트 메모리 파일
  (project_file_managed_persistent_data_inventory.md)이며, 원문은 다음과 같다(그대로 인용):
    "나이스/에듀파인 컬럼매핑정의서 파일은 저장소에 없다. load_encrypted_columns_from_definition
    가 요청 payload 로 받을 뿐이고, mv_mapping 테이블도 0행이다 → 암호화여부가 어디에도
    저장되지 않아, 정의서를 다시 안 실어보내면 재검증 때 암호화 컬럼 제외가 조용히 풀린다."
  즉 "확인했다"는 과거 근거 자체가 오히려 **정의서 실물이 없다는 진단**을 담고 있다 — "주제영역
  17개 세분류" 같은 구체 스펙의 출처는 이번 조사로 끝내 확인되지 않았다.

  코드가 실제로 다루는 구조는 훨씬 좁다(1절 load_encrypted_columns_from_definition 재확인):
    - headers(1행) + rows(데이터 행 리스트)라는 범용 페이로드일 뿐, 시트/컬럼 전체 스펙이 없다.
    - 헤더 매칭 대상은 "목적지컬럼명" 1열, "암호화여부" 1열, 단 2개뿐이다.
    - **원본 테이블명/컬럼명 열, 목적지 테이블명(=table_key) 열은 코드 어디에도 없다.** 즉
      "이 컬럼이 어느 테이블 소속인지" 식별할 방법이 현재 파싱 로직에 전혀 없다.
    - 주제영역/DEFAULT/변환규칙 열에 대응하는 코드는 존재하지 않는다.

  파급 효과 : column_encryption_flag_store.save_flag()는 UNIQUE(project_id, table_key,
  column_name) 3축을 요구하는데(services/column_encryption_flag_store.py:82-92), 현재 파싱
  로직은 이 중 table_key 를 채울 열을 전혀 찾지 않는다. **정의서에 "목적지 테이블명" 열이
  실제로 있는지조차 실물 없이는 확답할 수 없다.** 실물 샘플(1부 이상) 없이 헤더 별칭을 확장
  설계하면, 담당자가 실제 파일을 올렸을 때 매칭 실패로 파싱 0건 → 여전히 상시 OFF가 조용히
  재현되는 시나리오가 UI 계층에서 그대로 반복될 위험이 있다(운영상 위험 항목과 동일 근거).

  ▶ 권고 : Phase2 구현 착수 전, 사용자로부터 실제 컬럼매핑정의서 엑셀 샘플을 최소 1부 확보해
  시트명/헤더 목록/테이블 식별 열 유무를 실측 확인하는 절차를 선행 단계로 넣을 것을 권한다.

■ 3. UI 배치 위치 설계
────────────────────────────────────────────────────────────

  3-1. 현재 좌측 메뉴 실측(ui/tabler_renderer.py:2287-2420, 7그룹/15항목 — 준비중 2건 포함):
    1. 프로젝트 — 프로젝트 목록 / 검증 그룹 관리
    2. 데이터 준비 — 이관쿼리 업로드(id=nav-queryupload) / 메타데이터 수집(id=nav-metadata) /
       DB 프로필·검증 경로(id=nav-settings)
    3. 검증 실행 — 개별검증 / 일괄검증 / 전수검증[준비중]
    4. 현황 — 검증 현황판
    5. 결과/진단 — 실행 이력 / 검증 결과 상세 / 진단 이력
    6. 검증 기준 — 후보추천 정책 / 시맨틱 사전[준비중]
    7. 기반정보/설정 — DBMS 실행 지원

  3-2. F11(그룹 8→7) 정리 취지 재확인 — 근거 커밋 05d4fa1(주석 2278-2285행 인용):
    "제거된 항목은 전부 '클릭 무반응(죽은 링크)'로 실측된 것... 변화: 그룹 8→7 / 항목 28→15 /
    준비중 15→2 / 죽은 링크 14→0." 즉 그룹수 축소 자체가 목적이 아니라 **죽은 링크 제거가
    목적**이었다. tests/test_ui_menu_ia_restructure.py 가 현재 7개 그룹 라벨을 **하드코딩
    검증**하므로, (c) 완전 신규 그룹을 신설하면 이 테스트를 고쳐야 하고 F11 성과를 되돌리는
    모양이 된다 — CLAUDE.md "완료된 모듈 수정 시 사용자 확인" 예외 사유에 해당.

  3-3. (b) "메타데이터 수집 메뉴에 통합" 옵션 재정의 필요 : 조사 결과 "메타데이터 수집"은
    그룹이 아니라 "데이터 준비" 그룹 소속 **단일 탭 항목**이다(그런 이름의 그룹 자체가 없음).
    지침 원문의 (b)를 문자 그대로 보면 대상이 존재하지 않는다 — "메타데이터 수집 탭 화면
    내부에 섹션 추가"로 재해석해야 성립한다.

  3-4. 권장안 : (a) "이관쿼리 업로드" 화면 내 탭/섹션 추가.
    근거 : ①그룹/항목 수 변화가 없어 F11 취지(항목 최소화)를 해치지 않는다. ②"컬럼매핑정의서"는
    "이관쿼리 업로드 → 메타데이터 수집" 워크플로 사이에 끼는 인접 준비 단계라 워크플로 상
    자연스럽다. ③테스트 회귀(7그룹 하드코딩 검증) 위험이 없다.
    차선안 : (b')는 "데이터 준비" 그룹에 4번째 형제 항목으로 신설(그룹은 유지, 항목만 15→16) —
    그룹 신설(c)보다는 F11 취지 훼손이 작지만, 신규 항목 추가이므로 3-2절 테스트 확장은 필요.
    (c)는 비권장(테스트 계약 정면 충돌, 그룹 신설 회피 원칙에 반함).

■ 4. 저장 연결 설계
────────────────────────────────────────────────────────────

  services/column_encryption_flag_store.py::save_flag(*, project_id, table_key, column_name,
  is_encrypted, source="정의서", conn=None, db_path=None) 을 그대로 재사용한다(신규 upsert
  로직 불필요). 이미 conn 파라미터를 받으므로, 업로드 파싱 결과(행 리스트)를 순회하며 단일
  커넥션으로 묶어 반복 호출하면 된다(신규 "bulk 저장 함수"를 별도로 만들 필요가 원칙적으로
  없다 — CLAUDE.md "이미 있는 함수 재사용" 원칙에 부합).

  단, 이 배선은 2절 블로커에 정면으로 의존한다 : table_key 값을 정의서의 어느 열에서 가져올지
  결정되지 않으면(=정의서에 목적지 테이블명 열이 실제로 있는지 미확인) 이 저장 루프 자체를
  설계할 수 없다. 즉 4절은 2절 실물 샘플 확보 이후에만 확정 가능하다.

  project_id는 업로드 화면에서 사용자가 선택한(또는 이미 선택돼있는) 작업 프로젝트를 그대로
  쓰면 된다(기존 "메타데이터 수집" 탭이 이미 프로젝트 선택 UI를 쓰고 있어 동일 패턴 재사용 가능).
