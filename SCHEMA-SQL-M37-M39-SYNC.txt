5. 비판적 검토 — 구조적 위험 1건 발견(CLAUDE.md 비판적 검토 의무)
════════════════════════════════════════════════════════════════════════
db/schema.sql 은 기존에는 전부 "CREATE TABLE/INDEX IF NOT EXISTS" 로만 구성돼 몇 번을 재실행해도
안전했다(db/init_db.py 가 executescript() 로 그대로 실행). 이번에 지시대로 추가한 mv_db_preset
의 ALTER TABLE ADD COLUMN 3줄은 IF NOT EXISTS 가드가 없어(SQLite ALTER TABLE ADD COLUMN 문법
자체가 이 가드를 지원하지 않음), 이미 해당 컬럼이 있는 기존 DB(현재 운영 DB가 그 상태)에 대고
schema.sql 을 재실행하면 "duplicate column name" 오류로 executescript 가 중단된다.
  - 실측(신규 임시 DB에 schema.sql 을 연속 2회 실행): 1차 OK → 2차
    "OperationalError: duplicate column name: is_deleted"
  - 영향 범위: db/init_db.py 는 수동 1회성 스크립트(서버 자동기동 경로에서 호출되지 않음 —
    web_server.py 어디서도 import 되지 않음을 확인)이므로 즉시 장애는 아니나, 운영 DB가 이미
    구축된 상태에서 누군가 "스키마 재확인" 목적으로 `python db/init_db.py` 를 재실행하면
    스크립트가 예외로 죽는다. 데이터 손상은 아님(예외 시점까지의 CREATE TABLE IF NOT EXISTS 는
    전부 no-op 재확인일 뿐).
  - 이 저장소의 기존 관례(같은 파일 187~193행 주석, db/init_db.py::_apply_migrations)는 바로 이
    문제 때문에 "raw ALTER TABLE 은 schema.sql 에 직접 넣지 않고 init_db.py 의 _apply_migrations
    에 idempotent 가드(if col not in existing)로 넣는다" 는 패턴을 이미 쓰고 있다.
  - 이번 작업은 지시서가 "db/schema.sql 파일 하나만 수정, 다른 파일은 건드리지 마" 라고 명시했고
    "코드에 있는 것을 한 글자도 바꾸지 말고 그대로" 옮기라고 했으므로 지시대로 ALTER TABLE 을
    schema.sql 에 직접 추가했다. db/init_db.py 에 가드를 추가하는 대응은 이번 범위 밖(다른 파일
    수정 금지)이라 적용하지 않았다 — 필요하면 별도 작업(SCHEMA-SQL-INIT-DB-IDEMPOTENT-GUARD 류)으로
    분리 권장.
