1. 조사항목 ① — 프로파일 수집·스코어링이 컬럼 단위 루프인가
────────────────────────────────────────────────────────────────────────
■ 1-1. 수집 SQL 자체가 컬럼별 독립 집계 (services/column_profile_service.py)

    outer_sel_parts: list[str] = ["COUNT(*) AS pf_rc"]
    for idx, tgt_col in indexed_cols_outer:
        outer_sel_parts.append(f"COUNT({tgt_col}) AS pf_nn_{idx}")
        outer_sel_parts.append(f"COUNT(DISTINCT {tgt_col}) AS pf_dc_{idx}")
                                                  (column_profile_service.py:354-357)

  한 번의 쿼리로 N개 컬럼을 훑지만, 집계식은 전부 `COUNT(단일컬럼)` /
  `COUNT(DISTINCT 단일컬럼)` 이다. `COUNT(DISTINCT a||b)`, `GROUP BY a,b`,
  `COUNT(DISTINCT (a,b))` 형태는 **코드베이스 전체에 존재하지 않는다**(전수 grep 확인).
  → 쿼리 1회는 '성능 최적화(왕복 절감)'일 뿐 '함께 본다'는 의미가 아니다.

  결과 파싱도 컬럼별로 완전 분리된 dict 이다:

    profiles[col_name] = {
        "row_count": row_count, "non_null_count": non_null,
        "null_count": null_count, "null_ratio": null_ratio,
        "distinct_count": distinct, "distinct_ratio": distinct_ratio,
        "profile_error": None,
    }                                              (column_profile_service.py:407-415)

  → 저장 스키마에 '다른 컬럼과의 관계'를 담을 필드가 아예 없다.

■ 1-2. 값 샘플은 행 정렬 상태로 가져온 뒤 **곧바로 컬럼별로 해체**된다 (결정적 증거)

    sql = f"SELECT{_top} {col_list} FROM {from_table}" ...
    rows = cur.fetchall() or []
    ...
    for i, (t, _) in enumerate(missing):
        result[(t or "").upper()] = [r[i] for r in rows]
                                              (column_profile_service.py:125-132)

  LIMIT 100 샘플은 물리적으로 '같은 행의 여러 컬럼 값'을 이미 손에 쥔 상태다.
  상관관계를 계산할 유일한 원재료가 여기 있는데, 코드는 즉시 `[r[i] for r in rows]` 로
  **컬럼별 1차원 리스트로 쪼개 행 대응 정보를 버린다**. 이후 어떤 판정 함수도
  '행 단위로 두 컬럼을 함께 본' 적이 없다 — 볼 수 있는 자료구조가 남지 않기 때문이다.

■ 1-3. 재수집 경로도 동일 (services/profile_recollect_service.py:361)

    sel = ["COUNT(*) AS pr_rc"] + ["COUNT(DISTINCT %s) AS pr_d%d" % (...)

■ 1-4. pg_stats 스냅샷 경로는 애초에 교차 통계를 뽑을 수 없다
  services/source_profile_service.py:15,25 (모듈 헤더 '금지' 항목)

    2. pg_stats (catalog/statistics) 기반 — COUNT DISTINCT 직접 조회 금지.
    금지:

  PostgreSQL 의 다변량 통계(CREATE STATISTICS / pg_statistic_ext)는 사용하지 않는다
  (전수 grep: `pg_statistic_ext`, `CREATE STATISTICS` 히트 0건).

■ 1-5. 스코어링 진입점이 컬럼 단위 for 루프 (services/candidate_scoring.py:938-956)

    gb_scores:  list[dict] = []

2. 조사항목 ② — 관리컬럼(SYSTEM_AUDIT)에 '타 관리컬럼과의 동시성' 신호가 있는가
────────────────────────────────────────────────────────────────────────
■ 결론: **없다. 미구현이다.** (= 순수 단변량이라는 강한 방증)

관리컬럼 판정은 A·B 두 축의 '교차확인(crosscheck)' 구조지만, 이 '교차'는
**컬럼 간 교차가 아니라 같은 한 컬럼에 대한 근거 종류 간 교차**다.

    def evaluate_admin_audit_crosscheck(
        candidate:      dict,          # ← 컬럼 1개
        scoring_result: dict | None = None,
        role:           str = "group_by",
    ) -> dict:
        """B축(명칭=가설) × A축(값=검증) 교차확인으로 관리컬럼 여부를 최종 판정한다."""
                                          (candidate_subtype_service.py:652-657)

  · A축 = **그 컬럼의** 값 샘플 패턴 (배치 적재 스탬프 시그니처)
        def candidate_system_audit_value_pattern(candidate: dict) -> bool:
            vals = _candidate_sample_values(candidate)
            return detect_system_audit_value_pattern(vals) if vals is not None else False
                                                    (candidate_subtype_service.py:511-514)
  · B축 = **그 컬럼의** 명칭 표준사전 매칭 + **그 컬럼의** 코멘트 키워드 가설
        def detect_admin_audit_comment_hypothesis(comment) -> dict:   (:552)

  인자는 `candidate` 단수이며, 호출부도 컬럼 단위 루프 안이다:

        _audit_cc = evaluate_admin_audit_crosscheck(cand, sr, role)
                                              (candidate_subtype_service.py:1209)

  → "REG_DT 와 REG_ID 가 같은 행에서 함께 채워졌다", "UPD_DT 가 채워진 행은 반드시
     UPD_ID 도 채워져 있다" 같은 **관리컬럼 군집(동시성) 신호는 존재하지 않는다**.

■ 이 부재는 코드 주석 자체가 '알려진 한계'로 명시하고 있다

    ☆ 알려진 한계(미해소, 별도 지침 대상): B=True + A=None → CONFIRMED 는 '체크박스
      비활성(하드 배제)'까지 간다. A축이 관할 밖이라 침묵한 경우, 배제 근거는 결국
      WEAK(0.62) 명칭매칭 단독이며 이는 세션03 경고("이름 매칭 단독 신뢰 불가")가
      그대로 남는 지점이다. 값이 타임스탬프가 아닌 관리컬럼(BATCH_ID)과 명칭만
      감사스러운 업무컬럼(BIZ_REG_NO)은 A축으로 구분되지 않는다 — 구분하려면
      타임스탬프 외 관리컬럼 시그니처를 읽는 A축 확장이 필요하다(신규 판정 로직).
                                          (candidate_subtype_service.py:689-693)

  즉 BATCH_ID(값이 타임스탬프가 아님) 를 구제할 유일하게 남은 신호가 바로
  '다른 관리컬럼과 함께 채워지는 동시성'인데, 코드는 그 방향을 "신규 판정 로직 필요"
  로 미뤄 둔 상태다. → **교차 컬럼 신호 미구현이 명문화되어 있다.**

  또 다른 주석도 동일한 취지로 남아 있다:
    "... 가설-검증 교차확인 같은 정교화는 여전히 미구현으로 남긴다"
                                          (candidate_subtype_service.py:1197)

■ 유일하게 '컬럼 여러 개를 함께 보는' 관리컬럼 관련 코드는 **판정이 아니라 표시/집계**다
  (관리컬럼 감사 리포트가 컬럼 목록을 순회해 결과를 모으는 수준 — 컬럼 A의 판정이
   컬럼 B의 값/통계에 의해 바뀌는 경로는 없다).

▶ 항목 ② 결론: 교차 컬럼 신호 **0건**. 지시서의 가설("구현 안 됐다면 순수 단변량이라는
   방증")이 코드 주석 수준에서 확인됐다.

3. 조사항목 ③ — 다중 GROUP BY 조합(F6 / COMBO-PAIR) 판정이 조합 자체를 계산하는가
────────────────────────────────────────────────────────────────────────
■ 결론: **계산하지 않는다. 각 축의 독립 통계를 곱셈으로 결합할 뿐이다.**
  코드 주석이 스스로 "실측 아님", "독립성 가정" 이라고 못 박고 있다.

■ 3-1. 2축 PAIR 세트 (services/groupby_plan_service.py:96-127)

    for i in range(len(cands)):
        for j in range(i + 1, len(cands)):
            a, b = cands[i], cands[j]
            da, db = _distinct_of(a), _distinct_of(b)
            if not da or not db:
                excluded.append(_excl([a["col"], b["col"]], None, None,
                                      "조합 distinct 근거 부족(단일 축 계획만 실행)"))
                continue
            est = min(da * db, total) if total else da * db   # 조합 distinct 상한 추정(실측 아님)
            ...
            if not (_has_business_evidence(a) and _has_business_evidence(b)):
                excluded.append(_excl([...], est, avg, "업무 evidence 부족(자동 조합 제외)"))

  · 조합 그룹 수 = `da * db` (각 컬럼의 distinct 곱) → **주석에 "실측 아님" 명기**
  · 업무 evidence 판정 = `_has_business_evidence(a) and _has_business_evidence(b)`
    → 각 축을 독립 평가한 bool 두 개의 **AND 결합**. 조합 고유의 근거가 아니다.
  · `_distinct_of(cand)` 도 "재계산 없음" 을 주석에 명시:
        """후보 dict 에서 distinct(cardinality) 를 방어적으로 읽는다
           (필드명 다양성 흡수 — 재계산 없음)."""            (:44)

  ★ 이 곱셈이 실제와 어긋나는 구간이 바로 상관관계다.
    예) 시/도(17) × 시/군/구(250) 는 곱하면 4,250 이지만 실제 조합은 250 근처다
    (계층 종속). 반대로 완전 독립이면 곱에 근접한다. 현재 코드는 이 차이를 알 수 없고,
    `min(곱, total)` 라는 거친 상한으로만 방어한다.

■ 3-2. 조합 후보 추천 Phase 77 (services/diagnosis/candidate/recommender.py:296-329)

  · 조합 신뢰도 = 각 컬럼이 '업무 축'인지 세어(`axes`) 개수로 등급 부여

    "expected_total_groups": expected_total,   # §9 — 단일 축 합산(곱 아님)   (:149)

  → 즉 '조합'은 (a) 계산도 추정(곱)이고 (b) 실행도 단일축 N세트다.
    조합 자체의 실측 통계가 파이프라인 어디에도 남지 않는다.

▶ 항목 ③ 결론: **"조합 판정 시에는 교차 계산함" 은 사실이 아니다.**
   조합 판정 = (각 축 독립 통계) × (곱셈/AND 결합) + (min 상한 클램프).

5. 이 구조가 만드는 실제 리스크 (비판적 검토 — 참고, 수정 제안 아님)
────────────────────────────────────────────────────────────────────────
1) **조합 그룹 수 과대추정 → 조합 세트 부당 배제**
   groupby_plan_service.py:110 은 `est > max_groups(100)` 이면 조합을 제외한다.
   계층 종속(시/도 × 시/군/구, 대분류 × 소분류)에서 실제 조합은 곱보다 훨씬 작은데
   곱 기준으로 상한을 넘겨 "과세분화 방지" 사유로 잘려나간다.
   → 정작 유용한 업무 축 조합이 자동계획에서 사라진다. 반대로 `min(곱, total)` 클램프
     때문에 대형 테이블에서는 상한이 total 로 붙어 판정이 무의미해지는 구간도 생긴다.

2) **의미 중복 조합이 HIGH 신뢰도를 받는다**
   recommender.py:318-322 는 '업무 축 2개 이상'이면 HIGH 다. STATUS_CD 와 STATUS_NM
   처럼 사실상 1:1 종속인 두 컬럼도 axes=2 → HIGH. 조합해도 추가 정보가 0인데
   최우선 추천이 된다. (groupby_plan_service.py:121 의 `est <= max(da,db)` 가드는
   distinct 곱이 크게 나오므로 이 케이스를 잡지 못한다 — 곱이 곧 종속을 감춘다.)

3) **관리컬럼 오탐/미탐이 A축 확장 없이는 구조적으로 안 풀린다**
   candidate_subtype_service.py:689-693 이 자인하듯, BATCH_ID(관리컬럼인데 값이
   타임스탬프 아님)와 BIZ_REG_NO(업무컬럼인데 이름이 감사스러움)는 단변량으로 구분
   불가다. 이 둘을 가르는 가장 자연스러운 신호가 '다른 관리컬럼과의 동시 갱신'인데
   그 축이 없다. 현재는 WEAK(0.62) 명칭매칭 단독으로 하드 배제까지 간다.
   (실측 기록과도 일치: 라이브 픽스처에서 BIZ_REG_NO 만 WEAK 로 남는 케이스)

4) **explainability 는 오히려 양호**
   위 3건 모두 '조용한 실패'가 아니라 주석·필드명(`combination_product`,
   "실측 아님", "독립성 가정", "☆ 알려진 한계")으로 드러나 있다. 즉 이 진단의
   결론은 숨은 버그 발견이 아니라 **설계상 의도된 한계의 확인**이다.

5) **교차 계산 도입 시 비용 경고(선제 메모)**
   조합 실측(`COUNT(DISTINCT a||b)` 또는 `GROUP BY a,b`)은 현재 프로파일 예산 체계
   (SAMPLE_SRC 5만행 CTE + statement_timeout 15초, column_profile_service.py:47,53)
   와 정면 충돌한다. 컬럼 N개면 조합은 N(N-1)/2 로 폭증한다.
   도입한다면 (a) 5만행 샘플 위에서만, (b) 이미 추천된 소수 축에만, (c) 곱 대비
   실측이 크게 작을 때만 '종속 의심' 플래그를 다는 보수적 형태가 현실적이다.
   — 단, 이는 참고 의견이며 이번 지침 범위(조사) 밖이다.
