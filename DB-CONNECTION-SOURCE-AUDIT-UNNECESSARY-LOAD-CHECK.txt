[1-1] 단일 소비 chokepoint 구조
  services/db_query_service.py:573 `_cmn_db_connect` 가 물리 연결 획득의 유일한 진입점이다.
  - request_connection_scope 활성 시  → services/connection_pool.py 의 checkout()/return_conn() 경유(풀).
  - scope 비활성 시                   → _open_real_connection() 직행, 매번 새 연결 + 진짜 close().
  실제 물리 connect 는 services/db_adapter_registry.get_adapter(db_type).connect() 로 단일 위임되고
  (services/db_adapters/postgresql.py=psycopg2, oracle.py=oracledb, mssql.py=pyodbc, mysql.py=미구현→

[1-2] 커넥션 풀 실체 (services/connection_pool.py)
  - 자체 구현(표준 라이브러리만, 외부 pool 라이브러리 0건 확인).
  - **PostgreSQL 전용.** 그 외 DB 는 _is_pg(key)=False 라 checkout 이 곧바로 _open_real_connection,
    return_conn 이 곧바로 close → Oracle/MySQL/MSSQL 은 "매번 새로 연결"이 기본 패턴(설계 의도, HOLD).
  - 설정값: POOL_MAX_IDLE_PER_KEY=4, POOL_MAX_LIFETIME_S=300, POOL_IDLE_TIMEOUT_S=120,
    POOL_PING_AFTER_S=5(idle 5초 초과 시 checkout 시점에 SELECT 1 ping 후 재사용).
  - **동시 대여 상한 없음** — checkout() 은 idle 이 없으면 그냥 새 물리 연결을 열 뿐, 대기/세마포어가
    없다. MAX_IDLE=4 는 "반납받아 보관"하는 상한일 뿐이며, 초과분은 반납 즉시 close 된다(폐기 후
    다음 요청은 다시 cold open). 즉 풀은 "동시 사용량 제한기"가 아니라 "warm 재사용 캐시"다.
  - 격리: fingerprint(db_type,host,port,dbname,user,비밀번호 해시)가 key라 다른 profile 이 서로의
    warm 연결을 훔쳐 쓰지 못한다. invalidate_profile()로 profile 수정/삭제 시 세대(generation) 를
    올려 in-flight 연결까지 안전하게 폐기.

[1-4] 오늘 병렬화 3건의 동시 커넥션 수
  · COUNT side-parallel(services/count_common_service.py:683)
      ThreadPoolExecutor(max_workers=2) → 최대 2개(src 1 + tgt 1). 조건: run_src∧run_tgt ∧
      kill-switch(MV_COUNT_PAIR_PARALLEL) ∧ 서로 다른 물리 DB. scope 활성 + fingerprint 상이 시
      부모 scope 연결을 승계(추가 연결 0).
  · 4단계 통계검증 side-parallel(services/stats_execute_service.py:481, routes/execute_route.py 가
    2026-08-11 커밋 140297df 로 `_different_physical_db()` 판정에 따라 자동 설정)
      동일하게 max_workers=2, 최대 2개. scope 승계 시 추가 0.
  · 4단계 세트 병렬(_stats_set_parallelism, single_validation_run_facade.py, 기본 OFF/조건부 자동)
      max_workers=2(level 상한). **부모 scope 를 승계하지 않고** 워커마다 자기 scope 를 새로 연다
      (같은 fingerprint 동시사용 금지 규약). 세트 병렬이 켜지면:
        부모 scope(analyze/count 가 쥔 src+tgt) 2개 + 워커 2개×(자기 src+tgt) 4개
        = 개별검증 1회 이론적 최대 **6개 동시 커넥션**.
      실측(본 조사, 아래 2절)에서는 세트병렬 조건(COUNT 행수 ≥ 100만 등)을 만족하는 시나리오를
      직접 재현하지는 않았고, 코드 정독으로 상한을 계산한 값이다.
    → 셋 다 상수 상한이 있고 무제한 증식 구조는 아님. 다만 세트 병렬 + side 병렬이 겹치면 6개까지
      늘어나는 것은 사용자가 직관적으로 기대하는 "최대 2개"보다 크다 — 문서화 필요.

판정: **경미함** (구조적 개선 여지 있으나 현재 기본값 기준으로는 즉시 위험 아님)

근거:
  · 이미 확보된 대규모 실측([[project_50m_bottleneck_is_db_scan]], 5천만행)에서 DB 연결 수립은
    전체 시간의 1.7%(COUNT), 통계검증은 세트당 포함이지만 앱 계층 전체(파싱/비교/직렬화+연결)가
    0.8~2.5% 뿐이고 나머지 97%+는 순수 DB 스캔이다. 즉 "커넥션을 몇 개 더 여느냐"보다 "스캔을
    몇 번 하느냐"가 지배적 비용이며, 오늘 점검한 병렬화들은 스캔 횟수를 늘리지 않는다(같은 SQL을
    동시에 쏠 뿐, 추가 스캔 아님).
  · 원격(Neon 류) 접속 오버헤드는 [[project_stats_cost_band_benchmark_facts]] 실측상 "비례가 아니라
    고정 가산"(접속 465ms + 세션설정 5왕복 71ms, 양측 합 약 2,500ms)이고 규모가 커질수록 상대
    비중이 0 으로 수렴한다(1만행 +4.08배 → 5,000만행 +0.04배) — 소규모 테스트·소규모 이관 대상일
    수록 커넥션 비용 비중이 커진다는 뜻이므로, **작은 테이블을 많이 훑는 일괄검증일수록 1절의
    "커넥션 우회/누적" 개선 효과가 커진다.**
  · 풀 크기 제한: PostgreSQL 은 key 당 idle 4개로 작게 시작하는 보수적 설계고, 오늘 병렬화 3건은
    모두 max_workers=2 상수 상한이 있어 "무제한으로 늘어나는 구조"는 아니다. 다만 1-4/1-5 에서
    본 대로 (a) 세트병렬+side병렬 중첩 시 개별검증 1회가 이론상 6개까지, (b) 일괄검증 전역
    동시성 예산을 사용자가 올리면 이론상 24개까지 갈 수 있는데 이 상한이 **대상 DB의 실제
    max_connections 와 전혀 연동되지 않는다** — Neon 무료/저사양 tier 처럼 max_connections 가
    작은 환경에서 사용자가 배치 동시성 정책을 공격적으로 올리면 다른 워크로드에 영향을 줄 잠재
    위험은 존재한다(코드 검토로 확인된 리스크, 실측으로 직접 재현하지는 않음 — 상용 DB 를
    의도적으로 압박하는 테스트라 이번 조사 범위에서 보류).
  · 실측(2절)에서 개별검증 1회 기준으로는 PG 최대 2세션·Oracle 최대 1세션으로 매우 작았고, 실행
    후 정상 복귀(누적 없음)를 직접 확인했다. "오늘 병렬화 3건이 정상 실행 흐름에서 원본/목적 DB에
    부담을 주는가"라는 질문에는 **개별검증 단위로는 아니오**라고 답할 수 있다.
