■ 지시 3 먼저 — "AST 인가 EXPLAIN 인가" 조사 결과
진단(PK-RANGE-CHUNK-BOUNDARY-ORDERING-ASSUMPTION-DIAGNOSE §3-2)의 대조 실험이 갈림길을 이미
'구문 성질'로 확정해 두었다 — 윈도우 함수의 존재가 아니라 "청크 키가 그 윈도우의 PARTITION BY
컬럼 집합에 들어 있는가". 통계값이 아니라 SQL 구조가 결정하므로 AST 로 판정할 수 있다.
EXPLAIN 실행을 택하지 않은 이유(3가지):
  ① 왕복 추가 — 판정 지점은 이미 MIN/MAX 2회를 지불한 자리다. 정작 문제 형태(WRAPPED)에서는
     그 EXPLAIN 자체가 전체 스캔 계획 산정을 요구한다.
  ② 재현 불변성 상실 — 옵티마이저 판단은 통계·바인드 peeking 에 따라 같은 SQL 에서도 달라진다.
     "같은 입력 → 같은 판정"이 깨지면 게이트가 신뢰를 잃는다(P4 가 표본 게이트에서 같은 이유로
     '형태 기반·판정 불변'을 안전한 쪽으로 기록했다).
  ③ 방언 파편화 — PG `EXPLAIN (FORMAT JSON)` vs Oracle `EXPLAIN PLAN FOR`+PLAN_TABLE 권한+DBMS_XPLAN.
     계획 텍스트 파싱은 버전마다 깨진다.
→ sqlglot AST 정적 판정을 채택하되, AST 가 인덱스·옵티마이저를 볼 수 없다는 한계를 3값 판정으로 정직하게
   반영했다: PUSHDOWN_LIKELY / PUSHDOWN_BLOCKED / UNKNOWN. **UNKNOWN 은 어떤 동작도 바꾸지 않는다.**

■ 구현 (신규 services/exact_diff/chunk_pushdown.py — DB 접속·store 접근 0)
검사 항목은 백로그 원안 그대로 + 1개 추가:
  (a) 윈도우 PARTITION BY 에 청크 키가 있는가 (없으면 WINDOW_PARTITION_MISMATCH / PARTITION BY 자체가
      없으면 WINDOW_NO_PARTITION)
  (b) 파생 척추(FROM·CTE spine) 위 SELECT 에 DISTINCT / GROUP BY / 전체집계 / 중복제거 집합연산
  (c) [추가] 청크 키가 단순 컬럼이 아니라 표현식 결과라 인덱스를 못 타는 경우(KEY_NOT_PLAIN_COLUMN)
오탐 방지 2건: UNION ALL 은 정렬 barrier 가 아니므로 차단 사유가 아니고(정보만), SELECT 목록 안
스칼라 서브쿼리의 집계는 행집합 경로의 성질이 아니므로 척추 순회에서 제외한다.
sqlglot 호출은 S18 방어 래퍼(parse_one_guarded) 경유 필수 — error_level 은 넘기지 않는다(명시 전달
자체가 오라클 파서 hang 트리거인 사례가 실측돼 있다).

■ 실측 — 정적 판정 vs 실 오라클 실행계획 vs 빈 chunk 고정비 (L1)
대상: 실 오라클 tobe(1524) NXDNP.MV_ORA_XDIFF_TGT 249,950행 · chunk 50,000 · 빈 chunk 3회 median

  원본 형태                    AST 판정          실행계획(운영 chunk 조회 SQL)                 top card   빈 chunk

  PLAIN(단순 SELECT)           PUSHDOWN_LIKELY  INDEX RANGE SCAN (정렬 연산 없음)              49,980    0.0031s
  WRAPPED PARTITION BY C_CHAR  PUSHDOWN_BLOCKED WINDOW SORT ← HASH/NL ← TABLE ACCESS FULL    249,950    0.1289s
  WRAPPED PARTITION BY ID      PUSHDOWN_LIKELY  WINDOW NOSORT ← INDEX RANGE SCAN              49,980    0.0024s

  → 3형태 전부 AST 판정 = 실행계획(ast_matches_plan=true). BLOCKED 형태만 빈 chunk 고정비가
    PLAIN 대비 **41.6배**(0.1289s vs 0.0031s) — "청크마다 원본 전체 재정렬 1회"의 직접 증거.
  → 판정 비용: 1.92~2.60ms (1회, DB 왕복 0회)

  실측(오라클 라이브, 분포는 WHERE 로만 변형 · 데이터 변경 없음):

  HEAD_HEAVY     5      4.95배     0/5       true
  ENDS_HEAVY     6      2.99배     3/6       true
  → 진단 §2-1 이 기록한 수치(4.95배 / 빈 3/6)를 그대로 재현. 수정 전에는 이 값이 어디에도 없었다.

■ 요구 2 — chunk 폭증 시 실행 전 HOLD
  전(게이트 OFF, MV_CHUNK_PLAN_GUARD=0)  : READY · chunk 2,000개 전부 조회(2,000회) · **28.869초** ·
                                            빈 chunk 1,993/2,000
  후(게이트 ON, 기본)                     : **HOLD · CHUNK_COUNT_EXPLOSION · 0.307초 · 조회 0회**
                                            (0.307초는 MIN/MAX 조회분, chunk 조회는 1회도 없음)
  절감 28.562초. 재현 조건은 진단 §2-2 와 동일 — 목적지 PK 이상치 1건(99,999,999)이 합집합 범위를
  늘려 chunk 6개 → 2,000개. 사유 문구에 실제 수치가 들어간다:
    "PK 범위(1 ~ 99999999)와 청크 크기(50000)로 청크가 2000개 생성됩니다(상한 1000개, 실제 행 수
     249951건 대비 밀도 0.25%(빈 청크가 대부분)) — PK 이상치로 범위가 비정상 확장됐을 가능성이 높아
     실행 전 보류합니다. PK 이상치를 확인하거나 청크 크기를 키우십시오."
  ※ 이 형태는 PLAIN(빈 chunk 0.003s)이라 28.9초에 그쳤다. pushdown 불가 형태였다면 같은 2,000개가
    0.129s × 2,000 ≈ 258초다.

■ 요구 3 — 두 파트가 만나는 지점(순서를 신중히 정한 부분)
같은 파일(pk_range_chunk.py)에서 만나므로 게이트를 하나의 함수(evaluate_chunk_plan_guard)로 합치고
순서를 이렇게 정했다:
  ① pushdown 판정을 먼저 한다(정적·DB 왕복 0회)
  ② pushdown 불가면 chunk 수 상한을 낮춘다 — **BLOCKED 200개 / 절대 1,000개의 2단**
     근거: 빈 chunk 고정비가 형태마다 41배 다르다(실측). pushdown 되는 형태의 chunk 500개는 사실상
     공짜지만, 막힌 형태의 500개는 '원본 전체 정렬 500회'다. 상한을 하나로 두면 둘 중 하나가 틀린다.
  ③ 절대 상한은 **밀도 조건과 AND** 로 묶는다 — chunk 수만 보면 '이상치로 퍼진 25만행'(2,000 chunk,
     밀도 0.25%)과 '정직하게 큰 6,000만행'(1,200 chunk, 밀도 ~100%)을 구분하지 못해 **정상 대량 실행까지
     막는다**. 행 수(source/target count)를 알 때만 밀도로 구분하고, 모르면 chunk 수 단독으로 보수적 판정.
     BLOCKED 상한에는 밀도를 붙이지 않는다 — 그 비용은 행 수가 아니라 청크 개수에 비례하므로.
  ④ HOLD 는 store.create_run 보다 앞에서 반환한다 — 빈 run·checkpoint 잔여물을 만들지 않는다.
백로그 P5 원문 경고("규모 비례 청크 확대를 정렬 비용 대책으로 삼지 말 것")는 그대로 지켰다 —
청크 크기 정책은 건드리지 않았고, HOLD 문구도 크기 조정/DIRECT_STREAM 선택을 사용자 판단으로 남긴다.
운영 kill-switch: MV_CHUNK_PLAN_GUARD=0 → HOLD 만 즉시 해제(계측·판정 증적은 유지).
