1. 배경과 요청 요약
--------------------------------------------------------------------------------
RESULT-VIEW-RUNID-DECOUPLE-FEASIBILITY-DIAGNOSE 의 3순위 항목이다. 검증 현황판에서
"완료된 job 을 눌러 결과 화면을 연다"를 만들려면 완료된 job 의 목록이 있어야 하는데,
지금까지 job 통합 조회 계층에는 활성 목록(GET /jobs/active)밖에 없었다. 완료 목록
API 를 새로 만드는 것이 이번 작업의 전부이며, 화면 배선은 이번 범위가 아니다.

제약은 명확했다. 기존 두 엔드포인트의 동작과 응답 스키마를 건드리지 않을 것, 통합
계층의 "기존 저장소는 읽기만 한다" 원칙을 유지할 것, 수정 파일은
routes/job_dashboard_route.py 와 services/job_registry.py 두 개로 제한할 것.

--------------------------------------------------------------------------------
2. 설계 판단 ① — 별도 엔드포인트(GET /jobs/completed) 선택 근거
--------------------------------------------------------------------------------
지시는 "GET /jobs/active 에 active_only 파라미터 추가" 와 "GET /jobs/completed 신설"
중 어느 쪽이 기존 구조에 자연스러운지 판단해서 고르고 근거를 남기라고 했다.
**별도 엔드포인트 신설**을 선택했다. 근거는 네 가지다.

(1) 경로 이름이 곧 계약이다.
    `/jobs/active?active_only=false` 는 경로가 스스로를 부정하는 형태가 된다. 로그·
    브라우저 네트워크 탭·향후 코드 리뷰에서 "active 를 부르는데 완료가 온다"는 상황이
    생기고, 이는 잘못 쓰기 쉬운 API 다.

(2) 두 목록의 정렬 기준이 다르다.
    활성 목록은 '최근 시작 순'(started_at)이 옳다. 완료 목록은 '최근 종료 순'이 옳다.
    같은 엔드포인트에 두면 파라미터 값에 따라 정렬 축이 바뀌는데, 이는 응답 계약이
    파라미터에 따라 달라진다는 뜻이라 소비측이 방어하기 어렵다.

(3) 상한(limit)의 필요성이 정반대다.
    활성 job 은 동시에 몇 건뿐이라 상한이 필요 없고, 지금 화면은 상한 없는 전체 목록을
    전제로 폴링한다. 반면 완료 이력은 무한히 쌓인다(운영 DB 실측: 일괄검증 386건,
    개별검증 스냅샷 110건). 완료 목록에는 상한이 필수인데, 그 상한을 /jobs/active 에
    도입하면 **현재 폴링 중인 기존 호출자의 응답이 조용히 잘릴 수 있다**. 이것이
    하위호환을 깨는 가장 현실적인 경로였다.

(4) 완료 목록은 활성 목록이 읽지 않는 저장소를 하나 더 읽는다(아래 3절).
    같은 엔드포인트에 넣으면 "불리언 파라미터 하나로 조회 대상 저장소가 바뀌는" 형태가
    된다.

결과적으로 /jobs/active 의 코드는 **한 줄도 바뀌지 않았다**. 회귀 표면이 0 이라는 것이
이 선택의 실질적 이득이다.

3. 설계 판단 ② — 개별검증(single) 완료의 출처가 둘인 이유 (지시 전제의 정정 포함)
--------------------------------------------------------------------------------
지시에는 "개별검증(single) job 은 in-memory 라 서버 재시작 시 소실되므로, 완료 목록의
개별검증 항목은 '최근 세션 내 완료분만' 조회 가능함을 notes 로 명시"라고 되어 있었다.
구현하면서 확인한 결과, 이 전제는 **절반만 사실**이므로 그대로 옮겨 적지 않고 정정해
반영했다.

  · 활성 목록의 single = services/exact_diff/reimport_job.py 의 재이관 job.
    이것은 확실히 in-memory 이고 서버 재시작 시 소실된다. 지시의 서술이 맞다.
  · 그러나 지시가 함께 지목한 services/single_validation_result_store.py 는
    in-memory 가 아니라 **SQLite 영속 저장소**다(db/migration_validator.db 의
    single_validation_snapshot 테이블, 운영 실측 110행, 2026-07-23~27 기록 잔존).

그리고 이번 작업의 목적("완료 job 클릭 → 결과 보기")에 실제로 필요한 것은 후자다.
재이관 job 자체에는 독립된 '결과 화면'이 없고, 열어야 할 결과는 개별검증 실행 결과
스냅샷이기 때문이다. 그래서 개별검증 완료는 **두 출처를 합쳐** 구성하고, 각 항목이
자기 성질을 스스로 신고하게 했다.

    extra.origin = "reimport_job"                 → persistent=false, result_viewable=false
    extra.origin = "single_validation_snapshot"   → persistent=true,  result_viewable=true

응답 notes 에도 두 출처의 차이를 그대로 적었다. 이 구분을 화면이 감추면 "어제 돌린
검증이 왜 안 보이나"를 사용자도 개발자도 진단할 수 없다.

--------------------------------------------------------------------------------
4. 설계 판단 ③ — '완료'의 정의를 화이트리스트로 두지 않은 이유
--------------------------------------------------------------------------------
종료 상태를 나열(COMPLETED/FAILED/…)해 거르는 방식은, 원본 저장소에 새 종료 상태가
추가되면 그 job 을 **조용히** 목록에서 누락시킨다. 조용한 누락은 진단이 불가능하다.
그래서 여집합으로 정의했다.

    완료 = (활성 상태 아님) AND (아직 안 끝난 상태 아님)

  · 개별검증: PAUSED(일시중지·checkpoint 보존), RECOVER_REQUIRED(복구 대기)는
    이어서 실행 가능하므로 완료가 아니다 → 제외.
  · 일괄검증: IDLE(실행된 적 없음)은 완료가 아니다 → 제외.
  · 그 외 종료 상태는 이름을 몰라도 전부 완료로 잡힌다.

부작용을 하나 만든다: PAUSED·RECOVER_REQUIRED·IDLE 은 활성 목록에도 완료 목록에도
없다. 숨기지 않고 응답 notes 에 명시했다. 이 상태들의 노출은 별도 판단이 필요한
사안이라 이번 범위에 임의로 넣지 않았다.

      · tests/test_single_validation_result_view_persistence.py 6건 → HEAD 에서도 동일 실패
