■ 1-2. 우선순위 조회 (지시: TABLE_COLUMN > PROJECT_COLUMN > 자동판정)
  resolve_override() 가 TABLE_COLUMN 을 먼저 찾고, 없을 때만 PROJECT_COLUMN 을 본다.
  둘 다 없으면 **None** 을 돌려준다 — '자동판정을 그대로 쓰라'는 뜻이며, 이 저장소는
  스스로 판정하지 않는다(판정 책임을 저장소로 새어나가게 하지 않기 위함).
  반환에는 matched_scope / status_effective / is_stale / stale_reason 을 덧붙인다.

  설계상 한 가지 결정을 기록해 둔다: **table_key 가 비면 TABLE_COLUMN 조회를 건너뛴다.**
  빈 table_key 로 TABLE_COLUMN 을 조회하면 PROJECT_COLUMN 행과 키가 겹쳐 잘못 매칭될 수
  있기 때문이다. 같은 이유로 scope=PROJECT_COLUMN 저장 시 table_key 를 빈 문자열로 강제한다
  (값이 남으면 UNIQUE 키가 갈라져 '프로젝트 전체 적용'이 테이블별로 쪼개진다).

■ 1-3. STALE 전환 (지시: auto_verdict_at_decision 이 현재 자동판정과 달라지면 STALE)
  두 경로 모두 구현했다 — source_owner_binding 의 BOUND/STALE 과 같은 개념이다.
    · 계산형 : resolve_override(current_auto_verdict=...) 가 확정 당시 값과 비교해
               status_effective=STALE 로 **표시**한다(DB 미변경 — 조회가 쓰기를 유발하지 않음).
    · 영속형 : mark_stale() 이 DB status 를 STALE 로 전환한다(기록 보존, 삭제 아님).
  STALE 이어도 확정 행을 감추지 않는다. 사용자 확정을 조용히 무시하지 않고 화면에 드러내
  재확인시키는 것이 이 상태값의 목적이기 때문이다(적용 여부 판단은 상위 판정 계층의 몫).
  현재 자동판정을 모르면(빈 문자열) 비교 자체를 하지 않는다 — 판정 불가를 불일치로 단정하지
  않는다는 기존 A축 3-state 원칙과 같은 태도다.

6. 남은 일 — 이 저장소는 아직 화면에 영향이 없다
────────────────────────────────────────────────────────────────────────
  이번 단계는 의도적으로 '연결하지 않은' 상태다. 지금 API 로 확정을 저장해도 후보표 배지,
  체크박스, 자동선정 배제, date_bucket 대체추천, 일괄검증 어디에도 반영되지 않는다.

  후속 순서(진단 §6-3 권고 유지):
    ① CONFIRMED 관리컬럼을 참고/제외 표에 사유와 함께 되살린다.
       — 진단 §2-3 실측대로 CONFIRMED 행은 3곳에서 화면에서 제거되므로, '관리컬럼 아님'
         방향 확정은 지금 진입점 자체가 없다. 이 선행 없이 UI 를 붙이면 near-dead 배지에만
         컨트롤이 걸려 사실상 쓰이지 않는다.
    ② evaluate_admin_audit_crosscheck 에 override 를 최상위 우선순위로 주입(판정표 3축화)
       + enrich 경유 4곳에 override_map 전달.
    ③ 비고 셀 컨트롤(POST 즉시 반영 — 로컬 미확정 상태를 만들지 않아 재렌더 보존 함정 회피).
    ④ 일괄검증은 저장소 읽기만 배선(엑셀 입력 채널 신설 없음).
