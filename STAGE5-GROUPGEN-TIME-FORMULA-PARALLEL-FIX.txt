작업명 : STAGE5-GROUPGEN-TIME-FORMULA-PARALLEL-FIX
✅ 작업 완료 - 5단계 그룹생성 시간 공식을 병렬/순차 실행 여부에 따라 분기(음수→0.01초 미만 고착 해소)

배경
----
STAGE5-EXEC-TIME-GROUPGEN-SPLIT(오늘, 미커밋 상태로 작업트리에 존재 — "그룹생성 시간 = 전체시간
- 원본조회 - 목적조회" 공식을 만든 작업)와 STAGE4-SOURCE-TARGET-PARALLEL-EXECUTE(오늘 커밋
140297df, 4단계 통계검증 실행을 원본/목적 병렬화한 작업)가 서로 충돌했다: 그룹생성 시간 공식은
원본/목적이 순차 실행된다는 전제(순차면 전체≈원본+목적+그룹생성)로 만들어졌는데, 4단계가 병렬로
바뀌면서(전체≈max(원본,목적)+그룹생성) 서로 다른 물리 DB 조합에서는 공식이 원본+목적을 이중으로
차감해 거의 항상 음수가 되고, 기존 음수 방어 로직이 항상 "0.01초 미만"으로 표시를 뭉갰다
(STAGE2-STAGE4-SOURCE-TARGET-CONCURRENCY-TIMESTAMP-VERIFY 가 4단계 병렬 실행을 실측으로 재확인).

구현
----
1) services/stats_execute_service.py:640-647 — /execute 성공 응답 query_timing 에
   `parallel_sides` 필드 추가. 새 판정 로직 아님 — routes/execute_route.py::_stats_execute_inner
   (STAGE4-SOURCE-TARGET-PARALLEL-EXECUTE 가 이미 배선한 `_different_physical_db()` 판정 결과)가
   req.parallel_sides 에 담아 넘긴 값을 그대로 echo 만 한다.
2) services/multiset_execute_service.py:191-235(`_aggregate`) — 다중 세트(GROUP BY 2축 이상)
   집계 시 세트별 query_timing.parallel_sides 를 취합해 agg.query_timing.parallel_sides 로 전파.
   물리 DB 조합(src_db/tgt_db)은 세트 간 불변이므로 첫 세트 값만 채택.
3) ui/tabler_renderer.py:27545,27567-27572,27580-27581(`_runExecutePlanSets`) — 동기 다중세트
   경로의 클라이언트측 agg 조립도 서버(2)와 필드 단위로 대칭 전파(qtParallel 누적자 추가).
4) ui/grid_helpers.py:1170-1228(`_mvStage5ProcInfo(r)`) — 그룹생성 시간 공식 분기:
     · qt.parallel_sides === true  → 그룹생성 = 전체시간 - max(원본조회, 목적조회)
     · false 또는 필드 자체가 없는 구버전 응답 → 그룹생성 = 전체시간 - 원본조회 - 목적조회(기존 공식)
   음수 방어(음수면 0 표시 + console.warn)는 그대로 유지. 툴팁에 "[병렬 실행]"/"[순차 실행]" 라벨과
   해당 공식(병렬은 max(...), 순차는 -원본-목적)을 함께 표기 — 총시간·원본·목적 세 값 정보손실 없음.

[시나리오 A] 병렬 — 서로 다른 물리 DB
  DB 쌍   : PostgreSQL_asis(ep-bitter-moon-....neon.tech, neondb) -> PostgreSQL_tobe
            (ep-super-river-....neon.tech, neondb) — host 상이 → _different_physical_db()=True
  SQL     : mv_bt.orders_a[10,000행] → mv_bt.tgt_orders[19,750행], GB=STATUS_CD, SUM=ORDER_AMT,QTY
  /execute 응답 원문 : processing_ms=838.4ms
                       query_timing.source_duration_ms=78ms, target_duration_ms=105ms
                       query_timing.parallel_sides=true   ← 실측 확인(코드 추론 아님)
  기대 계산값(병렬 공식) : 838.4 - max(78,105) = 838.4 - 105 = 733.4ms ≈ 0.73초
  화면 '실행시간' 칸  : "실행 0.73초 / 상세 7.30초"   ← 일치 확인(대조=True, 0.01초 미만 아님)
  칸 툴팁            : "그룹생성(불일치 그룹 계산·비교) 0.73초 = 전체 0.84초 -
                        max(원본조회 0.08초, 목적조회 0.10초) [병렬 실행]
                        (733ms = 838ms - max(78ms, 105ms)) · 상세(불일치 그룹 펼침) …"
                       → "[병렬 실행]" 라벨 포함, max() 공식 명시, 총시간·원본·목적 세 값 모두 확인.

[시나리오 B] 순차 — 같은 물리 DB
  DB 쌍   : PostgreSQL_asis -> PostgreSQL_asis_SEQTEST_tgt
            (이번 검증 전용으로 mv_db_preset 에 TGT 프리셋 1건 추가 — PostgreSQL_asis 와 완전히
            동일한 접속정보(host/port/dbname/계정)를 그대로 복제한 것으로 새 DB 계정 발급 아님.
            host/port/dbname 이 원본과 완전히 동일 → _different_physical_db()=False)
  SQL     : mv_bt.orders_a[10,000행] → mv_bt.orders_b[10,000행, 같은 asis DB 안의 동일스키마 테이블],
            GB=STATUS_CD, SUM=ORDER_AMT,QTY
  /execute 응답 원문 : processing_ms=1028.0ms
                       query_timing.source_duration_ms=73ms, target_duration_ms=88ms
                       query_timing.parallel_sides=false  ← 실측 확인(코드 추론 아님)
  기대 계산값(순차 공식, 기존 그대로) : 1028.0 - 73 - 88 = 867.0ms ≈ 0.87초
  화면 '실행시간' 칸  : "0.87초"   ← 일치 확인(대조=True)
  칸 툴팁            : "그룹생성(불일치 그룹 계산·비교) 0.87초 = 전체 1.03초 -
                        원본조회 0.07초 - 목적조회 0.09초 [순차 실행]
                        (867ms = 1028ms - 73ms - 88ms)"
                       → "[순차 실행]" 라벨 포함, 기존 -원본-목적 공식 그대로 적용 확인(회귀 없음).

검산: 두 시나리오 모두 스크립트가 /execute 응답 원문(코드가 만든 값이 아니라 네트워크로 실제 수신한
값)으로 독립 재계산한 기대값과 화면에 실제로 그려진 텍스트를 문자열 대조했다(코드를 다시 실행해
재확인하는 방식이 아니라 응답 vs DOM 대조).
