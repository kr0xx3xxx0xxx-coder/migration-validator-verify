배경
----
SCHEMA-SQL-M37-M39-SYNC 작업(e79c7c2)에서 db/schema.sql에 추가한
mv_db_preset의 raw ALTER TABLE ... ADD COLUMN 3줄(is_deleted /
last_used_at / advanced_options_json)은 SQLite ALTER TABLE ADD COLUMN이
IF NOT EXISTS를 지원하지 않아, 이미 해당 컬럼이 존재하는 DB에
db/init_db.py를 재실행하면 sqlite3.OperationalError: duplicate column
name 예외로 초기화 전체가 중단됨이 실측 확인되었다.

수정 범위
--------
- 수정 파일: db/init_db.py 1개 파일만 수정 (지시서 준수)
- db/schema.sql은 변경하지 않음 (raw ALTER TABLE 3줄 그대로 유지)

왜 schema.sql을 그대로 두었는가 (기존 관례 확인 결과)
--------------------------------------------------
services/db_preset_service.py::_ensure_schema()에 이미 동일한
is_deleted/last_used_at/advanced_options_json 3개 컬럼에 대해
"PRAGMA table_info로 컬럼 존재 확인 → 없으면만 ALTER TABLE" 방식의
멱등 가드가 구현되어 있고, schema.sql 주석(47행)에도
"services/db_preset_service.py::_ensure_schema, 멱등 ALTER TABLE로
추가됨"이라고 명시되어 있다. 즉 이 저장소의 기존 관례는
"schema.sql에는 스키마 정의(문서/신규 DB 기준선)를 raw SQL로 남기고,
실제 재실행 안전성(멱등성)은 애플리케이션 코드 쪽 가드에서 보장한다"는
이중 구조다. init_db.py도 동일한 관례를 따라 코드 쪽(_apply_schema /
_apply_migrations)에서 멱등성을 보장하도록 수정했고, schema.sql은
지시서 지침대로 손대지 않았다.

구현 내용
--------
1. _apply_schema(conn, schema) 신설
   - 기존: conn.executescript(schema) 한 번에 전체 스크립트 실행
     -> 한 구문이라도 예외가 나면 그 뒤 구문은 전혀 실행되지 않고 중단됨
     (재현: mv_db_preset의 ALTER TABLE 구문에서 실패 시 이후 14개+
     CREATE TABLE 구문이 전부 스킵되는 것을 실측으로 확인)
   - 변경: schema.sql 텍스트를 ';' 단위 구문으로 분리해 개별 실행.
     sqlite3.OperationalError이고 메시지에 "duplicate column name"이
     포함된 경우만 건너뛰고, 그 외 예외는 그대로 raise. 나머지 구문
     (신규 테이블/인덱스 포함)은 계속 적용됨.
2. _apply_migrations()에 저장소의 기존 idempotent 가드 패턴
   (_migrate_table -- "컬럼이 없으면 ALTER TABLE, 있으면 skip")을
   그대로 사용해 mv_db_preset의 3개 컬럼과 ux_mv_db_preset_key
   유일성 인덱스를 추가 (defense-in-depth, 지시서 1번 항목 그대로 반영)
3. init_db()의 conn.executescript(schema); conn.commit() 호출을
   _apply_schema(conn, schema) 호출로 교체
