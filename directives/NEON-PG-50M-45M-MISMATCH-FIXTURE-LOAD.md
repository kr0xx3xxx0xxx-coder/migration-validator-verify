작업명 : NEON-PG-50M-45M-MISMATCH-FIXTURE-LOAD

배경: 클라우드 Neon PostgreSQL(PostgreSQL_tobe 프리셋)에 테스트용 대규모 픽스처를
적재한다 — 원본(SRC) 5,000만건, 목적(TGT) 4,500만건(500만건 의도적 차이).

────────────────────────────────────────────────────────────
구현
────────────────────────────────────────────────────────────
1. 테이블명은 samples/virtual_tables.py의 데모 DDL과 충돌하는 흔한 이름(TB_ 등)을
   피해라 — 예: NEON_MISMATCH50M_SRC / NEON_MISMATCH50M_TGT 같은 고유한 이름 사용.
2. `generate_series`로 양쪽에 결정적 데이터를 생성해라(오늘 P13 재측정 때 쓴 방식과
   동일) — 네트워크로 5천만 행을 실제로 복사하지 말고, 각자 독립적으로 생성해라.
3. 목적(TGT)이 원본(SRC)보다 정확히 500만건 적도록 만들어라 — 예: 원본은 PK
   1~50,000,000 전부 생성하고, 목적은 그 중 임의의(또는 뒤쪽) 4500만건만 생성해서
   "재이관대상"(누락 500만건)이 실제로 잡히게 해라.
4. 컬럼 구성은 기존 MV_SCATTER50M류와 유사하게(GROUP BY 축 1~2개, SUM 대상
   AMT/QTY 등) 만들어서, 오늘 쓰던 개별검증 화면 흐름을 그대로 테스트할 수 있게
   해라.
5. 이 프로젝트의 asis/tobe 실 테이블 CUD 금지 원칙 — 이건 실 운영 테이블이 아니라
   신규 테스트 전용 테이블이니 적재 자체는 문제없다. 다만 기존 프로젝트/DB 계정
   범위 밖으로 나가지 마라(PostgreSQL_tobe 프리셋 그대로 사용).

────────────────────────────────────────────────────────────
검증
────────────────────────────────────────────────────────────
- 적재 후 양쪽 COUNT를 직접 SQL로 확인해서 정확히 5000만/4500만인지 확인해라.
- 실제로 개별검증 화면에서 이 테이블 쌍으로 COUNT 사전검증까지 돌려서, 차이가
  정확히 500만으로 잡히는지 확인해라(4단계 이후까지는 지금 안 해도 된다 — 데이터
  적재와 기초 확인까지가 이번 작업 범위).
- 완료보고: 테이블명, 적재 방법(스크립트), 실측 COUNT 확인 결과, 적재 소요시간.
  작업명 첫줄/마지막줄.
