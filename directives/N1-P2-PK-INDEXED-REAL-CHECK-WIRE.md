작업명 : N1-P2-PK-INDEXED-REAL-CHECK-WIRE

N1-MERKLE-TREE-FEASIBILITY-DIAGNOSE.txt를 먼저 읽고 시작해줘. 승인 완료. 그
보고서가 권장한 P2다.

배경: `key_evidence.py:191`(`"indexed": bool(ev.is_pk or ev.is_unique)`)와
`ui/grid_helpers._mvDerivePkProfile`의 모든 반환 분기가 `pk_indexed:true`를
하드코딩하고 있다 — "PK다"와 "그 PK가 실제로 인덱스를 갖고 있다"를 같은 것으로
취급 중이다. 실무에서는 PK 선언 시 대부분 자동으로 인덱스가 생기지만(정상
케이스), 이 값을 실제로 확인 안 하고 항상 참으로 두면 "짐작하지 말고 실제
메타데이터로 확인한다"는 프로젝트 원칙에 어긋난다.

────────────────────────────────────────────────────────────
구현
────────────────────────────────────────────────────────────
`key_evidence.py`가 PK 인덱스 존재 여부를 실제로 조회하도록 배선해라 — 각 DBMS의
인덱스 카탈로그(오라클 USER_INDEXES/ALL_INDEXES, PostgreSQL pg_index 등)를
조회하는 경로를 만들되, 오늘 확립된 어댑터 패턴(DBMS별 분기는 물리적으로 분리)을
따라라. 조회 결과를 `ev.indexed`(또는 유사 필드)에 실제 값으로 반영하고,
`_mvDerivePkProfile`도 하드코딩된 `true` 대신 이 실측값을 그대로 전달하도록 고쳐라.

인덱스가 실제로 없는 것으로 확인되면(드문 케이스), 그 정보가 CHUNK 전략 판정
등 하류 로직에 정확히 반영되는지도 확인해라(단, CHUNK 판정 로직 자체를 새로
설계하지 말고, 이미 있는 `pk_indexed` 소비처들이 이제 진짜 값을 받게 되는
효과만 확인).

────────────────────────────────────────────────────────────
검증(필수, 실측)
────────────────────────────────────────────────────────────
- 실제로 인덱스가 있는 PK 테이블과, 가능하면 인덱스 없는 PK를 인위적으로 만든
  테스트 테이블 둘 다로 조회해서, 각각 정확한 값(true/false)이 나오는지 실측.
- 기존에 이 값을 소비하던 로직(CHUNK 자격 판정 등)이 실제 인덱스 있는 정상
  케이스에서는 기존과 동일하게 동작하는지(회귀 없음) 확인.
- 관련 테스트 서브셋 + baseline 대조, 신규 회귀 0건.
- CLAUDE.md 필수 회귀(virtual/complex) 최종 1회.

  첫줄/마지막줄.
