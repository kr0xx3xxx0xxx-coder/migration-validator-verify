작업명 : STAGE4-SQL-LAYOUT-STRATEGY-SPLIT-BLOCKED-ALERT-CLARITY-FIX

4가지를 순서대로 처리해줘(전부 ui/tabler_renderer.py 인접 영역). 시작 전 다른
터미널에서 같은 파일 작업이 없는지 확인해줘.

────────────────────────────────────────────────────────────
1순위 — SQL 헤더와 코드박스 사이 여백 축소
────────────────────────────────────────────────────────────
"목적지(Target) SQL"/"원본(Source) SQL" 제목과 그 아래 SQL 코드박스 사이 수직
여백이 과하게 넓다(스크린샷 근거). 해당 CSS margin/padding을 줄여서 제목과 코드박스가
더 가깝게 붙도록 수정. 다른 섹션 간격에는 영향 없게 국소적으로.

────────────────────────────────────────────────────────────
2순위 — "전략/신뢰도" 정보와 "조합 검증" 체크박스를 별도 블록으로 분리
────────────────────────────────────────────────────────────
오늘(M51/M54) SQL 하단에 배치한 "전략 [배지] 신뢰도 HIGH 규모 초대형 예상그룹 31개..."
정보 줄과, 그 아래 "조합(REGION_CD+STATUS_CD)도 함께 검증..." 체크박스 줄이 지금
시각적으로 하나처럼 붙어 있다. 이 둘을 명확히 구분되는 별도 블록(카드 또는 구분선,
여백)으로 나눠줘 — 서로 다른 정보(하나는 실행 계획 요약, 하나는 사용자가 조작하는
체크박스)라는 게 시각적으로 드러나야 함.

────────────────────────────────────────────────────────────
3순위 — 조합 체크박스 영역의 이중 배경 제거
────────────────────────────────────────────────────────────
"조합(...)도 함께 검증 — 세트 1개 추가 실행" 줄을 감싸는 배경이 현재 이중으로
(바깥 박스+안쪽 박스) 겹쳐 있다(스크린샷 근거 — 점선 테두리 박스 안에 또 다른 배경색
박스가 있는 구조로 보임). 안쪽 배경 하나만 남기고 바깥 이중 레이어를 제거해서 단일
배경으로 정리.

────────────────────────────────────────────────────────────
4순위 — "5단계 진행중"일 때 4단계 실행버튼·체크박스가 실제로 비활성화되지 않는 문제 (수정, 문구 개선이 아니라 실제 잠금)
────────────────────────────────────────────────────────────
스크린샷 근거: 4단계 탭 옆에 "●5단계 진행중" 보조 배지(오늘 M54에서 만든 표시)가 떠
있는데도, 4단계의 "단일축만 실행(조합 ... 자동제외)" 실행 버튼과 조합 체크박스가
여전히 클릭 가능한 상태(파랗게 활성)로 보인다. 실제로 클릭하면 "실행이 이미 진행
중입니다..." alert로 뒤늦게 막히는데, **이건 문구 문제가 아니라 애초에 버튼/체크박스가
disabled 상태로 회색 처리돼 있어야 하는 문제다.**

먼저 원인을 조사해줘 — 오늘 M47-REGRESSION-RECHECK-AND-FIX가 `_RUN_LOCK_FNS` 화이트
리스트(runAnalyze/`_mvCountStageAction`/runRevalidateFromCandidate/runGenerate)로
시각적 잠금을 배선했는데, **`runExecute`(4단계 자체 실행 버튼)는 그 보고서가 "자기치유
탈출구 보존" 목적으로 의도적으로 제외**했었다. 지금 이 스크린샷이 정확히 그 제외된
지점이다 — `_mvSyncRunLockedControls()`의 잠금 조건이 `_mvAnyRunActive()`(5단계
reimport 상태 포함)를 보긴 하는데, 그 잠금 대상 화이트리스트에 `runExecute`와 조합
체크박스가 빠져 있어서 시각적으로는 안 잠긴 것으로 보인다.

**재검토 후 수정**: "자기치유 탈출구"가 필요했던 이유(5단계가 멈췄을 때 4단계를 강제로
다시 트리거할 방법이 하나는 있어야 한다는 논리)와, 지금처럼 "클릭은 되는데 알림으로
뒤늦게 막히는" 현재 동작을 비교했을 때, **후자가 UX상 더 나쁘다**(눌러보기 전엔 막힐지
알 수 없음). 다음 방향으로 개선:
- 조합 체크박스는 5단계 진행 중이면 명확히 disabled 처리(클릭 자체가 안 되고, 왜
  안 되는지 tooltip으로 안내).
- `runExecute` 버튼 자체도 5단계 진행 중이면 disabled 처리하되, **그 버튼이 다른
  용도(예: 실행 중 자기 자신의 중단 등)로도 쓰이는지 먼저 확인** — 순수 "새로 실행
  시작" 트리거일 때만 잠그고, 이미 실행 중인 걸 멈추는 용도로도 겹쳐 쓰이면 그 경우는
  잠그면 안 됨(코드 확인 후 판단).
- "자기치유 탈출구"가 정말 필요한 시나리오(5단계가 영구히 멈춰서 사용자가 강제로
  4단계를 다시 돌려야만 하는 경우)가 있다면, 완전히 잠그지 말고 "5단계가 오래 멈춘
  것 같으면 여기를 눌러 강제 재실행" 같은 명시적 예외 경로로 분리하는 것도 검토
  (다만 이번 범위에서 새 UI를 만들 필요는 없음 — 이미 5단계 자체에 중단 버튼이 있으니
  그걸로 충분한지 먼저 확인).
- 원인·설계 재검토 결과를 완료보고에 명확히 기술(단순 disabled 속성 추가가 아니라
  "왜 이제는 안전하다고 판단했는지" 근거 포함).
