코드 수정 없이 조사만 해줘.

배경: 오늘 확인된 대로, "통계검증 실행"(4단계, GROUP BY/SUM 비교)이 원본↔목적이
같은 DBMS일 때만 지원되도록 3곳(서버측 정책 게이트, DBMS 능력정의 모듈, 클라이언트
JS 가드)에서 명시적으로 막혀있다. 반면 COUNT 비교는 이미 이기종 간에도 정상
작동한다(오늘 실측 확인).

────────────────────────────────────────────────────────────
1. 왜 이렇게 설계됐는지 확인
────────────────────────────────────────────────────────────
- 이 3곳의 게이트 코드 주변 커밋 이력(git blame/log)을 확인해서, 언제 왜 이
  제한이 들어갔는지 찾아라 — 커밋 메시지, 관련 PR/이슈, 코드 주석 등.
- CLAUDE.md나 프로젝트 문서에 이기종 지원 여부에 대한 명시적 설계 결정이 있는지
  확인해라.

────────────────────────────────────────────────────────────
2. 기술적 장벽이 실제로 존재하는지 확인
────────────────────────────────────────────────────────────
- COUNT는 왜 이기종이 되는데 통계검증(GROUP BY/SUM)은 안 되는지 — 두 기능의
  SQL 생성 로직 차이를 비교해라. COUNT는 단순 COUNT(*)라 방언 차이가 거의 없지만,
  GROUP BY/SUM은 방언별 문법 차이(예: 날짜함수, NULL 처리, 집계함수 이름 등)가
  더 클 수 있다 — 이게 실제 장벽인지, 아니면 단순히 아직 구현을 안 한 것뿐인지
  확인해라.
- 이기종 조합(오라클↔PostgreSQL)에서 GROUP BY/SUM SQL을 양쪽 방언으로 각각
  생성하는 게 기존 아키텍처(방언 어댑터 구조)로 실제로 가능한 구조인지 확인해라
  — 이미 오라클용 빌더/PG용 빌더가 각각 존재하니, 그 둘을 "같은 논리적 GROUP BY
  요청"에 대해 동시에 호출하기만 하면 되는 구조인지, 아니면 더 근본적인 재설계가
  필요한 구조인지 판단해라.
- 결과 비교 단계(원본 결과 vs 목적 결과)가 방언에 의존하는 부분이 있는지도
  확인해라(타입 변환, 정밀도 차이 등).

────────────────────────────────────────────────────────────
3. 결론
────────────────────────────────────────────────────────────
다음 중 어느 쪽에 가까운지 판단해서 명확히 답해라:
(a) "의도적으로 안전을 위해 막아둔 것 — 이기종 비교는 SQL 방언 차이로 인한
    오탐 위험이 실제로 크다"
(b) "기술적 장벽은 크지 않고, 단순히 아직 구현이 안 된 것뿐 — 기존 어댑터
    구조로 비교적 적은 작업으로 확장 가능해 보인다"
(c) 그 중간(부분적으로 장벽이 있고 부분적으로는 미구현)

만약 구현한다면 대략적으로 어느 정도 규모의 작업일지(파일 수, 예상 난이도)도
가늠해서 알려줘.
