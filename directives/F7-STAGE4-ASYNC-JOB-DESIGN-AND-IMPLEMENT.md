기존 진단서가 3가지 개선안을 정리해뒀다 — 그 3안을 먼저 검토하고, 오늘 5단계에
새로 적용한 설계 원칙(M56: 자동 전체처리 대신 필요한 만큼만, 명시적 상태 추적)을
참고해서 방향을 재확인해라.

────────────────────────────────────────────────────────────
1. 기존 3안 재검토 + 설계 확정
────────────────────────────────────────────────────────────
진단서의 3안 각각을 오늘 시점 기준으로 재평가(당시 이후 코드 변경 있었는지, 오늘
5단계 구조변경과 일관성 있는 방향인지)해서 하나를 확정. 최소한 다음을 설계에
포함해라:
- 4단계 실행을 실제로 백그라운드 job으로 추적 가능하게 만드는 방법(진행률/상태를
  어디서 어떻게 갱신할지 — 진짜 진행 신호가 없다면 "폴링으로 완료 여부만 확인"
  수준이어도 됨, 억지로 가짜 진행률을 만들지 말 것).
- 브라우저를 닫아도 서버에서 실행이 계속되는지(진짜 비동기).
- 완료 후 사용자가 다시 돌아왔을 때 결과를 어떻게 보여줄지(오늘 F9가 만든
  job↔run_id 연결 패턴 재사용 가능한지 확인).
- 5단계 자동 진입은 이번 범위에 포함하지 마라 — 오늘 M56/M58로 "5단계는 사용자가
  명시적으로 들어가야 시작"하는 방향으로 이미 재설계했으므로, "4단계 끝나면 자동으로
  5단계로 넘어간다"는 옛 전제 자체가 지금 설계 원칙과 어긋난다. 4단계 job 완료
  상태를 명확히 보여주는 것까지가 이번 범위.

────────────────────────────────────────────────────────────
2. 구현
────────────────────────────────────────────────────────────
1번에서 확정한 설계대로 구현. 기존 실행 로직(SQL 생성/실행 자체)은 최대한 안 건드리고,
"그 실행을 감싸서 job으로 추적 가능하게 만드는" 레이어만 새로 추가하는 방향을 우선
검토(완전 재작성보다 위험 낮음).
