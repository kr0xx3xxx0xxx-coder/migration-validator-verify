작업명 : DETAIL-EXTRACT-EARLY-STOP-ALL-PK-TYPES-COVERAGE-DIAGNOSE

코드 수정 없이 조사만 해줘.

배경: M91에서 "101건 조기중단(early_stop_abs)이 표준 단일 숫자 PK 테이블
(가장 흔한 구성)에서는 실제로 거의 발동하지 않는다 — 복합키/문자키 전용
좁은 폴백 경로에서만 강제 세팅된다"는 게 확인됐다. 사용자가 이 상황에
문제를 제기했다: "조기중단은 PK 종류(단일 숫자든 복합이든 문자든)와
무관하게 모든 경우에 작동해야 한다."

────────────────────────────────────────────────────────────
조사 항목
────────────────────────────────────────────────────────────
1. 표준 단일 숫자 PK 테이블의 대용량 그룹(예: 수백만 행)을 상세추출할 때,
   실제로 "재이관 대상 건수가 아주 많아지는 상황"에서 어떤 상한/보호장치가
   있는지(있다면 무엇인지, 없다면 없다고 명확히) 확인해라 — early_stop_abs
   가 아니더라도 다른 이름의 유사한 안전장치가 있는지 찾아라.
2. 만약 단일 숫자 PK 경로에 이런 상한이 전혀 없다면, 실제로 무슨 일이
   일어나는지 확인해라 — 재이관 대상이 수만~수십만 건이 나오는 극단적
   상황에서, 시스템이 그걸 다 수집하고 저장하려고 시도하는지(성능/메모리
   문제 가능성), 아니면 다른 방식(예: MAX_DISPLAY_ROWS=200 절단, M82에서
   확인된 것)으로 제한되는지 확인해라.
3. early_stop_abs=101 로직을 복합/문자 PK 전용 폴백에서 표준 단일 숫자 PK
   경로(PK_RANGE_CHUNK)로도 확장 적용하는 게 기술적으로 가능한지 확인해라
   — 이번엔 M85/M88/M90이 다뤘던 "GROUP BY 집계" 조기중단 문제가 아니라,
   "PK 행단위 비교"(이미 조기중단 가능하다고 확인된 그 메커니즘) 안에서의
   적용 범위 확장 문제이므로, 기술적 장벽이 이전 조사들과는 다를 수 있다 —
   구분해서 판단해라.
4. 만약 확장이 기술적으로 가능하다면, 왜 지금까지 복합/문자 PK 전용으로만
   좁혀져 있었는지 이유(설계 의도 또는 커밋 이력)를 확인해라 — 의도적
   제한인지, 아니면 놓친 부분인지 판단해라.

────────────────────────────────────────────────────────────
완료보고
────────────────────────────────────────────────────────────
- 1~4번 각각의 답.
- 종합 판단: "모든 PK 타입에서 조기중단이 작동해야 한다"는 요구사항이
  기술적으로 실현 가능한지, 실현 가능하다면 구현 규모(파일 수, 난이도)를
  제시해라. 결함(놓친 것)인지, 의도된 설계인지 명확히 구분해라.
- 코드 수정 없음. 작업명 첫줄/마지막줄.
