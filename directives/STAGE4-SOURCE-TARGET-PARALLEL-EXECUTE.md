작업명 : STAGE4-SOURCE-TARGET-PARALLEL-EXECUTE

BACKLOG.md M75 항목(COUNT 병렬은 이미 정상 작동, 4단계는 순차 확인됨)을 먼저 읽고
시작해줘. 승인 완료.

배경: 2단계 COUNT는 원본/목적을 이미 병렬로 쏘고 있는데(`count_common_service.py::
_execute_count_sides`, `ThreadPoolExecutor(max_workers=2)`, 기본 ON), 4단계
통계검증 실행은 순차로 돈다(원본 10.91초+목적 11.21초가 그대로 이어붙어 전체
23.15초가 됨). 사용자가 4단계도 COUNT와 동일하게 원본/목적을 병렬로 돌리길 원한다.

────────────────────────────────────────────────────────────
구현
────────────────────────────────────────────────────────────
`count_common_service.py::_execute_count_sides`가 쓰는 것과 동일한 패턴
(`ThreadPoolExecutor(max_workers=2)`)을 4단계 통계검증 실행 경로
(`routes/execute_route.py` → `stats_execute_service.py`)에도 적용해서, 원본/목적
쿼리를 병렬로 실행하게 해라. 새 병렬 메커니즘을 발명하지 말고 COUNT가 쓰는 것과
같은 방식을 그대로 재사용해라.

`stats_execute_service.py:416`의 `parallel_sides` 기본값(False)을 이 경로에서
True로 바꾸거나, COUNT와 같은 패턴으로 새로 배선해라 — 기존에 존재하던 두
특수경로(진단 재검증, 미연결 facade)의 병렬 코드를 재사용할 수 있으면 재사용하고,
안 되면 COUNT의 패턴을 참고해 새로 구현해라.

────────────────────────────────────────────────────────────
검증(필수, 실제 클릭)
────────────────────────────────────────────────────────────
- 실제로 4단계를 실행해서, 원본/목적 시간이 이제 병렬로 겹치는지(전체 실행시간이
  원본+목적의 합이 아니라 둘 중 큰 쪽에 가깝게 나오는지) 실측으로 확인해라 — 오늘
  확인한 사례(원본 10.91초/목적 11.21초 → 전체 23.15초)와 비교해서, 병렬화 후
  전체 시간이 약 11초대(큰 쪽 기준)로 줄어드는지 확인.
- 결과값(불일치 그룹 수, 재이관 대상 등)이 병렬화 전후로 완전히 동일한지(정합성
  회귀 없음) 확인 — 병렬 실행이 결과 자체를 바꾸면 안 된다.
- 일괄검증 경로도 이 변경의 영향을 받는지 확인하고, 받는다면 일괄검증에서도
  정상 동작하는지(대량 테이블 처리 시 문제없는지) 확인.
- 관련 테스트 서브셋 + baseline 대조, 신규 회귀 0건.
- CLAUDE.md 필수 회귀(virtual/complex) 최종 1회.
- 완료보고: 파일:라인, 병렬화 전/후 실측 시간 비교(구체적 수치), 정합성 회귀 없음
