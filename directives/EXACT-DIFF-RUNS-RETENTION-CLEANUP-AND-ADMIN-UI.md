작업명 : EXACT-DIFF-RUNS-RETENTION-CLEANUP-AND-ADMIN-UI

배경: BACKLOG.md M64 항목을 먼저 읽고 시작해줘. 승인 완료. `exact_diff_runs.db`가
정리 로직 전무로 무기한 누적되는 문제(실측 927MB/284run, 일괄검증 수천 테이블 반복
시 하루 6.5GB 추정)를 해결한다. 완료된 run 보관 기간은 **기본 7일**로 확정,
관리자가 화면에서 조정 가능하게 만든다.

────────────────────────────────────────────────────────────
1. 보존 정책 설정값
────────────────────────────────────────────────────────────
보관 기간(기본 7일)을 오늘 M59가 만든 전역설정 인프라(`resolve_setting`/
`execution_settings.py` 패턴, 또는 기존 `validation_policy_service`의 화면편집
가능한 정책 저장소 C계통 — 어느 쪽이 더 적합한지 판단해서 재사용, 새 설정 계통
발명 금지)에 신설. 값 이름은 예: `exact_diff_run_retention_days=7`.

────────────────────────────────────────────────────────────
2. 정리 로직 구현
────────────────────────────────────────────────────────────
- 기존 `services/exact_diff/store.py::delete_run()`(테스트에서만 쓰이던 함수)를
  실제로 배선 — 새로 만들지 말고 그대로 재사용.
- 완료 상태(READY 등 최종 상태)이고 보존 기간을 넘은 run을 찾아 삭제하는 정리
  작업 신설. 실행 방식은 서버 기동 시 1회 + 이후 주기적(예: 하루 1회) 백그라운드
  실행을 검토(기존 batch 스케줄러 패턴이 있으면 재사용, 새 스케줄링 프레임워크
  발명 금지).
- **RUNNING 상태로 멈춘 고아 run**(서버 비정상 종료로 발생, 실측 34건 확인됨)도
  서버 기동 시 감지해서 정리 대상에 포함(단, 진짜 지금 실행 중인 run과 착각해서
  지우면 안 되므로, 판별 기준을 신중히 설계 — 예: 서버 기동 시점 = 그 이전의
  RUNNING은 전부 고아로 간주 가능한지 확인).
- 삭제 전 로그 기록(무엇을 몇 건 지웠는지, explainability 원칙).

────────────────────────────────────────────────────────────
3. 관리자 화면
────────────────────────────────────────────────────────────
- 보존 기간 설정값을 조정할 수 있는 화면(기존 전역설정 확인창/정책 화면이 있으면
  거기에 항목 추가, 새 화면 신설은 최후 수단).
- 현재 저장공간 사용량(run 개수, 대략적 크기)과 마지막 정리 실행 시각을 보여주는
  간단한 현황 표시.
- "지금 즉시 정리 실행" 수동 트리거 버튼(주기 실행을 안 기다리고 필요시 바로 정리
  가능하게).

────────────────────────────────────────────────────────────
검증(필수)
────────────────────────────────────────────────────────────
- 보존 기간을 넘긴 완료 run을 실제로 만들어서(테스트 데이터), 정리 로직 실행 후
  실제로 삭제되는지 확인.
- 보존 기간 안의 run은 삭제되지 않는지 확인.
- RUNNING 고아 run 정리가 실제 실행 중인 run을 잘못 지우지 않는지(안전장치) 확인.
- 관리자 화면에서 보존 기간 변경 → 실제로 그 값이 정리 로직에 반영되는지 실제
  클릭으로 확인.
- "지금 즉시 정리" 버튼 실제 클릭 동작 확인.
