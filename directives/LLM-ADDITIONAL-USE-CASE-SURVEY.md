작업명 : LLM-ADDITIONAL-USE-CASE-SURVEY

코드 수정 없이 조사·브레인스토밍만 해줘. BACKLOG.md M50 항목(LLM 관리컬럼 판정
설계, 실측 호출빈도 0.8~1.0%라 보류)을 먼저 읽고, M50이 썼던 방법론(설계 먼저,
실제 호출빈도 추정 후 판단)을 그대로 참고해라.

배경: 사용자가 "관리컬럼 판정" 외에 이 프로젝트 안에서 LLM이 도움 될 만한 다른
지점이 있는지 물었다. 짐작으로 나열하지 말고, BACKLOG.md 전체와 오늘까지 쌓인
verify 저장소의 완료보고서들을 훑어서 실제 근거 있는 후보를 찾아라.

────────────────────────────────────────────────────────────
1. BACKLOG 전체 스캔 — LLM이 도움 될 만한 "판별 불가/모호함" 지점 찾기
────────────────────────────────────────────────────────────
BACKLOG.md 전체를 훑어서, "규칙기반으로는 판별 불가·애매함으로 처리하고 넘어간"
지점들을 찾아라. 예를 들어(이건 예시일 뿐, 실제로 코드/문서를 확인해서 판단해라):
- F18(cd1류 컬럼 판정 신호 없어 종결) — 종결됐지만, LLM이라면 다른 접근이 가능한지
- M25(LegacyParser 정규식 의존, 오탐 가능성)
- 그 외 "확신도 낮음/HOLD/판별불가"로 처리되는 다른 판정 로직들

각 후보에 대해, 왜 규칙기반으로 안 되는지, LLM이 왜 더 나을 수 있는지(또는 없는지)
판단해라.

────────────────────────────────────────────────────────────
2. 사용자 대면 텍스트 생성/설명 영역 탐색
────────────────────────────────────────────────────────────
불일치 원인을 사람이 읽기 쉽게 요약·설명하는 기능, 복잡한 오류 메시지를 친숙하게
바꾸는 기능처럼, "판정"이 아니라 "설명/요약" 목적의 LLM 활용처가 있는지 찾아라 —
이런 용도는 M50의 "3차 판정 근거"와 성격이 달라서(오판 위험보다 표현력이 중요),
별도로 평가해야 한다.

────────────────────────────────────────────────────────────
3. 각 후보의 실제 활용 빈도 가늠
────────────────────────────────────────────────────────────
M50이 그랬듯, 각 후보가 실제로 얼마나 자주 발동할지(전체 검증 작업 대비 비율)를
대략이라도 추정해라 — 정확한 실측까지는 이번 조사에서 안 해도 되지만, "이 후보는
M50처럼 1% 미만일 것 같다" 정도의 근거 있는 짐작은 필요하다.

────────────────────────────────────────────────────────────
4. 개별검증 외 일괄·전수검증 모드까지 적용 범위 확대 검토 (사용자 추가 요청)
────────────────────────────────────────────────────────────
1~3에서 찾은 각 후보가 개별검증(analyze) 화면에서만 의미 있는지, 아니면 일괄검증
(batch)·전수검증(exhaustive, 현재 "준비중") 경로에도 같은 방식으로 적용 가능한지
확인해라. 일괄/전수는 처리 대상 규모가 수백~수천 테이블로 개별검증과 다르니,
같은 후보라도 "테이블 1개당 호출 확률은 낮아도 전체 배치에서는 호출 총량이 커질
수 있다"는 관점에서 다시 평가해라(M50이 이미 "배치 경로 타임아웃 누적 방지용
circuit-breaker 설계"를 언급했던 것과 같은 맥락 — 그 설계를 재사용할 수 있는지도
확인).

────────────────────────────────────────────────────────────
5. "간접 활용"이라는 별도 카테고리 검토 (사용자 추가 요청)
────────────────────────────────────────────────────────────
이 프로젝트는 데이터 정합성 검증 도구라 **판정 결과 자체(어느 레코드가 불일치인지,
어느 컬럼이 관리컬럼인지 등)에 LLM을 직접 개입시키는 건 신중해야 한다**(정확성이
생명인 영역, M50이 이미 "비대칭 반영"으로 이 원칙을 지킨 것과 동일선상). 그래서
아래 두 층을 구분해서 각각 평가해라:
- **직접 활용**: 검증 판정 자체에 관여(예: 관리컬럼 판정 3차 근거) — 오판 위험이
  직접적이라 M50 수준의 엄격한 검증(실측 호출빈도, 비대칭 반영, fail-open 등)이
  필수.
- **간접 활용**: 판정 결과에는 관여 안 하고, **그 결과를 사람에게 더 잘 설명·정리·
  안내**하는 데만 쓰는 것(2번 항목의 "설명/요약" 계열이 여기 해당). 이쪽은 틀려도
  최종 판정 자체는 안 틀리니 상대적으로 안전한 영역 — 이 구분을 완료보고에
  명시적으로 반영해서, "직접 활용 후보"와 "간접 활용 후보"를 표로 나눠 제시해라.

완료보고에 이 두 항목(4·5번)까지 포함해서, 최종 우선순위 추천을 다시 정리해라 —
"신뢰를 주는 AI 활용"이라는 사용자의 관심사를 고려하되, 정확성이 생명인 판정
영역과 설명 영역을 명확히 구분해서 제시하는 게 핵심이다.
