작업명 : STAGE5-GROUP-DRILLDOWN-ARCHITECTURE-IMPLEMENT

배경/확정된 설계(사용자 결정, 재검토 없이 이대로 구현): 지금 4단계(통계검증)가 끝나면
5단계(상세비교)가 사용자 개입 없이 자동으로 백그라운드에서 전체 불일치 그룹의 행 단위
비교를 시작하고, 그 상태가 4단계 탭에 "●5단계 진행중" 배지로 새어 나온다. 이 구조를
아래로 바꾼다:

1. **4단계는 불일치 "그룹"을 찾는 것까지만 한다** — GROUP BY 집계 비교로 어느 그룹의
   COUNT/SUM 등이 다른지 찾고 끝. 그 결과(불일치 그룹 목록)를 저장하고 4단계는 완료
   상태로 끝난다. 5단계 상세비교를 자동으로 트리거하지 않는다.
2. **5단계는 그 불일치 그룹 목록을 보여주는 화면으로 시작한다** — 4단계가 저장한
   그룹 목록을 읽어서 리스트로 표시(아직 행 단위 상세는 없음).
3. **그룹을 클릭하면, 그때 그 그룹만 상세 추출(행 단위 비교)을 시작한다** — 전체
   그룹을 한꺼번에 도는 게 아니라 클릭한 그룹 하나만 온디맨드로 처리. 처리 중에는
   그 그룹 항목에 진행 표시, 끝나면 그 그룹의 불일치 레코드 표시.
4. **4단계 탭의 "●5단계 진행중" 교차 배지는 제거한다** — 이제 5단계 작업은 4단계
   완료 후 사용자가 5단계 화면에 들어가서 그룹을 클릭해야만 시작되므로, 4단계가
   5단계 상태를 알아야 할 이유 자체가 없어진다(역할 분리 원칙).

────────────────────────────────────────────────────────────
1. 먼저 확인 (구현 전 필수)
────────────────────────────────────────────────────────────
- 4단계가 찾은 불일치 그룹 목록이 이미 DB/저장소에 영속화되는지 확인. 저장 안 되고
  있으면(메모리에서 5단계로 즉시 전달만 하는 구조라면) 저장 로직을 먼저 만들어야 함
  — 그룹 식별자(GROUP BY 값 조합), 소속 프로젝트/테이블/실행(run_id) 정도가 최소
  스키마일 것.
- 현재 "그룹별 온디맨드 추출"이 기술적으로 가능한 구조인지 확인 — 지금 상세비교
  로직이 전체 그룹을 한 번에 도는 구조로 짜여 있다면, "그룹 하나만" 실행하도록
  파라미터화가 필요할 수 있음.
- 5단계 진입 시 자동 시작하던 기존 트리거 지점(오늘 조사 대상이던 그 코드)을 정확히
  찾아서, 그 자동 호출을 제거하고 대신 그룹 클릭 핸들러로 옮길 지점을 특정.

────────────────────────────────────────────────────────────
2. 구현
────────────────────────────────────────────────────────────
- 4단계: 불일치 그룹 확정 시점에 그룹 목록 저장(1번에서 확인된 방식대로). 5단계
  자동 트리거 호출 제거.
- 5단계 진입 화면: 저장된 그룹 목록을 리스트로 렌더(그룹별 상태: 미확인/추출중/완료).
- 그룹 클릭 핸들러: 그 그룹 하나만 상세 추출 API 호출 → 진행 표시 → 완료 시 해당
  그룹의 불일치 레코드 표시(기존 상세 레코드 렌더링 로직 재사용, 새로 만들지 말 것).
- 4단계 탭의 "●5단계 진행중" subBadge 렌더 로직(오늘 M54가 만든 것) 제거 — 4단계
  탭은 이제 자기 상태만 표시.
- 오늘 만들었던 관련 잠금 로직(M43/M47/M54가 "5단계 진행 중"을 이유로 1~4단계를
  잠그던 부분)도 재검토 — 이제 5단계가 자동으로 안 돌면 그 잠금 시나리오 자체가
  많이 줄어들 것이나, "특정 그룹 추출 중"에 4단계로 돌아가 재실행하는 것까지 막아야
  하는지는 판단해서 처리(막아야 한다면 훨씬 좁은 범위로 — 전체 5단계가 아니라 그
  그룹 추출 하나만).

────────────────────────────────────────────────────────────
2-1. 성능 트레이드오프 대응 (필수 설계 제약)
────────────────────────────────────────────────────────────
그룹별 온디맨드 추출로 바꾸면 실제 DB 부하가 두 방향으로 갈릴 수 있다:
  - 사용자가 일부 그룹만 확인하면 → 관심 없는 그룹까지 미리 스캔 안 하니 부하 감소
    (기존 "전체 자동" 대비 이득).
  - 사용자가 결국 전체 그룹을 다 클릭하게 되면 → 기존엔 여러 그룹을 한 쿼리로 묶어서
    (예: WHERE 그룹키 IN (...)) 처리했을 가능성이 높은데, "클릭당 쿼리 1번"으로
    짜면 커넥션 open/close 오버헤드가 그룹 수만큼 누적돼 오히려 총 소요시간이 늘 수
    있다.
반드시 다음을 확인·반영해라:
  - 현재 상세비교가 여러 그룹을 한 쿼리로 묶어서 처리하는지, 그룹마다 별도 쿼리인지
    코드로 확인.
  - 그룹 클릭 시마다 새 DB 커넥션을 열고 닫는 구조가 되지 않도록(가능하면 커넥션
    재사용/풀링), 최소한 순차 클릭 사이에 불필요한 재연결 오버헤드가 없는지 확인.
  - **"전체 한꺼번에 추출" 옵션도 함께 제공**(예: 그룹 목록 화면 상단에 "전체 그룹
    한번에 추출" 버튼) — 개별 클릭 방식만 강제하지 말고, 사용자가 결국 전체를 볼
    걸 이미 알고 있다면 기존처럼 일괄 처리도 선택할 수 있게. 이러면 온디맨드(부분
    관심)와 일괄(전체 관심) 두 시나리오 모두 최선의 방식으로 처리됨.
