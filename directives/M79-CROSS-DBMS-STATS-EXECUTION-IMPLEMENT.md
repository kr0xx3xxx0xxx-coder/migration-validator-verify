작업명 : M79-CROSS-DBMS-STATS-EXECUTION-IMPLEMENT

BACKLOG.md M79 항목(CROSS-DBMS-STATS-EXECUTION-LIMITATION-RATIONALE-DIAGNOSE.txt)을
먼저 읽고 시작해줘. 승인 완료 — 실제 구현 착수.

배경: 통계검증(GROUP BY/SUM) 이기종 DBMS(오라클↔PostgreSQL) 차단이, 통계검증
자체의 위험분석이 아니라 오라클 개방 시 HASH_BUCKET 안전원칙을 차용한 부산물임이
확인됐다. SQL 생성 계층은 이미 이기종 지원 구조지만, 결과비교 단계의 GROUP BY
키 매칭이 단순 str() 캐스팅뿐이라 타입별 canonical 정규화가 없는 게 진짜 공백.

────────────────────────────────────────────────────────────
필수 원칙 (사용자 명시 요구, 반드시 지켜라)
────────────────────────────────────────────────────────────
1. **일괄검증(batch)도 반드시 함께 고려해라** — 개별검증 경로만 고치고 끝내지
   마라. facade/capabilities/JS가드 3곳 중, 일괄검증이 타는 별도 경로가 있는지
   먼저 확인하고, 있다면 그쪽도 동일하게 이기종을 지원하도록 고쳐라.
2. **DBMS별 역할을 물리적으로 분리해라 — 한 파일에 여러 DBMS 로직을 몰아넣거나
   인라인 if/elif로 방언 분기하는 것 금지(CLAUDE.md 8번 규칙, 어댑터 패턴).**
   이번에 신설할 "타입별 canonical 키 정규화" 로직도, 기존 HASH_BUCKET의
   `services/diagnosis/dialects_hash/oracle.py` / `postgresql.py` 같은 어댑터
   분리 패턴을 그대로 따라서 만들어라 — 공통 인터페이스(예: `normalize_group_key`)
   + DBMS별 구현체 파일로 나눠라. 하드코딩(값을 특정 DBMS 이름으로 직접 비교하는
   코드)을 새로 추가하지 마라.
3. **필요하면 SQLite에 테이블을 만들어 저장해라** — 이 프로젝트의 내부 저장은
   SQLite만 쓰는 게 기존 원칙이다(신규 원격 DB 연결을 저장용으로 쓰지 마라).
   예를 들어 이기종 조합별 캐스트 규칙, 검증 이력, 타입 매핑표 등 저장이 필요하면
   SQLite 테이블로 만들어라.

────────────────────────────────────────────────────────────
구현 단계
────────────────────────────────────────────────────────────
1. **타입별 canonical 키 정규화 유틸 신설**(어댑터 패턴) — 숫자(trim/scale 통일),
   문자열(trim, 대소문자/공백 정책), NULL/빈문자열, 날짜(기존 date_trunc_expr
   패턴 확장)를 DBMS 무관 canonical 표현으로 변환하는 공통 인터페이스 + DBMS별
   구현체.
2. `services/stats_execute_service.py:254 _to_dict()`의 키 생성부를 이 정규화
   유틸을 쓰도록 교체해라.
3. 게이트 3곳(개별검증 경로) 조건 완화 — 무조건 열지 말고, "정규화 유틸이 실제로
   해당 타입 조합을 지원하는 경우에만" 이기종을 허용하는 방식으로 만들어라(안전
   장치 완전 제거가 아니라 조건부 개방).
4. 일괄검증 경로도 동일하게 확인·수정해라(위 원칙1).
5. COUNT 버튼과 클라이언트 가드 간 비대칭(오늘 조사에서 발견된 부수 사항 —
   드롭다운 dbms 값과 실제 접속프로필 dbms 어긋남 가능성)도 이번 기회에 같이
   확인해서, 문제가 실재하면 같이 고쳐라.

────────────────────────────────────────────────────────────
검증(필수, 실제 클릭 — 이기종 실데이터 없이는 안전 단정 불가하다고 조사서가
명시했으니 반드시 실측해라)
────────────────────────────────────────────────────────────
- 오늘 만든 물리분리 픽스처(내부망 PostgreSQL neon_cap_full_src ↔ Neon
  neon_cap_full_tgt, 5% 차이)를 활용하되, 이건 PG↔PG라 이기종 검증용으로는
  안 맞는다 — **오라클↔PostgreSQL 조합으로 별도 소규모 픽스처**를 만들어서
  실제 GROUP BY/SUM 통계검증을 실행해라.
- 숫자/문자열/날짜/NULL 각 타입 조합에서 키 매칭이 정확한지(같은 값인데 다른
  값으로 오판정되는 거짓 src_only/tgt_only가 없는지) 직접 데이터로 검증해라.
- 개별검증 + 일괄검증 둘 다 실제로 돌려서 확인해라.
- 관련 테스트 서브셋 + baseline 대조(오늘 조사서가 나열한 9개 관련 테스트 파일
  재검토·갱신), 신규 회귀 0건.
- CLAUDE.md 필수 회귀(virtual/complex) 최종 1회.

  결과(타입별 케이스), 개별+일괄 양쪽 검증, 커밋해시. 작업명 첫줄/마지막줄.
