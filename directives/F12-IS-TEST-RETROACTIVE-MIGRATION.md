작업명 : F12-IS-TEST-RETROACTIVE-MIGRATION

BACKLOG.md F12 항목과 근거 보고서 PROJECT-IS-TEST-FLAG-IMPLEMENT.txt §6을 먼저 읽고
시작해줘. **이 작업은 기존 데이터 삭제를 수반하므로 단계를 반드시 나눠서 진행해라.**

────────────────────────────────────────────────────────────
1단계 — 안전한 소급 마이그레이션 (삭제 없음, 바로 진행 가능)
────────────────────────────────────────────────────────────
is_test 플래그 소급 적용 자체(한 줄 명령)를 먼저 실행. 이 단계는 삭제가 아니라
플래그 값만 채우는 거라 안전하다.

────────────────────────────────────────────────────────────
2단계 — 12건 삭제 예정 항목 사전 확인 (실행 전 여기서 멈춰라)
────────────────────────────────────────────────────────────
소급 마이그레이션 결과로 삭제 대상 12건이 정확히 어떤 프로젝트인지(이름/생성일/
마지막 활동일) 목록으로 뽑아서 완료보고에 남겨라. **실제 삭제는 이번 지침 범위에서
실행하지 말고, 목록만 만들어서 사용자 확인을 기다려라.**

────────────────────────────────────────────────────────────
3단계 — HOLD 13건 cascade 분석 (실행하지 말고 설계만)
────────────────────────────────────────────────────────────
HOLD 13건을 없애려면 자식 데이터(owner_binding, batch_group, upload_row 등)까지 지우는
cascade가 필요하다고 진단서에 적혀 있다 — `group_hard_reset_service` 같은 기존 공통
core를 재사용하는 설계를 제안하되, **실제 cascade 삭제는 이번 지침에서 실행하지 마라.**
어떤 데이터가 얼마나 삭제되는지 정확한 범위를 완료보고에 남겨라.

────────────────────────────────────────────────────────────
완료보고
────────────────────────────────────────────────────────────
1단계 실행 결과(완료), 2단계 삭제 예정 12건 목록(실행 안 함, 확인 대기), 3단계 cascade
설계안과 삭제 범위(실행 안 함, 확인 대기). "삭제까지 진행해도 될지" 사용자 재확인이
이 완료보고 이후 필요하다는 걸 명시. verify 저장소에 완료보고 push.
