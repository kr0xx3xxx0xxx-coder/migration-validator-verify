코드 수정 없이 조사만 해줘. 이 지침은 X:\Projects\Migration_Validator 이관 완료 후,
그 새 경로 기준으로 실행해줘.

배경: 지금까지 개발은 127.0.0.1:8000(로컬)에서만 해왔는데, 실제 운영 배포는 다른
장비에 설치하고 사용자가 브라우저로 그 장비의 IP(127.0.0.1이 아닌 실제 네트워크
주소)로 접속하는 구조다. 백엔드 바인딩·프론트엔드 API 호출·CORS·쿠키/세션·리다이렉트
등 어딘가에 127.0.0.1이나 localhost가 하드코딩돼 있으면, 다른 장비에서는 접속
자체가 안 되거나 API 호출이 조용히 실패하는 배포 장애가 난다.

────────────────────────────────────────────────────────────
1. [백엔드 바인딩] 서버가 어느 주소로 리슨하는지
────────────────────────────────────────────────────────────
web_server.py(또는 실제 서버 기동 파일)에서 host= 인자가 '127.0.0.1'로 고정돼 있는지,
'0.0.0.0'(모든 인터페이스 허용)인지, 아니면 환경변수/설정으로 바꿀 수 있는지 확인.
127.0.0.1 고정이면 다른 장비 접속 자체가 원천 차단된다는 뜻이니 최우선 표시.

────────────────────────────────────────────────────────────
2. [프론트엔드 API 호출] JS가 API를 부를 때 절대 URL을 쓰는지
────────────────────────────────────────────────────────────
ui/*.py가 생성하는 JS 코드 전체(fetch(), XMLHttpRequest, WebSocket 있다면 그것도)에서
'http://127.0.0.1', 'localhost:8000', 하드코딩된 IP 패턴을 전수 검색. 상대경로
(`/api/...`, `fetch('/single/...')` 등)로 되어 있으면 안전, 절대 URL이면 위험 표시.

────────────────────────────────────────────────────────────
3. [CORS·쿠키·세션·인증]
────────────────────────────────────────────────────────────
- CORS 허용 origin 목록에 127.0.0.1만 들어있는지, 아니면 설정 가능한지.
- 쿠키 domain 속성이 고정돼 있는지(있다면 다른 호스트에서 세션 유지가 안 될 수 있음).
- 오늘 만든 auth_user 테이블 기반 Basic Auth가 호스트 종속적인 부분이 있는지
  (docs/AUTH_SETUP.md도 참고해서, TLS 관련 사전 경고가 이미 있었는지 재확인 —
  Basic Auth는 자격증명이 base64 인코딩일 뿐이라 HTTPS 없이 외부 네트워크에 열면
  평문 노출 위험이 있다고 이미 기록돼 있었음, 이번 조사에서 그 위험이 실제로 얼마나
  가까워졌는지도 짚어줄 것).

────────────────────────────────────────────────────────────
4. [DB 접속 프리셋·기타 설정]
────────────────────────────────────────────────────────────
M37에서 SQLite로 이관한 DB 접속 프리셋(mv_db_preset)이나 다른 설정값에 개발 환경
전용 주소가 기본값으로 박혀 있는지(운영 배포 시 그대로 쓰면 안 되는 값들 목록화).

────────────────────────────────────────────────────────────
5. [설정 가능 여부 확인]
────────────────────────────────────────────────────────────
위에서 발견한 하드코딩 지점들이, 환경변수나 설정 파일로 바꿀 수 있게 이미 설계돼
있는지(단순히 개발 편의상 기본값이 127.0.0.1인 것뿐인지), 아니면 코드를 직접 고쳐야만
하는 진짜 하드코딩인지 구분해서 표시.

완료보고: 1~5 각각 파일:라인 목록 + 위험도(배포 시 실패 확실/조건부 실패/영향없음
구분). 착수 시 예상 수정 범위. verify 저장소에 진단 보고서만 push(코드 변경 없음).
