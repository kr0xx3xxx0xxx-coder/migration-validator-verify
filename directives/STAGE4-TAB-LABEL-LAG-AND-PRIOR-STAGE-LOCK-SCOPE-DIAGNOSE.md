라벨이 여전히 "진행중"으로 표시되는 상태.

────────────────────────────────────────────────────────────
1. [탭 라벨 지연] 4단계 완료 시점과 탭 라벨 갱신 시점이 어긋나는 원인
────────────────────────────────────────────────────────────
1~5단계 탭 라벨 텍스트가 어느 상태 변수/함수로 계산되는지 추적(오늘 M44에서 확인한
_mvCmdBarLocks 계열과 같은 소스인지, 다른 별도 상태인지 구분).
- 5단계가 이미 "상세비교 진행 중"으로 진입해 결과 화면을 그리고 있는데, 4단계 탭이
  여전히 "진행중"인 게 실제로 4단계 백엔드 작업이 안 끝난 건지(즉 5단계가 4단계 완료를
  기다리지 않고 먼저 시작됨 — 이러면 데이터 정합성 문제일 수 있음), 아니면 4단계는
  이미 끝났는데 탭 라벨만 갱신이 안 되는 순수 표시 지연인지 실측으로 구분.
- 후자라면(표시만 지연) 몇 초 뒤에 자연히 "완료"로 바뀌는지, 아니면 영구히 안 바뀌고
  다른 탭으로 갔다 오는 등 특정 트리거가 있어야 바뀌는지 확인.

────────────────────────────────────────────────────────────
2. [잠금 범위] 5단계 실행 중일 때 1~4단계 실행 버튼이 여전히 활성 상태인 것이 의도인지
────────────────────────────────────────────────────────────
오늘 M43(STAGE-EXEC-CROSS-STAGE-CONTAMINATION-AND-STOP-BUTTON-FIX) 3순위가 "실행 중
선택 컨트롤 잠금"을 다뤘는데, 그 범위가 **현재 실행 중인 단계 자신의 컨트롤**(체크박스/
관리컬럼확정/조합체크박스/WHERE)이었는지, 아니면 **다른(이전) 단계의 실행 버튼 자체**까지
포함했는지 코드로 재확인.
- 5단계(상세비교) 실행 중에 1~4단계 실행 버튼을 눌러 재실행하면 실제로 어떤 일이
  일어나는지 재현: (a) M43/M44가 넣은 abort/무효화 가드가 이미 이 케이스를 방어하고
  있어서 안전한지, (b) 아니면 이번에 처음 발견된 새로운 사각지대인지.
  (참고: STAGE-EXEC-STOP-TOGGLE-AND-LOCK-SCOPE-DIAGNOSE.txt 케이스e가 "4단계 실행 중
  1단계 재실행"은 자동 abort로 안전하다고 실측했었다 — 이번 건(5단계 실행 중 1~4단계)이
  같은 방어망 안에 있는지, 5단계라 방어망 밖인지가 핵심.)
- 사용자 의견("현 단계 진행중일 때 전단계는 모두 막아야 한다")이 타당한지, 아니면
  이미 안전하게 방어되고 있어 화면 잠금은 UX 개선일 뿐 안전 문제는 아닌지 결론 낼 것.
