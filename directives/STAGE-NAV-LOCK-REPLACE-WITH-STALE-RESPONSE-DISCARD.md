작업명 : STAGE-NAV-LOCK-REPLACE-WITH-STALE-RESPONSE-DISCARD

BACKLOG.md M73 항목(탭이동 잠금 조사, COUNT의 좁은 잠금이 재현 없이 추론으로만
선택됐다는 발견)을 먼저 읽고 시작해줘. 승인 완료.

배경: 지금 COUNT는 실행 중일 때 그 탭에서 못 나가게 막는다(`_countInProgress`).
이유는 "응답이 늦게 도착하면 그 사이 사용자가 바꾼 화면 상태를 덮어쓸 수 있다"는
추론이었는데, 실제 재현은 안 됐고, 이 방식을 택한 이유도 "제일 적게 고치는 방법"
이었을 뿐이다. 3·4단계(`_generateInProgress`/`_executeInProgress`)엔 이 문제
자체를 다루는 장치가 아예 없다.

**이번 지침은 "탭 이동을 막는" 방식 대신, "늦게 도착한 응답이면 화면에 반영하지
않고 조용히 버리는" 방식으로 교체한다 — COUNT의 탭이동 잠금을 완전히 제거하고,
COUNT·3단계(generate/후보재확정)·4단계(execute) 세 곳 모두에 동일한 방식을
적용한다.**

────────────────────────────────────────────────────────────
구현
────────────────────────────────────────────────────────────
1. 각 실행(COUNT/3단계/4단계) 요청을 보낼 때, 그 시점의 "활성 탭"을 함께 기록해라
   (또는 이미 있는 `_singleSessionVer()` 같은 세대 스탬프를 재사용해서, 탭 이동
   시에도 값이 바뀌게 확장하는 방법도 검토해라 — 어느 쪽이 기존 코드 구조에 더
   자연스러운지 판단해서 하나만 골라라).
2. 응답이 도착했을 때, 그 응답이 "지금도 여전히 유효한 상황"(사용자가 그 탭을
   안 벗어났고, 세대가 안 바뀌었는지)인지 확인하는 게이트를 응답 처리 진입부에
   추가해라.
3. 유효하지 않으면(사용자가 이미 다른 탭으로 갔다면) 화면 렌더링·상태 갱신
   (`_countState`/`_analyzeData._countMatched`/`window._singleSrcCount`/
   `_lastCountResult` 등, COUNT 조사가 이미 특정한 소비 지점들)을 전부 건너뛰고
   조용히 버려라 — 에러 표시도 하지 마라(사용자가 이미 신경 안 쓰는 상황이므로).
4. 이 게이트가 정상 작동하면, `_countInProgress`/`_mvCountInflightLock()`이
   막던 탭이동 잠금을 제거해라 — COUNT도 이제 3·4단계처럼 언제든 자유롭게 다른
   탭으로 이동 가능해야 한다.
5. 3·4단계에도 같은 방식(응답 유효성 게이트)을 동일하게 적용해서, 그동안 없었던
   방어를 새로 갖추게 해라.

────────────────────────────────────────────────────────────
검증(필수, 실제 클릭)
────────────────────────────────────────────────────────────
- COUNT 실행 중에 다른 탭으로 즉시 이동 가능한지(더 이상 안 막히는지) 확인.
- COUNT 실행 중 탭 이동 후, 그 응답이 실제로 늦게 도착했을 때 화면이 조용히
  그대로 유지되고(덮어쓰지 않고) 다음 단계 게이트 상태도 오염 안 되는지 실제로
  재현해서 확인(타이밍 조작 또는 지연 mock 등으로 재현).
- 3·4단계도 동일한 시나리오(실행 중 다른 탭 이동 → 응답 늦게 도착)로 재현해서
  같은 방어가 작동하는지 확인.
- 정상 케이스(탭 안 벗어나고 응답 받는 경우)는 기존과 100% 동일하게 동작하는지
  (회귀 없음) 확인.
- 관련 테스트 서브셋 + baseline 대조, 신규 회귀 0건.
- CLAUDE.md 필수 회귀(virtual/complex) 최종 1회.

  결과, 커밋해시. 작업명 첫줄/마지막줄.
