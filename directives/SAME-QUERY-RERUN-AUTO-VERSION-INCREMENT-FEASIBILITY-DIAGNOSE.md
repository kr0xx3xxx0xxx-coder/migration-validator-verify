작업명 : SAME-QUERY-RERUN-AUTO-VERSION-INCREMENT-FEASIBILITY-DIAGNOSE

코드 수정 없이 조사만 해줘.

배경: 오늘 확인된 캐시 메커니즘(fingerprint 기반, TTL 없음)은 "동일한
조건(접속정보+SQL+GB/SUM+scope)으로 다시 실행하면, 새로 안 돌고 기존
저장된 결과를 그대로 재사용"한다. 사용자가 다른 방향을 제안했다:

"4단계까지 실행된 쿼리는(불일치에 한해) 내부 DB에 저장되는데, 완전히
동일한 쿼리를 처음부터(1단계부터) 새로 돌리면, 캐시를 재사용하는 게
아니라 자동으로 '차수'가 1 증가해서, 최종적으로 DB에 서로 다른 차수로
각각 저장되게 할 수 있는가?" — 즉 "덮어쓰기/재사용"이 아니라 "매번 새
버전으로 누적 저장"하는 방식.

────────────────────────────────────────────────────────────
조사 항목
────────────────────────────────────────────────────────────
1. 지금 4단계(통계검증) 실행 결과가 DB(어느 테이블)에 어떻게 저장되는지
   확인해라 — 매번 새 run으로 저장되는지(즉 4단계는 이미 실행할 때마다
   새 레코드가 쌓이는지), 아니면 5단계 상세추출(fingerprint 캐시)처럼
   동일 조건이면 재사용/덮어쓰기되는지 구분해서 확인해라. 이 둘이 서로
   다른 계층일 수 있다는 점을 감안해서 각각 확인해라.
2. "1단계부터 새로 실행"이 무엇을 의미하는지 확인해라 — 사용자가 F5 새로고침
   후 완전히 새 브라우저 세션에서 1→2→3→4단계를 다시 밟는 것을 말하는
   것으로 보인다. 이 경우 워크플로 토큰이 새로 발급되는지(오늘 확인된
   workflow_stage_guard 체계), 그리고 그 새 토큰으로 실행된 4단계 결과가
   이미 "새 run"으로 분리 저장되고 있는지 확인해라.
3. 만약 4단계 자체는 이미 매번 새 run으로 저장되고 있다면(질문1 답이 "예"),
   "차수 증가"라는 개념이 이미 사실상 구현돼 있는 셈인지 판단해라 — 이
   경우 "차수"라는 이름표를 붙여서 사용자에게 더 명확히 보여주기만 하면
   되는 수준인지 확인해라.
4. 만약 4단계도 fingerprint 기반으로 재사용/스킵되는 부분이 있다면(예:
   내부적으로 뭔가 캐시를 타는 지점이 있다면), 그 지점을 찾아서 "매번
   새 차수로 저장"하도록 바꾸는 게 기술적으로 얼마나 큰 변경인지 가늠해라.
5. "차수" 개념을 화면(5단계 등)에 명시적으로 보여주려면(예: "1차 실행",
   "2차 실행" 식으로 과거 실행 이력을 나열) 어떤 추가 작업이 필요한지
   확인해라 — 이력 목록 UI가 이미 있는지, 없다면 새로 만들어야 하는지.

  구현돼 있는지, 완전히 새로 만들어야 하는지, 구현 규모는 어느 정도인지.
