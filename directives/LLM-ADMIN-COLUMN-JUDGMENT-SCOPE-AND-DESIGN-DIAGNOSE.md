작업명 : LLM-ADMIN-COLUMN-JUDGMENT-SCOPE-AND-DESIGN-DIAGNOSE

코드 수정 없이 조사·설계만 해줘. 실제 모델 다운로드/설치도 이번 범위 아님(설계까지만).

배경: 관리컬럼(SYSTEM_AUDIT) 판정을 자체호스팅 오픈소스 LLM(메타 라마 계열)으로 보강하려
한다. 배포 제약: (1) 학습/파인튜닝 없음, 순수 추론만 (2) 프로젝트 종료 시 완전 삭제 가능해야
함(설치 흔적 최소화) (3) GPU 유무가 현장마다 다른 일반 리눅스 서버 (4) 폐쇄망 가능성 있음
(외부 API 호출 불가 전제). 사용자와 사전 합의된 방향: Ollama + Docker 컨테이너 서빙,
Llama 3.1 8B 또는 3.2 3B급 양자화 모델, 컬럼명 패턴 캐싱 필수.

────────────────────────────────────────────────────────────
1. [현재 관리컬럼 판정 로직 파악]
────────────────────────────────────────────────────────────
지금 관리컬럼(SYSTEM_AUDIT) 판정이 정확히 어느 파일/함수에서 이뤄지는지(axis_a 값기반
+ axis_b 이름기반 판정 등, M19/F18/F4 백로그가 언급한 그 로직) 코드로 정확히 추적.
- 입력(컬럼명, 코멘트, 샘플값 등)이 지금 어떤 형태로 판정 함수에 들어가는지
- 출력(관리컬럼 여부, 신뢰도 등)이 어떤 형태로 나가서 이후 GROUP BY 후보 목록에
  어떻게 반영되는지
- 이 로직이 "완료 모듈"에 해당하는지(향후 수정 시 승인 필요 여부 판단 근거로)

────────────────────────────────────────────────────────────
2. [LLM 삽입 지점 설계]
────────────────────────────────────────────────────────────
기존 규칙기반 판정(이름 패턴, 값 패턴)을 대체하는 게 아니라 **3차 판정 근거**(F18이
이미 이 구조로 설계돼 있었음 — "그래도 애매하면 억지 자동판정 금지"와 동일 원칙)로
LLM을 추가하는 형태로 설계해줘:
- 규칙기반으로 명확히 판정되는 케이스는 지금처럼 LLM 호출 없이 통과(비용/속도 절약).
- 애매한 케이스(cd1류 등, 이름/값 둘 다 약한 신호)에서만 LLM에 "컬럼명+한글명(있으면)+
  코멘트(있으면)+샘플값 3~5개"를 보내 판정 요청.
- LLM 응답을 그대로 최종 확정하지 말고, 기존 원칙(근거 없으면 '판별 불가' 유지)과
  일관되게 신뢰도 낮은 응답은 여전히 사람 확인으로 넘길 것 — LLM도 오판 가능하다는
  전제로 설계.

────────────────────────────────────────────────────────────
3. [자체호스팅 LLM 연동 방식]
────────────────────────────────────────────────────────────
- Ollama는 OpenAI 호환 API(POST /api/chat 또는 /v1/chat/completions)를 제공한다 —
  이 코드베이스가 이미 쓰는 HTTP 클라이언트 패턴(requests 등, 있다면)으로 호출 가능한지
  확인.
- Docker로 Ollama+모델을 띄우는 구성을, 이 프로젝트의 배포 체크리스트
  (docs/DEPLOYMENT_CHECKLIST.md, 오늘 M49로 신설됨)에 추가할 항목으로 정리.
- 연결 실패(Ollama 컨테이너 미기동, 네트워크 문제 등) 시 **기존 규칙기반 판정으로
  안전하게 폴백**하는 구조 설계 — LLM이 없어도 지금처럼 동작해야 함(하위호환 최우선).
- 캐싱 설계: 같은 컬럼명 패턴(정규화된 형태)에 대한 LLM 응답을 SQLite(오늘 만든
  X:\Data\ 이관 구조와 일관되게)에 캐시. 캐시 키·TTL·무효화 조건을 설계.

────────────────────────────────────────────────────────────
4. [비용/성능 추정]
────────────────────────────────────────────────────────────
- 애매한 케이스 비율을 기존 진단서(F18-STRUCTURAL-SIGNAL-FALSE-POSITIVE-RATE-PRELIMINARY-
  DIAGNOSE.txt가 실측한 479개 컬럼 스윕 데이터가 있다면 그걸 활용)로 추정해서, 일괄검증
  수백 테이블 규모에서 LLM 호출이 몇 번이나 발생할지 대략 산정.
- CPU 전용 서버에서 Llama 3.2 3B급 추론 1회가 대략 얼마나 걸릴지(공개 벤치마크 기준
  참고치, 실측은 이번 범위 아님) 감안해서, 캐싱 없이 돌릴 때와 있을 때의 체감 차이를
  추정.

여부, 위험도. 승인이 필요한 부분(완료 모듈 수정이 있다면)을 명확히 표시.
