작업명 : PER-STAGE-EXECUTE-BUTTON-CLEAN-SINGLE-PASS-AUDIT

코드 수정 없이 조사만 해줘(문제 발견 시 수정 여부는 완료보고 후 별도 지시).

배경: 개별검증 1~5단계(쿼리검토/COUNT사전검증/후보컬럼선정/통계검증실행/결과확인)
각각의 "실행" 버튼을 눌렀을 때, 한 번에 깔끔하게(누수 없이, 중복 없이, 불필요한
낭비 없이) 정상 진행되는지 전수 점검한다. 오늘 발견된 몇 가지(워크플로 토큰
검증, N1 전략표시 불일치, DB커넥션 누수 등)와 연결될 수 있으니 그 맥락도 참고해라.

사용자가 이미 알고 있는 사실 (원인 확인됨): "몇몇 탭은 실행 버튼을 두 번
눌러야 한다"는 것은, 2단계(COUNT 사전검증)와 4단계(통계검증 실행)가
"쿼리 생성" 버튼 1회 + 생성된 쿼리를 "실행"하는 버튼 1회로 **의도적으로
분리된 2버튼 구조**이기 때문이다(생성된 SQL을 실행 전에 사용자가 확인할 수
있게 하려는 의도로 추정). 즉 "버그라서 두 번 눌러야 하는 것"이 아니라
"애초에 생성/실행이라는 서로 다른 두 동작이 각자 버튼으로 분리된 것"이다.
이 구조 자체는 조사 대상이 아니다 — 아래 항목 1에서 이 전제하에 세부 확인만
수행한다.

────────────────────────────────────────────────────────────
단계별 점검 항목 (1~5단계 전부)
────────────────────────────────────────────────────────────
각 단계마다:
1. 2단계·4단계의 "생성→실행" 2버튼 구조는 의도된 설계로 간주하고 버그로
   취급하지 마라. 다만 그 안에서 아래 세 가지는 확인해라:
   a. "생성" 버튼을 눌렀을 때 서버에 불필요한 중복 요청이 나가지는 않는지.
   b. "실행" 버튼이 "생성" 단계에서 만든 쿼리를 그대로 재사용하는지, 아니면
      실행 시점에 쿼리를 처음부터 다시 만드는지(재사용이 맞는 설계 —
      재생성이라면 "생성" 단계에서 보여준 SQL과 실제 실행된 SQL이 다를 위험이
      있으므로 불일치 여부까지 확인).
   c. 이 "생성→실행" 2버튼 구조가 정말 2·4단계에만 있는지, 1·3·5단계는
      실제로 버튼 1회 클릭으로 완결되는지 확인해라(1·3·5단계에도 동일한
      2단계 구조나 숨은 재클릭 요구가 있다면 그건 이 조사에서 판단이
      필요한 대상이다 — 위 "조사 대상 아님" 예외는 2·4단계 생성/실행
      분리에 한정된다).
2. 버튼을 눌렀을 때 발생하는 네트워크 요청(브라우저 콘솔/서버 로그)을 확인해서,
   불필요하게 같은 요청이 중복으로 나가는 게 있는지 확인해라.
3. DB 커넥션이 이 단계 실행 중에 열렸다가, 그 단계가 끝나면 정상적으로
   반납/종료되는지 확인해라(오늘 M80에서 다룬 것과 같은 종류의 점검을 5단계
   전체에 대해 반복).
4. 오늘 발견된 워크플로 토큰 메커니즘(services/workflow_stage_guard.py)이
   각 단계 전환마다 올바르게 갱신되는지, 혹시 특정 단계에서 토큰 갱신이 누락돼
   다음 클릭이 실패할 潜在 위험이 있는지 확인해라.
5. 오늘 발견된 N1(화면표시-실행전략 불일치)과 비슷한 종류의 "화면에 뜬 정보와
   실제 서버가 한 일이 다른" 사례가 다른 단계에도 있는지 확인해라.
