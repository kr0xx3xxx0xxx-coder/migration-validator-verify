배경: 일괄검증은 테이블이 수백~수천 개라 "행별 안내"는 부적합하다. 대신 일괄검증
완료 후 "실패 N건을 원인 유형별로 묶은 요약 1건"만 생성한다(호출 총량 배치당
1회). `services/batch_report_service.py::build_summary_sheet`가 이미 라벨/값
표를 만드는데, 서술형 요약 자리가 비어있다 — 그 자리를 채운다.

────────────────────────────────────────────────────────────
1. LLM 연동 인프라 (E1과 완전히 동일한 것 재사용)
────────────────────────────────────────────────────────────
E1이 만든 인프라(`analyzer/base_count_mismatch_llm_explainer.py` 계열 패턴,
`urllib.request` 직접호출, 기본OFF+fail-open+circuit-breaker, SQLite 캐시)를 그대로
재사용해라 — 새로 설계하지 마라. 새 explainer 클래스(BaseBatchFailureSummaryLlm
Explainer 등)만 이 용도에 맞게 추가하고, 연동 방식·안전장치는 동일하게 맞춰라.

────────────────────────────────────────────────────────────
2. 안전조건 4가지 (E1과 동일, 이번 용도에 맞게 재해석)
────────────────────────────────────────────────────────────
(a) 화면에 표시되는 실패 건수·비율 등 수치는 전부 서버 집계값만 사용.
(b) 모델에는 유형별 집계(파싱오류 N건, 분석실패 N건 등)와 대표 오류 패턴(예:
    "X컬럼 관련"처럼 이미 집계된 패턴 요약)만 전달하고, 개별 테이블명·원본 오류
    메시지 원문(자격증명 포함 위험, 오늘 M72 조사가 지적한 항목)은 전달하지 마라.
(c) 단정문 금지 — 제안형 문장으로만 생성.
(d) 미기동/장애 시 기존 방식(라벨/값 표만, 서술형 요약 없이)으로 폴백.

────────────────────────────────────────────────────────────
3. 캐시·호출 빈도 설계
────────────────────────────────────────────────────────────
배치 실행 1건당 요약 생성은 1회만 호출되도록 해라(행별 반복 호출 절대 금지 —
오늘 조사가 확인한 "수백~수천 건에 동기 호출을 넣으면 지연이 누적된다"는 제약을
지켜라). 캐시 키는 실패 유형별 건수 분포의 패턴(정확한 숫자가 아니라 구간화된
값 등, E1의 `build_pattern_key` 접근 참고)으로 잡아서 비슷한 실패 분포의 재실행
시 캐시 재사용이 되게 해라.

────────────────────────────────────────────────────────────
4. 화면단 — 클릭 시 실제 데이터로 연결 (LLM과 무관한 부분)
────────────────────────────────────────────────────────────
생성된 요약문 안의 각 유형별 건수(예: "파싱 오류 80건")를 클릭하면, **LLM이 만든
게 아니라 서버가 이미 갖고 있는 `batch_item` 데이터를 그대로 필터링**해서 그
상태(`PARSE_ERROR` 등)에 해당하는 테이블 목록으로 이동하게 만들어라. 이건 LLM
연동이 아니라 순수 필터/네비게이션 기능이다 — 새 데이터 소스를 만들지 말고 기존
일괄검증 결과 화면의 필터 기능을 재사용해라(이미 있다면 그대로 연결, 없다면 최소
구현으로 추가).

  반복 호출 없음) 확인.

  실제 클릭으로 확인.
