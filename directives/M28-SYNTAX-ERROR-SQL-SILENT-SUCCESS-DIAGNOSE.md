배경: sqlglot hang 유발 패턴을 사전차단(281d9f8)하는 휴리스틱을 우회하는 실존
변형(실 오라클 테이블+명시 컬럼)을 만들면, sqlglot 파서 진입은 차단되지만 **regex
폴백이 이를 정상 파싱한 것처럼 처리**해 `/analyze`가 `success=true`로 응답한다.
사용자 화면엔 오류가 전혀 안 뜨고 다음 단계로 진행된다 — 조용한 거짓판정 계열.

────────────────────────────────────────────────────────────
1. 현재 동작 재확인
────────────────────────────────────────────────────────────
사전차단 → regex 폴백 경로를 코드로 다시 추적해서, 정확히 폴백이 뭘 "성공"으로
간주하는지, 원래 요청된 SQL이 실제로는 무엇을 뜻하는지(문법 오류가 있는데도 뭘
추출해서 성공 처리하는지) 확인.

────────────────────────────────────────────────────────────
2. 오탐률 확인 (착수 여부 판단의 핵심)
────────────────────────────────────────────────────────────
대응 방향에 "차단 자체를 오류로 승격할지는 오탐 비용 확인이 선행돼야 한다"고
명시돼 있다 — 사전차단이 발동하는 케이스들 중, **진짜 문법 오류인 경우**와 **정상
SQL인데 휴리스틱이 과민 반응한 경우**의 비율을 가능한 범위에서 추정(실측 데이터가
있으면 사용, 없으면 최소 몇 개 실제 케이스로 표본 확인).

────────────────────────────────────────────────────────────
3. 대응안 설계
────────────────────────────────────────────────────────────
최소 대응안(권장 방향): "사전차단됨 → 폴백 파싱 결과"라는 사실을 응답/화면에 남겨서
정상 파싱과 구분되게 하는 설계. 구체적으로 어느 응답 필드에 이 플래그를 추가할지,
화면 어디에 어떻게 노출할지(경고 배지 등, 오늘 여러 번 만든 위험전용 배지 패턴 참고
가능) 설계.
더 강한 대응안(2번 오탐률이 낮으면 검토): 차단을 아예 하드 오류로 승격.
두 안의 트레이드오프와 권장안을 정리.
