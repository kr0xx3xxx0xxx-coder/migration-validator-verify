작업명 : STAGE5-TIME-DISPLAY-CONFUSION-REVERIFY-AND-PAGE-FOOTER-EXPLAIN

코드 수정 없이 조사만 해줘.

배경(스크린샷 근거): "전체 재이관 대상 : 101건 (23.22초 · 저장 데이터)"가
표시됐는데, 사용자가 실제로 체감한 시간은 1초 내외였다. 사용자 질문 3가지:

1. 23.22초가 실제 체감(1초 내외)과 왜 이렇게 다른가 — 같은 쿼리로 반복 테스트
   중이라 그런 건지 궁금해함.
2. 브라우저를 새로고침하고 다시 실행했는데, 왜 "저장 데이터"(캐시 재사용)로
   뜨는지 이해가 안 됨.
3. 이 문구 바로 아래 있는 "현재 페이지 조회 0.12초 · 내부 DB 0.01초 미만 ·
   서버 0.01초 미만 · 전체 요청 0.12초 · 화면 0.01초 미만"이 무엇인지, 위의
   23.22초와 어떤 관계인지 모르겠다고 함.

────────────────────────────────────────────────────────────
조사 항목
────────────────────────────────────────────────────────────
1. 오늘 확인된 캐시 재사용 메커니즘(fingerprint 기반, TTL 없음, 파일DB
   무기한 보관)을 근거로, "23.22초"가 정확히 언제 최초로 측정된 값인지
   확인 가능하면 확인해라(가능하면 db/exact_diff_runs.db에서 이 fingerprint
   에 해당하는 run의 원본 생성 시각을 조회해라).
2. 캐시 판정 기준이 "브라우저 세션"이 아니라 "fingerprint(접속정보+SQL+
   GB/SUM+그룹scope 전부)"라는 걸 코드로 재확인하고, 이게 왜 "브라우저를
   새로고침해도 캐시가 재사용되는" 이유가 되는지 명확히 설명해라 — 즉
   브라우저 새로고침은 클라이언트 상태만 초기화할 뿐, 서버의 fingerprint
   캐시와는 완전히 무관하다는 걸 확인해라.
3. "현재 페이지 조회 0.12초 · 내부 DB 0.01초 미만 · 서버 0.01초 미만 · 전체
   요청 0.12초 · 화면 0.01초 미만" 이 줄이 정확히 무엇을 재는지 코드로
   찾아라 — "23.22초"(그룹 전체 추출 소요, detail_elapsed_ms)와 어떻게
   다른지, 왜 이렇게 훨씬 작은 값이 나오는지 명확히 설명해라(가설: 이건
   "지금 보고 있는 페이지(10건)만 다시 가져오는" 별도의 페이지네이션 조회
   시간이고, 전체 101건을 원래 추출했던 23.22초와는 완전히 다른 작업이다 —
   이 가설이 맞는지 코드로 확인해라).
4. 위 1~3번을 종합해서, 사용자가 이해하기 쉽게 전체 그림을 설명해라 — "왜
   체감은 빠른데 큰 숫자가 뜨는지"를 한 번에 정리해라.
