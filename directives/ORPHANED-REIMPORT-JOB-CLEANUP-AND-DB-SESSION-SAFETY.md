작업명 : ORPHANED-REIMPORT-JOB-CLEANUP-AND-DB-SESSION-SAFETY

오늘 채팅 조사(그룹 전환 시 방치된 재이관 백그라운드 job, DB에 status='RUNNING'
고아 행이 서버 크래시 시 영구 잔류하는 문제, 실제 34건·927MB 전례 확인됨)를 먼저
확인해줘. 승인 완료.

배경: 서버가 비정상 종료되면 그 순간 돌고 있던 재이관 스캔 job이 DB에 'RUNNING'
상태로 영구히 남는다(자동 정리 로직 없음). 사용자가 특히 우려하는 건 **파이썬 쪽
기록뿐 아니라, 실제 원본/목적 DB(오라클/PostgreSQL) 쪽 세션·커넥션도 안전하게
정리되는지**다 — 이건 오늘 조사에서 확인 안 됐다.

────────────────────────────────────────────────────────────
1. DB 세션 안전성 확인 (필수 선행 조사)
────────────────────────────────────────────────────────────
서버 프로세스가 죽거나(kill -9 등 강제종료) 스레드가 예외로 죽는 상황을 재현해서:
- 그 순간 원본/목적 DB(오라클/PostgreSQL)에 실제로 열려있던 세션이 어떻게 되는지
  확인해라 — DB 쪽에서 그 세션이 자동으로 끊기는지(TCP 연결 끊김 시 DB 엔진이
  세션을 정리하는 게 일반적이지만, 이 프로젝트의 커넥션 관리 방식에 따라 다를 수
  있음), 아니면 DB 쪽에 살아있는 세션/락으로 계속 남는지.
- 실제로 오라클 `V$SESSION`, PostgreSQL `pg_stat_activity`로 직접 확인해라(강제
  종료 재현 전/후 세션 목록 대조).
- 만약 DB 세션이 안전하게 정리된다면(TCP 연결 끊김으로 자동 정리), 이번 지침의
  2번(정리 로직)은 순수 "파이썬 쪽 기록 정리"만 하면 되고, 만약 DB 세션이 안
  끊기고 남는다면 그것부터 별도로 심각하게 다뤄야 한다 — 완료보고에 명확히 구분해서
  표시해라.

────────────────────────────────────────────────────────────
2. 파이썬 쪽 고아 기록 정리 로직 구현
────────────────────────────────────────────────────────────
- **서버 기동 시 1회 정리**: 서버가 새로 뜰 때, 그 이전 프로세스가 남긴
  status='RUNNING' 행은 전부 이번 프로세스가 시작한 게 아니므로 무조건 고아로
  간주해도 안전하다(오늘 M62에서 썼던 것과 같은 논리 — 기동 시점 이전 RUNNING은
  구조적으로 이전 프로세스 것). `store.finish_run(status="ORPHANED")`로 정리해라.
- **주기적 정리(sweeper)**: 진단 문서가 이미 제안한 "유휴 회수(idle reclaim)"
  설계(TTL/heartbeat 기반)를 참고해서, 아무도 그 그룹을 다시 조회하지 않아도
  주기적으로(예: 몇 분마다) 오래된 in-memory job 상태를 점검해 죽은 스레드를
  감지·정리하는 배경 스레드를 추가해라. 기존 `reclaim_dead_thread_jobs`(lazy
  방식)가 있다면 그 판정 로직은 재사용하고, "누군가 조회할 때만 발동"하는 트리거
  방식만 "주기적 자동 발동"으로 바꿔라.
- 오늘 M59에서 만든 heartbeat 패턴이 있다면(다른 job 시스템용이지만) 재사용
  가능한지 검토해라 — 없으면 새로 만들어도 된다.

────────────────────────────────────────────────────────────
검증(필수, 실측)
────────────────────────────────────────────────────────────
- 실제로 서버를 강제종료(kill -9)해서 RUNNING 고아 행을 만든 뒤, 재기동 시 자동으로
  ORPHANED 처리되는지 확인.
- 스레드만 죽는 상황(강제종료 아님)을 재현해서, 주기적 sweeper가 아무도 조회 안 해도
  스스로 정리하는지(기존엔 lazy라 아무도 조회 안 하면 영원히 안 됐던 것) 확인.
- 1번에서 확인한 DB 세션 상태와 연계해서, 이 정리 로직이 DB 세션 정리에도 관여해야
  하는지(1번 결과에 따라 판단) 최종 확인.
- 정상 진행 중인 job(진짜 살아있는 것)이 실수로 고아 처리되지 않는지(오탐 방지)
  확인 — 오늘 M59에서 정확히 이런 유형의 위험(정상 job이 죽은 것으로 오판)을
  피했던 것과 같은 신중함 필요.
