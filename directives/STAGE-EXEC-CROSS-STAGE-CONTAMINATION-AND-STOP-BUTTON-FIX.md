작업명 : STAGE-EXEC-CROSS-STAGE-CONTAMINATION-AND-STOP-BUTTON-FIX

STAGE-EXEC-STOP-TOGGLE-AND-LOCK-SCOPE-DIAGNOSE.txt(조사 완료본)를 먼저 읽고,
그 진단이 확정한 아래 4가지를 순서대로 고쳐줘. 각 항목 완료·검증 후 다음으로 넘어갈 것.
5번(2단계 COUNT SQL 기준 표시)·6번(死코드 정리 등)은 이번 범위 아님 — 건드리지 마.

────────────────────────────────────────────────────────────
1순위 [최우선] 다중 GROUP BY 세트 루프 신선도 방어 (항목2-1-나, 항목4-7)
────────────────────────────────────────────────────────────
_runExecutePlanSets(ui/tabler_renderer.py:26666)가 세트마다 DOM/전역객체(tgtWhere,
_analyzeData, candSnap, src_db/tgt_db)를 매번 재조회해서, 실행 도중 값이 바뀌면
세트마다 다른 조건으로 실행되는 문제(진단서 항목2-1-나 실측 재현 그대로).

- 루프 진입 시점에 필요한 값(tgt_where, analyze 스냅샷, candidate snapshot, db 선택)을
  **1회만 캡처해서 모든 세트가 그 스냅샷을 공유**하도록 수정. 세트 간 재조회 제거.
- fetch에 signal이 없는 문제(단일세트 경로:29360, runCount:24869, runGenerate:26392엔
  있는데 이 루프의 /generate:26743, /execute:26763엔 없음)도 같은 abort signal 배선.
- 세션버전 검사가 루프 종료 후 1회뿐인 것(:26788)을, 세트 반복 사이에도 검사하도록 추가
  (버전 바뀌면 루프 즉시 중단).

검증: 진단서 케이스e(4단계 실행 중 1단계 재분석)와 케이스(다중세트 중 tgtWhere 변경)를
동일 조건으로 재현해서, 이제 세트 간 조건이 안 섞이고/세션 바뀌면 루프가 멈추는지 확인.

────────────────────────────────────────────────────────────
2순위 [최우선] 4단계 실행 멈춤 버튼 신설
────────────────────────────────────────────────────────────
서버 CancelToken은 이미 완성(진단서 항목1 — /execute, /count 모두 있음), UI만 없음.
- 4단계 "실행 중…" 버튼을 클릭 가능한 "■ 중단" 버튼으로 교체(5단계 기존 "실행 중단"
  버튼과 동일 패턴 재사용 권장).
- 1순위에서 추가한 다중세트 루프 abort signal과 연결 — 세트 실행 중에도 멈춤이 먹혀야 함.
- 2단계 COUNT도 서버 로직은 있으니(항목1 표), 같은 패턴으로 멈춤 버튼 추가.
- 1·3단계, 5단계 死코드는 이번 범위 아님(보고서 6번 보류 항목).

검증: 4단계 단일세트/다중세트 각각 실행 중 멈춤 클릭 → 서버 쿼리 실제로 죽는지
(pg_stat_activity 등으로) 확인. 2단계도 동일 검증.

────────────────────────────────────────────────────────────
3순위 [우선] 실행 중 선택 컨트롤 잠금
────────────────────────────────────────────────────────────
진단서 항목2가 확인한 잠금 전무 지점들 — 3단계 GB/SUM 체크박스, 관리컬럼 확정 버튼
(js_admin_column_override.py), 조합 체크박스 #gbIncludePair(js_sql_preview.py),
목적지 WHERE(#tgtWhere) — 를 실행 중(_executeInProgress/_countInProgress/
_revalidateInProgress 등 기존 플래그 활용)에는 클릭 불가하게 잠글 것.

- 지시대로 disabled 속성이 아니라 **오버레이 방식(pointer-events 차단)**으로 구현
  (진단서 권장 — 게이트 로직 변경 없이 해소 가능).
- 진단서가 지적한 "가드끼리 서로 안 보는" 문제도 같이 고칠 것: runRevalidateFromCandidate
  (:16278)가 _executeInProgress도 확인하도록, runGenerate(:26305)에 in-progress 가드
  자체를 추가.

검증: 진단서 재현 케이스(S2/S5/S6)와 동일하게, 이제 실행 중 클릭 시도가 막히는지 확인.
"성공한 실행 결과에 도달 불가"(진단서가 지적한 치명급 UX 결함)도 같이 해소되는지 확인.

────────────────────────────────────────────────────────────
4순위 [중간] 4단계 실행 중 2·3단계 재실행 시 무효화 롤백 차단
────────────────────────────────────────────────────────────
늦게 끝난 실행이 무효화 상태를 되돌리는 문제(진단서 4-5,4-6) — 3순위(잠금)를 넣으면
애초에 발생 자체가 막히지만, 혹시 잠금을 우회하는 경로가 남는지 재확인하고,
_singleClearStage5ResultStale()이 렌더 경로에서 무조건 호출되는 부분(진단서가 지목한
지점)을 조건부 호출로 좁혀줘 — 무효화된 상태에서는 배너가 계속 보여야 함.

검증: 진단서 케이스b(4단계 실행 중 2단계 COUNT 재실행)를 3순위 적용 후에도 억지로
재현 시도해서, 무효화 배너가 끝까지 유지되는지 확인.
