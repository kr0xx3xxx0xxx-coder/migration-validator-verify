"바꿀 가치가 있어 보인다"고 판단했으나, 장기 과제로 표시된 만큼 바로 구현하지 말고
범위·설계부터 정하는 조사다.

배경: 다축 통계검증(GROUP BY 여러 개)이 지금은 축마다 독립 쿼리로 테이블을 반복
스캔한다. UNION ALL 또는 GROUPING SETS로 한 번에 여러 축을 집계하는 통합 쿼리로
바꾸면 스캔 횟수를 줄일 수 있다.

1. [현재 구조 파악] SQL 생성(축별 독립 쿼리를 만드는 지점) → 실행 → 결과 파싱 →
   판정(불일치 비교) 전체 파이프라인에서, "축 1개 기준"으로 짜여 있는 지점을 전부
   특정해라(파일:라인 목록).

2. [통합 쿼리 방식 비교] UNION ALL 방식과 GROUPING SETS 방식 각각:
   - 4방언(PostgreSQL/오라클/MySQL/MSSQL) 지원 여부·문법 차이
   - 결과 파싱 복잡도(통합 결과에서 축별로 다시 분리하는 로직 규모)
   - 기존 판정 로직(불일치 비교 등)에 미치는 영향 범위
   비교해서 권장안 제시.

3. [예상 작업 규모] SQL 생성기·실행기·파서·어댑터 계층 각각 몇 개 파일을 건드려야
   하는지, 이 저장소의 "완료 모듈" 규칙에 해당하는 파일이 몇 개나 포함되는지 확인.
   전면 재작업 vs 점진적 도입(예: PostgreSQL만 먼저 지원하고 나머지는 기존 방식
   유지) 중 더 안전한 착수 순서 제안.

4. [성능 이득 사전 추정] 지금 반복 스캔 방식과 통합 쿼리 방식을, 실제 대용량
   픽스처(가능하면 NXDNP.MV_SCATTER50M_SRC/TGT 등)로 축 2~3개 기준 미리 비교
   실측해서, 구조 변경이 실제로 유의미한 성능 이득을 주는지 먼저 확인(이득이
   미미하면 착수 우선순위를 재조정할 근거가 됨).
