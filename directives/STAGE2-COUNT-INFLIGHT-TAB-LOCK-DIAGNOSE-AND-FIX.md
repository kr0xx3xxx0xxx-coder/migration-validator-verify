작업명 : STAGE2-COUNT-INFLIGHT-TAB-LOCK-DIAGNOSE-AND-FIX

배경: 사용자가 2단계(COUNT 사전검증) 실행 중 응답이 지연되는 상황에서, 다음 단계
탭으로 이동 가능한(잠금이 안 걸린) 상태를 목격했다. 오늘 M43/M47/MVANYRUNACTIVE에서
"다른 실행이 진행 중이면 다른 단계 실행을 잠근다"는 원칙을 여러 번 다뤘는데, 2단계
COUNT 실행 중 탭 이동 자체를 막는 로직이 그 틀 안에 실제로 포함돼 있는지 확인이
필요하다.

────────────────────────────────────────────────────────────
1. 재현 및 원인 조사
────────────────────────────────────────────────────────────
2단계 COUNT 실행을 실제로 트리거하고(가능하면 응답이 느린 대용량 테이블로 지연 상황을
재현), 실행 중에 다음 탭(3단계)이나 다른 탭으로 이동 가능한지 실제 클릭으로 확인.

원인을 코드로 추적해줘 — 오늘 여러 번 다룬 `_mvAnyRunActive()`가 COUNT 실행 상태를
포함하는지, 포함한다면 왜 탭 이동 잠금에는 반영이 안 되는지(잠금 대상 목록에 탭
네비게이션이 빠져있는지), 아니면 COUNT 실행 자체가 애초에 `_mvAnyRunActive()`가 감시
하는 상태 목록에 안 들어가 있는지 확인.

────────────────────────────────────────────────────────────
2. 판정 — 의도된 설계인지 결함인지
────────────────────────────────────────────────────────────
"COUNT 실행 중에도 다른 탭으로 자유롭게 이동 가능"이 의도된 설계(예: COUNT는 가벼운
작업이라 탭 이동을 막을 필요가 없다고 판단됐을 수 있음)인지, 아니면 놓친 배선인지
코드 주석·커밋 이력에서 근거를 찾아라. 의도를 뒷받침하는 명시적 근거가 없다면 결함
쪽으로 판단.

────────────────────────────────────────────────────────────
3. 수정 (결함으로 판정된 경우)
────────────────────────────────────────────────────────────
2단계 COUNT 실행 중에는 다른 탭 이동이 오늘 4단계/5단계에 적용한 것과 같은 원칙
(잠금 표시 + 클릭 시 이유 안내)으로 막히도록 배선. 오늘 만든 `_mvAnyRunActive()`/
`_mvSyncRunLockedControls()` 패턴을 그대로 재사용(새 잠금 메커니즘 발명 금지).
