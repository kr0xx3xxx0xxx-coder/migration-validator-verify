================================================================================
0. 한 줄 결론
================================================================================
_evaluate_compatibility 는 **역할(GROUP BY/SUM) 분류와 완전히 무관하게, 스코어링 대상
컬럼 전체(매핑된 validated + excluded 컬럼 전부)에 대해 1행씩 무조건 호출된다.**
역할 필터는 이 함수 안에 존재하지 않으며, 오히려 이 함수의 결과가 SUM/GROUP BY 역할
평가의 **입력으로 먼저 계산**된다(호출 순서상 역할 판정보다 선행). 따라서 "GROUP BY·집계
컬럼에만 한정되는가"라는 우려는 코드상 **사실이 아니다 — 한정되지 않는다.**

단, 실효(판정에 영향을 주는) 범위는 별개 문제이며 4·5절에 분리해 기술한다.

================================================================================
1. 함수 시그니처
================================================================================
services/candidate_scoring_runner.py:327

    def _evaluate_compatibility(
        src_meta: ColumnMeta | None,
        tgt_meta: ColumnMeta | None,
        src_col: str,
        tgt_col: str,
    ) -> tuple[str, list[str], bool]:
        """
        (compatibility_status, risk_flags, risk_gate_blocked) 반환
        """

인자에 role / applicability / selection_status / 후보여부를 뜻하는 파라미터가 **하나도
없다.** 즉 이 함수는 호출 시점에 해당 컬럼이 GROUP BY 후보인지 SUM 후보인지조차 알 수
없다. 이것이 "역할 무관"의 1차 증거다(자료구조 수준 증거).

2-3. 상위 역추적 — 대상 컬럼 집합의 실제 정체

run_scoring_from_contexts 의 운영 진입점은 routes/csr_preview_route.py:165 (POST
/csr-preview) 이며, contexts 는 services/analyze_to_csr_adapter.py:
build_contexts_from_analyze 가 만든다. 그 대상 집합은:

    103    validated: list[dict] = analyze_result.get("validated", [])
    104    excluded:  list[dict] = analyze_result.get("excluded",  [])
    106    all_items = list(validated) + [ ... for c in excluded ]
    122    for item in all_items:
    127        if not tgt_col:
    128            continue

즉 대상은 **검증대상(validated) 컬럼 + 제외(excluded) 컬럼 전부**이며, 유일한 스킵
조건은 "목적지 컬럼명이 비어 있음"(127~128행)뿐이다. GROUP BY 후보/SUM 후보 여부는
집합 구성에 아무 영향을 주지 않는다. **제외 컬럼(EXCLUDED_COLUMN)까지 compat 평가를
받는다** — 역할 무관의 가장 강한 증거다.

run_scoring(A) 쪽 진입점은 scripts/run_candidate_scoring.py 등 스크립트 전용이다.

3. 역할(role)별 적용 여부 표
================================================================================
"_evaluate_compatibility 가 호출되는가"(=실효 문자 수용량 비교 코드에 진입하는가) 기준.

  후보 역할 분류                        | 호출됨? | 근거
  --------------------------------------|---------|--------------------------------
  GROUP BY 후보로 선정된 컬럼           |   ✅ 예 | 루프가 role 무관 (991 / 494행)
  SUM 후보로 선정된 컬럼                |   ✅ 예 | 동일
  둘 다 아닌 일반 검증대상 컬럼         |   ✅ 예 | 동일. role 필터 없음
  미분류(semantic UNKNOWN) 컬럼         |   ✅ 예 | 동일
  제외(excluded) 컬럼                   |   ✅ 예 | adapter 106행에서 집합에 포함
  단순 표시용 컬럼                      |   ✅ 예 | 별도 취급 자체가 없음
  목적지 컬럼명이 빈 컬럼               |   ❌ 아님| adapter 127~128행 continue
                                        |         | (role 아닌 '매핑 부재' 사유)

→ **role 에 따라 걸리기도/안 걸리기도 하는 분기는 존재하지 않는다.** 지침 4항이 가정한
  "GROUP BY 후보는 체크, 표시용은 미체크" 형태의 분기 조건은 코드에 없다.

5. 텍스트형(문자) 컬럼 판정이 role 필터를 통과한 컬럼에만 걸리는가
================================================================================
결론: **role 필터와 무관하다. 순수하게 타입 기반이다.**

게이트는 정규화 타입 2개뿐이다(339~340, 428, 448행):
    sn = (src_meta.normalized_type if src_meta else "unknown").lower()
    tn = tgt_meta.normalized_type.lower()
    if sn == tn:            ← 양쪽 동일 계열
        if sn == "text":    ← 양쪽 text
문자형 판정 경로에 semantic_type / applicability / selection_status / 후보목록 참조가
전혀 없다. role 정보는 애초에 이 함수로 전달되지 않는다(1절).

--------------------------------------------------------------------------------
5-1. 다만 '실효 영향'은 하류에서 비대칭이다 (중요 — 구분해 읽을 것)
--------------------------------------------------------------------------------
호출 범위는 role 무관이지만, 그 결과가 실제로 판정을 바꾸는 범위는 하류 소비자
(_evaluate_sum / _evaluate_group_by / _check_critical_fail)에서 갈린다.

  · SUM 축: 문자형은 Gate 2 에서 즉시 탈락한다.
        candidate_scoring_runner.py:496~497
        if norm_type in ("text",):
            return "NOT_APPLICABLE", None, "NOT_APPLICABLE", ["SUM_NA_TEXT_TYPE"]
    → 이 return 은 compat_status/rflags 를 **읽기 전에** 발생한다. 따라서
      CHAR_CAPACITY_SHRINK_RISK 가 SUM 판정을 바꾸는 일은 **구조적으로 불가능**하다.
      CF-SUM-03(896행 "PRECISION_LOSS_RISK → SUM SELECTED_DEFAULT")도 문자형은
      sum_selection_status 가 NOT_APPLICABLE 이므로 성립하지 않는다.

  · GROUP BY 축: 차단되지 않는다.
        candidate_scoring_runner.py:697
        if risk_gate_blocked and compatibility_status not in ("COMPATIBLE", "PRECISION_LOSS_RISK"):
    → 이번 플래그는 risk_gate_blocked=False + status="PRECISION_LOSS_RISK"(463행)로
      반환되므로 위 조건을 통과하지 못한다. GROUP BY 후보 자격은 **불변**이다.

  · 종합: 이번 추가분은 **판정을 바꾸지 않는 설명(explainability) 전용 플래그**로 동작
    한다. risk_flags 에 CHAR_CAPACITY_SHRINK_RISK 가 기록되고 compatibility_status 가
    COMPATIBLE → PRECISION_LOSS_RISK 로 바뀌는 것이 관측 가능한 전부다.

6. 운영 경로 미도달 (반드시 함께 읽어야 하는 제약)
================================================================================
위 호출 범위는 "함수가 호출되는 범위"이고, 실제 운영 화면에서 **수용량 비교 코드까지
도달하지는 못한다.** 근거:

  routes/csr_preview_route.py:164~169

          contexts=adapter_result.contexts, ...)

  services/analyze_to_csr_adapter.py:152~156
      # metadata/stats는 None → NullProvider 효과
      source_metadata=None,
      target_metadata=None,

  → tgt_meta 가 None 이면 candidate_scoring_runner.py:336~337 에서 즉시 반환된다.
      if tgt_meta is None:
          return "UNKNOWN_COMPATIBILITY", ["UNKNOWN_TARGET_COMPATIBILITY"], True
    타입별 분기(348행 이하)에 진입하지 못하므로 448행 수용량 비교는 실행되지 않는다.

메타를 실제로 채우는 provider 는 services/postgres_metadata_provider.py 하나뿐이고
PG 전용 + scripts/ 스모크 테스트 전용(웹 앱 미배선)이다. 오라클용 metadata provider 는
