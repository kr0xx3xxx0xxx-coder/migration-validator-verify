결론: 추정이 정확히 맞았다. PostgreSQL 은 오라클과 달리 text/integer 간 암묵 형변환이 전혀
없어(바인드 파라미터든 리터럴이든, 운영 코드 경로든 원시 SQL 이든 동일), 문자 PK 컬럼에 숫자를
비교하면 그 즉시 UndefinedFunction 쿼리 오류로 실행 자체가 막힌다 — "조용히 틀린 결과"가 아니라

"오류·경고 없이 조용히 틀림"(축 B, merge-join 정렬전제 위반) 결함이 PG 에서는 애초에 성립하지
않음을 뜻한다 — 오라클 쪽 결함(축A·축B)의 근본 대응(문자 키 chunk 경로 차단 등)은 여전히 필요
하지만, PG 는 그 결함의 "조용한 오판정" 버전에 노출되지 않는다는 비대칭이 실측으로 확정됐다.

[중요 발견 — 원안(v$session) 실행 불가, 새로운 환경 제약]
  PostgreSQL 대칭 스크립트(m69_pg_terminate_orphan_live_verify.py)와 동일하게 v$session 직접
  폴링을 먼저 시도했으나, 이 저장소의 유일한 오라클 프리셋 계정(Oracle_asis, nxdnp)은
  SELECT_CATALOG_ROLE 이 없어 v$session 은 물론 v$mystat 등 모든 V$ 뷰에서 ORA-00942(권한 부족)
  가 발생함을 실측으로 확인(DBA 권한 프리셋은 이 저장소에 없음). 이는 BACKLOG 부록에 새로 등재할
  가치가 있는 환경 제약이다(C2 표에는 미포함 — 별도 판단 필요 시 후속 지침에서 처리 권고).

[대체 실측 방법]
  같은 질문("죽은 클라이언트의 서버측 자원이 실제로 얼마나 빨리 회수되는가")에 권한 없이 답하는
  대리지표로 전환 — 자식 세션이 SELECT ... FOR UPDATE 로 행 잠금을 걸고(커밋 안 함) "쿼리 실행
  중"(CONNECT BY LEVEL 순수 CPU 연산) 상태에서 taskkill /F 로 강제종료된 뒤, 그 잠금이 다른
  세션에서 FOR UPDATE NOWAIT 로 몇 초 만에 획득 가능해지는지 폴링했다(잠금 해제는 세션 종료의
  직접 결과이므로 v$session 소멸 시점의 유효한 대리 지표).

  ※ 실측 중 발견한 레이스 1건(수정 반영됨): HEAVY_SQL 이 taskkill 이전에 먼저 끝나면 자식
    프로세스가 정상 종료되며 잠금이 "정상 rollback"으로 풀려버려, 애초에 좀비 시나리오가 성립하지
    않는 문제를 확인 — 부모가 강제종료할 때까지 자식이 확실히 살아있도록 쿼리 소요시간에 의존하지
    않는 강제 대기(time.sleep)를 추가해 결정적으로 재현되게 고쳤다.

  실측 결과(2회 반복, 재현성 확인):
    1회차 — 강제종료 전 잠금 보유=True, 강제종료→잠금해제 0.03초(총 경과 0.12초)
    2회차 — 강제종료 전 잠금 보유=True, 강제종료→잠금해제 0.01초(총 경과 0.10초)

  판정: 원 실측 기준선(ORPHANED-REIMPORT-JOB-CLEANUP-AND-DB-SESSION-SAFETY.txt §1, v$session
  기준 1.1초)과 같은 자릿수(오히려 더 빠름, 0.01~0.03초)로 재현됨 — "오라클은 강제종료 시
  안전하게 자동 정리된다"는 기존 결론을 지지하는 독립 실측 근거를 확보했다. 다만 측정 지표가
  다르므로(잠금 해제 vs v$session 소멸) 완전히 동일한 수치의 재현은 아니고, 같은 결론을 뒷받침
  하는 대리 실측이라는 점은 명시해 둔다.
