[0] 결론 요약
================================================================================
1. **두 값은 거의 항상 비슷하다 — 그리고 규모가 커질수록 더 똑같아진다.**
   병렬 실행에서 processing_ms ≈ max(원본, 목적) + 8~40ms 다. 5,000만행에서는 오차가
   0.07~1.0% 로 사실상 동일한 값이 된다. 지침이 세운 가설("대량 데이터·복잡 SQL 에서는 차이가
   유의미해질 것")은 **실측으로 기각**됐다 — 오버헤드는 규모·SQL 복잡도와 거의 무관한 상수다.

2. **정보 포함관계는 한 방향이다.** COUNT 소요(2값) → 처리시간은 계산 가능(오차 ±40ms),
   처리시간 → COUNT 소요는 복원 불가(어느 쪽이 느린지 알 수 없다).
   즉 중복이라면 **없앨 쪽은 처리시간이지 COUNT 소요가 아니다.** 지침 2번이 제시한
   "COUNT 소요를 툴팁으로 격하" 방향은 정보량이 큰 쪽을 숨기는 것이라 비권장한다.

3. 다만 **처리시간을 통째로 없애는 것도 권하지 않는다.** 병렬/순차에 따라 총시간이
   max 인지 합인지가 달라져(실측 확인) 사용자가 두 값에서 총시간을 암산할 수 없기 때문이다.
   → 최종 제안: 'COUNT 소요' 타일 하나에 원본/목적/총 3줄을 담고, 비는 타일 칸은
     'COUNT 방식'(count_generation_method)으로 채운다. 타일 8개 유지, 중복 제거, 정보량 +1.

================================================================================
[2] "COUNT 소요"가 "처리시간"을 포함해버리는가 (지침 2번)
================================================================================

■ 결론 : 포함한다. 단 **방향이 지침의 전제와 반대**다.

  · 처리시간 = f(COUNT 소요) : **계산 가능**
      병렬 → max(원본, 목적) + ε,  순차 → 원본 + 목적 + ε   (ε = 8~40ms, 실측)
  · COUNT 소요 = g(처리시간)  : **복원 불가능**
      총시간 하나로는 원본이 느린지 목적이 느린지, 비대칭이 얼마인지 알 수 없다.
      실측 예: 5,000만행 #1 은 원본 18,496ms / 목적 8,805ms 로 **2.1배 비대칭**인데
      처리시간(18,508ms)만 보면 이 사실이 전혀 드러나지 않는다.

■ 그래서 "COUNT 소요를 툴팁으로 격하하고 처리시간만 남기는" 안은 비권장한다.
  정보량이 큰 쪽(2값 + 비대칭)을 숨기고 파생값(1값)을 노출하는 셈이라, 지금 문제(중복)를
  해결하지 못한 채 어느 쪽 DB 가 병목인지만 다시 잃는다.

■ 반대로 "처리시간이 순수 중복이니 그냥 없애자"도 단독으로는 부족하다.
  1-B 실측대로 총시간 관계식이 병렬/순차에 따라 다르고, 화면은 그 모드를 알려주지 않는다.
  총시간을 사용자에게 암산시키면 안 된다.

■ 처리시간만이 담는 고유 정보 = 서버 오버헤드(파싱 + COUNT SQL 생성 + 연결)
  · 정상 상태 8~40ms — 초 단위로 표시되는 타일에서는 '0.01초 미만' 수준이라 사실상 안 보인다.
  · 프로세스 최초 1회만 ~350ms. 소규모(300행)에서는 총시간의 66~77% 를 차지하지만
    절대값은 0.35초이고, 두 번째 실행부터 사라지므로 상시 타일 한 칸의 값어치는 아니다.

    되어 있어 순차 경로(같은 물리 DB)에서는 사실과 어긋난다. 이는 별건의 표기 오류다.

[4] 처리시간 타일을 없애고 COUNT 소요만 남기는 반대 방향 (지침 4번)
================================================================================

■ 먼저 확인한 사실 : **처리시간은 화면에서 중복 표시되고 있지 않다.**
  단계 탭 바에 1~5단계 처리시간 슬롯이 있으나(tabler_renderer.py:2433-2437),
  1·2·3단계 슬롯은 상시 비노출로 차단돼 있다(validation_plan_renderer.py:871):

      var _hidden = { 1: true, 2: true, 3: true };   /* 1~3단계 = 각 단계 타일 '처리시간' 항목으로 이전됨 */

  주석(같은 파일 865-867)도 "값은 2단계 타일의 '처리시간' 항목이 같은 소스(c.processing_ms)로
  보여준다"고 못박는다. 즉 2단계 처리시간의 **화면 유일 출처가 이 타일**이므로, 그냥 제거하면
  값이 화면에서 사라진다.

■ 그럼에도 '한 칸을 통째로 쓸 값'인가 : 아니다.
  · [2]에서 본 대로 처리시간은 COUNT 소요의 파생값이고, 고유 정보(서버 오버헤드)는
    정상 상태에서 0.01~0.04초라 초 단위 표기에서 보이지도 않는다.
  · 타일 한 칸은 화면에서 가장 비싼 공간이다(8칸 고정, 나란히 비교되는 자리).

■ 최종 제안(구현하지 않음) — 흡수 + 대체

  제안 8타일 : 목적 테이블 | 원본 테이블 | COUNT 소요 | 목적건수 | 원본 건수 | 차이 | COUNT 방식 | 상태
                                              ↑                                          ↑
                          값 3줄로 확장                        처리시간 자리를 대체

      COUNT 소요 타일 값 :   원본 1.61초
                             목적 0.76초
                             총   1.62초        ← 기존 '처리시간' 값을 세 번째 줄로 흡수
      툴팁               :   원본 1610.2ms / 목적지 760.4ms · 총 1620.1ms

  선정 이유
    1) 중복의 근본 원인(파생값이 독립 타일을 차지)이 사라진다 — 같은 타일 안에 있으면
       '총 = 느린 쪽 + α' 관계가 나란히 보여 중복이 아니라 설명이 된다.
    2) 정보 손실 0 — 처리시간 값은 그대로 남는다(화면 유일 출처 유지, [4] 첫 항 문제 해소).
    3) 빈 칸에 처리시간과 안 겹치는 유일한 후보(COUNT 방식)가 들어가 정보량이 순증한다.
    4) 새 계측·새 서버 왕복·새 CSS 가 전혀 필요 없다 — 세 값 모두 이미 같은 응답에 있고,
       3줄 값 규격(kind:'multi')은 지금 'COUNT 소요' 타일이 이미 쓰고 있다
       (_MV_COUNT_TILE_VIRTUAL, tabler_renderer.py:24945).

■ 차선안(구현 비용을 더 낮추려면)
  · 타일 구성은 그대로 두고 **'처리시간' 라벨만 '총 소요(서버 포함)'로 바꾼다.**
    두 타일이 다른 것을 재고 있음이 라벨만으로 드러나 중복 인상이 줄어든다. 정보량 증가는 없다.

■ 비권장안
  · "COUNT 소요를 없애고 처리시간만" — [2]대로 정보량이 큰 쪽을 버리는 방향.
