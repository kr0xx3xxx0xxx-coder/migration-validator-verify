1. 각 열의 정확한 용도/출처 (코드 근거)
────────────────────────────────────────────────────────────────────────
대상 함수: ui/grid_helpers.py `_mvRenderCandidateGrid` (→ #mvStage3CtxGrid 렌더)

[입력 컬럼수 insCols / 추출 컬럼수 selCols]
  - 출처: `_mvColsOf(a).insN` / `.selN`
      insN = parse_result.insert_cols 길이 (INSERT 대상 컬럼 수)
      selN = parse_result.select_items 중 tgt_col 보유 수 (없으면 insert_cols 재사용)
  - 1단계 쿼리검토 그리드(_mvQueryReviewRows, grid_helpers.py:298)도 완전히 동일한
    `_mvColsOf(a).insN/selN` 을 사용 → 값·출처가 100% 동일.
  - 정상 INSERT..SELECT 는 입력=추출 이라 항상 같은 값(실측 7/7).
  - 판단: 순수 중복. 3단계 맥락에서 '후보 필터링 이후 남은 수' 같은 다른 의미가 아님
    (필터링 전 원시 파싱 개수 그대로). → 제거(1단계에서만 표시).

[매칭키 matchKey / 분할키 chunkKey]
  - 출처: `a.candidate_recommendation.exhaustive_validation_candidates
           .match_key_candidates[0] / .chunk_key_candidates[0]`
  - 이 필드를 만드는 유일한 생산자: services/diagnosis/candidate/recommender.py
    `recommend_candidates()` → `_exhaustive()` (match_key_candidates 는 is_pk/is_unique 일 때 채움).
  - `recommend_candidates()` 호출부는 전 코드베이스에서 단 1곳:
    routes/diagnosis_route.py:1065 (전수검증 '배치/진단' 상세 경로).
  - 개별검증 analyze 응답(single_validation_analyze_service.py / facade / postcount)은
    candidate_recommendation 을 절대 싣지 않는다.
  - 프론트 `_mvRenderCandidateGrid` 는 rec(=candidate_recommendation)가 있을 때만
    (`if(rec)` 분기) mk/ck 를 계산하고, 없으면 else 분기로 빠져 mk/ck 는 '-' 초기값 유지.
  - 판단: 개별검증 3단계에서는 PK 유무·테이블 규모와 무관하게 rec 이 항상 undefined 이므로
    매칭키/분할키는 구조적으로 항상 '-'인 죽은 열. (대용량 청크비교 전용 조건이 아니라,
    이 화면에는 데이터 원천 자체가 없음.) 매칭키/분할키는 전수검증 배치 진단 상세
    화면(_mvRenderCandidateRecommendation) 소관. → 제거.

[SUM / GROUP BY]  (유지)
  - rec 없을 때 else 분기가 a.all_groupby_candidates / a.all_sum_candidates pool 에서
    상위 후보를 source↔target 쌍으로 표시. 이 단계 고유 정보이며 1단계에 없음 → 비중복. 유지.
