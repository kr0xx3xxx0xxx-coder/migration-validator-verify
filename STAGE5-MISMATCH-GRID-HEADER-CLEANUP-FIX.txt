4. 항목5 조사 결과 — 설계인가 배선 누락인가
════════════════════════════════════════════════════════════════════════
결론: **설계상 맞다(배선 누락 아님).**

근거:
 (1) ui/tabler_renderer.py `_mvPkTreeRecRow()` 에 판정 열을 '의도적으로 비우는'
     분기가 명시돼 있었다 — `if (c.role === 'verdict') { tds += '<td></td>'; }`.
 (2) 같은 함수를 부르는 `_mvPkLoadPage()` 주석에 레코드표 컬럼 계약이 못 박혀 있다:
     "판정/영향항목/기여값/차이/조치 열 금지(§37·§38)".
     즉 판정은 '그룹 단위'로만 산출하며, 레코드 단위 판정은 애초에 존재하지 않는다.
 (3) 서버 pk-records 응답에도 레코드별 판정 필드가 없다(diff_cols 만 있고, 이는
     '어느 컬럼이 다른가'이지 PASS/WARNING 같은 판정이 아니다).

처리: 값을 날조하지 않고, 같은 표에서 이미 쓰는 '해당 없음' 표기로 통일했다.
  - `<td class="mv-tree-na" title="판정은 그룹 단위로만 산출됩니다(레코드 단위 판정
    없음). 위 그룹 요약 행의 판정을 확인하세요.">·</td>`
  - 이 표기는 같은 행의 '그룹 집계 전용 열(COUNT 등)'이 이미 쓰던 규칙과 동일해서
    새 패턴을 만들지 않았다. 빈 칸이 '값이 누락됐다'로 읽히던 문제만 사라진다.
  - rowspan 병합은 채택하지 않았다: 그룹 행과 레코드 행은 서로 다른 시점에(그룹 펼침
    시점에) DOM 에 삽입되고 페이지 이동마다 레코드 행만 교체되므로, rowspan 을 쓰면
    행 수가 바뀔 때마다 그룹 행의 rowspan 을 다시 계산해야 해 깨지기 쉽다.

5. 항목6 조사 결과 — 헤더 열 수는 가변인가 (확인만, 수정 없음)
════════════════════════════════════════════════════════════════════════
결론: **정상 동작(동적)이다. 별도 결함 아님.**

코드 근거:
  - 헤더는 `gbKeys.map(...)`(=응답 gb_keys) + `valCols.map(...)`(=응답 val_cols)로
    생성된다. 고정 개수 하드코딩이 없다.
  - 서버(services/stats_execute_service.py:476)에서 `val_cols = [c for c in src_cols
    if c not in gb_keys]` — 실제 실행 결과 컬럼에서 도출하므로 선택한 SUM 수를 그대로 따른다.
  - 총 열 수 = 1(그룹/PK 트리) + gb수×2 + val수×2 + 1(판정).
    val수 = COUNT 1개 + 선택 SUM 수.

실측(1) 단위 렌더 하니스 — GROUP BY 1~3 × SUM 1~3 (9조합, node 렌더):
    GB1/SUM1  th 8   GB1/SUM2  th 10   GB1/SUM3  th 12
    GB2/SUM1  th 10  GB2/SUM2  th 12   GB2/SUM3  th 14
    GB3/SUM1  th 12  GB3/SUM2  th 14   GB3/SUM3  th 16
    (모든 조합에서 헤더 th 수 == 본문 td 수, 열 순서 목적→원본 유지)

실측(2) 실 브라우저:
    GB1 · SUM1(FOUND_YEAR)                → 헤더 8열
    GB1 · SUM2(FOUND_YEAR, MAX_CAPACITY)  → 헤더 10열

부수 확인(참고 — 이번 범위 아님):
  GROUP BY 를 2개 이상 고르면 실행이 '다중 세트 경로'(_runExecutePlanSets)로 갈라져
  5단계 하단에 이 그리드 자체가 그려지지 않는다(별도 세트 뷰). 실측: GB2 선택 시
  `table.mtbl` 부재, executeOut 에 다른 표 2개. 이 그리드의 열 수 계산은 정상이며,
  '다중 세트일 때 이 그리드가 안 보인다'는 별개 축이라 이번엔 손대지 않았다.

7. 남긴 것 · 그 이유 (판단 근거)
════════════════════════════════════════════════════════════════════════
요청은 "안내/설명 박스만 제거, 핵심 기능은 절대 건드리지 말 것"이었다. 아래 3가지는
'안내 박스'가 아니라 동작·사실 고지에 해당해 의도적으로 남겼다 — 필요하면 별도 지시로
제거 가능하다.

 (a) 서버의 안전 판정(groupby_execution_safety)과 표시 등급(display_tier_info) '계산'
     → 화면 표기는 전부 지웠지만 계산 자체는 남겼다. 이 값들은 안내용이 아니라
       - 안전 판정: 그룹 수 폭발 시 통계검증 실행을 실제로 '차단'하는 게이트
       - 표시 등급: 실제로 몇 건을 수집·표시할지 정하는 정책값
       이라서, 지우면 안내가 아니라 동작이 바뀐다.

 (b) '실행 실패' 화면의 SQL 증적(_buildExecEvidencePanel)
     → 성공 결과 화면에서는 호출을 제거했다. 다만 통계검증이 실패했을 때 실패한 쪽
       SQL 을 보여주는 오류 패널은 그대로 뒀다. 지우면 실패 원인 추적 수단이 사라진다.
       (이 때문에 함수는 죽은 코드가 아니다 — 오류 경로가 계속 사용한다.)

 (c) 그룹별 '표시 N건 / 실제 M건' 사실 고지
     → '그룹당 표시 상한' 공통 안내 박스는 지웠지만, 각 그룹 상세의 머리말 한 줄
       (예: '목적 단독(과잉) 전체 17건 · 현재 1~5 표시 · 1/4페이지')은 남겼다.
       이걸 지우면 화면이 전체를 보여주는 것처럼 보이게 된다.

 (d) 접힘 안에 있던 사실 고지(허용오차/COUNT 사전검증 실패 등)의 위치 이동 ★확인 요망
     → '⚙ 세부 기준 및 SQL' 접힘을 없애면서, 그 안에 있던 경고/증적 문구
       (noticesFinal)는 삭제하지 않고 결과 컨트롤 위로 옮겼다.
       그 결과 이번 실측 화면에는 'ℹ COUNT 사전검증 실패 — 원본/목적지 건수가
       일치하지 않습니다.' 한 줄이 새로 '보이게' 됐다(전에는 접힘 안에 숨어 있었다).
       숨기면 결과의 유효성 경고가 사라지므로 남기는 쪽을 택했으나, 화면 정리 취지상
       이것도 없애길 원하면 알려주시면 제거하겠다.
