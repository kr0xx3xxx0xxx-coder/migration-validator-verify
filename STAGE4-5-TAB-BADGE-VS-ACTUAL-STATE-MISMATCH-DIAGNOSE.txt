작업명 : STAGE4-5-TAB-BADGE-VS-ACTUAL-STATE-MISMATCH-DIAGNOSE
일자   : 2026-08-01
성격   : 진단 전용(코드 수정 없음) · 읽기 전용 조사
결론   : 표시 버그가 아니라 "낡은 1차 실행 결과를 최신 결과처럼 계속 보여주는" 정합성 문제다.
         탭 배지(재검증 필요/대기중(잠금))는 오히려 내부 상태를 정확히 반영하고 있고,
         틀린 쪽은 "지워지지 않고 남아 있는 5단계 결과 화면"이다.

────────────────────────────────────────────────────────────────────────────
1. 무엇을 조사했나
────────────────────────────────────────────────────────────────────────────
사용자 관측 화면에서 세 표시가 서로 다른 상태를 가리켰다.
  ① 4단계 탭 배지 "재검증 필요", 5단계 탭 배지 "대기중(잠금)"
  ② 그런데 사용자는 5단계 탭(파란 활성)에 있고, 화면에는 COUNT 50,000,000/49,500,000,
     재이관 대상 11건, 최종상태 "불일치" 같은 완성된 5단계 결과가 전부 렌더돼 있음
  ③ 상단 "현재 단계" 안내는 4단계 문구

재현 경로(사용자 확인): 1~5단계를 끝까지 정상 완주 → 3단계로 복귀 → 후보 컬럼 선택은
전혀 바꾸지 않음 → 4단계로 진행. 즉 "내용 변경이 없었는데도" 재검증/잠금이 발동했다.

3. 조사 항목별 답
────────────────────────────────────────────────────────────────────────────
[항목 1] 탭 배지를 그리는 곳과 판정 조건
  ui/tabler_renderer.py:6242~6322 _renderSingleStepNav 의 steps.map 이 단일 출처다. 순서는
    · 6274  선행조건 미충족(accessible=false)      → status=locked, badge='잠김'
    · 6275~6281  BLOCKED/ERROR/RUNNING/SUCCESS/STALE/그 외 → 차단·오류·진행중·완료·재실행 필요·대기
                 (배지 '현재'는 "사용자가 실제 보고 있는 탭"(active)일 때만 붙는다)
    · 6295~6310  5단계 전용 보정. 재이관 상태 반영, 그리고 !accessible 이면 '대기중(잠금)'
    · 6315  최종 오버라이드 — "한때 완료했는데 지금은 유효하지 않은" 단계(_invalidated0)만
            '재검증 필요'(amber)로 덮어쓴다. 단 보고 있는 탭(active)은 이 오버라이드에서 제외된다.
  각 단계의 상태값은 6242 위쪽 _mvComputeWfStates(5973~6001)가 "진짜 결과 플래그"에서 계산한다.
    query=_singleSqlAnalyzed / count=_singleCountDone() / candidate=_analyzeData._candidateComputed /
    execute·result=_singleValidationExecuted
  접근 가능 여부는 공통 게이트 ui/js_stage_gate.py:52~58 prereqOk = "선행 단계가 SUCCESS 인가"다.

  → 그래서 관측 화면의 조합은 정확히 이렇게 만들어진다.
     후보 완료 플래그가 꺼지면 candidate=PENDING → execute/result 도 PENDING →
     4단계는 "한때 완료했는데 지금 무효" = 재검증 필요, 5단계는 선행 미충족 = 대기중(잠금),
     그런데 5단계가 "보고 있는 탭"이라 재검증 필요 오버라이드에서 제외돼 '대기중(잠금)'이 남는다.

[항목 2] 3단계 재방문 시 무엇이 4/5단계를 무효화하나 — 값 비교인가, 방문 사실인가
  값 비교가 아니라 "터치했다는 사실"이다. 두 경로 모두 diff 비교가 없다.
   (a) 3단계 주 버튼 '▶ 선택 적용 후 통계검증 진행'(runRevalidateFromCandidate, 16083~)
       16165에서 조건 없이 _singleInvalidateDownstream('candidate') 를 호출한다. 이 함수는
       6177~6187에서 validationSqlGenerated=false, _singleValidationExecuted=false 로 내린다.
       선택값(gb/sum/period)을 이전 값과 비교하는 코드는 이 경로 어디에도 없다. 실제로 이 함수는
       재렌더 전에 사용자 선택을 스냅샷했다가 그대로 복원까지 하므로(16154·16183~16213),
       "선택이 같다"는 사실을 알 수 있는 위치에 있으면서도 그 비교를 하지 않는다.
   (b) 후보 체크박스 onchange(checkLimit, 23818~23849)
       23846~23848에서 _analyzeData._candidateComputed=false 로 내린다. 여기도 "값이 실제로
       달라졌는지"를 보지 않는다. 같은 컬럼을 껐다 켜서 최종 상태가 동일해도 무효화된다.
  의도인가 실수인가 — 절반씩이다. "선택을 건드렸으면 재확정 버튼을 눌러야 다음 단계로 간다"는
  보수적 게이트는 주석(23841~23845)에 명시된 의도다. 그러나 (a)의 재검증 버튼까지 무조건
  무효화하는 것은 과하다. 사용자가 아무것도 바꾸지 않고 재검증만 눌러도 4·5단계를 통째로
  다시 실행해야 하고, 5,000만행 규모에서는 그 재실행이 수십 초~분 단위 비용이다.
  값 비교(이미 존재하는 _genSelSnapshot 과 같은 스냅샷)를 붙일 자리는 있는데 쓰지 않고 있다.

[항목 3] "잠금인데 조회는 허용"이 정상 설계인가
  아니다. 설계 의도는 "잠긴 단계는 조회도 불가"다. 근거가 세 곳에서 일관된다.
    · showSingleStep(6135) : 접근 불가면 이동 거부 + "🔒 선행 단계를 먼저 완료하세요"
    · _mvNavClick(6100~6114): 이동 불가면 사유 안내만 하고 이동하지 않음
    · _renderSingleStepNav(6234~6241): 보고 있는 탭이 접근 불가면 현재 단계로 되돌린다(스냅백)
  하니스 S6/S7-⑥에서 실제로 잠긴 5단계 탭을 클릭하면 차단된다("🔒 변경으로 재검증이 필요한
  단계입니다"). 즉 새로 들어갈 수는 없다. 그런데 이미 들어와 있으면 나가지지도 않는다.
  이유는 6236의 예외 한 줄이다.
      if (!_fullRunResultActive) { …스냅백… }
  _fullRunResultActive 는 5단계 [결과 확인] 버튼(_mvExecShowResult, 26910)이 true 로 세운다.
  그리고 이 플래그를 false 로 되돌리는 지점은 전수 확인 결과 6곳뿐인데(15187 새 작업 세션 전체
  리셋 / 20052 원클릭 전체검증 차단 / 20275·20311 재이관 prepare HOLD·결과 확인 전 / 27031
  상세비교 처음부터 다시 실행 / 29308 새로고침 복원 중단), 후보 무효화·3단계 재검증·4단계 SQL
  재생성 어디에도 없다. 그래서 한 번 결과 확인에 들어가면 이후 무효화가 일어나도 5단계 화면에
  그대로 머문다. 결함이며, 게이트 정책과 예외 플래그의 수명이 어긋난 것이 원인이다.

[항목 4] ★ 화면의 결과는 최신인가, 낡은 것인가 — stale 이 맞다
  낡은 1차 실행 결과다. 두 갈래 근거가 일치한다.
   (1) 코드: _singleInvalidateDownstream(6191~6205)이 비우는 DOM 은 7개뿐이다.
         countOut, colSelectOut, unifiedColOut, gbEstGroupCount, sqlOut, executeOut, singleResultSummary
       반면 5단계 결과 카드(execResultCard, tabler_renderer.py:2888~) 안의 표시 영역은 11개이며,
       아래 9개는 지워지지 않는다.
         mvStage5CtxGrid(COUNT 전체값·불일치 그룹·재이관 대상), singleMismatchItems(불일치 항목 요약),
         mvDiagCommonStrategy, singleGroupRegisterArea, singleGroupLoadError, singleGroupPolicyHint,
         singleFinalSaveMsg, singleFinalSaveHint, fullValidationArea
       execResultCard 자체의 display 도 none 으로 되돌리지 않는다.
       더 나쁜 경우가 (b) 체크박스 경로다. 이 경로는 _singleInvalidateDownstream 을 아예 호출하지
       않으므로 결과 카드가 "한 글자도" 지워지지 않는다. 1차 결과 전체가 그대로 남는다.
   (2) 실제 렌더: 브라우저 재현 ②에서 무효화 후에도 5단계 요약 그리드가 1차 값을 그대로 표시했다.
         "50,000,000 / 49,500,000 · 차이 +500,000 · 불일치 그룹 11개 · 재이관 대상 11건 · 불일치"
       (스크린샷 03/03b)
  위험도 재분류: 단순 표시 버그가 아니라 정합성 문제로 봐야 한다. 사용자가 그 화면에서 얻는
  숫자(COUNT 차이, 불일치 그룹 수, 재이관 대상 건수)는 "지금 기준"이 아니라 "이전 실행 기준"인데,
  그 사실을 알려주는 표시는 결과 카드에서 멀리 떨어진 상단 탭 배지뿐이다. 결과 카드 안에는
  "이 결과는 낡았다"는 문구가 전혀 없다. 3단계 재검증 경로에서는 상세표(executeOut)와 실행 기준
  (singleResultSummary)만 지워지고 요약 그리드는 남으므로, 화면이 "결과 일부"처럼 보이면서
  남은 수치를 최신으로 오인할 여지가 오히려 더 크다.

[항목 5] 상단 "현재 단계" 문구가 화면과 안 맞는 이유
  "현재 단계"를 표시하는 곳이 두 군데인데 서로 다른 값을 본다.
    · 상단 안내(mvStepHint) : 6324 _mvSetStepHintOwned(…, _MV_SINGLE_HINT[wfCurrent])
        → 워크플로가 판단한 "다음에 해야 할 단계"(MvStageGate.currentStage)
    · 하단 커맨드바         : 6506 var stage = _singleViewStep
        → 사용자가 "보고 있는 탭"
  정상 흐름에서는 둘이 같지만, 무효화가 일어나면 갈라진다. 재현 ②의 실제 화면에서
  상단은 "현재 단계: 후보 컬럼 선정", 하단은 "현재 단계: 결과 확인"이 동시에 떠 있다(스크린샷 03).
  사용자가 본 "4단계 문구"는 같은 원인의 다른 변형이다. 3단계 재검증 버튼을 눌러 후보가 다시
  확정되면 candidate=SUCCESS, execute=PENDING 이 되어 wfCurrent 가 execute 로 잡히고, 상단 문구가
  "현재 단계: 통계검증 실행 · 통계검증 SQL을 생성하고 실행하세요"가 된다(하니스 S1·S4·S7-③에서 확인).
  즉 상단 문구는 "화면"이 아니라 "워크플로 진행도"를 말하고 있고, 그 사실이 문구에 드러나 있지 않다.

[항목 6] 다중 세트(GROUP BY 2축↑) 한정 현상인가
  아니다. GROUP BY 축 개수와 무관하다. 판정에 관여하는 네 요소(_mvComputeWfStates,
  _singleInvalidateDownstream, checkLimit, _fullRunResultActive) 어디에도 축 개수·plan sets
  분기가 없다. 실행 완료 시 세우는 플래그도 단일 세트(runExecute 28451~28453)와 다중 세트
  (_runExecutePlanSets 26148)가 동일하다. 오늘 확인된 다른 결함들이 다중 세트 한정이었던 것과
  달리, 이 건은 1축 경로에서도 같은 조건이면 그대로 재현된다.

  다만 조사 중 다중 세트 쪽에서 별개의 비대칭을 하나 발견했다(이번 증상과는 다른 건).
    26148 : executionDone=true; _singleValidationExecuted=true; 를 agg.success 판정보다 먼저,
            조건 없이 실행한다. 단일 세트 경로는 r.success===false 면 플래그를 세우지 않고
            return 한다(28442~28448). 결과적으로 다중 세트에서 일부 세트가 실패해도 4단계가
            '완료'로 표시되고 5단계 접근이 열린다. 같은 계열(표시 vs 실제)의 문제라 기록해 둔다.

[추가 요구 4] 재실행이 끝나면 결과가 실제로 갱신되는가
  갱신된다. 재실행 성공 경로가 _mvRenderValidationDetail(16231~)을 호출하고, 그 안에서
  mvStage5CtxGrid(16259)·singleResultSummary(16255)·singleMismatchItems(16272)·executeOut(16277~)이
  모두 다시 그려진다. mvDiagCommonStrategy 는 _renderSingleResultSummary(16447)가 비운다.
  브라우저 재현 ③에서 재실행 완료 직후 요약 그리드가 2차 값으로 바뀌는 것을 확인했다.
    무효화 직후 : 50,000,000 / 49,500,000 · 차이 +500,000 · 불일치 11개 · 재이관 11건
    재실행 완료 : 50,000,000 / 49,999,000 · 차이 +1,000   · 불일치 2개  · 재이관 2건   (스크린샷 05)
  따라서 stale 노출 구간은 "무효화 시점 ~ 재실행 완료 시점"으로 한정된다. 문제는 그 구간이
  5,000만행 규모에서 수십 초~수 분이고, 그 사이 화면은 완성된 결과처럼 보인다는 점이다.

5. 결론과 권고(진단 범위 — 이번 회차 수정 없음)
────────────────────────────────────────────────────────────────────────────
결론. 탭 배지는 거짓말을 하고 있지 않다. 4단계 "재검증 필요", 5단계 "대기중(잠금)"은 내부 상태를
정확히 반영한다. 어긋난 것은 (ㄱ) 잠긴 단계에 머물게 놔두는 예외 플래그, (ㄴ) 무효화 시 지워지지
않는 5단계 결과 표시, (ㄷ) "현재 단계"라는 같은 이름으로 서로 다른 값을 말하는 두 표시다.
셋 중 실질 위험은 (ㄴ)이다. 낡은 검증 결과를 최신으로 오인하게 만들 수 있다.

권고(구현은 별도 작업으로):
  1) 무효화 시 5단계 결과 표시를 한 곳에서 함께 정리한다. _singleInvalidateDownstream 의 clear
     목록에 결과 카드 host 를 추가하거나, execResultCard 를 통째로 감추는 편이 낫다. 새 상태를
     만들 필요 없이 기존 함수의 대상 목록만 맞추는 일이다. 지우는 대신 "이 결과는 이전 실행
     기준입니다" 배너를 결과 카드 안에 띄우는 것도 대안이며, 이쪽이 사용자가 이전 결과를 참고할
     여지를 남긴다. 둘 중 하나는 반드시 필요하다.
  2) checkLimit 경로가 무효화 함수를 우회하는 비대칭을 없앤다. 지금은 체크박스만 건드리면
     "상태는 무효, 화면은 전부 유효"라는 최악 조합이 나온다.
  3) _fullRunResultActive 의 수명을 무효화와 묶는다. 후보/실행 결과가 무효화되면 이 예외도 함께
     해제해야 스냅백 정책(잠긴 단계에 머무르지 않는다)이 일관된다.
  4) 3단계 재검증 버튼에 선택값 diff 비교를 붙여, 변경이 없으면 4/5단계를 무효화하지 않도록 한다.
     대규모 테이블에서 불필요한 재실행 비용을 없애는 효과가 가장 크다. 판단 근거로 쓸 스냅샷
     (_genSelSnapshot 계열)은 이미 존재한다.
  5) 상단 안내 문구를 "현재 단계"가 아니라 "다음에 할 일"로 바꾸거나, 보고 있는 탭과 다를 때
     그 사실을 문구에 드러낸다. 하단 커맨드바와 같은 이름으로 다른 값을 말하는 상태를 없앤다.
  6) (별건) 다중 세트 실행 완료 처리 26148 의 무조건 플래그 설정을 단일 세트와 대칭으로 맞춘다.
