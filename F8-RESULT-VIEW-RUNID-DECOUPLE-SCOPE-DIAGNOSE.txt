1. 선결 3건 정리(RESULT-VIEW-RUNID-DECOUPLE-FEASIBILITY-DIAGNOSE.txt §6 원문 기준)
────────────────────────────────────────────────────────────────────────────
job_registry 의 single DTO 는 재이관(exact_diff) run_id 를 id 로 쓰는데, 통계검증 결과는
전혀 다른 run_id 체계(single_validation_snapshot 키)로 저장된다. 현황판이 쥔 id 로는
검증 결과를 못 찾는다는 것이 F8 전체의 뿌리이고, 그 위에 3개의 선결 조건이 있었다.

 (i) job DTO 가 검증 run_id/result_id 를 확보할 경로
     - 왜 전제조건인가: 이게 없으면 현황판 job 카드에 '결과 보기'를 달아도 어떤 결과를
       열어야 할지 서버가 모른다. 요약이든 그룹표든 이 링크가 0순위.
     - 원문 우려: 원천(reimport_job)이 값을 안 갖고 있으면 reimport_job 수정이 필요한데,
       이는 job_registry 의 "저장소 모듈 무수정" 원칙과 충돌한다.

 (ii) 완료 job 목록 API 신설
     - 왜 전제조건인가: 당시 GET /jobs/active 는 **활성** job 만 반환했다. "완료 job 클릭
       → 결과 보기"를 만들려면 클릭할 대상이 화면에 있어야 하는데, 목록 자체가 없었다.

 (iii) snapshot whitelist 확장(column_comment / null_value_transform_evidence)
     - 왜 전제조건인가: 그룹표 렌더(renderExecute)의 '값 변환 감지·확인 필요' 강등 판정이
       이 두 필드에만 의존하는데 snapshot 저장 whitelist 에 없었다. 이대로 그룹표를 열면
       **같은 run 이 마법사에서는 '값 변환 감지', 현황판에서는 '일치'로 표시**되는
       화면 간 판정 표기 불일치가 발생한다 — 그룹표 분리 자체를 막는 사유로 명시돼 있었다.

4. F8·F9·F10 의존관계
────────────────────────────────────────────────────────────────────────────
셋 다 "job_registry DTO 가 job 의 실행 식별자만 알고, 그 job 이 만든 검증 결과의
식별자는 모른다"는 같은 설계 한계에서 갈라져 나왔다. 다만 **원천이 다르다** —
같은 필드를 서로 다른 3곳(single/batch/stats)에 각각 채워야 하므로 코드 충돌은 없지만,
"DTO extra 에 무슨 이름으로 결과 링크를 넣을지"의 **네이밍 관례**는 먼저 정해진 쪽을
따라야 재작업이 없다.

  F9(개별검증 job ↔ 검증 run_id) — B안 확정·승인 대기. F8 선결 (i)의 해결책 그 자체다.
    F8 이 "선결 3건" 이라 부른 것 중 마지막 남은 한 건이 F9 다. F9 를 반영하면 F8 의
    선결 3건이 전부 닫힌다. → **F9 를 F8 보다 먼저(또는 동시에) 착수해야 순서가 맞는다.**
    F9 보고서 자신도 "완료 job 목록 API·snapshot whitelist 확장 등 나머지 선결 3건과
    독립"이라고 명시했다 — 즉 F9 는 이미 오늘 순서와 무관하게 단독 착수 가능.
    덤 효과: 반영 시 routes/single_restore_route.py:155(_enrich_from_result_store 를
    재이관 run_id 로 호출하는 죽은 코드, 실측 재확인 — 오늘도 동일하게 남아 있음)가
    처음으로 실제 동작하게 된다.

  F10(일괄검증 job id ↔ wrapper 결과) — F8·F9 와 **독립된 별도 트랙**이다. 원천이
    batch_execution_state/batch_wrapper_result_store 로 완전히 다르고, 문제 구조도 다르다
    (F8/F9: id 체계 자체가 다름 / F10: id 체계는 파생 관계이나 **1:N 오배정** — 같은
    batch_run_id 에 완료 exec 2건 이상이면 최신 회차로 뭉개져 32.4% 가 다른 회차 결과를
    보여준다, 실측). F10 은 아직 해결책조차 미확정(가/나/다 3안 문서화 우선 상태)이고,
    이번 재조사에서도 batch_execution_state_service.py 에 결과회차 FK 컬럼이나
    job_registry DTO 에 project_id 필드 어느 쪽도 추가된 적이 없음을 재확인했다.
    F8·F9 작업과 파일이 겹치지 않으므로 **병행 착수해도 서로 다시 만들지 않는다.**
    단, DTO extra 필드 네이밍(validation_run_id/result_ids 같은 패턴)을 F9 가 먼저
    확정하면 F10 쪽 필드명(예: result_round_id)도 그 관례를 따르는 게 일관적이다.

  권장 순서: F9(승인만 있으면 즉시, 9줄) → F8 요약 전용 1차(F9 반영 후 이어서) →
    F10(별도 트랙, 언제 시작해도 무방하나 결손1 해소 방향 결정 선행 필요) →
    F8 그룹표 확장(B4 설계 결정 이후).
