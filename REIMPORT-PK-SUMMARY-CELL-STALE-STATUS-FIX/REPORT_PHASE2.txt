1. 왜 2차가 필요했나
────────────────────────────────────────────────────────────────────────
1차(3dfafaa)는 ui/tabler_renderer.py 의 _mvUpdatePkSummaryCell 을 고쳐 요약 셀
(#mvPkSummaryCell)과 그 함수가 함께 갱신하는 #execPkTotal 의 고착을 해소했다.
그러나 #execPkTotal 을 쓰는 코드는 하나가 아니었다.

ui/execute_result_renderer.py 의 _execSrvGo(p) 는 /stats-result/page 응답을 받아
결과표 상단 요약 줄(#execSrvLine)을 innerHTML 로 통째로 다시 그린다. 그 문자열 안에
<span id="execPkTotal"> 이 매번 새로 만들어지고, 그 자리에서 조건이 이렇게 걸려 있었다.

    if (_pk && _pk.status === 'READY') pkTot = _pk.total_reimport_pks;   // 그 외 전부 '준비 중'

즉 1차가 고친 것과 같은 결함(READY 만 인정 · 폴링으로 오는 확정 상태를 못 봄)이 다른 파일에
한 벌 더 남아 있었고, 이쪽은 재렌더할 때마다 갱신된 값을 도로 덮는 성질까지 있었다.
작업 지시서가 지목한 execute_result_renderer.py:240 이 정확히 이 지점이다.

2. 실측으로 확인한 실제 증상 (BEFORE)
────────────────────────────────────────────────────────────────────────
· C3(EARLY_STOPPED · 저장 101건) — 같은 화면 안에서 두 값이 서로 모순됐다.
    요약표 셀     : "101건 이상 / 조기중단 · 표시(저장)분 기준 하한"
    상단 요약 줄  : "재이관 대상 준비 중"
· C4(정상 READY · 저장 50건) — 조기중단이 아닌 정상 완료도 상단 요약만 '준비 중' 이었다.
  1차 보고서는 이 경로를 측정하지 않아 정상 READY 도 고착이라는 사실이 드러나지 않았었다.
· ③(페이지 재이동) — 값이 한 번 제대로 들어가도 재렌더에서 다시 '준비 중' 으로 덮였다.

3. 수정 내용 (ui/execute_result_renderer.py 1파일)
────────────────────────────────────────────────────────────────────────
판정 로직을 이쪽에 복제하지 않았다. 두 작성자가 각자 판정해서 갈라진 것이 이 결함의 원인
그 자체이므로, 복제는 같은 사고를 세 번째로 만들 뿐이다.

  · _execSrvGo 는 자리표시자 <span id="execPkTotal">준비 중</span> 만 그린다.
  · 그 span 이 DOM 에 붙은 직후 단일 출처인 _mvUpdatePkSummaryCell 에 갱신을 위임한다.
    try { if (typeof _mvUpdatePkSummaryCell === 'function') _mvUpdatePkSummaryCell(); } catch(e){}
  · 이 형태는 새로 만든 관용구가 아니다 — ui/grid_helpers.py 가 같은 요약표를 그린 직후
    쓰는 호출 형태와 동일하다(typeof 가드 포함).

결과적으로 어휘는 P10 이 정립한 '건 이상' 과 '표시(저장)분 기준 하한'(title)을 그대로 따르게
되어, 셀과 상단 요약이 같은 문구를 쓴다. 이번 작업에서 새 용어를 만들지 않았다.

4. 실측 방법 (1차 하니스로는 이 결함을 잡을 수 없었던 이유 포함)
────────────────────────────────────────────────────────────────────────
1차 하니스(reimport_pk_summary_cell_stale_status_verify.py)는 #execSrvLine 을 하니스가
직접 만들어 두고 _mvUpdatePkSummaryCell 의 갱신만 관찰했다. 제품 함수 _execSrvGo 를 한 번도
호출하지 않았기 때문에 '두 번째 작성자'가 측정 범위 밖이었다.

2차 하니스(scripts/dev_e2e/reimport_pk_exec_srvline_stale_verify.py)는 그 함수를 실제로 부른다.
  · /agg-diff/pk-records — 실 라우트에서 실제 payload 수신(P10 픽스처 run 재사용)
  · _mvRiApplyProgress(d) — 제품 폴링 콜백을 그 payload 로 직접 호출(폴링 타이머만 생략)
  · _mvRenderResultGrid(...) — 제품 요약표 렌더(#mvPkSummaryCell 생성)
  · _execSrvGo(1) — 이번 수정 대상. /stats-result/page 실 라우트를 실제로 호출한다.

_execSrvGo 는 저장된 통계검증 결과가 없으면 d.ok === false 로 즉시 return 해 아무 것도 그리지
않는다. services/stats_result_store 는 프로세스 in-memory 라 외부 스크립트로는 서버 메모리에
넣을 수 없으므로, 기동 스크립트(scripts/dev_e2e/_f17_srvline_server.py)가 같은 프로세스에서
실제 저장 API(save_result)를 호출해 결과 1건을 심고 uvicorn 을 띄운다.
라우트·저장소·클라이언트 함수는 모두 제품 코드 그대로이고, 심은 것은 데이터뿐이다.
BEFORE 는 baseline worktree(ef440ee) 서버 8211, AFTER 는 수정 트리 서버 8210 — 별도 프로세스.
