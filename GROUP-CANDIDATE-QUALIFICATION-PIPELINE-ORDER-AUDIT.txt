✅ 작업 완료 - GROUP BY 후보 판정 파이프라인 순서와 고카디널리티 배제 기준값 특정(코드 수정 없음, 진단만)

────────────────────────────────────────────────────────────────────────
[1] GROUP BY 후보가 거치는 단계 (순서대로)
────────────────────────────────────────────────────────────────────────

■ 1차 결정 — ANALYZE 시점 (services/candidate_engine.py, build_column_candidates)
  후보 풀 자체가 여기서 만들어진다. 입력은 '카탈로그 통계(n_distinct) + semantic 사전'뿐(샘플 없음).

  · Step2 (metadata 경로): 컬럼 타입별 분기
      - PK/UNIQUE            → 후보 미생성(식별자)
      - NUMBER(숫자형)        → SUM 전용 분기(GROUP BY 후보 미생성)
      - DATE/TIMESTAMP        → date_bucket 경로(별건 — 이번 감사 범위 밖)
      - 그 외 + n_distinct ∈ [2,50] & not pk/unique → GROUP BY 후보 생성(auto 가능)  [candidate_engine.py:643-648]
      - 그 외 + n_distinct > 50            → GROUP BY 후보 '미생성'. 참고/제외표에만 사유 표기
        (_gb_noncandidate_reason → HIGH_CARDINALITY / FREE_TEXT)                    [candidate_engine.py:1070-1078]
  · Step3 (semantic 사전 경로): DIMENSION_* 매칭 컬럼 → GROUP BY 후보 생성.
      단 통계가 constant/high/very_high 면 auto_selected=False(관찰만)로 강등.        [candidate_engine.py:728-736]

■ 2단계 — COUNT 비교(게이트). postcount 진입 전제.

■ 3차 확정 — POSTCOUNT (services/candidate_postcount_finalize.py, finalize_recommendation_postcount)
  실제 '최종 후보 확정'은 여기서 일어난다. 순서:
    ① _run_bounded_sample        : 5만행 제한 샘플 profile(카탈로그 distinct 근거 없는 '최종 후보 컬럼'만).  [:614, _SAMPLE_LIMIT=50_000]
    ② _inject_profile_evidence   : row_count + 샘플 distinct 를 profile_evidence 로 주입 + analyze 임시선택 초기화. [:625-628]
    ②-b resolve_candidate_sample_values : 값 샘플 LIMIT 100 수집(값패턴·날짜·SYSTEM_AUDIT 게이트 입력용).      [:638-650, LIMIT 100]
    ③ enrich_candidates_for_display     : 점수·자동추천(top-N) 재산정. _gb_identifier_excluded 로 식별자성/고카디 auto 차단. [:659-669]
    ④ attach_evidence_contracts         : evidence_contract 재부착(distinct_ratio 등, row_count 결합).           [:677-687]
    ⑤ apply_recommendation_gates        : demote-only '하드 배제/강등' 게이트(고유값비율 과도 → EXCLUDED_BY_RULE 등). [:695-696]
    ⑥ date_bucket enrich + promote      : 날짜형 후보 처리(범위 밖).                                            [:707-742]
    ⑦ evidence guard + 대체 기본추천     : 근거부족 강등 + fallback 승격 + 상태계약 통일.                        [:724-]

  요약: 샘플링(①/②-b) → 카디널리티 판정(③ 점수·auto게이트) → 값패턴 판정(②-b 샘플로 ③에서) →
        계약화(④) → 최종 후보 확정·하드 배제(⑤) 순.

────────────────────────────────────────────────────────────────────────
[2] 고카디널리티(수만~수십만 그룹) '일반(날짜 아닌)' 컬럼의 배제 여부 + 기준값
────────────────────────────────────────────────────────────────────────

배제는 '두 단계'로 나뉘며, 각각 기준이 다르다.

(A) 자동추천에서 배제(auto_selected=False) — 후보 풀엔 남고 '수동 선택'은 가능
    · 카디널리티 등급(services/candidate_engine.py:1114-1150):
        LOW ≤ 50 / MEDIUM ≤ 200 / HIGH ≤ 1000 / very_high > 1000
        auto 허용 등급 = {low, medium, unknown}  → high/very_high(즉 n_distinct > 200)은 auto 제외
    · risk_flag HIGH_CARDINALITY: resolved_distinct > 100 이면 부여(services/db_statistics_service.py:692-694).
      enricher 의 _gb_identifier_excluded 가 risk_flags ∩ {HIGH_CARDINALITY, UNIQUE_LIKE, IDENTIFIER_LIKE}
      이면 True → 자동추천 차단(services/candidate_display_enricher.py:989-999, _GB_RESCUE_HARD_RISK:282).
    · metadata 진입 캡: 애초에 metadata 경로는 n_distinct ∈ [2,50] 만 GROUP BY 후보로 생성(위 [1] Step2).

(B) 완전 배제(EXCLUDED_BY_RULE) — '선택가능'에서도 제거, 수동 선택도 불가
    · 기준: distinct_ratio(고유값 비율 = 고유값수/행수) ≥ 0.9
      → "고유값 비율 과도(사실상 식별자)"로 EXCLUDED_BY_RULE
      상수: GB_IDENTIFIER_DISTINCT_RATIO = 0.9 (services/candidate_recommendation_policy.py:32, 게이트 :74-77)
    · PK/UNIQUE True 확인 시에도 EXCLUDED.
    · UNIQUE_LIKE risk_flag 도 동일 0.9 비율 기준(_UNIQUE_LIKE_RATIO_THRESHOLD=0.9 /
      PG 비율표기 _DISTINCT_UNIQUE_THRESHOLD=-0.9, services/db_statistics_service.py:64,702-708).

★ 핵심 결론(감사 답):
    - 완전 배제(EXCLUDED_BY_RULE)는 '비율(distinct_ratio ≥ 0.9)' 기준이지 '절대 그룹 개수' 기준이 아니다.
    - 따라서 그룹이 수만~수십만 개라도, 전체 행수가 그보다 충분히 크면(비율 < 0.9) 완전 배제되지 않는다.
      이 경우 자동추천은 막히지만(HIGH_CARDINALITY) '선택가능(SELECTABLE)'으로 남아 수동 선택이 가능하다.
    - 일반 컬럼에 대해 '그룹 개수가 절대적으로 너무 많다'는 이유만으로 배제하는 '절대 그룹수 상한'은 없다.
      (절대 상한이 존재하는 곳은 date_bucket 경로뿐 — DATE_BUCKET_MAX_GROUPS=60, 이번 범위 밖.)
    - 단, metadata 경로 컬럼은 진입 게이트(n_distinct ≤ 50)에서 이미 걸러져 '후보로 아예 안 뜨는' 형태의
      배제가 일어난다(참고/제외표에 HIGH_CARDINALITY/FREE_TEXT 사유로만 표기). 즉 metadata 고카디 텍스트는
      '후보 미생성', semantic DIMENSION 고카디는 '후보 O·자동추천 X·(비율≥0.9면)EXCLUDED' 로 경로가 갈린다.

실증(직전 FALLBACK 작업 MV_ORA_XDIFF 실측):
    - C_TS3 : 고유값 86,400 / 250,000행 = 비율 0.345 → HIGH_CARDINALITY(auto 차단) BUT 비율 < 0.9
              → EXCLUDED 아님 → AVAILABLE_ADDITIONAL(선택가능). "수만 그룹인데도 완전 배제 안 됨"의 실례.
    - C_TS/C_TS6 : 고유값 ≈ 100%(비율 ≥ 0.9) → UNIQUE_LIKE + distinct_ratio 게이트 → EXCLUDED_BY_RULE.
    두 대조가 "배제 기준이 절대 그룹수가 아니라 고유값 '비율' 0.9"임을 그대로 보여준다.
