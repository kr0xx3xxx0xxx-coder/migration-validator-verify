0. 결론 요약 (먼저 읽는 부분)
================================================================================

전체 43칸(1단계 9 + 2단계 8 + 3단계 9 + 4단계 8 + 5단계 9) 중
  - 테이블명(목적/원본) 10칸  : 사용자가 "겹쳐도 된다"고 명시한 공통 축 → 그대로 유지
  - 나머지 33칸 중 **진짜 중복(순수 재출력) 7칸 + 정보량 0 인 칸 1칸 = 8칸** 확인

진짜 중복 7칸 (b 분류)
  ① 4단계 '목적그룹'     ← 3단계 '목적그룹' 과 동일 값
  ② 4단계 '원본그룹'     ← 3단계 '원본그룹' 과 동일 값
  ③ 4단계 '목적집계'     ← 3단계 '목적집계' 과 동일 값
  ④ 4단계 '원본집계'     ← 3단계 '원본집계' 과 동일 값
  ⑤ 4단계 '처리시간'     ← 실행 완료 후 5단계 '처리시간' 과 **완전 동일 값**
                            (tabler_renderer.py:16448·16454 — 같은 r.processing_ms, 같은 라벨을
                             4단계·5단계에 동시 기록한다)
  ⑥ 5단계 '통계검증규모' ← 3단계 '통계검증규모' 와 같은 API·같은 필드(provisional_grade)
  ⑦ 1단계 '컬럼매핑수'   ← 같은 탭 안의 '입력컬럼수'·'추출컬럼수' 를 'n/m' 으로 다시 쓴 값

정보량 0 인 칸 1칸
  ⑧ 4단계 '상태' — 값이 항상 'READY / SQL 생성됨' 하나뿐 (생성 전은 '—')
     ※ 2단계 '검증항목'(항상 'COUNT')이 같은 사유로 이미 제거된 선례가 있다.

가장 심각한 곳은 **4단계**다. 8칸 중 테이블명 2 + 중복 5 + 무정보 1 = 8칸 전부가 4단계
고유 정보가 아니다(실행 전 한정으로 '처리시간'이 SQL 생성 시간이라 잠깐 고유할 뿐,
실행이 끝나면 그것마저 5단계와 같아진다). 즉 4단계 타일은 현재 "3단계 선택 + 5단계 시간의 사본"이다.

한 줄 처방:
  4단계 → 그룹/집계 4칸은 **그대로 두고**(정정 지침), 처리시간을 'SQL생성시간'과
          '실행시간(원본/목적 2행)'으로 분리하고, '상태' 자리에 4단계에만 있는 사실
          (조합검증 ON/OFF · SQL 경고 등)을 넣는다.
  5단계 → '통계검증규모' 를 빼거나 '실행 시점 재산정값' 으로 의미를 바꾼다(현재는 순수 재출력이며,
          §5 처럼 3단계 값보다 오래된 값일 수 있는 구조적 문제까지 있다).
  1단계 → '컬럼매핑수' 를 빼고 '매핑불명확 컬럼수' 같은 실제 판단값으로 대체한다.

2. 각 탭의 고유 목적 재정의 (코드/화면 흐름 확인 후 다듬은 것)
================================================================================

1단계  "이 SQL을 검증할 수 있는가, 무엇이 무엇으로 매핑되는가?"
       → 답해야 할 것: 파싱 성공 여부, 매핑 가능/불가 컬럼, 검증을 막는 요소(WHERE/JOIN 복잡도)

2단계  "원본과 목적지의 전체 건수가 얼마나 다른가, 그 비교에 얼마가 드는가?"
       → COUNT 는 이 탭이 유일한 원산지다(5단계는 인용자)

3단계  "무엇으로 비교할지 어떻게 고를 것인가, 그 선택의 대가는 얼마인가?"
       → '통계검증규모' 가 이 탭에 있는 이유는 "선택을 바꾸면 등급이 즉시 따라오는" 피드백 루프
         (체크박스 변경마다 _mvRenderStrategyPlan 재호출 — tabler_renderer.py:24210)

4단계  "그 선택이 실제로 어떤 SQL·어떤 실행 단위가 되었고, 실행은 어떻게 진행되는가?"
       → 답해야 할 것: 생성된 SQL, 실행 옵션(조합 검증 여부), 생성 시 경고, 실행 진행/소요
       → **답하지 말아야 할 것: 선택 그 자체**(선택은 3단계의 산출물)
       → 단, 이번 정정 지침에 따라 그룹/집계 타일은 현행 유지한다(§7-C)

5단계  "불일치가 있는가, 무엇을 얼마나 재이관해야 하는가?"
       → 규모 '등급'은 이 질문의 답이 아니다(사전 예측값이며 결과가 아님)

판정: 제거하거나 의미를 바꾼다.
  · 권장(단순)   : 5단계에서 삭제. 규모 등급은 '실행 전 계획' 정보이고 5단계 질문의 답이 아니다.
  · 대안(정보보존): '실행규모' 로 라벨을 바꾸고 값을 실행 실측으로 교체

B. 제안 — 4단계 '실행시간' 타일 한 칸에 원본/목적 2행
──────────────────────────────────────────────────────────────────────────────

 적용 대상: **통계검증 실행 시간 단 한 곳**(4단계 실행시간). 다른 단계는 A 표대로 대상 아님.

 형태(2단계 'COUNT 소요' 타일 패턴 그대로 재사용):

     [라벨: 실행시간]
     ┌──────────────┐
     │ 원본 12.30초  │
     │ 목적  8.10초  │
     └──────────────┘

 구현 형태(제안 — 구현은 하지 않음)
  · 컬럼 정의  : _mvStage4Columns() 에 { title:'실행시간', field:'execElapsed', kind:'multi' }
                 — kind:'multi' 는 배열을 <br> 로 잇는 기존 규격이며 'COUNT 소요'와 동일
  · 값 빌더    : _mvCountTileElapsed(c) 와 같은 모양의 _mvStage4ExecElapsed(r) 를 두고
                 r.query_timing.source_duration_ms / target_duration_ms 를 읽어
                 ['원본 12.30초', '목적 8.10초'] 를 만든다. 포맷은 기존 _mvFmtStageDur 재사용
  · 새 계측 0  : 서버는 이미 보내고 있다. **UI 가 읽기만 하면 된다**
  · 미실행/미보유 시 : 다른 미실행 타일과 같이 '—'

 ★ 툴팁 문구는 'COUNT 소요' 것을 그대로 복사하면 안 된다 — 실행 방식이 반대다.
   · COUNT      : 원본/목적 **병렬** → 개별시간의 합이 총시간보다 **클 수** 있다
                  (실측 21,186 + 19,301 vs 총 21,190)
   · 통계검증 실행: 원본/목적 **순차** → 개별시간의 합이 총시간보다 **작다**.
                  차액 = 그룹 비교·직렬화 등 앱 시간
                  (근거: stats_execute_service.py:596 "순차 실행이라 음수 없음",
                   그리고 query_timing.source_target_gap_ms = target 시작 − source 종료)
   권장 툴팁: "원본 12,300ms / 목적지 8,100ms · 총 21,000ms(순차 실행, 차액은 그룹 비교·
              직렬화 등 앱 처리시간) · 원본↔목적 간격 40ms"
   ※ source_target_gap_ms 도 같은 응답에 있으므로 툴팁에 함께 넣을 수 있다(추가 왕복 0).

 부수 효과(중요)
  · §0 의 진짜 중복 ⑤(4단계 처리시간 = 5단계 처리시간)가 이 분리로 해소된다.
    4단계 = 'SQL생성시간' + '실행시간(원본/목적 DB 시간)',
    5단계 = '처리시간(실행 총시간 = DB 시간 + 앱 시간)' 으로 서로 다른 사실이 된다.
  · 지금까지 툴팁으로만 구분되던 '같은 슬롯 두 값'(SQL 생성 시간 → 실행 시간 덮어쓰기)
    문제도 함께 사라진다.

 위험/주의
  · 다중 세트 실행(_runExecutePlanSets, GROUP BY 2축 이상)에서는 /execute 가 세트마다
    호출되므로 query_timing 도 세트마다 온다. 마지막 세트 값만 보이면 오해를 부른다
    → 세트별 합계를 쓰거나, 라벨에 "(마지막 세트)"를 명시해야 한다. 어느 쪽이든
      값 집계 로직이 새로 필요하므로 **단일 세트부터 적용**하는 것을 권장한다.
      (관련 기지 결함: 다중세트 agg 경로에는 processing_ms 자체가 없다)
  · BLOCKED 응답 경로도 query_timing 을 담지만 키가 하나 더 많다(total_elapsed_ms 포함,
    stats_execute_service.py:68-101). source/target duration 키 이름은 동일하므로
    같은 빌더로 읽어도 안전하다.

C. 확인 — 그룹/집계 타일은 이번 통합 검토 대상이 아니다
──────────────────────────────────────────────────────────────────────────────

 목적그룹 / 원본그룹 / 목적집계 / 원본집계 4개 타일은 **현재의 분리된 형태를 그대로 유지**한다.
 한 타일 안에서 원본/목적을 행으로 나누는 통합은 검토하지 않으며, 이번 제안의 변경 대상이
 아니다(3단계·4단계 모두 해당). §3 분류표에 4단계 그룹/집계가 (b) 로 남아 있는 것은 사실
 기록이며, 정정 지침에 따라 §6 권장안에서는 유지 대상으로 처리했다.

8. 위험·주의 (구현 시 참고)
================================================================================

· _mvTilesHtmlFromCols 는 3·4·5단계 공용이다. 값 렌더 규칙(kind:'multi' 등)을 건드리면
  3·5단계까지 함께 바뀐다 — 컬럼 정의(_mvStage4Columns)만 수정할 것.
· 5단계 '통계검증규모' 제거 시 cellId='mvSizeSummaryCell' 이 사라진다.
  _mvUpdateSizeSummaryCell 은 셀이 없으면 조용히 return 하므로 즉시 깨지지는 않으나,
  그 함수 안의 _mvComputeStatsScale 재산정 트리거도 함께 죽는다.
  → window._mvStrategyPlan 은 3단계 목록 규모 셀·일괄검증에서도 쓰므로 트리거를 어디로
    옮길지 먼저 정해야 한다. 단순 삭제로 끝나지 않는 유일한 항목이다.
· 5단계 요약 빌더(_mvTargetSummary*)는 일괄검증 다건 목록과 공유된다. 개별 5단계만 바꾸려면
  _mvStage5Columns 만 수정하고 _mvTargetSummaryView/CellsHtml 은 손대지 말 것.
· 타일은 한 줄에 9칸까지만 들어간다(폭 실측 1256px · minmax(118px,1fr) · gap 10px).
  10칸이 되면 9+1 로 줄이 갈라진다 — 어떤 안이든 9칸을 넘기지 않는다.
  → 4단계 권장안이 정확히 9칸인 이유이며, '조합검증'과 '상태'를 동시에 넣을 수 없다.
· 4단계 실행시간 분리는 '값 읽기 추가'라 SQL/판정 로직에 영향이 없다(표시 전용).
  단 window._mvStage4ProcMs 를 쓰던 기존 슬롯 덮어쓰기 흐름(_mvShowStageProcessingTime(4,…))
  을 어떻게 남길지 함께 정해야 한다 — 라벨 이원화가 사라지므로 정리 기회이기도 하다.
