1. 무엇을 왜 했는가
--------------------------------------------------------------------
테스트가 운영 DB(db/migration_validator.db)에 프로젝트 잔재를 남기던 문제의 근본원인(생성
경로와 정리 경로가 서로 다른 DB 를 보던 비대칭)은 앞선 PROJECT-TEST-DB-PATH-ASYMMETRY-FIX
(fe8e6b4)에서 이미 제거됐다. 이번 작업은 그 위에 얹는 '안전망'이다. 즉 정리 로직이 또 어긋나
잔재가 남더라도, 그 행이 테스트가 만든 것임을 이름 패턴 추측이 아니라 명시적 플래그로 알 수
있게 하고, 그 플래그를 통과한 행만 안전하게 회수할 수 있게 했다.

설계안 (A)~(E) 를 순서대로 그대로 구현했고, 새 방식을 발명하지 않았다. 삭제 정책·라우트·화면
3층은 이미 존재하는 '그룹 삭제'(services/batch_group_service.resolve_delete_policy /
hard_delete_group / routes/group_master_route.py)의 구조를 그대로 대칭 이식했다.


2. 구현 내역 (A~E)
--------------------------------------------------------------------
(A) 스키마 — services/project_store.py : ensure_schema()
    기존 is_deleted/deleted_at 과 같은 멱등 ALTER 루프에 is_test 를 추가했다.
      is_test INTEGER NOT NULL DEFAULT 0
    DEFAULT 0 = 운영이므로 기존 행은 손대지 않아도 전부 '운영 프로젝트'로 남는다. CREATE TABLE
    정의가 아니라 ALTER 루프에 넣었기 때문에 이미 만들어진 DB 에도 그대로 적용되고, 두 번
    호출해도 컬럼이 중복되지 않는다.

(C) 생성 — services/project_store.py : create_project()
    create_project(project_name, description, status, *, is_test=False, db_path=None)
    is_test 를 키워드 전용(*, 뒤)으로 두어, 위치인자만 쓰는 기존 호출부는 한 줄도 고치지 않고
    전부 is_test=0(운영)을 유지한다. 조회 함수(list_projects/get_project)에도 is_test 를
    COALESCE(is_test,0) 로 노출해 정책 판정과 화면이 같은 값을 본다.

(D) 테스트 헬퍼 — tests/_group_test_project.py : test_project_id()
    테스트 전용 프로젝트를 만들 때 is_test=True 를 붙인다. 이 헬퍼를 경유하는 18개 테스트
    파일은 수정 없이 일괄 커버된다(설계 확인 사항이며 이번에 실제로 그대로 성립했다).
    추가로, 실제 잔재의 다수(22건)를 만들어 온 OWN-* 생성처 2곳
      tests/test_owner_connection_enforcement.py
      tests/test_single_official_register_owner_binding.py
    은 헬퍼를 경유하지 않고 create_project 를 직접 호출하므로 같은 표식을 부여했다. 설계 (D)의
    문자 그대로의 범위는 아니지만, 안전망이 실제 잔재 발생원을 덮지 못하면 의미가 없어 포함했다.

(E) 회수 — services/project_store.py + scripts/cleanup_test_projects.py
    · count_project_refs(project_id)
      project_id 를 참조하는 13개 자식 테이블의 건수를 모은다. 참조 컬럼 타입이 테이블마다
      TEXT/INTEGER 로 섞여 있어(SQLite 는 타입이 다르면 같지 않다고 본다) 문자열·정수 두 형태를
      모두 대조한다. mv_project 는 자식이 아니라 별도 legacy master 라 제외했다.
    · resolve_project_delete_policy()
      is_test=1 이고 참조 0건 → mode='hard'(완전 삭제).
      is_test=1 이지만 참조가 있으면 → mode='soft' 로 '완전 삭제 보류' 사유를 붙여 반환한다.
      여기서 blocked 로 막지 않은 것은 의도적이다. 안전망을 넣은 결과 기존에 가능하던 soft
      delete 가 불가능해지면 기능 축소이므로, 완전 삭제만 보류하고 soft 는 그대로 허용한다.
      운영 프로젝트(is_test=0)의 판정은 이전과 완전히 동일한 soft 다.
    · hard_delete_project() — 2중 게이트
      게이트① is_test=1 이 아니면 거부(운영 프로젝트는 참조가 0건이어도 물리 삭제 불가).
      게이트② 참조가 1건이라도 있으면 거부(HOLD).
      둘 다 통과한 '빈 테스트 프로젝트 row' 만 DELETE 한다. cascade 삭제는 하지 않는다.
    · scripts/cleanup_test_projects.py (신설, 그룹용 cleanup_test_groups.py 구조 재사용)
      기본이 dry-run 이고, --apply 를 줘야 삭제한다. 실제 삭제는 반드시 hard_delete_project
      를 경유해 게이트 로직을 중복 구현하지 않는다. 보고는 세 구획으로 나눈다.
        [삭제 대상]  is_test=1 & 참조 0건
        [HOLD]       is_test=1 이지만 참조 존재
        [패턴 후보]  is_test=0 + 테스트성 이름 — 나열만 하고 절대 삭제하지 않음

    3층 일치를 위해 다음 두 곳도 함께 맞췄다(그룹 삭제와 동일 구조):
      routes/project_route.py  : mode='hard' 면 hard_delete_project, 그 외는 기존 soft.
      ui/tabler_renderer.py    : 삭제 modal '삭제 방식' 표기가 서버 mode 를 그대로 따른다.
    이 둘을 맞추지 않으면 modal 은 '소프트 삭제'라고 쓰고 사유문은 '완전 삭제합니다'라고 쓰는
    설명 불일치가 생긴다.


3. (B) 기존 패턴 마이그레이션 — 판단: 보류(미적용)
--------------------------------------------------------------------
현재 운영 DB 의 프로젝트 26건 중 25건이 테스트성 이름(OWN-% 22, TESTONLY% 2,
__TEST_PROJECT__ 1)이고 실제 운영 프로젝트는 1건(project_id=2)뿐이다. 이 25건에 is_test=1 을
소급 부여할지 판단하기 위해 참조 현황을 읽기전용으로 실측했다.

  참조 0건(표식 부여 시 즉시 삭제 대상) : 12건
  참조 존재(표식을 줘도 HOLD)          : 13건
    832 TESTONLY_REG            : batch_group 7 / upload_row 7 / owner_binding 1 / 외 3종
    898 __TEST_PROJECT__        : batch_group 13 / upload_row 44 / owner_binding 9 / 외 3종
    899,910 OWN-ENF-*           : batch_group 1 / owner_binding 1
    905,906,908,909,916,917,919,920 OWN-BIND-* : owner_binding 1~2
    921 TESTONLY_ASYNC_PARALLEL : batch_group 2 / upload_row 10

보류 사유는 네 가지다.
  ① is_test=1 부여는 단순 표기가 아니라 hard delete 게이트를 여는 '무장' 행위다. 그 근거가
     이름 패턴 추측이면, 나중에 'OWN-' 으로 시작하는 실제 운영 프로젝트가 생겼을 때 조용히
     삭제 대상이 된다. 안전망을 만들면서 새 위험을 들이는 셈이다.
  ② 근본원인은 이미 해결됐고 (D) 로 앞으로 생기는 잔재는 자동으로 표식을 얻는다. 소급
     마이그레이션의 실익은 '과거 25건'으로 한정된다.
  ③ 실익 자체가 절반이다. 25건을 전부 표시해도 삭제 가능한 것은 12건뿐이고 13건은 참조
     때문에 HOLD 된다. 목록은 어차피 절반만 정리된다(나머지는 자식 데이터까지 손대야 하며,
     그것은 이번 설계 범위 밖의 cascade 정리다).
  ④ 되돌릴 수 없다. 물리 삭제는 복구가 없다.

대신 실행 경로는 열어 뒀다. 사용자가 확인한 뒤 아래 한 줄이면 표식 부여와 회수가 함께 된다.
  python scripts/cleanup_test_projects.py --mark-test --apply
--mark-test 를 명시하지 않으면 패턴 후보는 절대 표식을 얻지 않는다(자체 테스트로 고정).
