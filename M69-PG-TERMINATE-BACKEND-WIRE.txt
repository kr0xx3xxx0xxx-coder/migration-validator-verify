지나간다. 그래서 캡처를 이 한 곳에만 넣으면 두 경로가 함께 덮인다.

→ 완료 모듈로 지목됐던 pk_range_chunk.py / agg_contribution.py 는 **한 줄도 수정하지 않았다**.
   (승인은 받았으나 수정할 필요가 없었다 — 최소 침습 원칙에 부합. 두 파일에 PG 전용 분기를 넣지

   ORACLE-EXACT-DIFF-PHYSICAL-FILE-SEPARATION 원칙 유지 — 코어에 db_type if/elif 없음.)

지침 범위 밖으로 넘어간 판단 1건(스코프 명시):
  지침 3번은 "sweeper(reclaim_dead_thread_jobs)가 ORPHANED 로 확정하는 지점"만 지목했으나, 검증이
  요구한 taskkill 시나리오는 그 지점만으로는 구조적으로 성립하지 않는다 — 클라이언트(=서버 프로세스)를
  강제종료하면 in-memory job(_JOBS_BY_RUN)과 sweeper thread 가 함께 사라지므로, 살아남은 PG 세션의
  PID 를 아는 주체가 프로세스 안에 남지 않는다. 그래서 PID 를 DB(exact_diff_run)에 영속화하고, 재기동
  직후 RUNNING→ORPHANED 를 확정하는 기존 지점(retention_cleanup.mark_startup_orphans)에도 동일한
  종료 호출을 배선했다. 두 지점 모두 "job 이 ORPHANED 로 확정되는 바로 그 자리"이며, 새 확정 경로를
  만들지 않았다(기존 2개 경로에 종료 1줄씩 추가).

3. PID 캡처/저장 방식
────────────────────────────────────────────────────────────
캡처: dialects/postgresql.raw_connect 가 psycopg2.connect 직후
        SELECT pg_backend_pid(), (SELECT backend_start FROM pg_stat_activity WHERE pid=pg_backend_pid())
      1회 실행(연결당 1회, 비용 무시 가능). 캡처 쿼리가 연 트랜잭션은 **즉시 rollback** 한다 —
      psycopg2 는 트랜잭션 중 set_session() 을 거부하므로, rollback 없이는 그 직후 실행되는
      open_reimport_stream 의 set_session(readonly=True) 이 깨진다(실 DB 로 재확인함: 스트림 정상 동작).

저장: 두 곳에 이중으로 둔다(둘 다 필요해서지 중복이 아니다).
  (가) in-memory : thread ident → 세션 목록. 같은 프로세스 안에서 실행 thread 만 죽은 경우(sweeper 경로).
  (나) DB 영속   : exact_diff_run.pg_sessions_json (신규 컬럼). 프로세스가 통째로 강제종료된 뒤
                   재기동했을 때 끊을 PID 를 아는 유일한 단서다. in-memory 만으로는 taskkill 시나리오를
                   구조적으로 덮을 수 없다(위 §1 마지막 문단).
  선택 근거: 지침이 위임한 "컬럼 추가 vs job 객체 필드" 중, job dict 필드만으로는 검증이 요구한
  taskkill 재현이 불가능하므로 컬럼 추가를 선택했다. 컬럼 1개 + 조회/저장 메서드 2개로 끝나고,
  기존 finish_run(basis 덮어쓰기)과 간섭하지 않는 별도 컬럼이라 부작용이 없다.

src/tgt 양쪽 처리: **양쪽 모두 저장한다.** 재이관 job 은 원본/목적 각 1개씩 PG 커넥션을 여는데(둘 다
  raw_connect 를 지난다), 어느 쪽이 무거운 연산을 물고 있을지는 사전에 알 수 없다(원본 스캔이 길 수도,
  목적 조회가 길 수도 있다). 캡처는 thread 단위로 누적되므로 별도 배선 없이 양쪽이 자동으로 담긴다
  (thread 당 상한 8개). 종료 시에는 접속정보(host/port/dbname/user/sslmode)별로 묶어 관리자 커넥션을
  1개씩만 연다 — src/tgt 가 같은 인스턴스면 커넥션 1개로 두 PID 를 모두 처리한다.

비밀번호: PgSessionRef 에 password 필드 자체가 없다. 저장 항목은 PID·backend_start·접속 identity 뿐이며,
  종료용 관리자 커넥션의 비밀번호는 기존 chokepoint(_pg_raw_connect → _with_resolved_password →
  프리셋 저장소)로만 복원한다. 유닛테스트로 "저장 JSON 에 password 키·값이 없음"을 고정했고,
  커밋 시 저장소 pre-commit 비밀번호 스캔도 통과했다.

4. PID 재사용 안전장치 설계와 근거
────────────────────────────────────────────────────────────
설계(채택): backend_start 대조. 캡처 시점에 pg_stat_activity.backend_start(세션 시작 시각, 마이크로초
  포함)를 함께 저장하고, 종료 직전에 그 PID 를 다시 조회해
    ① 행이 없다        → ALREADY_GONE  : 이미 자연 종료 — pg_terminate_backend 를 호출조차 하지 않는다
    ② backend_start 상이 → PID_REUSED   : 다른 세션이 그 PID 를 쓰는 중 — 절대 끊지 않고 건너뛴다(경고 로그)
    ③ 일치             → 그때만 pg_terminate_backend(pid) 호출
  application_name/query 패턴 대조는 넣지 않았다 — backend_start 는 마이크로초 단위 시각이라 동일 PID +
  동일 backend_start 인 다른 세션은 존재할 수 없다(대조 1개로 충분, 과공학 방지).

재사용 위험의 실제 크기(정직한 평가): 리눅스 PID 공간(기본 pid_max=32768~4194304)을 한 바퀴 돌아야
  재할당되므로 확률 자체는 낮다. 다만 이번 배선은 "확정까지 30초(유예) + 최대 300초(sweep 주기)" 뒤에
  호출되고, **재기동 경로는 그보다 훨씬 긴 시간(서버가 꺼져 있던 시간 전체)** 뒤에 호출된다 — 밤새 꺼져
  있다가 아침에 켜지는 경우 그 사이 PID 가 재사용될 여지는 실재한다. 잘못 끊으면 무관한 사용자 세션이
  죽는 사고이므로, 비용이 조회 1회뿐인 backend_start 대조는 넣는 것이 명백히 옳다고 판단했다.
  (반대로, 대조 없이도 '무해'하다는 근거는 없다 — 아래 §5 실측은 '죽은 PID 호출이 무해'하다는 것이지
   '재사용된 PID 호출이 무해'하다는 뜻이 전혀 아니다.)

부가 안전장치 3종:
  - worker 정상 종료 시 in-memory 추적 즉시 해제(_runner finally) — 끝난 job 의 PID 를 나중에 끊지 않는다.
  - 실행 thread 가 살아 있는 job 은 애초에 ORPHAN 확정 대상이 아니다(기존 L1 사실 판정 그대로 재사용).
  - 접속 불가 대상 fail-fast(60초 창) — raw 연결이 connect_timeout=30 이라, 고아 run 이 여러 건이면
    서버 기동(_lifespan)이 그만큼 지연될 수 있어 한 번 실패한 대상은 그 창 동안 건너뛴다.
