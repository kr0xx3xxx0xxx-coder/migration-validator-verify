1. 무엇이 문제였나
────────────────────────────────────────────────────────────────────────
선행 진단(SINGLE-STEP5-MULTI-GROUPBY-REPRESENTATIVE-AXIS-DIAGNOSE)에서 확정된 사실은
다음과 같았다. 사용자가 개별검증 3단계에서 GROUP BY 를 2개(예: STATUS_CD + DEPT_CD)
선택하면, 4단계 화면은 "생성된 SQL 기준"이라는 제목 아래

    GROUP BY STATUS_CD, DEPT_CD

형태의 '조합' 통계검증 SQL 을 원본/목적지 양쪽으로 보여준다. 그런데 이 SQL 은 실제로는
한 번도 실행되지 않는다. 4단계 '통계검증 실행'을 누르면 runExecute 가

    if (gbSel.length >= 2) → _runExecutePlanSets(...)

로 분기해, /groupby-plan 이 만든 '축별 단일 세트' 계획대로 /generate·/execute 를 세트마다
다시 호출한다. 즉 화면에 보이던 조합 SQL 대신 GROUP BY STATUS_CD 한 세트, GROUP BY
DEPT_CD 한 세트가 각각 따로 생성·실행된다(services/groupby_plan_service.py 의
build_groupby_execution_plan 이 선택 축마다 SET_SINGLE 세트를 1개씩 만들고, 단일 축은
자동 제외 대상이 아니므로 세트 수 N 은 선택 축 수와 항상 같다. 2축 보강 세트는 사용자가
'보강 분석'을 명시적으로 실행할 때만 추가된다).

5단계(결과 확인)의 실행 근거 영역에는 이미 "단일 축 2세트: STATUS_CD / DEPT_CD" 라고
사실대로 표기되고 있었다. 사실과 다른 화면은 4단계 하나뿐이었고, 그 결과 사용자는
'조합(STATUS_CD × DEPT_CD) 단위로 검증했다'고 오인할 수 있었다. 조합 검증과 축별 검증은
탐지 범위가 다르므로(조합에서만 드러나는 불일치는 축별 집계에서 상쇄될 수 있다) 이는
단순 문구 문제가 아니라 검증 범위를 오해하게 만드는 표시 오류였다.


────────────────────────────────────────────────────────────────────────
2. 무엇을 고쳤나
────────────────────────────────────────────────────────────────────────
4단계 '생성된 SQL 기준' 박스 안에, GROUP BY 가 2개 이상일 때만 나타나는 안내 한 개를
추가했다(요소 id: genSqlComboDecomposeNotice). 표시 문구는 아래와 같다.

  ⚠️ 이 SQL은 참고용입니다 — 실제로는 각 축을 독립적으로 실행합니다.
     아래 조합 SQL(GROUP BY STATUS_CD, DEPT_CD)은 실행되지 않습니다. 통계검증 실행 시
     단일 축 2세트(STATUS_CD / DEPT_CD)로 분해해 축별로 따로 집계·비교합니다.
     실제 실행된 SQL과 세트 구성은 5단계(결과 확인)에서 확인할 수 있습니다.

세트 수와 축 목록은 선택값에서 그대로 만들어 5단계의 "단일 축 N세트" 표기와 같은 어휘를
쓰도록 맞췄다. GROUP BY 가 0개(전체 기준 집계) 또는 1개인 경우에는 조합 분해 자체가
일어나지 않으므로 안내가 붙지 않는다.

변경 범위는 표시 문구 한 곳뿐이다. 표시되는 SQL 원문은 손대지 않았고(여전히 조합 SQL 을
그대로 보여준다 — 사용자가 선택 기준을 검토하는 용도), SQL 생성·실행·판정 로직은 한 줄도
건드리지 않았다.

  변경 파일 : ui/js_sql_preview.py  (+20줄, 신규 함수 없음)
  변경 위치 : renderSQL() 의 '생성된 SQL 기준'(gen-sql-basis) 박스 구성부


지시와 다른 점 — 수정 파일 (사전 보고)
  작업 지시는 "ui/tabler_renderer.py 만 수정"이었으나, 4단계 생성 SQL 을 실제로 그리는
  renderSQL 은 과거 UI-RENDERER-DISPLAY-COMPONENT-EXTRACTION 작업으로 tabler_renderer.py
  에서 ui/js_sql_preview.py 로 이미 분리되어 있었다(tabler_renderer.py 25287행에 이관
  주석만 남아 있다). tabler_renderer.py 쪽에서 처리하려면 renderSQL 호출부 2곳
  (runGenerate, 원클릭 전체검증 경로) 뒤에서 DOM 을 사후 주입해야 하고, 호출부가 하나라도
  늘면 안내가 조용히 빠지는 구조가 된다. 그래서 지시의 취지("4단계 SQL 표시 부분만,
  판정/실행 로직 불가침")를 그대로 지키면서 표시 단일 출처인 js_sql_preview.py 를
  수정했다. 이 파일은 설계상 presentation 전용 모듈이므로 판정/실행 로직과는 무관하다.
  tabler_renderer.py 는 이 작업에서 한 글자도 수정하지 않았다.

4. 남은 사실과 한계
────────────────────────────────────────────────────────────────────────
- 이번 변경은 표시 정확성만 회복한다. 다중 GROUP BY 를 '조합'으로 검증하지 않는다는
  동작 자체는 그대로다. 조합 단위 검증이 필요하다는 요구는 별개 작업으로 남는다.
- 안내에 적히는 세트 수 N 은 선택 축 수를 그대로 쓴다. 현재 실행계획이 단일 축 세트를
  자동 제외하지 않으므로 실제 세트 수와 일치하지만, '보강 분석'을 명시 실행하면 2축
  세트가 1개 추가될 수 있다(그 경우 실행 세트 수는 N+1). 안내는 분해 실행 사실을
  알리는 것이 목적이므로 이 경우도 오해를 유발하지 않는다고 판단했다.
- 이 작업 중 다른 세션이 ui/tabler_renderer.py, ui/grid_helpers.py 를 동시 수정 중이었다.
  스테이징은 내 파일만 선별해 커밋했고(js_sql_preview.py + 신규 검증 스크립트 2개),
  타 작업 변경분은 손대지 않았다. 다만 (1) 항의 실 서비스 검증은 그 미커밋 변경분이
  함께 올라간 서버에서 수행됐다는 점을 사실대로 남긴다.
