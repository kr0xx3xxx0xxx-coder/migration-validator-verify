- 실측 재현 결과(전 계층 추적): 폴링은 정상 작동(‘재이관 대상 준비 중’ 표시). 실제 근본원인은 다름 —
  · /agg-diff/prepare → PREPARING, 직후 /agg-diff/pk-records → FAILED
    error: "재이관 index 스트리밍 오류: ORA-00904: \"RN\": invalid identifier"
  · 그 결과 프론트가 STALE_PLAN(막다른 길) 표시. (즉 '고착'이 아니라 ~1.7초 만의 빠른 크래시.)
- 근본원인(규명): 파서(sqlglot)가 CTE+JOIN+윈도우 SQL 을 잘못 평탄화 —
    from_table = MV_ORA_XDIFF_SRC(CTE 내부 베이스 테이블), joins = [](CTE 안 JOIN 미포착),
    where = 'rn >= 1'(윈도우 별칭 rn 참조), select_items 는 CASE/윈도우 변형 소실.
  → 드릴다운 재파생 _derive_row_sqls(routes/exact_diff_route.py)는 joins=[] 라 통과하고
    'SELECT (ID) AS ID, … FROM NXDNP.MV_ORA_XDIFF_SRC WHERE rn >= 1' 을 생성.
    베이스 테이블엔 rn 컬럼이 없어 재이관 스트림이 ORA-00904 로 즉시 실패. 기존 JOIN 가드(joins 검사)는
    CTE 안에 숨은 JOIN 을 놓쳤다. (_pk_resolve 가 만든 실패 SQL 을 xdiff_join_pk_resolve_probe.py 로 확정.)
- 수정: routes/agg_diff_route.py 의 _pk_resolve 가 행수준 재파생 전에 원본 SQL(query_full, 드릴다운
    payload 로 이미 전달됨)의 shape 를 재사용 유틸(services.sql_cte_utils.extract_physical_source_tables·
    extract_cte_names)로 재검사 — CTE(WITH)/다중 원본(JOIN)/UNION 이면 충실한 행수준 파생이 불가하므로
    명확한 HOLD(HOLD_UNSUPPORTED_SHAPE)로 조기 반환. 크래시/STALE_PLAN 대신 정직한 안내를 표시한다.
    통계검증(COUNT·SUM)은 원본 SQL 을 그대로 감싸 실행하므로 영향 없음 — 제한은 '행 단위 재이관 목록'만.
- 안내 문구(실측 after 패널):
    "HOLD_UNSUPPORTED_SHAPE — 이 SQL 형태(공통 테이블 식(WITH/CTE) · 다중 원본 테이블(JOIN/서브쿼리))는
     재이관 상세(행 단위 PK 비교)를 지원하지 않습니다. 통계검증(COUNT·SUM) 결과는 정상이며, 행 단위
     재이관 목록은 단일 테이블 1:1 이관 SQL 에서만 제공됩니다."

■ 중요 — '100건 초과' 배너에 관하여 (추가 작업 판단)
- 이 SQL 형태(CTE+JOIN+윈도우)는 '행 수준 재이관 상세 드릴다운'을 설계상 지원하지 않는다
  (_derive_row_sqls 의 기존 정책: 'JOIN 이관은 Phase 1-B 미지원 — 1:1 단일 테이블만'). 따라서 태스크
  기대(b) '100건 초과' 재이관 배너는 이 SQL 에서 원래 나올 수 없으며, 정상 동작은 HOLD 안내다.
- 이번 수정은 '크래시→STALE_PLAN 막다른 길'을 '정직한 HOLD 안내'로 바꾼 것이다(통계검증 결과는 정상 표시).
- 만약 JOIN/CTE SQL 에서도 행 단위 재이관 목록(및 배너)까지 제공하려면, 파생 소스(원본 SQL 그대로 감싸
  행수준 비교)를 쓰는 '행수준 드릴다운 파생소스 지원'을 새로 구현해야 한다(현 설계의 명시적 보류를
  뒤집는 신규 기능 → 별도 계획·승인 필요). 기술적 타당성은 확인됨(원본 CTE 를 감싼 FROM (cte) ORDER BY ID
  첫 200행 오픈 0.26초로 빠름). 진행 여부는 사용자 결정 사항이라 ⚠️로 표시.
