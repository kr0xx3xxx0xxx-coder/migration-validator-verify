작업명 : M50-EDGE-CASE-VERDICT-DISTRIBUTION-MEASURE
✅ 작업 완료 - evaluate_admin_audit_crosscheck 실 DB 재스윕(506컬럼) 결과 LLM 호출후보(N1+N3+B-only-CONFIRMED)는 27건(5.3%), 그중 근거부족(N1) 24건은 23건이 오늘 시점 0행 픽스처 테이블 부작용 — 실질 호출후보는 4~5건(0.8~1.0%). "문서화 우선·구현 보류" 결론 유지 권고, 단 LLM 없이도 즉시 처리 가능한 더 위험한 결함 1건(무배지 CONFIRMED) 함께 실측됨

■ 조사 목적과 성격
  LLM-ADMIN-COLUMN-JUDGMENT-SCOPE-AND-DESIGN-DIAGNOSE(설계 확정, 2026-08-07)가 남긴 갭
  — "LLM이 실제로 몇 %의 컬럼에서 호출될지 지금 데이터로 추정 불가" — 을 메우기 위한
  축소 실측이다. 인프라(Ollama/Docker) 설치는 범위 밖, 코드 변경도 없음(읽기 전용 조사 +
  계측 스크립트 신규 작성만). 실 DB 접근은 SELECT/카탈로그 조회만 수행했다(DDL·DML 없음).
  services/candidate_subtype_service.py 는 이번 조사에서도 한 줄도 수정하지 않았다.

  F18(2026-08-07)이 axis_a(값=단조증가) 신호만 스윕해 "3차 신호가 실제로 호출될 모집단"

  전체(B축 명칭/코멘트 × A축 값)를 실제 함수로 호출해 verdict 4종의 실측 분포와, 그 안에서
  "axis_a/axis_b 둘 다 결론 못 낸(=LLM 호출 대상)" 케이스가 정확히 몇 건인지를 잰다.

1. [방법론 — F18 데이터셋 재사용 시도와 재스윕으로 전환한 이유]
────────────────────────────────────────────────────────────────────────────

  지시서는 "가능하면 F18이 스윕한 479개 컬럼 데이터셋을 재사용(중복 조사 방지)"을
  요청했다. 실제로 시도했으나 3가지 이유로 전체 재사용이 불가능해 재스윕으로 전환했다
  (재사용 시도 자체는 값 실측 근거로 남긴다):

  (1) axis_b 계산에 필요한 원본 데이터가 캐시에 없다
      scratchpad/_f18_broad.json(F18 이 남긴 캐시)에는 axis_a(값 판정)만 있고, 컬럼
      코멘트·B축 명칭매칭에 필요한 원문 값 샘플이 없다. evaluate_admin_audit_crosscheck
      의 B축(axis_b_naming/axis_b_comment)을 재구성하려면 어차피 컬럼 코멘트(pg
      col_description)를 다시 조회해야 해서, "값 조회 재사용"의 실익이 크지 않았다.
  (2) F18 의 mono/strict 계산이 "값 부족" 컬럼을 조용히 스킵했다
      f18_broad_sweep.py 는 mono()가 None(비-NULL 값 2개 미만)을 반환하면 그 컬럼을
      결과에서 통째로 뺐고, 테이블 자체가 <2행이면 테이블째 스킵했다. 이 스킵이 바로
      N1("값 미배선")이 발생하는 조건과 정확히 겹친다 — 즉 F18 캐시는 이번 조사가 가장
      보고 싶은 N1 케이스를 구조적으로 배제하고 있었다(재확인 결과 스키마 전체 580컬럼
      중 40개 누락, 아래 [표0]).
  (3) 스키마가 F18 실측일(2026-08-07)과 오늘(2026-08-08) 사이 변경됐다
      asis01.mvq_dept/mvq_emp 등 F18 스키마 덤프에 있던 테이블 일부가 오늘 재조회에서
      사라졌고, t_to_1_etl01/t_sumnullx_tgt/ntb.mvq_tgt 는 오늘 시점 0행이다(F18 당시
      행수는 재확인 불가 — 캐시에 rows 필드가 있으나 self_sort 등 다른 이유로 존재 자체가
      기록되지 않은 테이블도 있어 직접 비교가 어려움). 캐시를 그대로 쓰면 "어제의 분포"를
      "오늘의 결론"으로 보고하는 오류가 생긴다.

4. [★ CONFIRMED(B-only) 3건 — LLM-ADMIN 문서가 지목한 "미해소 한계"가 실제로 재현됨]
────────────────────────────────────────────────────────────────────────────

  해당하는 3건 전부를 확인했다.

  (1) asis01.t_admcol_src.biz_reg_no (사업자등록번호), (2) tobe01.t_admcol_tgt.biz_reg_no
      — 코멘트 없음, 명칭매칭만으로 SYSTEM_AUDIT(WEAK) 판정, 값 600건 실측했으나
      타임스탬프가 아니라 axis_a=None → 배지 없이 CONFIRMED(GROUP BY 자동선정에서
      하드 배제). ★ 이 컬럼은 LLM-ADMIN-COLUMN-JUDGMENT 설계 문서가 §2 에서 직접 예시로
      든 "명칭만 감사스러운 업무컬럼(BIZ_REG_NO)"과 정확히 일치하는 실제 재현 사례다
      (설계 당시엔 가상의 우려였는데, 이번 실측으로 같은 픽스처에서 실제로 발생함을
      확인했다). 사업자등록번호는 GROUP BY 로 그룹 비교에 쓰일 수 있는 정상 업무 컬럼인데
      화면에 아무 경고도 없이 체크박스가 비활성화된다.
  (3) tobe01.t_to_1_etl01.updated_at — 코멘트 있음, 명칭매칭 SYSTEM_AUDIT, 그러나 이

      명백한 관리컬럼(updated_at)이라 CONFIRMED 가 오판이 아닐 가능성이 높다 — §3 의
      0행 테이블 문제와 같은 원인.

  대조 사례(같은 로직의 다른 갈래, NAMING_VALUE_MISMATCH 2건):
    mvbench.bench_1m.reg_dt, mvbench.bench_src.reg_dt — 이름은 SYSTEM_AUDIT 로 매칭됐지만
    실제 값이 타임스탬프로 파싱되고 배치 스탬프 조건을 반증(axis_a=False)해 값이 이름을
    이겨 정상적으로 선택 가능 상태를 유지했다. 이는 axis_a 가 "있고 반증 가능할 때"는
    설계대로 잘 작동함을 보여준다 — 문제는 axis_a 가 "반증할 수 없을 때(None)"에 국한된다.

  ▶ 즉 재현된 오탐(biz_reg_no 2건)은 표본 크기는 작지만(506건 중 2건, 0.4%) **화면에
  경고가 전혀 없는 상태(무배지 CONFIRMED)**라는 점에서 N1/N3(배지는 뜨는 애매)보다
  질적으로 심각하다 — LLM-ADMIN 설계 문서 §2 의 우선순위 판단("(B)가 (A)보다 위험이
  크다")이 실측으로 뒷받침된다.

5. [해석 — Ollama 인프라 투자 가치 판단]
────────────────────────────────────────────────────────────────────────────

  ■ 투자 가치: 낮음 — M50 "문서화 우선·구현 보류" 결론 유지를 권고한다.
    근거:
    (1) 실측 LLM 호출 후보 비율은 5.3%(픽스처 아티팩트 포함) ~ 1.0%(제외)다. 506컬럼
        중 5~27건을 위해 Ollama+모델+Docker(GPU 유무 대응·폐쇄망 반입·컨테이너
        수명주기 관리·SQLite 캐시·circuit-breaker)를 들이는 것은, LLM-ADMIN 문서 §5 가
        이미 지적한 "실제로는 거의 안 쓰이는 기능에 배포 복잡도만 얹을 위험"이 수치로
        확인된 것이다.
    (2) N1(설계 문서가 원래 겨냥한 "이름/값 둘 다 애매") 은 이번 표본에서 순수 형태로는
        2건뿐이고, 그마저 업무 규칙(재직자 NULL)으로 이미 설명 가능하다 — LLM 이 아니라
        기존 사용자 override 경로(§1 언급된 apply_admin_column_overrides, 이미 존재)로
        충분히 처리 가능한 수준이다.
    (3) N3(형태는 타임스탬프인데 파싱 실패)는 이번 506컬럼 전체에서 0건 관측됐다.
        F18 이 우려했던 ymd/base_dt 류 cd1 컬럼들은 시간 성분이 없어
        detect_timestamp_shaped_values 에 애초에 걸리지 않고 N2(정상 업무컬럼, 배지 없음)
        로 올바르게 처리된다 — 삽입지점(A) 중 이 하위 유형은 지금 근거가 없다.
    (4) F18 이 이미 "3차 신호는 오탐률 미검증 시 착수 보류"라는 선례를 남겼고, LLM 도
        "오판 가능"이 전제인 신호라 같은 기준이 적용돼야 한다는 LLM-ADMIN 문서의 논리는
        이번 실측으로 강화된다 — 애초에 호출 자체가 드물면 오탐률을 신뢰 구간 있게
        재는 것도 더 오래 걸린다(표본이 작다).

  ■ 그러나 발견한 더 시급하고 훨씬 저렴한 대안이 있다(LLM 불필요, 순수 규칙기반)
    §4 에서 재현한 biz_reg_no 오탐은 **LLM 없이도 지금 당장 고칠 수 있는 문제**다.
    삽입지점(B, axis_b=True(WEAK)+axis_a=None) 의 최종 verdict 를 CONFIRMED 대신
    N1/N3 와 같은 "배지 있는 애매(NOT_AUDIT_AMBIGUOUS 계열)"로만 낮춰도(값 우선 원칙은
    그대로, 자동 하드 배제만 배지로 전환), 화면에 경고 없이 조용히 사라지던 정상
    업무컬럼(biz_reg_no)이 사용자 검토 대상으로 노출된다. 이는:
      · services/candidate_subtype_service.py 의 판정표 한 줄만 바꾸는 순수 규칙기반
        변경(코드 라인 수 매우 작음, LLM/인프라 전혀 불필요)
      · 다만 verdict 값의 의미가 바뀌므로 소비처 4곳 + JS 미러(§1) 회귀 검토가 필요하고,
        "완료 모듈에 준하는 승인" 대상(LLM-ADMIN 문서 §5 가 이미 명시)이라 별도 지침+
        사용자 승인 없이 이번 조사에서 손대지 않았다.
    ★ 권고: LLM 투자보다 이 규칙기반 수정을 먼저 별도 지침으로 검토할 것을 제안한다 —
    비용은 훨씬 낮고, 이번 실측이 실제 오탐(biz_reg_no)을 재현해 가치를 입증했다.

  ■ M50 결론 재검토 여부: 유지(구현 보류) — 단, 우선순위 갱신
    "언젠가 Ollama 도입"이 아니라 "지금은 규칙기반 배지 전환(§4의 대안)으로 가장 위험한
    사례(무배지 CONFIRMED)부터 해소하고, LLM 은 그 이후에도 남는 진짜 애매 케이스(N1
    순수형·N3)가 실 운영 데이터에서 유의미한 비율로 관측될 때 재검토"로 구체화한다.

7. [제한사항 / 한계]
────────────────────────────────────────────────────────────────────────────
  · 실측 대상은 PostgreSQL 단일이다(oracle/mysql/mssql 미실측 — F18 과 동일 한계 승계).
  · 표본은 이 저장소의 픽스처 DB 하나다. §3 이 보이듯 "오늘 시점 몇 개 테이블이 우연히
    비어 있었다"는 표본 특유의 사정이 N1 비율에 크게 영향을 준다 — 다른 시점/다른
    프로젝트 데이터에서는 N1·N3 비율이 다를 수 있다(특히 이관 진행 초기에는 목적지가
    비어 있는 경우가 오히려 전형적일 수 있음). "5.3%"·"1.0%" 어느 쪽도 일반화된 상한/
    하한으로 인용해서는 안 되며, 이 픽스처 표본 1건의 관측치로만 취급해야 한다.
  · axis_b_naming 을 "①scoring 경로(_best_semantic_match) OR ②엔진 게이트 경로
    (build_semantic_type_candidates)"로 계산했는데, 실제 프로덕션에서 ②는 SUM(숫자형)·
    GROUP_BY(날짜/시간형) 후보에만 계산돼 candidate 에 실린다(services/candidate_engine.py
    494/596행) — 이번 스윕은 컬럼 타입 무관하게 항상 두 경로를 다 계산해 OR 결합했으므로,
    실제 파이프라인보다 axis_b_naming 이 넓게(=CONFIRMED/AMBIGUOUS 쪽으로) 잡혔을 수
    있다(보수적 방향 — LLM 호출 후보를 과소평가하지 않는 방향의 근사다). 정확한 게이트
    조건까지 재현하려면 candidate_engine.py 의 타입별 후보 생성 경로 전체를 재실행해야
    하는데, 이는 이번 "계측만" 범위를 넘는 별도 조사가 필요하다.
  · N2(458건, 90.5%)의 내부 구성(예: 실제 코드성 저카디 컬럼 vs 다른 이유로 A축이 관할
    밖인 컬럼)은 이번 조사에서 더 세분하지 않았다 — 지시서가 요구한 N1/N2/N3 비율과
    LLM 후보 비율에는 영향 없음.
  · 조사용 스크립트는 scratchpad/m50_verdict_sweep.py 로 남겼다(코드 저장소 커밋 대상
    아님). 코드 저장소에는 어떤 변경도 가하지 않았다.

✅ 작업 완료 - evaluate_admin_audit_crosscheck 실 DB 재스윕(506컬럼) 결과 LLM 호출후보(N1+N3+B-only-CONFIRMED)는 27건(5.3%), 그중 근거부족(N1) 24건은 23건이 오늘 시점 0행 픽스처 테이블 부작용 — 실질 호출후보는 4~5건(0.8~1.0%). "문서화 우선·구현 보류" 결론 유지 권고, 단 LLM 없이도 즉시 처리 가능한 더 위험한 결함 1건(무배지 CONFIRMED, biz_reg_no 재현)이 함께 실측됨
