✅ 작업 완료 - 서버는 기동 실패가 아님. PID 24640 정상 LISTENING 중이며 접속 불가의 실체는 HTTP Basic Auth 401 요구

작업명 : SERVER-STARTUP-FAILURE-DIAGNOSE
일시   : 2026-07-29 14:20 (KST)
성격   : 순수 진단(코드 수정 없음)

================================================================================
1. 결론
================================================================================
"재시작 실패 / 기동 직후 크래시" 가설은 반증되었다.
서버는 12.7분째 정상 가동 중이고, 브라우저(msedge)는 실제로 서버에 도달해
TCP 연결을 유지하고 있다. 접속되지 않는 것처럼 보인 실체는 다음 두 가지다.

  (주 원인) 모든 요청이 HTTP Basic Auth 401 을 반환한다.
            브라우저 로그인 대화상자를 취소하거나 자격증명을 잘못 입력하면
            401 JSON 본문(65바이트)만 표시되어 "접속 안 됨"처럼 보인다.
  (부 요인) 서버가 127.0.0.1 에만 바인딩되어 IPv6(::1) 은 연결 거부된다.
            localhost 는 ::1 을 먼저 해석하므로 브라우저가 첫 시도에 실패한 뒤
            127.0.0.1 로 폴백한다. 폴백은 성공하지만 환경에 따라
            ERR_CONNECTION_REFUSED 가 표시될 수 있다.

4. 포그라운드 재실행을 수행하지 않은 사유
================================================================================
지시 3항(포그라운드 재실행으로 에러 캡처)은 의도적으로 수행하지 않았다.

  web_server.py:332 의 _cmn_free_port(8000) 이 기동 직전
  web_server.py:320 에서 포트 8000 점유 프로세스를 taskkill /F 로 강제 종료한다.
  현재 그 점유 프로세스는 정상 가동 중인 서버(PID 24640) 본인이다.

즉 재실행하면 살아있는 정상 서버를 죽이게 되고, 브라우저 세션도 함께 끊긴다.
진단 목적(기동 실패 여부 판별)은 2-1~2-7 로 이미 달성되었으므로,
정상 서버를 파괴하는 절차는 실행하지 않았다.
대신 서버를 건드리지 않는 방식(별도 프로세스 import 검증, HTTP 실측)으로 대체했다.

5. 사용자 조치 안내 (수정은 별도 지침 대기)
================================================================================
  1) 브라우저에서 http://127.0.0.1:8000 접속 시 뜨는 로그인 대화상자에
     등록된 계정(3명 중 하나)의 자격증명을 입력하면 된다.
     자격증명을 모르면 재발급: python scripts/auth/create_user.py
  2) localhost 대신 127.0.0.1 을 사용하면 IPv6 첫 시도 실패를 회피한다.
  3) 브라우저 캐시에 이전 401 이 남아 대화상자가 뜨지 않으면
     시크릿 창 또는 캐시 삭제 후 재시도한다.

  ※ 이번 작업 범위는 진단까지다. 위 항목 중 코드 변경이 필요한 것은 없으며,
     변경이 필요하다고 판단될 경우(예: 정적 파일 무인증 허용, ::1 동시 바인딩)
     사용자 지침을 받은 뒤 별도 작업으로 진행한다.
