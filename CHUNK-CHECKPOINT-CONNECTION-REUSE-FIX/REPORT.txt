1. 무엇이 문제였나
──────────────────────────────────────────────────────────────────────────────
PK_RANGE_CHUNK 실행은 청크가 하나 끝날 때마다 chunk_checkpoint.checkpoint() 를 호출해
진행 상태를 db/chunk_checkpoints.db 에 영속화한다. 이 write 1회의 실측 비용이 8.11 ms 였는데,
선행 진단이 그 내역을 분해한 결과 실제 데이터 갱신(UPDATE+commit)은 1.39 ms 에 불과하고
나머지 6.7 ms(82%)는 _conn() 이 매 호출마다 반복하던 부대작업이었다.

    수정 전 _conn() 이 write 마다 하던 일 (chunk_checkpoint.py:62-74)
      ① sqlite3.connect()            — 파일 열기
      ② PRAGMA journal_mode=WAL      — 저널 모드 질의
      ③ PRAGMA busy_timeout=5000
      ④ CREATE TABLE IF NOT EXISTS   — 이미 있는 테이블을 매번 확인
      ⑤ ALTER TABLE ADD COLUMN × 3   — 매번 실패(중복 컬럼)를 예외로 삼키는 시도
      ⑥ 실제 UPDATE + commit         ← 여기만이 본 목적
      ⑦ close()

즉 "디스크가 비싼 게 아니라 연결 방식이 비쌌다". ④⑤ 는 스키마가 이미 갖춰진 뒤에는
한 번도 아무 일을 하지 않으면서 매 write 마다 비용만 지불하는 순수 낭비였다.


2. 무엇을 바꿨나
──────────────────────────────────────────────────────────────────────────────
저장되는 데이터의 스키마·컬럼·필드·의미는 한 글자도 바꾸지 않았다. 오직 연결 관리 방식만
바꿨으며, 변경은 chunk_checkpoint.py 한 파일에 갇혀 있다(호출측 API 시그니처 불변).

(1) 스키마 DDL 을 DB 파일당 최초 1회만 실행
    모듈 전역 _SCHEMA_READY(set) 에 DDL 적용을 마친 DB 경로를 기록한다. 이미 들어 있는
    경로면 CREATE TABLE / ALTER TABLE 을 아예 건너뛴다. 서버 기동 시 web_server.py 가
    호출하는 mark_interrupted_on_startup() 이 사실상 최초 1회 초기화 지점이 되고, 그
    이후의 모든 청크 write 는 UPDATE + commit 만 수행한다.

(2) connection 을 스레드별로 캐시·재사용
    threading.local() 에 {db_path: connection} 딕셔너리를 두어, 같은 스레드가 같은 DB 경로로
    다시 write 할 때는 이미 열어 둔 connection 을 그대로 쓴다. 캐시 키를 "경로"로 둔 이유는
    테스트가 _DB_PATH 를 임시 경로로 교체하기 때문이다(경로가 바뀌면 자동으로 새 connection).

(3) 테이블 소실 자가복구(_with_conn)
    수정 전 코드는 매 호출 CREATE TABLE IF NOT EXISTS 를 돌렸기 때문에, DB 파일이 외부에서
    삭제되거나 테이블이 사라져도 다음 호출에서 저절로 복구되는 성질이 있었다. DDL 을 1회로
    줄이면 이 내구성이 사라진다. 그래서 모든 DB 접근을 _with_conn(fn) 으로 감싸,
    "no such table" OperationalError 가 나면 캐시 connection 을 버리고 스키마를 다시 만든 뒤
    딱 1회 재시도하도록 했다. 기존과 동일한 복원력을 유지하되 정상 경로에는 비용이 없다.

(4) conn_debug_info() — 진단 전용 helper
    현재 스레드의 재사용 connection 식별자와 스키마 초기화 완료 경로 수를 반환한다.
    "정말 재사용되고 있는가", "스레드끼리 공유하고 있지는 않은가" 를 테스트와 실측 하니스가
    추측이 아니라 값으로 확인하기 위해 추가했다.


3. 스레드 안전성을 어떻게 확보했는가 (지시 2의 핵심)
──────────────────────────────────────────────────────────────────────────────
sqlite3 connection 은 파이썬 기본값 check_same_thread=True 에서 "만든 스레드 밖"에서 쓰면
ProgrammingError 를 낸다. 따라서 "전역 connection 1개를 모든 스레드가 공유" 하는 흔한 방식은
check_same_thread=False 로 이 안전장치를 꺼야만 성립한다. 일괄검증(ValidationScheduler)이
여러 job 을 제한 병렬로 돌리고, 각 job 이 자기 스레드에서 checkpoint 를 쓰는 이 프로젝트에서는
그 방식을 택하지 않았다. 판단 근거는 다음과 같다.

  · 이 모듈의 모든 공개 함수는 이미 모듈 전역 _LOCK(RLock)을 획득한 뒤에만 DB 를 만진다.
    따라서 "전역 1개 공유 + 안전장치 해제" 도 이론적으로는 성립한다. 그러나 그것은
    _LOCK 이 앞으로도 영원히 모든 경로에서 획득된다는 가정에 안전성을 의존하는 구조다.
    누군가 나중에 _LOCK 없는 접근 경로를 하나만 추가해도 조용히 깨진다.
  · 스레드별 캐시는 그 가정이 깨져도 안전하다. 각 스레드는 자기가 만든 connection 만
    만지므로 sqlite3 의 기본 방어(check_same_thread=True)를 그대로 유지한 채 재사용 이득을
    전부 가져간다. 안전성이 "코드 규율"이 아니라 "구조"로 보장된다.
  · 동시 write 의 직렬화는 기존과 완전히 동일하게 유지된다 — 프로세스 안에서는 _LOCK 이,
    프로세스 간(포트 8000/8001 등 같은 파일을 공유하는 경우)에는 WAL + busy_timeout=5000 이
    담당한다. 이번 변경은 이 두 계층을 건드리지 않았다.

실측으로도 확인했다. 4개 스레드가 각자 다른 fingerprint 로 150회씩(총 600회) 동시에 write 하는
시나리오에서 스레드별 connection 식별자가 4개 모두 서로 달랐고(공유 0건), 예외·락 오류 0건,
각 fingerprint 의 최종 값이 정확히 보존됐다(교차 오염 0건).

6. 남은 위험과 한계 (비판적 검토)
──────────────────────────────────────────────────────────────────────────────
· 라이브 DB 미측정. 내부망 단절로 오라클/PG 종단 실측을 못 했다. 다만 이 변경은 Source/Target
  DB 와 무관한 로컬 SQLite 계층이고, 실 엔진 경로 종단([D])까지는 확인했다. 내부망 복구 후
  1M PK_RANGE_CHUNK 라이브 run 으로 한 번 재확인하는 것이 남았다.
· 파일 핸들 상시 점유. connection 을 계속 열어 두므로, 서버 실행 중에는 Windows 에서
  db/chunk_checkpoints.db 파일을 삭제·이동하기 어려워진다(수정 전에는 write 순간에만 열렸다).
  운영상 이 파일을 실행 중에 지울 일은 없으나, 장애 대응으로 파일을 치우려면 서버를 먼저
  내려야 한다는 점이 달라졌다.
· connection 명시적 회수는 없다. job 스레드가 끝나면 threading.local 저장소가 해제되어 GC 가
  connection 을 닫는다. 스레드가 매우 많이 생성·소멸하는 구조라면 핸들이 잠시 쌓일 수 있으나,
  ValidationScheduler 는 상한 병렬이라 실질 위험은 낮다고 판단했다.
· _SCHEMA_READY 는 프로세스 전역이다. 다른 프로세스가 테이블을 지우면 이 프로세스는 그 사실을
  모른다. 그 경우는 (3) 의 "no such table" 자가복구가 받아낸다.
· 효과의 크기를 과장하지 않는다. 1M 검증 1건 기준 청크 write 총합은 20청크 × 8.15 ms = 약
  0.163초에서 20 × 1.38 ms = 약 0.028초로 줄어든다. 전체 실행시간의 0.19% → 0.03% 이므로
  사용자가 체감하는 단축은 사실상 없다. 이번 작업의 실질 가치는 두 가지다 —
  ① 동시 write 지연이 34.5 ms → 5.7 ms 로 줄어 병행 job 이 많을수록 대기 사슬이 짧아진다,
  ② 앞으로 진행률 대시보드가 write 빈도를 늘릴 때 쓸 수 있는 여유(headroom)를 확보했다.
  선행 진단이 1순위로 지목한 tracemalloc 상시 ON 은 이미 별건(c7142be)으로 처리되어 있다.
