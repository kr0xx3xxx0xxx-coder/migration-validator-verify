작업명 : STATS-SCALE-COST-BAND-BENCHMARK-MEASURE
✅ 작업 완료 - STATS-SCALE-COST-BAND-BENCHMARK-MEASURE - 현재 밴드(8/16/24)는 실측 0.16초~82초(×507) 전 구간을 단일 등급 '잠정 중형' 하나로 뭉갠다(측정 41건 전부 동일 등급). 재조정 방향은 "밴드를 12.5/13.25/14.5로 내리고 유효 스캔에 세트 수를 곱한다"(일치율 0%→80%)이며, 반대로 카디널리티를 현행 가중치 그대로 실어 보내면 오히려 나빠진다(순위상관 +0.854→+0.499) — 코드 수정 0건 · 측정 전용

────────────────────────────────────────────────────────────────────────
0. 요약 (결론 먼저)
────────────────────────────────────────────────────────────────────────
실 DB 41케이스(PostgreSQL 36 + Oracle 6, 1만행~5,000만행)를 제품 실제 실행 경로로
측정했다. 결론 4개.

 [결론 1] 현재 밴드는 '변별력 없음'이 아니라 **작동하지 않는다**.
   측정 41건의 cost 는 8.286 ~ 15.684 범위에 전부 들어가고, 밴드가 8/16/24 이므로
   **41건 전부가 '잠정 중형'** 이다. 실제 소요시간은 161ms ~ 82,159ms(×507)로 갈린다.
   현재 밴드로 '소형'이 되려면 7,188행 미만, '대형'은 7,188만행 초과, '초대형'은
   7,188억행 초과여야 한다(로컬·SUM 2개 기준 역산). 실무 규모는 전부 중형 한 칸이다.

 [결론 2] cost 자체는 규모를 잘 따라간다 — 못 쓰는 건 **밴드 경계**다.
   cost_now ↔ log10(소요시간) 순위상관 +0.854(규모만 바꾼 10건 한정 +0.976).
   즉 식이 무의미한 게 아니라, 경계값이 실측과 3~4자리수 어긋나 있다.
   경계만 12.5 / 13.25 / 14.5 로 내리면 시간대 일치율이 0% → 75% 가 된다.

 [결론 3] 카디널리티/예상그룹수를 **현행 가중치 그대로** 실어 보내면 더 나빠진다.
   진단서 §7-P2 제안을 그대로 시뮬레이션한 결과, 순위상관이 +0.854 → +0.499 로
   떨어지고 최적 밴드를 다시 잡아도 일치율이 75% → 60% 로 내려간다.
   근거: 1,000만행에서 카디널리티를 20 → 100,000 으로 바꿔도 실측은 26,459ms →
   29,792ms(+12.6%)뿐인데, cost_card 는 20.897 → 39.181(+18.28 = 3등급 점프)이다.
   **카디널리티 가중치(group 3.0 + cardinality 2.0 = 실질 5.0)가 실측 영향의 수십 배**다.

 [결론 4] 원격 ×1.05 배율은 크기도 방향도 틀렸다.
   같은 형태·같은 규모(100만행)에서 로컬 대비 원격 실측은 ×3.33 / ×9.18 이었다.
   더 중요한 건 형태다 — 원격 초과분은 **비례가 아니라 고정 가산(+2,179ms / +2,465ms)**
   이고, 그 대부분은 접속·세션설정 왕복이다(원격 접속 460ms · 1왕복 71ms vs
   로컬 35ms · 2.5ms). 규모가 커질수록 이 고정분의 비중은 **줄어드는데**, ×1.05 는
   cost 가 클수록 절대 가산이 **커지는** 정반대 특성이다.

 ※ 지침대로 코드는 한 줄도 고치지 않았다. cost 계산식·밴드 상수·_mvBuildStatsScaleProfile·
   판정 로직 전부 무변경, 기존 픽스처 CUD 0건(SELECT 전용).

3. 현재 밴드가 실제 소요시간과 얼마나 안 맞는가
────────────────────────────────────────────────────────────────────────
[3-1] 등급 분포 — 구분이 아예 일어나지 않는다
    잠정 중형 : 40건(성공분 전부) · 실측 161ms ~ 82,159ms · **폭 ×507**
    잠정 소형 / 대형 / 초대형 : **0건**
  등급 표시는 41번 모두 같은 문자열을 내보냈고, 그 안에 0.16초짜리와 82초짜리가
  같이 들어 있다. 사용자가 이 배지에서 얻는 정보량은 사실상 0이다.

[3-2] 현재 밴드를 '행수'로 역산한 값 (화면이 보내는 프로파일 기준)
    로컬 · SUM 2개 : 중형 진입 7,188행 / 대형 71,880,919행 / 초대형 718,809,194,372행
    원격 · SUM 2개 : 중형 진입 4,636행 / 대형 29,900,134행 / 초대형 192,839,926,338행
    로컬 · SUM 0개 : 중형 진입 9,994행 / 대형 99,942,451행 / 초대형 999,424,519,379행
  (진단서 §5 의 역산과 일치 — 재현 확인)
  '중형' 한 칸이 7천행 ~ 7천만행, 즉 4자리수를 덮는다. 실측으로 보면 그 구간 안에서
  소요시간은 0.16초에서 60초 이상까지 벌어진다.

[3-3] 그런데 cost 식 자체는 규모를 잘 따라간다
    cost_now ↔ log10(실측 ms)  Spearman +0.854 / Pearson +0.836
    규모만 바꾼 10건 한정      Spearman +0.976
  → 문제는 "cost 가 엉터리"가 아니라 "경계가 실측과 3~4자리수 어긋나 있다"이다.
    이 구분이 중요하다 — 식을 갈아엎을 게 아니라 경계를 다시 자르는 게 1순위다.

[3-4] 다만 같은 cost 안의 편차도 작지 않다(경계 재조정만으로 100%는 불가)
    cost 10.3 (4건) :    161 ~    304 ms  ×2
    cost 12.0 (5건) :    266 ~    909 ms  ×3
    cost 12.3 (7건) :    339 ~  1,491 ms  ×4
    cost 14.3 (8건) : 22,849 ~ 82,159 ms  ×4
  같은 cost 에서 ×2~4 편차가 남는다. 원인은 §3-5·§3-6.

[3-5] cost 가 못 보는 요인 ① — 세트 수(가장 큰 누락)
  GROUP BY 3개 선택은 제품에서 **단일축 3세트 순차 실행**이다. 실측은 정확히 3배다.
      1,000만행 1세트 27,342ms × 3 = 82,028ms  ↔  실제 3세트 82,159ms (오차 +0.2%)
        100만행 1세트    379ms × 3 =  1,137ms  ↔  실제 3세트  1,336ms (오차 +17.6%)
  그런데 cost_now 는 1세트(14.000)와 3세트(14.286)가 사실상 같다. group_axis_count 는
  프로파일로 **전달되고 있는데도** cost 식이 쓰지 않는다(basis 기록 전용).
  → 82초짜리(초대형)를 24초짜리(대형)와 구분할 수단이 지금 없다.

[3-6] cost 가 못 보는 요인 ② — 실행계획(행당 작업량)
  같은 1,000만행인데 쿼리 형태만으로 ×10 이 갈린다.
      COUNT(*)만            2,537ms   (인덱스 온리 스캔 + 병렬 집계)
      COUNT+SUM 2개        23,501ms   (×9.3)
      GROUP BY 1축만       27,342ms   (×10.8)
  cost 는 SUM 2개에 +0.286 만 준다(가중치 sum=0.6). 실측 영향은 ×9.3 이다.
  이건 밴드 재조정으로 해결되지 않는 구조적 한계이며, §6-4 에서 다룬다.

[3-7] cost 가 못 보는 요인 ③ — 환경(DBMS·호스트)
      cost 15.241 · PG 3,000만행   → 60,753ms (초대형)
      cost 15.684 · 오라클 5,000만행 → 12,390ms (대형)
  **cost 가 더 높은 쪽이 5배 빠르다.** 같은 밴드를 전 방언·전 사이트에 고정 적용하면
  이런 역전이 계속 나온다. PG만으로 밴드를 최적화하면 일치율 79.4%, 오라클을 섞으면
  75.0% 로 내려간다(§6-1).

[3-8] 규모-시간 관계는 순수 선형이 아니다(밴드 설계 시 유의)
  A 사다리의 처리량(행/초, 양측 합산 기준):
      1만행 36,818 · 10만행 475,737 · 100만행 1,174,950 · 300만행 1,419,379
      1,000만행 410,740 · 3,000만행 493,801
  100만~300만행에서 최고 처리량을 찍고 1,000만행에서 3분의 1로 떨어진다
  (버퍼 캐시 경계). 즉 100만→1,000만은 행수 ×10 인데 시간은 ×28.6 이다.
  → 밴드 경계를 100만~1,000만 사이에 두면 환경 편차에 가장 민감해진다.

────────────────────────────────────────────────────────────────────────
4. 카디널리티 / 예상그룹수 반영 시뮬레이션 (진단서 §7-P2 검증)
────────────────────────────────────────────────────────────────────────
진단서는 "값을 실어 보내기만 하면 등급이 실제 부하를 반영한다"(§6-1)고 봤다.
실측으로 검증한 결과 **그 전제는 성립하지 않는다.**

[4-1] 카디널리티는 실측 소요시간을 거의 바꾸지 않는다
  1,000만행 고정 · GROUP BY 1축 · 축만 교체:
      카디널리티      20 :  26,459ms   (기준)
      카디널리티      50 :  27,090ms   (+2.4%)
      카디널리티     730 :  26,832ms   (+1.4%)
      카디널리티 100,000 :  29,791ms   (+12.6%)
  카디널리티가 5,000배 늘어도 실측은 +12.6% 다. 스캔량이 같으면 집계 비용도 거의 같다.

[4-2] 그런데 cost_card 는 3등급을 건너뛴다
      카디널리티      20 → cost 20.897 (대형)
      카디널리티 100,000 → cost 39.181 (초대형)   ← +18.28
  group 3.0·log10 + cardinality 2.0·log10 = 실질 5.0·log10(카디널리티) 가 붙는다.
  실측 영향(+12.6% = log10 으로 +0.05)의 **약 360배**를 가중하는 셈이다.

[4-3] 결과: 상관과 일치율이 모두 나빠진다
      순위상관(Spearman)   cost_now +0.854  →  cost_card +0.499
      Pearson              cost_now +0.836  →  cost_card +0.373
      최적 밴드 재조정 후 일치율  75.0%  →  60.0%
  최악 오분류 예:
      C-100000-reg_dt  실측 191ms(소형)      → cost_card 24.606 → '잠정 초대형'
      B-10000000-g0s2  실측 23,501ms(대형)   → cost_card 14.286 → '잠정 소형'(경계 19.0 기준)

[4-4] 카디널리티가 유효한 구간은 따로 있다 — '그룹수/스캔량 비율'
  같은 카디널리티 100,000 이라도 규모에 따라 영향이 다르다.
      10만행 · 100,000그룹(= 행마다 그룹 1개) :   303ms → 2,040ms  (×6.7)
    1,000만행 · 100,000그룹(= 100행당 그룹 1개) : 26,459ms → 29,791ms (×1.13)
  즉 부담을 만드는 건 카디널리티의 절대값이 아니라 **집계 압축률(groups/scan)** 과
  **결과 그룹의 절대 개수(앱 비교 비용)** 다. 앱 구간 실측이 이를 뒷받침한다 —
  그룹 20개면 앱 79~170ms 로 평평하고, 그룹 100,000개면 1,295~1,603ms 로 늘어난다
  (그룹당 약 13~16µs). 반면 DB 구간은 스캔량에 비례한다.

[4-5] 그래서 P2 를 지금 적용하면 안 된다
  진단서 §7-P2 는 "밴드 재조정과 함께 해야 한다"고 조건을 달았는데, 실측 결론은 더
  강하다 — **밴드를 어떻게 다시 잘라도 현행 가중치로는 지금보다 나빠진다(75%→60%).**
  카디널리티를 반영하려면 밴드가 아니라 **가중치를 먼저 낮춰야** 한다(§6-3).

────────────────────────────────────────────────────────────────────────
5. 로컬 / 원격 ×1.05 배율 타당성
────────────────────────────────────────────────────────────────────────
[5-1] 고정 오버헤드 실측(접속 3회 · SELECT 1 왕복 60회)
                       접속 1회      1왕복
      로컬(내부망)      34.5 ms      2.51 ms
      원격(Neon src)   472.7 ms     71.58 ms   (×13.7 / ×28.5)
      원격(Neon tgt)   457.3 ms     71.00 ms

[5-2] 같은 형태·같은 규모(100만행) 로컬 ↔ 원격 대조
      GB1 + SUM2   로컬 1,056ms → 원격 3,520ms   ×3.33   (+2,465ms)
      COUNT-only   로컬   266ms → 원격 2,445ms   ×9.18   (+2,179ms)
      cost 배율은 두 경우 모두 ×1.050
  → 배율로 보면 ×3.33 / ×9.18 로 제각각인데, **가산으로 보면 +2,465 / +2,179ms 로
    거의 같다.** 원격 초과분은 비례가 아니라 고정 가산이다.

[5-3] 가산분의 정체 — 접속 + 세션설정 왕복
  read-only 실행 1회는 접속 1 + (SET TRANSACTION READ ONLY / SET LOCAL
  statement_timeout / SHOW transaction_read_only / 본쿼리 / ROLLBACK) 약 5왕복이고,
  원본·목적지 두 번 일어난다.
      예상 가산 = 2 × (472.7 + 5 × 71.6) = 2 × 830.7 ≈ 1,661ms
      실측 가산 = 2,179 ~ 2,465ms  (TLS·드라이버 오버헤드 포함하면 같은 자릿수)
  실제로 원격 케이스의 '앱/네트워크' 구간은 1,764 ~ 3,237ms 인데 로컬은 93 ~ 341ms 다.
  DB 구간(280 ~ 3,871ms)이 아니라 이 구간이 차이를 만든다.

[5-4] 판정: ×1.05 는 **크기도 방향도 근거가 없다**
  · 크기: 100만행 COUNT-only 에서 실제 영향은 ×9.18(= log10 으로 +0.96)인데
          cost 는 ×1.05(= +0.6 point)를 준다. 규모가 작을수록 과소평가다.
  · 방향: 고정 가산이므로 **규모가 커질수록 상대 영향은 줄어야 한다**
          (3,000만행 60초 작업에 2.2초는 +3.7%). 그런데 ×1.05 는 cost 에 비례하므로
          cost 12 이면 +0.60, cost 24 이면 +1.20 으로 **큰 작업일수록 더 많이** 가산한다.
          실측과 정확히 반대다.
  · 부작용: 진단서 §5 가 지적한 "접속 위치만으로 등급 경계가 7,188↔4,636행,
          7,188만↔2,990만행으로 이동" 이 이 비례 방식 때문이다.
  권장(구현 안 함): 배율 대신 **고정 가산 항**으로 바꾼다.
          예) 예상 소요시간 모형에 remote_overhead_ms ≈ 2 × (접속 + 5 × RTT) 를 더하고,
              그 값은 접속 테스트에서 이미 측정 가능한 RTT 로 산출한다(추가 왕복 0회).

────────────────────────────────────────────────────────────────────────
6. 밴드 재조정 제안 (데이터 기반 · 이번 지침 범위상 구현하지 않음)
────────────────────────────────────────────────────────────────────────
목표 시간대(운영 근거를 붙인 정의):
    소형   < 1초      체감 즉시 — 진행 표시 불필요
    중형   1 ~ 10초   대기 인지 구간
    대형   10 ~ 60초  진행 표시·취소 수단이 필요한 구간
    초대형 >= 60초    제품 기본 실행 상한(EXECUTE_STATEMENT_TIMEOUT_MS=60000) 도달 위험
  60초 경계는 임의값이 아니라 제품이 이미 갖고 있는 상한이라 등급의 의미가 자명해진다.

[6-1] 안 ① (최소 변경 · 권장 1순위) — 밴드만 다시 자른다
      _PROVISIONAL_BANDS = [(8.0, 소형), (16.0, 중형), (24.0, 대형)]
        →  [(12.5, 소형), (13.25, 중형), (14.5, 대형)]
      시간대 일치율 0% → **75.0%** (PG만이면 79.4%)
      행수로 환산(로컬·SUM2): 중형 진입 1,278,243행 / 대형 3,031,193행 / 초대형 12,782,435행
      장점: 계산식·프로파일·전송 필드 전부 무변경. 상수 3개만 교체.
      한계: §3-5·§3-6·§3-7 요인(세트 수·실행계획·환경)은 여전히 못 본다.

[6-2] 안 ② (권장 1순위와 함께) — 유효 스캔에 세트 수를 곱한다
      estimated_scan_rows_effective = estimated_scan_rows × max(1, group_axis_count)
      근거: 다중 GROUP BY 는 단일축 N세트 **순차** 실행이고 실측이 정확히 N배다(§3-5).
      필요한 입력은 이미 프로파일로 오고 있다(group_axis_count) — 추가 전송·왕복 0회.
      같은 밴드(12.5 / 13.25 / 14.5)에서 일치율 75.0% → **80.0%**,
      82초짜리 3세트 케이스를 '초대형'으로 잡아낸다(현재는 '중형').

[6-3] 안 ③ — 카디널리티를 반영하려면 가중치를 먼저 낮춘다
      지금: group 3.0 · cardinality 2.0 (실질 5.0 × log10(카디널리티))
      실측 회귀에서 얻은 상대 비중:
          log10(소요ms) = 0.819·log10(scan) + 0.189·log10(groups+1)
                        + 0.353·log10(sets) − 2.020        (R² = 0.766, n=40)
      scan : groups = 0.819 : 0.189 ≈ **4.3 : 1**. 현행은 scan 2.0 : group 5.0 = 1 : 2.5
      로 **약 11배 뒤집혀 있다**. 현행 scan 가중치 2.0 을 유지한다면 카디널리티 계열
      가중치는 합쳐서 **0.46 수준**이 실측 비례에 맞는다(현행 5.0).
      → P2(카디널리티 전송)는 이 가중치 조정과 **같은 변경으로 묶어야** 한다.
        단독 적용은 §4-3 대로 지금보다 나쁘다.

[6-4] 안 ④ (구조적 · 별도 지침 권장) — cost 를 '예상 소요시간의 log10' 으로 재정의
      cost ≡ log10(예상 소요 ms) 로 정의하면 밴드가 자명해진다:
          1초 = 3.00 · 10초 = 4.00 · 60초 = 4.78
      밴드가 더 이상 '근거 없는 상수'가 아니라 시간 경계의 로그값 그 자체가 되므로
      '잠정' 접두를 뗄 근거도 이때 생긴다.
      다만 이번 회귀식을 그대로 쓰면 밴드 일치율은 62.5% 로 안 ②(80.0%)보다 낮다.
      이유는 환경 상수(DBMS·호스트·캐시 상태)가 잔차의 주범이기 때문이다(§3-7).
      → 이 방향으로 가려면 환경 상수를 **사이트에서 실측해 채우는** 배선이 필요하다.
        마침 `StrategyProfile.recent_throughput_rows_per_sec` 필드가 이미 존재하고
        routes/strategy_route.py:68 에서 전달까지 되는데 **cost 식이 쓰지 않는다**
        (저장소 전역 13개 참조 중 계산에 쓰는 곳 0개). 이 훅을 살리는 것이
        환경 편차를 흡수하는 가장 자연스러운 경로다.

[6-5] 권장 우선순위
      1) 안 ① + 안 ② 를 한 번에 (상수 3개 + 곱셈 1개, 회귀 위험 최소, 0% → 80%)
      2) 원격 ×1.05 → 고정 가산으로 교체 (§5-4)
      3) 안 ③ (카디널리티 전송 + 가중치 재조정) — 반드시 묶어서
      4) 안 ④ (throughput 실측 배선) — 별도 지침
      ※ 1)~3) 을 하기 전까지 '잠정' 접두는 유지하는 것이 정직하다(진단서 §4-1 과 동일 결론).

────────────────────────────────────────────────────────────────────────
7. 부수 발견 (이번 범위 밖 · 보고만)
────────────────────────────────────────────────────────────────────────
[7-1] 결과 그룹 상한 초과는 **시간을 다 쓴 뒤** 차단된다.
  C-10000000-id(1,000만 그룹)는 56,255ms 를 소모하고 나서 "허용 한도 100,000개 초과"로
  BLOCKED 됐다. 사전 차단이 아니라 사후 차단이라 사용자는 56초를 기다린 뒤 아무 결과도
  못 받는다. 그런데 등급은 '잠정 중형'(cost 14.181)이라 사전 경고도 없다.
  카디널리티를 프로파일에 실으면(§6-3) 이 케이스만은 사전 예측이 가능해진다.

[7-2] BLOCKED 응답에는 query_timing 이 없다.
  같은 케이스의 DB 구간이 0ms 로 기록됐다(앱 구간에 56초가 통째로 잡힘). 성공 경로에만
  query_timing 을 채우기 때문이다. 성능 회귀를 이 필드로 추적하면 차단 케이스가 통계에서
  사라진다.

[7-3] 실행이 한 번 무기한 정지했다(재현 1/약 90회).
  C-100000-amt(10만 그룹) 실행 중 13분 이상 진행이 멈췄다. 그때 서버측
  pg_stat_activity 는 해당 세션이 `idle in transaction / ClientRead`(= 서버는 결과를
  다 보냈고 클라이언트 응답 대기)였고, 클라이언트 프로세스는 CPU 0.64초 고정 · 메모리
  57MB 고정 · 목적지 연결은 아직 열리지도 않은 상태였다. 즉 **원본 fetch 반환과 목적지
  fetch 시작 사이에서 CPU 를 전혀 쓰지 않고 정지**했다. 프로세스를 죽이고 같은 케이스를
  단독 재실행하니 2,493ms 에 정상 완료했고, 이후 전체 재측정에서도 재발하지 않았다.
  원인 미확정 — 재발 대비로 측정 하니스에 faulthandler 주기 덤프를 걸어 두었다.
  (참고: 그때 남아 있던 다른 유휴 연결 1개가 `SET statement_timeout = 0` 상태로
   25분간 idle 이었다 — 연결 반납 경로도 함께 볼 필요가 있다.)

[7-4] 4단계 화면 SQL(조합)과 실제 실행(N세트)의 비용 차이가 규모에 따라 역전된다.
      100만행  : 3세트 1,336ms  vs 조합 1,491ms  → 조합이 12% 느리다
    1,000만행  : 3세트 82,159ms vs 조합 28,378ms → **3세트가 2.9배 느리다**
  화면은 조합 SQL 을 보여주는데 실행은 3세트다(기존에 알려진 표시 불일치). 규모가 커지면
