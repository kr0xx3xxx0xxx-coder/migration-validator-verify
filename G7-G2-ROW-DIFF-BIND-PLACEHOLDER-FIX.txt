✅ 작업 완료 - row_diff.py 오라클 바인드 표기를 이름 바인드(:K0..)로 교체해 DPY-4009 해소, 실 오라클↔오라클 4케이스 전부 정답 일치 확인

[원인 재확인]
services/diagnosis/row_diff.py:76,81(수정 전) 의 exp.Placeholder() 는 sqlglot 렌더 시
  - postgres 방언 → '%s' (psycopg2 호환, 기존 _row_fetch_fn 의 list 위치 바인딩과 정상 동작)
  - oracle   방언 → '?'  (python-oracledb 는 위치 바인드 '?' 를 지원하지 않음 → DPY-4009)
실측(1): sqlglot 으로 ':1'(오라클 숫자 위치 바인드) 파싱 시도 → ParseError(EQ.expression 누락).
  즉 '?' 를 ':1' 로만 바꾸면 sqlglot 이 oracle 방언에서 파싱조차 못해 readonly_sql_guard(AST 검사)가
  UNPARSEABLE 로 실행 자체를 차단한다 — DPY-4009 보다 더 앞단에서 막히는 별개 실패 모드.
실측(2): 오라클 실접속(Oracle_asis)에서 이름 바인드(':K0') + list 위치 인자 조합은 정상 동작,
  '?' + list 조합은 DPY-4009 재현. ':1'/':2' 숫자 위치 바인드는 DB 레벨에서는 되지만 위 sqlglot 이슈로
  readonly_sql_guard 를 통과하는 실행 경로에서는 못 쓴다.

[exact_diff 참고 패턴]
services/exact_diff/dialects/oracle.py:64-70 oracle_key_bind_names() 의 주석이 정확히 같은 원인을
먼저 겪고 남긴 근거: "위치 표기(:1) 를 쓰지 않는 이유: 실행 전 readonly 가드가 sqlglot 으로 AST 를
검사하는데 sqlglot 이 숫자 placeholder(:1) 를 파싱하지 못해 UNPARSEABLE 로 차단된다. 이름 표기(:K0)
는 정상 파싱되며 oracledb 는 dict 바인딩으로 받는다." → 이 이름 바인드 규칙을 row_diff.py 에 그대로
재사용했다(신규 표기 발명 안 함). 단, exact_diff 의 detail_fetch_sql 은 오라클 dict 바인딩을 쓰지만
row_diff 의 fetch 경로(_row_fetch_fn → cmn_db_fetch_select_readonly)는 params 를 항상
list(params or []) 로 넘기므로(라우트 파일은 수정 범위 밖), 오라클 실접속으로 "서로 다른 이름의
바인드는 list 위치 인자로도 정상 바인딩된다"는 점을 별도 실측해 이 제약 안에서 해법을 확정했다.
