0. 요약
════════════════════════════════════════════════════════════════════════
- 이 앱에는 "테이블 크기/규모"를 등급 문자열로 표현하는 독립 분류 체계가 **7개**
  존재한다(임계 플래그만 내는 체계 1개 포함 시 8개). 그중 2개(D·H)는
  config/size_threshold_registry.py 에 등록조차 안 된 하드코딩 체계다.
- `stats_scale_class` 가 원래 참조하려던 체계는 그중 **H(통계검증 cost 등급,
  stats_strategy_planner._provisional_grade)** 로 특정된다.
- 그런데 H는 이미 `provisional_grade` 라는 **다른 이름·다른 전달 경로**로 구현되어,
  같은 함수(_mvStatsScaleText) 안에서 `stats_scale_class` 보다 **상위 우선순위 분기**를
  차지하고 있다. 즉 예약 필드가 방치된 것이 아니라 **이미 대체 실현**됐다.
- 따라서 재사용 가능한 체계가 있느냐 하면 "있다"가 아니라 "**이미 그 체계가 그 자리를
  차지했다**" 가 정확한 답이다. 죽은 필드를 살리는 것은 같은 목적 로직의 이중화다.
- 결론: **제거 권장**(F34 → 제거 방향). 단 이번 지침대로 코드는 건드리지 않았다.

판정 — **이번 "통계검증 규모"와 목적이 다르다(겹치지 않는다).**
  근거 3가지:
   (1) 입력 축이 다르다. 이 체계는 `src/tgt COUNT 중 큰 값(행 수)` 단독이다.
       통계검증 규모는 설계 주석(ui/grid_helpers.py:939-941)이 명시적으로
       "원본 COUNT 가 아니라 GROUP BY·SUM·스캔량·인덱스 등 종합 실행부하" 이며
       "COUNT 만으로 등급 결정 금지" 라고 못박았다.
   (2) 출력 용도가 다르다. 이 체계의 등급은 **ROW_DIFF 허용/금지 라우팅**
       (row_diff_allowed_for_size — SMALL/MEDIUM 만 허용)에 쓰인다. 즉 불일치
       발생 후 "행 단위 비교를 해도 되는가" 를 정하는 진단 단계 게이트다.
       통계검증 규모는 **3단계에서 통계검증 실행 전 부하 예고**를 표시한다.
   (3) 산정 시점이 다르다. 이 체계는 COUNT 비교 결과 확보 후(진단), 통계검증
       규모는 후보 선정 직후(GROUP BY/SUM 확정 시점)다.

  ※ 어휘만은 유일하게 겹친다 — SMALL/MEDIUM/LARGE/**XLARGE** 4단은 이 체계와
    H 체계에만 있다(B는 HUGE, C·D는 VERY_LARGE, E는 huge). 이 어휘 일치가
    §4의 설계 의도 추정에서 근거로 쓰인다.

3. 관찰 — 통합이 이미 한 번 기각된 이력
════════════════════════════════════════════════════════════════════════
config/size_threshold_registry.py 상단 주석(7~12행)에 다음이 명시돼 있다:

  "이 값들은 서로 다른 목적의 독립 임계값이며 의도적으로 일치시키지 않았다.
   값이 우연히 같아 보여도 서로 다른 소비처의 서로 다른 판정에 쓰이므로
   하나의 통합 변수로 합치지 않는다. 정책 정렬(등급 통합 = get_table_size_tier
   단일 분류기)은 별도 논의 대상이며, SIZE-TIER-UNIFICATION-IMPACT-DIAGNOSE 에서
   통합 시 실제 동작이 바뀌는 지점(HIGH 3곳 포함)이 확인되었으므로 이 파일은
   '값 이동(단일 출처화)' 만 수행한다 — 어떤 값도 변경하지 않는다."

즉 "같은 목적의 로직을 여러 곳에 만들지 않기" 원칙은 이 프로젝트에서 이미 적용됐고,
그 결과가 **"값은 단일 출처로 모으되 분류기는 합치지 않는다"** 였다. 7개 체계가 남아
있는 것은 방치가 아니라 **의도된 상태**다. 본 조사도 그 판단을 뒤집을 근거를 찾지
못했다 — 각 체계는 입력 축(행수 / 바이트 / cost)과 출력 용도(라우팅 / cap / chunk /
표시)가 실제로 다르다.

다만 §2 표에서 확인되듯 **D와 H 두 체계는 registry 단일 출처화에서 누락**돼 있다
(각각 파일 내 하드코딩). F32 대응 시 H를 registry 로 옮기라는 백로그 권고가 이미
있으므로(F32 대응 방향), D도 같이 검토 대상이 될 수 있다 — 본 조사의 부수 발견이며
이번 범위 밖이다.

4. 조사 4 — stats_scale_class 의 설계 의도 추정(근거)
════════════════════════════════════════════════════════════════════════
추정 결론: **H(통계검증 cost 등급 체계)를 참조하려고 미리 뚫어 둔 자리표시자**이며,
그 체계는 이후 `provisional_grade` 라는 다른 이름으로 실현됐다.

근거 4가지:

[근거 1] 도입 커밋이 UI 단독 커밋이다 — 처음부터 생산자가 없었다.
  커밋 fa4f147 (2026-07-05)
    "feat(ui): [통합지침 §1] '원본 테이블 크기'→'통계검증 규모' 등급 표시(COUNT 분리)"
  변경 파일: ui/grid_helpers.py + 테스트 4개 + 스크린샷 1매.
  **서버/서비스 코드 변경 0건.** 즉 필드가 나중에 죽은 것이 아니라, 태어날 때부터
  "생산자는 나중에" 를 전제로 소비처만 먼저 만든 필드다.
  커밋 메시지 자체가 "실측/계획기 확정 전(§3) 기본값 '산정 전'" 이라고 적어 두었다.

[근거 2] 코드 주석이 참조 대상을 지목한다.
  ui/grid_helpers.py:942
    "profile.stats_scale_class(**향후 계획기 산출**)가 있을 때만 등급 매핑
     (임계치 하드코딩 없음 §1·§3)"
  - "향후 계획기" = 당시 미구현이던 통계 전략 계획기. 실제로 그 계획기
    (services/strategy/stats_strategy_planner.py)가 이후 Phase 4-A 에서 만들어졌다.
  - "임계치 하드코딩 없음" 제약 → UI 는 임계값을 가질 수 없으므로 **서버가 등급
    문자열을 통째로 내려주는 형태**여야 한다. stats_scale_class 는 그 수신 슬롯이다.

[근거 3] 값 어휘가 H·A 계열이다.
  소비 코드가 매핑하는 값은 SMALL/MEDIUM/LARGE/**XLARGE** 4단이다.
  XLARGE 어휘를 쓰는 체계는 A(size_strategy)와 H(strategy_models.GRADE_XLARGE)뿐이며,
  B는 HUGE·C/D는 VERY_LARGE·E는 huge 로 다르다.
  이 중 A는 같은 주석이 "COUNT 만으로 등급 결정 금지" 로 **명시적으로 배제**한 축이다.
  → 소거법상 남는 것은 H.

[근거 4] 실제로 H가 그 자리를 가져갔다 — 상위 우선순위로.
  ui/grid_helpers.py:945-948 (Phase4-D5 에서 **stats_scale_class 분기보다 위에** 삽입)
    var sp = window._mvStrategyPlan;
    if (sp && sp.provisional_grade) return sp.provisional_grade;   ← H 체계
    var c = String(p.stats_scale_class || '')...                    ← 죽은 폴백
  전달 경로: /strategy/plan (routes/strategy_route.py:90) → provisional_grade
            → window._mvStrategyPlan (grid_helpers.py:1206) → 표시.
  즉 "향후 계획기 산출" 은 **약속대로 구현됐고**, 다만 필드명이 stats_scale_class 가
  아니라 provisional_grade 였으며 전달 경로도 analyze 프로파일이 아니라 별도 API 였다.
  그 결과 원래 슬롯만 빈 채로 남았다.

[5-1] 재사용 후보 평가

  후보 ① H(provisional_grade) 를 stats_scale_class 에도 채운다
    → **불가/무의미.** 같은 함수에서 H가 이미 상위 분기를 차지한다. 같은 값을 두
      필드로 내려보내는 것은 그 자체가 "같은 목적 로직 이중화" 다. 폴백이 트리거되는
      유일한 조건은 `window._mvStrategyPlan` 부재인데, 그 상황은 /strategy/plan 을
      아직 못 부른 시점(COUNT 전)이므로 채울 값도 없다.

  후보 ② D(table_load_profile_service.table_size_class) 재사용
    → **배선 비용은 0에 가깝지만 부적절.** UI 가 읽는 프로파일 객체가 바로 D의 출력
      (analyze 응답 table_load_profiles.source)이라, 키 이름만 바꿔 읽으면 즉시 값이
      들어온다. 그러나 4가지 결함이 있다:
        (a) 축 위배 — D는 **물리 바이트** 단독. 설계 주석이 금지한 "규모를 단일 물리
            지표로 결정" 과 같은 결함이며(COUNT 금지의 취지 그대로), GROUP BY·SUM 을
            전혀 반영하지 않는다.
        (b) DB 커버리지 1/4 — table_load_profile_service 는 **PostgreSQL 만** 실제
            수집하고 비-PG 는 no-op(UNSUPPORTED_DBMS→UNKNOWN)다. 지원 DB 4종
            (oracle/mysql/postgresql/mssql) 중 3종에서 폴백이 여전히 죽는다.
        (c) 어휘 불일치 — D는 VERY_LARGE, 소비처는 XLARGE 를 기대. 변환 코드가 새로
            필요하다(= UI 에 매핑 로직 추가, "임계치/판정 UI 반입 금지" 취지에 역행).
        (d) 표시 흔들림 — 폴백이 뜨는 시점(COUNT 전)에 물리크기 기준 '중형' 을 보여
            줬다가, 계획 생성 후 H 기준 '잠정 초대형' 으로 바뀌면 사용자가 등급이
            요동치는 것으로 인식한다. 현재의 '산정 전' 표기가 오히려 정직하다.

  후보 ③ A/B/C/E/F(행수 기반) 재사용
    → **설계상 금지.** 전부 COUNT/행수 단독 축이며, 이 화면은 COUNT 기반 등급 표시를
      제거하려고 만들어진 것이다(커밋 fa4f147 제목 자체가 "COUNT 분리").
      C(execution_profile_service)는 라벨이 소형/중형/대형/초대형으로 **문자열까지
      동일**해 가장 헷갈리는 후보지만, 입력이 COUNT 실측 건수이므로 같은 이유로 배제.
      추가로 C는 일괄검증 저장 경로 산출물이라 개별검증 3단계 시점에 존재하지 않는다.

[5-2] 권고 — **제거**(F34 대응 방향: "죽은 필드 제거")

  이유 요약:
   1. 참조 대상 체계(H)가 이미 다른 필드로 실현되어 폴백의 존재 이유가 소멸했다.
   2. 남은 재사용 후보(D)는 축 위배 + DB 커버리지 1/4 + 어휘 변환 필요 + 표시 흔들림
      으로, "저비용으로 죽은 폴백을 살린다" 는 전제가 성립하지 않는다.
   3. 살리는 쪽을 택하면 등급 산정 로직이 서버(H)와 클라이언트 폴백 두 곳으로 갈라져,
      §3의 "분류기를 늘리지 않는다" 원칙에 정면으로 어긋난다.
   4. 유지 비용은 낮지만 0이 아니다 — 이 필드가 있는 한 코드를 읽는 사람은 매번
      "생산자가 어디 있나" 를 다시 찾게 된다(F34 자체가 그 비용의 증거다).

  제거 시 예상 범위(참고 — 이번에 실행하지 않음):
    ui/grid_helpers.py:938-956 중 949-953(5줄) + 942 주석 문구 정리
    tests/test_stats_result_full.py 및 관련 소스검사 테스트가 이 문자열을 검사하는지
    사전 확인 필요(현재 확인된 검사 대상은 provisional_grade 쪽이며, 소스 마커 검사
    관행이 있는 저장소이므로 제거 전 grep 재확인이 반드시 선행돼야 한다).
    ※ 회귀 위험 자체는 낮다 — 제거해도 폴백은 지금과 동일하게 '산정 전' 으로 떨어진다
      (생산자가 없으므로 현재도 항상 그 경로다). **동작 변화 0** 인 순수 정리다.

[5-3] 대안(제거를 택하지 않을 경우)
  제거 대신 **주석만 갱신**하는 선택지도 있다 — 코드는 그대로 두고 942행 주석을
  "이 폴백은 provisional_grade 로 대체됨(생산자 없음, 의도적 무동작)" 로 바꿔 다음
  독자가 다시 조사하지 않게 하는 방식이다. 제거보다 안전하지만 죽은 코드는 남는다.
  본 조사는 §5-2(제거)를 1순위, 이 방식을 2순위로 권고한다.

[5-4] 함께 판단해야 할 항목
  `stats_scale_estimable` 도 동일하게 생산자가 없다(§2). 다만 소비처가 2곳이고 그중
  tabler_renderer.py:28134 는 3단계 타일 상태열('산정 불가')을 만든다. 제거를 진행할

  한 지침에서 함께 처리**할 것을 권고한다.

6. 조사 6 — F32(cost 밴드 재조정)와의 연계
════════════════════════════════════════════════════════════════════════
연계된다. 다만 방향은 "F32 결과를 폴백에도 반영" 이 아니라 **"제거해야 F32 가 깨끗
해진다"** 쪽이다.

  (1) F32 는 H 체계의 밴드(8/16/24)를 벤치마크로 교체하는 작업이다. 그 결과물은
      provisional_grade 로 표시된다 — 즉 **F32 의 산출물이 도달하는 표시 경로와
      stats_scale_class 의 표시 경로가 동일**하다(같은 함수, 같은 셀).
  (2) 만약 F34 를 '구현' 으로 처리하면, 밴드가 서버(H)와 폴백 두 곳에 존재하게 된다.
      F32 의 명시적 권고는 "밴드를 config/size_threshold_registry.py 처럼 단일 출처로
      이전" 인데, 폴백 필드는 그 단일 출처를 우회하는 **두 번째 경로**가 되어 F32 의
      목표와 충돌한다.
  (3) 시기 문제도 있다. F31(카디널리티·그룹 수 전달)이 적용되면 등급이 크게 이동
      하고(백로그 실측: 중형 → 초대형), F32 로 밴드를 다시 옮긴다. 이 두 작업 전에
      폴백에 어떤 값을 넣어도 곧 어긋난다.
  (4) 반대로 **제거를 먼저 하면 F32 는 단일 경로만 손보면 된다.** 따라서 권고 순서는
      **F34(제거) → F31 → F32** 이며, F34 는 F32 의 선행 정리 작업으로 두는 것이
      비용이 가장 낮다(F34 는 동작 변화 0이므로 언제 해도 안전하다).
  (5) 부수: F32 로 밴드를 registry 로 옮길 때, §3에서 확인된 **또 하나의 미등록 체계
      D(table_load_profile_service 의 50MB/1GB/10GB)** 도 같은 기준으로 등록할지
      함께 판단하면 registry 의 "리터럴 단일 출처" 선언이 실제로 완결된다.
