4. 실측 [2] — 오라클 실 DB /agg-diff/prepare (핵심 재현)
────────────────────────────────────────────────────────────────────────────
환경: 내부망 오라클 asis 192.168.0.151:1523 / tobe 192.168.0.151:1524, 스키마 NXDNP
      픽스처 NXDNP.MV_COMBO_SRC(1,200행) → NXDNP.MV_COMBO_TGT(1,200행, PK=ID)
      접속정보는 UI 프리셋(db_presets_src/tgt.json)에서 로드 — 비밀번호는 출력·기록하지 않음.
방식: DB 로 나가는 SELECT 를 기록만 하는 wrapper 로 감싸고(실행은 그대로 통과),
      운영 함수 _pk_resolve 와 라우트 핸들러 agg_diff_prepare 를 실제 실행.

[BEFORE] (baseline worktree, HEAD f1a31a0)
  probe SQL  : SELECT 1 FROM NXDNP.MV_COMBO_SRC WHERE id IS NULL LIMIT 1
               SELECT 1 FROM NXDNP.MV_COMBO_TGT WHERE id IS NULL LIMIT 1
  결과       : ORA-03049: SQL keyword 'LIMIT' is not syntactically valid following
               '...MV_COMBO_SRC WHERE id IS NULL '   (2건, src/tgt 각 1건)
  _pk_resolve: key_src/key_tgt = ID / ID, trusted=false, native_unique=TRUE
               → contract chunk key 미확정 → 물리 PK 네이티브 폴백
               → prepare 에서 compare_strategy="" 로 강제(청크 우회, DIRECT merge)
  prepare    : status=READY (run_id PKFFC05BDE55DF, 1.12s) — 조용히 열화(에러 미표출)

[AFTER] (현재 트리)
  probe SQL  : SELECT 1 FROM NXDNP.MV_COMBO_SRC WHERE id IS NULL FETCH FIRST 1 ROWS ONLY
               SELECT 1 FROM NXDNP.MV_COMBO_TGT WHERE id IS NULL FETCH FIRST 1 ROWS ONLY
  결과       : ORA 에러 0건 (probe 2건 모두 성공)
  _pk_resolve: key_src/key_tgt = id / id, trusted=false, native_unique=FALSE
               → contract 기반 chunk key 정상 확정 → 청크 고속경로 유지
  prepare    : status=READY (run_id PK8C753F151887, 0.89s)

  핵심 차이  : ORA-03049 2건 → 0건 / native PK 폴백(native_unique=true) → contract 확정(false).
  정직 기록  : 1,200행 픽스처에서는 벽시계 차이가 유의하지 않다(1.12s vs 0.89s, 네트워크 편차 범위).
               이번 수정의 실효는 '전략 경로 복원'이며 대용량에서 비용 차이로 나타난다.
               _pk_resolve 단독 시간은 AFTER 가 오히려 길다(1.06s → 3.43s) — BEFORE 는 probe 가 즉시
               ORA 에러로 실패해 빨리 포기했기 때문이며, AFTER 는 실제 NULL 검증을 수행한 결과다.

  잔여(이번 범위 밖, BEFORE/AFTER 동일하게 관측됨):
    chunk key 후보 생성 중 `SELECT column_name, data_type, is_nullable FROM information_schema.columns ...`
    (PG 전용 카탈로그)가 오라클에서 2건 차단된다. 이번 수정과 무관한 별개 갭이며, 그럼에도 AFTER 는
    chunk key 확정에 성공했다(차단 요인 아님). 수정 대상 파일 범위 밖이라 손대지 않았다.
