1. 파트 A · S18 — sqlglot 파싱 무한루프 방어
════════════════════════════════════════════════════════════════════════

■ 근거
DEPENDENCY-VERSION-AND-CHANGELOG-RELEVANCE-DIAGNOSE §2·§4·§7-3.
진단서 권장 우선순위 3(버전 상향과 무관한 근본 방어)을 채택. 버전 업그레이드(F29)는 범위 밖.

■ 수정 전 실측 (재현)
  자식 프로세스에서 오라클 방언으로 아래를 파싱:
    "SELECT * FROM t WITH x AS (SELECT 1) SELECT * FROM x"
  결과: 20초 상한까지 종료되지 않아 강제 kill.
    RESULT: HANG (20초 초과 → 강제 종료)
    START 30.8.0        ← 파싱 시작 로그만 찍히고 그 뒤 아무것도 없음
  → 파이썬 예외가 아닌 순수 CPU 루프. try/except 로 막히지 않고 워커 스레드가 영구 점유된다.

■ 구현
  신규 parser/sqlglot_safe_parse.py
    · Windows 라 signal.alarm 사용 불가 → **daemon 스레드 + join(timeout)** 방식.
    · ThreadPoolExecutor 를 쓰지 않은 이유: hang 스레드가 워커 슬롯을 영구 점유하면 이후
      '정상' 파싱까지 큐에 막혀 같은 증상이 재현된다. 호출당 스레드 생성이 안전하다.
    · 타임아웃 시 SqlParseTimeout(Exception 하위) 발생 → 기존 `except Exception` 폴백 경로
      (extract_select_from_insert 의 regex fallback 등)는 수정 없이 그대로 동작.
    · **negative cache** 추가(아래 '잔여 위험' 대응): 한 번 타임아웃난 (방언, SQL) 조합은
      기억해 두고 재실행 없이 즉시 실패시킨다. 사용자가 같은 오타 SQL 로 '분석'을 반복해도
      스레드가 누적되지 않는다(LRU 64건).

  parser/sqlglot_parser.py — parse_one 호출 2곳(parse / extract_select_from_insert)을 래퍼 경유로 교체.
    parse() 타임아웃 반환값은 기존 예외 경로와 동일 형태:
      ParseResult(error_message="sqlglot 파싱 시간 초과: ...")
    → 호출부(validation_sql_parse_service / sql_validation_service / sql_change_detection) 수정 불필요.

  config/model_config.py — SQL_PARSE_TIMEOUT_SECONDS = 15 (env MV_SQL_PARSE_TIMEOUT_SECONDS)

■ 제한시간 15초의 근거
  · 정상 SQL 파싱은 DB 왕복이 없는 in-memory CPU 작업으로 통상 밀리초 단위다.
    본 작업 실측: oracle CTE 1.46ms / oracle UNION 0.81ms / pg CTE 4.19ms / mssql 7.75ms.
    15초는 정상 파싱 대비 3자리수 이상 여유 → 정상 케이스를 끊을 위험이 사실상 없다.
  · 기존 코드베이스 관례 사이에 위치: GROUPBY_SAFETY_CHECK_TIMEOUT_SECONDS=5(초) 보다는 길고,
    EXECUTE_STATEMENT_TIMEOUT_MS=60000(통계검증 실행 상한)보다는 짧다 — 파싱은 DB 왕복이
    없으므로 실행 상한보다 먼저 실패해야 한다는 순서가 유지된다.

■ 수정 후 실측 (검증 편의상 MV_SQL_PARSE_TIMEOUT_SECONDS=3 으로 단축)
  ① hang 케이스
       HANG_oracle_cte_typo   3035.4ms
       err = "sqlglot 파싱 시간 초과: SQL 파싱이 제한시간 3초 안에 끝나지 않았습니다.
              SQL 문법(예: CTE 앞 세미콜론 누락 등)을 확인하세요."
     → 수정 전 무한 → 수정 후 제한시간 내 오류 반환.

■ 잔여 위험(정직 기록)
  · **누수 스레드가 이후 파싱을 느리게 만든다.** 파이썬은 스레드를 강제 종료할 수 없어
    타임아웃된 스레드는 백그라운드에서 계속 CPU 를 돌며 GIL 을 경합한다.
    실측: hang 1건 발생 후 정상 파싱이 0.667ms → 64.5ms (x96.7 열화).
    절대값은 여전히 통계검증 실행 상한(60초)에 비해 무시할 수준이고, 서버 재기동으로 해소된다.
    지침이 명시한 대로 "요청이 영원히 매달림" → "타임아웃 후 오류 반환 + 스레드 누수" 는
    명백한 개선이므로 이 상태로 채택했다. negative cache 로 '반복 제출에 의한 누적'만 차단했다.
    누적 건수는 sqlglot_safe_parse.abandoned_parse_count() 로 관측 가능하게 남겼다.
  · **가드 미적용 sqlglot 호출부 53곳이 남아 있다**(이번 지침 범위는 parser/sqlglot_parser.py).
    파일 기준 25개 — routes/agg_diff_route.py, routes/diagnosis_route.py,
    services/analysis/*, services/diagnosis/*, services/sql_cte_utils.py,
    services/count_sql_builder.py, services/validation_sql/source_stats_sql_builder.py,
    services/readonly_sql_guard.py, parser/sql_parser.py 등.
    같은 부류의 hang 이 이 경로들에서는 여전히 서버 스레드를 영구 점유할 수 있다.
    parse_one_guarded() 로 1줄 교체하면 되지만 각각 별도 회귀 확인이 필요해 별건으로 남긴다.

■ 회귀 테스트 신규 (지침 요구: 자식 프로세스 + 타임아웃 방식)
  tests/test_sqlglot_parse_timeout_guard.py — 5 tests + 6 subtests, 전부 통과
    TC-1 hang SQL 이 제한시간 안에 error_message 로 반환(자식 프로세스 실행, 부모는 60초 상한)
    TC-2 재제출이 negative cache 로 스레드 재생성 없이 즉시 실패
    TC-3 정상 SQL 4방언 무회귀
    TC-4 run_with_timeout 반환값/예외 통과
    TC-5 제한시간 설정 해석
  ※ hang 케이스를 in-process 로 돌리면 누수 스레드가 pytest 프로세스에 남아 스위트 전체가
     느려지므로 반드시 자식 프로세스에서 실행하도록 했다. 부모는 subprocess timeout 을 걸어
     "자식 무한루프에 pytest 가 영구 정지"하는 기존 함정을 피한다.

■ [3] 임계 초과 시 EXPLAIN 강등
  기존 explain_required 축을 그대로 재사용(새 축 발명 없음).
  경과시간 > 임계 → eff_cfg["explain_required"]=True 로 구조화 evidence 즉시실행 경로를 건너뛰고
  실 DB EXPLAIN 재확인 경로로 내린다. SAFE→BLOCKED 는 가능하고 그 역은 불가한 단방향 안전 변경.

  임계값 GROUPBY_PROFILE_MAX_AGE_SECONDS = 1800(30분), env MV_GROUPBY_PROFILE_MAX_AGE_SECONDS.
  근거: 후보 프로파일은 3단계 분석 시점의 표본(5만행) 기반 분포 스냅샷이다. 정상 세션
        (분석→COUNT→후보→실행)은 본 저장소 실측상 최악(5,000만행)에서도 수 분 내에 끝난다.
        30분은 정상 세션 대비 충분한 여유이면서, 그 사이 원본/목적지에 추가 적재가 일어나
        분포가 달라질 만큼은 긴 값이다. 0 이하로 두면 강등 비활성(관측만).

■ 실측 (tests/test_groupby_profile_staleness_gate.py — 6 tests 전부 통과, 임계 60초로 단축)
  TC-1 신선한 프로파일(경과 0초)  → status=SAFE, profile_stale=False,
                                    estimate_source != 'explain' (EXPLAIN 미수행 — 기존과 동일)
  TC-2 1시간 전 프로파일          → profile_stale=True, explain_required_by_staleness=True,
                                    EXPLAIN 근거 없음 → BLOCKED_UNVERIFIABLE (즉시실행 아님)
                                    detail 에 "EXPLAIN 확인 강제" 병기
  TC-3 강등 + EXPLAIN 가능        → SAFE, estimate_source='explain' (무조건 차단이 아님)
  TC-4 시각 출처 UNKNOWN          → 강등하지 않음, SAFE 유지 (일괄 경로 무회귀)
  TC-5 서버 토큰 시각 우선        → payload 가 '1시간 전'이라 해도 SERVER_TOKEN 채택 → stale=False
  TC-6 잔여 위험 고정             → 토큰 없이 collected_at 만 '지금'으로 위조하면 강등 우회됨

■ 잔여 위험(지침 요구 — 정직 기록)
  · **신뢰경계 문제 자체는 해소되지 않았다.** EXPLAIN 강등은 '오래된 프로파일'이라는 최악
    시나리오의 피해를 줄이지만, 클라이언트가 distinct_count 를 낮게 조작하거나 collected_at 을
    '지금'으로 위장하면 여전히 우회할 수 있다(TC-6 이 이를 테스트로 고정). 완전 해소는
    [4] 신선도 서명 + [5] 서버측 재검증이 필요하며 구조 변경 폭이 커서 별도 승인 대상이다.
  · UNKNOWN(토큰 미동반)일 때 강등하지 않는 선택은 의도적이다 — 알 수 없다는 이유로 강등하면
    토큰이 없는 정상 일괄검증 경로가 전면 차단된다. 그 대신 출처를 응답/로그에 항상 남긴다.
  · 원클릭 전체검증(facade)은 ExecuteRequest 에 토큰/collected_at 을 싣지 않아 UNKNOWN 이다.
    다만 이 경로는 analyze~execute 가 **한 요청 안**에서 끝나므로 프로파일이 구조적으로 항상
    신선하다 — staleness 가 성립하지 않는 경로라 강등 대상이 아니다.
  · 다중 GROUP BY 세트 경로의 5단계 집계 객체는 groupby_execution_safety=null 로 만들어지므로
    (기존 동작) 그 화면에서는 경과시간 줄이 뜨지 않는다. 세트별 개별 결과에는 값이 들어 있다.

■ 근거

  default_inflight_ttl() / inflight_snapshot()

  · **식별 단위는 토큰이 아니라 토큰의 ctx_key** (정규화 SQL hash + src/tgt profile fingerprint
    + project). 원클릭 전체검증은 실행 도중 '새 토큰'을 발급하므로 토큰 단위로 잠그면 지침이
    지목한 재현 시나리오("통계검증 진행 중 원클릭 재시도")를 막지 못한다. 토큰이 있으면 그
    토큰의 ctx_key 를, 없으면 요청에서 ctx_key 를 재계산한다.
  · 문맥을 확정할 수 없는 요청(토큰도 SQL 도 없음)은 표식을 만들지 않는다(무회귀 우선).
  · is_enabled() 를 따른다 — 테스트 기본 OFF 환경에서는 표식도 동작하지 않아 기존 라우트
    단위 테스트에 영향이 없다.

  좀비 표식 방지(지침 필수):
  · TTL 기반 자동 만료. 기본 180초 = EXECUTE_STATEMENT_TIMEOUT_MS(60초) × 3.
    근거: 실행 상한이 원본/목적지 양측에 각각 걸리고 비교·후처리 시간이 더해진다.
    env MV_WORKFLOW_INFLIGHT_TTL_MS 로 조정 가능.
    /single/run-standard 는 analyze→count→generate→execute 를 모두 수행하므로 기본값 ×4 를 쓴다.
  · 만료는 fail-open(차단 해제) 방향 — "한 번 실패한 요청이 그 토큰을 영구히 잠근다"는
    더 나쁜 결함을 만들지 않는다.
  · marker 는 문맥키 + 난수. end_execution 은 **자기 marker 일 때만** 해제한다 —
    TTL 만료 후 다른 요청이 재점유했을 때 이전 요청이 남의 표식을 푸는 것을 막는다.
  · 서버 재시작은 메모리 상태를 통째로 날리므로 자동 해소된다.
