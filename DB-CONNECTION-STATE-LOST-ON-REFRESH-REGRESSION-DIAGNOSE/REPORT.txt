────────────────────────────────────────────────────────────────────────────
1. 결론 요약
────────────────────────────────────────────────────────────────────────────

이번 증상은 오늘 세션의 UI 커밋(JOB-DASHBOARD-STAGE3-UI-AND-MENU-REORG = 05d4fa1,
DB-PROFILE-CONNECTION-STATUS-STALE-CACHE-AND-NOTE-FIX = 639d4f5)으로 인한 회귀가
아니다. 오늘 코드와 오늘 이전 코드를 각각 별도 서버로 띄워 같은 조건으로 4가지 조합을
실측했고, 결과가 완전히 동일했다.

실제로 벌어진 일은 "접속이 성공하지 않았다"이다. 접속이 성공하지 못하면
_saveActivePath() 가 호출되지 않으므로 새로고침 복원 대상이 애초에 저장되지 않고,
같은 성공 블록 안에 있는 '검증 경로 접속 성공' 안내도 뜨지 않는다. 즉 사용자가 본
두 증상은 별개 결함 두 개가 아니라 하나의 원인(접속 성공 분기 미도달)에서 동시에
파생된 같은 증상이다.

그런데 이 상황이 "어제까진 됐는데 오늘부터 풀린다"처럼 보이게 만든 실제 코드 결함이
하나 별도로 존재한다. 상단 Source/Target 배지가 접속 성공 여부와 무관하게 '프로필을
선택한 시점에' 이미 '· 접속중'으로 바뀐다. 접속에 실패해도 상단 배지는 '접속중'이고,
새로고침 후에는 정직하게 '미연결'로 돌아간다. 사용자 눈에는 접속이 됐다가 새로고침에서
풀리는 것으로 보인다. 이것이 이번 신고의 체감 근본원인이다.

핵심 관찰 세 가지.

(1) 살아있는 DB(DB2)로는 현재 코드에서도 새로고침 후 '접속중'이 그대로 유지된다.

    _restoreActivePath 가 실제로 실행되어 silent 재접속 검증을 하고 있다는 뜻이다.
    복원 로직은 정상 동작한다. 회귀가 아니다.

(2) 불통 DB로는 오늘 이전 코드에서도 똑같이 풀린다. before/after 차이가 0이다.

(3) 접속에 실패했는데도 상단 배지는 '접속중'으로 표시된다(위 표의 "(!)" 지점).
    after_deadpg_2_after_connect.png 한 장에 세 표시가 서로 모순된 상태로 함께 찍혔다.
      · 상단 Source DB 배지        : "PostgreSQL_Inter_asis [POSTGRESQL] · 접속중" (파랑)
      · DB 프로필 목록 같은 행     : "접속실패" (빨강)
      · 검증 경로 목록 같은 행     : "미접속"
    사용자가 평소 보는 곳은 상단 배지다.

또한 connectPair 를 함수 단위로 추적해(db_conn_state_connectpair_trace.py) 어디까지
진행되는지 기록했다. 불통 DB에서는 selectPair 까지 정상 통과한 뒤 _testProfileConn 이

JS 예외로 중단된 것이 아니라 정상 경로로 실패 분기를 탄 것이다.

6. '접속 성공 메시지'의 트리거 조건이 여전히 유효한가 (요청 4)
────────────────────────────────────────────────────────────────────────────

유효하다. 이 안내는 DOM 엘리먼트에 의존하지 않는 순수 alert 이며(13711),
조건은 connectPair 안의 allSrcOk && tgtOk 하나뿐이다. 오늘 변경으로 없어지거나
이름이 바뀐 DOM/상태값을 참조하지 않는다.

살아있는 DB(DB2)로 실측하면 현재 코드에서도 "검증 경로 접속 성공: …" 이 정상 발화한다
(after_db2_repro.json 의 step2_dialogs). 불통 DB에서는 같은 함수가 실패 분기로 가서
"원본 DB 접속 실패: [프로필명] …" 이 대신 뜬다 — 다만 원본 10초 + 목적지 10초를
직렬로 기다린 뒤 20초 이상 지나서야 뜬다. 그 20초 동안 화면에 보이는 것은
'· 접속중' 배지뿐이므로, 사용자가 그 사이 다른 화면으로 이동하거나 새로고침하면
실패 안내를 아예 못 볼 수 있다. 이것이 "성공 메시지가 안 뜬다"로 체감된 부분이다.


────────────────────────────────────────────────────────────────────────────
7. 두 증상은 같은 원인인가 (요청 5)
────────────────────────────────────────────────────────────────────────────

같은 원인이다. 저장(_saveActivePath)과 성공 안내(alert)는 connectPair 성공 분기
13710/13711 두 줄로 붙어 있다. 성공 분기에 못 들어가면 둘이 함께 사라진다.
따라서 "새로고침에서 풀림"과 "성공 안내 미표시"는 우연히 같은 시점에 터진 별개 결함
두 개가 아니라, 하나의 선행 사실(접속 미성공)의 두 얼굴이다.

다만 이 상황을 회귀로 오인하게 만든 표시 결함은 별개로 실존한다(아래 8-①).
그리고 접속 미성공의 선행 원인은 두 갈래이며, 사용자 브라우저 localStorage 값 하나로
즉시 구분된다. 두 갈래 모두 실측해 두었다.

  갈래 A — 대상 DB 도달 불가 (오늘 이 PC의 실제 상태)
    · 판별: localStorage 의 mv_active_path 가 null / 없음
    · 접속 클릭 시 20초 뒤 "원본/목적지 DB 접속 실패 …" alert
    · 조치는 코드가 아니라 DB·네트워크(150/151/211 호스트, Neon quota)

  갈래 B — 작업 프로젝트 미선택
    · 판별: mv_active_path 는 남아 있는데 work_project_id 가 없음
    · _restoreActivePath 가 13773 에서 조용히 return 하므로 복원을 시도조차 안 한다
      (저장값은 지워지지 않고 남는다 — A 와 구분되는 지문)
    · 접속 클릭 시 "작업 프로젝트를 먼저 선택하세요…" alert (성공 안내 아님)
    · 실측: variant_noproject.json — 접속 성공 후 work_project_id 만 지우고 새로고침하면
      배지가 '미연결'로 떨어지고 mv_active_path 는 그대로 남는다

   ui/tabler_renderer.py:13682-13690  connectPair 의 원본/목적지 접속 테스트가 직렬

   그 사이 화면 피드백이 ①의 거짓 '접속중' 배지뿐이라 사용자가 성공으로 오인한다.

③ [확정 · 안내 누락]
   ui/tabler_renderer.py:13773  작업 프로젝트 미선택 시 복원을 조용히 건너뛴다.
   ui/tabler_renderer.py:13779-13782  복원 재접속 실패도 조용히 저장만 제거한다.
   두 경우 모두 화면에 아무 사유가 남지 않아 "이유 없이 풀렸다"로 보인다.

④ [코드 결함 아님 · 환경]
   PostgreSQL_Inter(192.168.0.150:5433/5434) timeout, Oracle(151), MariaDB(211) 불통,
   Neon 4건 quota 소진. 현재 접속 가능한 것은 DB2(192.168.0.10:50000) 한 쌍뿐.


────────────────────────────────────────────────────────────────────────────
9. 수정 방향 제안 (요청 6 — 제안만, 이번에 실행하지 않았다)
────────────────────────────────────────────────────────────────────────────

권장 순서는 ① → ③ → ② 다. ④ 는 코드 수정 대상이 아니다.

제안 1 (핵심) — 상단 배지의 상태 어휘를 실제 판정과 일치시킨다
  · _setSelectedBadge 의 라벨을 '· 접속중' 이 아닌 중립 표현(예: '· 선택됨')으로 바꾸고,
    '접속중' 은 _connectedPair 와 양쪽 CONNECTED 가 성립할 때만(즉 _isPairConnected
    기준으로만) 쓰도록 좁힌다. 판정 로직은 이미 _pairStatusLabel / _isPairConnected 에
    단일 출처로 존재하므로 새 heuristic 을 추가하지 않고 그 결과를 배지에 재사용하면 된다
    (표시 전용 변경 — 판정·SQL·후보 로직 무관).
  · 주의: tests/test_active_path_header_and_profile_order.py:43 이 현재
    `"· 접속중" in fn` 을 단언하고 있다. 이 계약이 지금의 거짓 표시를 고정하고 있으므로
    수정 시 테스트 계약도 같이 갱신해야 한다(계약을 '선택 시점은 접속중이라고 쓰지 않는다'로 역전).
  · 위험: 배지 문구는 batchLoadGroupConnectionStatus 가 endsWith('연결실패')로 파싱한다
    (ui/tabler_renderer.py:8197-8198). 문구를 바꿀 때 이 소비자를 반드시 함께 확인해야
    한다. DOM 텍스트 파싱 자체가 취약점이므로, 배지 문구가 아니라 상태값을 읽도록
    바꾸는 것이 더 나은 방향이다.

제안 2 — 복원 실패/스킵 사유를 화면에 남긴다
  · _restoreActivePath 가 복원하지 않은 경우(프로젝트 미선택 / 재접속 실패) 상단 배지나
    검증 경로 행에 '이전 접속 복원 실패(사유)' 를 표시한다. 자동 재시도는 넣지 않는다
    (네트워크 비용 · 기존 정책과 동일하게 온디맨드 유지).

제안 3 — 접속 시도 중 진행 표시 + 실패 지연 완화
  · 최소안: 접속 클릭 즉시 배지/버튼에 '접속 확인 중…' 을 표시하고 완료 시 확정 상태로
    바꾼다(가장 저비용, 구조 영향 없음).
  · 선택안: 원본/목적지 접속 테스트 병렬화. 다만 현재 직렬 구조는 '어느 쪽이 실패인지'
    분리 표시(§7,§8)의 근거이므로, 병렬화하면 실패 사유 수집 코드를 함께 손봐야 한다.
    구조 안정성 관점에서는 최소안을 먼저 적용하는 편이 낫다.

제안 4 — 운영 조치(코드 아님)
  · 150/151/211 호스트 도달성과 Neon quota 를 먼저 확인한다. 사용자 브라우저의
    localStorage mv_active_path / work_project_id 두 값을 보면 갈래 A/B 를 즉시 판별할 수 있다.

구조 영향 검토 : 위 제안 1~3 은 전부 표시 계층 한정이며 web_server.py 를 건드리지 않고
                 판정·SQL·후보 로직에 새 분기를 추가하지 않는다. 새로운 heuristic 하드코딩
                 없음, scoring 영향 없음. explainability 는 제안 2 로 오히려 개선된다.
                 보안 영향 없음(비밀번호·host 표시 없음 유지).
지금 구현 여부 : 보류 — 이번 작업은 진단 전용이며, 제안 1 은 기존 테스트 계약 역전을
                 동반하므로 별도 작업으로 승인 후 진행하는 것이 맞다.
