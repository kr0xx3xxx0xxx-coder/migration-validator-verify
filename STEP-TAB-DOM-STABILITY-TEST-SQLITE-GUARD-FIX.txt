1. 요청과 실측의 불일치 (가장 먼저 보고)
────────────────────────────────────────────────────────────────────────
요청서 전제 : 이 8건은 운영 SQLite 쓰기 가드 [PROD-DB-WRITE-BLOCKED] 에 막혀 실패한다.
              → 요구사항 1·2 는 "운영 SQLite 경로 참조 지점을 찾아 tmp_path 로 전환" 이었다.

실측 결과   : 이 전제는 사실과 다르다. 실패 원인은 SQLite 와 무관하다.

근거 3가지
  (1) 이 테스트 파일에는 운영 SQLite 경로를 참조하는 지점이 아예 없다.
      sqlite3 import 도, db/migration_validator.db 참조도, DB 연결 코드도 없다.
      (요구사항 1 의 "참조 지점" 은 존재하지 않으므로 tmp_path 전환 대상도 없다.)
  (2) 실패 메시지에 [PROD-DB-WRITE-BLOCKED] 가 등장하지 않는다. 실제 실패는 node
      런타임의 TypeError 였다:
        TypeError: Cannot read properties of null (reading '_uid')
        at out.q_first_uid = q_first._uid;
  (3) 가드에 걸렸다면 TablerRenderer().render_full_page() 단계에서 RuntimeError 로
      죽어야 하는데, 그 단계는 정상 통과해 HTML/JS 추출까지 끝났다. 즉 파이썬 측
      DB 가드는 발동하지 않았다.

따라서 요구사항 3 ("가드에 안 걸리면서 DOM 안정성 검증 목적은 유지") 만 유효하고,
요구사항 1·2 (tmp_path 전환) 는 대상이 없어 적용 불가하다. 목적 유지라는 본래 의도를
그대로 지키면서 실제 원인을 고쳤다. 백로그 M4/M5 의 원인 진단은 정정이 필요하다.

2. 실제 근본 원인
────────────────────────────────────────────────────────────────────────
운영 코드 ui/tabler_renderer.py 의 renderMvStepNav 는 공용 컨테이너(mvStepNavInner)를
개별(analyze) nav 와 일괄(batch) nav 가 공유하기 때문에, 호출자가 어느 쪽인지를
"전달된 onClick 함수의 identity" 로 판정한다.

  var _isSingleCaller = (typeof _mvNavClick === 'function' && onClick === _mvNavClick);
  if (_isSingleCaller && _mvCurrentTab !== 'analyze') return;   /* 개별 nav 인데 개별화면 아님 */
  if (!_isSingleCaller && _mvCurrentTab !== 'batch') return;    /* 일괄 nav 인데 일괄화면 아님 */

과거 개별 nav 진입점은 showSingleStep 이었으나 STAGE-STEPPER 작업에서 _mvNavClick 으로
통합되었다(운영 호출부도 renderMvStepNav('mvStepNavInner', steps, _mvNavClick) 로 변경됨).

그런데 테스트 하니스는 여전히 showSingleStep 이라는 이름의 스텁을 만들어 넘기고 있었다.
하니스 안에 _mvNavClick 이라는 전역이 없으므로:

  typeof _mvNavClick === 'function'  → false
  _isSingleCaller                    → false          (일괄 writer 로 오판)
  _mvCurrentTab('analyze') !== 'batch' → true          → 조기 return

결과적으로 renderMvStepNav 가 아무것도 그리지 않고 즉시 반환한다. 탭 DOM 이 0개이므로
itemByStep(_container,'query') 가 null 이 되고, 그 뒤 모든 단정이 null 참조로 붕괴한다.
8건 전부가 같은 하나의 원인으로 실패한 "죽은 빨간 불" 이었다.

성격 : 운영 결함이 아니라 테스트 하니스의 낡은 계약(stale harness contract).
        운영 코드는 정상 동작하며, 이번 작업에서 운영 코드는 한 줄도 수정하지 않았다.
