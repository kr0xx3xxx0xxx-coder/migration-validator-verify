2. 실사용 시나리오 — COUNT 탭은 실제로 쓸모가 있는가
════════════════════════════════════════════════════════════════════════

결론부터: **있다. 그룹 목록 좁히기 용도로 명확히 유용하며, 그것이 유일한 설계 의도다.**

2-1. 실측으로 이미 증명돼 있다
────────────────────────────────────────────────────────────────────────
  TAB-FILTER-COUNT-SUM-DIVERGENCE-VERIFY-DIAGNOSE(2026-07-31, 오라클 라이브 실 브라우저) 결과:
    탭 배지  : [전체 10] [COUNT 5] [AMT 10] [QTY 10]
    COUNT 탭 : G01/G03/G05/G07/G09 만 남고 G02/G04/G06/G08/G10 은 전부 제외됨
    기준값   : 짝수 그룹은 COUNT 99,000 = 99,000 (완전 동일), AMT/QTY 만 상이
  → 10개 중 5개로 정확히 좁혀 준다. "COUNT 문제가 있는 그룹만 빠르게 찾고 싶다"는 요구를
    그대로 충족한다.

2-2. 유용한 3가지 상황
────────────────────────────────────────────────────────────────────────
  (a) 그룹 목록 좁히기 — 사용자가 예로 든 바로 그 용도
      도입 커밋 문구의 예시가 `[전체 480][COUNT 200][ORDER_AMT 200]` 인 데서 보듯, 실제 운영 규모는
      수백 그룹이다. 480그룹 중 COUNT 가 어긋난 3개를 눈으로 찾는 것과 탭 한 번 누르는 것의 차이다.
      **이 용도만으로도 탭은 충분히 값을 한다.**

  (b) 원인 계열 분류 — 목록을 좁히기 전, 배지 숫자만 봐도 진단 방향이 갈린다
      [COUNT 0][AMT 10]  → 건수는 다 맞는데 금액만 틀림. 행 누락이 아니라 **값 변환/정밀도** 의심
                            (ROUND/TRUNC/CAST, 타입 축소 — 화면의 변환식 안내와 같은 계열).
      [COUNT 10][AMT 10] → 행이 빠져서 금액도 따라 틀림. **누락/중복 적재**를 먼저 조사.
      [COUNT 5][AMT 10]  → 두 원인이 섞임. 위 실측 픽스처가 정확히 이 모양이었다.
      이건 목록을 좁히는 기능이 아니라 **한 눈에 읽는 요약 지표**로서의 값이다.
      (원래 '컬럼별 차이 요약 카드'였다는 태생을 생각하면 이 용도가 오히려 원형이다.)

  (c) 재이관 우선순위 판단
      COUNT 가 어긋난 그룹은 목적지에 아예 없는 행이 있다는 뜻이라 **재이관 대상 PK 가 실제로
      존재하는 그룹**일 가능성이 높다. SUM 만 어긋난 그룹은 행은 다 있고 값만 틀린 경우가 많아
      재이관보다 변환식 수정이 답인 경우가 많다. 조치가 갈리므로 먼저 나눠 보는 게 맞다.

2-3. "레코드 단계에서는 의미가 없다" — 절반만 맞다
────────────────────────────────────────────────────────────────────────
  맞는 부분:
    레코드 행의 **COUNT 열 자체**는 영구히 '·' 다(1-5). 여기서 읽을 값은 없다. 사용자 관찰이 정확하다.

  틀린 부분(중요):
    **COUNT 탭에서 그룹을 펼쳤을 때 나오는 레코드 목록 자체가 COUNT 차이의 증거다.**
    COUNT 차이의 원인은 '값'이 아니라 '행의 존재/부재'이고, 그 증거는 화면에 이미 그려져 있다:
      ui/tabler_renderer.py:17069-17077  _mvPkCellSplit(sv, tv, missing, isDiff, ...)
        var b = missing ? '-' : ...;
        var tgtStyle = (isDiff || missing) ? ';color:#C2410C;font-weight:700' : '';
      → 목적지에 없는 레코드는 목적 셀이 '-' + 주황 굵게로 표시된다.
    즉 COUNT 지표의 레코드 레벨 표현은 'COUNT 열의 숫자'가 아니라 **'이 행이 목적에 없다'는 사실**
    그 자체다. 그 표현은 이미 있고, 다만 화면이 그 대응관계를 한 번도 말해주지 않는다
    (툴팁은 "그룹 요약 행에서 확인하세요"라고만 하고, 왜 COUNT 에는 레코드 값이 없는지는 설명 안 함).

  → 판정: **"그룹 목록에서만 유용하고 레코드 드릴다운에서는 의미가 없다"는 게 맞는 설계다.**
    구현 누락도 오구현도 아니다. 부족한 것은 기능이 아니라 **설명**이다.

════════════════════════════════════════════════════════════════════════

3-1. 축별 대조표(코드 근거 기준)
────────────────────────────────────────────────────────────────────────
 축                        | 전체 탭 | COUNT 탭      | AMT/QTY 탭      | 근거
 --------------------------|---------|---------------|-----------------|---------------------------
 그룹 목록을 걸러 주는가    |  해제   | 걸러 줌       | 걸러 줌         | exec_result_renderer:124-125

 레코드 값 열이 채워지는가  |  해당없음| **항상 '·'** | 실제 값 + 주황  | tabler_renderer:17365, 17575

3-2. 사용자 가설("AMT/QTY 는 그룹 필터 + 레코드 값 확인 둘 다 의도")에 대한 판정
────────────────────────────────────────────────────────────────────────
  **코드상 근거가 없다. 세 탭 모두 '그룹 목록 필터 전용'으로 동일하게 설계됐다.**

  결정적 근거 — 드릴다운 조회는 탭 상태를 전혀 모른다:
    ui/tabler_renderer.py:17392-17394
      d = await (await fetch('/agg-diff/pk-records?run_id=' + encodeURIComponent(runId)
        + '&page=' + (page || 1) + '&page_size=5&view=' + view
        + '&scope_col=' + encodeURIComponent(scopeCol) + '&scope_val=' + encodeURIComponent(scopeVal))).json();
    넘어가는 파라미터는 run_id / page / page_size / view / scope_col / scope_val 뿐이다.
    지표(_execColFilter)는 넘어가지 않으며, 앞서 확인했듯 tabler_renderer.py 는 그 변수를 아예 모른다.

  실질적 귀결:
    **AMT 탭에서 그룹을 펼쳐도 "AMT 는 맞고 QTY 만 틀린 레코드"가 그대로 섞여 나온다.**
    AMT 탭의 레코드 목록 = QTY 탭의 레코드 목록 = 전체 탭의 레코드 목록으로 완전히 동일하다
    (같은 그룹이면 같은 scope, 같은 캐시 키 — :17385 cacheKey 에 지표가 없다).

  → 따라서 AMT/QTY 에서 레코드 값이 보이는 것은 **탭의 기능이 아니다.** 드릴다운 표가 원래
    '선택 SUM 열'을 갖고 있기 때문에 생기는 **부수 효과**다. 탭을 COUNT 로 두든 AMT 로 두든
    그 열은 똑같이 채워진다.

  → 정리하면 비대칭은 **"레코드 값 열이 채워지는가" 한 축뿐**이고, 그것은 탭 설계의 비대칭이 아니라
    **지표 자체의 성질**(COUNT 는 집계 파생, SUM 은 레코드 값의 합)에서 나온다.

5. 사용자 질문에 대한 직접 답

Q1. COUNT 탭이 실제로 쓸모 있는 상황이 있는가?
  → **있다.** ① 수백 그룹 중 건수가 어긋난 그룹만 골라내기 ② 배지 숫자만으로 원인 계열
    (누락/중복 vs 값 변환) 즉시 분류 ③ 재이관 대상이 실재하는 그룹 우선 선별.
    실측으로 10그룹 → 5그룹 정확 축소가 확인돼 있다.

Q2. "그룹 목록에서만 유용하고 레코드 단계에서는 무의미"가 맞는 설계인가,
    아니면 구현이 안 됐거나 잘못된 것인가?
  → **맞는 설계다.** 탭은 처음부터 그룹 차이 요약 카드에서 파생됐고(4d56656), 화면 문구·주석·구현이
    모두 '그룹만'으로 일관된다. 레코드 행의 '·' 도 트리 병합 시 명시적으로 결정된 표기다(a33251d).
    **다만 절반의 단서가 있다** — COUNT 탭의 레코드 목록은 '목적 미존재 행' 이라는 형태로
    COUNT 차이의 증거를 이미 담고 있는데, 화면이 그 대응관계를 설명하지 않는다. 빠진 것은
    기능이 아니라 설명이다.

Q3. COUNT 만 예외적으로 레코드 레벨 의미가 없는 것인가?
  → 값 열 관점에서는 그렇다. 하지만 **필터 관점에서는 세 탭 모두 똑같이 레코드를 걸러주지 않는다.**
    AMT 탭에서 그룹을 펼쳐도 AMT 가 일치하는 레코드가 그대로 섞여 나온다(드릴다운 fetch 가
    지표를 전혀 안 넘김 — :17392-17394). 'AMT/QTY 는 레코드 값 확인까지 의도했다'는 해석은
    코드상 근거가 없고, 그건 드릴다운 표가 원래 선택 SUM 열을 갖고 있어 생기는 부수 효과다.
