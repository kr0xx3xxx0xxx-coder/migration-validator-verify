NEON-PG-50M-45M-MISMATCH-FIXTURE-LOAD
⚠️ 추가 작업 필요 - Neon 프로젝트 512MB 저장용량 캡으로 지시서 원문 규모(50M/45M) 적재 불가, 10:9 비율 보존한 축소 규모(900K/810K)로 대체 적재·검증 완료

────────────────────────────────────────────────────────────
배경 / 지시서
────────────────────────────────────────────────────────────
directives/NEON-PG-50M-45M-MISMATCH-FIXTURE-LOAD.md
원본(SRC) 5,000만건 · 목적(TGT) 4,500만건(500만건 의도적 누락)을 PostgreSQL_tobe
(Neon 클라우드) 프리셋에 생성해, 개별검증 화면 COUNT 사전검증까지 실측하라는 지시.

────────────────────────────────────────────────────────────
1. 규모 축소 경위 (핵심 발견사항)
────────────────────────────────────────────────────────────
1차 시도(지시서 원문 그대로 SRC 1~50,000,000 / TGT 5,000,001~50,000,000)를 청크
(1,000만행) 단위 INSERT ... SELECT FROM generate_series 로 실행하던 중 SRC 첫 청크에서
아래 오류로 실패:

  psycopg2.errors.DiskFull: could not extend file because project size limit
  (512 MB) has been exceeded
  HINT: This limit is defined externally by the project size limit, and
  internally by neon.max_cluster_size GUC

실측 확인 결과:
  - PostgreSQL_tobe(neondb)는 Neon 프로젝트 전체 512MB 하드 스토리지 캡이 걸려있음.
  - 실패 시점 이전에 이미 기존 테스트 데이터(다른 작업 소유 픽스처, 예: tgt_orders
    186MB 등)로 325MB 사용 중 — 가용 여유는 187MB뿐이었음.
  - 실패한 SRC 적재 시도는 롤백되어 COUNT=0 이었으나, 물리 파일은 182MB 를 이미
    점유한 상태(DB 총 507MB, 512MB 캡 턱밑)로 남아있어 즉시 DROP TABLE 로 회수함
    (VACUUM 이 아닌 DROP 이 즉시 회수됨을 확인) → 325MB 로 원복.
  - 1,000,000행(PK 포함) 실측 크기 = 87MB(행당 ≈90.8B, 파일럿 측정) → 5,000만행급은
    이 프로젝트에서 물리적으로 적재 불가능함을 확인.
  - 기존 데이터(다른 작업 소유)는 "기존 데이터 삭제 시 사용자 확인 필수" 원칙에 따라
    임의 삭제하지 않음 → 확보 가능한 여유 용량 내에서 축소하는 방향으로 판단.

대응: 안전 여유(≈32MB, 캡의 약 6%)를 남기고, 지시서의 핵심 비율(500만/5,000만 =
10% 누락)을 그대로 보존한 **SRC 900,000건 / TGT 810,000건(90,000건 누락, 10%)**으로
축소해 재적재. 테이블명은 지시서 원문 그대로(NEON_MISMATCH50M_SRC/TGT) 유지.

────────────────────────────────────────────────────────────
2. 구현
────────────────────────────────────────────────────────────
스크립트: scripts/dev_e2e/neon_pg_50m_45m_mismatch_fixture_load.py (신규)
대상: PostgreSQL_tobe 프리셋 (Neon, ep-super-river-aoeo1f81...neon.tech / neondb)
테이블: public.neon_mismatch50m_src / public.neon_mismatch50m_tgt

적재 방식:
  - generate_series 로 SRC/TGT 를 각각 서버 사이드에서 생성(네트워크로 행 복사 안 함).
  - 컬럼: id(PK, integer) / region_cd(8종, GROUP BY축1) / status_cd(3종, GROUP BY축2)
    / amt(numeric(12,2), SUM대상) / qty(integer, SUM대상) / item_nm(varchar(50)).
  - id 기반 결정식으로 값 산출 → SRC/TGT 겹치는 id 구간은 완전히 동일한 값
    (COUNT 차이 외 부수적 값 불일치 0건).
  - SRC id범위: 1 ~ 900,000 (전체)
  - TGT id범위: 90,001 ~ 900,000 (뒤쪽 90%) → 앞쪽 90,000건이 "재이관대상"(누락).
  - PK 는 청크 INSERT 완료 후 별도 ALTER TABLE ADD PRIMARY KEY (인라인 PK 대비
    빠름), 이후 ANALYZE.

3. 실측 결과
────────────────────────────────────────────────────────────
[적재 소요시간]
  구분        건수(기대=실제)   INSERT    PK추가   ANALYZE   합계
  SRC(원본)   900,000행         1.73s     0.47s    0.16s     2.64s
  TGT(목적)   810,000행         1.54s     0.44s    0.16s     2.41s

[직접 SQL COUNT 재확인]
  SRC = 900,000  /  TGT = 810,000  /  diff = 90,000  (기대값과 정확히 일치)

[개별검증 화면 경로(services.count_common_service.run_count_pair) in-process 실행]
  status = FAILED (COUNT 불일치이므로 정상 판정)
  source_count = 900,000
  target_count = 810,000
  count_diff   = 90,000   ← 기대한 누락분과 정확히 일치, 화면 COUNT 사전검증
                              단계에서 "재이관대상"이 실제로 잡힘을 확인
  실행시간 = 1,958.6ms

판정: OK (기대 diff=90,000 과 direct SQL / run_count_pair 양쪽 모두 일치)

[DB 용량 최종 상태]
  전체 512MB 캡 중 473MB 사용 (SRC 78MB + TGT 70MB 신규, 기존 325MB 유지)
  → 여유 39MB 잔존. 추가 확장 여지 거의 없음(다른 작업 픽스처 정리 없이는 불가).

────────────────────────────────────────────────────────────
4. 후속 필요 사항 (⚠️ 추가 작업 필요 사유)
────────────────────────────────────────────────────────────
- 지시서 원문의 문자 그대로의 규모(5,000만/4,500만)는 이 Neon 프로젝트(512MB 캡)에서
  달성 불가. 진짜 5,000만행급 시나리오가 필요하면 다음 중 하나가 선행되어야 함:
    a) Neon 프로젝트 스토리지 플랜 상향(유료 티어) — 사용자 판단 필요.
    b) 이 DB 안의 다른 작업 소유 테스트 픽스처(tgt_orders 186MB 등) 정리 —
       "기존 데이터 삭제" 항목이라 사용자 확인 필수, 본 작업 범위에서 임의 삭제 안 함.
    c) 5,000만행급 규모가 실제로 필요하면 내부망 PostgreSQL(더 큰 여유 확인됨,
       [[project-neon-quota-exhausted]] 참고)처럼 별도 인프라 사용 — 단, 이 지시서는
       명시적으로 "PostgreSQL_tobe 프리셋 그대로 사용, 기존 계정 범위 밖으로 나가지
       마라"고 제한했으므로 본 작업에서는 채택하지 않음.
- 4단계 이후(통계검증 SQL 생성·실행)는 지시서 범위 밖이라 미실시.
