[1] 확정 조회 키(table_key)에 스키마가 없다

  실측: services/single_validation_analyze_service.py:1664
    override_table_key = (str(tgt_table) if tgt_table else "")
  이 tgt_table 은 파서 원문 그대로(스키마 없음)다. 그런데 같은 함수 안(707행)에 이미 스키마-qualify
  된 값이 존재한다:
    parse_result["tgt_table_qualified"] = _tgt_q or tgt_table   (services/db_query_service.py 의
    qualify_insert_target_from_sql 결과, project_qualify_single_source 가 단일 출처로 지목한 그 함수)
  즉 "정규화 함수 자체를 새로 만들거나 고칠 필요는 없다" — 이미 계산된 값을 1664행에서 tgt_table 대신
  parse_result.get("tgt_table_qualified") 로 바꿔 넣기만 하면 값 자체는 스키마를 포함하게 된다.
  (지시가 우려한 "여러 기능이 공유하는 정규화 함수"는 존재하지 않는다 — qualify_insert_target_from_sql
  자체를 건드리지 않으므로 이 함수를 공유하는 다른 소비자(COUNT SQL 생성 등)에는 영향이 없다.)

  그런데도 승인 필요로 분류한 이유는 두 가지다.
  (a) single_validation_analyze_service.py 는 CLAUDE.md 가 말하는 "1~6단계 완료된 모듈"의 핵심(1단계
      분석 실행 서비스, /analyze 파이프라인)이라 임의 수정 금지 대상이다. 다만 override_table_key
      대입 자체는 이미 이 파일에 "+5줄"로 존재하는 지점을 1줄 바꾸는 것뿐이라 구조적 침습은 작다.
  (b) 더 큰 문제는 데이터 호환성이다. services/admin_column_override_store.py 의 normalize_table_key()
      (87행)는 strip()+upper() 만 하고 스키마 유무를 흡수하지 않는다. resolve_override/get_override 는
      table_key 문자열을 그대로 비교한다(정확 일치). 지금까지 저장된 TABLE_COLUMN 확정은 전부 bare
      키('MV_ORA_DEMO_TGT')로 저장돼 있다. 조회 키를 qualified('NXDNP.MV_ORA_DEMO_TGT')로 바꾸면
      기존에 저장된 확정이 새 키와 더 이상 일치하지 않아 **조용히 확정이 사라진 것처럼 보인다**(에러
      없이 자동판정으로 되돌아감). 로컬 개발 DB(db/migration_validator.db)는 현재 admin_column_override
      0행으로 직접 조회 확인했으나, 운영 배포본에 데이터가 있다면 이관/마이그레이션 절차 없이는 배포
      즉시 사용자 확정이 유실된다.
  (c) 추가로 확인된 사실: services/single_validation_analyze_service.py:730-737 의 M41 암호화컬럼 정책
      (attach_encrypted_columns_from_store)도 동일하게 bare tgt_table 을 자기 자신의 table_key 관례로
      독립 소비하고 있다. 이번 fix는 override_table_key(1664행) 파라미터만 바꾸는 것이라 그 경로에는
      영향이 없다(별개 키워드 인자) — 다만 "스키마 없는 tgt_table 을 table_key 로 쓰는 관례"가 이미
      최소 2개 기능에서 각자 채용돼 있다는 사실 자체는 향후 유사 신고가 또 나올 수 있음을 시사한다.
  (d) 부분적 해결 한계: tgt_table_qualified 도 원본 SQL에 스키마가 없으면 707행 폴백으로 bare 그대로
      떨어진다(_tgt_q or tgt_table). 즉 이 fix로도 스키마 미표기 SQL 에서는 문제가 재현된다 — 완전한
      해결이 아니라 "스키마가 명시된 SQL 한정 개선"이다.
  결론: 코드 변경량은 1줄이지만 완료 모듈 파일 + 기존 저장 데이터 유실 가능성이 겹쳐 승인 필요(고위험
  재평가). 승인 시 최소한 (i) 기존 bare 키 확정에 대한 폴백 조회(구키로도 한 번 더 조회) 또는 (ii)
  마이그레이션 스크립트 중 하나를 함께 설계해야 한다.

[4] 낙관적 반영이 자동선정 pool 재배치를 하지 않는다

  pool(전역 자동선정) 재계산 로직의 유일한 소스는 services/candidate_display_enricher.py:888
  _apply_global_autoselection(cands, scoring_map, max_n, active, is_sum) 이다. 실측 확인한 특성:
    - DB/프로파일을 직접 재조회하지 않는 순수 함수다(입력으로 받은 scoring_map·후보 dict의 필드
      selection_status/simulated_selection_status/auto_selected 만 갱신).
    - 이 함수는 같은 enrich_candidates_for_display() 안에서 Step 4-a(관리컬럼 확정 적용,
      apply_admin_column_overrides, 1432행) 바로 다음 Step 4.5(1449-1450행)로 호출된다 — 즉 서버
      쪽에는 "확정 적용 → pool 재계산"이 이미 한 세트로 붙어 있다.
    - 문제는 이 세트를 호출하는 진입점이 지금 둘뿐이라는 것이다: ① /analyze 전체 재실행, ② 3단계
      재확정(POST /validation-sets/preview → _refreshValidationPlanWithRowCount). 두 경로 모두
      DB 재접속·프로파일 재수집을 동반하는 무거운 전체 재계산이며, 원본 보고서 §3-(1)에서 "확정
      버튼 한 번에 치를 비용이 아니다"라고 이미 기각된 방식과 동일하다(재확인 결과 그 판단은 여전히
      타당함 — workflow_token 재발급으로 2단계 COUNT 확인 상태까지 초기화되는 부작용은 지금도 그대로).

  결론: _apply_global_autoselection 자체(완료·안정 함수)는 수정할 필요가 없다 — 재사용 가능한 순수
  함수이기 때문이다. 대신 필요한 것은 "이 함수만 가볍게 태우는 새 진입점"이다. 클라이언트는 이미
  화면 표시를 위해 스코어가 포함된 후보 리스트(ad.all_groupby_candidates 등)를 들고 있으므로, 그
  리스트를 그대로 서버에 되돌려 재계산만 요청하는 방식이 DB 재접속 없이 기술적으로는 가능해 보인다.
  다만 이 방식은 새로운 신뢰 경계 문제를 만든다 — 서버가 클라이언트가 보낸 스코어 값을 그대로 믿고
  선정 여부를 계산하면, 화면 조작(devtools 등)으로 특정 컬럼의 점수를 올려 자동추천에 끼워 넣는 것이
  이론상 가능해진다. 최소 대응은 (i) 후보 목록/스코어는 서버가 직전 /analyze 응답을 세션·캐시에
  보관해두고 재사용하거나, (ii) 클라이언트가 보내는 것은 "override 변경분(컬럼+decision)"뿐이고
  스코어는 서버가 들고 있는 값으로만 판정하는 구조 중 하나로 좁혀야 한다. 이 설계 결정 자체가 새 API
  표면(신규 라우트)을 여는 일이라 "완료 모듈 임의 수정"은 아니지만 구조 변경에 해당해 승인이 필요하다.
  판정: 중위험, 승인 필요(구현 전 API 형태 설계 결정 선행 요구 — CLAUDE.md "기능/구조 변경 요청 응답
  형식" 절차 대상).
