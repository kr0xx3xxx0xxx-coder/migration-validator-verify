작업명 : REIMPORT-COUNTONLY-CHUNK-SIZE-DIAGNOSE
⚠️ 추가 작업 필요 - 원인은 '청크 크기'가 아니라 '표본 preflight' — 25만행 CTE/JOIN 재이관 준비 475초 중 471.5초(99.3%)가 표본 게이트, 실제 전수 merge 는 2.7초

────────────────────────────────────────────────────────────────────────────
0. 한 줄 결론
────────────────────────────────────────────────────────────────────────────
가설(“청크 크기가 25만으로 잡혀 청크 1개가 됐다”)은 실측으로 반증됐다.
청크 크기가 크게 잡힌 게 아니라 **청크 경로 자체가 실행되지 않았다**(chunk_size=null,
actual_strategy_id=DIRECT_STREAM_COMPARE). 그리고 정체 구간은 비교 단계가 아니라
그 앞의 **표본 preflight(anchor 2,000개 × CTE 전체 재스캔)** 였다.
가변 청크 크기로는 이 증상이 해결되지 않는다.

5. CTE/JOIN pushdown 문제가 재이관 경로에도 적용되는가  (지시 5)
────────────────────────────────────────────────────────────────────────────
[결론] **동일하게 적용된다. 회피 장치(임시테이블 물질화 등)는 없다.**
       재이관 chunk 조회도 통계검증과 똑같이 원본 SQL 을 인라인뷰로 감싸고 그 '위에'
       述어를 얹는 방식이라, 윈도우함수가 view merging 을 막아 매 조회가 전체 재스캔이다.

[코드] services/exact_diff/dialects/oracle.py:515-516 (make_ora_fetch_chunk)
       'SELECT %s FROM (%s) Q0 WHERE Q0.%s >= :1 AND Q0.%s < :2 ORDER BY Q0.%s'
       → 원본 SQL 을 Q0 로 감싸고 WHERE 를 바깥에 붙인다. 물질화·임시테이블 없음.
       PostgreSQL 판(make_pg_fetch_chunk)도 동일 계약.

[EXPLAIN PLAN 실측 — 같은 述어, 같은 폭, 원본 shape 만 다름]
  ■ CTE+JOIN+ROW_NUMBER wrapping   ← pushdown 실패
      SELECT STATEMENT
        SORT ORDER BY
          VIEW                     [filter: "ID">=:1 AND "ID"<:2 AND "RN">=1]   ← 뷰 '밖'
            WINDOW SORT
              FILTER               [filter: :2>:1]
                HASH JOIN RIGHT OUTER  [access: "T"."ORDER_ID"(+)=MOD("X"."ID",300)+1]
                  INDEX FULL SCAN  PK_MV_ORA_TEST_TGT
                  TABLE ACCESS FULL MV_ORA_XDIFF_TGT                            ← 전체 스캔
  ■ 단순 SELECT(대조군)             ← pushdown 성공
      SELECT STATEMENT
        FILTER                     [filter: :2>:1]
          TABLE ACCESS BY INDEX ROWID MV_ORA_XDIFF_TGT
            INDEX RANGE SCAN PK_MV_ORA_XDIFF_TGT  [access: "ID">=:1 AND "ID"<:2]

[비용 실측 — 오라클 직접(scripts/dev_e2e/reimport_countonly_phase_cost_probe.py)]
      측정 항목                                    CTE wrapping    단순(대조군)
      전체 1회 통과 COUNT(*)  (249,950행)             340.7 ms        25.1 ms
      PK MIN/MAX (ora_pk_min_max)                    350.0 ms        14.2 ms
      chunk[1, 50001)        50,000행 폭            1,869.8 ms     1,771.7 ms
      chunk[100001, 150001)  50,000행 폭            1,896.8 ms          —
      chunk[1, 1001)          1,000행 폭              372.5 ms        32.9 ms   ← 결정적
      표본 8 anchor (CROSS APPLY)                  2,463.9 ms        17.3 ms
        └ anchor 1개당                               308.0 ms         2.2 ms
        └ 2,000 anchor 선형 환산                     **616 초**       4.3 초

  → 1,000행 폭 청크가 372ms = 전체 통과(340ms) + 행 전송. 즉 **청크 폭과 무관한
    고정비 약 340ms(전체 재스캔)가 청크마다 붙는다.** 청크를 작게 나눌수록 총비용이
    선형 증가한다. CTE 형태에서 청크 분할은 이득이 아니라 순손실이다.
  → 표본 어댑터(dialects/oracle.py:301-304)는 anchor 마다
    `SELECT * FROM (원본) Q0 WHERE Q0.ID >= anchor ORDER BY ID FETCH FIRST 1`
    를 CROSS APPLY 로 돌린다. anchor 2,000개 = **CTE 전체 스캔 2,000회**.
    실측 anchor당 236~246ms(서버, 커넥션 warm) / 308ms(직접) — 환산치와 자릿수 일치.

[추가 위험 — 아직 안 터진 것]
  services/exact_diff/sampling_preflight.py:205,209 _expansion_steps(2000, 10000)
    = [2000, 5000, 10000]. 표본 비율이 임계(10%) 근처면 확장한다.
  이번 실측은 표본 불일치 0건이라 1단계(2,000)에서 확정돼 멈췄다.
  임계에 걸치면 2,000+5,000+10,000 = **17,000 anchor ≈ 67분**까지 늘어난다.
  표본 게이트에는 비용 상한·타임아웃·shape 가드가 **전혀 없다**.

6. 사용자 제안(COUNT 재사용 가변 청크 크기) 타당성 검토  (지시 6)
────────────────────────────────────────────────────────────────────────────
- 요청 요약 : 2단계에서 이미 확보한 원본 COUNT 를 재사용해, 규모에 비례하도록 청크
              크기를 가변 산정한다(목표 청크당 처리시간 1~5분 역산).
- 긍정적 효과 : 개념 자체는 타당하다. 현재 50,000 고정은 1만행에도 1,000만행에도
              같은 값을 쓰는 무차별 상수이고, 실제로 벤치 주석에도 "벤치마크 후 조정"이
              그대로 남아 있다. pushdown 이 되는 형태에서는 진행률 해상도와 재개 입도를
              규모에 맞게 맞출 수 있다.
- 그러나 이번 증상에는 무효 : ① 이 경로는 청크 엔진에 진입조차 하지 않았고(2절),
              ② 진입했더라도 CTE 형태는 청크당 전체 재스캔이라 청크를 늘리면 손해이며(5절),
              ③ 정체 구간 471초는 청크 이전 단계(표본)라 청크 파라미터의 관할 밖이다.
              가변 청크로 바꿔도 이번 케이스의 475초는 1초도 줄지 않는다.
- 구조적 문제점 : chunk_size 는 재개 계약의 일부다.
              services/exact_diff/chunk_checkpoint.py:243-254 resumable() 이
              chunk_size 불일치를 CHUNK_SIZE_MISMATCH 로 판정해 **재개를 차단**한다.
              실행 중 동적으로 크기를 바꾸면 중단 후 이어서 실행이 전부 깨진다.
              → 가변화하더라도 'run 시작 시 1회 산정 후 run 내 고정'이어야 한다.
- 운영상 위험 : 정책값(strategy_resource_weights.pk_range_chunk_size)이 현재 None 이라
              모든 판단이 코드 상수로 떨어진다. 가변식을 코드에 심으면 heuristic 하드코딩이
              늘고 explainability 가 준다(왜 이 크기인지 근거 미저장).
- heuristic / scoring / explainability 영향 : 산정 근거(목표시간·측정 throughput·PK 밀도)를
              metrics/basis 에 저장하지 않으면 "왜 청크가 3개였나"를 사후 설명할 수 없다.
- 지금 구현 여부 : **보류(문서화 우선)**. 우선순위는 아래 7절 (A) 표본 게이트다.

[그럼에도 요청대로 — 가변 청크 크기 설계안(구현 금지, 설계만)]
  적용 조건 게이트(필수):
      pushdown 가능 shape 에서만 적용. _reimport_source_needs_wrapping(req) == True
      (CTE/JOIN/UNION wrapping)이면 가변화 대상에서 제외하고 청크 1개(=DIRECT) 유지.
      근거: 5절 실측(청크당 고정비 340ms 전체 재스캔).
  입력(모두 이미 확보돼 있어 신규 조회 0회):
      source_count   : 2단계 COUNT — 이미 req.source_count 로 prepare 에 전달 중
      pk_min, pk_max : chunk 엔진 진입 직전 ora_pk_min_max 로 이미 조회 중
      throughput     : 첫 청크 실측(행수 ÷ 소요초). 정적 추정 대신 실측 피드백 사용
  산정식:
      density        = source_count / max(1, pk_max - pk_min + 1)        # PK 구멍 보정
      rows_per_chunk = clamp(target_seconds × throughput_rows_per_sec,
                             min_chunk_size(10,000), max_chunk_size(200,000))
      chunk_size_pk  = ceil(rows_per_chunk / density)                    # PK 값 기준 폭
      target_seconds = 60~300 (1~5분). 초기 throughput 미지 시
                       DEFAULT_TRANSITION.default_throughput_rows_per_sec(7,000) 사용
                       → 초기 chunk_size ≈ 7,000 × 120 = 840,000 → max 200,000 으로 clamp
  run 내 고정 규칙:
      위 값을 run 시작 시 1회 확정하고 checkpoint 에 기록. 실행 중 재산정 금지
      (CHUNK_SIZE_MISMATCH 로 재개가 깨짐). 다음 run 부터 실측 throughput 반영.
  explainability:
      metrics 에 chunk_size_basis = {source_count, pk_min, pk_max, density,
      target_seconds, throughput_used, throughput_source: MEASURED|DEFAULT, clamped}
      를 저장해 사후 설명 가능하게 한다.
  GB 유무와의 관계:
      이 개선은 GB=0 전용이 아니다. chunk 경로는 GB 를 크기 산정에 쓰지 않으므로
      GB 있는 경로도 완전히 동일하게 적용된다(개선 여지도 동일).

7. 진행률 표시를 포기해야 하는가 + 권장 대응책  (지시 7)
────────────────────────────────────────────────────────────────────────────
[답] **포기할 필요 없다.** 진행률이 안 보인 건 원리적 한계가 아니라 순서 문제다.
     실제 전수 merge 는 스트림이고 20,000행마다 진행 신호를 이미 낸다
     (services/exact_diff/agg_contribution.py:671). 실측에서도 CASE B 는 3회 발행됐다.
     문제는 그 앞에 무신호 471초짜리 표본 게이트가 붙어 있다는 것이다.
     표본 게이트만 정리하면 이 케이스 전체 소요가 **475초 → 약 3초**가 되어
     경고도 진행률 문제도 동시에 사라진다. "정직한 경고 유지"는 차선책이 아니라 불필요하다.

권장 대응책(우선순위 순, 이번 작업 범위 밖 — 구현하지 않음):

 (A) 최우선 — 표본 preflight 를 wrapping 소스에서 건너뛴다
     routes/agg_diff_route.py:344-404 _run_sampling_gate 진입부에
     _reimport_source_needs_wrapping(req) 이면 None 반환(= INCONCLUSIVE, 기존 전체 merge 진행).
     이미 dbms 불일치(:358)로 건너뛰는 선례가 있어 구조 변경 없이 조건 1개 추가다.
     근거: 전체 merge 2.7초 vs 표본 471초 — 표본의 목적(비용 절감)이 완전히 역전됐다.
     효과: 475초 → 약 3초. 경고 소멸. 판정 결과는 불변(표본은 게이트일 뿐 판정이 아님).

 (B) 표본 어댑터 shape 교체(A 를 못 쓰는 경우의 대안)
     dialects/oracle.py:301-304 의 anchor별 CROSS APPLY(N회 재스캔)를
     '원본 1패스 + PK 범위 IN/BETWEEN' 또는 'ROW_NUMBER 기반 1패스 샘플링'으로 바꾼다.
     단순 SELECT 는 현행도 anchor당 2.2ms 로 문제없으므로, wrapping 소스 전용 분기가 된다.

 (C) 표본 단계 비용 가드 + 진행 신호(어느 쪽을 택하든 필요)
     · 사전 프로브: anchor 8개 시범 실행 → 환산치가 임계(예: 60초) 초과면 표본 포기(INCONCLUSIVE).
       이번 케이스면 8 anchor 2.5초에서 즉시 판정 가능(총 2.5초 소요로 회피).
     · _expansion_steps 확장(2,000→5,000→10,000)에 누적 시간 상한 추가. 현재 상한 전무 —
       최악 17,000 anchor ≈ 67분까지 무신호로 갈 수 있다.
     · 표본 단계에도 progress_cb 발행(anchor i/N). 현재 이 구간은 last_progress_at=null 이라
       /jobs/active 가 START_ONLY 로만 보이고 정체와 구분이 안 된다.

 (D) UI 표시 개선(부수)
     ui/tabler_renderer.py:17107-17109 의 PREPARING 표시는 available_count(저장된 불일치 건수)
     하나만 보여준다. 그래서 "0건"으로 읽힌다. 같은 응답에 이미 들어 있는
     processed_source_count / chunks_done / chunks_total / sampling_status 를 함께 쓰면
     '무엇을 하는 중인지'가 드러난다(5단계 재이관 패널 _mvRi* 는 이미 그렇게 표시 중 — :26267, :26728).
     ※ 단, (A) 를 적용하면 이 구간 자체가 3초로 줄어 표시 개선의 실익은 작아진다.

 (E) 별개 — 청크 경로 자체가 CTE/JOIN 대량 소스에서 영구 미사용인 점
     _unique_native_key 강제 DIRECT(2절)는 '복합/문자 PK 드릴다운' 목적으로 도입됐는데,
     단일 숫자 PK + CTE wrapping 조합까지 함께 DIRECT 로 떨어뜨린다.
     현재는 pushdown 불가라 DIRECT 가 오히려 유리해 결과적으로 옳지만, 그 이유가
     코드/증적에 남아 있지 않다(조용한 전환). 사유 기록이 필요하다.
