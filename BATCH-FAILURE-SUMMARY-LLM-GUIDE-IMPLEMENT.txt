3. 안전조건 4가지 검증 결과 (지시서 §2, 실측)
════════════════════════════════════════════════════════════════════════
(a) 화면 표시 수치는 서버 집계값만
    → generate_batch_failure_summary() 는 batch_item 을 직접 순회해 total_items/failed_items/
      status_counts 를 만들고, LLM 은 summary_text(서술)만 만든다. 반환 dict 에 is_matched/
      diff_groups/verdict 등 판정 필드 0개(test_service_output_has_no_verdict_fields 통과).
      화면 필터 칩(status_counts)도 LLM 출력이 아니라 이 서버 값을 그대로 사용.

(b) 모델 입력에는 유형별 집계 + 대표 패턴(컬럼명+건수)만, 테이블명·원문 오류 메시지 금지
    → BatchFailureSummaryInput 필드셋 고정 확인(test_guide_input_has_only_aggregate_fields_
      no_table_or_raw_text). _extract_column_patterns() 가 이 배치에 실제 등장하는 target_table
      명을 후보에서 제외함을 실측 확인(test_extract_column_patterns_excludes_table_names_and_
      raw_message) — 실 Ollama 호출로도 재확인: 추출된 패턴 [{'column':'ORDER_DT','count':2},
      {'column':'TARGET','count':2}, {'column':'AMBIGUOUS','count':1}] 에 T_ORDER/T_CUSTOMER/
      T_PRODUCT/T_DISCOUNT/T_COUPON(이 배치의 실제 테이블명) 전부 미포함.
      LLM 에 넘기는 status_counts 도 "실패로 분류된 상태만"으로 좁혔다(최초 구현은 성공 건수까지
      넘겨 LLM 이 "DEFAULT_EXECUTE_OK 확인해보세요"류 노이즈 문장을 실제로 생성하는 것을 실측으로
      발견 → services/batch_failure_summary_service.py generate_batch_failure_summary() 내
      failure_status_counts 분리로 수정 후 재검증, 재발 없음 확인).

(c) 단정문 금지 — 제안형만
    → _ASSERTIVE_PATTERN(E1 과 동일 정규식) 재사용 + 실 Ollama(llama3.2:3b) 응답으로 실측:
      "원인은/이유는/틀림없이/확실히/반드시 + 습니다/입니다" 패턴 미검출 확인(assert 통과).
      단, 소형 로컬모델 특성상 "~로 인해 발생합니다"류 설명조 문장은 정규식을 통과하는 경우가
      있었다(예: "PARSE_ERROR는 잘못된 Column Name 등으로 인해 발생합니다") — E1 도 동일한 한계를
      가진 구조(프롬프트+정규식 이중방어이지 완전 차단은 아님)이며 이번 작업에서 새로 만든 위험은
      아니다.

(d) 미기동/비활성 시 서술형 요약 없이 폴백(라벨/값 표만)
    → 비활성(monkeypatch env=0)/explainer 예외/explainer None 반환/실패 0건 4가지 경로 전부
      available=False, summary_text="" 로 수렴함을 테스트로 확인(4건 통과). 화면은 카드 자체를
      숨긴다(_renderBatchFailureSummary — E1 처럼 고정 3줄 문구조차 띄우지 않음, 배치는 "요약할
      원인 유형" 자체가 없을 수 있어 고정 문구가 항상 맞지 않기 때문).
