================================================================================
■ 0. 맨 앞 요약 — 판정이 어떻게 바뀌었나
================================================================================

수정 전에는 CHAR_USED 를 아예 조회하지 않아 VARCHAR2(50 BYTE) 와 VARCHAR2(50 CHAR) 가
도구에게 똑같이 "50" 으로 보였다. 그래서 아래 비교가 항상 거짓이 되어 통과했다.

    t_len(50) < s_len(50)  →  거짓  →  "COMPATIBLE, 위험플래그 없음"

수정 후에는 선언 숫자를 그대로 믿지 않고 '실효 문자 수용량'으로 환산해 비교한다.

    원본 KO16MSWIN949 VARCHAR2(50 BYTE) → 한글 1자=2바이트 → 25자
    목적지 AL32UTF8   VARCHAR2(50 BYTE) → 한글 1자=3바이트 → 16자
    16 < 25  →  PRECISION_LOSS_RISK + CHAR_CAPACITY_SHRINK_RISK

  ** 실측 결과: 수정 전 코드는 12개 문자형 컬럼 전부를 COMPATIBLE 로 통과시켰고,          **
  ** 수정 후 코드는 같은 입력에서 9건을 PRECISION_LOSS_RISK 로 전환했다.                  **
  ** 반면 양측 캐릭터셋이 같은 실환경(둘 다 AL32UTF8)에서는 12건 전부 COMPATIBLE 유지 —   **
  ** 즉 판정 변화는 '캐릭터셋이 다른 경우'에만 발생하고 현재 환경 판정은 불변이다.        **


================================================================================
■ 1. 수정 내용 (파일별)
================================================================================

지침이 지정한 수정 대상은 2개 파일이었으나, 그 2개만 고치면 새 로직이 **도달 불가한 죽은
코드**가 되어 실제로 7개 파일을 건드렸다. 늘어난 5개는 전부 '값을 흘려보내는 배선'이며
판정 로직은 candidate_scoring_runner.py 한 곳에만 있다. 아래에 이유를 명시한다.

── 1-1. services/db_adapters/oracle.py  (지침 지정 ①)

  build_tgt_column_meta_query : 5컬럼 → **7컬럼** (6=char_used, 7=data_length)
  build_column_meta_query     : 4컬럼 → **6컬럼** (5=char_used, 6=data_length)
      기존 char_length 조회는 지침 1항대로 그대로 유지했다.
      **앞부분 컬럼 순서를 건드리지 않고 뒤에만 추가**했다 — 위치 기반으로 읽는 소비자와
      PG/MySQL 어댑터(여전히 5·4컬럼)를 깨지 않기 위한 선택이다.

  build_db_charset_query : **신설**
      지침 2항의 "캐릭터셋 정보를 어디서 확보할지 판단해 보고에 명시" 에 대한 답이다.
      → **기존에 재사용할 수 있는 조회 경로가 없어 신규 조회를 추가했다.**
        · 연결 계층(§1 관련) 은 캐릭터셋을 조회하지 않는다. connect() 는 user/password/dsn
          만 넘기고, oracledb 4.x 는 클라이언트를 항상 UTF-8 로 고정하므로 캐릭터셋을 알
          필요가 없었다(진단서 §1-2). 즉 재사용할 값이 애초에 존재하지 않는다.
        · 프리셋의 encoding/nencoding 필드는 **읽는 코드가 0건인 죽은 설정**이고(진단서
          §1-4) 드라이버가 그 인자를 받지도 않으므로 출처로 쓸 수 없다.
        · 따라서 진단서 §0/§7 이 실측에 사용한 SQL 을 그대로 재사용해
          `SELECT value FROM nls_database_parameters WHERE parameter='NLS_CHARACTERSET'`
          을 어댑터 메서드로 넣었다. read-only 1회, 바인드 없음.
      세션 뷰(NLS_SESSION_PARAMETERS)가 아니라 **DB 뷰**를 쓴 이유: 수용량은 '저장' 기준이고
      DB 캐릭터셋은 DB 생성 시 확정돼 접속별로 흔들리지 않는다.

── 1-2. services/candidate_scoring_runner.py  (지침 지정 ②)

  _CHARSET_CJK_BYTES_PER_CHAR : 캐릭터셋 → 한글 1자당 바이트 수 표(12종)
      AL32UTF8/UTF8=3, KO16MSWIN949/KO16KSC5601=2, US7ASCII 등=1, JA16EUC=3, ZHS16GBK=2 …
      **최댓값(AL32UTF8=4)이 아니라 한글 기준(3)** 을 쓴 이유: 최댓값을 쓰면 순수 ASCII
      컬럼까지 과도하게 경고한다. 진단서 §4-3 이 실측한 3바이트 기준을 따랐다.
      한계: 보충문자(이모지·희귀한자, 4바이트)가 실제 데이터에 있으면 이 계산도 낙관적이다.

  _effective_char_capacity(meta) : 신설 — 실효 문자 수용량 환산
      char_used='C' → char_length 그대로 (캐릭터셋 무관하게 선언 글자 수 보장 = 이미 안전)
      char_used='B' → data_length // 한글 1자당 바이트 수
      판단 불가 시 None → 호출측이 비교를 건너뛴다(없는 위험을 날조하지 않는다)

  _evaluate_compatibility 의 text-text 분기 : 수용량 비교 추가
      **발동 조건 3개를 모두 만족할 때만** 플래그를 올린다(판정 변화 범위를 최소화):
        (1) 어느 한쪽이라도 char_used='B'  — 바이트 의미가 개입해야 캐릭터셋이 수용량을 바꾼다
        (2) 실효 수용량이 실제로 줄어든다 (t_cap < s_cap)
        (3) 선언 길이는 줄지 않았다 (t_len >= s_len) — '숫자만 보면 안전해 보이는' 경우로 한정
      부여 결과: compatibility_status = PRECISION_LOSS_RISK (기존 어휘 재사용)
                risk_flags += CHAR_CAPACITY_SHRINK_RISK (신규, 설명용)
                risk_gate_blocked = False (경고 수준 — 검증 자체를 막지 않는다)

      status 를 신설하지 않고 기존 PRECISION_LOSS_RISK 를 재사용한 이유: COMPAT_PRIORITY /
      RISK_GATE_BLOCKED_STATUSES / UI 라벨맵 등 status 어휘가 여러 파일에 박혀 있어 신설하면
      영향 범위가 불필요하게 넓어진다. 구분이 필요한 정보는 risk_flag 로 분리했다.

── 1-3. 배선 4개 (지침에 없었으나 없으면 신규 로직이 죽는 파일)

  services/db_adapters/base.py

      _query_columns_info / _fetch_columns_info 도 동일하게 폭 가변 처리하고 char_used/
      data_length 를 결과 dict 에 **값이 있을 때만** 추가한다(PG/MySQL dict 는 키 개수까지 불변).

■ 2. 전/후 판정 결과 변화 목록 (실측)
================================================================================

방법: 동일한 검증 스크립트를 (a) 수정 전 코드가 있는 baseline worktree 와 (b) 수정 후 main
에서 각각 실행했다. 스크립트는 ColumnMeta 의 dataclass 필드를 런타임에 확인해 수정 전 코드에
없는 필드는 자동으로 생략하므로, 스크립트 1개로 진짜 Before/After 를 얻는다.
입력은 tobe 실 테이블 CDC_ALL_HIST 의 **실제 카탈로그 값**이며 컬럼명은 원본=목적지 동일
(col_renamed=False — 실 이관에서 가장 흔하고, 기존 길이 비교가 아예 동작하지 않던 조건)이다.

── 2-1. 시나리오별 집계

  ┌──────────────────────────────────────┬────────────────────┬────────────────────┐
  │ 시나리오                              │ BEFORE(수정 전)     │ AFTER(수정 후)      │
  ├──────────────────────────────────────┼────────────────────┼────────────────────┤
  │ D-1 양측 AL32UTF8 (실환경 그대로)      │ COMPATIBLE 12건    │ COMPATIBLE 12건    │
  │                                       │ 위험 0건           │ 위험 0건 ← **불변** │
  ├──────────────────────────────────────┼────────────────────┼────────────────────┤
  │ D-2 원본 KO16MSWIN949 → 목적지 AL32UTF8│ COMPATIBLE 12건    │ PRECISION_LOSS 9건 │
  │     (레거시 CP949 원본 이관 가정)      │ 위험 0건           │ COMPATIBLE 3건     │
  │                                       │                    │ ← **9건 전환**      │
  ├──────────────────────────────────────┼────────────────────┼────────────────────┤
  │ D-3 양측 KO16MSWIN949                 │ COMPATIBLE 12건    │ COMPATIBLE 12건    │
  │                                       │ 위험 0건           │ 위험 0건 ← **불변** │
  └──────────────────────────────────────┴────────────────────┴────────────────────┘

  → 판정이 바뀌는 것은 **D-2, 즉 양측 캐릭터셋이 다를 때뿐**이다.
    D-1/D-3 처럼 캐릭터셋이 같으면 수용량 비율이 양측 동일해 비교 결과가 그대로다.

── 2-2. 컬럼별 상세 (D-2, 실 카탈로그 값)

  COLUMN            CHAR_LEN  DATA_LEN  CHAR_USED  CP949 실효  UTF8 실효  전/후
  ───────────────────────────────────────────────────────────────────────────────
  CD_LOAD_NO             50        50       B         25자       16자    COMPATIBLE→PRECISION_LOSS_RISK
  CD_NODE_ALIAS         100       100       B         50자       33자    COMPATIBLE→PRECISION_LOSS_RISK
  CD_SCHEMA             100       100       B         50자       33자    COMPATIBLE→PRECISION_LOSS_RISK
  CD_TABLE              100       100       B         50자       33자    COMPATIBLE→PRECISION_LOSS_RISK
  CD_XID_LSN            100       100       B         50자       33자    COMPATIBLE→PRECISION_LOSS_RISK
  CD_OFFSET              30        30       B         15자       10자    COMPATIBLE→PRECISION_LOSS_RISK
  CD_TS                  30        30       B         15자       10자    COMPATIBLE→PRECISION_LOSS_RISK
  CD_DT                  30        30       B         15자       10자    COMPATIBLE→PRECISION_LOSS_RISK
  CD_REG_DT              17        17       B          8자        5자    COMPATIBLE→PRECISION_LOSS_RISK
  CD_OP                   1         1       B          0자        0자    COMPATIBLE (불변)
  CD_PK_EXIST_YN          1         1       B          0자        0자    COMPATIBLE (불변)
  CD_CDC_REG_YN           1         1       B          0자        0자    COMPATIBLE (불변)

  전환 9건 / 불변 3건. 불변 3건은 모두 VARCHAR2(1 BYTE) 로, 어느 캐릭터셋에서도 한글을 한 자도
  담을 수 없어(1//2=0, 1//3=0) 수용량이 줄지 않는다 — 경고하지 않는 것이 맞다.
  CHAR_USED='C' 컬럼은 이 테이블에 없었다(실측 분포: B 12건 / C 0건). 'C' 불변은 단위 테스트로 고정했다.

── 2-3. 판정이 바뀌지 **않는** 것을 확인한 항목(무회귀 경계)

  · 양측 캐릭터셋 동일 (AL32UTF8/KO16MSWIN949/US7ASCII) → COMPATIBLE 유지
  · CHAR_USED='C' 양측 + 캐릭터셋 상이 → COMPATIBLE 유지 (지침 2항: 이미 안전)
  · 캐릭터셋 미상/미등록 → COMPATIBLE 유지 (경고 날조 금지)
  · char_used/data_length/charset 미설정 기존 메타 → COMPATIBLE 유지
  · 역방향(AL32UTF8 → KO16MSWIN949, 수용량 증가) → COMPATIBLE 유지
  · 숫자형(precision/scale) 판정 → 기존 로직 그대로
  · 컬럼명 변경 + 선언 길이 축소(50→30) → 기존 경로 그대로 PRECISION_LOSS_RISK,
    신규 플래그는 붙지 않음
  · **PostgreSQL/MySQL 결과 dict 는 키 개수까지 완전 불변** (char_used 키를 아예 넣지 않음)

스크립트: scripts/dev_e2e/varchar2_byte_char_capacity_comparison_verify.py (커밋 포함)

── [A] 신규/변경 카탈로그 쿼리가 실 DB 에서 도는가 — **통과**
    밑줄 별칭 ORA-00911 전례가 있어 '실행된다'는 사실 자체를 확인했다.
      asis: build_tgt_column_meta_query 반환 7컬럼 / 7행, build_column_meta_query 6컬럼 / 7행
      tobe: build_tgt_column_meta_query 반환 7컬럼 / 14행, build_column_meta_query 6컬럼 / 14행
      (수정 전 동일 실행: 각각 5컬럼 / 4컬럼 — 폭 증가가 실측으로 확인됨)
    실측 CHAR_USED 분포: asis 문자형 5컬럼 전부 'B', tobe 문자형 12컬럼 전부 'B'
    실측 값 예: CD_LOAD_NO VARCHAR2 CHAR_LENGTH=50 DATA_LENGTH=50 CHAR_USED=B
               → 진단서 §4-2 의 "BYTE 의미에서 CHAR_LENGTH=DATA_LENGTH=선언 숫자" 재확인

── [B] 캐릭터셋 조회 — **통과**
    asis NLS_CHARACTERSET = AL32UTF8 / tobe NLS_CHARACTERSET = AL32UTF8 (양측 동일)
    → 진단서 §0 실측과 일치. **현재 테스트 환경은 캐릭터셋 차이를 재현하지 못하므로**
      D-2 는 원본 캐릭터셋만 KO16MSWIN949 로 치환해 실 컬럼 shape 위에 얹어 측정했다.
      (진단서 §3-3 이 정렬 붕괴를 재현할 때 쓴 것과 같은 방식 — 운영 코드에 실 데이터를 주입)

── [C] 앱 공통 경로가 넓어진 행을 소비하는가 — **통과**
    운영 함수 _cmn_fetch_tgt_col_meta(오라클, CDC_ALL_HIST) 직접 호출:
      컬럼 14개 정상 반환, 그중 12개에 char_used/data_length 실림, 언패킹 붕괴 없음
      예: CD_LOAD_NO type=varchar length=50 char_used=B data_length=50
    수정 전 동일 호출: 14개 반환, char_used 실린 컬럼 0개 (기존 동작 보존 확인)
    ※ 이 검증의 첫 시도는 asis 테이블명을 tobe 에 조회해 0행이 나왔다(스크립트 결함).
      tobe 실재 테이블로 고쳐 재측정한 값이 위 결과다 — 0행 상태로 '통과'라 쓰지 않았다.

■ 5. 지침 3항 — PG/MySQL/MSSQL '표시 길이 ≠ 실제 저장 용량' 검토 (설계 메모, 미구현)
================================================================================

지침대로 **오라클만 구현했고 타 방언은 코드를 건드리지 않았다.** 검토 결과를 남긴다.

── 5-1. PostgreSQL — **동일 문제 없음** (우선순위 낮음)
    varchar(n)/char(n) 의 n 은 **항상 문자 수**이며 byte 의미 선언이 존재하지 않는다.
    서버 인코딩은 저장 바이트만 바꾸고 선언 문자 수용량을 바꾸지 않으므로,
    현재 어댑터가 읽는 information_schema.character_maximum_length 는 그대로 비교 가능하다.
    단, 좁은 예외 1건: **server_encoding=SQL_ASCII** 는 바이트를 검증 없이 문자로 취급해
    한글 1자가 3문자로 계산된다 → 사실상 byte 의미와 같아진다. 실 이관에서 SQL_ASCII 를
    쓰는 원본을 만나면 오라클과 같은 조용한 축소가 발생할 수 있다.
    구현 시 필요한 값: SHOW server_encoding (또는 pg_database.encoding). 조회 경로 신설 필요.

── 5-2. MySQL/MariaDB — **문자 수용량 문제는 없으나 다른 축의 위험 있음** (우선순위 중)
    VARCHAR(n) 의 n 은 4.1 이후 **문자 수**라 캐릭터셋이 넓어져도 문자 수용량은 줄지 않는다.
    대신 바이트 기준 제약이 별도로 존재한다:
      · 행 최대 크기 65,535 바이트, 인덱스 키 접두사 제한(767/3072 바이트)
      · latin1(1B) → utf8mb4(4B) 전환 시 varchar(255)=1,020 바이트가 되어 인덱스/행 한계를
        넘을 수 있다 → **조용한 절단이 아니라 DDL/INSERT 실패**로 드러난다(성격이 다르다)
    유리한 점: information_schema.columns 가 character_maximum_length(문자)와
    **character_octet_length(바이트)를 모두 제공**하므로 추가 카탈로그 신설 없이 판정 가능하다.
    주의: MySQL 은 캐릭터셋이 **컬럼/테이블 단위**(columns.character_set_name)라, 오라클처럼
    DB 단위 1회 조회로 끝나지 않는다 — 구현 시 컬럼별 캐릭터셋을 함께 읽어야 한다.

── 5-3. MSSQL — **오라클과 가장 유사한 실제 위험** (우선순위 높음 — 다음 대응 권장)
    VARCHAR(n) = **n 바이트**, NVARCHAR(n) = **n 문자**(내부 2바이트). 그런데
    information_schema.columns.character_maximum_length 는 둘 다 n 을 돌려주므로
    **VARCHAR(50) 과 NVARCHAR(50) 이 똑같이 '50' 으로 보인다** — 오라클 CHAR_USED 미구분과 동일 구도.
    SQL Server 2019+ 의 UTF-8 collation(_UTF8) 을 쓰면 VARCHAR(50) 이 한글 16자로 줄어
    오라클 사례와 완전히 같아진다.
    구현 시 필요한 값: character_octet_length + collation_name(→ 코드페이지별 바이트 수).
    **단, 현재 MSSQLAdapter 는 build_tgt_column_meta_query / build_column_meta_query 를
    아예 구현하지 않아(base 의 None 반환) 이 판정 경로에 도달조차 하지 않는다.**
    따라서 MSSQL 대응은 '수용량 비교 추가'가 아니라 '컬럼 메타 조회 구현'이 선행 과제다.

── 5-4. 공통 구조 메모
    이번에 넣은 ColumnMeta.char_used/data_length/charset 3필드와 _effective_char_capacity 는
    방언 중립이다. 타 방언은 (a) 어댑터가 char_used 상당값('B'/'C')과 바이트 길이를 채우고
    (b) 캐릭터셋 조회를 build_db_charset_query 로 제공하면 **비교 로직 수정 없이** 동작한다.
    MySQL 처럼 컬럼 단위 캐릭터셋인 방언은 charset 을 컬럼별로 채우면 되므로 필드 위치도 맞다.
