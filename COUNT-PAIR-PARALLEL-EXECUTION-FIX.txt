2. 구현 내용 (기존 메커니즘 재사용 — 새 병렬 메커니즘 발명 없음)
────────────────────────────────────────────────────────────────────────────────
통계검증 stats_execute_service.execute_stats_validation 의 parallel_sides 경로와 **동일 규약**을 그대로 재사용:
  · ThreadPoolExecutor(max_workers=2) — Source/Target 각 1 worker (통계검증과 같은 방식)
  · 연결 재사용 scope 승계는 CONN-REUSE-PARALLEL 규약 그대로
    (export_connection_scope_state / adopt_connection_scope_state / connection_scope_cache_key)
    → fingerprint 가 서로 다를 때만 승계(같은 연결의 동시 사용 금지)
  · 결과 취합 순서 = source → target 고정 → 오류 보고는 항상 '원본 우선'

신규 함수(전부 count_common_service.py 내부):
  _count_pair_parallel_enabled()   병렬 사용 여부(기본 ON, env MV_COUNT_PAIR_PARALLEL=0 이면 순차 복귀)
  _physical_db_key / _different_physical_db   host:port/dbname 기준 물리 DB 동일 판정
        (single_validation_run_facade._different_physical_db 와 같은 판정 규칙. 저수준 서비스가
         상위 facade 를 import 하지 않도록 동일 규칙을 이 모듈 내부에 둠 — 의존 방향 유지)
  _run_one_count_side(role, conn, sql)  한쪽 COUNT 1회 실행(예외를 raise 하지 않고 반환값에 담음)
  _execute_count_sides(...)             둘 다 실행 대상 + 서로 다른 물리 DB → 병렬, 그 외 → 기존 순차
  _probe_flags_snapshot / _probe_adopt_flags / _probe_capture_thread_metrics / _probe_merge_thread_metrics
        count_exec_probe 는 thread-local 이라 worker 에서 계측이 유실된다. 부모의 force flag 를 승계하고
        worker 계측(events/conns/재사용·재시도 카운터)을 부모 스레드로 합산 → 계측 스냅샷이 순차와 동일.
        (계측 코드는 전 구간 try/except — 계측 실패가 COUNT 실행에 영향 주지 않음)

병렬 적용 조건(모두 만족해야 병렬):
  ① 원본·목적지 양쪽 모두 실행 대상(host + COUNT SQL 존재)
  ② MV_COUNT_PAIR_PARALLEL 이 0/false/off/no 가 아님(기본 ON)
  ③ 원본/목적지가 서로 다른 물리 DB(host:port/dbname 상이)
  → 같은 물리 DB / 한쪽만 실행 / kill-switch OFF 는 기존 순차 경로 그대로(실행 순서도 원본→목적지 유지)

6. 커넥션 동시 사용 안전 확인 (지침 요구사항 4)
────────────────────────────────────────────────────────────────────────────────
· services/connection_pool.py 는 **PostgreSQL 만 풀링**한다(모듈 docstring 명시). Oracle/MySQL/MSSQL 은
  매 호출 물리 연결 생성 후 close — return_conn 이 비-PG 를 즉시 close 한다(:191). 따라서 오라클 병렬
  COUNT 는 서로 다른 물리 연결 2개이며 공유 객체가 없다(동시 사용 위험 없음).
· POOL_MAX_IDLE_PER_KEY=4 는 **동시 사용 상한이 아니라 key 당 idle 보관 상한**이다. checkout(:150-177)에
  세마포어/블로킹이 없고, idle 이 없으면 새 물리 연결을 연다. 원본/목적지는 서로 다른 key
  (db_type/host/port/dbname/user/fingerprint)라 COUNT 쌍 1건이 요구하는 동시 연결은 key 당 1개 →
  4 ≥ 1 로 여유 충분(통계검증 세트 병렬이 쓰는 pool_headroom 기준 `>= 2` 도 충족).
· scope 승계는 fingerprint 가 다를 때만 → 같은 연결이 두 worker 에서 동시에 쓰이는 경로가 구조적으로 없다.
· 일괄검증 영향: batch 스케줄러 예산이 profile 당 동시 3(max_concurrent_per_source/target_profile)로
  row 수를 제한한다. 측면 병렬은 한 row 가 원본·목적지 연결을 '동시에' 쥐게 하지만, **profile 별 동시
  연결 상한(3)은 변하지 않는다**(원본 profile ≤3, 목적지 profile ≤3). 상한이 아니라 점유 시간대만 겹친다.
· 롤백 수단: env MV_COUNT_PAIR_PARALLEL=0 → 즉시 순차 복귀(서버 재기동만 필요, 코드 변경 없음).
