1. 무엇이 문제였나
────────────────────────────────────────────────────────────────────────────
STATS-VALIDATION-CHUNKED-VS-SINGLE-TRADEOFF-DIAGNOSE 의 2순위 권고 항목이다.
DBMS 어댑터 계층은 쿼리 실행 시간 상한을 apply_query_timeout(conn, cur, timeout_ms) 하나로
통일해 두었는데, PostgreSQL(SET statement_timeout)과 Oracle(connection.call_timeout)만 실제로
구현돼 있었고 MySQL·MariaDB·MSSQL 세 방언은 본문이 `return None` 이었다. 소스에도
"HOLD: 실DB 검증 후 … 적용 검토" 로 남아 있었다.

결과적으로 이 세 방언을 원본/목적지로 쓰면 4단계 통계검증 SQL 에 60초 상한이 설정돼 있어도
그 값이 DB 에 전혀 전달되지 않았다. 즉 상한이 있는 것처럼 보이지만 실제로는 무제한이었고,
쿼리가 끝날 때까지 서버 워커 스레드도 함께 붙잡히는 상태였다.

────────────────────────────────────────────────────────────────────────────
2. 어떻게 고쳤나
────────────────────────────────────────────────────────────────────────────
세 방언 각각의 '실제' 타임아웃 설정 방법이 서로 다르다는 점이 이번 작업의 핵심이었다.
같은 MySQL 계열이라도 변수 이름과 단위가 다르고, SQL Server 는 아예 SQL 로 걸 수 없다.

  MySQL   services/db_adapters/mysql.py
          SET SESSION max_execution_time = <ms>
          MySQL 5.7.8+ 의 세션 변수이며 단위가 이미 밀리초라 변환이 없다.
          문서상 read-only SELECT 에만 걸리는데, 이 도구의 상한 대상이 검증용 SELECT 라
          실사용 범위와 일치한다.

  MariaDB services/db_adapters/mariadb.py
          SET SESSION max_statement_time = <초>
          MariaDB 에는 MySQL 의 max_execution_time 변수 자체가 없다(실측: 11.1.3 에서
          SHOW VARIABLES 결과 0건). 단위가 '초(소수 허용)' 라 공통 계약인 ms 를 어댑터에서
          초로 변환한다. 이 DB 는 0 이 '무제한' 이라, 양수 상한이 반올림으로 0.0 이 되어
          무제한으로 뒤집히지 않도록 양수에는 0.001초 하한을 뒀다.

  MSSQL   services/db_adapters/mssql.py
          pyodbc connection.timeout = <초 정수>
          SQL Server 에는 '문장 실행 시간 상한' T-SQL 구문이 없다(SET LOCK_TIMEOUT 은 잠금
          대기 상한일 뿐 실행 시간 상한이 아니다). 그래서 PostgreSQL 처럼 SQL 로 걸 수 없고,
          ODBC 의 SQL_ATTR_QUERY_TIMEOUT 을 쓰는 Oracle 과 같은 계열의 방식이 된다.
          초 단위 정수만 되므로 양수는 올림해 최소 1초로 둔다 — 내림했다가 0(=무제한)이 되어
          상한이 사라지는 쪽을 막기 위해서다.

지시대로 apply_query_timeout 의 시그니처는 그대로 두었고 호출부는 한 줄도 고치지 않았다.
PostgreSQL/Oracle 어댑터도 건드리지 않았다. 계약도 두 어댑터와 대칭으로 맞췄다.

  - timeout_ms=None  → 아무 것도 하지 않는다(호출측이 값을 모르는 경우, 기존 설정 유지)
  - timeout_ms=0     → 명시적으로 무제한(0)으로 재설정한다
                       (재사용/pool warm 연결에 이전 scope 의 세션 설정이 남아, 상한을 요구하지
                        않는 이후 작업의 정상적인 장시간 쿼리가 오탐 취소되는 것을 막는다)
  - 적용 실패        → 예외를 전파하지 않는다. 미지원 버전이면 조용히 기존과 같은 no-op 이 된다.
  - supports_statement_timeout() 은 세 방언 모두 True 로 바꿨다(현재 이 값을 읽는 운영 코드는
    없고 어댑터 자체 문서/테스트용이다).

작업 중 발견해서 함께 처리한 것이 하나 있다. MSSQL 방식은 SQL 실행이 아니라 '속성 대입'
(conn.timeout = n)인데, 공통 경로는 재사용 연결을 프록시(_NoCloseConn)로 감싸 넘긴다. 이 프록시는
읽기(__getattr__)만 위임하고 쓰기(__setattr__)는 위임하지 않아서, 프록시에 속성을 걸면 실제 드라이버
연결에는 닿지 않고 조용히 무제한이 된다. 그래서 내부 실 연결(_real)까지 풀어 함께 설정하도록 했고,
프록시를 통과시키는 회귀 테스트도 넣었다.

[3-1] 실 DB 실측 — MariaDB 11.1.3 (192.168.0.211:3309 / nxdnp)

접속 가능한 실 인스턴스는 MariaDB 뿐이었다. MySQL 전용 인스턴스는 사내망에 없고, MSSQL 은
인스턴스도 pyodbc 드라이버도 없다(외부 패키지 금지 규칙상 드라이버를 새로 설치하지 않았다).

  M4 상한 0      세션변수 0 으로 재설정 → SLEEP(8) 이 다시 8.0초 완주             (무제한 복귀)
  M5 상한 None   직전 3.0초 설정이 그대로 유지 → 미변경 계약 확인

                 → 중단 + timeout 판별 (검증 SELECT 와 같은 형태에서의 확인)

스크립트 전체 판정 PASS 를 연속 재실행에서 재현했다.

[3-2] 실측에서 드러난 한계 — 상한은 하드 보장이 아니다

정직하게 남겨야 할 관측이 있다. MariaDB 의 중단은 타이머가 kill 플래그를 세우고 실행 중인
쿼리가 그 플래그를 확인하는 협조적 방식이라, 확인 지점이 듬성한 실행 단계에서는 상한을 넘겨서
끊기거나 아예 안 끊긴다.

  - SLEEP 계열(M2/M3)          : 관측 전부 2.00~2.01초 — 지정 시각에 정확히 중단
  - 사용자 테이블 조인(M7)     : 8회 중 5회 2.0초 정시, 3회 지연 중단(5.5 / 13.9 / 15.7초)
  - information_schema 조인(M8): 정시 중단도 있었지만 상한을 넘겨 완주(미중단)한 경우도 3회

즉 이번 수정으로 '무제한 → 실질적 상한'이 된 것은 분명하지만, '반드시 N초에 끊긴다'는
하드 보장은 아니다. M8 은 그래서 PASS/FAIL 판정에서 빼고 관측값만 기록하도록 스크립트를 짰다.
적용 실패가 아니라 DB 동작 사양이며, 실제 검증 워크로드인 사용자 테이블 SELECT 는 대체로
정시 중단된다.

5. 남는 이야기 (이번 범위 밖 · 보고만)
────────────────────────────────────────────────────────────────────────────
(1) 실사용 도달 경로 — 지금 MySQL/MariaDB/MSSQL 어댑터에는 connect() 구현이 없어
    (supports_connect()=False) 공통 실행 경로 _cmn_db_connect 는 이 방언들로 연결 자체를
    만들지 못한다. 따라서 이번 수정은 '연결이 생기면 상한이 걸린다'까지를 보장하는 것이고,
    운영에서 이 방언이 실제로 통계검증을 도는 것은 connect 구현(별도 트랙) 이후다.
    실측은 그래서 드라이버로 직접 연결해 어댑터 메서드를 호출하는 방식으로 했다.

(2) 프록시 뒤 속성 설정 — 3장에서 MSSQL 에 대해 처리한 문제는 Oracle 의
    conn.call_timeout 에도 똑같이 존재할 수 있다. db_query_service.py:558 처럼 프록시가
    넘어오는 호출부에서는 Oracle 의 속성 대입도 실제 연결에 닿지 않을 수 있다.
    (다만 재사용 연결은 checkout 시점(:471)에 실제 연결로 이미 한 번 적용되므로 완전한
    구멍은 아니다.) 근본 해결은 _NoCloseConn 에 __setattr__ 위임을 넣는 것인데,
    이번 지시 범위(어댑터 3파일)를 벗어나므로 건드리지 않고 보고만 한다.

(3) MySQL 실측 미완 — MySQL 전용 인스턴스가 확보되면 M2 에 해당하는 발화 실측
    (errno 3024)을 남기는 것이 좋다. 스크립트는 방언만 바꿔 재사용할 수 있는 구조다.
