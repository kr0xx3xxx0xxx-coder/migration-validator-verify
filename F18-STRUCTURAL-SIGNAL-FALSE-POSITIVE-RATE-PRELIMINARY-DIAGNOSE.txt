✅ 작업 완료 - 신호(a) 단조증가는 확정 관리컬럼에서 TPR 0%·업무컬럼 FPR 16~40%로 역상관, 신호(b) 동시성은 실DB 양성표본 0건 — F18 착수 보류가 데이터 기반 결론

■ 조사 목적과 성격
  BACKLOG.md F18("cd1류 컬럼의 관리컬럼 판정 3차 방어선")에 명시된 착수 전제 —
  "신호 후보의 오탐률 실측이 선행돼야 착수 가능" — 을 충족하기 위한 선행 실측이다.

  실 DB 접근은 SELECT / 카탈로그 조회만 수행했다(DDL·DML 없음).

  services/candidate_subtype_service.py
    - detect_system_audit_value_verdict()   : A축 3-state(True/False/None) 본체
    - detect_system_audit_value_pattern()   : 위를 bool 로 접는 래퍼

2. 신호 (a) 단조증가 — 조작적 정의와 실측
──────────────────────────────────────────────────────────────────────────────
  [조작적 정의]
    정렬키를 오름차순으로 고정하고 행을 읽었을 때(선두 10,000행, 소표본 측정은 20,000행),
    NULL 이 아닌 인접 값 쌍 (v[i], v[i+1]) 중
      · mono_ratio   = v[i+1] >= v[i] 인 쌍의 비율 (비감소)
      · strict_ratio = v[i+1] >  v[i] 인 쌍의 비율 (엄격증가)
    정렬키는 단일 컬럼 PK 가 있으면 PK, 없으면 물리순서(ctid).

  [정의의 타당성과 한계 — 이것이 이번 조사의 핵심 발견이다]
    "값이 단조증가한다"는 명제는 정렬 기준 없이는 정의되지 않는다. 그런데 이 도구가
    4개 방언(oracle/mysql/postgresql/mssql)에서 이식 가능하게 쓸 수 있는 정렬 기준은
    사실상 PK 뿐이다. 물리순서(ctid)는 PostgreSQL 전용이고, 오라클 rowid 는 의미가 다르며,
    MySQL/MSSQL 에는 대응 개념이 보장되지 않는다. 게다가 PG 에서조차 ctid 는 UPDATE·VACUUM
    으로 재배치되어 안정적이지 않다.
    아래 [표3]이 보여주듯 이 신호의 결과는 정렬키 선택에 따라 정반대로 뒤집힌다.
    즉 신호(a)는 "측정 대상의 성질"이 아니라 "측정 방법의 우연"을 재는 쪽에 가깝다.

  [표1] 광역 스윕(479컬럼) — threshold 별 발화율

  │              │ (TPR, n=19)          │ (FPR, n=460)          │

  │ mono   >=1.00│  9/19  (47%)         │ 123/460  (27%)        │

  고유값이 1개인 상수 컬럼이라 "비감소"가 공허하게 참이 된 경우다(strict=0.000).
  상수 공허참을 제거한 strict 기준에서는 TPR 이 정확히 0%로 떨어지고 FPR 만 16~45% 남는다.
  즉 이 신호는 약한 것이 아니라 **방향이 반대**다.

3. 신호 (b) 갱신 시점 동시성 — 조작적 정의와 실측 가능성
──────────────────────────────────────────────────────────────────────────────
  [조작적 정의]
    같은 테이블 안의 확정 관리컬럼 R(A축 True)을 기준축으로 두고, 대상 컬럼 C 에 대해
      cooc_day(C,R) = 같은 행에서 date(C) == date(R) 인 행의 비율
      cooc_min(C,R) = 같은 행에서 분단위 절단값이 같은 행의 비율
    "다른 관리컬럼과 함께 갱신된다"를 행 단위 시각 일치로 조작화한 것이다.

  [실측 결과 — 양성 표본이 존재하지 않는다]
    광역 스윕 80개 테이블의 확정 관리컬럼 보유 개수 분포:
      ┌────────────────────────┬────────────┐
      │ 확정 관리컬럼 0개      │ 61 테이블  │
      │ 확정 관리컬럼 1개      │ 19 테이블  │
      │ 확정 관리컬럼 2개 이상 │  0 테이블  │
      └────────────────────────┴────────────┘
    asis/tobe 양쪽 DB를 통틀어 관리컬럼을 2개 이상 가진 테이블이 단 하나도 없다.
    신호(b)는 정의상 관리컬럼 쌍이 있어야 양성 사례를 만들 수 있으므로
    **TPR 표본 수 = 0** 이다. TPR 을 추정할 방법이 지금 데이터에는 없다.

    음성 쪽만 측정 가능했다: 대상 컬럼 50개 × 같은 테이블 관리컬럼 1개 쌍
      · cooc_day 값 집합 = {0.000, 0.003, 0.004}
      · cooc_min 값 집합 = {0.000}
      · 어떤 threshold(>=0.50 이상 전 구간)에서도 오탐 0/50 (0%)
    다만 이 0%는 신호의 강건함이 아니라 픽스처 설계의 산물이다. asis01 픽스처의
    업무 날짜는 적재일과 무관한 과거 난수 일자로 생성돼 있어, 애초에 겹칠 수 없다.
    실 운영계에서 흔한 "레코드가 적재 당일 생성되는 업무 등록일시"가 표본에 없다.

  [합성 시나리오 분석 — ★ 실측 아님, 구조 확인 목적]
    양성 표본 부재로 TPR 을 못 재므로, 신호가 무엇을 구분하고 무엇을 못 구분하는지만
    합성 데이터(5,000행, 배치 스탬프 3종)로 확인했다. 아래 수치는 합성이며
    실측치로 인용해서는 안 된다.
    ┌────────────────────────────────────────┬────────┬────────┬────────┐
    │ 시나리오                               │ cooc_day│cooc_min│ 정답   │
    ├────────────────────────────────────────┼────────┼────────┼────────┤
    │ S1 동일 배치가 찍은 두 번째 관리컬럼   │ 1.000  │ 1.000  │ 양성   │
    │ S2 같은 배치·적재순서로 0~9분 지연     │ 1.000  │ 0.099  │ 양성   │
    │ S3 관리컬럼이나 전일 야간 별도 배치    │ 0.000  │ 0.000  │ 양성   │
    │ S4 업무 등록일시(적재 당일 생성 설계)  │ 1.000  │ 0.000  │ 음성   │
    │ S5 업무 날짜(과거 임의 일자)           │ 0.000  │ 0.000  │ 음성   │
    │ S6 업무 마감일시(같은 날 다른 고정시각)│ 1.000  │ 0.000  │ 음성   │
    └────────────────────────────────────────┴────────┴────────┴────────┘
    · 일(day) 단위: S4·S6(업무) 이 S1·S2(관리) 와 완전히 같은 1.000 이라 분리 불가.
    · 분(minute) 단위: S2·S3(관리) 를 놓쳐 재현율이 붕괴하고 S1 만 남는다.
    어느 입도에서도 분리 경계가 존재하지 않는다.

  [더 근본적인 적용 범위 문제]
    3차 신호가 호출되는 조건은 "A축이 None" 이다. 그런데 A축이 None 을 내는 주된 이유는
    값이 타임스탬프로 파싱되지 않기 때문이다(코드/번호/CHAR8 날짜 등 — 관할 밖).
    신호(b)는 대상 컬럼의 "갱신 시점"을 읽어야 성립하는데, 대상이 타임스탬프가 아니면
    시점 비교 자체가 불가능하다. 즉 신호(b)의 적용 가능 영역과 F18 이 구하려는
    cd1류 사각지대는 사실상 서로 겹치지 않는다.
    실측 뒷받침: 코멘트 없음 + A축 None 인 cd1류 부분집합 49컬럼 중 확정 관리컬럼 0건,
    그리고 이들 대부분(ymd 계열 CHAR8 등)이 타임스탬프가 아니어서 동시성 계산 불가.

──────────────────────────────────────────────────────────────────────────────
4. 억지 자동판정 금지 원칙과의 충돌 여부
──────────────────────────────────────────────────────────────────────────────
  충돌한다 — 지금 데이터 기준으로는 명백하게 충돌한다.

  · 현행 판정은 B=False + A=None 을 NOT_AUDIT_AMBIGUOUS(근거부족 배지)로 두고
    배제·점수·선정에 전혀 영향을 주지 않는다. 즉 "모르면 아무것도 하지 않는다"이며
    이것이 세션03 원칙의 구현이다.
  · 여기에 신호(a)를 3차 근거로 넣으면, 판정이 없던 자리에 판정이 생긴다. 그런데
    그 판정의 실측 오탐률은 16~58%다. 특히 그 신호가 실제로 발화하는 모집단
    (A축 None 458컬럼)에는 확정 관리컬럼이 0건이므로, 발화 = 오탐이다.
  · 관리컬럼 확정(CONFIRMED)은 GROUP BY 자동선정 배제·체크박스 하드 배제까지 가는
    비가역적 판정이다. 오탐 1건의 비용이 미탐 1건보다 크다(사용자가 쓰려던 업무
    코드 컬럼이 조용히 사라진다). 오탐률 16%조차 수용 한도를 넘는다.
  · 신호(b)는 오탐을 논하기 이전에 양성 표본이 0건이라 "맞히는지 여부"를 아직
    한 번도 확인하지 못한 신호다. 검증되지 않은 신호를 판정 근거로 넣는 것 자체가
    억지 자동판정에 해당한다.

──────────────────────────────────────────────────────────────────────────────
5. 착수 가능 여부 결론
──────────────────────────────────────────────────────────────────────────────
  ▶ 결론: 두 신호 모두 **착수 보류**. threshold 를 제안하지 않는다.

  보류 이유(숨기지 않고 전부 명시):
   (1) 신호(a)는 약한 신호가 아니라 방향이 반대인 신호다. 이식 가능한 유일한 정렬
       기준인 PK 정렬에서 확정 관리컬럼의 발화율이 0/7(0%)이고, 업무 컬럼은
       79/327(24%)이 발화한다. 어떤 threshold 를 잡아도 TPR < FPR 이므로
       분리 경계가 존재하지 않는다.
   (2) 신호(a)의 겉보기 TPR 47%(mono>=1.0)는 상수 컬럼의 공허참이다.
       엄격증가로 바꾸면 TPR 이 0%가 된다.
   (3) 신호(a)의 결과는 정렬키 선택으로 뒤집힌다(PK 0% ↔ ctid 75%). 측정 대상의
       성질이 아니라 측정 방법의 우연을 재고 있다. ctid 의존은 PG 전용이라
       "4개 방언 모두 처리" 규칙과도 충돌한다.
   (4) 신호(b)는 실 DB 전체(80 테이블)에 관리컬럼 2개 이상 테이블이 0개라
       TPR 표본이 0건이다. 정확도를 측정한 적이 없는 신호다.
   (5) 신호(b)의 음성 오탐 0/50 은 픽스처가 "적재일과 무관한 과거 난수 업무일자"로
       구성된 결과이지, 신호의 강건함이 아니다. 합성 시나리오에서 실 운영계에 흔한
       "적재 당일 생성 업무 등록일시"를 넣자마자 일 단위 동시성이 1.000 으로 붙어
       관리컬럼과 구분되지 않았다.
   (6) 신호(b)의 적용 영역(대상이 타임스탬프여야 함)과 F18 이 메우려는 사각지대
       (A축이 타임스탬프로 못 읽어 None 이 난 컬럼)가 구조적으로 거의 겹치지 않는다.

  ▶ threshold 제안: 없음.
    "오탐 위험 감수보다 판별 불가 유지가 항상 안전"이라는 원칙에 따라, FPR 이 0 에
    가깝지 않으면 제안하지 않는다는 기준을 그대로 적용했다. 실측 FPR 최저치가 16%다.

  ▶ 현행 동작 유지 권고
    B=False + A=None → NOT_AUDIT_AMBIGUOUS(배지만 표시, 판정·배제·점수 불변)를
    그대로 둔다. 3차 방어선을 자동판정으로 만들지 말고, 지금처럼 사용자 검토를
    유도하는 표시에 머무르는 것이 현재 데이터가 지지하는 유일한 선택이다.

6. (참고) 예상 구현 범위 — 실제 구현하지 않았음
──────────────────────────────────────────────────────────────────────────────
  착수 보류가 결론이므로 구현 계획이 아니라, 향후 재검토 시 어디를 건드리게 되는지의
  범위 표시만 남긴다. 이번 작업에서 아래 파일은 읽기만 했고 수정하지 않았다.
    · services/candidate_subtype_service.py
        - 신호 계산 함수 추가 위치: detect_system_audit_value_verdict 인근(A축 계열)
        - 판정 결합 위치: evaluate_admin_audit_crosscheck 의 axis_a 산출 직후
          (판정표에 3번째 축을 추가하는 형태 — 단, 현재는 추가 대상 없음)
        - 신호 계산에는 값 샘플 외에 "정렬키 순서로 읽은 값 시퀀스"가 필요한데,
          현재 candidate 에 실려오는 sample_values 는 순서 보장이 없다. 즉 신호(a)를
          넣으려면 후보 수집 경로(값 샘플링)부터 계약을 바꿔야 한다 — 파급이 크다.
          이 사실 자체도 착수 보류 근거에 해당한다.

7. 제한사항 / 한계
──────────────────────────────────────────────────────────────────────────────
  · 양성 표본(확정 관리컬럼)이 19개로 작다. 다만 19개 중 PK 정렬 7개가 전부 0% 발화,
    나머지 12개 중 9개가 상수 공허참이라, 표본을 늘려도 방향이 뒤집힐 여지는 낮다고 본다.
    그럼에도 "19개 기준"이라는 점은 결론의 강도를 제한한다.
  · 관리컬럼 라벨은 현행 A축(값 기반) 판정을 정답으로 삼았다. A축 자체에 미탐이 있다면
    일부 실제 관리컬럼이 음성 쪽에 섞여 FPR 을 과대추정했을 수 있다. 다만 그 방향의
    보정은 결론(보류)을 뒤집지 못한다 — 신호(a)의 TPR 0%가 먼저 걸리기 때문이다.
  · 실측 대상 DBMS 는 PostgreSQL 단일이다. oracle/mysql/mssql 실측은 하지 않았다.
    특히 정렬키 문제(표3)는 방언별로 더 나빠질 뿐 좋아질 요인이 없다.
  · 조회창은 테이블당 선두 10,000행(소표본 측정 20,000행)이다. 전량 스캔이 아니므로
    창 밖에서 단조성이 깨질 가능성은 남는다. 이 방향의 오차는 FPR 을 과소추정하는
    쪽(=신호에 유리한 쪽)이므로 보류 결론을 약화시키지 않는다.
  · 신호(b)의 시나리오 표는 합성 데이터다. 실측 근거가 아니며, "구분되지 않는 구조가
    존재한다"는 반례 제시 용도로만 유효하다. 실측을 하려면 관리컬럼을 2개 이상 가진
    테이블(예: created_at + updated_at 동시 보유)을 먼저 확보해야 한다.
  · 조사용 임시 스크립트는 C:\projects\migration-validator\scratchpad\ 아래 f18_* 로
    남겼다(코드 저장소 커밋 대상 아님). 코드 저장소에는 어떤 변경도 가하지 않았다.
