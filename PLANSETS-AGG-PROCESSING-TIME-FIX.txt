작업명 : PLANSETS-AGG-PROCESSING-TIME-FIX

===============================================================================
1. 배경과 수정 대상
===============================================================================
선행 진단(STAGE4-5-STATUS-TIMING-DISPLAY-STALE-DIAGNOSE)이 확정한 근본원인:

  GROUP BY 2개 이상 선택 시 클라이언트는 다중 세트 경로(_runExecutePlanSets)로 분기하는데,
  이 경로가 만드는 세트 합산 객체 agg 에 processing_ms 필드가 아예 없다.
  표시 함수 _mvShowStageProcessingTime 은 `if (ms == null) return;` 로 조기 반환하므로

    (A) 5단계 상단 슬롯(mvStage5ProcessingTime)에 clear 가 넣어둔 "5단계 계산 중..."
        잠정 문구가 실행 완료 후에도 그대로 남아 영구 고착된다.
    (B) 4단계 슬롯(mvStage4ProcessingTime)의 실행 완료 갱신도 `r.processing_ms != null`
        가드에 막혀 /generate 시점 값("0.01초 미만")에 그대로 묶인다.

같은 모양의 결함이 서버 원클릭 경로(services/single_validation_run_facade._run_multi_gb_sets)의
agg 리터럴에도 대칭으로 존재했다(주석에 "클라 _runExecutePlanSets agg 와 동형"이라 명시돼 있음).

수정 대상 파일:
  - ui/tabler_renderer.py                      (클라 다중 세트 agg + runExecute finally 안전망)
  - services/single_validation_run_facade.py   (서버 원클릭 경로 agg — 클라와 대칭)
  - ui/validation_plan_renderer.py             (표시 함수에 선택 인자 label 추가)
  - ui/js_sql_preview.py                       (4단계 생성 시점 라벨)

지침이 요구한 적용 순서 (2) → (1) → (3) 을 그대로 지켰다.

2. 수정 내용
===============================================================================
(2) 안전망 — 5단계 finally 잔여 "계산 중" 청소  [ui/tabler_renderer.py, runExecute]

  runExecute 의 다중 세트 분기 finally 에, 2단계(COUNT)가 같은 증상에 붙인 청소 패턴
  (COUNT-GATE-LIVE-SESSION-LABEL-MISMATCH-FIX)의 조건식·구조를 그대로 재사용했다.
  새 패턴을 발명하지 않았다.

      if (_ver === _singleSessionVer()) {
        try {
          var _s5pt = document.getElementById('mvStage5ProcessingTime');
          if (_s5pt && (_s5pt.textContent || '').indexOf('계산 중') >= 0) _s5pt.textContent = '';
        } catch (e) {}
      }

  세션 가드 안에 둬서 늦게 끝난 이전 세션이 새 세션 표시를 건드리지 않게 했다(§40 동일 취지).
  근본수정 (1) 이 적용되면 정상 종료에서는 이미 처리시간으로 교체돼 있어 no-op 이다 —
  실행계획 생성 실패·세트 없음 같은 조기 return, 예외, abort 종료에서만 실제로 발동하는
  최후 방어선으로 남긴다.

(1) 근본 수정 — agg 에 처리시간 포함 (클라/서버 대칭)

  ■ 클라이언트 (ui/tabler_renderer.py, _runExecutePlanSets)
      함수 진입 직후 벽시계 시작 → 전 세트 루프 종료 직후 경과 확정 → agg 리터럴에 포함.

        var _psT0 = (window.performance && performance.now) ? performance.now() : Date.now();
        ...(/groupby-plan → 세트별 /generate + /execute 루프)...
        var _psWallMs = Math.round((now - _psT0) * 10) / 10;
        var agg = { ..., processing_ms: _psWallMs };

      세트별 processing_ms 단순 합산을 쓰지 않은 이유(지침 지시대로):
      서버가 조건 충족 시 최대 2세트를 동시 실행(_stats_set_parallelism)하므로 합산값은
      실제 벽시계보다 커져 부정확하다. 감싸는 방식은 순차/병렬 어느 쪽이든 사용자가 실제로
      기다린 시간과 일치한다.
      시작점을 함수 진입(= /groupby-plan 호출 이전)으로 잡은 것은, 이 경로의 4단계 진행
      표시가 이미 "세트 계획(/groupby-plan) 구간도 실행 시간에 포함된다"고 선언하고 있는
      것과 맞추기 위함이다.
      단위·자릿수는 서버 라우트(routes/execute_route.py)의 round(..., 1) 규약과 동일하게 맞췄다.

  ■ 서버 (services/single_validation_run_facade.py, _run_multi_gb_sets)
      동일 구조로 세트 실행 전체를 감싸는 perf_counter 벽시계 1개를 두고 agg 에 넣었다.

        import time as _pt_rt
        _pt_t0 = _pt_rt.perf_counter()
        ...(_stats_set_parallelism 판정 → 순차 또는 최대 2세트 병렬 실행)...
        _pt_wall_ms = round((_pt_rt.perf_counter() - _pt_t0) * 1000.0, 1)
        agg = { ..., "processing_ms": _pt_wall_ms }

      한쪽만 고치면 단계별 수동실행(클라) 또는 원클릭(서버) 중 하나만 나아지므로 양쪽 다 고쳤다.

(3) 문구 정정 — 4단계 라벨이 실행시간을 암시하는 오해 해소

  ui/validation_plan_renderer.py 의 _mvShowStageProcessingTime 에 선택 인자 label 을 추가했다.
  기존 호출부(1/2/4-실행완료/5단계)는 인자를 넘기지 않으므로 문구가 그대로다 — 기존 표기 관례
  "N단계 XXX: 값" 을 유지했고 새 용어를 만들지 않았다.

        span.textContent = label ? (' · ' + stageNum + '단계 ' + label + ': ' + _mvFmtStageDur(ms))
                                 : (' · ' + stageNum + '단계 처리시간: ' + _mvFmtStageDur(ms));

  ui/js_sql_preview.py 의 renderSQL(= SQL 생성 직후)만 label 을 넘긴다:

        _mvShowStageProcessingTime(4, g.processing_ms, 'SQL 생성 시간');

  → 생성 시점  : " · 4단계 SQL 생성 시간: 0.01초 미만"   (DB 접속 없음 — 진단 §4-B3 확정)
    실행 완료  : " · 4단계 처리시간: 0.83초"             (실제 실행시간으로 덮어씀)

  (1)과의 상호작용: (1)이 적용돼 다중 세트 실행 완료 후에도 4단계 슬롯이 실제 값으로 갱신되므로,
  구분 표기는 "생성 시점"에만 해당한다. 실행 완료 시 갱신 경로(_mvRenderValidationDetail)는
  label 을 넘기지 않아 기존 "처리시간" 라벨을 유지한다.
