3. 지침 전제 1건과 실측의 불일치 (M4)
════════════════════════════════════════════════════════════════════════════════
지침의 M4 요약은 "8건을 tmp_path 기반으로 전환해 운영 SQLite 가드에 막히던 실패를 해소" 였다.
그런데 근거 보고서 `STEP-TAB-DOM-STABILITY-TEST-SQLITE-GUARD-FIX.txt` 는 §1 에서 그 전제를
스스로 반증하고 있다.

  · 해당 테스트 파일에는 운영 SQLite 경로 참조도, sqlite3 import 도 아예 없다
    → tmp_path 전환 대상 자체가 존재하지 않아 요구사항 1·2 는 적용 불가였다
  · 실패 메시지에 [PROD-DB-WRITE-BLOCKED] 가 등장하지 않는다
    (실제 실패는 node 런타임 TypeError: Cannot read properties of null (reading '_uid'))
  · 진짜 원인은 테스트 하니스의 낡은 계약이었다 — 개별 nav 스텁 이름이 showSingleStep 이라
    renderMvStepNav 의 소유자 판정(onClick === _mvNavClick)에서 일괄 writer 로 오판돼 조기 return,
    DOM 이 0개가 되어 이후 단정이 전부 null 참조로 붕괴했다. 스텁 이름을 _mvNavClick 으로 맞춰 해소.
  · 그 보고서 자체가 "백로그 M4/M5 의 원인 진단은 정정이 필요하다" 고 적고 있다(§1 마지막 줄)

지침을 글자 그대로 옮기면 백로그에 이미 반증된 원인 진단이 '해결 요약' 으로 고정된다. 그래서
해결 완료 표시는 지침대로 하되, 제목을 `✅ 해결 완료(원인 진단 정정 — SQLite 가드가 아니었다)` 로
달고 본문에 위 실측을 '원인 진단 정정(실측)' 으로 명시했다.

추가로 남는 사실 2가지를 '잔여(미해결)' 로 남겼다.
  ① M4 가 예시로 들었던 test_batch_report_service.py 등 다른 테스트군은 이번 범위 밖이다.
  ② 백로그 M5 는 M4 와 달리 정확히 같은 파일(test_step_tab_dom_stability.py) 8건을 가리키므로
     사실상 함께 해소됐다. 다만 이번 지침의 범위가 M4 뿐이고 "다른 항목은 절대 건드리지 말 것"
     이었으므로 M5 표기는 손대지 않았고, M4 본문에 교차참조만 남겼다.
     → M5 의 해결 완료 표시는 다음 정리 대상이다(이 보고서로 인계).
