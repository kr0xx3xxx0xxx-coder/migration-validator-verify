[G1] dialect 인자 미전달 → 오라클 계약 SQL 을 postgres 로 오파싱
  routes/diagnosis_route.py:804-807  diagnose_multi_scope(...) 호출 — dialect 인자 없음
  routes/diagnosis_route.py:827-830  rd.execute_row_diff(...) 호출 — dialect 인자 없음
  두 호출 모두 하류 함수의 dialect 기본값("postgres")으로 떨어진다. OracleHashContract 가 방출하는
  SQL fragment(3인자 TO_CHAR, BITAND, STANDARD_HASH 등)를 sqlglot 이 postgres 방언으로 파싱하려 하면
  ParseError 로 SQL 생성 자체가 실패한다. 이미 존재하는 _routing_dialect(req) 헬퍼를 두 호출부에
  전달하기만 하면 해소되는 형태 — 실측으로 확인.

[G2] row_diff 바인드 플레이스홀더가 오라클 드라이버와 불일치
  services/diagnosis/row_diff.py:76,81  exp.Placeholder() 사용 지점
  이 표현식이 oracle 방언으로 렌더될 때 '?' 로 나오는데, python-oracledb 는 위치 바인드로 '?' 를
  지원하지 않아 DPY-4009 로 실패한다(PG 는 '%s' 로 렌더되어 정상 동작). exact_diff 오라클 이식(이미
  SUPPORTED)이 이 문제를 어떻게 회피했는지 참고해 동일 패턴 적용이 필요해 보이나, 구체적 수정 방식은
  ⑤⑥ 범위 밖이라 설계하지 않았다.

위험도: 둘 다 **fail-closed**(거짓 일치가 아니라 실행 자체가 EXECUTION_ERROR/파싱 예외로 막힘)이므로
데이터 정합성 위험은 없다. 다만 ⑥ 등록 이후 오라클 페어는 더 이상 "계약 없음 HOLD" 가 아니라
"EXECUTION_ERROR" 로 실패 사유가 바뀌므로, 오라클 사용자에게 HASH_BUCKET 을 실제로 제공하려면 G1·G2
후속 배선 지시가 별도로 필요하다. 다음 착수자는 이 보고서의 route_wiring_gap_probe.json 실측 결과부터
재사용해 착수할 것을 권고한다.

7. 결론
════════════════════════════════════════════════════════════════
G7-HASH-BUCKET-ORACLE 시리즈의 계약 계층(①③④⑤⑥)은 이번 작업으로 전부 완료·라이브 검증까지 마쳤다.
오라클↔오라클 canonical hash 계약은 코드/설정 상으로 완전히 개방됐고, DIRECT_STREAM_COMPARE 대비 PK
집합 완전일치·NLS 방어 실효·상한 방어 실효·cross-DBMS 무회귀·PG 무회귀까지 전부 실측 PASS 다.
단, 운영 라우트(routes/diagnosis_route.py)의 dialect 배선(G1)과 row_diff 의 오라클 바인드 표기(G2)가
남아 있어, 사용자가 실제로 오라클 테이블 쌍에 HASH_BUCKET 을 실행하면 지금은 EXECUTION_ERROR 로
막힌다 — "계약 완료"를 "기능 완료"로 오인하지 말 것.
