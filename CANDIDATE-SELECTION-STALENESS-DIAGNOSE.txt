작업명 : CANDIDATE-SELECTION-STALENESS-DIAGNOSE
✅ 작업 완료 - CANDIDATE-SELECTION-STALENESS-DIAGNOSE - 검증 판정값(COUNT/SUM diff)은 매번 실 DB 재조회라 안전하나, 3단계 후보 프로파일(distinct_count)이 브라우저 메모리에 그대로 실려 4단계 GROUP BY '실행 안전 게이트'의 1순위 근거로 재사용되며 TTL·재조회·수집시각 대조가 전무 → 안전 게이트 한정 실질적 위험 있음

────────────────────────────────────────────────────────────────────────
조사 일시 : 2026-07-31 (KST)
조사 성격 : 읽기 전용 정적 코드 추적 — 운영 코드 수정 0건 · DB 접속 0건 · 테스트 실행 0건
조사 대상 : 개별검증 3단계(후보 선정) → 4단계(통계검증 실행) → 5단계(재이관 드릴다운)
근거 커밋 : 520eecb (main)

■ 요약 (결론 먼저)

판정 : **실질적 위험 있음** — 단, 영향 범위를 정확히 좁혀야 한다.

  ┌──────────────────────────────────────────────────────────────────┐
  │ 영향 없음 : 검증 결과의 정확성(PASS/WARNING/SKIP, 그룹별         │
  │             COUNT/SUM 불일치 건수). 4단계는 통계검증 SQL 을      │
  │             매번 원본/목적지에 실제로 실행하므로 비교값은 항상   │
  │             실행 시점 데이터다. 이건 stale 될 수 없다.           │
  ├──────────────────────────────────────────────────────────────────┤
  │ 영향 있음 : GROUP BY '실행 안전 게이트'(예상 그룹 수 상한 차단). │
  │             이 게이트만은 3단계에서 계산된 distinct_count 를     │
  │             그대로 믿고, 신선도를 한 번도 확인하지 않는다.       │
  └──────────────────────────────────────────────────────────────────┘

즉 이것은 "검증 결과가 틀리는" 버그가 아니라 **"폭주 차단 장치가 옛 값으로 판정해
열려버리는"** 문제다. 심각도를 그렇게 읽어야 정확하다.

부수 발견(중요) : `candidate_snapshot_full` 은 코드 주석 3곳에서 일관되게
"증적용이며 **실행 판정에는 사용하지 않는다**" 라고 선언돼 있으나, 실제로는 실행
안전 게이트의 1순위 판정 근거다. 선언과 동작이 정반대다. 이 오선언이 바로 이 필드에
대해 아무도 staleness 를 고려하지 않은 이유로 보인다(§4-6).


────────────────────────────────────────────────────────────────────────
■ 조사항목 1 — 3단계 후보 프로파일은 어디에 저장되는가
────────────────────────────────────────────────────────────────────────

저장소가 **두 개**이고, 서로 다른 목적을 가지며, **실행을 좌우하는 쪽에만 신선도
정책이 없다.**

[A] 브라우저 메모리 (← 4단계 실행 판정이 실제로 읽는 쪽 · 신선도 정책 없음)

버튼을 누르는 순간 후보 pool 을 그대로 떠서 payload 에 싣는다.

■ 조사항목 3 — 그 시간 간격이 실제로 존재하는가
────────────────────────────────────────────────────────────────────────

존재한다. 그리고 **상한이 없다.**

3-1. 서버 토큰에 만료가 없다

  P3 단계 가드 토큰은 발급 시각을 저장하지만 만료 비교를 하지 않는다.

  services/workflow_stage_guard.py:66      _MAX_TOKENS = 512
  services/workflow_stage_guard.py:172-177 _evict()  ← LRU 축출만(개수 기준)
  services/workflow_stage_guard.py:179-180 def _now(): return time.time()
  services/workflow_stage_guard.py:217     _TOKENS[token] = _TokenCtx(..., _now())
  services/workflow_stage_guard.py:242,377 ctx.updated_at = _now()

  → `_now()` 는 기록만 되고 어떤 만료 판정에도 쓰이지 않는다. 전체 파일에 TTL 상수·
    경과시간 비교가 없다. 토큰 512개가 밀려나기 전까지, SQL hash·접속 지문·project 가
    같으면 **하루 뒤에 눌러도 4단계가 통과한다.**

3-2. 실측 소요시간 (오늘 측정분 · LARGE-SCALE-...-MEASURE-RETRY, 2026-07-31 09:30~10:05)

  100만 행 오라클 픽스처(MV_SCATTER_SRC 1,000,000 / MV_SCATTER_TGT 990,000) 기준
  화면 표시 처리시간 :
      1단계 분석      0.34 ~ 0.81초
      2단계 COUNT     0.16 ~ 0.33초
      4단계 통계검증  0.27 ~ 0.39초
      5단계 재이관수집 0.38 ~ 1.18초
      변형별 총 wall  68.0 ~ 69.1초 (대부분 드라이버 고정 대기 sleep)

  → **기계 구동(Playwright 클릭스루)에서는 3→4 간격이 수 초**다. 이 조건만 보면
    위험은 낮다. 이 점은 정직하게 밝혀둔다.

3-3. 그러나 실제 운영 간격을 결정하는 것은 서버 처리시간이 아니라 사람이다

  3단계는 설계상 **사람이 검토하고 판단하는 화면**이다(CLAUDE.md "Web UI 4단계 화면
  흐름" — 컬럼 분류 결과 확인, GROUP BY/SUM 체크박스 최대 3개 선택). 여기서 소비되는
  시간은 서버 성능과 무관하며, 다음이 전부 현실적이다.

    · 후보 표를 훑고 근거 배지를 확인하며 컬럼을 고르는 수 분
    · 다른 담당자에게 "이 컬럼으로 잡아도 되냐" 확인하는 수십 분
    · 점심/회의 후 복귀
    · 탭을 열어둔 채 다음 날 이어서 진행 (§3-1 에 따라 토큰이 살아 있어 실제로 가능)

3-4. 괴리가 발생하는 구체 시나리오

  09:00  3단계. analyze 가 ORD_STATUS 를 프로파일 → distinct_count=8,
         evidence_type=EXACT. 담당자가 GROUP BY 로 선택하고 나머지 컬럼 검토를 시작.
  09:00~ 원본(as-is)에 이관/연계 배치가 돌면서 ORD_STATUS 매핑 오류로 세션ID 문자열이
  10:30  유입 → 실제 고유값 8 → 400,000 으로 폭증.
  10:30  4단계 [통계검증 실행] 클릭.
         · candidate_snapshot_full 의 distinct_count 는 **여전히 8**
         · estimate_groupby_count → 8
         · kind = EXACT → _effective_count 가 안전계수를 **곱하지 않음** (§2-4)
         · 8 ≤ max_groups → **SAFE 판정 → 통계 SQL 실행**
         · 우선순위 1에서 return 되므로 EXPLAIN 재확인도 없음 (§2-3)
  결과   게이트가 막으라고 만들어진 바로 그 상황(40만 그룹)이 그대로 실행된다.
         원본·목적지 양쪽에서 대량 GROUP BY 쿼리가 완주한다.

  방향이 반대(고유값 감소)면 과잉 차단 → 보수적이므로 무해하다.

3-5. 실제로 남아 있는 방어선 — 사후(post-hoc)이지, 사전 차단이 아니다

  · estimate_groupby_count 가 고유값 곱을 source_row_count 로 clamp
    (단 그 row count 도 2단계 COUNT 라 함께 stale — §2-2)
  · 실행 **후** 결과 상한 hard cap : STATISTICS_RESULT_LIMIT_EXCEEDED
    (services/groupby_execution_safety.py:46,
     services/stats_execute_service.py:68-98 `_exec_blocked_result`)

  → 후자가 진짜 최종 안전망이다. 그러나 이름 그대로 **실행 후**에 동작한다.
    결과는 폐기되어 잘못된 PASSED/MISMATCH 는 만들어지지 않지만(이 점은 잘 설계됨),
    쿼리 자체는 이미 원본·목적지에서 완주한 뒤다. 사전 게이트가 방지하려던 부하는
    이미 발생한다. **손실 축소 장치이지 예방 장치가 아니다.**

■ 조사항목 5 — 최종 판정
────────────────────────────────────────────────────────────────────────

판정 : **실질적 위험 있음** (범위 한정)

  위험 있음 : GROUP BY 실행 안전 게이트가 stale 한 3단계 distinct_count 로 SAFE 를
              내주어, 예상 그룹 수 상한 차단이 무력화될 수 있다. EXACT 라벨 후보는
              안전계수도 적용되지 않아 마진이 0이며, 구조화 evidence 로 통과하면
              EXPLAIN 실 DB 재확인도 건너뛴다. 서버 토큰에 만료가 없어 3→4 간격의
              상한이 없다.

  위험 없음 : 검증 결과 자체(PASS/WARNING/SKIP, 그룹별 COUNT/SUM 불일치, 5단계 재이관
              대상). 전부 실행 시점 실 DB 재조회 결과다. 잘못된 판정이 저장될 경로도
              없다(사후 hard cap 이 결과를 폐기).

  발생 조건 : 아래가 겹칠 때만 실현된다.
              (1) 단계별(클릭) 흐름 — 원클릭은 간격이 수 초라 사실상 해당 없음
              (2) 3단계 검토 중 원본의 **고유값 분포**가 변할 것 (행수 증가만으로는
                  부족 — 곱셈 항이 커져야 함)
              (3) 선택 컬럼 전부가 프로파일을 갖출 것 (그래야 우선순위 1에서 조기
                  return 되어 EXPLAIN 재확인을 건너뜀)

  현실 빈도 : 낮은 편으로 본다. 이관 검증의 원본은 보통 정지(quiesce)된 as-is 스냅샷
              이라 검토 중 카디널리티가 변하지 않는다. 이것이 지금까지 드러나지 않은
              이유로 보인다. 다만 다음에서는 실제로 발생 가능하다.
                · 운영계를 as-is 로 직접 검증하는 경우
                · 이관 배치와 검증을 병행하는 경우
                · 세션을 열어둔 채 익일 이어서 진행하는 경우(토큰 무만료라 가능)

  종합    : "즉시 조치가 필요한 결함"은 아니되, "이미 방어돼 있음"은 명백히 아니다.
            방어 장치(profile_snapshot TTL/delta)가 **존재하는데 이 경로에 연결되어
            있지 않은** 상태이므로, 신규 설계가 아니라 **배선 누락**으로 분류하는 것이
            정확하다.
