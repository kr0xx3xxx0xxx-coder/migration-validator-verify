1. 배경과 문제
------------------------------------------------------------------------------
선행 진단(SINGLE-STEP5-COMBO-VIEW-AND-SKEWED-GROUP-VOLUME-DIAGNOSE)이 확정한 사실은
다음과 같다. GROUP BY 를 2개 이상 선택하면 실행계획이 이를 "축별 독립 단일 세트"로
분해해 실행한다(services/groupby_plan_service.py:88-93). 이는 과세분화를 막기 위한
의도된 정책이며 이번 작업에서 바꾸지 않았다.

문제는 그 결과가 화면에 어떻게 표현되는가였다. 축별로 따로 집계하면 두 축의 조합
에서만 드러나는 차이가 각 축 안에서 서로 상쇄되어 사라진다. 진단이 만든 상쇄 픽스처
(asis01.t_combo_src / tobe01.t_combo_tgt — (P,D01)+10 / (P,D02)-10 / (A,D01)-10 /
(A,D02)+10 의 2x2 라틴 상쇄)에서 실제로 이런 일이 일어났다.

  GROUP BY status_cd            그룹=3  불일치=0
  GROUP BY dept_cd              그룹=4  불일치=0
  GROUP BY status_cd + dept_cd  그룹=12 불일치=4   <- 조합에서만 드러남

축별 분해 실행은 앞의 두 줄만 수행하므로 통계검증 판정이 matched=7 / diff=0 이 되고,
화면은 "통계결과 일치 · 불일치 그룹 0개 · 최종상태 정상"이라고 표시했다. 그런데 같은
화면 아래쪽 행 수준 상세비교는 같은 데이터에서 값 불일치 400건(= 4조합 x 100행)을
정확히 검출한다. 한 화면 안에서 위쪽은 "정상", 아래쪽은 "재이관 400건"이라는 모순이
사용자에게 그대로 노출되고 있었다.

조합 비교 기능 자체를 새로 만드는 것은 실행계획 계층의 큰 설계 변경이라 이번 범위가
아니다. 이번 작업의 목표는 하나다 — "조합은 검증하지 않았다"는 사실을 요약이 숨기지
않게 만드는 것.

5. 서버 재기동에 대한 기록
------------------------------------------------------------------------------
코드 수정 후 서버를 새로 기동했다. 다만 포트는 8000 이 아니라 8010 을 썼다.

이유는 이렇다. 작업 시점에 동일 저장소에서 다른 세션 두 건이 포트 8000 의 실행 중인
서버를 대상으로 'before' 기준 캡처를 진행하고 있었다(step4_combo_sql_label_accuracy_
verify.py, stats_excel_gb_cols_index_verify.py). 이 상태에서 8000 을 재기동하면 진행
중이던 그 캡처들이 중간에 깨진다. 조용한 대기 창을 기다렸으나 새 before 실행이 계속
이어져 열리지 않았다.

그래서 web_server.py 는 전혀 수정하지 않고, 같은 app 객체를 새 프로세스로 8010 에
올리는 검증 전용 기동 스크립트(scripts/dev_e2e/_combo_warn_server_8010.py)를 만들어
사용했다. 새 프로세스이므로 수정된 ui/grid_helpers.py, ui/tabler_renderer.py 가 실제로
적재된 상태이며(실행 중 서버는 reload=False 라 파일 수정이 반영되지 않는다), 위 (C)
실측은 전부 이 서버를 대상으로 한 것이다.

그대로 반영된다(정적 파일 변경이 아니라 파이썬 모듈 변경이므로 재기동만 하면 된다).


6. 비판적 검토 — 남는 문제와 한계
------------------------------------------------------------------------------
- 이번 수정은 문구를 정정한 것이지 결함을 없앤 것이 아니다. 조합 불일치는 여전히
  통계검증에서 검출되지 않는다. 사용자는 배너를 읽고 아래 상세비교로 내려가야 한다.
  근본 해소는 조합 세트 실행(실행계획 계층 변경) 또는 PAIR 진입점 복구가 필요하며
  별도 과제다.
- 배너를 항상 표시하는 선택은 정보 노이즈를 늘린다. 다축 검증을 늘 쓰는 사용자에게는
  매번 같은 안내가 보인다. 다만 "조합을 검증하지 않았다"는 사실이 결과에 따라
  달라지지 않으므로, 조건부로 숨기면 오히려 신뢰를 해친다고 판단했다.
- 판정 조건을 plan.sets 증적 유무로 좁힌 탓에, 실행계획 증적이 보존되지 않는 복원·
  이력 재조회 경로에서는 배너가 표시되지 않을 수 있다. 잘못 붙는 것보다 안 붙는 쪽이
  안전하다고 보고 보수적으로 잡았다. 해당 경로에 증적이 실리면 자동으로 표시된다.
- heuristic 하드코딩은 늘지 않았다(임계값·규칙 추가 없음). 판정은 전부 기존 실행 증적
  필드를 읽는 것으로만 이뤄진다. explainability 측면에서는 오히려 개선됐다 — 어떤
  축을 개별로만 검증했는지 배너와 tooltip 에 명시된다.
- web_server.py 비대화는 없다(서버 코드 변경 0줄). grid_helpers.py 에 함수 3개가
  늘었으나 모두 순수 함수이고 node 하니스로 단위 검증이 가능한 형태다.
