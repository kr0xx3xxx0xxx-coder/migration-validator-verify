1. 요약
────────────────────────────────────────────────────────────────────────
요구사항 3건을 모두 반영했다. 요구사항 1·2 는 표시/네비게이션 계층이고, 요구사항 3 은
표시 시점 판정의 결함이다. 값 계산·SQL 생성·집계·판정 로직은 한 줄도 바꾸지 않았다.

  1) 4단계 '실행시간' 타일 — 다중 세트(GROUP BY 2축 이상)도 **원본/목적 개별시간 2줄**로
     표시한다. 값이 없어서 못 나눴던 게 아니라, 세트 합산 루프가 세트별 query_timing 만
     버리고 있었다. 합계는 툴팁에만 '총 N초'로 병기한다.
     타일 순서를 '실행시간' ↔ '조합검증' 으로 교체해 2·5단계와 같은 '시간 → 상태'로 끝낸다.
  2) 4단계 **재실행 중에도 [다음 ▶]를 비활성**으로 유지한다. 종전에는 첫 실행만 잠기고
     재실행은 활성으로 남아, 실행이 끝나기 전에 5단계로 넘어갈 수 있었다.
  3) 5단계 '처리시간'이 상세비교 진행 중에 표시되던 문제 — **서버 재기동은 이미 되어 있었고**
     진짜 갭이었다. 대규모에서만 드러나는 조건을 규명해 최소 수정했다.

실 DB(Oracle asis/tobe, MV_SCATTER50M_SRC 5,000만행 → MV_SCATTER50M_TGT 4,950만행,
GROUP BY REGION_CD + STATUS_CD 2축 = 세트 2개, SUM AMT) 1~5단계 클릭스루를 before/after
각 1회 실행. **요구사항 1~3 전 항목 PASS(after)**, before 는 3건 모두 문제 상태를 그대로
재현했다. 페이지 오류 0건.

2. 요구사항 1 — 4단계 '실행시간' 원본/목적 분리 + 순서 교체
────────────────────────────────────────────────────────────────────────
2-1. 지시하신 확인 항목 ①②에 대한 답
  ① 원본/목적 개별값이 실제로 존재하는가 → **존재한다.** /execute 응답의
     query_timing.source_duration_ms / target_duration_ms 이며, 단일 세트 경로의 4단계
     '실행시간' 타일이 이미 그 필드를 쓰고 있다(RESULT-GROUP-LIMIT-PRECHECK-FIX 가 언급한
     'src 98ms/tgt 102ms'와 같은 필드). 재사용 가능하다.
  ② 다중 세트는 어떻게 처리할 것인가 → **세트마다 값이 따로 오고, 기존 합산 루프가 그 값만
     버리고 있었다.** 즉 '값이 이미 세트 통합 합계'인 것도, '분리가 불가능'한 것도 아니었다.

  before 실측(같은 화면에서 동시에 읽은 값):
      화면 표시            : 실행시간 = '총 24.40초' (한 줄)
      agg.query_timing     : null                      ← 화면에 넘어간 합산 객체
      세트별 응답          : REGION_CD  src 5,397ms / tgt 8,221ms
                             STATUS_CD  src 5,104ms / tgt 4,746ms   ← 값은 이미 있었다
      agg.processing_ms    : 24,404ms(벽시계)

  → 새 계산 로직을 만들지 않고, matched/diff/rows 를 더하는 **그 루프에서 같은 방식으로**
    원본 합·목적 합을 더해 agg.query_timing 으로 넘긴다. 표시 함수(_mvStage4ExecElapsed)는
    단일 세트와 완전히 같은 코드를 타며 다중 전용 분기가 없다.
    클라(_runExecutePlanSets)와 서버(_run_multi_gb_sets)를 **대칭**으로 고쳤다 —
    과거 processing_ms 누락이 정확히 이 비대칭에서 온 사고였기 때문이다.

2-2. 합계를 값 줄이 아니라 툴팁에 둔 이유(지시 ③)
  총시간(processing_ms)은 '세트 실행 전체를 감싼 벽시계'라 세트 계획 생성·SQL 생성·그룹 비교
  구간을 포함하고, 서버 조건부 병렬(_stats_set_parallelism)이 켜지면 세트가 동시에 돌아
  **벽시계 < 개별시간 합**도 될 수 있다. 성격이 다른 두 값을 한 칸에 나란히 두면 다시
  '어느 게 전체인가'를 오해하게 되므로, 값은 원본/목적 2줄만 두고 합계는 툴팁에 병기했다.
  단일 세트 툴팁('순차 실행, 차액은 앱 처리시간')을 그대로 복사하지 않고 문구를 분리했다.

  after 실측(첫 실행):
      화면 표시  : 실행시간 = '원본 10.47초 / 목적 13.44초' (2줄)
      agg        : source_duration_ms 10,468 · target_duration_ms 13,437 · aggregated_sets 2
      세트별     : REGION_CD src 4,545 / tgt 7,259 · STATUS_CD src 5,923 / tgt 6,178
      검산       : 4,545 + 5,923 = 10,468 ✅   7,259 + 6,178 = 13,437 ✅
      툴팁       : '원본 10,468ms / 목적지 13,437ms · 총 24.81초(24,808ms) — 다중 세트
                    (GROUP BY 2축 이상) 2세트의 … 벽시계라 개별시간 합과 같지 않으며 …'
      벽시계 24,808ms vs 개별합 23,905ms → 차이 903ms 가 세트 계획·SQL 생성·그룹 비교 구간.

  재실행 후에도 동일하게 동작: '원본 9.72초 / 목적 10.44초'(4,207+5,514=9,721 / 6,440+3,995=10,435).

2-3. 값이 없을 때(지시 ④)
  집계 응답에 query_timing 이 아예 없으면(구버전 응답·전 세트 실패) 무리해서 나누지 않고
  종전 '총 N초' 한 줄로 폴백하며, 그것도 없으면 '—' + 사유 툴팁으로 남긴다.
  → 즉 '분리 불가'는 이번 케이스에 해당하지 않으며, 폴백 경로로만 남겨 뒀다.

2-4. 타일 순서 교체(지시 ⑤)
  before : … 통계전략 · 실행시간 · 조합검증 · 상태
  after  : … 통계전략 · 조합검증 · 실행시간 · 상태     (10칸 유지, 한 줄 유지)
  근거는 지시하신 그대로다 — 2·5단계가 모두 '처리시간 → 상태'로 끝나는데 4단계만 시간 칸이
  상태 두 칸 앞에 있었다. 조합검증은 SQL 생성 시점에 채워지는 계획성 값(그룹·집계와 같은
  성격)이라 앞쪽이 제자리이고, 실행시간은 상태와 함께 실행 결과다. 값·계산·툴팁 불변.

3. 요구사항 2 — 재실행 중 [다음 ▶] 잠금
────────────────────────────────────────────────────────────────────────
3-1. 지시하신 확인 항목 ①에 대한 답 — 첫 실행/재실행이 다른 코드 경로인가
  **아니다. 같은 판정식이 재실행에서만 참이 되는 비대칭이었다.**
  하단 [다음 ▶]의 disabled 는 _mvCanNavStep('result') → MvStageGate.isTabAccessible('result')
  → Gate 의 execute 상태 하나로 정해진다. 그 상태를 계산하는 _mvComputeWfStates 가
  _singleValidationExecuted **하나만** 보고 있었다.
      · 첫 실행  : 아직 false → execute=PENDING → 5단계 prereq 미충족 → 정상 잠김
      · 재실행   : 직전 실행의 true 가 그대로 남아 있음 → execute=SUCCESS → 실행 중에도 활성
  이 플래그는 실행 완료 시 true 가 되고 재실행 시작 시점에 false 로 내려가지 않는다.

  before 실측(실행 중 샘플링):
      첫 실행 : 실행중 49~62 샘플 전부 [다음 ▶] disabled=True   (wfExecute=PENDING)
      재실행  : 실행중 49 샘플 전부 [다음 ▶] disabled=**False** (wfExecute=SUCCESS)  ← 결함

3-2. 조치(지시 ②) — 새로 만들지 않고 첫 실행이 쓰는 잠금을 재사용
  실행 중(_executeInProgress — runExecute 진입 시 true, 모든 종료 경로 finally 에서 false)
  이면 Gate 의 execute 를 RUNNING 으로 둔다. 그러면 첫 실행과 **완전히 같은 경로**로
  5단계 prereq 가 미충족이 되어 [다음 ▶]와 상단 5단계 탭이 함께 잠긴다.
  새 플래그·새 잠금 로직·새 렌더 경로가 없다. 시작 시점 반영만 _renderSingleStepNav() 한 번
  추가했다(커맨드바는 클릭 시 '누른 버튼 하나'만 스피너로 바꾸고 전체 재렌더는 unlock 시점에만
  하므로, 이 호출이 없으면 실행이 끝날 때까지 [다음 ▶]에 반영되지 않는다).
  해제는 각 종료 경로의 finally 가 이미 하던 같은 재렌더가 맡는다(성공/실패 불문).

  ★ 잠기는 것은 5단계뿐이다 — 4단계(execute) 탭 자체의 접근성은 prereq(candidate SUCCESS)
    기준이라 영향이 없다(실행 중에 보고 있던 4단계에서 튕기지 않음, 실측 확인).
  ★ 원클릭 전체검증(_fullRunInProgress)·3단계 재검증(_revalidateInProgress)은 이 플래그를
    쓰지 않아 종전 동작 그대로다.

  after 실측:
      첫 실행 : 실행중 62 샘플 전부 disabled=True (wfExecute=RUNNING) → 완료 후 False  ✅ 무회귀
      재실행  : 실행중 53 샘플 전부 disabled=True (wfExecute=RUNNING) → 완료 후 False  ✅ 해소

4. 요구사항 3 — 5단계 '처리시간' 조기 표시(대규모 재발)
────────────────────────────────────────────────────────────────────────
4-1. 지시하신 확인 항목 ① — 서버 재기동 여부
  **재기동은 이미 되어 있었다.** 재기동 누락이 아니다.
      직전 수정 커밋 486b1a1 : 2026-08-05 19:28:29
      web_server.py 프로세스 : 2026-08-05 19:55:48 기동
  기동이 커밋보다 27분 뒤이므로 그 수정은 서버에 반영된 상태였고, 그래도 재현됐다.
  (교차 확인: 재기동 전 서버가 내려주던 HTML 에 이번 작업 마커가 없는 것으로 '옛 코드'임을
   따로 확인했고, 이번 AFTER 실측 전에는 재기동 후 마커 존재를 확인하고 진행했다.)

4-2. 원인(지시 ②) — 대규모에서만 뒤집히는 판정
  직전 수정이 쓴 판정 _mvPkPrepRunning() 의 마지막 줄은 window._mvExecTerminal 을 본다.
  그런데 **_mvExecTerminal 은 상세비교 전용 신호가 아니다** — 4단계 통계검증(runExecute)의
  finally 도 "폴링이 아직 없으면 실행 패널을 닫는다"는 취지로 같은 플래그에 true 를 쓴다
  (단일 세트·다중 세트 두 경로 모두).

  소규모에서 통과했던 이유:
      _mvPkPrewarm 이 통계검증 렌더 직후 곧바로 prepare 를 걸어 st.promise 가 서므로,
      판정이 그 윗줄에서 true 로 빠져나가 마지막 줄에 닿지 않는다.
  대규모에서 뒤집히는 이유:
      _mvPkPrewarm 은 자동 준비 상한(_MV_PK_PREWARM_MAX_ROWS, 기본 100만행) 초과이거나
      PostgreSQL 이 아니면 prepare 를 걸지 않고 그냥 빠진다. 5,000만행 Oracle 은 두 조건에
      모두 걸린다 → promise 가 없다 → 그 사이 4단계 finally 가 _mvExecTerminal=true 를 남긴다
      → 이후 5단계에서 상세비교가 실제로 시작(PREPARING + 폴링)돼도 마지막 줄이 false 를
      돌려주어 '처리시간'이 그려진다.

  before 실측(진행 중 시점에 같은 샘플에서 함께 읽은 값 — 어느 하나도 추정이 아니다):
      처리시간 = '24.40초'  ← 표시됨
      compareRunning=true(상세비교 진행 중입니다) · reimportPreparing=true(재이관 대상 준비 중)
      riPolling=true        ← 상세비교 폴링은 실제로 돌고 있다
      execTerminal=true     ← 4단계가 남긴 값
      prepRunning=false     ← 그래서 판정이 뒤집혔다
      진행 중 관측 37/38 샘플, 그 중 '진행 중인데 처리시간 표시' **37건**

4-3. 조치(지시 ③) — 최소 수정
  _mvPkPrepRunning 이 **상세비교 자신의 진행 신호**(_mvRiState._polling — _mvRiStartPolling 이
  켜고 _mvRiStopPolling 이 끄는 값)를 먼저 본다. 폴링이 돌고 있으면 진행 중이고, 폴링이 없을
  때만 종전 _mvExecTerminal 폴백을 그대로 쓴다(그 폴백의 '영구 미표시 방지' 취지는 유지).
  추가로 폴링 시작/종료 두 시점에 5단계 타일을 다시 그린다 — prepare 응답 시점의 재렌더는
  폴링 시작 '이전'이라 그것만으로는 시작이 화면에 반영되지 않고, 종료쪽은 _mvPkAdoptDetail 이
  READY/EARLY_STOPPED 만 채택하므로 FAILED·CANCELLED 에서 값이 '—'로 굳는다.
  기존 repaint(_mvRepaintStage5Tiles) 재사용이며 새 렌더 경로가 없다.

  after 실측:
      진행 중 시점: 처리시간 = '—' · prepRunning=**true**(execTerminal=true 인데도) ·
                    riPolling=true · compareRunning=true
      진행 중 관측 34/35 샘플, '진행 중인데 처리시간 표시' **0건**  ✅
      완료 후    : 처리시간 = '24.81초'  ✅ (영구 미표시로 굳지 않는다)

5-2. 이번 변경으로 실제로 깨진 계약 테스트 3건 (커밋 2042b40)
────────────────────────────────────────────────────────────────────────
셋 다 '지키려는 사실'은 그대로 두고 **판정 대상만 정확히** 했다. 단언을 약화하지 않았다.

  1) test_stage3_button_dom_dedup_and_gate45_real_fix.py
     ::test_execute_success_ignores_reimport_active_state_for_accessibility
     단언이 '_mvComputeWfStates 안에 st.execute = S.RUNNING 문자열이 없을 것'이라 지키려는
     범위보다 넓었다. 이 테스트가 막아야 하는 것은 **'재이관 상태를 근거로 RUNNING 을 세우는
     것'**(4→5단계 순환)이지 RUNNING 자체가 아니다 — 통계검증이 실제로 실행 중인 동안에는
     RUNNING 이어야 [다음 ▶]가 잠긴다(이번 요구사항 2).
     → 재이관 신호(_mvReimportStatus/_mvRiState/_mvExecPanelActive/_mvPkState)가 이 함수에
       없을 것 + RUNNING 의 근거가 _executeInProgress 일 것으로 바꿨다(원래 의도 그대로).

  2) test_plansets_agg_processing_time_fix.py::test_client_agg_has_processing_ms_from_wall_clock
     '세트별 processing_ms 합산 금지' 검사가 **그 규칙을 설명하는 한글 주석**('총시간
     (processing_ms)은 … 합산하지 않는다')까지 위반으로 잡았다 — 규칙을 지키는 코드가 규칙을
     어긴 것으로 판정됐다. → 주석 제거 후 실행 코드만 검사한다.

  3) test_run_execute_conn_payload_consolidate.py::test_run_execute_uses_common_builder
     runExecute 시작에서 **고정 8,000자 창**만 보는데 srcDb 대입이 8,192자 지점이라, 함수
     앞부분에 몇 줄만 늘어도 '공통 빌더 미호출'로 오판했다(이 테스트가 지키려는 것은 위치가
     아니라 '인라인 payload 구성이 없고 공통 빌더를 쓴다'는 사실이다).
     → 함수 본문 전체를 보도록 넓혔다. 함께 runExecute 의 이번 작업 주석도 3줄로 줄였다.

  ★ 1)·2) 는 이번 변경이 없었어도 언젠가 같은 방식으로 걸릴 구조였다(주석 문자열·고정폭 창을
    판정 근거로 삼는 검사). 정정으로 그 취약성이 함께 사라진다.
