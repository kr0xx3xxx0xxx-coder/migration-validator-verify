작업명 : STAGE2-COUNT-INFLIGHT-TAB-LOCK-DIAGNOSE-AND-FIX
✅ 작업 완료 - 2단계 COUNT 실행 중 다른 탭으로 무제한 이동 가능하던 결함을 실측 확정하고 _countInProgress 재사용 좁은 가드로 수정(before/after 실 클릭 대조로 검증), COUNT 커맨드바 lockMaxMs 20초 오경보(별건, 사용자 추가 목격)도 runExecute 와 동일 180초로 함께 수정

■ 결론 요약
  1) 2단계 COUNT 사전검증 실행 중, 상단 탭(1단계 쿼리검토 등)·하단 ◀이전 버튼으로 다른 단계 이동이
     실제로 아무 제지 없이 가능했다(실측 재현 성공). 원인은 탭 이동 게이트(MvStageGate.canNavigateStep/
     _mvCanNavTab)가 '뒤로(인접 이전)'는 상태 무관 무조건 허용하고, 완료 탭 자유이동도 접근성(prereq)만
     보고 실행 중 여부를 아예 보지 않는 구조적 공백이었다. 오늘(M43/M47/MVANYRUNACTIVE) 다룬
     _mvAnyRunActive()/_mvSyncRunLockedControls() 는 실행 버튼·특정 입력 컨트롤(mv-run-locked)만 잠갔지,
     탭 네비게이션은 애초에 그 잠금 대상 목록에 없었다.
  2) 근거 부족 → 결함으로 판정. 명시적으로 "COUNT 는 가벼워서 탭 이동을 막을 필요 없다"는 주석/커밋
     근거는 없었다. 다만 _mvAnyRunActive() 를 있는 그대로 탭 게이트 전체에 얹으면, 오늘 M47이 의도적으로
     열어 둔 "5단계 상세비교 job 진행 중에는 진행상황을 보러 다른 탭으로 옮겨 다닐 수 있어야 한다"는
     설계(:6870 주석, nav 를 잠금 화이트리스트에서 명시적으로 제외)를 회귀시킨다. 그래서 COUNT 전용
     플래그(_countInProgress)로 좁혀 2단계 이탈만 막았다.
  3) 사용자가 조사 도중 추가로 목격한 "이전 요청 응답이 지연되어 버튼 잠금을 해제했습니다" 팝업은
     별개 원인으로 확정했다 — 커맨드바 클릭락 안전 타이머(고착 방지, 의도된 설계)의 기본 상한이 20초인데
     COUNT 액션(_mvCountStageAction)에만 lockMaxMs 미지정이라 그 기본값을 그대로 썼다(통계검증 실행은
     이미 180초로 개선됐지만 COUNT 는 누락). 대량 테이블 COUNT 는 이미 32초대 실측(5,000만행 CTE 케이스)이
     있어 정상 실행 중에도 20초에 팝업이 뜬다. 재클릭은 _countInProgress 가드로 안전하지만(중복실행 없음)
     사용자 혼란을 유발한다. 이 타이머의 강제해제는 _mvAnyRunActive() 의 COUNT 판정(#countRunBtn 스피너)을
     손상시키지 않는다는 것도 실측으로 확인했다(별도 DOM 갱신 경로 — runCount() 자신이 관리).

■ 2. 판정 — 의도된 설계인지 결함인지 (지시서 2번)
  결함으로 판정. 근거: (a) "COUNT 는 가벼우니 탭 이동을 막을 필요 없다"는 주석/커밋이력 전무.
  (b) 반대로 M47-REGRESSION-RECHECK-AND-FIX(:6852~6872)는 "5단계 job 진행 중 1~4단계 실행 버튼을
  시각적으로도 잠근다"는 명시적 원칙을 이미 세웠는데, COUNT(2단계) 자체 실행 중 탭 이동은 그 원칙의
  적용 대상에서 아예 빠져 있었다(같은 클래스의 미완결 배선). (c) 단, _mvAnyRunActive() 를 탭 게이트에
  '그대로' 얹는 것은 위험하다 — 그 함수는 5단계 상세비교 job(_mvReimportStatus)도 함께 감시하는데,
  M47 은 "그 job 진행 중에는 진행상황을 보러 다른 탭으로 이동할 수 있어야 한다"(:6866~6870, 영구
  먹통 방지 근거)는 이유로 nav 버튼을 잠금 화이트리스트에서 명시적으로 제외했다. 이 예외를 깨지 않기
  위해 새 잠금 메커니즘 없이 기존 _countInProgress 플래그만으로 2단계 이탈 범위에 한정해 막았다.
