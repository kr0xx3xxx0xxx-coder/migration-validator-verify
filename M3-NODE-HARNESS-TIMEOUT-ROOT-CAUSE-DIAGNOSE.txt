  근본원인: 2026-07-27 17:58 커밋 05d4fa19(JOB-DASHBOARD-STAGE3-UI-AND-MENU-REORG)가
  페이지 기본 랜딩 탭을 'home' → 'job-dashboard'(검증 현황판)로 바꿨다. 이 탭은 진입 시

  환경에서는 지연 0 인 채로 초당 수천 회 재귀 호출되며 CPU 1코어를 무기한으로 점유한다.

  이 원인 커밋(05d4fa19, 17:58)과 최초 정지 사고(PID 32744, test_blocked_state_reset.py,
  19:38 기동)의 시간 간격은 1시간 40분 — 우연이 아니라 인과관계로 판단한다.

  3개 파일 모두 **동일한 스텁 코드**(setTimeout 동기 실행 + localStorage/location.hash 빈 값

2. 원인 계측(코드 수정 없이 격리 재현 — 스크래치 임시 사본에서만 진행, 저장소 무변경)

【2-1 1차 관찰 — pytest 는 멈추는데 단독 실행은 순간 종료(모순 발견)】
  test_blocked_state_reset.py 의 harness/asm 을 그대로 스크래치에 복제해 node 로 직접 실행하면
  stdout(JSON 결과)까지는 70~90ms 만에 출력됐다. Bash 백그라운드 PID 확인은 신뢰할 수 없어서
  (`kill -0`가 실제 node.exe 가 아닌 래퍼 프로세스를 가리킴), **foreground + 도구 타임아웃**으로
  재검증하니 stdout 출력 후에도 프로세스가 90초 넘게 종료되지 않았다(exit 143). 즉 "유용한 출력은
  즉시 끝나지만 프로세스 자체는 안 끝난다" — pytest 의 subprocess.run(capture_output=True) 는
  파이프 EOF(=프로세스 종료)까지 기다리므로 이게 그대로 "정지"로 관측된다.

【2-2 CPU 실측 — 진짜 바쁜 루프인지 idle 대기인지 판별】
  PowerShell Start-Process + Get-Process.TotalProcessorTime 으로 5초/15초 시점 CPU 누적을 측정:
    CPU@5s  ≈ 4.92초   (경과 5초 대비 98%)
    CPU@15s ≈ 14.70초  (경과 15초 대비 98%)
  → 유휴 대기(idle wait)가 아니라 **코어 1개를 거의 100% 점유하는 바쁜 루프**임을 확정
    (2026-07-27 최초 사고 기록의 "26시간 동안 코어 100% 점유"와 동일 패턴).

【2-3 node --prof 샘플링 프로파일러 — 어느 함수가 도는지 특정】
  12초 프로파일링 → node --prof-process 분석 결과 상위 항목:
    JS: _jdRenderOverall / _jdRenderAll (assembled.js:6338/6387)
    JS: querySelector / makeEl (harness 스텁, _jdRenderAll 이 반복 호출)
  → ui/js_job_dashboard.py 의 "검증 현황판(job-dashboard)" 렌더 함수가 반복적으로 도는 것으로 특정.

【2-4 카운터 계측(스크래치 사본에 1회성 console.error 추가 — 저장소 원본 무변경) — 확정 증거】
  ui/js_job_dashboard.py:679 의 _jdSchedule() 진입 시 visible/stopWhenIdle/activeCount 를
  기록하도록 **스크래치 임시 사본**(asm3.js)에만 계측 코드를 추가해 6초간 실행:
    [TRACE _jdSchedule] n=1  visible=true stopWhenIdle=true activeCount=0 interval=3000 badgeInterval=15000
    [TRACE _jdSchedule] n=2  visible=true ... (동일값 반복)
    ...
    [TRACE _jdSchedule] n=30000  visible=true ...  (6초 안에 3만 회 도달, 강제 중단)
  → _MV_JD.visible 이 기본값 false 가 아니라 **매 호출 true** 로 고정돼 있어, 정지 조건
    `!visible && stopWhenIdle && activeCount===0` 이 단 한 번도 만족되지 않고 무한 재귀한다.

【2-5 코드 추적 — visible=true 가 되는 경로 + 실제 타이머 지연이 사라지는 경로】
  ui/tabler_renderer.py:7344-7355 (_mvResolveInitialTab/_restoreActiveTab):
    "초기 진입 탭 결정: URL hash > localStorage > job-dashboard(검증 현황판)"
    "[JOB-DASHBOARD-STAGE3] 기본 랜딩이 홈 대시보드에서 검증 현황판으로 바뀌었다."
  harness 스텁은 location.hash=''·localStorage 초기값 없음이므로 항상 3순위 fallback
  'job-dashboard' 로 귀결 → showTab('job-dashboard') → mvJobDashboardEnter()
  (ui/tabler_renderer.py:7277, ui/js_job_dashboard.py:730) → _MV_JD.visible=true 설정 →
  _jdSchedule() 이 setTimeout(_jdPollOnce, 3000) 으로 자기 자신을 재예약(js_job_dashboard.py:679-684,
  주석: "setTimeout 체인이라 응답이 늦어도 요청이 겹치지 않는다(setInterval 폭주 방지)" — 정상
  브라우저 설계로는 합리적인 선택).
  이 자동 진입 트리거는 ui/tabler_renderer.py:7395-7418 의 _mvInitNav() 가 담당하는데, 스텁의
  document.readyState 가 미설정(undefined)이라 "로딩 중" 분기를 타지 않고
  `else setTimeout(_mvInitNav, 0)` 로 즉시 실행된다.
  harness 스텁의 setTimeout 구현(3개 파일 공통):
    setTimeout(fn){try{if(typeof fn==='function')fn();}catch(e){}return 0;}
  → 지연을 전혀 지키지 않고 fn 을 그 자리에서 즉시 실행 — 브라우저의 setTimeout 계약을 깬다.
  fetch 스텁도 항상 즉시 resolve 하므로(`Promise.resolve({ok:true,json(){...{}...}})`),
  _jdPollOnce 의 fetch('/jobs/active') 응답도 지연 0 으로 즉시 돌아와 루프를 가속한다.

3. 지침 §2 — M4 선례와의 비교 판정
════════════════════════════════════════════════════════════════════════════
  M4 는 "하니스의 낡은 계약"(스텁 nav 이름이 실제 코드와 달라 소유자 판정에서 조기 return →
  이후 전부 null 참조 붕괴, 동기적 TypeError)이었다. 이번 3개 파일은 그와 **다른 성격**이다:
    · M4: 이름 불일치 → 동기 예외로 "즉시" 실패(하니스가 낡아서 죽는다).
    · 이번: setTimeout 의 **시간 지연 계약**을 스텁이 지키지 않아서(0ms 즉시 실행) →
      실제 코드는 정상 설계(3초 폴링, setInterval 대신 setTimeout 체인으로 요청 중첩 방지)인데
      **하니스가 "시간이 흐른다"는 전제를 깨서** 무한루프가 된다.
  즉, 지침이 제시한 두 갈래("하니스 계약 노후화" vs "무한루프/미해결 Promise/이벤트리스너 미해제")
  중 표면적 현상은 **무한루프**이지만, 그 무한루프의 촉발 원인은 **하니스 계약 결함**(setTimeout
  스텁이 비동기 지연을 흉내내지 않음)이다 — 두 갈래가 결합된 성격으로 판정한다. M4 와 마찬가지로
  **제품 코드 결함이 아니라 테스트 하니스 쪽 문제**라는 결론은 같다(제품은 브라우저에서 정상 동작).
  미해결 Promise·이벤트리스너 미해제는 이번 원인과 무관함을 §2 계측으로 배제했다.

4. 수정 필요 여부 판단 및 착수 시 예상 범위
════════════════════════════════════════════════════════════════════════════
  판단: **수정 권장(진행 권장) — 단, 이번 지침 범위 밖(조사만 지시됨)이라 실행하지 않았다.**

  현재 상태로도 스위트 전체 정지 위험은 이미 해소돼 있다(전역 타임아웃 가드, 커밋 a2c3646).
  다만 이 3개 파일은 **현재도 100% 재현되는 TIMEOUT 실패**를 계속 낸다 — M4 가 지적한 "회귀
  신호를 가리는 죽은 빨간 불"과 동일한 부작용이다: 이 3개 파일에 실제 회귀가 생겨도 항상
  TIMEOUT 실패만 보이므로 구분이 불가능하다.

  대응 방향(3가지, 권장도 순):
    (a) [권장] harness 스텁에 `localStorage.setItem('mv_active_tab','analyze')`
        (또는 job-dashboard 가 아닌 유효 탭 아무거나) 1줄을 vm.runInThisContext 실행 전에
        주입 — _restoreActiveTab() 이 job-dashboard 로 fallback 하지 않게 만들어 폴링 자체가
        시작되지 않는다. 3개 파일에 각 1줄, 테스트 전용 변경, 제품 코드 무변경, 회귀 위험 최소.
        예상 범위: 파일 3개 × 1~2줄 + 각 파일 개별 재실행(3×60초 상한 없이 정상 종료되는지)
        + 전체 스위트 회귀 대조(§4-2 방식 재사용).
    (b) [비권장] harness 공용 setTimeout 스텁을 실제 지연 흉내(setImmediate/실제 setTimeout 위임)로
        바꾼다 — 144곳의 다른 timeout-미지정 호출과 100여 개 파일이 이 패턴을 공유해 파급 범위가
        넓고, 다른 테스트의 타이밍 가정을 깨뜨릴 위험이 있어 이번 좁은 문제에 비해 과함.
    (c) [비권장] 제품 코드에서 job-dashboard 자동 폴링 시작 조건을 document.hasFocus()/실제
        DOMContentLoaded 로 제한 — 사용자 체감 동작(현황판 진입 시 즉시 갱신) 변경이라 별도 논의 필요,
        이번 테스트 문제만을 이유로 제품 동작을 바꾸는 것은 근거가 약하다.

  결론: (a) 안이 가장 작고 안전한 범위다. 이번 지침은 "조사만"이므로 실행하지 않았고,
  진행 여부는 사용자 확인 후 별도 작업으로 착수 권장.
