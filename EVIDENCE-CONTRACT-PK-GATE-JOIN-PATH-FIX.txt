3. JOIN 경로가 원본 key_metadata 를 조회하지 않는 이유 (요구사항 2)
================================================================================
결론: **단순 누락이 아니라 도입 시점부터의 명시적 설계 배제다.**

근거 (git 이력 — fa33023 의 직전 커밋 fa33023^, routes/analyze_route.py:496-519):

    _has_join = bool(parsed.join_clauses)
    if _is_pg and req.src_conn and from_tbl and not from_tbl.startswith('('):
        _all_tbls = [from_tbl]
        if not _has_join:
            # 단일 테이블: pg_stats + key_metadata 기반 정밀 점수화
            _pg_stats = fetch_postgres_column_stats(req.src_conn, _all_tbls)
            _key_meta = fetch_postgres_key_metadata(req.src_conn, from_tbl)
            ...
        else:
            # JOIN 포함: pg_stats 미적용, 기본 score 필드만 추가
            ...

fa33023("공통 후보추천 엔진 통합")가 이 if/else 를 `and not _has_join` 하나로 접었을 뿐,
'조회한다/안 한다'의 의미는 처음부터 동일하다. 이후 3d7ed59(서비스 계층 이동) → 현재까지 그대로다.

설계 이유(코드 성질로 확인 가능):
  services/metadata_provider.from_pg_stats(pg_stats, key_meta, table_name, tgt_map) 는
  **단일 테이블(from_tbl)** 의 카탈로그를 컬럼명만으로 매칭한다
  (149-175행 `key.replace(f"{tbl_up}.","")`, `km = (key_meta or {}).get(col_upper, {})`).
  JOIN 이면 컬럼이 여러 테이블에서 오므로 from_tbl 하나의 통계·키를 전부에 귀속시키게 되고,
  동명 컬럼이 있으면 조용한 오귀속이 된다. **'조회를 안 한 것'이 아니라 '귀속할 수 없어서 안 한 것'.**

→ 따라서 요구사항 4대로 **원본 수집을 JOIN 으로 확장하지 않았다.** 목적지 근거로만 완화했다.

── 5-4. 보강 케이스: SQL 명시 GROUP BY 에 목적지 단일 PK 가 등장 (JOIN) ─────
candidate_engine 의 is_pk 게이트는 Step2(메타)/Step3(시맨틱)에만 있고 Step1(SQL 명시·HIGH)은
통과한다. 계약 pk 완화가 §22(PK/UNIQUE 자동추천 제외)를 **새로** 발동시키는지 확인할 수 있는
유일한 경로라 별도 측정했다(MV_ORA_DEMO_SRC ⋈ MV_ORA_DEPT_MASTER, GROUP BY s.ID, s.DEPT_CD —
ID 는 목적지 MV_ORA_DEMO_TGT 의 단일 PK).

  컬럼      역할      BEFORE                            AFTER
  ID        GROUP_BY  ev_pk=None · rec=EXCLUDED         ev_pk=True(TARGET)  · rec=EXCLUDED
  DEPT_CD   GROUP_BY  ev_pk=None · rec=MANUAL_REVIEW    ev_pk=False(TARGET) · rec=MANUAL_REVIEW
  AMT       SUM       ev_pk=None · rec=AUTO_RECOMMENDED ev_pk=False(TARGET) · rec=AUTO_RECOMMENDED

  · ID 는 **수정 전에도 이미** 다른 규칙('식별자성 의심 — GROUP BY 정책상 제외')으로 EXCLUDED 였고,
    수정 후에는 여기에 실제 PK 근거가 붙었을 뿐 판정은 동일하다.
  · 즉 이번 완화는 **근거를 채우되 판정을 바꾸지 않았다** — 새 배제 0건, 새 완화 0건.

── 5-5. "근거부족 배지" 기대치에 대한 정정 (중요) ───────────────────────────
지침/§11-R2 는 pk 게이트가 열리면 '근거부족 배지가 줄어들 것'으로 기대했다.
**실측 결과 배지 수는 줄지 않았고(ins_changed=0), 이는 결함이 아니라 정상이다.**
화면의 '근거부족' 신호는 pk 를 입력으로 쓰지 않는다:

  services/fallback_recommendation.py
    · enforce_recommendation_evidence_guard(326행)가 `evidence_insufficient=True` 를 세우는
      유일한 조건은 recommendation_evidence_sufficient() == False (316행)이고,
    · 그 함수(262-297행)는 GROUP BY 는 `"cardinality" in missing`,
      SUM 은 `"numeric_or_semantic"` / `_sum_review_required` 만 본다.
      **pk / unique 는 판정 입력이 아니다.**
  services/candidate_recommendation_policy._gate_verdict(199-225행)도 GROUP BY 강등 근거는
    cardinality 계열뿐이다(pk 는 True 일 때 '제외'로만 작용).

  JOIN 경로에서 '근거부족'이 뜨는 실제 원인은 **cardinality(고유값) 근거 미수집**이며,
  그것은 원본 profile/통계를 JOIN 에서 수집하지 않기 때문이다(§3의 설계 배제와 같은 뿌리).
  → pk 게이트만으로는 배지가 줄 수 없다. 배지를 줄이려면 JOIN 경로의 cardinality 근거 확보가
     필요하고 그것은 이번 범위(요구사항 4: 원본 수집 확장 금지) 밖이다 → §8 후속으로 남긴다.

  이번 수정이 실제로 얻은 것(측정된 사실):
    ① 계약 pk 가 JOIN 경로에서 처음으로 실값을 갖는다(12건).
    ② missing_evidence 에서 'pk' 가 사라진다(12건) — 근거 목록 정확도 향상.
    ③ §22 PK/UNIQUE 자동추천 제외 gate 가 JOIN 경로에서도 **판단 근거를 갖게 됐다**
       (현 픽스처에선 결과 동일하나, 목적지 단일 PK 가 SQL 명시 후보로 들어오는 형태에서
        더 이상 '모름'으로 통과하지 않는다).
    ④ COUNT 후 재부착(postcount)에서도 PK 근거와 그 출처가 보존된다.

F1 (중) **JOIN 경로 cardinality 근거 부재** — '근거부족' 배지의 실제 원인(§5-5). 원본 profile/
        통계가 JOIN 에서 수집되지 않아 GROUP BY 후보가 계속 MANUAL_REVIEW 로 남는다.
        해결하려면 JOIN 의 컬럼→원본테이블 귀속(lineage)을 확정한 뒤 테이블별로 통계를 수집해야
        하며, 이는 이번 지침이 명시적으로 범위 밖으로 정한 '원본 수집 확장'이다 → 별도 작업 필요.
F2 (중) **원본 key_metadata 의 JOIN 경로 수집 확장** — 지침 요구사항 4에 따라 이번엔 하지 않았다.
        하면 pk 를 '원본 기준'으로도 알 수 있어 SUM 합산근거 신호(source_key_signal)까지 정상화되나,
        §3의 귀속 문제를 먼저 풀어야 한다(from_pg_stats 가 단일 테이블 전제).
F3 (하) **목적지 unique 미수집** — `_cmn_fetch_tgt_col_meta` 는 어댑터 키메타에서 is_pk 만 싣고
        is_unique 는 버린다(db_query_service.py:1435-1441). 실으면 unique 도 목적지 근거로 열 수
        있어 missing_evidence 의 'unique' 가 줄지만, 소비처(§22 제외 gate)에 영향이 있어 별도 판단 필요.
F4 (하) **c2 유형(목적지 PK 없음) 은 계속 pk=None** — 어댑터가 빈 dict 를 반환해 '키 없음'과
        '미지원/조회불가'를 구분할 수 없다. 어댑터가 'PK 없음 확인'을 명시 신호로 돌려주면 해소된다.
