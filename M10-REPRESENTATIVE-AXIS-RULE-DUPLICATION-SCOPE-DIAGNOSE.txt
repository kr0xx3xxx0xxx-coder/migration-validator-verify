■ 1. 두 곳의 정확한 위치·로직 대조 — 완전 동일 로직의 순수 복제(미묘한 차이 없음)

  ⓐ services/exact_diff/pk_range_chunk.py:216-251
     select_deterministic_rep_axis(axis_counts, axis_coverage)
  ⓑ routes/agg_diff_route.py:698-729
     _select_direct_rep_axis(axis_counts, axis_coverage)

  두 함수를 라인 단위로 대조한 결과:
    - 후보 필터: `[a for a in axes if coverage.get(a,0)>0] or axes` — 완전 동일
    - band 상수: pk_range_chunk 는 _REP_AXIS_BAND_MIN/MAX(2,200) / agg_diff_route 는
      _DIRECT_REP_AXIS_BAND_MIN/MAX(2,200) — 이름만 다르고 값·용도 동일
    - 정렬키: (구간밖=1, 그룹수 오름차순, 컬럼명 대문자 오름차순) — 완전 동일, 입력 순서 미참조
    - 반환 3분기(SINGLE_AXIS / IN_BAND_FEWEST_GROUPS / OUT_OF_BAND_FEWEST_GROUPS)와 사유문구
      포맷 문자열까지 완전 동일
  → 함수 시그니처(axis_counts, axis_coverage)·본문·반환값 모두 byte 단위로 동일하다. "미묘하게 다른
    부분"은 없다 — 리팩터링으로 단순 통합(rebind) 가능한, 말 그대로의 복제다.
  이는 이미 tests/test_pk_range_chunk_representative_axis_unify.py::test_규칙_자체가_DIRECT_와_동치다
  가 7개 케이스로 증명해 두었다(재확인함, 코드 미수정 상태로 재실행 없이 로직 대조만).

  단, 이 둘을 "감싸는" 상위 함수는 대칭이 아니다(구조적으로 중요한 차이):
    - pk_range_chunk._select_rep_axis (515-547) 는 gb_candidate_scores/gb_selection_order 가
      실제 전달되면 D7-16C 정책(①2~200 ②후보점수 ③선택순서)으로 분기하는 ⓐ 브랜치를 갖고 있다.
    - agg_diff_route._group_dist_from_store (732-786) 는 그런 분기가 아예 없다 — 언제나
      _select_direct_rep_axis(결정적 규칙)만 호출한다. DIRECT 쪽은애초에 후보점수·선택순서라는
      개념 자체가 함수 시그니처에 없다.
  즉 "말단 결정 규칙"은 완전 복제·동일이지만, "그 규칙을 언제 쓰는가"의 정책 계층은 비대칭이다.
  이 비대칭이 §2 시나리오의 핵심이다.


■ 2. gb_candidate_scores/gb_selection_order 를 채우면 정확히 어떤 시나리오에서 순서의존이 되살아나는가

  2-1) 현재 운영 상태(실측, 코드 확인)
    routes/agg_diff_route.py 전체에서 gb_candidate_scores·gb_selection_order 문자열은 0건 —
    유일한 프로덕션 호출부(agg_diff_route.py:337 run_pk_range_chunk_compare)는 이 두 인자를
    아예 넘기지 않는다(grep 재확인, 테스트 파일 제외 전무). 따라서 현재는
    _axis_policy_hint == False 로 항상 고정되어 chunk 경로도 결정적 규칙만 쓴다 — DIRECT 와
    100% 동치가 유지되는 것은 이 두 인자가 "아직 아무도 채우지 않기 때문"이다.

  2-2) 채우기 시작하면 깨지는 지점 — DIRECT 쪽엔 대응 브랜치가 없다
    D7-16C 정책은 pk_range_chunk.py 에만 구현돼 있다. gb_candidate_scores/gb_selection_order 를
    운영에서 채우기 시작해도, 그 값을 넘겨받는 통로는 run_pk_range_chunk_compare(chunk 경로) 뿐
    이고 _group_dist_from_store(DIRECT 경로)는 애초에 이 값을 받을 파라미터가 없다. 즉:
      - 5만행 이하(DIRECT) : 항상 결정적 규칙(select_deterministic_rep_axis) 그대로
      - 5만행 초과(chunk)  : _axis_policy_hint=True 가 되는 순간 D7-16C 정책(점수/순서 기반)으로 전환
    같은 데이터·같은 GROUP BY 선택이라도 5만행 경계를 넘나들 때 대표축 산정 "규칙 자체"가
    바뀐다 — 이것이 바로 PK-RANGE-CHUNK-REPRESENTATIVE-AXIS-UNIFY 가 고친 증상(경계에서 축이
    뒤바뀜)이 D7-16C 정책 활성화를 계기로 재발하는 구조다. 단, 이번엔 "gb_cols 전달 순서"가
    아니라 "정책값을 채우기 시작한 시점"이 방아쇠가 된다는 점이 다르다.

  2-3) 부분 값만 채워도 순서의존이 살아난다(코드로 확인한 구체 조건)
    pk_range_chunk.py:505-506
      _cand_scores = {...gb_candidate_scores...}
      _sel_order = [str(a).upper() for a in (gb_selection_order or _axes)]   # ← 미전달 시 gb_cols 순서로 폴백
    pk_range_chunk.py:511
      _axis_policy_hint = bool(gb_candidate_scores) or bool(gb_selection_order)   # ← 둘 중 하나만 있어도 True
    즉 "후보점수만 채우고 선택순서는 안 채우는" 흔히 있을 법한 부분 배선에서도 _axis_policy_hint
    가 True 로 켜져 D7-16C 분기(538행)로 들어가고, 거기서 동점 tie-break 인 _order(a)(528-530행)는
    다시 gb_cols 전달 순서로 조용히 폴백한다. 점수가 모든 축에 동일/누락(None→-1)이면 사실상
    "gb_cols 순서가 곧 대표축"이던 옛 버그와 동일한 경로로 되돌아간다 — 원 서술의 "순서 의존 경로가
    되살아난다"는 경고가 가리키는 정확한 조건이다.

  2-4) DIRECT 전략과의 "결정성 요건" 충돌
    select_deterministic_rep_axis 계열은 axis_selection_deterministic=True 를 응답에 싣도록
    설계돼 있다(대표축 선정이 재현 가능함을 화면에 명시). D7-16C 정책 분기는 반대로
    axis_selection_deterministic=False 를 싣는다(기존 테스트
    test_후보점수_전달시_기존_정책_유지 113행에서 확인 — "순서/점수 의존 경로임을 정직하게 표기").
    D7-16C 를 chunk 경로에서만 활성화하면:
      - 화면에 표시되는 "선택 순서 무관 고정" 배지·툴팁 문구(§5 실측, PK-RANGE-CHUNK... 보고서
        119-125행)가 5만행 이하/초과에서 서로 다른 근거로 나타난다(DIRECT=deterministic=true
        고정, chunk=선택 시점 값에 따라 true/false 요동).
      - 사용자가 같은 조건을 5만행 경계 앞뒤로 반복 실행하면 "결정적"이라던 배지가 어떤 실행에서는
        사라지는 모순이 재발한다 — DIRECT 는 애초에 이 개념(비결정)이 없어 절대 안 흔들리는데
        chunk 만 흔들리므로, 사용자 입장에서는 "chunk 로 넘어가면 갑자기 불안정해진다"로 읽힌다.
    결론: gb_candidate_scores/gb_selection_order 를 운영에서 채우려면, DIRECT 쪽에도 동일한
    D7-16C 브랜치(또는 최소한 "값이 채워지면 무시하고 항상 결정적 규칙만 쓴다"는 명시적 정책)를
    같이 설계해야 한다 — 그러지 않으면 5만행 경계에서 "규칙 종류 자체"가 갈리는 새로운 형태의
    비대칭이 생긴다.

  2-5) 참고 — gb_candidate_scores 의 잠재적 실제 출처
    저장소 전역에 "candidate_score" 개념은 컬럼 후보 추천(3단계 GB/SUM 후보 선정,
    services/candidate_scoring.py 등)에도 존재하나, 그것은 "이 컬럼을 GROUP BY 후보로 얼마나
    추천하는가" 점수이지 "이미 선택된 GROUP BY 축들 중 어느 것을 대표로 보여줄까"의
    gb_candidate_scores 와는 별개 개념이다. 저장소 어디에도 후자를 실제로 채워 넣는 배선은
    없다(§2-1 grep 결과와 일치) — 즉 이 위험은 "이미 발생 중"이 아니라 "향후 이 값을 채우는
    작업을 설계 없이 진행하면 발생할" 잠재 위험이다.
