1. 결론 요약
────────────────────────────────────────────────────────────
· '판정값(effective)' = ceil(raw × safety_factor). safety_factor 기본값 = 2.0.
· 86,472 × 2.0 = 172,944 (정확히 2배). 이 값이 한도 100,000을 초과 → 실행 차단.
· raw와 판정값이 2배인 이유는 '원본+목적 합산' 같은 정당한 축이 아니라, 단일 추정값에
  곱해지는 보수화 안전계수(2.0) 하나 때문이다.
· 이 2배는 오늘 고친 '오라클 EXPLAIN 15배 과대추정'(ORACLE-GROUPBY-SAFETY-GATE-
  ESTIMATOR-FALLBACK)과는 다른 계층의 로직이다. 그 이슈는 raw 값 자체의 과대추정이었고
  COUNT(*) 래핑으로 이미 수정됨. 이 2배는 raw 산정 '이후' 방언 무관하게 적용되는 별도 계수.
· 산술 버그는 아니다(문서화된 의도적 안전계수). 그러나 두 가지 과보수/혼란 지점이 실재한다
  (아래 5항). 특히 오라클/MySQL/MSSQL의 EXPLAIN 경로는 실제로는 '정확 COUNT'인데
  estimate_kind를 PLANNER_ESTIMATE로 오라벨해 2배를 적용 → 정확값에 과소추정 여유를
  덧씌우는 모순(개선 대상).

3. raw(86,472)와 판정값(172,944)이 정확히 2배인 이유
────────────────────────────────────────────────────────────
· 판정값 = ceil(raw × safety_factor) = ceil(86,472 × 2.0) = 172,944.
· safety_factor 기본값이 2.0이라 정확히 2배.
· '원본 COUNT + 목적 COUNT'를 더한 값이 아님을 두 raw 경로에서 확인:
    - 구조화 경로: min(고유값 곱, source_row_count) — 단일 테이블 기준 단일 값.
    - EXPLAIN 경로: max(src, tgt) — 원본/목적 중 '더 큰' 하나(합산 아님).
· 따라서 2배의 유일한 출처는 안전계수(2.0). 데이터/테이블과 무관한 상수배.

4. 오늘 고친 오라클 EXPLAIN 과대추정 이슈와의 관계
────────────────────────────────────────────────────────────
· ORACLE-GROUPBY-SAFETY-GATE-ESTIMATOR-FALLBACK: 오라클 EXPLAIN PLAN이 표현식 GROUP BY
  (예: 분기버킷)의 NDV를 '거의 전 행 distinct'로 약 15배 과대추정 → 날짜버킷이 되레 차단.
  해결: 오라클/MySQL/MSSQL은 EXPLAIN 대신 COUNT(*) 래핑(정확). → 이건 'raw 값'의 문제였고 수정됨.
· 이번 2배(판정값)는 '같은 계열의 잔존 버그'가 아니라, raw 산정 이후에 적용되는 완전히
  별개의 보수화 계수(safety_factor)다. 방언과 무관하고, PostgreSQL에도 동일하게 걸린다.
· 다만 '연결점'이 하나 있다(3항 재현으로 실증): 오라클 수정으로 EXPLAIN 경로 raw가 이제
  '정확 COUNT'가 되었는데, safety core(라인 224)는 여전히 그 값을 PLANNER_ESTIMATE로 라벨한다.
  → 정확값에 '과소추정 대비 여유(2배)'를 씌우는 모순. 즉 오라클 수정의 후속 정합화가
    안전게이트의 estimate_kind 라벨에는 반영되지 않은 상태다(별개 결함).

5. 정당한 안전장치인가, 버그인가 — 판단
────────────────────────────────────────────────────────────
[정당한 부분 — 산술 버그 아님]
· safety_factor=2.0은 config/model_config.py:178-180에 명시·문서화된 '의도적 보수화 계수'.
  근거: catalog n_distinct·PG 플래너 추정은 상관 컬럼/오래된 통계에서 실제 그룹 수를
  '과소'추정할 수 있으므로, effective=ceil(raw×2)로 여유를 둬 대형 결과 폭발을 예방.
· 정확값(EXACT/EXACT_UPPER_BOUND: 날짜버킷·유한도메인·정확 distinct)에는 계수 미적용 →
  근본 설계는 '추정에만 여유, 정확값엔 여유 없음'으로 올바른 방향.
· reason_code가 ESTIMATE_SAFETY_MARGIN_EXCEEDED(= raw는 한도 이내인데 안전여유로 초과)로
  구분되어 있음 → 시스템이 이 상황을 스스로 인지·기록하고 있다는 증거(은폐된 오류 아님).

[문제/과보수 지점 — 개선 여지]
(P1) 표시 한도 vs 실효 한도 불일치(UX 혼란, 전 방언 공통)
   · 화면엔 '한도 100,000'으로 보이지만, 비정확 추정에는 실효 상한이 50,000이다
     (50,000 × 2 = 100,000). 사용자 입장에선 raw 86,472가 '한도 100,000 이내'인데 차단되어
     "왜 막히지?"라는 인상을 받는다. 신고된 혼란의 핵심이 바로 이 지점.
   · 개선안(진단): 문구에 "안전계수 ×2 적용, 추정값 실효 상한 50,000" 명시 또는 안전계수를
     반영한 '실효 한도'를 함께 표기. (수정 아님 — 제안만)

(P2) 오라클/MySQL/MSSQL 정확 COUNT를 PLANNER_ESTIMATE로 오라벨 → 정확값에 2배 적용(실질 결함)
   · groupby_explain_estimator는 이 3개 방언에서 COUNT(*) 래핑으로 '정확한' 그룹 수를 반환한다
     (docstring: 실측 3ms, 정확). 그런데 safety core 라인 224가 이를 무조건 PLANNER_ESTIMATE로
     라벨 → _EXACT_KINDS에 안 들어가 2배가 적용된다.
   · 결과: 오라클에서 실제 그룹 수가 정확히 86,472인 GROUP BY(한도 100,000 이내로 안전)가
     172,944로 부풀려져 차단된다. 이는 '추정의 과소평가 대비'라는 계수 취지에 어긋난다
     (정확값엔 과소평가 위험이 없음). ← 이번 신고가 오라클 대형 테스트였다면 이 경로일 가능성.
   · 개선안(진단): 라인 224에서 방언별로 kind를 구분(오라클/MySQL/MSSQL COUNT 래핑 결과는
     EXACT, PostgreSQL Plan Rows는 PLANNER_ESTIMATE)해 정확값엔 계수 미적용. 또는 estimator가
     (값, 정확/추정) 종류를 함께 반환하도록 계약 확장. (수정 아님 — 제안만)

[86,472 케이스의 정확한 경로 판별 — 미확정 요소]
· detail 문자열은 구조화·EXPLAIN 두 경로 모두 동일 포맷이라, 문구만으로는 경로를 구분 못 한다.
· 확정하려면 그 실행의 공식 snapshot에 저장된 estimate_kind / estimate_source를 봐야 한다
  (SNAPSHOT_FIELDS에 포함됨, groupby_execution_safety.py:276-278):
    - estimate_source="catalog", kind="CATALOG_ESTIMATE" → 우선순위1(catalog n_distinct). 2배는
      '정당한 보수화'(catalog는 실제로 과소추정 가능). 단 P1 혼란은 여전히 적용.
    - estimate_source="explain", kind="PLANNER_ESTIMATE" + 방언이 오라클/MySQL/MSSQL → P2 결함
      (정확 COUNT에 2배). 방언이 PostgreSQL이면 진짜 플래너 추정이라 2배 정당.
· 오라클 라이브 DB(asis 1523/tobe 1524)가 현재 미기동(접속 거부)이라 XDIFF 라이브 재현은 보류.
  단, 산출 로직 자체는 데이터 무관 상수배(×2.0)이므로 라이브 없이도 이미 확정적으로 규명됨.
