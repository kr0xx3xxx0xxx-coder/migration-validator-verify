  대상 축이 최대 3개(GROUP BY 상한, CLAUDE.md 절대 규칙)이므로 **쌍은 최대 3개**

  순간 사라진다 — 30컬럼이면 435쌍이지만 3축이면 3쌍이다.

  ┌ 방언 ────────┬ 추가 쿼리 ┬ 형태 ────────────────────────────────────────┐
  │ PostgreSQL   │ **1개**   │ 기존 SAMPLE_SRC CTE 의 외부 SELECT 에         │
  │              │           │ `COUNT(DISTINCT (a,b)) AS pf_px_0` 3개 추가.  │
  │              │           │ ROW 생성자 지원 → 왕복 1회만 늘어난다.        │
  │ 오라클       │ 1~2개     │ `COUNT(DISTINCT a,b)` **미지원**.             │
  │              │           │ concat 우회(`a||CHR(1)||b`) 또는              │
  │              │           │ `COUNT(*) FROM (SELECT DISTINCT a,b ...)`.    │
  │              │           │ 후자는 별도 쿼리 1개가 더 붙는다.             │
  │ MySQL        │ (1개)     │ `COUNT(DISTINCT a,b)` 네이티브 지원.          │
  │ MSSQL        │ (2개)     │ 미지원 — 파생 테이블 필요.                    │
  └──────────────┴───────────┴───────────────────────────────────────────────┘

        30M행 × 8컬럼 : 64.13초      → **0.06초**
        ⇒ 5만행 표본 위에서는 **컬럼 수와 무관하게 0.1~0.3초 수준**으로 상한된다.
  근거 ③ 대상 쌍 최대 3개 = 단일컬럼 환산 최대 6컬럼분 미만의 부하.

  추정:
    · PostgreSQL(쿼리 1개 추가) : **+40~120ms**
      (표본 5만행 위 pair 3개 ≈ 단일컬럼 6~10개분 ≒ 4ms×10 + 왕복 1회)
    · 오라클(concat 우회)       : **+80~250ms**
      (문자 결합·NLS 정렬 비용 가산. 별도 쿼리 방식이면 왕복 1회 더)

  ▶ 판정: **예산 안에 들어온다.** 15초 timeout 대비 1% 미만이고, 3단계 진입
    상호작용 지연 임계(수백 ms, :28 주석의 기존 판단 기준)에도 들어온다.
    ⑥ 날짜 버킷이 이미 **표본 없이 전체 스캔**(build_date_bucket_profile_sql:393
    `FROM {from_part}` — SAMPLE_SRC 미사용, 15초 timeout 으로만 방어)을 하고 있으므로,
    표본 위에서 도는 교차 계산은 **기존 ⑥보다 오히려 가볍다**.

3-4. 비용 외 위험 3건 (반드시 설계에 반영해야 하는 것)

  (가) **concat 충돌** — 오라클 우회 `a||b` 는 (a='X|', b='Y') 와 (a='X', b='|Y') 를
       같은 값으로 세어 **종속을 과대 탐지**한다. 구분자는 데이터에 나올 수 없는
       제어문자(CHR(1))를 써야 하고, 그래도 이론적 충돌은 남는다 →
       "종속 '의심'" 이라는 보수적 표현이 정당화되는 근거다(확정 아님).
  (나) **NULL 의미 차이** — `COUNT(DISTINCT)` 는 NULL 을 세지 않는다. PG 에서
       `NULL||'x'` = NULL(행 통째로 누락), 오라클에서 `NULL||'x'` = 'x'(NULL 과 ''
       구분 못함). **같은 데이터에서 방언별 결과가 달라진다.** ROW 생성자 방식
       `COUNT(DISTINCT (a,b))` 는 NULL 을 포함한 튜플을 세므로 또 다른 값이 나온다.
       → 방언 간 판정 일관성이 깨질 수 있어, 방언별 기대값을 테스트로 못 박아야 한다.
  (다) **표본 편향** — 5만행 표본에서 종속으로 보여도 전체에서는 아닐 수 있다
       (특히 계층 데이터가 시간순 적재된 경우). 표본 절단 여부를 근거에 반드시
       남겨야 한다 — 52c22fc 가 도입한 "표본 5만행 기준" 표기 규약을 재사용할 것.

4-2. 권장: **B → C 순차** (한 번에 한 단계 규칙)

  1차 = B(표기만). 실측값을 수집·저장·표시만 하고 **판정은 한 줄도 바꾸지 않는다.**
        → 라이브 데이터에서 "곱 대비 실측" 분포가 실제로 어떻게 나오는지 관측할 수 있고,
          그 관측 없이 임계치(예: 실측 ≤ 곱×0.3 이면 종속 의심)를 정하는 것은
          전형적인 "scoring 미성숙 — 가중치 없는 단락 평가"다(CLAUDE.md 비판적 검토 의무).
  2차 = C(est 치환). 1차에서 임계치를 실측으로 정한 뒤에만 진행.
        C 는 새 판정을 추가하지 않고 **입력값만 정확하게 만드는** 접근이라
        heuristic 증가가 없다는 점에서 구조적으로 가장 깨끗하다.

  A·D 는 권장하지 않는다. A 는 근거 강도(표본·concat 충돌)에 비해 결과가 과하고,
  D 는 F19(점수 분해 미노출)가 해소되기 전에는 점수를 더 불투명하게 만든다.

6. 비판적 검토 (CLAUDE.md 비판적 검토 의무)

6-1. 긍정적 효과
  · 계층종속 조합(시/도 × 시/군/구)이 부당 배제되지 않는다 → 유용한 업무 축 조합 회복.
  · 1:1 종속 쌍(STATUS_CD/STATUS_NM)의 무의미한 중복 추천이 드러난다.
  · 곱 추정이 **"실측 아님"에서 "실측"으로** 바뀌는 유일한 경로다 —
    groupby_plan/groupby_estimate/recommender 3파일의 주석이 10개월째 자인해 온 한계다.

6-2. 구조적 문제점
  · **heuristic 하나 증가**: "실측/곱 비율이 얼마 이하면 종속 의심" 이라는 새 임계치가
    생긴다. 근거 없이 정하면 전형적 하드코딩이다 → §4-2 의 B 선행(관측 후 임계치 결정)이
    이 문제를 정면으로 회피하는 유일한 순서다.
  · **방언 분기 확대**: BaseDialect 에 신규 메서드가 추가되고 4방언 구현 의무가 생긴다.
    다만 실행 지원은 PG·오라클 2개뿐이라 나머지 2개는 None 반환 stub 로 족하다.
  · web_server.py 비대화와는 무관(전부 services/ 계층).

6-3. 운영상 위험
  · **최대 위험은 성능이 아니라 SQL 실패다.** pair 표현식이 방언/타입(CLOB, BLOB,
    XMLTYPE 등 DISTINCT 불가 타입)에서 깨지면, 같은 SELECT 에 있는 단일컬럼 근거까지
    함께 잃는다. → **반드시 별도 쿼리로 발행하고 try/except 로 격리**해야 한다
    (⑥ 날짜 버킷이 이미 그렇게 하고 있다 — :417 "실패는 무시(보조정보)").
  · 오라클 concat 우회는 NLS 정렬·캐릭터셋 이슈 이력이 있는 영역이다
    (기존 project_oracle_charset_collation_merge_break 계열). 문자 결합은 그 위험을
    직접 건드린다 → 오라클은 `SELECT COUNT(*) FROM (SELECT DISTINCT a,b ...)` 형태가
    concat 보다 안전하다(쿼리 1개 더 들지만 충돌·NLS 위험 없음). **이쪽을 권장한다.**
  · (B) groupby_plan_route 는 원본 DB 접속정보를 받지 않는다(GroupbyPlanRequest 는
    candidates/total_rows/include_pair 3필드뿐 — routes/groupby_plan_route.py:18-23).
    여기서 직접 조회하려면 요청 스키마 확장 + 접속정보 전달이 필요하고, 이는
    "평문 비밀번호 전달 경로 확대" 위험이다. → §2-4 권장(A에서 측정, B는 읽기만)이
    보안상으로도 옳다.

6-4. ★ 심각도 재평가 — F20 의 실제 피해는 생각보다 작다
  진단서와 지시서는 "조합이 부당 배제된다"를 주요 피해로 들었으나, 조사 결과
  **2축 조합은 애초에 기본 실행계획에 없다**:
      include_pair: bool = False       (groupby_plan_service.py:69, route:23)
      "§23(v2): 2축 보강은 기본 실행에서 제외 — '보강 분석' 명시 요청(include_pair)일
       때만 세트로 추가."                                  (groupby_plan_service.py:130-131)
  즉 곱 과대추정의 결과는 "검증에서 빠진다"가 아니라 **"'보강 분석' 버튼이 안 뜬다"**이다.
  반대로 1:1 종속 중복 추천(:121 가드가 곱 때문에 무력화)은 **기본 추천 3슬롯을 실제로
  낭비**하므로 이쪽이 더 실질적인 피해다.
  → 착수 시 **우선순위를 '중복 추천 탐지'에 두고, '조합 구제'는 부수 효과로 다루는 것**이
    비용 대비 효과가 크다. 지시서의 문제 서술 순서와는 반대다.

6-5. 지금 구현 여부 판단
  **문서화 우선 → 이후 옵션 B 진행.**
  이유: (1) 임계치를 정할 실측 데이터가 아직 없다. (2) 병행 작업 2건
  (STAGE4-5-STRATEGY-TIMING-AND-TEXT-CLEANUP-FIX / CANDIDATE-SCORE-CONTRIBUTION-
  SERVER-STORAGE-FIX)이 진행 중이고, 후자는 같은 후보 dict 에 필드를 추가하는 작업이라
  **응답 payload 증가가 겹친다**. F19 착수가 끝난 뒤 순차 진행이 안전하다.
