[4] 중복 성격 판단 — 부분적으로 정당하나 GROUP BY/SUM 부분은 통합 필요
════════════════════════════════════════════════════════════════════════
■ 정당한 분리(재사용 불가 사유 있음):
  - diagnosis 서브시스템은 '전수검증(행 단위 대조)'용 역할 후보(MATCH_KEY / CHUNK_KEY / HASH_COMPARE /
    EXCLUDE)와 '불일치 드릴다운 축 선정'을 담당한다. 이 역할들은 메인 통계검증 엔진에 존재하지 않는다.
    → recommender.py 의 exhaustive/match_key/chunk_key/hash 부분은 고유 책임이라 별도 존재가 정당하다.

■ 위험한 중복(복붙 성격, 프로젝트 원칙 '공통화·분리화 최우선, 중복 금지' 위배):
  - GROUP BY / SUM 후보의 '카디널리티 등급 판정 + near-unique/식별자 배제 + 저카디 그룹 적합성' 로직이
    메인 엔진과 diagnosis 양쪽에 각각 구현돼 있고, 임계값이 서로 다르다(low 20 vs 50, mid 1000 vs 200,
    절대상한 60은 diagnosis 에 아예 없음).
  - 오늘의 두 수정(절대 그룹수 상한 60, 날짜형 durable 배제)은 메인에만 반영됐고 diagnosis 에는 없다.
    예) 오늘 C_DATE(distinct 900) 는 메인에선 '월 버킷 구제'되지만, diagnosis recommender 기준으론
        900≤1000 이라 그냥 'mid' 로 추천되고(날짜 버킷 개념 자체가 없음), groupby_scoring 기준으론
        900>200 이라 '그룹 과다'로 제외된다 — 세 경로가 같은 컬럼에 서로 다른 결론.
  - 또한 diagnosis 는 이름 단어 heuristic 을 쓰는데, 이는 메인 정책이 근거저장(explainability) 취약을
    이유로 금지한 방식이다.
  → 앞으로 후보추천 GROUP BY/SUM 규칙이 바뀔 때마다 두 곳을 따로 고쳐야 하고, 누락 시 조용히 divergence
    가 발생하는 구조적 부채가 실재한다.

■ 지금의 실질 영향도 = 낮음
  - /diagnosis/candidate-recommend 는 UI 미배선(사실상 미사용/실험 엔드포인트), diagnosis GROUP BY/SUM
    추천은 전수검증 상세화면에 국한되고 주 4단계 통계검증 흐름에 유입되지 않음. 사용자 대면 버그 아님.

■ 권장 대응책(문서화 우선 — 즉시 리팩토링 아님):
  - GROUP BY/SUM 의 '카디널리티 등급·near-unique/식별자 배제·저카디 적합성' 결정을 메인 공통 core
    (candidate_engine + candidate_recommendation_policy 상수)로 단일화하고, diagnosis 는 그 결과를 소비만
    하도록 전환. diagnosis 고유 역할(MATCH_KEY/CHUNK_KEY/HASH/드릴다운 축)은 그대로 분리 유지.
  - 대규모 리팩토링에 해당하므로(완료된 모듈 다수 관여) CLAUDE.md 규칙대로 계획 제시 + 사용자 승인 후
    별도 작업으로 진행 권장. 본 감사에서는 코드 수정 없음.
