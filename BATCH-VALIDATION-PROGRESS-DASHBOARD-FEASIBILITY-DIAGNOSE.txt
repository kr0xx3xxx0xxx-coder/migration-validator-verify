■ 환경 및 한계 (정직 고지)
- 서비스 포트 8000 가동 확인 (HTTP 401 = 인증 ON 정상 동작)
- 실 DB 전 노드 미가용: Oracle 192.168.0.151:1523/1524 TCP 실패,
  내부 PG 192.168.0.150:5433/5434 TCP 실패, Neon 은 전송 쿼터 소진 상태
- 따라서 라이브 DB 검증 불가 → 운영과 동일한 코드 경로를 in-process 로 구동해 대체 실측
- 결과적으로 진행률 '배선/존재 여부' 확인은 유효하나, 처리량 수치는 엔진 순수값이라
  DB read 시간이 빠져 있음 (시간 추정은 기존 실 DB 실측치를 인용해 분리 기재)

■ 1. 시간 상한 추정 (지시 1)

청크 크기 = 고정 아님, 3단 설정값
  엔진 기본 50,000  services/exact_diff/execution_settings.py:29 (min 10,000 / max 200,000)
  정책 override     routes/agg_diff_route.py:164 (현재 미설정 → 기본값)
  요청 override     routes/agg_diff_route.py:61-62
  ※ 청크는 행 수가 아니라 PK '값' 범위 균등분할(pk_range_chunk.py:128) → 청크당 행 수 불균일

실측 기준값 3종 (250,000행 기준)
  엔진 순수(merge+판정+저장, DB 없음)  약 3.6초    ≈ 70,000 rows/s  ← 이번 in-process 실측
  실 DB · 단순 테이블 + PK 인덱스      약 25초     ≈ 10,000 rows/s  ← 기존 진단 문서 인용
  실 DB · CTE/JOIN wrapping           약 372초    ≈    672 rows/s  ← 오늘 실측(6.2분)

  핵심: 시간의 98%가 DB read/네트워크. 엔진은 1~2%. 코드측 시간 예측은 원리적으로 어려움.
        동일 250k 에서 단순 25초 vs CTE/JOIN 372초 = 15배 차이.

스케일링 (선형 가정, 복합PK18 은 보수적 ×2.5)
  행 수        단순(10k r/s)   CTE/JOIN(672)   CTE/JOIN+복합PK18(269)
  1,000,000      1.7분           24.8분           62분
  3,000,000      5.0분           74분             3.1시간
  5,000,000      8.3분           2.1시간          5.2시간
  10,000,000    16.7분           4.1시간          10.3시간

  → 상한선 결론: 나이스 4세대급 대형 테이블 1건 = 대략 1시간 ~ 10시간
    (예측값 아님. "이보다 오래 걸리면 이상"을 판단하는 상한 용도)

반드시 함께 봐야 할 3가지
  (1) 기존 전체 상한과 충돌 — 일괄검증 상한 기본 7,200초(2시간),
      wrapper_async_job.py:48-58. 3M행 이상은 테이블 1개로 상한 초과.
      대시보드보다 이 상한 재검토가 먼저.
  (2) 복합 PK 는 청크 전략에 진입 못 함 — agg_diff_route.py:39-41 이 복합/문자 PK 를
      DIRECT_STREAM 으로 확정, :269-273 이 HOLD_NON_NUMERIC_PK 로 안전 종료.
      즉 나이스급 복합 PK 18컬럼에서는 chunks_total 이 아예 생기지 않음.
  (3) 오늘 실측 6.2분은 단순 250k 가 아니라 CTE/JOIN 경로 값.

정밀 예측을 막는 변수
  인덱스 유무(지배적) / CTE·JOIN 복잡도(15배) / 통계정보 최신성(플래너 seq scan 선택)
  / 동시 실행 개수(전역4·프로필당3) / PK 값 분포 공백(진행률 비선형)
  / 네트워크 편차(동일작업 wall 2.2배) / Source∥Target 병렬 read 발동조건

■ 3. 3개 검증 유형 job 저장소 (지시 3) — 분리 확정

  A 개별검증 재이관   reimport_job._JOBS_BY_FP/_JOBS_BY_RUN (in-memory)  휘발  청크 또는 행  시각❌
  B 일괄검증 wrapper  batch_execution_state(SQLite)+batch_pause_control  혼합  row(테이블)   시각❌
  C 통계검증 plan     batch_stats_execute_run(SQLite)                    영속  plan          시각✅
  D 전수검증          없음 — UI shell 만(tabler_renderer.py:2290 준비중)

상호참조 실측: B·C 의 references_reimport_job 모두 false.
  batch_pause_control 의 reimport_job 언급은 주석(설계원칙 인용)일 뿐 코드 참조 아님.
  reimport_job.start_or_attach 의 production 호출자는 agg_diff_route.py:946 단 1곳 → A 전용 인프라.

A 내부에서도 전략별로 진행 필드가 다름
  PK_RANGE_CHUNK_COMPARE : chunks_done/total/current_chunk/last_processed_key + processed_*
  DIRECT_STREAM_COMPARE  : processed_src/tgt 만 (청크 필드 없음), 20,000행마다 발행
                           agg_diff_route.py:927 → agg_contribution.py:664-670
  ※ 현재 정책 live_enabled 미설정(=OFF) → 기본 경로는 DIRECT_STREAM. 즉 기본 상태에서는
     청크 진행률이 발생하지 않는다. 이번 진단의 가장 중요한 발견.

결론: 별도 구조 → 통합 계층 필요. 단 난도는 낮음 —
  네 구조 모두 총량/완료량/현재대상/상태 4요소를 이미 갖고 이름만 다름.
  총량   chunks_total|source_count / total_rows / total_plans
  완료량 chunks_done|processed_src / completed+failed+skipped / executed_plans
  현재   last_processed_key / current_target_table / current_plan_table
  → 읽기전용 어댑터 3개 + 통합 DTO 1개로 구현 가능(기존 저장소 미변경)

■ 4. UI 배치 설계 (지시 4)

좌측 메뉴: 신규 최상위 그룹 대신 '주요 검증' 그룹의 첫 항목으로 추가 권장
  주요 검증 (기본 펼침)
    ├ 검증 현황판 [2]   ← 신규(실행 중 job 수 배지)
    ├ 개별검증
    ├ 일괄검증
    └ 전수검증(준비중)
  사유: '검증 결과' 그룹은 끝난 것을 다루고 기본 접힘 → 진행 중 작업에 부적절.
        항목 1개짜리 신규 최상위 그룹은 메뉴 복잡도만 키움(구조 안정화 우선 규칙).
        현황판은 개별/일괄/전수를 가로지르는 뷰이므로 셋을 담은 그룹 머리가 의미상 맞음.
        배지는 다른 그룹이 접혀 있어도 보임.

각 페이지 링크: 공통 컴포넌트 1개(_mvRunningJobsBadge)를 세 화면에서 재사용
  개별검증  단계 커맨드바 우측   "⏳ 이 화면 작업 1건 · 39%"
  일괄검증  그룹 헤더 우측       "⏳ 실행 중 4/40 테이블"
  전수검증  준비중 배너 하단     비활성(개방 시 동일 컴포넌트)
  필터 기준은 기존 스코프 재사용 — session_id + project_id + workflow_type
                                   (reimport_job.active_runs:281-302)
  주의: 개별검증의 기존 '진행 중이던 검증 작업' 팝업(_mvSingleAutoRestore)과 정보 중복.
        팝업→배지 대체가 맞으나 완료 기능 변경이므로 별도 승인 후 진행.

■ 5. 프로그레스바 방식 (지시 5)

청크/행 기반 권장 사유(시간 기반 비권장)
  (1) 남은 시간 계산 근거 없음 — 시간의 98%가 DB read, 경로별 15배 차이
  (2) 청크당 행 수 불균일 — PK 값 균등분할이라 시간 외삽 전제 불성립
  (3) 틀린 ETA 는 신뢰를 깎음 — "47/120 완료"는 항상 참이고 검증 가능
  (4) 조기중단·일시중지 분기를 시간 예측이 반영 못 함(pk_range_chunk.py:374)
  표기: "청크 47/120 (39%)" + 보조 "1,850,000/4,700,000행" + "경과 12:34". 잔여시간 미표시.

단위 폴백 필수(현재 기본경로에 청크 없음)
  chunks_total 있으면      → 청크 기반
  meta.source_count 있으면 → 행 기반
  둘 다 없으면             → "처리 N행(전체 미상)" + 무한 스피너 (가짜 진행률 금지)

동시 진행 시 목록형 2단(부모 배치 + 자식 테이블)
  ▼ 일괄검증·인사급여   row 12/40 (30%)  경과 18:42
      ├ HR_EMP_MASTER   청크 47/120 (39%)  경과 12:34  [일시중지][중단]
      ├ HR_PAY_HISTORY  행 82,000/1,200,000 (7%)
      ├ HR_DEPT         완료 ✅
      └ HR_CODE         대기 ⏸
  부모 진행률은 자식 평균이 아니라 row 완료 수 기준
  (batch_pause_control._percent:267-272 이미 그 방식 — 재사용)

폴링: 기존 pk-records 패턴 그대로 재사용은 비권장
  사유: _mvPkLoadPage 는 패널 단위 독립 루프 → 패널 25개면 체감 1500ms÷25 ≈ 60ms 폭주
        (STATS_VALIDATION_JOB_ORPHAN_CLEANUP §3 실측)
  권장: 화면당 단일 타이머 1개 + 목록 일괄 조회(GET /jobs/active)
        주기 2,000ms(현황판 활성) / 10,000ms(배지만) — 기존 active_run_poll_interval_ms=1000 대비 완화
        정지조건: 전 job terminal · visibilitychange · 화면 이탈 (현재 visibilitychange 핸들러 0개)
        주기는 execution_settings.polling 신규 필드로(하드코딩 금지)
  SSE/WebSocket 비권장 — 전 구간 폴링 기반, 표준 라이브러리 제약에서 이득 없음

■ 6. 기존 회수 메커니즘과의 재사용 (지시 6) — 동일 인프라 구현 가능

  필드                회수 용도                     대시보드 용도              현재
  last_progress_at    정체 판정(>STALL_TTL)         "3분째 진행 없음" 경고     ❌
  last_client_seen    유휴 회수(→PAUSED)            폴링이 자동 touch          ❌
  chunks_done/total   회수 후 재개 지점             진행률 분자/분모           ✅
  started/finished_at 완료 보존 TTL                 경과 시간 표시             ✅

  상호 이득
   - 대시보드 폴링이 곧 last_client_seen 의 갱신원 → 회수 설계가 필요하던 신호를 공짜로 제공
   - 회수의 last_progress_at 이 대시보드 정체 감지 UI 를 그대로 가능하게 함
     ("47/120 · ⚠ 4분째 진행 없음") — 사용자가 원한 "지금 상황을 알 방법"에 가장 근접
   - STALL_TTL 실측 근거는 진행 중인 REIMPORT-JOB-PROGRESS-HEARTBEAT-INTERVAL-DIAGNOSE 가 생산
     (reimport_progress_heartbeat_interval_measure.py) → 대시보드 정체 임계와 동일 상수 사용
  ⚠ 단 gap 실측은 실 DB 필요, 이번 DB 미가용으로 미확보. 임계 없이 정체 경고를 먼저 붙이면
    정상 job 을 정체로 오표시함.
  권장: last_progress_at 추가(2줄)를 회수+대시보드 공통 1단계로. 필드를 두 번 설계하지 않음.
