작업명 : LARGE-DATA-SORT-EXPOSURE-DIAGNOSE
⚠️ 추가 작업 필요 - 정렬 노출 전수 진단 완료(코드 무수정). 도구측 최대 위험은 재이관 DIRECT_STREAM 의 전체 테이블 ORDER BY — 30M행 실측 첫 행까지 270초, 5만행 상한이 이를 못 막음. PostgreSQL 라이브 실측만 환경 미도달로 미완.

0. 결론 요약
════════════════════════════════════════════════════════════════════════════════
사용자 우려는 실재한다. 다만 위험은 경로마다 크게 다르고, 가장 큰 도구측 노출은
"통계검증"이 아니라 "재이관 DIRECT_STREAM" 이다.

  위험 순위(도구가 만드는 정렬)
   1위  재이관 DIRECT_STREAM 전체 ORDER BY   ── 사전 크기 게이트 없음. 30M행 270초 blocking. ★최대
   2위  후보추천 profile 재수집 COUNT(DISTINCT) ── 샘플·타임아웃 전무, 최대 30컬럼. 30M×8컬럼 158초
   3위  재이관 PK index 집계 ORDER BY         ── AGG_MAX_KEYS(6만) 상한이 정렬 완료 후에만 작동
   안전  PK_RANGE_CHUNK / 통계검증 / 후보추천 3단계 profile ── 각각 범위한정·그룹수 게이트·5만행 샘플로 통제됨

사용자 원본 SQL 유래 정렬(CTE+윈도우함수)은 도구측 정렬보다 3.9배 무겁다
(250K행 기준 옵티마이저 TempSpc 추정 67.4MB vs 17.3MB). 도구가 제거할 수 없는 영역이다.

핵심 구조 결함 1건: 코드베이스 전체에 work_mem / PGA / sort_area / TEMP / 스필 관련
참조가 **0건**이다(grep 전수). 즉 정렬 메모리를 인지·추정·경고하는 장치가 아예 없다.

3. 대량 데이터 실측 — 디스크 스필 재현
════════════════════════════════════════════════════════════════════════════════
계측 방법(제약 대응)
  · nxdnp 계정은 v$mystat / v$sesstat / v$sql_workarea / v$tempseg_usage 전부 ORA-00942(권한 없음).
    → 워크에어리어 통계 직접 조회 불가.
  · ALTER SESSION workarea_size_policy=MANUAL + sort_area_size=1MB 는 명령은 성공하나
    **23ai 에서 실효 없음을 실측 확인**(정렬 시간 AUTO 2.409s vs MANUAL 2.389s, 무차이) → 대조군 무효.
  · 최종 채택: 동일 SQL 의 'ORDER BY 있음' vs 'ORDER BY 없음' 실행시간 차 = 순수 정렬비용.
    행 증폭은 CONNECT BY 승수 조인(테이블 생성/변경 없음, 순수 읽기).

[3-1] 도구 STREAM SQL 첫 행 도달 시간 — 정렬의 blocking 특성 ★핵심
   실제 도구가 발행하는 SQL(dialects/oracle.key_hash_stream_sql)을 그대로 실행

     규모      ORDER BY 있음(첫 행)   ORDER BY 없음(첫 행)   배율
     ───────   ────────────────────   ────────────────────   ──────
     250K              1.964 s               0.015 s          131 x
     5M               34.652 s               0.286 s          121 x
     30M             270.286 s               0.539 s          501 x

   · 5,000행까지 받는 시간은 첫 행 시간과 거의 같다(30M: 270.286 → 270.306s).
     = 정렬이 끝나기 전에는 단 1행도 나오지 않고, 끝나면 한꺼번에 쏟아진다.
   · **30M행에서 4분 30초 동안 서버가 정렬만 하고 클라이언트는 완전 대기**한다.

[3-2] 정렬비용 스케일 곡선 (좁은 투영, ROWNUM 래퍼로 네트워크 배제)
     규모        행수         정렬있음    정렬없음    순수정렬    행당 정렬비용
     ────────    ──────────   ─────────   ─────────   ────────    ─────────────
     250K           250,000     0.074s      0.024s      0.050s       0.200 µs/행
     1M           1,000,000     0.304s      0.095s      0.209s       0.209 µs/행
     5M           5,000,000     2.196s      0.505s      1.691s       0.338 µs/행  ← 꺾임 시작
     15M         15,000,000     6.651s      1.220s      5.431s       0.362 µs/행

   · 행당 비용이 0.200 → 0.461 µs 로 2.3배 악화. 1M~5M 구간에서 꺾인다
     = 워크에어리어를 넘어 TEMP 스필로 전환된 지점. 초선형 열화 확인.
   · 이 표는 md5 계산이 pruning 된 좁은 투영이라 [3-1] 대비 과소평가치다. 실제 도구 부하는 [3-1].

[3-3] 후보추천 profile 재수집(services/profile_recollect_service.py) — 무제한 COUNT(DISTINCT)
     규모        5컬럼        8컬럼
     ────────    ─────────    ─────────
     250K           0.37 s       0.53 s
     5M             9.78 s      14.64 s
     30M          116.99 s     158.29 s

   · max_cols 상한이 30 이므로 30컬럼이면 30M행에서 500초 이상으로 외삽된다.
   · statement timeout 이 없어 그때까지 세션이 계속 물린다.

[3-4] 성능 저하 정리
   · 스필 자체의 절대 비용은 이 Free 인스턴스(2 vCPU) 기준 30M행 정렬 13.8~270초.
   · 진짜 위험은 시간이 아니라 **TEMP 용량과 PGA limit** 이다. §2 외삽대로
     STREAM 2.08GB / 사용자 윈도우 8.09GB 는 pga_aggregate_limit(2GB)를 넘는다.
     운영 오라클에서 TEMP 테이블스페이스가 부족하면 ORA-01652(temp segment 확장 실패),
     PGA limit 초과 시 ORA-04036 으로 세션이 종료된다. 다중 사용자 동시 실행이면 배수로 악화된다.
   · 본 진단 인스턴스는 TEMP 여유가 충분해 ORA-01652 를 재현하지는 못했다(과장 금지).

5. 대응 방향 제안 (이번엔 구현하지 않음)

[5-A] 도구가 통제 가능한 지점

 A-1 재이관 DIRECT_STREAM 사전 행수 게이트 (최우선, 위험 대비 비용 최소)
     run_exact_diff 진입 시점에 이미 보유한 expected_src_count / COUNT 사전검증 결과로
     PHASE1_MAX_ROWS 초과 여부를 **SQL 발행 전에** 판정해 HOLD 한다.
     지금은 같은 값을 스트리밍이 끝난 뒤(engine.py:428) 쓰고 있을 뿐이라, 판정 시점만 앞당기면 된다.
     신규 DB 왕복 0회. 30M행 기준 270초 → 0초.
     · 구조 영향: engine.py 진입부 가드 1개. 모듈 분리·의존 방향 불변.
     · 위험: 사전 count 가 없는 호출 경로에서는 게이트가 비어 기존 동작으로 남는다(무해한 폴백).

 A-2 전략계획을 실제 실행 경로에 연결
     full_compare_strategy_planner 는 이미 대형이면 PK_RANGE_CHUNK 를 고르도록 되어 있으나
     (:44-51), direct_stream_max_rows 가 None 이면 항상 DIRECT 로 떨어진다(:47).
     routes/strategy_route.py:48-55 외에는 이 임계가 주입되지 않는다.
     → §3 실측(1M~5M 구간에서 스필 전환)을 근거로 기본 임계값을 부여하는 안.
     · 주의: CLAUDE.md 자동 fallback 금지 원칙(§3·§14)과 충돌하지 않도록, 자동 전환이 아니라
       "DIRECT 차단 + CHUNK 권고" 형태여야 한다.

 A-3 profile 재수집에 3단계와 동일한 5만행 샘플 + statement timeout 적용
     column_profile_service 의 SAMPLE_SRC CTE 구조를 그대로 재사용(신규 로직 없음).
     30M×8컬럼 158초 → 1초 미만. distinct 값이 표본 기반이 되므로 근거 표기에
     "표본 5만행" 을 함께 남겨야 한다(explainability 훼손 방지 — 이게 없으면 조용한 과소추정이 된다).

 A-4 A2/A3 의 order_by=True 재검토
     agg_contribution.py:114-119 주석의 "Index Scan 으로 정렬 회피" 전제가 오라클에서 성립하지
     않음이 §2 R2 로 확인됐다. merge-join 알고리즘 요건이라 정렬 자체는 제거 불가하나,
     최소한 주석의 근거(PG 12M 실측)를 오라클에 확대 적용하지 않도록 기록 정정이 필요하다.

 A-5 정렬 규모 사전 경고(선택)
     실행 전 EXPLAIN 의 TempSpc(오라클) / Sort Method·work_mem(PG) 를 읽어
     임계 초과 시 사용자에게 경고 배너를 띄우는 안. 이미 groupby_explain_estimator 가
     EXPLAIN 호출 인프라를 갖고 있어 재사용 가능.
     · 다만 heuristic 임계 하드코딩이 늘어나므로, 값은 config/size_threshold_registry 단일 출처로.

[5-B] 사용자 원본 SQL 에 내재된 정렬 — 도구가 제거할 수 없음
     제거하면 결과 자체가 달라지므로(윈도우함수·DISTINCT 는 의미론적 필수) 손대면 안 된다.
     대응은 '안내·경고' 뿐이다.

 B-1 1단계 분석 결과에 "정렬 유발 구문 감지" 표시
     파서가 이미 CTE/윈도우함수/DISTINCT 를 인식한다(sql_structure_check.py 등).
     감지 시 "이 이관 SQL 은 원본에 전체 정렬을 유발하는 구문(윈도우함수 등)을 포함합니다.
     대량 테이블에서는 원본 DB 의 TEMP 사용량이 커질 수 있습니다" 수준의 정보 배너.
     · 판정(PASS/WARNING/SKIP)에는 영향 주지 않는 순수 표시 축으로 둘 것.

 B-2 도구가 그 위에 정렬을 겹치지 않는지 확인
     현재 통계검증은 최상위 ORDER BY 를 제거(B1)하므로 겹치지 않는다 — 유지되어야 할 좋은 성질이다.
     §2 U2 에서 WINDOW SORT + HASH GROUP BY 2단으로 쌓이는 것은 사용자 SQL 의 정렬 1개 +
     도구의 해시집계 1개이며, 도구가 정렬을 추가한 것은 아니다.

[5-C] 우선순위 판단
