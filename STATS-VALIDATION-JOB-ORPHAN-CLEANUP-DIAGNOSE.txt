[정정 — 중요] "새로고침 이후에도 폴링이 계속된다"는 재현되지 않았다.
  구간별 pk-records 호출 실측:
    드릴다운 진행 중 25초           → 5회 (간격 1.6~2.0초)
    새로고침 후 팝업 방치 ×3(각 40초) → 0회 (active-run 1회뿐)
    새로고침 후 25초                 → 0회
    '이어서 보기' 후 25~60초         → 0회
    개별검증 화면 이탈 후 60초        → 0회
  새로고침은 문서를 파괴하므로 이전 setTimeout 루프는 반드시 소멸하며,
  새 문서에서 폴링이 자동 재개되지도 않았다.
  → 화면에서 본 반복 요청은 '새로고침 직전' L2 폴링 기록일 가능성이 높다
    (DevTools Preserve log 가 켜져 있으면 새로고침 후에도 목록에 남는다).
  → 60ms 급 간격은 그룹 패널을 여러 개 열었을 때로 설명된다. _mvPkLoadPage 폴링은
    패널(uid|cacheKey)마다 독립 루프라 체감 간격 = 1500ms ÷ 열린 패널 수 (25개면 60ms).
    단일 패널이었던 이번 실측은 1.6~2.0초였다.
  확정 방법: 증상 화면에서 반복 요청의 Initiator 스택(_mvPkLoadPage 인지 _mvRiStartPolling 인지)과
    동시에 열린 그룹 패널 수를 확인하면 즉시 판별된다.

라이브 확인:

  즉 명시적 취소 API 외에 job 을 멈추는 경로가 없다.
→ CACHE-REUSE-VERIFY 의 "시간 기반 TTL 없음" 결론과 일치하며, 이번 증상과 직접 연결된다.

4. 좀비 누적과 _JOBS_MAX=16 LRU 상호작용 (지시 4)
────────────────────────────────────────────────────────────────────────
라이브: 서로 다른 fingerprint job 2개 추가 → active count=2 동시 진행, 브라우저 종료 후에도 유지.

결정적 검증(in-process, 동일 코드 경로 · 실 DB 부하 없음):
  PREPARING 좀비 20개 생성        → store 20개 잔류 (상한 16 초과, 축출 0건)
  + 정상 완료(READY) job 7개 투입 → 완료 job 은 1개만 생존, 좀비 20개 전원 잔류
  5초 방치                        → 시간 기반 회수 0건

원인 — reimport_job._evict():
  done = [... if j["status"] != PREPARING]; if not done: break
  · PREPARING 은 축출 제외 → 좀비 불멸, 상한 16 사실상 무력화
  · 축출 압력이 전부 '완료 job' 에 쏠린다 → prepare 1회 후 재사용 캐시가 좀비 때문에 조기 폐기
    (오늘 CACHE-REUSE-VERIFY 에서 확인한 재사용 이득이 좀비 환경에서 무너진다)
  · 부수 결함: done 판정이 status != PREPARING 이라 CANCEL_REQUESTED / PAUSE_REQUESTED(진행 중)도
    '완료'로 분류되고, finished_at=None → 0 정렬이라 최우선 축출 대상이 된다(실측: 압력 투입 후 소멸)

즉 질문하신 "정상적인 새 job 이 밀려나는가"의 답은 —
  좀비가 밀려나는 게 아니라, 좀비가 자리를 점유한 채 정상 완료 job 이 밀려난다.

5. 설계안 (지시 5)
────────────────────────────────────────────────────────────────────────
(a) 클라이언트 beforeunload/pagehide → 서버 취소 신호 (sendBeacon)
  한계(모두 실재):
   · 강제종료·탭 크래시·OS 절전·전원차단·네트워크 단절에서는 미도달 → 단독으로 문제 해결 불가
   · sendBeacon 은 Content-Type 제약(text/plain·Blob)이라 현재 JSON body 라우트 그대로 못 씀
   · session_id 는 localStorage 공유 → 한 탭을 닫으면 다른 탭의 정상 실행을 죽일 위험
   · 현행 UX 와 정면 충돌: beforeunload 에서 새로고침과 탭 닫기를 구분할 수 없어,
     여기서 취소하면 '이어서 보기' 기능 자체가 무의미해진다
  → 취소 신호로 쓰는 것은 부적절. 쓰더라도 '뷰어 이탈 힌트' 기록 수준이어야 한다.

(b) 서버측 유휴 회수(idle reclaim) — 권장
  job 에 두 시각 기록:
    last_client_seen  : pk-records / active-run* 조회 시 touch (화면이 이 run 을 보고 있는가)
    last_progress_at  : worker 진행 콜백에서 touch (job 이 실제로 전진하는가)
  판정(값은 execution_settings 로 관리 — 하드코딩 금지):
   1) 유휴 회수: now-last_client_seen > CLIENT_IDLE_TTL(10~15분) → PAUSED 로 정지(취소 아님).
      checkpoint 보존 → 사용자가 돌아오면 '이어서 실행'. 기존 pause/resume 배선 재사용.
   2) 정체 판정: now-last_progress_at > STALL_TTL(30분) → FAILED/ORPHAN 확정 + store.finish_run
      호출로 디스크 RUNNING 잔재를 남기지 않는다.
   3) 완료 보존 TTL: finished_at + KEEP_TTL(2시간) 경과분 제거. LRU 상한과 분리해
      '완료 job 이 좀비 때문에 밀려나는' 현상 제거.
   4) _evict done 판정을 (READY, FAILED, CANCELLED, EARLY_STOPPED, PAUSED) 로 좁혀
      CANCEL_REQUESTED/PAUSE_REQUESTED 오축출 차단.
  장점: 클라이언트 협조 불필요(크래시·전원차단에도 동작), 판정 지점이 서버 한 곳,
        시각 주입으로 단위 테스트 가능.

병행 여부 의견: (b) 단독으로 충분하다.
  (a)는 회수 지연을 줄이는 보조일 뿐이고 현행 '이어서 보기' UX 와 충돌 위험이 있어 지금 넣을 이유가 없다.
  굳이 넣는다면 pagehide 에서 last_client_seen 만 앞당기는 형태여야 하고, 판정·정지는 서버가 한다.
