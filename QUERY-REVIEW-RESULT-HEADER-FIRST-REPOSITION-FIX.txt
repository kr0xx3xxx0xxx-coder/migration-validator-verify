■ 1. 요청 내용과 이번 작업의 범위

개별검증 1단계(쿼리검토) 화면의 "쿼리 검토 결과" 표를 아래와 같이 재구성했다.

  (1) 표의 위치를 "SQL 입력" 박스 아래에서 위(상단 단계 탭과 SQL 입력 사이)로 옮긴다.
  (2) 표시 방식을 바꾼다 — 탭에 진입한 순간부터 헤더(컬럼명)는 항상 보이고,
      값(데이터 행)은 쿼리검토 실행 후에만 그 아래 채워지도록 한다.
  (3) 헤더 항목과 순서를 바꾼다(No 열 제거, 목적/원본 순서 교체, 라벨 변경).
  (4) [추가 요구] 헤더에 "처리시간" 열을 상태 바로 앞에 추가하고, 값은 기존 계측값을 재사용한다.
  (5) [추가 요구] 탭 아래 별도로 떠 있던 "· 1단계 처리시간: N초" 표시 줄을 제거한다.

범위는 사용자가 명시한 대로 1단계(쿼리검토) 화면 하나로 한정했다. 2~5단계의 유사한 표·요약
카드는 이번에 손대지 않았다.


■ 2. 현재 구조 파악 결과 (수정 전에 먼저 확인한 사실)

"쿼리 검토 결과" 표는 다음 3개 지점이 협력해 그려지고 있었다.

  · DOM      : ui/tabler_renderer.py 의 #queryReviewCard > #qrSummary
  · 렌더 함수 : renderQueryReviewSummary(data)  — /analyze 응답을 받아 그리드를 그린다
  · 그리드 정의: ui/grid_helpers.py 의 _mvQueryReviewColumns() / _mvQueryReviewRows(a)
                (Tabulator 로 그리고, 미로드/실패 시 _mvGridDataToHtml 의 HTML table 로 폴백)

데이터 출처는 전부 /analyze 응답이다. 원본/목적 테이블은 _mvTablesOf(a), 입력·추출 컬럼수와
매핑은 _mvColsOf(a)(parse_result.insert_cols / select_items), 조건은 parse_result.where 유무,
조인은 parse_result.joins 개수, 상태는 blocked/success 로 판정한다.

여기서 "왜 실행 전에는 헤더조차 안 보였는가"의 원인이 드러났다. #queryReviewCard 는
#mvResultArea(분석 결과 영역) 안에 있었고, 이 영역은 분석 전 display:none 이다. 즉 표가 늦게
그려져서가 아니라 표를 담은 영역 자체가 감춰져 있었던 것이다. 따라서 "헤더 먼저 노출"은
렌더 타이밍만 손대서는 해결되지 않고 DOM 위치 이동이 반드시 함께 필요했다.

"1단계 처리시간" 줄은 단계 탭 옆 슬롯(#mvStage1ProcessingTime)에 표시되며, 값의 출처는
/analyze 응답의 diagnostics.total_ms 다. 이 값을 쓰는 표시 함수(_mvShowStageProcessingTime /
_mvClearStageProcessingTime / _mvSyncStageProcessingTimeVisibility)는 1·2·4·5단계가 공유한다.


■ 3. 실제 수정 내용

(1) 표 위치 이동 — ui/tabler_renderer.py
    #queryReviewCard 블록을 #mvResultArea 안에서 꺼내 #sqlInputCard 바로 위로 옮겼다.
    카드는 여전히 SINGLE_STEP_CARDS.query 소속이므로 2~5단계 pane 에서는 기존과 동일하게
    가려진다(단계별 pane 가림은 id 기준이라 DOM 위치 이동의 영향을 받지 않는다).

(2) 헤더 상시 노출 — ui/tabler_renderer.py
    _mvRenderQueryReviewHeaderOnly(force) 를 신설했다. 값 행이 0개인 '같은 그리드'를 그리는
    함수로, 컬럼 정의와 렌더러를 실행 후 렌더와 완전히 동일하게 재사용한다(테두리·글자체·색상이
    같고 새 디자인을 만들지 않았다). 호출 지점은 두 곳이다.
      · _applySinglePane() — 1단계 pane 진입 시. 단 이미 값 행이 있으면 덮어쓰지 않는다
        (탭을 다시 눌러도 결과가 사라지지 않는다).
      · resetAnalysisUi() — 분석 초기화/차단 시. 기존에는 카드를 통째로 display:none 처리해
        잔상을 지웠는데, 이제 카드는 상시 노출 자리이므로 값 행만 비우고 헤더를 다시 그린다.

(3) 헤더 구성 변경 — ui/grid_helpers.py
    최종 순서: 목적테이블 · 원본테이블 · 입력컬럼수 · 추출컬럼수 · 컬럼매핑수 · 조건문 · 조인 ·
    처리시간 · 상태.
      · No 열 제거: 자동 No 열은 모든 단계 그리드가 공유하는 helper(_mvGridDataToHtml,
        _mvRenderTabulatorGrid)가 붙인다. 공용 동작을 바꾸면 2~5단계까지 영향을 받으므로
        gridData.noRowNumber 라는 opt-in 플래그를 만들어 1단계 그리드만 선언하도록 했다.
        다른 단계 그리드는 플래그를 지정하지 않으므로 No 열이 그대로 유지된다.
      · 목적/원본 순서 교체, '매핑'→'컬럼매핑수', '조건'→'조건문' 으로 라벨만 변경했다.
        각 열이 읽는 field(값 출처)는 전부 그대로다.

(4) 처리시간 열 — ui/grid_helpers.py
    _mvQueryReviewProcMs(a) 를 추가해 /analyze 응답의 diagnostics.total_ms 를 그대로 읽는다.
    새로 계측하지 않으며, 포맷도 기존 _mvFmtStageDur() 를 그대로 쓴다(값·표기 규약 동일).
    미계측(실행 전)이면 '-' 로 표시한다.

(5) '1단계 처리시간' 줄 제거 — ui/validation_plan_renderer.py
    표시 함수가 1·2·4·5단계 공유라는 점을 근거로, 함수를 삭제하거나 계측을 끊지 않고
    _mvSyncStageProcessingTimeVisibility() 안에서 1단계 슬롯만 상시 숨기도록 했다.
    슬롯 DOM 과 저장 값(textContent)은 그대로 유지된다 — 값을 기록하는 다른 로직과 회귀
    테스트가 깨지지 않게 하기 위해서다. 2~5단계 표시는 종전과 완전히 동일하다.
    (이 판단 근거는 사용자 지시의 "공유 함수라면 조건부로 1단계만 제외" 요건을 따른 것이다.)

■ 6. 남은 사항 / 참고

· 이번 범위는 1단계 한정이다. 2~5단계의 유사 표(COUNT 그리드 등)는 No 열·라벨·처리시간 줄
  모두 종전 그대로 두었다. 다른 탭 적용은 별도 지침으로 진행한다.
· No 열 제거는 1단계 그리드만 opt-in 하는 방식이라, Tabulator 툴바의 "↕ 초기 순서" 버튼은
  이 그리드에서만 정렬 기준(No)이 없어 동작하지 않는다. 이 그리드는 원본이 1개면 1행,
  다중 원본이어도 원본 수만큼의 행이라 실사용 영향은 없다고 판단해 그대로 두었다.
· 1단계 슬롯은 숨겼을 뿐 값 기록은 계속된다. 표시 재개가 필요하면
  _mvSyncStageProcessingTimeVisibility 안의 숨김 목록 한 줄만 되돌리면 된다.
