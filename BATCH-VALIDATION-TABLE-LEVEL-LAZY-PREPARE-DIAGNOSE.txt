작업명 : BATCH-VALIDATION-TABLE-LEVEL-LAZY-PREPARE-DIAGNOSE
⚠️ 추가 작업 필요 - 테이블 단위 지연 조사(lazy prepare) 구조 미존재(prepare 자체가 일괄에 미배선), 재사용 가능 컴포넌트는 확보됨 — 코드 수정 없이 진단만 완료

────────────────────────────────────────────────────────────────────────
■ 한 줄 결론
────────────────────────────────────────────────────────────────────────
일괄검증은 각 테이블에 대해 "COUNT + 그룹별 집계 요약"까지만 계산하고,
상세 레코드 조사(prepare = /agg-diff/prepare, exact_diff PK index)는
**한 번도 호출하지 않는다**. 즉 "5,000개 테이블 전부 무거운 조사가 미리 도는 구조"는 아니다.
그러나 "클릭했을 때 그 테이블만 조사한다"는 지연 조사 구조도 **없다**(클릭해도 아무 조사도 안 함).
prepare 는 개별검증 화면에만 존재하며, 그것도 전역 단일 상태(window._mvPkState)라
현재 열려 있는 테이블 1개 전용이다. → 테이블 단위 lazy prepare 는 **신규 구현 필요**.

[테이블 1건당 실제 DB 작업]
  ① analyze   — 파싱 + 컬럼 메타/pg_stats/프로파일 조회

  (c) docs/PHASE_4_D8_BATCH_INDIVIDUAL_PARITY_PLAN.md:57
      "Core B(정밀 exact-diff, /agg-diff/prepare + reimport_job) — 일괄: **미사용**,
       일괄엔 정밀 chunk 경로 없음, 위험 높음 → **HOLD**(후속 adapter)"
      같은 표 :59 — "판정(재이관/목적단독) … Core B 미사용에 종속 → HOLD"

  ⇒ 질문 1 답: **요약만 계산한다. 상세(prepare)는 전부 미리 계산하지 않는다(0회).**

■ 2. "목록은 가볍게, 상세는 클릭 시" 구조가 테이블 단위에도 있는가?
────────────────────────────────────────────────────────────────────────
결론: **그룹 단위에만 있고, 테이블 단위엔 없다.** 그나마 그 그룹 단위 구조도 개별검증 화면 전용이다.

[개별검증 — 존재하는 지연 구조(그룹 단위)]
  ui/tabler_renderer.py:16421  _mvToggleRowAggDiff()   ← 통계 그룹 행 클릭
    → :16480  _mvPkEnsurePrepared()  → POST /agg-diff/prepare   (여기서만 원본/목적 DB 접속)
    → :16474  _mvPkGo_<uid>()        → _mvPkLoadPage() → GET /agg-diff/pk-records
  · prepare 는 코드 문구 그대로 "재이관 PK index 준비 중…(**테이블당 1회**)"(:16489).
    즉 단가는 이미 '테이블 1개' 단위다.
  · 그룹 클릭은 그 준비된 index 에 scope 필터(scope_col/scope_val)만 거는 조회다
    → **그룹 단위 lazy 는 사실상 "prepare 이후의 조회 필터"이지 별도 조사 트리거가 아니다.**
  · 상태 보관은 전역 단일 객체 window._mvPkState(:16481) — 동시에 테이블 1개만 다룰 수 있다.

[개별검증 — 자동 prewarm(참고)]
  ui/tabler_renderer.py:17064 _mvPkPrewarm() — 통계검증 완료 직후 백그라운드 1회 자동 prepare.
  발화 조건: 불일치>0 AND PostgreSQL AND 원본 COUNT ≤ 50,000 (:17071). 일괄에는 이 호출이 없다.

[일괄검증 — 없음]
  일괄 결과 화면의 공통 요약행에는 '재이관 PK' 열이 **이미 존재**하지만
  (ui/grid_helpers.py:990 헤더 / :977 셀),
  일괄은 그 값이 고정 문자열이다 — tabler_renderer.py:29709 에서
  ctx.pkTxt = 'HOLD'(게이트 차단 시) 또는 '—'. 클릭 핸들러도, prepare 호출도 없다.

  ⇒ 질문 2 답: **테이블 단위 지연 조사 구조 없음. 그룹 단위 구조는 개별검증에만 있음.**

■ 3. 5,000 테이블 실행 시 실제 부담 (코드 기준 추정)
────────────────────────────────────────────────────────────────────────
"무거운 조사(prepare)가 한꺼번에 도는" 부담은 **없다**(2번 참조).
대신 다른 종류의 부담이 구조적으로 존재한다.

[순차/병렬]
  · row(테이블) 간 병렬 = **0**. batch_single_core_wrapper.py:592~607 의 단순 for 루프.
  · docs/BATCH_VALIDATION_SPEED_IMPROVEMENT_DESIGN.md:61 —
    "row 루프 완전 순차(row 간 병렬 0) … 구조 — N× 직렬(**지배적**)"
  · 한 row 내부만 부분 병렬: 통계 src/tgt 2스레드(원본·목적이 서로 다른 물리 DB일 때만,
    facade:337). 세트 병렬은 기본 OFF(facade:402 _stats_set_parallelism, flag MV_STATS_SET_PARALLEL).
    COUNT 은 항상 순차(설계문서 :36).
  · 제한 병렬 스케줄러 services/batch/validation_scheduler.py 는 **존재하지만 공식 경로에 미배선**.
    유일한 호출부가 routes/batch_route.py:2122 — 이미 DISABLED 된 legacy /batch/excel/run-minimal 안이다.
    또한 max_concurrent_per_target_profile=1 이라 동일 src/tgt 배치는 켜도 병렬 0(설계문서 :49~53).

[연결]
  · batch 실행 1회 = request_connection_scope 1개로 전체를 감싼다
    (batch_single_core_wrapper.py:621) → 원본/목적 연결 **각 1개**를 5,000 row 가 공유.
    연결 폭증 위험은 없다. 대신 그만큼 완전 직렬이다.
  · 시작 시 pg_stats / PK·UK 메타를 connection 별 1회 bulk prefetch(:536 _prefetch_batch_column_stats).

[타임아웃]
  · 통계검증 SQL: 60,000ms (services/stats_execute_service.py:43,
    EXECUTE_STATEMENT_TIMEOUT_MS, env MV_EXECUTE_STATEMENT_TIMEOUT_MS)
  · analyze 메타조회: 별도 예산(_ANALYZE_DB_STATEMENT_TIMEOUT_MS)
  · **COUNT 은 타임아웃 없음**(stats_execute_service.py:40~41 주석에 명시)
  · **배치 전체 상한 없음**. 중단은 row 경계 cooperative cancel 뿐
    (진행 중 SQL kill 안 함 — batch_single_core_wrapper.py:597 주석)

[HTTP 형태 — 실질 위험]
  · run-wrapper 는 **동기 blocking 단일 요청**이다. 5,000 row 루프가 끝날 때까지 응답하지 않는다
    (routes/column_candidate_gen_route.py:491 → :530 return).
    UI 도 단일 await fetch(ui/tabler_renderer.py:7893).
  · 진행상황은 별도 GET /batch/runs/{id}/execution-status 폴링으로만 확인.
  · ⇒ 5,000건이면 브라우저/역방향 프록시 타임아웃, 서버 워커 1개 장기 점유가 현실적 위험.
    (테이블당 1초만 잡아도 약 1.4시간, 3초면 4시간 이상 — 전 구간 단일 요청 유지)

  ⇒ 질문 3 답: 순차(병렬 0)·per-쿼리 60초 타임아웃·배치 전체 상한 없음·동기 단일 HTTP.
     부담의 본질은 "무거운 조사 5,000회"가 아니라 "**가벼운 요약조차 5,000회 직렬**"이다.

■ 5. 오늘 만든 개별검증 드릴다운 구조를 테이블 단위로 재사용 가능한가?
────────────────────────────────────────────────────────────────────────
[그대로 재사용 가능 — 서버측(수정 0)]
  · POST /agg-diff/prepare              routes/agg_diff_route.py:707
    - fingerprint 기반 중복 방지: 같은 지문이면 READY 즉시 재사용 / PREPARING 이면 기존 job 에 연결
      (:798~805). 테이블 N개를 각각 준비해도 서로 간섭 없음.
  · GET  /agg-diff/pk-records           routes/agg_diff_route.py:899
    - **완전히 테이블 무관**: (run_id, scope_col, scope_val, page) 만 받는다.
    - docstring 명시 "저장 index 만 조회(Source/Target DB **0회**)".
    - PREPARING 중이면 status=PREPARING 빈 응답 → 폴링 가능(:920).
      ※ 이번에 493bf7b 로 넣은 "스트림 prepare PREPARING 폴링"이 여기에 대응한다.
  · services/exact_diff/store.py:425 default_exact_diff_store(persist)
    - run_id 별 저장. 공식 실행(persist=True)은 **파일 영속**, test-only 만 in-memory.
    - 테이블별로 run_id 가 다르므로 5,000개 테이블도 분리 저장 가능.
  · services/exact_diff/reimport_job — fingerprint→job 매핑(비동기 스트리밍 job).
    다만 이 매핑은 프로세스 메모리라 서버 재기동 시 소멸
    → 이미 알려진 'PK index 를 찾을 수 없습니다' 현상과 동일. 테이블 단위로 확장해도 같은 제약.

[그대로 재사용 가능 — 클라이언트]
  · _mvPkLoadPage(uid, run_id, key_col, scopeCols, scopeVals, page, ...)
    → 전역 상태를 안 읽고 **인자만으로** 동작. 테이블별 uid 만 다르게 주면 그대로 사용 가능.
  · window['_mvPkGo_'+uid] 패턴(:16474) — uid 별 네임스페이스라 테이블 다중화에 적합.
  · 공통 요약행 '재이관 PK' 셀은 이미 셀 ID 주입 지원(grid_helpers.py:960 pkCellId 인자,
    개별은 'mvPkSummaryCell' 사용) → 일괄 행마다 고유 ID 를 주면 셀 갱신 재사용 가능.

[재사용 불가 — 신규 필요(3가지, 여기가 실제 구현 지점)]
  (a) 전역 단일 상태 → 테이블별 맵
      ui/tabler_renderer.py:16481  var st = window._mvPkState = window._mvPkState || {};
      한 테이블 전용. 일괄에는 _mvPkState[target_table] 형태의 키 분리가 필요.
      (planFp 기반 폐기 로직 :16486 도 테이블별로 나뉘어야 함)
  (b) prepare payload 를 만들 재료가 일괄에 없다  ← **가장 큰 갭**
      ui/tabler_renderer.py:16522 _mvPkPayload(r) 가 요구하는 것:
        - parse_result      ← _analyzeData (개별 화면 전역)
        - src_conn/tgt_conn ← _mvScopePayload (개별 화면 전역)
        - source_count/target_count ← _lastCountResult (개별 화면 전역)
        - gb_cols/sum_cols  ← _execPlanRun._execEvidence (개별 화면 전역)
        - plan_fingerprint / selection_fingerprint ← _execPlanRun (개별 화면 전역)
      일괄 저장 row 에는 이 중 **어느 것도 없다**(4번의 스키마 참조).
      → 클릭 시점에 payload 를 재구성할 **서버측 어댑터**가 필요:
         · migration_sql : policy_target_table_config(검증대상 등록 row, validation_target_id)에서 조회
                           — run-wrapper 가 이미 여기서 SQL 을 읽는다
                             (column_candidate_gen_route.py:459 resolve_execution_items)
         · 접속정보     : 화면의 원본/목적 프로필(일괄 실행과 동일 경로,
                          batch_single_core_wrapper.py:106 _resolve_conn 재사용 가능)
         · parse_result : 클릭 시 analyze 1회 재실행 (또는 실행 시점 snapshot 을 별도 저장)
         · GB/SUM       : 등록 plan(stats_validation_plan_service) 또는
                          저장된 effective_selection(batch_single_core_wrapper.py:292) 에서 복원
  (c) 지문(plan_fingerprint/selection_fingerprint) 재현
      prepare 는 이 지문으로 run/store 를 분리한다(agg_diff_route.py:775).
      일괄 결과에는 effective_selection 요약만 남아 있어, 같은 지문을 재현하거나
      '일괄 전용 지문 규약'을 정해야 한다(아무 값이나 넣으면 매 클릭마다 새 run 생성).

  ⇒ 질문 5 답: **서버 API(prepare/pk-records)와 store, 클라 _mvPkLoadPage 는 그대로 재사용 가능.
     막히는 지점은 (a) 전역 단일 상태, (b) payload 재료 부재, (c) 지문 재현 — 3곳.**

■ 6. 결론 — 구현 필요 여부
────────────────────────────────────────────────────────────────────────
  현재 구조 유무 : **없음**(테이블 단위 lazy prepare 미존재. prepare 자체가 일괄 경로에 미배선)
  긍정적인 점    : 원하는 동작의 절반은 이미 만족한다 —
                   일괄 실행은 요약만 계산하고(무거운 조사 0회), 목록/상세 화면도 분리돼 있으며,
                   클릭 시 DB 재접속도 0이다. 없는 것은 "클릭했을 때 그 테이블만 조사하는" 나머지 절반이다.
  재사용 가능    : /agg-diff/prepare, /agg-diff/pk-records(테이블 무관·DB 0회),
                   exact_diff store(run_id 별·영속), reimport_job(중복 prepare 방지),
                   _mvPkLoadPage/_mvPkGo_<uid>, 요약행 '재이관 PK' 셀(이미 존재)
  신규 필요      : ① _mvPkState 테이블별 키 분리
                   ② 서버측 'batch row → prepare 입력' 어댑터(SQL·접속·parse_result·GB/SUM 복원)
                   ③ 일괄용 지문(plan/selection fingerprint) 규약
  기존 계획과 일치: docs/PHASE_4_D8_BATCH_INDIVIDUAL_PARITY_PLAN.md:57 이 이미 이 항목을
                   "HOLD(후속 adapter)"로 남겨 둠 — 이번 진단은 그 HOLD 항목의 구체화에 해당한다.
  같이 볼 것     : 상세 조사와 별개로, 일괄 실행 자체가 row 간 병렬 0 + 동기 단일 HTTP 다.
                   5,000 테이블에서는 lazy prepare 를 붙이기 전에 이쪽이 먼저 문제가 된다
                   (docs/BATCH_VALIDATION_SPEED_IMPROVEMENT_DESIGN.md 의 B1 항목).
